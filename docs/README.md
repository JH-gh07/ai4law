# DataComplyFlow 文档中心

本文件是仓库文档的唯一总入口。阅读顺序是：先看现行工程边界，再看阶段治理计划，最后按需要查阅事实审计和历史材料。

## 文档分层

| 目录 | 角色 | 是否约束当前开发 | 使用方式 |
|---|---|---:|---|
| `engineering/` | 现行工程规范与活动架构 | 是 | 开发、评审和测试首先查阅 |
| `governance/` | 仓库规范化计划、批次状态、来源与软著治理 | 是 | 每批治理前登记，完成后更新证据 |
| `handoff/` | 事实审计、Benchmark 分析和最新实施记录 | 有条件 | 属于有时间边界的事实材料，以当前代码和测试覆盖旧结论 |
| `archive/` | 已被替代的方案、旧设计和历史记录 | 否 | 只用于追溯，不可作为实现依据或运行依赖 |

## 推荐阅读路径

1. [`engineering/DataComplyFlow_活动架构与权威源.md`](engineering/DataComplyFlow_活动架构与权威源.md)：确认当前入口、配置、知识源和兼容边界。
2. [`engineering/DataComplyFlow_AI辅助开发与代码规范.md`](engineering/DataComplyFlow_AI辅助开发与代码规范.md)：确认命名、API、Schema、RAG、测试和 AI 辅助开发要求。
3. [`governance/DataComplyFlow_仓库规范化分阶段治理计划.md`](governance/DataComplyFlow_仓库规范化分阶段治理计划.md)：确认当前治理批次、验收和暂停条件。
4. [`handoff/README.md`](handoff/README.md)：按时效选择事实审计、评测分析或实施报告。

## 冲突处理

事实优先级固定为：当前可运行代码和测试结果 → 当前配置与真实调用链 → 现行工程规范 → 有日期的事实审计与实施报告 → 归档材料。发现冲突时，不得用旧文档覆盖当前代码；应在治理计划中登记差异，并通过独立批次修复代码或更新文档。

## 文档生命周期

- `active`：仍约束当前开发，必须随相关代码一同更新；
- `snapshot`：保留审计时点，不应被理解为实时状态；
- `superseded`：已有更高优先级文档替代，移入 `archive/`；
- `unknown`：来源或用途未确认，先隔离和标记，不直接删除；
- `delete`：仅用于字节重复、无引用生成物或已确认无追溯价值的内容。

本轮没有把业务知识、法规材料、Prompt、运行 Trace 或研究论文纳入文档清理范围。
