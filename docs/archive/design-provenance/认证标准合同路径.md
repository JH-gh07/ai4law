# 1. 路径诊断 Agent：解决“标准合同 / 认证 / 豁免 / 安全评估”分流不准的问题

## 当前问题

当前 CN SCC 更像“标准合同报告生成器”，不是完整的“中国数据出境路径诊断器”。它主要依赖 `pii_count`、`spi_count`、`has_scc_draft` 等少数字段触发 4 条硬编码规则；而预期测试案例里，实际需要判断：

1. 是否适用标准合同；
2. 是否可能适用认证路径；
3. 是否满足人力资源管理豁免；
4. 是否因规模、重要数据、CIIO、敏感个人信息触发安全评估；
5. 是否存在“用户以为是认证，其实不是中国法下的数据出境认证”的概念混淆。

例如测试案例三要求系统区分“欧盟业务准入认证”和“中国个人信息出境认证”，并指出 EuroCert 不是中国网信部门认可的专业认证机构。 当前 CN SCC 规则显然覆盖不到这个复杂判断。

## 适合加的 Agent

**路径诊断 Agent / Path Decision Agent**

它不负责直接生成报告，而是先做“路径分流 + 风险解释”。

## 预期处理逻辑

输入：

```text
企业基础信息
是否 CIIO
是否涉及重要数据
个人信息人数
敏感个人信息人数
出境目的
合法性基础
接收方类型
行业领域
是否人力资源管理
是否认证机构
是否已有标准合同 / 认证材料 / 豁免材料
```

处理：

```text
Step 1：结构化读取用户输入
Step 2：调用规则表做硬门槛判断
        - CIIO / 重要数据 / 人数阈值 / 敏感个人信息阈值
Step 3：判断是否存在豁免场景
        - 人力资源管理
        - 合同订立或履行所必需
        - 法定义务
        - 紧急保护自然人生命健康财产安全
Step 4：判断是否误选路径
        - 用户选择“认证”，但接收方只是业务认证机构
        - 用户选择“标准合同”，但实际可能触发安全评估
        - 用户声称“豁免”，但制度证据不足
Step 5：输出路径建议
        - 主路径
        - 备选路径
        - 是否建议继续生成 PIPIA
        - 当前路径不确定的原因
        - 需要补充的问题
```

输出示例：

```json
{
  "recommended_path": "standard_contract",
  "alternative_path": "exemption_hr_management",
  "confidence": 0.72,
  "blocking_issues": [
    "员工手册未明确数据出境条款",
    "集体合同未专门提及数据出境"
  ],
  "next_questions": [
    "是否已通过民主程序制定包含数据出境条款的劳动规章制度？",
    "是否能提供最新版集体合同？"
  ]
}
```

## 加了之后的效果

这个 Agent 能解决当前最大缺口：**系统不能像合规律师一样先判断“该走哪条路”**。预期案例二就是典型例子：系统要提示“可能符合人力资源管理豁免，但证据不足，建议审慎完成 PIPIA，并可选择标准合同路径增强确定性”。 这不是简单阈值规则能完成的。

# 2. 数据字段识别 Agent：解决“个人信息 / 敏感个人信息 / 匿名化 / 去标识化”判断不细的问题

## 当前问题

当前 CN SCC 输入只有 `pii_count`、`spi_count`，缺少字段级识别能力。可预期案例要求系统能识别：

1. `Hashed_Device_ID` 虽然被用户标成“非个人信息”，但可能存在重标识化风险；
2. `Product_Category_Preference` 包含“母婴用品”“医疗保健品”等标签，可能推断敏感状况；
3. 薪酬、奖金属于敏感财产信息；
4. 商户联系人姓名、邮箱是否属于个人信息；
5. 企业注册号是否只是企业信息，是否可能和联系人关联后形成个人信息。

预期输出明确要求系统根据 Excel 清单统计人数，并高亮 Hashed_Device_ID 重标识化风险、偏好标签可能被认定为敏感个人信息。

## 适合加的 Agent

**数据字段分类 Agent / Data Classification Agent**

它负责字段级推理，不直接替代规则。

## 预期处理逻辑

输入：

```text
字段名
字段描述
样例值
用户标注：是否个人信息 / 是否敏感个人信息
处理方式：明文、哈希、脱敏、匿名化、聚合
业务用途
关联字段
```

处理：

```text
Step 1：字段语义识别
        - Name / Email / Phone / Device ID / Salary / Health / Location 等

Step 2：结合业务上下文判断
        - 营销推荐
        - 员工管理
        - 支付认证
        - 跨境分析

Step 3：识别用户误标
        - 用户标“非个人信息”，但字段可能可识别自然人
        - 用户标“一般个人信息”，但字段可能属于敏感个人信息
        - 用户声称“匿名化”，但只是哈希或去标识化

Step 4：判断证据是否充分
        - 是否有哈希算法说明
        - 是否有盐值管理说明
        - 是否有重标识化风险评估
        - 是否有字段最小化说明

Step 5：输出字段级风险
```

输出：

```json
{
  "field": "Hashed_Device_ID",
  "user_claim": "not_personal_information",
  "agent_judgment": "potential_personal_information",
  "risk": "MEDIUM",
  "reason": "哈希设备ID仍可能通过碰撞、关联分析或字典攻击实现重识别",
  "required_evidence": [
    "哈希算法说明",
    "是否加盐",
    "碰撞风险分析",
    "重标识化测试报告"
  ]
}
```

## 加了之后的效果

这部分非常适合 Agent，因为字段语义和敏感性判断不是纯规则问题。规则能识别 `salary`、`phone`，但很难判断“母婴用品偏好 + 医疗保健品偏好 + 高价值会员标签”组合后是否会推断敏感状态。Agent 能做**上下文推理 + 用户误标纠正 + 风险解释**。

# 3. 合法性基础审查 Agent：解决“用户填了合法性依据，但论证站不住”的问题

## 当前问题

当前系统更关注路径和合同是否存在，但预期案例里大量风险来自“合法性基础论证不充分”：

1. 用户说“个性化服务是履行合同所必需”，但这可能过宽；
2. 用户说“欧盟认证要求是法定义务”，但这是欧盟法要求，是否能作为中国法下合法性基础存在争议；
3. 用户说“员工人力资源管理所必需”，但员工手册和集体合同证据不足；
4. 用户说“已取得同意”，但没有完整批量同意记录。

测试案例三明确要求系统质疑“欧盟认证要求”作为中国法下“法定义务”的合法性，并建议强化“合同所必需”或“个人同意”的论证。

## 适合加的 Agent

**合法性基础审查 Agent / Legal Basis Review Agent**

它负责判断“用户选择的合法性基础是否与事实匹配”。

## 预期处理逻辑

输入：

```text
出境目的
合法性基础选择
用户论证文本
合同文件摘要
隐私政策摘要
员工手册摘要
集体合同摘要
同意记录摘要
```

处理：

```text
Step 1：识别用户选择的合法性基础
        - 同意
        - 合同所必需
        - 人力资源管理所必需
        - 法定义务
        - 其他

Step 2：建立合法性基础所需证据清单
        例如：
        - 同意：告知内容、接收方名称、出境目的、撤回机制、记录
        - 合同所必需：合同主给付义务、必要性、不可替代性
        - HR 管理：员工手册、集体合同、民主程序、确需性
        - 法定义务：具体法律条款、适用主体、强制性要求

Step 3：对照用户材料
        - 有证据
        - 部分证据
        - 仅用户声称
        - 明显不匹配

Step 4：输出合法性强度
        - 可支持
        - 勉强支持
        - 证据不足
        - 不建议使用
```

输出：

```json
{
  "legal_basis": "performance_of_contract",
  "status": "weak",
  "reason": "个性化营销并非跨境电商服务合同的核心必要履行内容，可能被认为属于提升体验或商业营销目的",
  "recommended_adjustment": "补充单独同意，并明确境外接收方名称、所在地、处理目的和联系方式"
}
```

## 加了之后的效果

这能显著提升报告质量。当前 LLM 可以写“合法性、正当性、必要性分析”，但如果前面没有 Agent 先做结构化审查，生成内容容易变成泛泛而谈。合法性 Agent 的价值在于：**把用户声称转化为可审查的证据强度**。

# 4. 法律文件审查 Agent：解决“只知道有没有合同，不知道合同缺什么”的问题

## 当前问题

当前 CN SCC 只看 `has_scc_draft`。如果没有合同，就提示缺失；如果有合同，系统并不会真正审查合同条款。文档中也写到 CN SCC 没有条款比对、没有附录审查、没有事实/问题/证据分层，而 EU SCC 才有条款比对和 Annex 审查。

但预期版本要求系统能指出：

1. 缺少“境外接收方所在国家/地区法律政策变化应对”条款；
2. 未约定接收方定期提供安全审计报告；
3. 德国法和柏林法院管辖对中国个人信息主体维权构成障碍；
4. 英文协议未提供经认证中文译本；
5. 协议没有保障中国个人信息主体权益。

## 适合加的 Agent

**法律文件审查 Agent / Contract Review Agent**

这个 Agent 应该类似 EU SCC 的条款审查，但面向中国标准合同、认证服务合同、DPA、隐私政策、员工手册。

## 预期处理逻辑

输入：

```text
上传合同文本
标准合同模板条款库
预期条款清单
合同类型：标准合同 / DPA / 认证服务合同 / 员工手册 / 集体合同
接收方国家
路径类型
```

处理：

```text
Step 1：文档类型识别
        - 标准合同
        - 数据处理协议
        - 认证服务合同
        - 员工手册
        - 集体合同
        - 隐私政策

Step 2：条款切分
        - 主体信息
        - 出境目的
        - 数据范围
        - 接收方义务
        - 安全措施
        - 转委托 / 再传输
        - 个人权利响应
        - 法律政策变化应对
        - 审计和监督
        - 争议解决
        - 终止与返还删除

Step 3：对照模板要求
        - 缺失
        - 表述过泛
        - 与中国强制性规则冲突
        - 管辖条款不利于个人信息主体
        - 证据不足

Step 4：生成 findings
```

输出：

```json
{
  "finding_id": "CN-SCC-CONTRACT-003",
  "location": "数据保护附件 第12条",
  "issue": "争议解决条款仅约定德国法和柏林法院",
  "severity": "HIGH",
  "risk_analysis": "可能增加中国个人信息主体维权成本，并削弱中国法强制性保护要求的可执行性",
  "suggested_text": "双方确认本协议的履行不得排除中国个人信息保护相关法律法规的强制性要求..."
}
```

## 加了之后的效果

这是最值得加 Agent 的位置之一。因为当前 CN SCC 只能做“有无合同”的判断，无法做到“合同合不合格”。预期报告中要求明确列出法律文件缺失核心条款、法律适用和管辖风险。 这必须靠文档理解 + 条款对照 + 风险解释，单靠 4 条硬编码规则不够。

# 5. 证据核验 Agent：解决“用户声称有证据，但系统不知道证据够不够”的问题

## 当前问题

预期功能强调材料附件准备、同意记录、制度文件、合同条款、技术验证报告等。功能说明也写到系统应列出信息缺失项、依赖假设和待人工核验内容。

当前 EU SCC 有 evidence_builder，但 CN SCC 没有完整的 Fact / Issue / Evidence 分层。文档里明确对比：CN SCC “事实/问题/证据无分层”，EU SCC 有 fact_builder、issue_builder、evidence_builder。

## 适合加的 Agent

**证据核验 Agent / Evidence Verification Agent**

它不是验证材料真伪，而是判断“材料是否足以支撑报告中的结论”。

## 预期处理逻辑

输入：

```text
用户主张
上传材料列表
材料摘要
报告中要生成的正向结论
法规依据
```

处理：

```text
Step 1：抽取 claim
        - 已取得单独同意
        - 接收方具备安全能力
        - 数据已匿名化
        - 已履行告知义务
        - 已具备内部制度
        - 认证机构合法有效

Step 2：为每个 claim 匹配证据
        - 合同
        - 隐私政策
        - 同意日志
        - 安全认证
        - 审计报告
        - 制度文件
        - 技术说明

Step 3：判断证据成熟度
        - user_claim_only
        - partial_evidence
        - documented_evidence
        - verified_evidence

Step 4：决定报告写法
        - 可以肯定表述
        - 只能谨慎表述
        - 必须标记为缺失
        - 必须作为高风险项
```

输出：

```json
{
  "claim": "已获得50万目标用户单独同意",
  "evidence_status": "partial_evidence",
  "supporting_material": "用户同意记录查询截图",
  "gap": "无法覆盖全部目标用户，缺少批量同意记录清单或统计报告",
  "report_strategy": "不得写成已充分取得全部用户同意，应写为用户提供了部分样本证据，完整性仍需核验"
}
```

## 加了之后的效果

它能解决一个实际产品问题：**报告不能把用户声称直接写成合规事实**。例如测试案例一中，用户只有同意时间戳截图，但无法提供覆盖 50 万目标用户的批量同意记录，预期输出要求指出同意记录不完整。 证据核验 Agent 可以把“用户输入”转化为“可支撑程度”。

# 6. RAG 检索规划 Agent：解决“检索词太粗、法规召回不稳定”的问题

## 当前问题

当前 CN SCC 的 RAG 是半动态，只拼了 `purpose + country`；EU SCC 的 RAG 更完整，会拼 GDPR Article 46、Schrems II、module、role 等。 这说明 CN SCC 的法规检索还不够精细。

预期功能要求输出依据覆盖法律、部门规章、国家标准、官方指南。Reference 库也包含《个人信息出境标准合同办法》《促进和规范数据跨境流动规定》《个人信息出境认证办法》《个人信息保护认证实施规则》、GB/T 39335、GB/T 46068 等。

## 适合加的 Agent

**法规检索规划 Agent / Legal Retrieval Planner Agent**

它不直接生成报告，而是根据 issue 规划应该检索哪些法规和标准。

## 预期处理逻辑

输入：

```text
路径类型
issue 类型
行业
国家/地区
数据类型
风险点
```

处理：

```text
Step 1：按 issue 分类
        - 路径适用
        - 告知同意
        - 敏感个人信息
        - 重要数据
        - 认证机构资质
        - 合同条款
        - 境外接收方安全能力
        - 去标识化

Step 2：为每类 issue 生成检索 query
        - 法律条文 query
        - 指南模板 query
        - 国家标准 query
        - 行业规定 query

Step 3：控制 RAG 结果
        - 必须包含上位法
        - 必须包含直接操作依据
        - 必须包含模板依据
        - 技术问题补充国家标准
```

输出：

```json
{
  "issue": "hashed_device_id_reidentification",
  "queries": [
    "个人信息 去标识化 重标识化 风险 GB/T 42460",
    "个人信息安全规范 设备标识符 个人信息",
    "个人信息保护影响评估 去标识化 效果评估"
  ],
  "required_source_types": [
    "national_standard",
    "personal_information_law",
    "official_guide"
  ]
}
```

## 加了之后的效果

它能提升报告“引用依据”的准确性。现在 CN SCC 的 RAG 很容易只召回泛泛法规，不能精准支撑具体风险点。加检索规划 Agent 后，每个 issue 都能挂到对应条文、指南或标准上。

# 7. 报告生成审稿 Agent：解决“LLM生成内容可能泛化、跳结论、引用不稳”的问题

## 当前问题

当前 CN SCC 是 LLM 直接生成 4 章；EU SCC 是 LLM + placeholder 兜底。文档中写到 `generate_chapter` 会组装 prompt、context 和 citations，并进行引用后处理。 但这仍然不能保证：

1. 结论是否与前面的 facts 一致；
2. 是否把“用户声称”写成“系统确认”；
3. 是否遗漏高风险项；
4. 是否引用了不相关法规；
5. 是否模板结构完整；
6. 是否把“认证路径”和“业务认证”混淆。

## 适合加的 Agent

**报告审稿 Agent / Report Review Agent**

它在报告生成之后运行，专门做一致性、完整性、合规表达审查。

## 预期处理逻辑

输入：

```text
生成报告全文
facts
issues
evidence
retrieved regulations
路径诊断结果
风险评级
模板要求
```

处理：

```text
Step 1：模板完整性检查
        - 是否覆盖 PIPIA 模板要求
        - 是否包含整体情况、接收方、影响评估、结论

Step 2：事实一致性检查
        - 是否引入用户未提供事实
        - 是否遗漏用户明确提供的风险点
        - 是否把不确定项写成确定结论

Step 3：风险覆盖检查
        - 每个 HIGH/BLOCKER issue 是否进入报告
        - 每个缺失材料是否进入待补充项
        - 风险评级是否和 issue 严重度一致

Step 4：引用检查
        - 每个法律判断是否有法规依据
        - 技术判断是否有标准依据
        - 模板格式是否有指南依据

Step 5：生成修复建议或自动修复
```

输出：

```json
{
  "review_status": "needs_repair",
  "problems": [
    {
      "type": "unsupported_positive_claim",
      "text": "企业已取得全部用户同意",
      "reason": "证据仅为单张截图，不能证明覆盖全部50万用户",
      "repair": "改为：企业提供了部分同意记录样本，但完整性仍需进一步核验"
    }
  ]
}
```

## 加了之后的效果

这能解决报告产品最常见的问题：**生成出来像报告，但证据链不严谨**。功能说明中本来就要求输出“当前草案的已知合规差距与待定项”，并提示人工核验、附件准备和迭代优化。 审稿 Agent 可以把这件事系统化。

# 8. 用户追问 Agent：解决“一次填表不够，系统不知道该问什么”的问题

## 当前问题

预期案例里有很多“不确定但关键”的信息：

1. 是否完整取得 50 万用户同意；
2. 哈希算法是否足以避免重识别；
3. 员工手册和集体合同是否依法制定；
4. EuroCert 是否是中国认可的认证机构；
5. 全球隐私政策是否可查；
6. 英文协议是否有中文译本；
7. 接收方安全审计报告是否存在。

当前系统多数情况下只能生成“请补充材料”，但不能根据当前路径动态追问最关键的几个问题。

## 适合加的 Agent

**动态追问 Agent / Clarification Agent**

它的目标不是让用户填更多废话，而是最小化追问，问“影响路径判断和风险评级”的问题。

## 预期处理逻辑

输入：

```text
当前 facts
missing_materials
blocking issues
path confidence
用户已上传材料
```

处理：

```text
Step 1：找出影响结论的缺口
Step 2：按优先级排序
        - 会改变路径的优先
        - 会改变风险等级的优先
        - 会影响报告是否可备案的优先
Step 3：合并重复问题
Step 4：生成 3-5 个关键追问
```

输出：

```json
{
  "questions": [
    {
      "priority": "HIGH",
      "question": "是否能提供覆盖全部目标用户的单独同意记录清单或统计报告？",
      "why": "该问题直接影响告知同意义务是否成立"
    },
    {
      "priority": "HIGH",
      "question": "员工手册或集体合同是否明确写入个人信息出境目的、接收方和数据范围？",
      "why": "该问题直接影响是否可以主张人力资源管理豁免"
    }
  ]
}
```

## 加了之后的效果

这个 Agent 对前端体验很重要。它能把“泛泛补充材料”变成“下一步必须回答什么”。尤其对比赛项目展示来说，动态追问会让系统显得更像专业合规助手，而不是静态表单生成器。

# 9. Trace / 可解释 Agent：解决“为什么得出这个结论”展示不足的问题

## 当前问题

当前只有 EU SCC 有 TraceRecorder，CN SCC 没有。文档中明确写到 EU SCC 记录 `rule_engine_result / facts_built / retrieval_hits / issues_built / evidence_built / context_pack_built / chapters_generated / consistency_issues / alignment_issues` 等事件。

但是对于用户来说，仅有后端 JSON Trace 不够。需要把 Trace 转换成“可读解释”。

## 适合加的 Agent

**可解释链路 Agent / Explanation Agent**

它将系统内部 trace、facts、issues、evidence 转换成用户可理解的“判断路径说明”。

## 预期处理逻辑

输入：

```text
trace events
facts
issues
evidence
RAG命中法规
最终报告结论
```

处理：

```text
Step 1：提取关键判断节点
Step 2：按时间顺序重组
Step 3：把技术字段翻译为业务语言
Step 4：标出每个结论的来源
Step 5：生成“生成逻辑说明”
```

输出：

```text
本次系统先根据出境人数和敏感个人信息规模判断未触发安全评估门槛；
随后发现接收方为境外子公司，适合进入标准合同路径；
但合同附件缺少法律政策变化应对条款，且同意记录证据不足；
因此系统将整体风险评为中等偏高，并建议整改后再备案。
```

## 加了之后的效果

它直接对应预期交付物中的《生成草案的逻辑与合规性说明》。功能说明要求系统说明输入摘要、遵循模板与规范、核心生成逻辑、关键判断与合规化处理、已知差距和后续步骤。 这个 Agent 可以把“内部流程”转成“用户看得懂的理由链”。

# 10. 优先级排序：不是所有地方都要先加

按实际收益排序，我建议这样加：

| 优先级 | Agent          | 解决的核心问题                 | 是否值得优先做 |
| --- | -------------- | ----------------------- | ------- |
| P0  | 路径诊断 Agent     | 标准合同 / 认证 / 豁免 / 安全评估分流 | 必须做     |
| P0  | 数据字段识别 Agent   | 敏感信息、去标识化、误标识别          | 必须做     |
| P0  | 法律文件审查 Agent   | 合同有无变成合同是否合格            | 必须做     |
| P1  | 证据核验 Agent     | 用户声称不能直接写成合规事实          | 很值得     |
| P1  | 合法性基础审查 Agent  | 合法性、必要性论证不再泛泛而谈         | 很值得     |
| P1  | 报告审稿 Agent     | 修复幻觉、遗漏、不一致             | 很值得     |
| P2  | RAG 检索规划 Agent | 提升法规引用准确性               | 建议做     |
| P2  | 动态追问 Agent     | 提升交互体验和材料补全效率           | 建议做     |
| P2  | 可解释链路 Agent    | 支撑生成逻辑说明和前端展示           | 建议做     |

# 11. 推荐的最终 Agent 协作架构

不要做成一个“大而全 Agent”。建议做成“规则引擎主控 + 多 Agent 专项协作”。

```text
用户输入 / 上传材料
        │
        ▼
[资料解析层]
表单解析器 + 文件解析器 + Excel字段解析器
        │
        ▼
[路径诊断 Agent]
判断：安全评估 / 标准合同 / 认证 / 豁免 / 不确定
        │
        ▼
[专项审查 Agent 组]
├─ 数据字段识别 Agent
├─ 合法性基础审查 Agent
├─ 法律文件审查 Agent
├─ 接收方能力审查 Agent
├─ 证据核验 Agent
        │
        ▼
[规则引擎]
硬门槛、阈值、强制条款、风险评级
        │
        ▼
[Issue / Evidence 构建]
facts → issues → evidence → risk summary
        │
        ▼
[RAG 检索规划 Agent]
按 issue 检索法规、指南、标准、模板
        │
        ▼
[报告生成 Agent]
生成 PIPIA 草案 + 生成逻辑说明
        │
        ▼
[报告审稿 Agent]
检查：事实一致性、证据支撑、风险遗漏、引用准确性
        │
        ▼
[输出]
PIPIA 草案
生成逻辑说明
风险清单
材料补充清单
批注版 DOCX
Trace / 可解释链路
```

---

# 12. 一句话结论

这个功能最需要 Agent 的地方，不是替代确定性规则，而是补齐当前 CN SCC 的“判断能力”：**路径分流、字段识别、合法性论证、合同条款审查、证据核验、报告审稿**。这些地方本质上都不是单一规则判断，而是“多材料、多法规、多事实之间的推理与解释”，加 Agent 后能明显提升系统从“表单报告生成器”到“合规审查助手”的质量。
