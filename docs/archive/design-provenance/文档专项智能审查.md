你的问题本质不是“这个模块有没有实现”，而是：

**当前实现的文档专项审查模块，是否真的能达到预期中的“像合规律师一样审查隐私政策、标准合同、DPA、保密协议，并输出条款级法律风险和修改文本”的效果。**

结论先说：**当前实现的流程架构已经明显强于前面的 CN SCC 模块，属于比较完整的审查流水线；但它距离预期版本仍有差距，主要差在“场景事实识别、隐含出境风险判断、标准合同强制条款对比、跨文档一致性、法规依据精准性、建议文本质量”这几块。**

---

# 1. 预期版本到底要求做到什么

预期的文档专项审查模块不是普通文档总结，而是要审查所有与数据收集、流转有关的法律文件，包括数据处理协议、数据出境标准合同、云服务协议中的数据处理附件、数据安全与保密协议、隐私政策、企业内部制度等。系统输出应是《数据出境合同（法律文件）合规审查报告》，并且报告要包含文件概要、总体合规评级、条款级发现、定位、原文引用、问题类型、风险分析、法规/标准依据、修改建议或新增条款草案。

也就是说，预期版本有几个关键能力：

1. **能看懂文档类型**：隐私政策、SCC、DPA、保密协议、云服务协议附件。
2. **能定位条款问题**：文件、章节、页码、条款号。
3. **能识别缺失项**：不是只审查已有条款，还要发现“该有但没有”的条款。
4. **能发现隐含风险**：比如协议没写出境，但背景场景实际涉及海外服务器。
5. **能给法律依据**：不是泛泛说不合规，要挂到具体法律、监管要求或标准。
6. **能给可替换文本**：不是只说“建议完善”，而是给可直接修改的条款草案。

# 2. 当前实际实现流程是什么

当前实现已经做成了一个 **8 阶段增强流水线**，核心路径是 `backend/services/review_service/`，整体采用 **DSL 规则引擎 + LLM 深度审查 + 专项审查器** 三层架构，支持隐私政策、标准合同、DPA、其他协议等文档类型，覆盖 23 种条款类型，并输出 9 节专业审查报告。

当前流程可以概括为：

```text
用户上传文档
  ↓
Stage 0 文档理解：解析 DOCX/PDF/文本，识别文档类型，提取场景
  ↓
Stage 1 条款切分：按条、章、节、附录切成 Clause
  ↓
Stage 2 条款分类：按关键词 + LLM 兜底归入 23 类 ClauseType
  ↓
Stage 3 缺失项检测：根据文档类型和场景判断是否缺条款
  ↓
Stage 4 条款审查：DSL 规则 + 标准条款差异比对 + 专项审查器 + LLM
  ↓
Stage 5 跨文档一致性检查
  ↓
Stage 6 聚合评分：去重、排序、风险评分、总体评级
  ↓
Stage 7 报告渲染：DOCX 报告 + 批注版 DOCX
```

从当前实现看，它已经不是简单 LLM 审查，而是有明确的结构化数据模型：`Clause`、`ClassifiedClause`、`ReviewIssue`、`MissingItem`、`AggregatedReview`。其中 `ReviewIssue` 已经包含条款位置、原文摘录、问题类型、风险分析、法规引用、建议修改、置信度等字段，和预期报告结构基本对齐。

# 3. 当前已经接近预期的部分

## 3.1 文档解析与条款切分基本符合预期

预期要求系统能审查 DOCX、PDF、隐私政策截图/文本、合同模板等文件。当前实现里 `StructuredDocumentParser` 支持 DOCX 段落和表格、PDF 分页、纯文本，并能提取 SCC 附件字段。这个方向是对的。

这意味着它已经具备“把文档转成可审查对象”的基础能力，不是把整篇文档直接丢给 LLM。

## 3.2 缺失项检测已经有雏形

预期测试案例经常要求发现“全局性缺失”，比如缺少数据出境条款、缺少审计权、缺少境外保存地点、缺少再转移限制、缺少个人信息主体权利保障路径。当前实现有 `MissingItemChecker`，能根据文档类型的 required clause types 和场景条件动态增加必需条款。

这个和预期是匹配的。

## 3.3 三层审查架构方向正确

当前实现不是单纯 LLM，而是：

```text
DSL 规则
+ 标准条款差异比对
+ 专项审查器
+ LLM 深度审查
```

文档里也明确说明，三层架构的设计目标是：LLM 不可用时仍能规则兜底，同时用规则引擎提供确定性合规检查。

这对法律文档审查很重要，因为“标准合同正文被修改”“责任限额削弱主体权利”“香港法院管辖”等问题不能完全靠自由生成，需要确定性规则兜底。

## 3.4 输出结构比预期更完整

预期报告主要是文件概要、总体评级、条款级发现、法规依据、修改建议。当前实现的 `ReviewReportRenderer` 输出 9 节，包含执行摘要、审查概况、文档画像、整体风险、完整性检查、逐条问题、整改路线图、法规依据、审查边界与置信度说明，还能生成 DOCX 和批注版 DOCX。

从“报告结构”看，当前实现甚至比预期更完整。

---

# 4. 核心差距一：隐含场景识别还不一定能达到预期

这是最大差距。

预期案例一要求系统发现：协议本身是境内委托处理协议，但乙方为跨国企业，运维平台服务器位于海外，因此**虽然协议没有明写数据出境，实际业务可能涉及数据出境**。预期输出要求将其评级为高风险，并指出协议未约定数据处理地理位置，若实际传输至新加坡服务器，则构成数据出境行为，需要满足《个人信息保护法》第三十八条等要求。

当前实现有 `ScenarioExtractor`，能提取公司名称、数据类别、敏感数据、跨境指标、处理目的、接收方国家，也能构建数据流图。 但问题在于：

**当前流程更像“从文档文本中提取场景”，不一定能从文档外背景推断隐含出境风险。**

例如测试案例里，“乙方服务器位于海外”有时来自用户补充背景，不一定出现在合同正文。如果当前系统只看合同正文，它可能只能看到：

```text
乙方进行数据分析与运维
数据包括师生消费记录、门禁记录、图书借阅记录
协议没有写数据出境
```

它未必能推出：

```text
乙方是跨国企业
运维平台服务器在海外
存在隐含数据出境
```

所以差距是：

| 项目     | 预期                  | 当前实现可能情况             |
| ------ | ------------------- | -------------------- |
| 隐含出境识别 | 能结合背景发现“未写出境但实际出境”  | 主要依赖文档关键词和场景抽取       |
| 外部事实依赖 | 能接受用户背景、企业资料、系统部署信息 | 当前更偏文档内事实            |
| 风险结论   | 直接上升为高风险            | 可能只标记为“缺少处理地点”或“不确定” |

这里需要补一个 **场景事实 Agent / Cross-border Scenario Agent**，专门处理“文档没写，但业务事实暗示出境”的情况。

---

# 5. 核心差距二：标准合同强制条款比对需要更硬

预期案例三要求审查《个人信息出境标准合同》时，识别附录二对标准合同核心条款的实质性修改，包括：

1. 改成香港法院管辖；
2. 境外接收方可暂缓处理个人信息主体请求；
3. 设置责任总额上限；
4. 约定其他协议优先于标准合同；
5. 技术和管理措施未填写；
6. 保存期限过长；
7. 保存地点包含美国但未评估当地法律政策影响。

这些问题不是普通“合同风险”，而是**标准合同强制性保护结构被削弱**。测试案例明确要求将这类问题评为中高风险或极高风险，并指出可能导致备案失败甚至条款无效。

当前实现已经有 `StandardClauseLocator` 和 `StandardClauseDiffer`，能通过 RAG 检索标准条款原文，并对比义务缺失、义务弱化、高风险修改。设计方向正确。

但差距在于：**当前文档写的是“通过 RAG 检索标准条款候选并相似度匹配”，这在标准合同场景下不够稳。**

标准合同不是普通知识库文本。它应该有一套**强制条款锚点库**，包括：

```text
标准合同正文第1-9条
附录一各字段
附录二不得冲突原则
争议解决可选范围
第三方受益人权利
境外接收方义务
保存期限最短必要
再转移限制
审计权和记录保存
当地法律政策影响评估
```

如果只靠 RAG 召回 + 相似度匹配，可能出现两个问题：

1. **召回不稳定**：标准条款没召回，差异比对就失效。
2. **语义比对不够强**：比如“以集团主协议为准”不一定和某一条标准条款高度相似，但法律效果是架空标准合同。

所以这里的差距不是“没有标准条款比对”，而是**标准合同场景需要从 RAG 辅助升级为确定性模板对照 + 语义弱化识别**。

# 6. 核心差距三：隐私政策审查可能还停留在条款层，缺少“告知完整性矩阵”

你截图里是华为隐私政策样例。隐私政策审查的预期不是简单看“有没有隐私政策”，而是要检查它是否完整告知：

```text
收集什么个人信息
为什么收集
如何使用
Cookie 和同类技术
如何披露/共享/转让
用户权利
儿童个人信息
跨境传输
保存期限
安全措施
联系方式
更新机制
```

功能说明明确把当前线上生效的《隐私政策》或《个人信息处理规则》纳入审查对象。

当前实现有 `PrivacyPolicyReviewer`，也有 23 种 ClauseType 分类。但差距可能在于：

**隐私政策不是只审查单个条款，而是要形成“告知义务覆盖矩阵”。**

例如：

| 告知事项   | 隐私政策是否覆盖 | 是否具体      | 是否与实际业务一致 |
| ------ | -------- | --------- | --------- |
| 处理者身份  | 有        | 具体        | 待核验       |
| 个人信息种类 | 有        | 是否过泛      | 待核验       |
| 处理目的   | 有        | 是否具体      | 待核验       |
| 第三方共享  | 有        | 是否列明具体接收方 | 可能不足      |
| 跨境传输   | 有/无      | 是否列明境外接收方 | 关键风险      |
| 用户权利   | 有        | 是否有路径     | 需审查       |
| 儿童信息   | 有        | 是否单独规则    | 需审查       |

当前条款分类可以发现某些条款类型，但未必能稳定输出这种矩阵式结论。隐私政策审查尤其需要“**覆盖性 + 具体性 + 一致性**”三层判断。

---

# 7. 核心差距四：跨文档一致性当前有模块，但预期场景要求更复杂

预期输入里不仅有单个合同，还包括公开隐私政策、内部制度、数据处理协议、标准合同、保密协议等。功能说明还明确提到企业内部制度可用于审查内外一致性。

当前实现有 `CrossDocConsistencyChecker`，这是对的。 但预期真正需要的跨文档一致性不是简单文本冲突，而是：

```text
隐私政策说不会出境
但 DPA 写明会传到香港/新加坡
=> 高风险冲突

标准合同附录一写保存期限 3 年
但云服务协议写备份保存 6 年
=> 保存期限不一致

内部制度要求 24 小时通知
但合同写“及时通知”
=> 安全事件通知时限不一致

隐私政策写关联方共享
但标准合同接收方是境外子公司
=> 接收方告知不充分

员工手册写“集团内共享”
但 DPA 写美国总部处理薪酬数据
=> 员工告知不足
```

当前文档只说明“跨文档一致性检查”，没有看到它是否已经建立这种**合规语义级一致性规则**。所以差距是：

| 层级    | 当前可能做到                       | 预期需要做到 |
| ----- | ---------------------------- | ------ |
| 文本层   | 检查关键词或字段不一致                  | 不够     |
| 条款层   | 检查同类条款冲突                     | 需要     |
| 合规语义层 | 检查“公开告知—合同安排—内部制度—实际数据流”是否一致 | 预期核心   |

---

# 8. 核心差距五：数据类型和敏感性识别还需要更强

预期案例一里，师生消费记录、门禁记录、图书借阅记录可能涉及个人信息甚至敏感个人信息。预期要求指出协议未区分数据类型，未设置差异化保护要求。

预期案例二里，“脱敏后的用户 ID”描述不清，若可逆则是去标识化个人信息，若不可逆才可能是匿名化信息，合规要求差别很大。

当前实现的 `ScenarioExtractor` 能提取数据类别和敏感数据，但这类判断不是简单关键词能解决。比如：

```text
门禁记录 → 可能推断行踪轨迹
图书借阅记录 → 可能推断思想、兴趣、健康、宗教等敏感倾向
学生心理健康数据 → 明显高敏感
脱敏用户 ID → 可能仍是个人信息
设备类型 + 浏览记录 + 停留时长 → 可能重识别
```

当前差距在于：**字段/数据类型识别需要上下文推理，而不是只靠关键词表。**

尤其是“脱敏、匿名化、去标识化”的区分，必须单独做审查。否则系统容易把用户写的“匿名化行为日志”直接当成匿名化，忽略其可能只是去标识化。

---

# 9. 核心差距六：法规依据引用需要从“有引用”提升到“引用能支撑该问题”

当前实现有 RAG Provider，也有 `CitationRelevanceChecker`。 这说明系统已经意识到法规引用不能乱挂。

但预期案例要求每个问题都要有**强相关的法规依据**。例如：

1. 数据出境合规路径 → 《个人信息保护法》第三十八条；
2. 数据出境专项合同条款 → 《数据出境安全评估办法》第九条、标准合同条款；
3. 保存期限过长 → 《个人信息保护法》第十九条、标准合同第三条第五项；
4. 安全事件通知时限模糊 → 《数据安全法》第二十九条、《网络安全法》第二十五条；
5. 格式条款不公平 → 《民法典》第四百九十七条。

预期案例里对第十四条第 3 款的责任错配问题，要求明确引用《个人信息保护法》第三十八条和《个人信息出境标准合同办法》第四条，并给出替换文本。

当前可能存在的差距是：

```text
RAG 能找到法规
≠ 每个 issue 都挂到最合适的条文
≠ 引用一定能支撑风险分析
≠ 修改建议一定对应条文要求
```

所以这里需要加强 `issue_type → legal_basis → citation → recommendation` 的绑定，而不是报告末尾堆法规依据。

---

# 10. 核心差距七：修改建议质量要更接近“可直接替换条款”

预期输出不是“建议完善数据出境条款”，而是给出具体可替换文本。比如针对责任错配条款，预期建议直接改为：

```text
甲方作为个人信息处理者，应负责根据中国法律法规要求，完成数据出境安全评估、订立标准合同或通过保护认证等合规手续。乙方应提供必要的信息与配合。未经甲方事先书面同意，乙方不得将数据向其他境外实体提供。
```

这个要求很高。

当前实现的数据模型里有 `SuggestedRevision`，报告渲染也包含“建议替换文本”。 但真正差距在于：**建议文本是否能按文档类型、条款类型、风险类型生成专业条款，而不是通用整改建议。**

例如同样是“安全事件通知模糊”，不同文档的建议应不同：

```text
隐私政策：说明发生个人信息安全事件时的通知方式和内容
DPA：约定受托方通知委托方的时限、内容、协助义务
标准合同：不得弱化境外接收方通知义务
保密协议：补充数据安全事件报告和主管部门报告配合机制
```

如果当前系统只输出统一模板，质量会低于预期。

---

# 11. 核心差距八：当前报告结构完整，但可能还缺“审查边界与不确定事实”的业务化表达

当前 9 节报告里有“审查边界与置信度说明”，这是好的。

但预期案例里经常有“不确定但必须提示”的情况：

```text
乙方是否真的使用海外服务器，需要补充确认
脱敏 ID 是否匿名化，需要技术证明
是否涉及重要数据，需要结合行业目录判断
隐私政策是否实际生效，需要确认版本
标准合同是否已备案，需要确认备案材料
```

当前模型里有 `facts_uncertain` 和 `uncertainty_rationale`，但差距在于：**是否能把不确定事实转化成用户下一步材料清单和审查结论边界。**

也就是说，报告不能只写：

```text
存在不确定性。
```

而应该写：

```text
当前结论基于“乙方服务器位于境外”的背景信息。如果该信息不成立，则数据出境风险等级可下调；如果成立，则必须补充服务器位置证明、境外接收方信息、出境路径合规材料。
```

这才符合预期的合规审查逻辑。

# 12. 总体差距表

| 模块能力   | 预期版本                       | 当前实现                                           | 差距判断                  |
| ------ | -------------------------- | ---------------------------------------------- | --------------------- |
| 文档类型覆盖 | 隐私政策、DPA、SCC、保密协议、云协议、内部制度 | 支持 privacy_policy / scc_contract / dpa / other | 基本达成，但云协议/内部制度可能还需细化  |
| 文档解析   | DOCX/PDF/文本/截图样例           | DOCX/PDF/文本为主                                  | 截图类隐私政策需要 OCR 或图像解析能力 |
| 条款切分   | 能定位章节、页码、条款号               | ClauseSegmenter 已实现                            | 基本达成                  |
| 条款分类   | 能识别多类合规条款                  | 23 种 ClauseType                                | 基本达成                  |
| 缺失项检测  | 能发现全局性缺失                   | MissingItemChecker 已实现                         | 方向正确，但依赖场景识别准确性       |
| 隐含出境识别 | 能结合背景发现未明示出境               | ScenarioExtractor 有雏形                          | 仍有明显差距                |
| 标准合同比对 | 能发现强制条款被改写/架空              | RAG 标准条款差异比对                                   | 需要更确定性的模板锚点库          |
| 隐私政策审查 | 告知义务完整性、具体性、一致性            | 有专项审查器                                         | 需补“告知完整性矩阵”           |
| 跨文档一致性 | 外部政策、内部制度、合同、实际数据流一致       | 有 CrossDocConsistencyChecker                   | 需要合规语义级规则             |
| 法规依据   | 每个问题绑定精准条文                 | 有 RAG 和引用相关性检查                                 | 需要 issue-to-law 强绑定   |
| 修改建议   | 可直接替换的条款草案                 | 有 SuggestedRevision                            | 需要按文档类型定制             |
| 风险评分   | 总体评级能反映重大法律风险              | 加权评分                                           | 基本达成，但权重需用测试案例校准      |
| 输出报告   | DOCX + 批注 + 条款清单           | DOCX + Annotated DOCX + 9节报告                   | 基本达成，甚至更完整            |

# 13. 最值得优先补的 6 个点

## 第一，补“隐含出境风险识别”

这是预期案例一和案例二的关键。不能只看文档有没有“跨境”“境外”“香港”“新加坡”等词，还要结合：

```text
乙方是否跨国公司
服务器是否境外
开发团队是否境外
云服务商是否境外
数据中心是否境外
是否远程访问境内数据
是否有境外备份
```

否则会漏掉“协议没写出境但实际出境”的最大风险。

## 第二，补“数据类型敏感性识别”

要能识别：

```text
学生心理健康数据
门禁记录
行程轨迹
支付信息
薪酬奖金
脱敏用户 ID
设备 ID
浏览记录
图书借阅记录
```

并判断它们是否属于个人信息、敏感个人信息、去标识化信息、匿名化信息。

## 第三，补“标准合同强制条款锚点库”

不要只靠 RAG 找标准条款。应建立：

```text
标准合同正文条款库
附录一字段要求库
附录二禁止冲突规则库
标准合同不得削弱规则库
争议解决合法选项库
责任限制风险规则库
主体权利保障规则库
```

这样才能稳定识别附录二不当修改。

## 第四，补“隐私政策告知矩阵”

针对你截图中的隐私政策，应输出：

```text
收集使用
Cookie
共享披露
用户权利
安全保护
儿童信息
跨境传输
保存期限
联系方式
更新机制
```

并判断每一项是否存在、是否具体、是否与其他文件一致。

## 第五，补“法规依据绑定”

每个 issue 应该强制有：

```text
issue_type
→ legal_rule_id
→ citation
→ why_applicable
→ recommended_revision_basis
```

避免报告看起来有引用，但引用和问题之间关系弱。

## 第六，补“修改文本生成规范”

不同文档类型应有不同建议模板：

```text
保密协议：审计权、处理地点、安全事件通知、数据返还销毁
DPA：委托方责任、受托方协助、再委托、跨境传输
SCC：不得冲突、主体权利、技术措施、保存期限
隐私政策：告知事项、用户权利路径、儿童信息、跨境说明
```

# 14. 一句话总结

当前实现已经完成了“文档专项智能审查”的技术骨架：**文档解析、条款切分、分类、缺失检测、三层审查、RAG、风险聚合、DOCX 和批注输出**都已经具备；但距离预期的“专业合规审查”还有差距，主要差在 **隐含出境场景推理、数据敏感性判断、标准合同强制条款精确比对、隐私政策告知矩阵、跨文档语义一致性、精准法规绑定和可直接使用的修改条款文本**。


这里适合加 Agent 的位置，不是替代当前 8 阶段流水线，而是补在**规则、关键词、普通 RAG 不够稳定的地方**。

当前文档专项审查模块已经有比较完整的工程骨架：文档解析、条款切分、条款分类、缺失项检测、DSL 规则、标准条款差异比对、专项审查器、LLM 审查、跨文档一致性、风险聚合和 DOCX/批注输出。也就是说，现在缺的不是“流程”，而是**复杂合规判断能力**。当前模块定位为“DSL 规则引擎 + LLM 深度审查 + 专项审查器”的 8 阶段审查流水线，覆盖隐私政策、SCC、DPA 等文档类型。

# 1. 场景事实识别 Agent：解决“文档没写，但实际业务存在风险”的问题

## 为什么需要

预期案例一的核心难点是：协议本身看起来只是境内委托处理，但背景里乙方使用海外服务器，因此实际可能涉及数据出境。预期输出要求系统指出“协议未约定数据处理地理位置，若实际传输至新加坡服务器，则构成数据出境行为”。

当前系统有 `ScenarioExtractor`，能提取公司名称、数据类别、敏感数据、跨境指标、处理目的、接收方国家等信息。 但它更偏“从文档文本中抽取事实”，对“文档外业务背景 + 隐含数据流”的推理不足。

## Agent 应放在哪里

放在 **Stage 0：PREPARING** 后面，作为 `ScenarioExtractor` 的增强层。

```text
StructuredDocumentParser
  ↓
DocumentClassifier
  ↓
ScenarioExtractor
  ↓
场景事实识别 Agent
  ↓
ScenarioGraph / ReviewScenarioContext
```

## 预期处理逻辑

```text
Step 1：读取文档内事实
- 主体：甲方、乙方、境外接收方、第三方
- 数据：数据类型、数据规模、敏感程度
- 行为：收集、存储、加工、传输、运维、分析、备份
- 地点：服务器、数据中心、云平台、远程访问地

Step 2：读取用户补充背景
- 乙方是否跨国公司
- 运维平台是否部署在境外
- 是否使用境外云服务
- 是否存在境外远程访问
- 是否有境外备份或灾备中心

Step 3：构建数据流图
- 数据从谁流向谁
- 在哪里存储
- 在哪里访问
- 是否传输至境外
- 是否只是境内访问，还是境外远程访问境内数据

Step 4：发现隐含风险
- 文档没有写出境，但背景显示境外服务器
- 文档没有写境外接收方，但存在海外子公司/云平台
- 文档写“运维”，但没有说明远程访问边界
- 文档写“数据分析”，但没有说明处理地点

Step 5：输出场景风险结论
```

## 输出示例

```json
{
  "scenario_findings": [
    {
      "type": "implicit_cross_border_transfer",
      "severity": "HIGH",
      "basis": "协议未约定数据处理地点，但背景信息显示乙方运维平台服务器位于新加坡",
      "impact": "可能构成个人信息出境，现有协议无法支撑出境合规",
      "required_confirmation": [
        "乙方服务器部署地点",
        "是否存在境外远程访问",
        "是否存在境外备份",
        "是否向境外接收方提供个人信息"
      ]
    }
  ]
}
```

## 加了之后的效果

它能解决当前文档审查最容易漏掉的点：**不是合同写了什么，而是实际业务是不是被合同覆盖了**。这会让系统从“条款审查器”升级成“业务场景 + 法律文件一致性审查器”。

# 2. 数据类型与敏感性识别 Agent：解决“数据名称写得模糊，系统判断不准”的问题

## 为什么需要

预期案例里多次出现数据类型判断难点：

* “师生消费记录、门禁记录、图书借阅记录”可能包含个人信息甚至敏感个人信息。
* “脱敏后的用户 ID”到底是匿名化还是去标识化，合规要求完全不同。
* 标准合同案例里，“订单记录、支付信息、行程轨迹”中支付信息、行程轨迹明显涉及敏感个人信息。

当前系统有数据类别和敏感数据提取，但这类判断不是纯关键词匹配能解决的。

## Agent 应放在哪里

放在 **Stage 0 场景提取之后**，并向 Stage 3 缺失项检测、Stage 4 条款审查提供数据分类结果。

```text
ScenarioExtractor
  ↓
数据类型与敏感性识别 Agent
  ↓
MissingItemChecker / ClauseReviewer / RiskScorer
```

## 预期处理逻辑

```text
Step 1：抽取所有数据对象
- 用户 ID
- 设备 ID
- 浏览记录
- 门禁记录
- 图书借阅记录
- 支付信息
- 行程轨迹
- 薪酬绩效
- 联系人姓名/邮箱
- 企业注册号

Step 2：判断是否为个人信息
- 是否能识别自然人
- 是否能与其他字段结合识别自然人
- 是否经过匿名化
- 是否只是去标识化

Step 3：判断是否为敏感个人信息
- 行踪轨迹
- 金融账户/支付信息
- 财产信息
- 未成年人信息
- 医疗健康
- 特定身份
- 可能推断敏感状态的数据

Step 4：判断用户/合同表述是否模糊
- “匿名化”但无技术证明
- “脱敏”但未说明是否可逆
- “用户行为日志”但未说明字段
- “业务分析数据”但未细分种类

Step 5：输出数据分类结论和证据缺口
```

## 输出示例

```json
{
  "data_item": "脱敏后的用户ID",
  "classification": "potential_personal_information",
  "sensitivity": "uncertain",
  "reason": "合同未说明脱敏方式是否不可逆，若可通过映射表还原或与其他字段关联识别用户，则仍属于个人信息",
  "required_evidence": [
    "脱敏算法说明",
    "是否保留映射表",
    "是否可逆",
    "重识别风险评估"
  ],
  "recommended_issue": "数据性质描述模糊"
}
```

## 加了之后的效果

它能显著提高缺失项检测和风险评级的准确性。否则系统可能被合同里的“匿名化”“脱敏”字样误导，把本应高风险的问题降级。

# 3. 隐私政策告知矩阵 Agent：解决“隐私政策不是逐条看，而是看告知义务是否完整”的问题

## 为什么需要

你给的截图是隐私政策。隐私政策审查不能只看有没有“收集使用”“Cookie”“共享披露”等章节，而要判断是否完整告知、是否具体、是否与实际业务一致。功能说明也明确把线上生效的《隐私政策》或《个人信息处理规则》作为专项审查对象。

当前系统有 `PrivacyPolicyReviewer`，但如果只按条款分类检查，容易漏掉“整体告知矩阵”的问题。

## Agent 应放在哪里

放在 **Stage 4：REVIEWING** 的专项审查器里，作为 `PrivacyPolicyReviewer` 的增强 Agent。

```text
ClauseReviewer
  ├── DSL
  ├── StandardClauseDiffer
  ├── PrivacyPolicyReviewer
  │       └── 隐私政策告知矩阵 Agent
  └── LLM deep review
```

## 预期处理逻辑

```text
Step 1：识别隐私政策章节
- 处理者身份
- 收集和使用个人信息
- Cookie 和同类技术
- 共享、转让、公开披露
- 委托处理
- 跨境传输
- 用户权利
- 信息保存期限
- 安全保护措施
- 儿童个人信息
- 联系方式
- 政策更新机制

Step 2：构建告知义务矩阵
每个事项判断：
- 是否存在
- 是否具体
- 是否可操作
- 是否与其他文件一致
- 是否有必要的联系方式/路径/期限

Step 3：识别高风险缺口
- 未列明境外接收方名称和联系方式
- 只写“关联方”但未列具体主体
- 写“可能共享”但无具体目的和范围
- 用户权利路径不可操作
- 儿童信息处理规则过泛
- 跨境传输缺失或模糊

Step 4：输出矩阵和问题清单
```

## 输出示例

```json
{
  "privacy_notice_matrix": [
    {
      "notice_item": "跨境传输",
      "status": "missing_or_vague",
      "severity": "HIGH",
      "problem": "隐私政策未明确境外接收方名称、联系方式、处理目的、处理方式和个人信息种类",
      "recommendation": "增加个人信息出境专项告知条款"
    },
    {
      "notice_item": "用户权利",
      "status": "present_but_incomplete",
      "severity": "MEDIUM",
      "problem": "列明了访问、更正、删除权利，但未说明响应时限和具体申请渠道"
    }
  ]
}
```

## 加了之后的效果

它能让隐私政策审查更像监管合规检查，而不是普通文本审查。尤其适合你截图这种完整隐私政策页面，系统可以输出“告知事项覆盖表”，展示效果会更专业。

# 4. 标准合同强制条款审查 Agent：解决“标准合同被附录二架空”的问题

## 为什么需要

预期案例三最关键的是：标准合同表面使用了模板，但附录二里写了很多削弱条款，例如香港法院管辖、暂缓处理主体请求、责任总额上限、集团主协议优先。这些会影响标准合同效力。

当前系统有 `StandardClauseDiffer`，会检测义务缺失、义务弱化、高风险修改。 但标准合同是强模板文件，不能只靠 RAG 召回和相似度，应建立专门 Agent 做强制条款审查。

## Agent 应放在哪里

放在 **Stage 4：REVIEWING**，作为 `SccContractReviewer` 的增强。

```text
SccContractReviewer
  ↓
标准合同强制条款审查 Agent
  ↓
ReviewIssue[]
```

## 预期处理逻辑

```text
Step 1：识别是否为个人信息出境标准合同
- 是否有标准合同正文
- 是否有附录一
- 是否有附录二
- 是否存在商业合同优先条款

Step 2：锁定强制条款锚点
- 个人信息处理者义务
- 境外接收方义务
- 第三方受益人权利
- 个人信息主体权利响应
- 再转移限制
- 安全事件通知
- 合规审计
- 当地法律政策影响评估
- 争议解决条款
- 附录一字段
- 附录二不得与正文冲突

Step 3：检测标准合同被削弱
- 增加责任上限
- 改为境外法院管辖
- 其他协议优先
- 境外接收方可自行暂缓主体请求
- 删除或模糊技术管理措施
- 保存期限过长且无必要性论证
- 境外保存地点包含高风险地区但无评估

Step 4：输出条款级 finding
```

## 输出示例

```json
{
  "location": "附录二 第4条",
  "problem_type": "与法规冲突 / 标准合同保护条款被架空",
  "severity": "HIGH",
  "original_excerpt": "本合同与《集团数据共享主协议》冲突时，以《集团数据共享主协议》为准。",
  "risk_analysis": "该条款可能导致标准合同正文中的个人信息保护义务被其他商业协议排除或削弱，影响标准合同作为出境合规路径的有效性。",
  "recommendation": "删除该条，或改为：如其他协议与本合同不一致，应以更有利于个人信息主体权益保护且不低于本合同要求的约定为准。"
}
```

## 加了之后的效果

它能专门解决“看起来签了标准合同，但实际上被附录或主协议改坏了”的问题。这是 SCC 审查里最有展示价值、也最有合规价值的部分。

# 5. 跨文档一致性 Agent：解决“隐私政策、合同、内部制度互相打架”的问题

## 为什么需要

功能说明明确说，输入可以包括公开法律文件、数据处理协议、标准合同、数据安全制度等，企业内部制度可用于审查内外一致性。

当前系统有 `CrossDocConsistencyChecker`，但需要进一步升级成语义级一致性，而不是只做字段/关键词对比。

## Agent 应放在哪里

放在 **Stage 5：CROSS_DOC_CHECK**，增强现有 `CrossDocConsistencyChecker`。

```text
CrossDocConsistencyChecker
  ↓
跨文档一致性 Agent
  ↓
ConsistencyWarning[] / ReviewIssue[]
```

## 预期处理逻辑

```text
Step 1：从每份文档抽取关键事实
- 数据类型
- 处理目的
- 处理方式
- 接收方
- 第三方共享
- 跨境传输
- 保存期限
- 安全事件通知时限
- 用户权利响应
- 审计权
- 管辖条款

Step 2：建立事实对照表
例如：
隐私政策：不涉及出境
DPA：传至香港服务器
SCC：接收方为开曼公司
内部制度：安全事件 24 小时内通知
合同：写“及时通知”

Step 3：识别冲突
- 隐私政策未告知，但合同实际出境
- 内部制度要求更严，但外部合同更宽
- 标准合同接收方与隐私政策接收方不一致
- 保存期限在不同文件中不一致
- 用户权利响应路径不一致

Step 4：判断冲突严重度
- 影响出境合法性：HIGH
- 影响证据一致性：MEDIUM
- 表述风格差异：LOW

Step 5：输出跨文档问题
```

## 输出示例

```json
{
  "type": "cross_document_inconsistency",
  "severity": "HIGH",
  "conflict": [
    {
      "file": "隐私政策",
      "statement": "未披露个人信息将传输至境外"
    },
    {
      "file": "数据处理协议",
      "statement": "部分中间过程数据传输至香港数据中心"
    }
  ],
  "risk_analysis": "公开告知文件与合同安排不一致，可能导致告知义务和单独同意义务无法成立。",
  "recommendation": "同步修订隐私政策、补充跨境传输告知，并与数据处理协议保持一致。"
}
```

## 加了之后的效果

它能把系统从“单文档审查”升级为“整套法律文件体系审查”。这是文档专项模块相比普通合同审查工具的核心差异。

# 6. 法规依据绑定 Agent：解决“引用有了，但不一定支撑判断”的问题

## 为什么需要

预期报告要求每个条款问题都包含法规/标准依据。功能说明明确要求报告主体每项问题包括定位、原文引用、问题类型、风险分析、法规/标准依据、修改建议。

当前系统有 RAG 和 `CitationRelevanceChecker`。 但现实问题是：RAG 找到法规，不等于引用和 issue 精准匹配。

## Agent 应放在哪里

放在 **Stage 4 审查之后、Stage 6 聚合之前**，作为 issue 的法规依据增强层。

```text
ReviewIssue[]
  ↓
法规依据绑定 Agent
  ↓
ReviewIssue[with structured_citations]
```

## 预期处理逻辑

```text
Step 1：识别 issue 类型
- 缺失数据出境条款
- 责任错配
- 管辖条款不利
- 保存期限过长
- 安全事件通知模糊
- 数据类型描述模糊
- 标准合同条款冲突
- 主体权利保障不足

Step 2：匹配法规依据库
- 上位法
- 部门规章
- 标准合同模板
- 国家标准
- 示范文本
- 行业规范

Step 3：判断引用是否能支撑该 issue
- 条文是否直接相关
- 是否只是背景性依据
- 是否需要组合引用
- 是否需要模板依据而不是法律依据

Step 4：生成 why_applicable
说明为什么该条文适用于这个问题

Step 5：回填 structured_citations
```

## 输出示例

```json
{
  "issue_id": "ISSUE-014",
  "legal_basis": [
    {
      "citation": "《个人信息保护法》第三十八条",
      "why_applicable": "该问题涉及向境外提供个人信息的合规路径选择，第三十八条规定了安全评估、标准合同、认证等出境条件。"
    },
    {
      "citation": "《个人信息出境标准合同》附录一",
      "why_applicable": "该问题涉及出境个人信息种类、保存地点、保存期限等填写要求。"
    }
  ]
}
```

## 加了之后的效果

它能显著提高报告可信度。否则报告容易出现“有引用，但像是装饰”的问题。

---

# 7. 修改条款生成 Agent：解决“建议泛泛而谈，不能直接改合同”的问题

## 为什么需要

预期报告不是只说“建议完善”，而是要给出具体修改文本或新增条款草案。功能说明明确要求“提供具体的、可供参考的修改文本或新增条款草案”。

当前模型里有 `SuggestedRevision` 字段，但需要专门 Agent 确保建议文本和文档类型匹配。

## Agent 应放在哪里

放在 **Stage 4 审查之后**，为每个高/中风险 issue 生成修改建议。

```text
ReviewIssue
  ↓
修改条款生成 Agent
  ↓
ReviewIssue.suggested_revision
```

## 预期处理逻辑

```text
Step 1：识别文档类型
- 隐私政策
- 标准合同
- DPA
- 数据安全保密协议
- 内部制度
- 云服务协议附件

Step 2：识别问题类型
- 缺失条款
- 定义模糊
- 责任限制过度
- 与法规冲突
- 与实践不一致
- 证据不足

Step 3：选择条款模板
不同文档类型使用不同模板：
- DPA：委托方责任、受托方协助、再委托、跨境传输
- 保密协议：数据处理地点、审计权、安全事件通知、销毁证明
- SCC：不得与正文冲突、主体权利、保存期限、技术措施
- 隐私政策：告知事项、用户权利路径、跨境说明

Step 4：结合原文生成替换文本
- 保留原合同风格
- 不引入未提供事实
- 对不确定事实用可填空占位
- 给出新增条款或替换条款

Step 5：输出 suggested_revision
```

## 输出示例

```json
{
  "revision_type": "add_clause",
  "suggested_text": "乙方应仅在中华人民共和国境内处理、存储和访问甲方提供的数据。未经甲方事先书面同意，乙方不得将数据传输、存储至中华人民共和国境外，亦不得允许境外主体远程访问相关数据。如确需发生数据出境，双方应在出境前另行完成适用的数据出境合规手续。"
}
```

## 加了之后的效果

它能让审查报告从“指出问题”变成“能直接推进合同修改”。对比赛答辩和产品落地都很关键。

---

# 8. 审查边界与追问 Agent：解决“不确定事实没有转化成下一步问题”的问题

## 为什么需要

当前模型里有 `facts_uncertain` 和 `uncertainty_rationale`，这很好。 但合规审查中，不确定事实不能只停留在报告说明里，还要转化成“下一步补充材料清单”。

例如：

* 乙方是否使用境外服务器？
* 脱敏 ID 是否可逆？
* 是否涉及重要数据？
* 是否取得个人单独同意？
* 隐私政策是否为线上最新版本？
* 标准合同是否已经备案？

## Agent 应放在哪里

放在 **Stage 6：AGGREGATING**，和风险聚合一起生成“待确认事项”。

```text
ReviewIssue[]
  ↓
审查边界与追问 Agent
  ↓
priority_actions / missing_materials / review_boundary
```

## 预期处理逻辑

```text
Step 1：收集所有不确定事实
- facts_uncertain
- uncertainty_rationale
- 缺失材料
- 条款模糊点
- 场景矛盾点

Step 2：判断这些事实是否影响结论
- 是否影响是否构成数据出境
- 是否影响是否属于个人信息
- 是否影响是否为敏感个人信息
- 是否影响路径选择
- 是否影响风险评级

Step 3：按优先级排序
P0：不确认就不能下结论
P1：影响风险等级
P2：影响修改建议完整性

Step 4：生成用户追问和材料清单
```

## 输出示例

```json
{
  "critical_questions": [
    {
      "priority": "P0",
      "question": "乙方是否存在境外服务器、境外备份或境外远程访问？",
      "impact": "直接影响是否构成数据出境"
    },
    {
      "priority": "P0",
      "question": "脱敏后的用户ID是否可通过映射表或其他方式还原到具体用户？",
      "impact": "直接影响该数据是否仍属于个人信息"
    }
  ]
}
```

## 加了之后的效果

它能避免系统“强行下结论”。对法律合规场景来说，能清楚说明“当前结论基于哪些假设、哪些材料缺失会改变结论”，非常重要。

---

# 9. 报告质检 Agent：解决“最终报告是否漏项、错引、泛化”的问题

## 为什么需要

当前已经有审查流水线和报告渲染，但最终报告仍可能出现：

* 高风险 issue 没进入摘要；
* 缺失项没有进入整改路线图；
* 法规引用和问题不匹配；
* 修改建议过泛；
* 把不确定事实写成确定事实；
* 条款定位不准确；
* 隐私政策审查没有输出完整矩阵。

## Agent 应放在哪里

放在 **Stage 7：RENDERING 前**，作为最终质量门禁。

```text
AggregatedReview
  ↓
报告质检 Agent
  ↓
repair / approve
  ↓
ReviewReportRenderer
```

## 预期处理逻辑

```text
Step 1：检查结构完整性
- 是否有文件概要
- 是否有总体评级
- 是否有条款级发现
- 是否有法规依据
- 是否有修改建议
- 是否有审查边界

Step 2：检查风险覆盖
- 所有 HIGH issue 是否进入摘要
- 所有 MissingItem 是否进入缺失项章节
- 所有跨文档冲突是否进入报告

Step 3：检查事实一致性
- 是否引用了用户未提供事实
- 是否把“不确定”写成“已确认”
- 是否与场景图冲突

Step 4：检查引用质量
- 每个法律判断是否有对应依据
- 引用是否能支撑该问题

Step 5：检查建议质量
- 是否给出可执行修改文本
- 是否按文档类型定制
```

## 输出示例

```json
{
  "quality_status": "needs_repair",
  "problems": [
    {
      "type": "missing_high_risk_in_summary",
      "issue_id": "ISSUE-003",
      "repair": "将隐含数据出境风险加入执行摘要和总体评级理由"
    },
    {
      "type": "unsupported_statement",
      "text": "乙方已完成数据出境合规手续",
      "repair": "改为：协议声称由乙方负责完成合规手续，但未提供证明材料"
    }
  ]
}
```

## 加了之后的效果

它能把当前模块的输出稳定性拉高，避免“流程很完整，但报告质量不稳定”的问题。

# 10. 推荐优先级

不是所有 Agent 都要一起做。建议按收益排序：

| 优先级 | Agent            | 解决问题            | 加入价值 |
| --- | ---------------- | --------------- | ---- |
| P0  | 场景事实识别 Agent     | 隐含出境、境外服务器、远程访问 | 最大   |
| P0  | 数据类型与敏感性识别 Agent | 脱敏/匿名化、敏感个人信息误判 | 最大   |
| P0  | 标准合同强制条款审查 Agent | SCC 被附录二削弱或架空   | 最大   |
| P1  | 隐私政策告知矩阵 Agent   | 隐私政策完整性、具体性、一致性 | 很高   |
| P1  | 跨文档一致性 Agent     | 隐私政策、合同、内部制度冲突  | 很高   |
| P1  | 法规依据绑定 Agent     | 引用和问题精准绑定       | 很高   |
| P2  | 修改条款生成 Agent     | 生成可直接替换文本       | 高    |
| P2  | 审查边界与追问 Agent    | 不确定事实转为补充问题     | 高    |
| P2  | 报告质检 Agent       | 最终报告稳定性         | 高    |

---

# 11. 最推荐的整体 Agent 架构

```text
用户上传文档 / 背景信息
        ↓
Stage 0 文档解析与分类
        ↓
场景事实识别 Agent
        ↓
数据类型与敏感性识别 Agent
        ↓
Stage 1-2 条款切分与分类
        ↓
Stage 3 缺失项检测
        ↓
Stage 4 条款审查
    ├─ 隐私政策告知矩阵 Agent
    ├─ 标准合同强制条款审查 Agent
    ├─ 法规依据绑定 Agent
    └─ 修改条款生成 Agent
        ↓
Stage 5 跨文档一致性
    └─ 跨文档一致性 Agent
        ↓
Stage 6 风险聚合
    └─ 审查边界与追问 Agent
        ↓
Stage 7 报告渲染前
    └─ 报告质检 Agent
        ↓
输出：
- 合规审查报告 DOCX
- 条款级问题清单
- 批注版 DOCX
- 修改建议文本
- 待补充材料清单
- 审查边界说明
```

---

# 12. 一句话结论

当前模块已经有完整的“文档审查流水线”，现在最需要 Agent 的地方是：**让系统从“看条款”升级为“理解业务场景、识别隐含出境、判断数据敏感性、比对强制合同结构、校验跨文档一致性、生成可用修改文本”**。这几类问题都不是单条规则能稳定解决的，加 Agent 后会明显提升审查深度和报告可信度。
