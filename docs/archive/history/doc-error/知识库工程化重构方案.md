# 知识库 — 工程化重构方案

## 一、现状诊断

当前 `doc/` 下的知识资产分布在 **四个独立目录树** 中，彼此之间没有结构关系：

```
doc/
├── knowledge/                    ← 运行时索引（CSV + registry + 正文快照）
│   ├── index/sources.csv
│   ├── raw/cn_regulations/*.html
│   ├── registry/module_catalog.v1.json
│   └── evaluation/*.jsonl
│
├── 数规通功能路径描述.../         ← Spec 文档 + 原始 Reference PDF
│   ├── 中国数据出境路径/
│   │   ├── 中国数据出境路径reference库/
│   │   │   └── 中国数据出境路径reference文件库/  ← 3层冗余嵌套
│   │   └── 任务1-4/  (功能说明.docx + 测试案例.docx)
│   ├── 欧盟数据出境路径/  (同上结构)
│   └── 美国（加州）数据出境路径/  (同上)
│
├── addition/                     ← 模块级 Prompt/模板
│   ├── 01_pathway_layer/cn_diagnosis/
│   └── 02_function_layer/contract_review/scc/
│
├── v2/                           ← 新版重构的早期草稿
│   └── assets/templates/
│
├── error/                        ← 错误记录（本次新增）
└── 开发文档/                     ← 开发说明
```

**五个核心问题：**

| # | 问题 | 具体表现 |
|---|------|---------|
| 1 | **同一份法规存在于两个地方** | `数规通.../reference文件库/个人信息保护法.pdf` vs `knowledge/raw/cn_regulations/cac_2021_08_20_pipl.html` — 一个是原始 PDF，一个是 HTML 快照，但它们之间没有关联 |
| 2 | **中文目录名** | `数规通功能路径描述（含reference）、流程描述、测试案例` — 命令行 tab 补全灾难，git 操作易出错 |
| 3 | **冗余嵌套** | `中国数据出境路径 → 中国数据出境路径reference库 → 中国数据出境路径reference文件库` — 三层目录只为装一个文件列表 |
| 4 | **版本演化无迹可寻** | `knowledge/`、`addition/`、`v2/` 三套体系并存，不知道哪个是 current |
| 5 | **Spec 与实现断裂** | `数规通.../` 里的功能说明.docx 定义了模块行为，但 `backend/modules/` 的代码不引用它。知识库 CSV 也不引用原始 PDF |

## 二、设计原则

### 原则 1：一个根目录

所有知识资产从 `doc/knowledge/` 出发。Spec 文档、Reference 原文、正文快照、元数据索引、RAG 评估数据全部放在一个树里，不用记住"这份 PDF 是在 `数规通/` 下面还是 `v2/assets/` 下面"。

### 原则 2：按功能模块分，不按法域分

当前 `数规通/中国数据出境路径/` 的组织方式把"中国所有的法规 + 功能说明 + 测试案例"堆在一起。但一条法规（如《个人信息保护法》）同时被 `cn_diagnosis`、`cn_assessment`、`cn_review` 三个模块引用。按法域分导致同一法规无法找到"属于哪个模块"。

正确做法：**按后端模块组织**。每个模块目录下有自己的 spec、reference、test-cases、snapshots。

### 原则 3：管道分层，不是文件堆

知识库是一个四阶段管道：

```
原始文件        →   正文提取       →   元数据索引      →   前端服务
(Reference)         (Snapshot)          (CSV)               (API)
```

每个阶段对应一个子目录，目录名表达它在管道中的位置。

### 原则 4：一个模块 = 一个文件夹，可独立 copy 到另一个项目

类比 npm 包或 Go module：每个模块目录自包含，把自己的 spec + reference + test-cases + snapshots 打包就可以迁移。

### 目录规则

| 前缀 | 含义 | 示例 |
|------|------|------|
| `_` | 全局索引/配置（不属于任何单一模块） | `_index/`、`_registry/`、`_evaluation/` |
| `cn-` | 中国法域模块 | `cn-diagnosis`、`cn-assessment`、`cn-review` |
| `eu-` | 欧盟法域模块 | `eu-scc`、`eu-bcr`、`eu-dpia`、`eu-tia` |
| `us-` | 美国法域模块 | `us-14117`、`us-cpra` |

### 每个模块文件夹的四件套

```
<module-name>/
├── spec.md           ← 功能说明（markdown，从原 .docx 转换）
├── test-cases.md     ← 测试案例 + 预期输出（markdown）
├── references/       ← 原始法规文件（PDF/docx，只读，git-lfs 管理）
└── snapshots/        ← 正文快照（HTML/JSON/Markdown，供 RAG 和前端阅读）
```

## 四、与后端代码的绑定关系

`_index/sources.csv` 的每一行有一个 `snapshot_path` 字段，指向对应模块的 `snapshots/` 目录：

```csv
source_id,jurisdiction,module,title,...,snapshot_path
CN-LAW-001,cn,cn-diagnosis,网络安全法,...,cn-diagnosis/snapshots/cac_2025_12_29_cybersecurity_law.html
CN-LAW-003,cn,cn-assessment,个人信息保护法,...,cn-assessment/snapshots/cac_2021_08_20_pipl.html
EU-LAW-001,eu,eu-scc,GDPR 2016/679,...,eu-scc/snapshots/eurlex_gdpr_2016_679_excerpts.md
```

这样 **一份 CSV 文件即可驱动所有模块的知识库展示**，不需要为每个模块单独维护索引。

后端 `knowledge_index.py` 读取 CSV 的路径不需要变：
```python
SOURCES_CSV = ROOT / "doc/knowledge/_index/sources.csv"
```

`module_catalog.v1.json` 中的 `legal_index_*` 仍然指向 RAG 索引，不受此次重构影响。

## 五、迁移步骤

### 阶段 A：建立新骨架（不删旧文件）

```bash
# 1. 创建新目录结构
mkdir -p doc/knowledge/{_index,_registry,_evaluation}
mkdir -p doc/knowledge/{cn-diagnosis,cn-assessment,cn-review,cn-pipia}/{spec,test-cases,references,snapshots}
mkdir -p doc/knowledge/{eu-scc,eu-bcr,eu-dpia,eu-tia}/{spec,test-cases,references,snapshots}
mkdir -p doc/knowledge/{us-14117,us-cpra}/{spec,test-cases,references,snapshots}

# 2. 迁移全局文件（移动，不是复制）
mv doc/knowledge/index/*.csv        doc/knowledge/_index/
mv doc/knowledge/registry/*.json    doc/knowledge/_index/
mv doc/knowledge/normalized/*.jsonl doc/knowledge/_registry/
mv doc/knowledge/evaluation/*       doc/knowledge/_evaluation/

# 3. 写 README.md
```

### 阶段 B：逐模块迁移内容

以 `cn-assessment` 为例：

```bash
# 1. 从 .docx 提取 spec（Python 脚本一键）
python tools/extract-docx.py \
  "doc/数规通.../中国数据出境路径/任务2.../安全评估路径功能说明.docx" \
  > doc/knowledge/cn-assessment/spec.md

# 2. 同样提取 test-cases
python tools/extract-docx.py \
  "doc/数规通.../中国数据出境路径/任务2.../安全评估路径测试案例.docx" \
  > doc/knowledge/cn-assessment/test-cases.md

# 3. 复制 reference 文件
cp "doc/数规通.../中国数据出境路径reference库/...reference文件库/数据出境安全评估办法.pdf" \
   doc/knowledge/cn-assessment/references/

# 4. 移动已有 snapshot
mv doc/knowledge/raw/cn_regulations/cac_*_assessment*.html \
   doc/knowledge/cn-assessment/snapshots/
```

**每个模块单独一个 commit，可独立回滚。**

### 阶段 C：更新 CSV 引用路径

`_index/sources.csv` 中所有 `snapshot_path` 改为相对于 `doc/knowledge/` 的相对路径：

```
旧: doc/knowledge/raw/cn_regulations/cac_2025_12_29_cybersecurity_law.html
新: cn-diagnosis/snapshots/cac_2025_12_29_cybersecurity_law.html
```

后端 `knowledge_index.py` 中统一拼接根路径：
```python
ROOT = Path(__file__).resolve().parents[2]  # 项目根
SNAPSHOT_BASE = ROOT / "doc/knowledge"

def _resolve_snapshot(relative_path: str) -> Path:
    return SNAPSHOT_BASE / relative_path
```

### 阶段 D：删除旧目录（确认新结构可用后）

```bash
rm -rf "doc/数规通功能路径描述（含reference）、流程描述、测试案例"
```

## 六、为什么这样设计

### 为什么按模块分而不是按法域分？

当前 `数规通.../` 按法域分 → 把中国的 4 个模块的法规全堆在一起，分不清哪条法规服务于哪个模块。按模块分后：
- 新增一个模块 = 新建一个文件夹 + 四件套
- 删除一个模块 = 删除一个文件夹（CSV 中标记 `module` 列为 deprecated）
- 每个模块的法规引用一目了然：看 `references/` 目录就知道这个模块依赖哪些法规原文

### 为什么把 Reference PDF 和 Snapshot 放在同一个模块下？

因为它们是同一份法规的两个形态。当更新一份法规时（如网信办发布新版申报指南），需要同时更新 PDF 原文和 HTML 快照。放在一个文件夹下，开发者一眼看到"这个模块的法规原文和渲染快照是不是同一版本"。

### 为什么 CSV 不拆成每个模块一份？

拆开会导致查询跨模块的法规变得困难（如 `EvidenceCenterPage` 的"全部法规"视图需要 UNION 多份 CSV）。一份 CSV 加一个 `module` 列即可过滤。

### 为什么用 `_` 前缀标记全局目录？

视觉区分。`_index/` 不是模块，是基础设施。用户浏览目录时不需要关心 `_index/` 的内部结构，但需要知道它不是某个业务模块。

## 七、与 Spec 同步的闭环

重构后，Spec 的变化能直接对应到目录操作：

| Spec 变化 | 目录操作 |
|-----------|---------|
| 新增一个模块（如"日本 APPI 合规"） | 新建 `jp-appi/` + 四件套 |
| 某个模块的法规依据更新 | 替换 `references/` 中的 PDF + 更新 `snapshots/` 中的 HTML |
| 测试案例补充 | 编辑 `test-cases.md` |
| 功能描述补充 | 编辑 `spec.md` |
| 某条法规不再使用 | CSV 中标记 `status: deprecated`，不删文件 |

**所有改动都可以通过 `git log -- doc/knowledge/<module>/` 追溯历史。**
