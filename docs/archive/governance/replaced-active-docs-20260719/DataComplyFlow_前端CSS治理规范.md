# DataComplyFlow 前端 CSS 治理规范

## 1. 治理目标

全局 CSS 是具有顺序依赖的行为代码。治理目标是让样式归属可查、覆盖关系可解释、修改可以验证，不以简单减少行数为目标。

## 2. 当前事实基线

拆分前的 `frontend/src/styles/app.css`：

- 13,035 个实际文本行；
- 1,898 条 CSS 规则；
- 1,875 个“上下文 + 选择器”组合；
- 22 组重复选择器；
- 0 组相邻且声明完全相同的规则。

22 组重复选择器均属于不同声明的后置覆盖，不能仅因选择器同名而删除。本轮未删除任何 CSS 规则。

拆分前后生产 CSS 保持完全一致：

## 3. 权威入口与目录职责

`frontend/src/styles/app.css` 是应用全局样式的唯一入口，且只负责按固定顺序导入：

```text
app.css
├── app/base.css
├── app/landing.css
├── app/pages.css
├── app/workspace.css
└── app/product-pages-and-overrides.css
```

各文件职责：

| 文件 | 职责 |
|---|---|
| `base.css` | 应用壳、导航、认证、按钮和通用基础组件 |
| `landing.css` | 首页及历史上仍在使用的 Landing 方案 |
| `pages.css` | 任务、设置、证据、知识和通用弹窗页面 |
| `workspace.css` | 工作台、模块运行、资源、助手、Trace 和报告预览 |
| `product-pages-and-overrides.css` | 法域页、报告中心、文档中心、Citation 以及必须后置的响应式覆盖 |

`tokens.css` 继续作为颜色、字体和基础变量入口；SuperDesign 的嵌入样式继续隔离在其集成目录中，不并入应用全局样式。

## 4. 强制规则

1. `main.tsx` 只导入 `tokens.css` 和 `app.css`，不得直接导入上述分卷文件。
2. 分卷文件之间不得相互 `@import`；导入顺序只由 `app.css` 管理。
3. 不得因为选择器重复就删除前一条或后一条规则。
4. 删除覆盖规则前必须同时检查选择器优先级、源码顺序、媒体查询上下文和实际页面。
5. 新增组件样式应放入其所属分卷，不得默认追加到最后一个文件。
6. 后置覆盖必须靠近被覆盖模块，或在代码旁说明必须后置的原因。
7. 不通过增加 `!important` 解决归属不清或选择器冲突。
8. 不在同一批次同时进行 CSS 大规模移动、组件结构重写和视觉设计调整。

## 5. 安全删除条件

CSS 只有满足以下证据之一才可以删除：

- 对应组件、页面和动态 class 已确认不存在；
- 规则在相同媒体查询上下文中相邻、选择器相同、声明完全相同；
- 浏览器覆盖分析、视觉回归和构建检查均证明规则不产生效果；
- 对应产品入口已经明确废弃并整包移除。

以下情况不得直接删除：

- 同名选择器但声明不同；
- 位于不同 `@media`、伪类或伪元素上下文；
- class 名由字符串拼接或后端数据生成；
- 仅凭编辑器显示“未引用”。

## 6. 验收门禁

每批 CSS 修改至少执行：

```bash
cd frontend
npm test
npm run build
```

同时检查：

- CSS 结构测试通过；
- 生产 CSS 大小和变化原因可解释；
- 关键页面在桌面和窄屏尺寸下完成视觉检查；
- 无非预期新增全局选择器、`!important` 和跨分卷导入。

## 7. 后续治理顺序

1. 先为 `ModuleRunPanel` 和 `WorkspaceShell` 建立 feature 边界；
2. 再把相应样式跟随组件迁移到更细的 feature 样式；
3. 最后根据实际视觉回归结果处理过期 Landing 方案和历史覆盖；
4. 未建立页面级视觉回归前，不开展批量“未使用 CSS”删除。
