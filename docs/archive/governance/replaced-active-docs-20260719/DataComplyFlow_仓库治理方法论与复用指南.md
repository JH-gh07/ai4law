# DataComplyFlow 仓库治理方法论与复用指南

> 建立日期：2026-07-17
> 状态：活动、持续追加
> 适用范围：代码、测试、配置、文档、知识资源、评测资产与运行产物的结构治理

## 1. 目的

本文沉淀 DataComplyFlow 从探索式开发进入稳定维护阶段后形成的仓库治理经验。治理不是为了追求目录形式整齐，也不是借清理之名重写系统，而是让仓库中的物理结构、真实调用链、权威配置和文档描述重新一致。

统一优先级为：

```text
正确性 → 简洁性 → 结构收敛 → 能力补强
```

## 2. 基本原则

1. 以可运行代码、当前配置、真实调用链和测试结果为最高事实依据；
2. 文件存在不等于能力接入，测试存在不等于产品使用，文档描述不等于代码实现；
3. 先确认消费者和权威替代实现，再进行移动或删除；
4. 一类问题使用一份治理契约、一批修改和一组验收，不混入算法优化；
5. 优先删除重复和失效资产，不为“看起来规范”增加无实际职责的层级；
6. 逻辑身份用于降低迁移风险，物理归位用于完成最终收敛；
7. 测试验证行为，静态复扫验证结构，两者不能互相替代；
8. 明确保留的例外必须记录状态、理由、边界和后续接入条件。

## 3. 标准治理闭环

### 3.1 冻结事实

- 记录 Git branch、commit 和 dirty status；
- 记录活动入口、配置、规则、Prompt、数据集和索引；
- 保存修改前测试结果、路由清单或其他行为基线；
- 区分产品事实、代码推断、未验证事项和后续建议。

### 3.2 分类资产

| 类别 | 含义 | 默认处理 |
|---|---|---|
| active | 当前主流程使用 | 保留为权威源 |
| duplicate | 有权威替代实现 | 迁移消费者后删除 |
| obsolete | 已失效且无兼容价值 | 验证后删除 |
| legacy-compatible | 仍承担兼容协议 | 隔离并标注边界 |
| generated | 可重新生成 | 忽略版本控制 |
| runtime artifact | 运行期数据 | 与源码隔离 |
| research asset | 非运行研究材料 | 禁止进入生产调用链 |
| sensitive/unknown provenance | 来源或敏感性未确认 | 隔离并人工确认 |

### 3.3 建立治理契约

每批操作前至少写清：当前事实和问题、目标权威源、保留/迁移/删除/例外清单、本批边界、调用链影响、验收命令与回退条件。

### 3.4 分批执行

```text
确认活动入口
→ 建立权威目录和稳定导入路径
→ 迁移真实消费者
→ 验证新入口
→ 删除旧副本及孤立测试
→ 复扫失效引用和级联死代码
→ 更新契约执行结果
```

## 4. 删除判定方法

不得只依据名称、修改时间、版本号或目录位置删除。删除前检查 Python/TypeScript import、属性调用、Router、工厂、注册表、配置驱动加载、脚本、任务、测试、Benchmark、前端路径、动态名称与外部契约。

符号级删除必须同时满足：

```text
仓库内零消费者
+ 非框架回调
+ 非协议或序列化入口
+ 非动态注册目标
+ 非明确保留资产
+ 删除后测试和调用链不变
```

删除后必须再次扫描。入口删除可能使其私有辅助函数成为新的死代码，只有多轮复扫才能完成安全的级联收敛。

## 5. 结构设计经验

### 5.1 协议层与业务层分离

- `api/v0`、`api/v1` 负责 HTTP 版本、协议适配和路由装配；
- `domains/{cn,eu,us}` 负责版本无关的法律业务；
- `common` 只保留确实被多个模块复用且不依赖特定法域的能力；
- 新 API 版本优先复用领域服务，不复制完整业务模块。

### 5.2 版本实现必须收敛为运行策略

探索期的 v1/v2/v3 可以并存，稳定期必须明确唯一活动入口、可解释的策略名称、必要的兼容或 fallback 边界，以及历史实现的退役条件。

### 5.3 测试按职责组织

- API 版本集成测试按 `api/v0/tests`、`api/v1/tests` 区分；
- 跨版本装配和重复路由检查放在 `api/tests`；
- 领域单元测试可以就近放置，不因开发结束而删除；
- 只验证孤立、未接入实现的测试不能单独证明产品能力。

## 6. 验证矩阵

```text
语法/类型检查
+ 静态引用复扫
+ 单元和集成测试
+ Benchmark 回归
+ API 路由与 OpenAPI 检查
+ 前端测试和生产构建
+ 仓库卫生检查
+ git diff --check
+ 临时产物清理
```

测试失败时先判断是否发现隐式契约，不能为了维持删除结论而修改无关业务行为。

## 7. 保留例外

负责人明确要求保留、但尚未接入主流程的资产，应登记为受控例外。记录必须包含保留原因、当前真实状态、不得对外宣称的能力，以及后续接入所需入口、测试和数据同步条件。

## 8. 常见失败模式

- 根据文件名中的 `agent`、`v2`、`legacy` 推断真实状态；
- 只移动目录，不迁移消费者和删除旧副本；
- 把兼容入口与业务领域混在同一层；
- 用新的注册表、Facade 或 Schema 掩盖重复实现；
- 把清理、Bug 修复、Prompt 优化和算法实验放入同一批修改；
- 只跑测试，不检查孤立文件、重复路由和失效引用；
- 把来源材料、运行输出或研究资料误当生产知识源。

## 10. 当前结论

仓库治理完成的含义不是代码永不再改，而是后续开发已经拥有清楚的活动入口、稳定的权威源、可验证的变更边界和可回退的基线。
