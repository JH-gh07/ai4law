## 1. 固定原则

治理顺序固定为“正确 → 简洁 → 补强”。

- 不因名称旧、文件较大或目录不美观直接删除；
- 删除前必须核对 import、Router、脚本、配置、测试和文档引用；
- 不同时混入清理、Bug 修复、算法优化和架构重写；
- 每批必须有事实基线、范围、非目标、验收和回退条件；
- 当前重点是仓库自洽，不以最终安全体系或法律 Gold 抬高结构治理门槛。

## 3. 已确认保留边界

- `/api/v0` 是兼容任务网关，不复制为 v1，也不因版本号直接删除；
- `/api/v1` 是当前主 API；
- RAG 通过 `backend/common/rag/service.py` 统一进入，版本语义优化不与目录治理混做；
- 大型业务文件拆分属于后续可维护性工作；
- 法律 Gold、管理员 RBAC、密钥加密落盘和高级安全加固均不属于当前结构治理完成条件；
- `storage/runtime_settings.json`、Trace、报告和上传文件属于本地运行资产，不进入 Git。

## 4. 下一批执行顺序

1. `GIT-GATE`：人工审查确认后再分批暂存和提交；结构治理与统一回归已经完成。

## 5. 单批门禁

每批开始前记录：

- 当前结构、消费者和测试基线；
- 保留、移动、删除和暂缓清单；
- 不改变的接口、Schema 与运行行为；
- 验收命令和失败回退条件。

每批结束后必须：

- 更新权威 README 或工程规范；
- 将完成契约移入 `docs/archive/governance/executed-batches/`；
- 检查活动文档链接和旧路径；
- 执行与风险相称的测试；
- 不自动提交 Git。

## 6. 当前停止条件

发生以下任一情况立即停止该批：

- 无法确认文件是否仍有运行消费者；
- 删除会改变 API、Schema、Prompt、规则或法律结论；
- 发现来源不明且可能敏感的用户数据；
- 需要引入新的权限、存储或复杂 Agent 才能继续；
- 测试失败且不能证明与本批无关。
