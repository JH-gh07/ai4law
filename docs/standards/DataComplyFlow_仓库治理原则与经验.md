# DataComplyFlow 仓库治理原则与经验

> 类型：长期治理知识资产
> 维护方式：只追加经过实际治理验证、可复用且有适用边界的经验。

## 1. 核心原则

治理顺序固定为：

```text
正确 → 简洁 → 结构收敛 → 能力补强
```

1. 可运行代码、当前配置、真实调用链和测试结果高于文件名、注释和规划文档。
2. 文件存在不等于能力接入；目录看起来旧、文件较大或测试不完整都不是删除依据。
3. 先确认消费者和权威替代实现，再移动或删除。
4. 优先删除完全重复、无消费者、可重建和明确退役资产，不为外观整齐增加新层级。
5. 一类问题一批修改，清理、Bug、契约、算法和安全补强分开。
6. 文档只保留唯一活动规范；阶段事实进 `handoff`，历史执行证据进 `archive`。
7. 不自动提交 Git；人工审查完成后按单一目标分批提交。

## 2. 资产分类

| 类别 | 含义 | 默认处理 |
|---|---|---|
| active | 当前主流程使用 | 保留为权威源 |
| duplicate | 与权威源内容或职责重复 | 迁移消费者、验证后删除 |
| obsolete | 已失效且无兼容价值 | 删除 |
| legacy-compatible | 仍承担已发布兼容契约 | 隔离并记录退役条件 |
| generated | 可由源码和配置重建 | 忽略版本控制 |
| runtime artifact | 上传、数据库、Trace、报告和运行输出 | 与源码隔离，按数据策略清理 |
| research asset | 不参与运行的研究或来源材料 | 归档、外移或人工确认，不进入生产调用链 |
| sensitive / unknown | 敏感性或来源不明 | 停止自动处理并人工确认 |

## 3. 标准治理闭环

```text
冻结 Git 与测试基线
→ 扫描 import、Router、脚本、配置、测试和文档消费者
→ 分类 active / duplicate / legacy / generated / sensitive
→ 写明本批目标、非目标、回退和验收
→ 迁移真实消费者
→ 验证新入口
→ 删除旧副本与级联死代码
→ 再次扫描失效引用
→ 更新唯一活动规范
```

符号或文件删除至少满足：仓库内零消费者、非框架回调、非动态注册目标、非协议入口、非保留资产，并且删除后调用链与测试不变。

## 4. 已验证经验

- API 版本属于协议层，法律业务属于领域层；新增版本复用领域服务，不复制业务模块。
- 探索期 v1/v2/v3 可以存在，稳定期必须收敛为一个活动入口和有名称、可观察的运行策略。
- 公共目录只放多个模块真实复用且不含特定法域判断的能力。
- 测试按职责组织：源码单元测试就近，跨模块门禁集中；测试不完整不等于测试无价值。
- 静态法规、模板和规则与生成索引分离；运行输出、上传件和 Trace 不成为源码或 Gold。
- 同 Hash 文件可以安全去重；内容相似但 Hash 不同的来源材料必须先确认版本和用途。
- 空目录可以删除，但不能据此删除相邻非空运行数据；运行目录是否自动重建必须以代码为证。
- 外部集成目录只在没有消费者时删除；已被容器或业务服务调用的适配器是活动架构边界。
- 前端 Page、Component、Feature Model 和 API 各有职责；拆分以数据流可追踪为目标，不以文件数量为目标。
- 全局 CSS 具有源码顺序行为，不能用静态“未引用”或选择器同名直接批量删除。

## 5. 验证与停止条件

每批至少组合使用：静态引用复扫、类型/语法检查、单元和集成测试、API/OpenAPI 检查、前端构建、Benchmark 回归、仓库卫生检查、`git diff --check` 和临时产物清理。

出现以下情况停止自动处理：无法确认消费者；会改变 API、Schema、规则、Prompt 或法律结论；发现可能敏感数据；需要扩大权限或引入新架构；测试失败且无法证明与本批无关。

### 7.3 Benchmark 事实边界

- Product Smoke 检索 17 例：Recall@K 1.0、MRR 0.7471、跨法域污染率 0；它验证小规模固定产品链路，不代表一般检索能力。
- Product Smoke 生成 14 例：Issue Recall 0.7143；4 个 EU/US 案例为 0。Citation correctness 1.0 仅表示期望 source ID 覆盖，不等于法律相关性、蕴含性或充分性。
- 规模化合成 RAG 数据集包含 240 个正例和 140 个负例。Top-5 下 vector 与 hybrid 均为 Recall 0.150、Top1 0.133、MRR 0.140、SafeReject 0.243；两种模式结果完全相同，说明当前评测调用链没有体现有效的 hybrid 增益。
- 当前案例和期望来源主要是合成内部回归数据，法律 Gold 尚未经过专家确认。因此可以认定“评测入口可运行”，不能认定“RAG 已达到产品质量”或“法律结论已验证”。

### 7.4 收口结论与剩余边界

目录、入口、法域身份、测试组织、资源边界和活动文档已经达到结构治理收敛条件，可以冻结并进入正式 Git 收口。以下事项不应与结构治理混写为已完成：

1. 工作树仍包含大规模未提交移动和删除；正式基线必须经过暂存后的 rename/删除清单人工复核、分批提交和 Tag 才成立。
2. RAG 规模化指标、EU/US 生成 Issue 覆盖和法律 Gold 需要独立产品与领域专项处理。
3. Ruff、Mypy、ESLint 尚未形成可执行门禁；现阶段由 pytest、TypeScript build、卫生脚本和 diff check 提供基础保障。
4. 本地 `outputs/` 与 `storage/` 体积较大但未受 Git 管理；是否归档或清理属于运行数据策略，不应在源码提交中批量删除。

### 7.5 收口审计新增经验

- “目录治理通过”“测试通过”“产品指标达标”“法律结论正确”是四个不同结论，必须分别给证据。
- 小规模 Smoke 必须与规模化 Benchmark 同时观察；Smoke 满分不能覆盖长尾召回、拒答和跨模块退化。
- 测试产物必须使用隔离目录，并在记录结果后清理；有价值的摘要进入知识资产，运行文件继续留在忽略区。
- 最后一次治理审计必须同时给出通过项、真实弱项和未授权事项，不能为了宣布完成而隐藏能力差距。
