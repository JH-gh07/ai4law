## 2. 逐层落到类/函数

### 2.1 入口层

| 符号 | 位置 | 说明 |
|---|---|---|

### 2.2 容器层（`backend/core/container.py::AppContainer`）

```python
class AppContainer:
    def __init__(self, settings: Settings):
        self.engine           = build_engine(settings.database_url)       # SQLAlchemy engine
        self.session_factory  = build_session_factory(self.engine)         # sessionmaker
        self.websocket_manager = WebSocketManager()                        # WS 连接池
        self.task_dispatcher  = build_task_dispatcher(settings.task_mode)  # Inline/Threaded
        self.llm_client       = LLMClient(settings)                        # LLM 客户端
        self.file_service     = FileService(settings)                      # 上传/抽取
        self.report_service   = ReportService(settings)                    # 报告产物
        self.session_service  = SessionService()                           # 会话编排
        self.legal_api_service= DeliLegalService(settings)                 # 得理法搜
        self.diagnosis_service= DiagnosisSessionService(...)               # 诊断会话
        self.review_service   = ReviewService(...)                         # 文档审查
```

> 依赖注入方式：**手动构造器注入**（非框架自动），所有服务在 `AppContainer.__init__` 里 `new` 出来并互相接线。

### 2.3 模块运行器（三层，这是关键）

你图里的「模块运行器」实际是**三个正交的东西**，缺一不可：

**① 领域服务（`domains/<country>/<module>/service.py`）—— 业务如何算**

| 模块 | 类 | 主方法 | 规则引擎 | 智能体 |
|---|---|---|---|---|
| diagnosis | `DiagnosisService` | `evaluate()` | `decision_tree.json` | 4 |
| assessment | `AssessmentService` | `generate_report()` | WorkflowPipeline | 0 |
| pipia | `PIPIAService` | `generate_report()` | 专项 | 0 |
| cn_flow | `CNFlowService` | `generate_report()` | 流量向 | 0 |
| eu_scc | `EU_SCCService` | `generate_report()` | `scc_rule_engine.py` | 6 |
| bcr | `BCRService` | `generate_report()` | 双通道 | 10 |
| dpia | `DPIAService` | `generate_report()` | `need_detector` | 9 |
| tia | `TIAService` | `generate_report()` | 结构化四层 | 3 |
| us_14117 | `US14117Service` | `generate_report()` | `rule_engine.py` | 5 |
| cpra | `CPRAService` | `generate_report()` | `gap_rules.py` | 4 |
| review | `ReviewService` | `generate_from_request()` | `rulebook_loader` | 专项 |

每个领域服务都实现 `submit_async(payload) → AsyncAccepted`、`get_async_status(task_id)`、`retry_async(task_id)` 三个异步方法（见 §3.2）。

**② 异步执行器（`common/tasks/manager.py::InMemoryTaskManager`）—— 任务如何调度**

| 方法 | 作用 |
|---|---|
| `submit(runner)` | 提交同步 runner 到线程池 |
| `submit_with_trace(runner, trace_recorder, ...)` | 提交并绑定 TraceRecorder，发布 CREATED 事件 |
| `get(task_id)` / `get_or_raise(task_id)` | 查询快照（`TaskSnapshot`） |
| `retry(task_id)` / `cancel(task_id)` | 重试/取消 |
| `_execute(task_id)` | 线程池执行体：RUNNING → 执行 runner → COMPLETED/FAILED |
| `_persist_status(record)` | 状态落库到 `async_tasks` 表（task061 阶段四新增） |
| `_persist_manifest(record)` | 写 `run_manifest.json` |

**③ CLI 运行器（`harness/runner.py`）—— 案例如何验收**

| 符号 | 作用 |
|---|---|
| `_ADAPTER_DEFINITIONS` | 模块别名 → (package, request_name, service_name) 映射 |
| `ModuleAdapter.invoke()` | 分派到 `_generic_invoke` / `_diagnosis_invoke` / `_review_invoke` |
| `execute(module, case_id)` | 单案例执行：解析 case → 建 run_dir → invoke → 断言 → 写 manifest |
| `validators.validate_expected()` | 11 个断言操作符 |

## 3. 详细工作流

### 3.1 工作流 A：同步生成（`POST /cpra/generate` → 报告产物）

以 CPRA（同步端点）为例：

```
[1] 前端 lib/api/cpra 调 POST /api/v1/cpra/generate
        ↓
[2] cpra/router.py::generate_cpra(payload, db, current_user, container)
        │  dependencies=[Depends(require_healthy_llm)]  ← 健康检查
        ↓
[3] trace_sync("cpra", lambda: service.generate_report(payload))
        │  backend/common/trace/tracer.py::trace_sync
        │  → TraceRecorder(trace_dir=storage/traces/cpra_sync)
        │  → current_trace.set(recorder)  ← contextvar 注入
        ↓
[4] CPRAService.generate_report(payload)
        │  prepare_run(module="cpra", task_id=..., trace=...)  ← 绑定 SSEManager 订阅
        │  → 规则引擎 gap_rules → 智能体 → 章节生成 → render_artifacts
        ↓
[5] register_module_result_artifacts(db, container, user, "cpra", result)
        │  backend/services/artifact_registry.py::register_module_result_artifacts
        │  → 把 output_files 登记进 ReportArtifactModel
        ↓
[6] 返回 SCCReviewResult（含 chapters / output_files / report_path）
```

### 3.2 工作流 B：异步生成（`POST /eu_scc/generate_async` → SSE 推送 → 轮询）

这是 10 个异步模块的**主路径**，也是 task070 重点治理的对象：

```
[1] 前端 POST /api/v1/eu_scc/generate_async
        ↓
[2] eu_scc/router.py::generate_eu_scc_async(payload, db, current_user)
        │  service.submit_async(payload)  → EU_SCCService.submit_async
        │  claim_task_access(db, task_id, user_id, "eu_scc")  ← 写 task_ownerships
        ↓
[3] EU_SCCService.submit_async(payload):
        │  self.tasks = InMemoryTaskManager(module="eu_scc")
        │  trace_recorder = TraceRecorder(...)
        │  self.tasks.submit_with_trace(
        │      runner=lambda: self.generate_report(payload, task_id=..., trace=...),
        │      trace_recorder=trace_recorder,
        │      llm_client=self.llm_client,
        │      input_snapshot=payload,
        │  )
        ↓
[4] InMemoryTaskManager.submit_with_trace(...):
        │  trace_recorder.subscribe(sm.on_event)     ← 把 SSEManager 挂到 trace
        │  创建 _TaskRecord(state="CREATED")
        │  _persist_status(record)                    ← 写 async_tasks 表
        │  sm.publish(task_id, RunEvent(state=CREATED))  ← SSE 广播
        │  self._executor.submit(self._execute, task_id) ← 线程池启动
        │  返回 TaskSnapshot（含 task_id）
        ↓
[5] _execute(task_id)（在 ThreadPoolExecutor 线程里）:
        │  置 RUNNING → 发布 RUNNING → 持久化
        │  current_cancel_event.set(record.cancel_event)  ← 取消上下文
        │  result = record.runner()                        ← 真正跑 generate_report
        │  build_success_events → record("final"/"final_brief")
        │  synthesize_citation_map → write_citation_map_json
        │  置 COMPLETED → 发布 COMPLETED → 持久化
        │  （异常时：置 FAILED → 发布 FAILED → 持久化）
        ↓
[6] 前端 SSE 流 GET /api/v1/events/task/{task_id}/stream?token=...
        │  events.py::task_event_stream → SSEManager.subscribe(task_id, queue)
        │  → 每个 TraceRecorder.record() 都会触发 sm.on_event(run_event)
        │  → SSEManager.publish → 推送到 queue → yield 给 EventSource
        ↓
[7] 前端轮询 GET /api/v1/eu_scc/tasks/{task_id}
        │  get_eu_scc_task → require_task_access → service.get_async_status(task_id)
        │  → 若 status.result 存在，register_module_result_artifacts 登记产物
        │  → 返回 SCCAsyncStatus（含 result/error）
```

### 3.3 工作流 C：SSE 事件链路（`TraceRecorder.record → SSEManager.publish → EventSource`）

这是「实时进度」的完整链路：

```
TraceRecorder.record(name, payload)
  → _record_locked(name, payload)
      ├─ 写 trace/NNN_name.json（落盘）
      ├─ 生成 RunEvent(task_id, seq, event_type, detail)
      └─ for sub in self._subscribers: sub(run_event)   ← 调用 SSEManager.on_event
                                                              ↓
SSEManager.on_event(event)                                   ↓
  → publish(task_id, event)                                  ↓
      ├─ (有持久化) event = _event_log.append(...)           ↓
      ├─ 统一生成严格递增 transport_seq                       ↓
      └─ for q in self._task_queues[task_id]: q.put_nowait(event)  ↓
                                                                   ↓
events.py::_stream_events:                                          ↓
  event = await queue.get()                                        ↓
  yield f"id: {event.seq}\ndata: {event.model_dump_json()}\n\n"  → 前端 EventSource
```

### 3.4 工作流 D：CLI 案例验收（harness）

```
python -m backend.tests.harness.runner eu_scc 03_module_mismatch
  → runner.py::execute("eu_scc", "03_module_mismatch")
      ├─ _resolve_case_input(case)     读 benchmarks/cases/eu_scc/.../scenario.json 的 request
      ├─ _resolve_case_expected(case)  读 .../expected.json 的 harness
```

### 3.5 工作流 E：Review 文档审查（DB-backed，唯一不同）

`review`（document_review）是**唯一不用 `InMemoryTaskManager` 的模块**，它的任务状态存在 `ReviewTaskModel` 表，而不是内存：

```
POST /api/v1/review/generate_async
  → review router → ReviewService.submit_async_from_request(db, user_id, payload)
      ├─ _create_task_from_request(db, user_id, payload)  ← 写 ReviewTaskModel（PREPARING）
      ├─ self.task_dispatcher.dispatch(self._run_pipeline, task_id, user_id)
      │    └─ ThreadedTaskDispatcher.dispatch → 线程池跑 _run_pipeline
      └─ 返回 ReviewAsyncAccepted

_run_pipeline(task_id, user_id):  8 阶段
  PREPARING → SEGMENTING → CLASSIFYING → REVIEWING → SCORING →
  CONSISTENCY → AGGREGATING → COMPLETED
  （每阶段更新 ReviewTaskModel.status + progress）
```

> 这就是 task070 里「Review 适配」和「10 个异步模块」要区别对待的根因：Review 已经是**数据库权威状态**，而另外 10 个模块是**内存权威状态**（跨 worker 会 404）。

## 5. 关键设计判断（为什么长这样）

1. **两种异步范式并存**：10 个模块用 `InMemoryTaskManager`（快、简单、但内存态跨 worker 丢失），`review` 用 `ReviewTaskModel`（DB 态、可恢复）。task070 的核心就是把前者**也升级成 DB 权威状态**，收敛成一种。
2. **事件三源合一**：`TraceRecorder.record()` 是唯一事件发源地，`SSEManager` 是唯一分发器，`RunEvent` 是唯一事件体——保证 trace 落盘、SSE 推送、manifest 汇总三者同源一致。
3. **流水线是「回调注入」而非继承**：`WorkflowPipeline` 不做任何业务，只做「按固定顺序调 15 个回调」，业务逻辑全在领域服务注入的回调里——这是「策略注入」而非「模板方法继承」。
4. **`prepare_run`/`trace_sync` 用 contextvar 传递 TraceRecorder**：避免给每个 `generate_report` 显式传 trace 参数，让领域代码里能裸调 `trace.record()`。
5. **`models/`（ORM）与 `schemas/`（DTO）与 `domains/*/schema.py`（领域 DTO）三层分离**：持久化、HTTP 契约、领域模型各自独立演进。
