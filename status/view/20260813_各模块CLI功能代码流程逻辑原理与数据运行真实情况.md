## 1. 统一 CLI 执行框架（Harness）

### 1.1 一句话定位

所有 11 个模块的「命令行运行」都收敛到**同一个白盒执行器** `backend/harness/runner.py`。它不直接调用各模块的 HTTP 接口，而是**在进程内直接 import 各模块的 `service.py` + `schema.py`**，构造 Pydantic 请求对象，调用主方法（`generate_report` / `evaluate`），再用**声明式断言器** `validators.py` 校验输出，最后把「可观测性」落盘为 `run_manifest.json`。

### 1.2 命令入口

```bash
# 跑单个模块（默认跑该模块全部 CLI 案例）
python -m backend.harness.runner eu_scc

# 跑单个模块的单个案例
python -m backend.harness.runner eu_scc 03_module_mismatch

# 跑全部模块
python -m backend.harness.runner all

# 关闭 LLM（走纯规则/模板确定性路径，速度快，用于回归）
python -m backend.harness.runner all --no-llm

# 打开逐事件 trace 输出
python -m backend.harness.runner eu_scc --verbose-trace
```

关键参数（`runner.py` 的 `main()` → `argparse`）：
- `module`：`choices=["all", *sorted(MODULE_ADAPTERS)]`，共 11 个模块别名。
- `--no-llm`：服务构造时注入 `_DisabledLLM()` / `llm_client=None`，走确定性路径。
- `--quiet` / `--verbose-trace`：控制输出粒度。

### 1.3 核心数据结构与执行流程

**（A）`_ADAPTER_DEFINITIONS`**（`runner.py:97`）——模块别名到「包 + 请求/服务类」的映射，10 个标准模块 + 1 个特殊 review：

| 别名 | package（module_id） | 请求类 | 服务类 |
|---|---|---|---|
| diagnosis | cn.transfer_diagnosis | DiagnosisAnswers | DiagnosisService |
| assessment | cn.security_assessment | AssessmentRequest | AssessmentService |
| pipia | cn.pipia | PIPIARequest | PIPIAService |
| cn_flow | us.eo_14117_flow_review | CNFlowRequest | CNFlowService |
| eu_scc | eu.scc_review | SCCReviewRequest | EU_SCCService |
| bcr | eu.bcr_review | BCRRequest | BCRService |
| dpia | eu.dpia | DPIARequest | DPIAService |
| tia | eu.tia | TIARequest | TIAService |
| us_14117 | us.eo14117 | US14117Request | US14117Service |
| cpra | us.cpra | CPRARequest | CPRAService |
| review | cn.document_review | （special） | （special） |

**（B）`ModuleAdapter.invoke()` 三种分派**（`runner.py:203/228/267`）：
- `_generic_invoke(alias, package, request_name, service_name)`：标准模块。`importlib` 动态加载 `backend.domains.<package>.schema.<Request>` 与 `.service.<Service>`，构造服务 → `generate_report(payload)`。
- `_diagnosis_invoke()`：diagnosis 特例。主方法不是 `generate_report` 而是 `DiagnosisService.evaluate(answers, trace=recorder)`。
- `_review_invoke()`：review 特例。走 `container.review_service.generate_from_request(...)`，因为文档审查服务依赖 SQLite 持久化上下文（`ReviewTaskModel` 等）。

**（C）`execute()` 主流程**（每案例一次）：
1. 解析案例定义 `backend/tests/<module>/cases/<case_id>.json`，其中 `scenario_path` 指向共享基准场景 `benchmarks/cases/<module>/<scenario>/<scenario>.json`（真实输入），`expected_path` 指向 `expected.json`（断言期望）。
2. `_ensure_database_schema()`：初始化 SQLite schema（review 等模块需要）。
3. 创建运行目录 `runs/<module>/<run_id>/`，`run_id` 形如 `20260812_014934_947509_02_geolocation_yellow`（时间戳 + 随机 + case_id）。
4. `adapter.invoke()` → 拿到 Pydantic 结果对象。
5. `_serialize_result()` → `model_dump(mode="json")`，并把 `chapters/regulations/risk_matrix/mitigation_plan` 额外冗余 `*_count` 字段供断言用。
6. `validate_expected()` → 跑断言；全过 → `PASS`，否则重试（默认 `max_attempts=1`）后 `FAIL`。
7. 写 `run_manifest.json`：`status` / `duration_ms` / `provider_snapshot`（LLM 模式与模型指纹）/ `input`（字段与 sha256）/ `output` / `observability`（`event_count`、`llm_calls`、`tokens`、`fallback_count`）。

### 1.4 声明式断言器（`backend/harness/validators.py`）

`expected.json` 里声明要验证的断言，由 `validate_expected()` 逐条执行。共 **11 个操作符**：

| 操作符 | 含义 |
|---|---|
| `result_not_empty` | 结果非空 |
| `fields_equal` | 指定字段与期望值严格相等 |
| `fields_present` | 指定字段存在且非空 |
| `min_counts` / `max_counts` | 列表类字段（issues/chapters/findings…）数量下界/上界 |
| `list_contains` / `list_excludes` | 列表包含/不包含指定项 |
| `output_formats` | 输出文件格式存在性（markdown/docx/pdf…） |
| `output_roles_contains` | 附件角色（file_role）包含指定值 |
| `profile_contains` | 画像字段包含指定关键字 |
| `legal_basis_contains` | 法律依据字段包含指定条款 |

> 断言数量即 `case_inventory.json` 里每案例的 `assertions` 值；本次全量统计为 **26 个 CLI 案例 / 603 条断言 / 28 个前端案例**。当前 CLI 实测 **24 PASS / 2 FAIL**（2 个失败均在 `pipia`，见 §2.3）。

## 2. 逐模块 CLI 功能流程详解

### 2.1 diagnosis —— 跨境传输路径诊断（规则优先）

- **代码地址**
  - 服务：`backend/domains/cn/transfer_diagnosis/service.py`（主方法 `evaluate`）
  - 规则引擎：`backend/domains/cn/transfer_diagnosis/rule_engine.py` + 决策树 `decision_tree.json`
  - 智能体：`backend/domains/cn/transfer_diagnosis/agents/`（`important_data_agent`、`pi_classify_agent`、`exemption_agent`、`clarification_agent`）
- **流程逻辑**
  1. `DiagnosisService.evaluate(answers)` 接收答题输入，做字段规范化。
  2. 对「未知/缺失」的事实，按需调用 LLM 智能体补全（`--no-llm` 下跳过）：重要数据识别、个人信息分类、豁免判定、澄清提问。
  3. `DiagnosisRuleEngine.evaluate(facts)` 加载 `decision_tree.json`，**首条命中**返回诊断结论（推荐路径 / 触发条件 / 法律依据 / 是否需人工）。
  4. 输出 `DiagnosisResult`：`recommended_path`、`matched_rule_id`、`legal_basis`、`missing_facts`、`requires_human_review` 等。
- **真实运行**：`01_scc_path` → `PASS`，`no_llm` 模式 366ms / 3 事件 / 0 LLM 调用，风险 `LOW`（纯规则路径，零 token）。

### 2.2 assessment —— 数据安全评估（WorkflowPipeline 流水线）

- **代码地址**
  - 服务：`backend/domains/cn/security_assessment/service.py`（主方法 `generate_report`）
  - 流水线：`_build_pipeline()` → `backend/common/workflow/pipeline.py` 的 `WorkflowPipeline`
  - 问题构建：`backend/domains/cn/security_assessment/issue_builder.py`（`build_assessment_issues` / `_issue`）
- **流程逻辑**
  1. `generate_report(payload)` 解析评估请求，构建数据类型清单（`_build_data_type_lists`）。
  2. `_build_pipeline()` 组装 `WorkflowPipeline`，`run()` 依次执行：profile 抽取 → 诊断 → facts → 法规检索 → issues → evidence → per_issue_rag → context_pack → 分章节生成 → 一致性校验 → 对齐 → repair → 渲染。
  3. 输出 `AssessmentResult`（8 章节 markdown + docx）。
- **真实运行**：`02_structured` → `PASS`，`live` 模式（siliconflow / DeepSeek-V3.2）400s / 36 事件 / 10 LLM 调用 / 50306 tokens / 0 fallback。

### 2.3 pipia —— 个人信息保护影响评估（专项服务）

- **代码地址**
  - 服务：`backend/domains/cn/pipia/service.py`（主方法 `generate_report`，含 `_build_facts` / `_build_structured_issues` / `_build_evidence_chain` / `_issue`）
- **流程逻辑**
  1. `generate_report` 解析 PIPIA 请求（route_type、company_profile、transfer_context、personal_info_scope、rights_protection、emergency_plan、attachments）。
  2. `_build_facts()` 汇总事实；`_build_structured_issues()` 结构化生成问题清单（含标准合同路径 / 认证路径分支）。
  3. `_build_evidence_chain()` 建立证据链；最后 `_build_template_mapping()` 渲染章节（7 章节）。
  4. `--no-llm` 下走确定性模板，`live` 下由 LLM 生成建议措辞。
- **真实运行（2026-08-13 更新）**：`01_minimal` / `03_source_derived_scc_draft` / `04_hr_exemption` → `PASS`；`02_source_case_missing_scc`（30 通过 / 3 失败）、`05_certification_eurocert`（29 通过 / 1 失败）→ `FAIL`。失败为 pipia 专项整改在途（新增 `04_hr_exemption`、`05_certification_eurocert` 案例与 `schema.py`/`service.py` 改动）导致，非 harness 迁移引入；`no_llm` 模式 8 事件 / 0 LLM 调用 / 0 token。

### 2.5 eu_scc —— 欧盟标准合同条款审查（规则 + 多智能体 + 流水线）

- **代码地址**
  - 服务：`backend/domains/eu/scc_review/service.py`（主方法 `generate_report`）
  - 规则引擎：`backend/domains/eu/scc_review/scc_rule_engine.py`（`run_eu_scc_rule_engine`）

- **流程逻辑**
  1. `generate_report` → `_use_uploaded_scc_document()`（若上传了 SCC 文档则优先采用）→ `parse_scc_document()` 解析条款。
