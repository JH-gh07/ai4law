## 一、问题重新定义

本 issue 要纠正的核心不是“BCR 内容写得对不对”，而是：

> 同一份 BCR 报告进入网页、DOCX 和 PDF 后，没有形成专业法律报告应有的视觉结构。标题、正文、finding、整改条款、表格和多级编号未被当作结构化排版对象，而是被当作一串 Markdown 或普通字符串处理，最终造成三种载体各自失真。

三张截图共同体现的是一条排版故障链：

```text
报告数据先被拼成 Markdown 字符串
        ↓
网页：DOCX 抽取为纯文本，再按 Markdown 猜测渲染
DOCX：字符串直接替换进普通段落
PDF：自制逐行 Markdown 解析后塞入 A4 固定版面
        ↓
网页、DOCX、PDF 内容大致相同，但视觉层级、列表、表格和分页都不合格
```

因此，不能把本问题简化为：

- 字体太大；
- 行距不舒服；
- CSS 不美观；
- PDF 缩放比例不对；
- 换一个模板即可。

这些只是表象。根本问题是报告缺少可跨格式渲染的结构化排版语义。

## 四、网页排版故障链

### 4.1 DOCX 被错误降级成纯文本

[artifacts.py:109](../../backend/api/v1/endpoints/artifacts.py#L109) 将 `.docx` 与 `.md/.txt/.json/.csv` 一并返回：

```python
render_mode="text"
content=parser.parse_text(str(resolved))
```

[file_parser.py:36](../../backend/common/storage/file_parser.py#L36) 只提取：

```text
paragraph.text
table cell.text
```

以下 Word 排版信息全部丢失：

- Heading 级别；
- 字体和字号；
- 段前段后距；
- 列表编号和缩进；
- 表格行列和边框；
- 页眉页脚；
- 分页符和 keep-with-next；
- 脚注与批注；
- section 页面设置。

因此，前端收到的不是“可预览 Word 文档”，而是“从 Word 中抽出的字符串”。

### 4.2 纯文本又被按 Markdown 二次解释

[WorkspaceShell.tsx:988](../../frontend/src/components/workspace/WorkspaceShell.tsx#L988) 对默认文本 artifact 使用 `CitationMarkdownRenderer` 或 `ReactMarkdown`。

实际链路为：

```text
DOCX
→ FileParser 抽取字符串
→ ArtifactPreview(render_mode=text)
→ normalizeMarkdownForRender()
→ Markdown renderer
```

这会产生两个问题：

1. 原有 Word 结构已经丢失，无法恢复；
2. 抽取出的 `|`、`-`、数字编号又会被当作 Markdown 语法重新解释。

所以第一张截图不是“DOCX 没加载好”，而是产品当前根本没有 DOCX 忠实预览能力。

### 4.3 网页同一内容存在双重容器

[WorkspaceShell.tsx:331](../../frontend/src/components/workspace/WorkspaceShell.tsx#L331) 会把文本 artifact 包装为报告 section；[WorkspaceShell.tsx:1271](../../frontend/src/components/workspace/WorkspaceShell.tsx#L1271) 又在“导出文件预览”中显示同一 artifact。

```text
artifactPreview.content
├─ buildSectionsFromArtifactPreview() → 正文容器
└─ renderTextArtifactPreview()        → 导出预览容器
```

在缺少结构化 chapters 的恢复场景中，页面可能将同一文本展示两次。即使用户当前截图只截到一次，这个布局链路仍然客观存在。

### 4.4 CSS 放大了长文阅读问题

网页正文样式位于 [workspace.css:1169](../../frontend/src/styles/app/workspace.css#L1169) 至 [workspace.css:1339](../../frontend/src/styles/app/workspace.css#L1339)。关键事实为：

- `.workspace-report-richtext` 没有适合长文阅读的 `max-width`；
- paragraph 使用 `text-align: justify`；
- table 固定 `width: 100%`；
- table 没有独立横向滚动 wrapper；
- table 没有按列类型设置最小宽度；
- finding 没有专用结构，只继承通用 Markdown 表格/列表样式；
- 所有 chapter 都被放进圆角卡片，长报告仍然按短内容卡片处理；
- 小屏规则只缩小字号和 padding，没有改变六列表格的信息结构。

因此，即使后端返回正确 Markdown，网页也缺少针对长法律报告的专用版式策略。

## 五、DOCX 排版故障链

### 5.1 模板本身没有完整报告结构

[3.2_bcr_review_template_v0.docx](../../resources/templates/eu/3.2_bcr_review_template_v0.docx) 实际只有 11 个段落、0 个表格：

```text
Title   BCR-C Compliance Review Report
Normal  {{bcr_subject}}
Normal  {{review_scope}}
Normal  {{review_date}}
Normal  Overall Rating: {{overall_rating}}
Normal  Key Findings: {{key_findings}}
Normal  Detailed: {{detailed_findings}}
Normal  High Risk: {{high_risk_items}}
Normal  Medium Risk: {{medium_risk_items}}
Normal  Low Risk: {{low_risk_items}}
Normal  Remediation: {{remediation_roadmap}}
```

它缺少：

- 封面和报告元数据区；
- Heading 1/2/3 层级；
- 页眉页脚与页码；
- finding 表格或 finding 分块容器；
- 风险标签样式；
- 法律依据/证据/建议的版式分区；
- 多级法律条款编号；
- 跨页表头和分页控制；
- 附录和引用样式。

所以即使字符串替换完全成功，产物也只能是“填充后的简易模板”，不会自然变成专业报告。

### 5.2 Markdown 表格被写入普通段落

[service.py:52](../../backend/domains/eu/bcr_review/service.py#L52) 将 18 条 finding 编码成 Markdown 六列表格；[service.py:813](../../backend/domains/eu/bcr_review/service.py#L813) 把它放入 `detailed_findings`。

[report.py:69](../../backend/common/render/report.py#L69) 的 DOCX renderer 只遍历既有段落并做字符串替换。[report.py:86](../../backend/common/render/report.py#L86) 遇到换行时只插入 line break：

```python
paragraph.add_run().add_break()
```

它没有调用 Word 原生的：

- `add_table()`；
- `add_heading()`；
- `List Bullet` / `List Number`；
- paragraph formatting；
- section/page break；
- repeat table header。

真实输出因此为：

```text
普通段落：11
Word 表格：0
```

这直接解释了第一张截图中 Markdown 表格源码连续出现的问题。

### 5.3 多级条款无法成为 Word 多级列表

整改建议以一个长字符串进入 `{{remediation_roadmap}}`。即使字符串内含：

```text
- finding
1. 主条款
(a) 子条款
2. 后续条款
```

DOCX renderer 也只会将它们作为同一段落中的换行，不会生成 Word numbering definitions。因此：

- 编号无法自动续排；
- 续行无法悬挂缩进；
- 子条款无法建立层级；
- 跨页时编号和正文关系不稳定；
- 用户在 Word 中继续编辑时无法利用原生列表行为。

## 六、PDF 排版故障链

### 6.1 固定 A4 竖版承载不下六列长文本

[artifacts.py:15](../../backend/common/render/artifacts.py#L15) 使用：

```python
SimpleDocTemplate(
    pagesize=A4,
    leftMargin=40,
    rightMargin=40,
    topMargin=40,
    bottomMargin=40,
)
```

可用宽度约为：

```text
595pt - 40pt - 40pt = 515pt
```

这 515pt 被用于同时放置：

```text
检查项 | 主题 | 风险 | 现状 | 整改建议 | 法律依据
```

其中“现状、整改建议、法律依据”都是长文本列。在 A4 竖版中要求六列同时可读，本身就是不合理的版式约束。

### 6.2 列宽算法没有最小可读宽度

[artifacts.py:288](../../backend/common/render/artifacts.py#L288) 依据每列最大字符串长度计算权重；[artifacts.py:294](../../backend/common/render/artifacts.py#L294) 再按比例分配全部可用宽度。

算法没有：

- ID 列最小宽度；
- 风险列最小宽度；
- 单词不可逐字符断裂约束；
- 文字列最大宽度；
- 横向页面切换阈值；
- 超过列数后改用 finding 分块的策略。

实际 PDF 文本层因此出现：

```text
BCR
-C-1
.1

HIG
H

ME
DIU
M
```

这是实际 PDF 中的断词，不是截图渲染问题。

### 6.3 表格选择本身不适合长 finding

每条 finding 同时包含主题、现状、建议和法律依据。将 18 条 finding 全部放入六列表格，会产生：

- 单元格高度巨大；
- 一行内容可能跨越大半页；
- 表头与当前行关系变弱；
- 读者横向来回移动视线；
- 中英文单词断裂；
- 页面利用率看似很高，实际扫描效率很低。

这类内容更适合：

```text
摘要表：编号 / 风险 / 主题 / 状态
        +
详细 finding：每条独立分块展示现状、证据、依据和建议
```

问题不是表格样式颜色，而是信息密度和版式类型选择错误。

### 6.4 PDF 解析器只支持平铺列表

[artifacts.py:227](../../backend/common/render/artifacts.py#L227) 连续读取 `- ` 作为无序列表；[artifacts.py:240](../../backend/common/render/artifacts.py#L240) 连续读取 `数字. ` 作为有序列表。

它没有 Markdown AST，也不支持：

- 列表项内的 continuation paragraph；
- 无序列表内嵌有序列表；
- 法律条款 `(a)/(b)/(c)` 层级；
- 任意深度缩进；
- 列表项跨页保持；
- 标题与首段 keep-with-next。

### 6.5 源 Markdown 的嵌套语义也不完整

实际 Markdown 中，一个 finding 条目后直接出现：

```markdown
- **BCR-SHARED-1 ...**：Security of Processing
1. GlobalTech Inc. ...

(a) ...
(b) ...
2. In assessing ...
3. The specific security measures ...
```

这些 `1./2./3.` 没有缩进到外层 bullet 下，`(a)/(b)` 也不是标准 Markdown 子列表。通用逐行 parser 只能把它拆成：

```text
一个 bullet list
一个 numbered list
四个普通段落
另一个 numbered list
```

这正是第二张截图中“大圆点 + 孤立 1 + 普通 (a)-(d) + 再次编号”的直接原因。

### 6.6 PDF 缺少出版级分页控制

当前 renderer 没有明确实现：

- heading 与后续正文不得分离；
- finding 标题不得孤立在页尾；
- 短 finding 尽量整块排版；
- 长 finding 可跨页但重复身份标题；
- 表格跨页重复表头后的上下文提示；
- 页码、报告名称、保密级别页眉页脚；
- widow/orphan 控制；
- 多级编号跨页连续。

所以即使文字没有断裂，当前 PDF 仍未达到正式法律报告排版标准。

## 七、跨格式共同根因

### 7.1 数据层提前绑定 Markdown 表现形式

BCR service 构造的是：

```text
detailed_findings: Markdown table string
remediation_roadmap: Markdown headings + lists string
```

而不是：

```text
Report
├─ metadata
├─ executive_summary
├─ findings[]
│  ├─ id
│  ├─ risk
│  ├─ title
│  ├─ current_state
│  ├─ evidence[]
│  ├─ legal_basis[]
│  └─ recommendation
└─ remediation_sections[]
   └─ clauses[] / subclauses[]
```

一旦 service 提前生成 Markdown，DOCX 和 PDF 就只能猜测字符串的结构。

### 7.2 三种载体没有各自的版式适配器

目前实际情况是：

```text
网页：Markdown renderer + 通用 CSS
DOCX：占位符字符串替换
PDF：自制行级 Markdown parser
```

正确边界应是：

```text
同一份结构化报告数据
├─ Web renderer：屏幕阅读、锚点、折叠、响应式表格
├─ DOCX renderer：Word 原生样式、列表、表格、分页
└─ PDF renderer：固定版面、可读行宽、分页和页眉页脚
```

三种格式应保持内容和编号一致，但不应该强行使用完全相同的布局。

### 7.3 当前模板只是字段容器，不是排版系统

DOCX 模板和 Markdown 模板解决的是“字段放在哪里”，没有完整定义：

- 信息层级；
- finding 的重复结构；
- 长文本排版；
- 多级编号；
- 表格降级；
- 分页；
- 不同载体的适配策略。

因此“换一个更漂亮的模板”仍不能解决结构丢失问题。

## 八、排版问题与内容问题的边界

为避免 issue067 再次跑偏，以下问题不纳入本 issue：

| 问题 | 是否属于 issue067 | 理由 |
|---|---|---|
| 六列表格挤压、异常断词 | 是 | 固定版面和列宽策略问题 |
| 大项目符号、编号漂移、缩进混乱 | 是 | 列表结构和样式问题 |
| DOCX 没有 Word 原生表格 | 是 | 文档结构与排版问题 |
| 网页把 DOCX 当 Markdown 文本 | 是 | 预览格式路由与版式真实性问题 |
| 长行、文字墙、缺少 finding 分块 | 是 | 屏幕阅读版式问题 |
| 占位符是否应该出现 | 否 | 内容完整性问题，应另设 issue |
| 法律依据是否正确 | 否 | 法律内容质量问题 |
| finding 与建议是否匹配 | 否 | 业务逻辑与内容正确性问题 |
| 告警数、证据数、风险 KPI | 否 | 状态与结果适配问题 |
| RUNNING 与 COMPLETED 冲突 | 否 | 任务状态口径问题 |
| localStorage 超限 | 否 | task066 的状态持久化问题 |

内容中的长英文、占位符或复杂条款可以作为排版压力样本，但 issue067 只评价它们如何被布局，不判断其法律内容是否正确。

## 九、为什么只改 CSS 不够

CSS 只能调整网页，无法改变：

- DOCX 的 11 段、0 表格结构；
- Word 多级编号缺失；
- PDF 的 A4 六列表格算法；
- PDF 的平铺列表解析；
- Markdown 字符串提前绑定格式；
- PDF 分页和页眉页脚。

只改 CSS 最多能改善：

- 网页字号；
- 网页行距；
- 网页卡片间距；
- 网页表格横向滚动。

它不能完成跨格式排版纠正。

## 十、当前测试为何没有拦截排版退化

现有 BCR 测试主要验证：

- Markdown 表格字符串存在；
- DOCX 文件存在且非空；
- PDF 以 `%PDF` 开头；
- PDF 至少一页；
- ZIP 包含相应文件。

这些测试证明“文件生成了”，不证明“文件可读”。缺失的排版验核包括：

### 10.1 DOCX 结构门禁

- Heading 1/2/3 数量和顺序；
- Word 原生表格数量；
- 原生多级列表和编号定义；
- 页眉、页脚、页码；
- section 页面尺寸和页边距；
- 禁止 Markdown 表格分隔符出现在普通段落；
- finding 标题与正文的样式关系；
- 分页控制属性。

### 10.2 PDF 结构与视觉门禁

- 页面尺寸和方向；
- 文本层不得出现 `HIG\nH`、`ME\nDIU\nM` 等异常断词；
- ID 不得逐段拆成 `BCR / -C-1 / .1`；
- 标题不得孤立在页尾；
- 列表编号连续、层级正确；
- 表格/分块不得越界或相互覆盖；
- 每页截图的视觉回归；
- 页面像素非空、内容边界在页框内。

### 10.3 网页排版门禁

- 正文容器可读行宽；
- 六列表格在窄屏有明确降级方式；
- 不出现同一 artifact 的双重正文；
- DOCX 预览明确标识“文本抽取”或使用忠实预览；
- finding 能按编号、风险、主题、依据、建议扫描；
- 桌面和移动 viewport 无横向页面溢出；
- 实际浏览器截图验收。

## 十一、排版纠正应达到的理想效果

### 11.1 网页版

网页不应模拟一张纸，而应发挥屏幕能力：

```text
报告标题与元数据
综合评级与摘要
风险筛选 / 章节导航
finding 摘要列表
finding 详情分块
  编号 + 风险标签 + 标题
  现状
  证据
  法律依据
  整改建议
建议条款（可折叠的多级条款）
引用与附件
```

关键要求：

- 正文设置稳定的可读行宽，而不是填满整个中栏；
- 长表格使用横向滚动、列冻结或移动端分块；
- finding 作为重复信息单元，不放在嵌套卡片中；
- 多级法律条款保留原始编号和缩进；
- 文档正文与导出文件入口分开，不重复全文；
- 页面宽度改变时，结构降级而不只是缩小字体。

### 11.2 DOCX 版

DOCX 必须是可继续编辑的 Word 原生文档：

- 封面/标题页；
- 报告元数据表；
- Heading 1/2/3；
- 自动目录所需的 heading outline level；
- finding 摘要采用原生表格；
- finding 详情采用标题 + 字段段落或两列表格；
- 多级建议条款采用 Word numbering；
- 页眉、页脚、页码；
- 表头跨页重复；
- 标题 keep-with-next；
- 适合打印和二次编辑的字体、行距和段距。

### 11.3 PDF 版

PDF 应是稳定的交付版，不照搬 DOCX 或网页布局：

- A4 竖版只保留适合竖版的信息密度；
- 摘要表最多保留少量短列；
- 详细 finding 使用纵向分块，不采用六列长文本表格；
- 多级编号作为结构化 flowable 渲染；
- 页眉页脚显示报告名、版本和页码；
- heading、finding 标题与首段保持；
- 长 finding 跨页时保持身份提示；
- 中英文采用明确字体方案；
- 避免逐字断词、孤立编号和异常大 bullet。

## 十二、排版验核的可量化判定标准

后续 task067 应将以下标准转成自动测试或人工截图验收，不能只写“更美观”。

### 12.1 网页

- 正文在桌面 viewport 下具有明确 `max-width`；
- 页面本身无横向滚动；
- 宽表仅在自身容器中滚动或转为分块；
- finding ID、风险、标题在首屏宽度内可完整辨识；
- 多级列表至少支持三级且编号不重置；
- 同一正文不重复展示；
- `1280×800`、`1440×900`、`390×844` 三类 viewport 截图通过；
- 控制台无渲染错误。

### 12.2 DOCX

- Markdown 表格源码不得出现在普通段落；
- 至少存在可识别的 Heading 层级；
- 摘要表是 Word 原生 table；
- 建议条款使用原生编号，不是手写数字字符串；
- 标题、表格、列表和正文样式可通过 `python-docx` 自动检查；
- 转 PDF 后无标题孤行、表格越界和编号漂移；
- Word/LibreOffice 打开后版式一致性人工验收通过。

### 12.3 PDF

- 文本层不得出现已知异常断词模式；
- ID 和风险等级不得逐字符换行；
- 表格不超出页面边界；
- 列表编号连续且缩进层级一致；
- 标题不单独落在页尾；
- 每页 raster screenshot 无裁切、重叠、空白页；
- PDF 页面像素检查和人工视觉验收同时通过；
- 页面总数变化需要有合理解释，不能以压缩字号换取页数减少。

### 12.4 三格式一致性

- finding 数量一致；
- finding 顺序一致；
- finding ID 和风险等级一致；
- 章节顺序一致；
- 多级条款编号语义一致；
- 允许布局不同，但不允许因布局转换丢段、重复段或改变编号归属。

## 十三、问题严重性排序

| 优先级 | 排版问题 | 原因 |
|---|---|---|
| P0 | DOCX 将 Markdown 表格写入普通段落 | 下载文件本身结构错误，无法靠前端修复 |
| P0 | PDF 六列长表造成 ID/风险逐字断裂 | 正式交付文件不可有效扫描 |
| P0 | 多级条款编号和层级丢失 | 可能改变读者对条款从属关系的理解 |
| P1 | 网页把 DOCX 抽取文本当 Markdown | 预览不忠实于文件，且产生二次解释 |
| P1 | 网页长文无可读行宽、finding 无专用结构 | 高频审阅体验不合格 |
| P1 | PDF 缺少分页、页眉页脚和标题保持 | 正式报告完成度不足 |
| P2 | 同一 artifact 可能重复展示 | 页面冗余，干扰阅读 |
| P2 | 中英文混排与 bullet 比例不协调 | 影响专业观感和节奏 |
