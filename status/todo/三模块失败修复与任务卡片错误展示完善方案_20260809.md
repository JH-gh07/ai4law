# 三模块失败修复与任务卡片错误展示完善方案

> 日期：2026-08-09
> 状态：方案，待执行

## 一、问题全景

三个用户功能（文档专项智能审查、SCC 审查、BCR 审核）的任务卡片在 `TaskSpacesPage` 中统一显示为 `FAIL`，没有区分"执行中失败"和"从未执行成功"，也没有展示具体失败原因。

### 1.1 三个真实失败根因

| 模块 | 卡片显示 | 真实错误 | 代码位置 |
|---|---|---|---|
| 文档专项智能审查 `REVIEW` | `FAIL` | `Uploaded file path is outside storage directory` | `backend/domains/cn/document_review/service.py:728` — 上传文件路径不在 storage 目录内 |
| SCC 审查 `EU_SCC` | `FAIL` | `ValidationError: IssueItem.recommended_action — String should have at least 1 character` | `backend/common/workflow/issues.py:128` — `IssueItem.recommended_action` 字段 `min_length=1`，SCC 问题构造时 `recommended_action` 为空字符串 |
| BCR 审核 `BCR` | `FAIL` | `TypeError: BCRTiaReasoningAgent.run() got an unexpected keyword argument 'tia_section'` | `backend/domains/eu/bcr_review/service.py:345` 传参 `tia_section=..., gov_access_section=...`，Agent 实际签名是 `run(self, tia_text: str, has_tia_document: bool = False)` |

### 1.2 前端展示链路

**卡片状态渲染：** `TaskSpacesPage.tsx:311-325`

```ts
latestRun.state === "success" ? "OK" : "FAIL"
```

五态逻辑：`idle → running → success/failed/unreachable`，非 `success`/`running` 全部显示 `FAIL`。

**状态映射：** `getRunLifecycleState()` 将 `ModuleRun` 映射为展示五态，`error` 字段在映射中**被丢弃**。

**数据恢复：** `app-store.tsx:390-428` — `buildRecoveryStateFromRuns()` 从后端 `/me` 接口读取历史任务，`ModuleRun.error` 字段保留了后端传来的错误信息（`me.py:189`），但前端卡片渲染**没有消费 `error` 字段**。

**后端端：** `me.py:173-191` — `_build_recovered_run()` 中：
- `success` = `task.status.lower() in {"completed", "succeeded"}`
- `error` = `task.status`（当非 success 且非 running 时）— **保留原始失败原因**

也就是说后端已经把错误信息传给了前端，前端 `ModuleRun.error` 字段有值，但 `TaskSpacesPage` 卡片没有展示它。

### 1.3 历史任务保留机制

`me.py:173-191` → `app-store.tsx:383-427` 这条链路会把数据库中**所有失败/完成的任务**恢复为前端 `ModuleRun` + `TaskSpace`。这不是系统自动重复执行，而是**历史记录恢复**——失败卡片会持续显示，直到被手动删除。

## 二、修复方案

### 第 1 步：Review — 文件路径校验修复

**文件：** `backend/domains/cn/document_review/service.py:718-734`

**当前逻辑：** `_resolve_uploaded_path()` 仅允许 storage 目录下的文件。用户上传的文件路径如果不在 storage 内，直接抛 `400`。

**修复：** 前端上传文件后、提交审核任务前，将文件**先复制到 storage 目录**，再提交相对路径。或者在后端 `_resolve_uploaded_path` 中增加 fallback：非 storage 路径时自动 copy 到 storage（当前代码 `_copy_external_preset_into_storage` 已存在此逻辑，需确认其覆盖范围是否够）。

**具体改法：**

1. 前端 `uploadFile()` 返回的 `uploaded_path` 必须是 storage 内的路径
2. 或者在 `review_service.py` 的 `_resolve_uploaded_path` 中，`_copy_external_preset_into_storage` 的 fallback 路径已完成复制后，返回 storage 内新路径而不是继续抛异常

**验收：** 上传任意 `.docx` 文件 → 提交审核 → 任务状态 `OK`，不再显示 `FAIL`。

---

### 第 2 步：SCC — `recommended_action` 必填字段修复

**文件：** `backend/domains/eu/scc_review/issue_builder.py`

**当前逻辑：** `_issue()` 辅助函数构造 `IssueItem`，其中 `recommended_action` 来自调用方参数。某些调用路径传入了空字符串，触发 Pydantic `min_length=1` 校验失败。

**修复：** 在 `_issue()` 函数中加防御性默认值——如果 `recommended_action` 为空或全是空白，使用统一默认文本：

```python
def _issue(..., recommended_action, ...) -> IssueItem:
    if not (recommended_action or "").strip():
        recommended_action = "依据 SCC 标准条款进行合规整改，并在补充条款中明确双方责任。"
    return IssueItem(
        ...,
        recommended_action=recommended_action,
        ...
    )
```

或者遍历 `build_eu_scc_issues()` 的每个调用路径，确保每条 `_issue()` 调用都传入了非空 `recommended_action`。

**验收：** SCC 审查任务运行后 `citation_map.json` 正常生成，任务状态 `OK`。

---

### 第 3 步：BCR — Agent 参数签名对齐

**文件：** `backend/domains/eu/bcr_review/service.py:344-347`

**当前逻辑：** 调用 `self.agents["tia_reasoning"].run(tia_section=..., gov_access_section=..., legal_refs=...)`。
Agent 实际签名是 `run(self, tia_text: str, has_tia_document: bool = False)`，不接受 `tia_section`、`gov_access_section`、`legal_refs` 参数。

**修复：** 将 service 调用改为匹配 Agent 实际签名：

```python
agent_tia = self.agents["tia_reasoning"].run(
    tia_text=tia_text + "\n" + gov_text,
    has_tia_document=bool(tia_text),
)
```

`tia_text` 和 `gov_text` 已在 L341-342 按章节标题过滤拼接好，直接合并传入。`legal_refs` 参数 Agent 不需要（其规则检查是纯正则不依赖外部引用），直接移除。

**验收：** BCR 审核任务运行后正常生成报告，任务状态 `OK`。

---

### 第 4 步：前端任务卡片增加失败原因摘要

**文件：** `frontend/src/pages/TaskSpacesPage.tsx:295-332`

**当前逻辑：** 卡片仅显示 `FAIL · MODULE`，不展示 `error` 字段。

**修复：** `latestRunByTask` Map 目前只存 `state`/`module`/`at` 三个字段，需要增加 `error` 字段：

1. **`latestRunByTask` Map value 类型扩展** — 增加 `error?: string`
2. **构建时填充** — 从 `run.error` 读取
3. **卡片渲染** — `FAIL` 状态行增加一行红色小字展示 `error`，截断至 80 字符

```ts
// L71: 扩展 Map value 类型
const map = new Map<string, {
  state: "idle" | "running" | "success" | "failed" | "unreachable";
  module: string;
  at: string;
  error?: string;  // 新增
}>();

// L76: 填充 error
map.set(run.taskSpaceId, {
  state: getRunLifecycleState(run),
  module: run.module,
  at,
  error: run.error,  // 新增
});

// L325 后新增：
{latestRun.error && (
  <span className="tasks-error-summary">
    {latestRun.error.length > 80
      ? latestRun.error.slice(0, 80) + "…"
      : latestRun.error}
  </span>
)}
```

**验收：**
- REVIEW 卡片显示 `Uploaded file path is outside storage directory`
- EU_SCC 卡片显示 `String should have at least 1 character` 或更友好中文
- BCR 卡片显示 `run() got an unexpected keyword argument 'tia_section'`

---

### 第 5 步：对历史失败任务提供"重新运行"/"删除"操作

**文件：** `frontend/src/pages/TaskSpacesPage.tsx` — 卡片操作区

**当前逻辑：** 失败卡片只有点击进入工作区一个操作，没有"重新运行"或"删除"快捷入口。

**修复：** 在卡片底部增加操作按钮行：

```tsx
{latestRun?.state === "failed" && (
  <div className="tasks-card-actions">
    <button onClick={() => handleRetryTask(task.id)}>重新运行</button>
    <button onClick={() => handleDeleteTask(task.id)}>删除</button>
  </div>
)}
```

"重新运行"需要跳转到工作区并自动触发 `runModule`；"删除"调后端 API + 前端 `removeTaskSpace`。

**验收：** 失败卡片底栏显示两个操作按钮，删除后卡片消失。
