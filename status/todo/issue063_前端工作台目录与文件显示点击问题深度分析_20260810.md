# issue063 — 前端工作台目录/文件显示与案例测试点击问题深度分析

> **日期**: 2026-08-10
> **严重程度**: P1（用户可感知的交互缺陷，部分为 P0 阻断性功能缺失）
> **影响模块**: 全部 10 个模块的工作区左侧 ResourcePanel（资源面板）
> **关联范围**:

> - `frontend/src/features/resource-explorer/input-resources.ts` — 输入文件扫描与构建

> - `frontend/src/lib/workspace.ts` — response → artifact 提取

---

## 概述

工作台左侧"任务材料"面板（ResourcePanel）是用户查看已提交输入文件和生成结果的主入口。当前存在三组问题：

1. **工作台目录结构异常**：输入/输出文件不反映实际文件目录结构，层级扁平
2. **生成结果文件显示误导**：用抽象的"报告 Word 版"等名字替换真实文件名，按"第N次生成结果"虚拟分组
3. **案例测试输入文件不可点击**：输入文件全为 `<div>` 渲染，无法点击预览/下载

以下逐组展开根因分析。

---

## Issue 063-1: 工作台目录结构扁平化 — 不反映实际文件系统层级

### 问题描述

ResourcePanel 的树结构始终只有两级：
```
  📁 已提交材料 (N)
    ├── 📄 privacy-policy.pdf
    ├── 📄 data-flow.png
    └── 📄 contract.docx
  📁 生成结果 (M)
    ├── 📁 第1次生成结果
    │   ├── 📄 报告 Word 版
    │   └── 📄 报告 PDF 版
    └── 📁 第2次生成结果
        └── 📄 报告 Markdown 版
```

无论实际文件位于 `outputs/cpra/abc123/report.docx`、`storage/uploads/subdir/file.pdf` 还是任何深层路径，面板中永远只有上述两级（"已提交材料"列表 + "第N次生成结果"虚拟分组）。用户无法得知文件在服务器上的真实位置，也无法按目录浏览。

### 根因分析

**原因 1：输入文件始终渲染为扁平的 `<li>` 列表**

```tsx
// frontend/src/components/workspace/ResourcePanel.tsx:168-186
{expandedFolderIds.has("tree-root-input") ? (
  inputEntries.length > 0 ? (
    <ul className="ide-tree-list ide-tree-children">
      {inputEntries.map((entry) => (
        <li key={entry.id}>
          <div
            className="ide-tree-row ide-tree-row-file"
            style={{ ["--tree-depth" as string]: 1 }}
            title="..."
          >
            ...
            <span className="ide-tree-label">{entry.name}</span>
          </div>
        </li>
      ))}
    </ul>
  ) : (...)
) : null}
```

`inputEntries` 是一个扁平的 `InputEntry[]` 数组，通过 `.map()` 直接渲染，完全没有用到 `buildPathTree()`。输入文件从不按目录分组。

**原因 2：`normalizeResourcePath()` 主动剥离路径前缀**

```typescript
// frontend/src/features/resource-explorer/file-path.ts:24-28
if (!scheme) {
  const knownRootIndex = segments.findIndex((segment) =>
    ["benchmarks", "outputs", "reports", "resources", "storage", "uploads"].includes(segment.toLowerCase()),
  );
  if (knownRootIndex >= 0) return segments.slice(knownRootIndex).join("/");
}
```

该函数找到第一个"已知根"目录后，将之前的所有层级全部丢弃。例如 `"/workspace/outputs/cpra/abc123/report.docx"` → `"outputs/cpra/abc123/report.docx"`。虽然这避免了绝对路径和相对路径的碰撞，但也**永久丢失了文件系统的层级信息**。

**原因 3：`InputEntry` 不携带目录信息**

```typescript
// frontend/src/features/resource-explorer/contracts.ts:5-16
export type InputEntry = {
  id: string;
  name: string;          // ← 只有文件名，没有目录路径
  kind: "file";
  sourcePath: string;    // ← 存在但渲染时未使用层级信息
  createdAt: string;
};
```

`buildInputEntries()` 调用 `toFileName()` 只提取文件名部分：
```typescript
// frontend/src/features/resource-explorer/input-resources.ts:93
const fileName = toFileName(candidate.path);  // ← 只取最后一段
```

`sourcePath` 虽然保留了完整路径，但在 `ResourcePanel.tsx:182` 渲染时仅用于 `title` 属性（tooltip），不参与树形构建。

**原因 4：输出产物使用 `virtualPath` 而非真实路径建树**

```typescript
// frontend/src/components/workspace/ResourcePanel.tsx:66-68
const outputTree = useMemo(
  () => buildPathTree(outputEntries.map((entry) => entry.virtualPath), "tree-output"),
  [outputEntries]
);
```

`virtualPath` 是 `"第N次生成结果/报告 Word 版"` 这样的虚拟路径，按运行批次分组。而不是 `"outputs/module/taskId/report.docx"` 的真实路径。

**原因 5：输出树渲染不使用 `sourcePath`**

```tsx
// frontend/src/components/workspace/ResourcePanel.tsx:107-138
const artifact = node.path ? outputFileMap.get(node.path) : undefined;
const isActive = allowFileSelect && !!artifact && selectedOutputPath === artifact.path;
```

`node.path` 来自 `buildPathTree` 中文件节点的路径（即 `virtualPath`），与 `outputFileMap` 的 key 匹配。点击后触发 `onOpenResource({ kind: "output", artifact })`，artifact 包含真实路径 → 正确打开。**但树节点上显示的一直是虚拟名，用户看不到真实路径。**

**影响评估**

| 问题 | 严重性 | 后果 |
|------|--------|------|
| 输入文件永不建树 | P1 | 数十个文件无法按目录浏览，全部平铺在一个列表里 |
| normalizeResourcePath 丢弃层级 | P2 | 不同目录的同名文件会碰撞（但当前有 `buildInputEntries` 的 `pickUniqueName` 兜底） |
| 输出文件用虚拟路径建树 | P2 | 用户看不到 `outputs/cpra/abc123/` 这样的真实目录，无法对应到本地文件 |
| `sourcePath` 仅作 tooltip | P3 | 鼠标悬停才能看到完整路径，体验差 |

## Issue 063-2: 生成结果文件显示误导 — 抽象名替真实名、虚拟分组歧义

### 问题描述

执行完成后，用户在"生成结果"文件夹中看到：
```
  📁 第1次生成结果
    ├── 📄 报告 Word 版
    ├── 📄 报告 PDF 版
    └── 📄 报告 Markdown 版
```

而不是：
```
  📁 outputs
    └── 📁 cpra
        └── 📁 abc123
            ├── 📄 compliance_report.docx
            ├── 📄 compliance_report.pdf
            └── 📄 compliance_report.md
```

几个问题：
1. 如果生成了同类型但不同名称的文件（如 `mitigation_plan.xlsx` 和 `risk_matrix.xlsx`，两者 kind 都是 `xlsx`），`resolveArtifactDisplayName()` 会如何处理？
2. "第N次生成结果" 的 N 是怎么确定的？如果有多次运行，artifact 的时间戳可能不落在任何 run 的窗口内，结果归入"未知批次生成结果"。
3. 如果 run 删除或顺序变更后再有新的 artifact 加入，N 会改变，用户感知到"同一次运行"突然变了编号。

### 根因分析

**原因 1：`resolveArtifactDisplayName()` 用抽象名替换文件名**

```typescript
// frontend/src/features/resource-explorer/output-artifacts.ts:31-53
export function resolveArtifactDisplayName(artifact: OutputArtifact, lang: ResourceLanguage): string {
  const kind = artifact.kind.toLowerCase();
  const fileName = toFileName(artifact.path);
  const extension = getFileExtension(fileName);
  const upperExtension = extension.toUpperCase();

  if (kind === "html") return lang === "zh" ? "报告预览页" : "Report Preview";
  if (kind === "pdf") return lang === "zh" ? "报告 PDF 版" : "Report PDF";
  if (kind === "docx" || kind === "annotated_docx") return lang === "zh" ? "报告 Word 版" : "Report Word";
  if (kind === "markdown" || kind === "md") return lang === "zh" ? "报告 Markdown 版" : "Report Markdown";
  if (kind === "zip") return lang === "zh" ? "完整输出包" : "Complete Output Bundle";
  if (kind === "report") {
    const suffix = upperExtension ? (lang === "zh" ? `（${upperExtension}）` : ` (${upperExtension})`) : "";
    return lang === "zh" ? `审查报告${suffix}` : `Review Report${suffix}`;
  }
  // fallback: 尝试匹配配置的 stem，否则用 prettifyStem
  const configuredStem = Object.keys(OUTPUT_STEM_LABELS).find((stem) => lowerName.includes(stem));
  const displayStem = configuredStem
    ? OUTPUT_STEM_LABELS[configuredStem]?.[lang]
    : prettifyStem(fileName);
  return upperExtension
    ? `${displayStem || fileName}${lang === "zh" ? `（${upperExtension}）` : ` (${upperExtension})`}`
    : displayStem || fileName;
}
```

问题在于：
- 所有 PDF 都叫"报告 PDF 版"，即使有多个不同名称的 PDF 文件（如 `compliance_report.pdf` 和 `mitigation_plan.pdf`），用户无法从名字区分
- `kind` 是后端返回的抽象分类，可能不精确。例如多个不同用途的 xlsx 文件 kind 都是 `xlsx`
- 备选逻辑 `OUTPUT_STEM_LABELS` 只有 2 个配置项 (`mitigation_plan`、`risk_matrix`)，覆盖面极窄

**原因 2：运行批次编号不可靠**

```typescript
// frontend/src/features/resource-explorer/output-artifacts.ts:70-81
const resolveRunNumber = (artifact: OutputArtifact): number | null => {
  const artifactTime = parseTime(artifact.createdAt);
  if (artifactTime === null) return null;
  for (let index = 0; index < runsWithTime.length; index += 1) {
    const lowerBound = runsWithTime[index]?.time;
    const upperBound = index === 0 ? Number.POSITIVE_INFINITY : runsWithTime[index - 1]?.time;
    if (lowerBound !== undefined && upperBound !== undefined
        && artifactTime >= lowerBound && artifactTime < upperBound) {
      return runNumberById.get(runsWithTime[index]?.runId ?? "") ?? null;
    }
  }
  return null;  // ← 落在了运行窗口之外 → "未知批次生成结果"
};
```

算法假设：artifact 的 `createdAt` 落在某次 run 的 `startedAt` 与下一次 run 的 `startedAt` 之间。这个假设在以下情况会失效：
- 某次运行缺少 `startedAt`（被 `parseTime` 过滤掉）
- artifact 的 `createdAt` 早于最早的 run（如 SSR 预生成的 artifact）
- 运行记录被清理后 artifact 仍然保留
- 异步任务中 artifact 在 run 完成后很久才生成

**原因 3：`filterUserFacingArtifacts()` 静默隐藏中间产物**

```typescript
// frontend/src/features/resource-explorer/output-artifacts.ts:17-29
export function filterUserFacingArtifacts(artifacts: OutputArtifact[]): OutputArtifact[] {
  const seenPaths = new Set<string>();
  return artifacts.filter((artifact) => {
    const identity = normalizeResourcePath(artifact.path);
    if (seenPaths.has(identity)) return false;
    const fileName = toFileName(artifact.path).toLowerCase();
    // 三重过滤
    if (INTERNAL_ARTIFACT_PATTERNS.some((pattern) => fileName.includes(pattern))) return false;
    if (!USER_FACING_ARTIFACT_KINDS.has(artifact.kind.toLowerCase())) return false;
    if (!USER_FACING_OUTPUT_EXTENSIONS.has(getFileExtension(fileName))) return false;
    seenPaths.add(identity);
    return true;
  });
}
```

`INTERNAL_ARTIFACT_PATTERNS` 包含 15 个模式：
```typescript
// frontend/src/features/resource-explorer/config.ts:48-65
export const INTERNAL_ARTIFACT_PATTERNS = [
  "citation_map", "compliance_reasoning", "document_ir",
  "dpia_need_assessment", "evidence_chain", "facts.json",
  "findings.json", "generation_basis_pack", "internal_ai_review",
  "issue_list", "legal_grounding", "material_checklist",
  "path_judgment", "rule_engine_result", "trace_manifest",
  "writing_strategy",
] as const;
```

这些都是后端生成的重要中间产物（证据链、事实提取、问题清单等），但对用户完全不可见。用户甚至不知道它们存在，无法用于调试或验证。

**影响评估**

| 问题 | 严重性 | 后果 |
|------|--------|------|
| 所有 PDF/DOCX 显示同名 | P1 | 多个导出文件无法从树中区分 |
| 运行批次编号不可靠 | P2 | 同一次运行的产物可能被分到不同批次，或显示"未知批次" |
| 中间产物完全隐藏 | P2 | 无法在 UI 中查看 evidence_chain、facts.json 等调试信息 |
| `OUTPUT_STEM_LABELS` 覆盖面窄 | P3 | 非标准命名的 xlsx/csv 文件 fallback 到 `prettifyStem`，名字可能怪异 |

## Issue 063-3: 案例测试输入文件不可点击 — 全部输入为 `<div>` 无交互

### 问题描述

用户在"已提交材料"文件夹中看到的输入文件（包括通过案例选择器自动回填的测试文件），全部是纯展示的灰色文本，无法点击预览或下载。鼠标悬停时只显示 tooltip "已记录输入文件；安全预览接口尚未统一，当前仅展示"。

### 根因分析

**原因 1：输入条目硬编码为 `<div>` 非交互元素**

```tsx
// frontend/src/components/workspace/ResourcePanel.tsx:171-185
{inputEntries.map((entry) => (
  <li key={entry.id}>
    <div                          // ← <div>，不是 <button>
      className="ide-tree-row ide-tree-row-file"
      style={{ ["--tree-depth" as string]: 1 }}
      title="已记录输入文件；安全预览接口尚未统一，当前仅展示"
    >
      <span className="ide-tree-caret ide-tree-caret-empty" aria-hidden="true" />
      <span className="ide-tree-icon">
        <FileNodeIcon width="14" height="14" />
      </span>
      <span className="ide-tree-label">{entry.name}</span>
    </div>
  </li>
))}
```

**对比输出文件**：输出文件**可以点击**——它们被渲染为 `<button>` 元素并绑定了 `onClick` 处理器：

```tsx
// frontend/src/components/workspace/ResourcePanel.tsx:122-130
{allowFileSelect && artifact ? (
  <button
    type="button"
    className={rowClass}
    style={{ ["--tree-depth" as string]: depth }}
    onClick={() => onOpenResource({ kind: "output", artifact })}
  >
    {rowContent}
  </button>
) : (
  <div className={rowClass} style={{ ["--tree-depth" as string]: depth }}>
    {rowContent}
  </div>
)}
```

**原因 2：工具链断裂——输入文件缺少后端预览 API**

`ResourceOpenTarget` 类型只定义了 `{ kind: "output"; artifact: OutputArtifact }`，没有 `{ kind: "input" }` 变体：

```typescript
// frontend/src/features/resource-explorer/contracts.ts:31
export type ResourceOpenTarget = { kind: "output"; artifact: OutputArtifact };
```

这意味着即使将 `<div>` 改为 `<button>` 并添加 onClick，也没有对应的处理逻辑来获取和渲染输入文件预览。整个 `onOpenResource` 流程（`WorkspaceShell.tsx:870-890`）设计为仅处理 `kind: "output"`：

```typescript
// frontend/src/components/workspace/WorkspaceShell.tsx:870-890
const handleOpenResource = (target: ResourceOpenTarget) => {
  const path = target.artifact.path;    // ← 直接取 artifact.path，不支持 InputEntry.sourcePath
  setSelectedArtifactPath(path);
  const resource: OpenedResource = {
    kind: "output",
    name: toFileName(path),
    path,
    fileType: readFileType(path)
  };
  // ...
};
```

**原因 3：测试案例文件的路径嵌入在请求 payload 中，通过 `collectUserInputFiles` 扫描得出**

```typescript
// frontend/src/features/resource-explorer/input-resources.ts:101-135
export function buildInputEntries(
  runs: ModuleRun[], outputArtifacts: OutputArtifact[], lang: ResourceLanguage,
): InputEntry[] {
  [...runs]
    .sort((left, right) => right.startedAt.localeCompare(left.startedAt))
    .forEach((run) => {
      collectUserInputFiles(run.request).forEach((candidate) => {
        const identity = normalizeResourcePath(candidate.path);
        if (seenPaths.has(identity) || outputPaths.has(identity)) return;
        seenPaths.add(identity);
        entries.push({
          id: `input-file-${candidate.path}`,
          name: pickUniqueName(resolveInputDisplayName(candidate, lang)),
          kind: "file",
          sourcePath: candidate.path,
          createdAt: run.startedAt,
        });
      });
    });
  return entries;
}
```

`collectUserInputFiles` 递归扫描 request payload 中的 `uploaded_files`、`attachments` 等容器字段。测试案例的 `backendFilePaths` 被回填为 `uploaded_files`（部分模块则是 `attachments`），因此它们会出现在输入列表中。

但由于整个输入列表都是 `<div>`，测试案例文件也不例外地**无法点击**。

**原因 4：`ResourceOpenTarget` 契约只支持输出**

```typescript
// frontend/src/features/resource-explorer/contracts.ts:31
export type ResourceOpenTarget = { kind: "output"; artifact: OutputArtifact };
```

要支持输入文件点击，需要：
1. 扩展 `ResourceOpenTarget` 为 `{ kind: "output"; artifact } | { kind: "input"; sourcePath: string; name: string }`
2. 在 `WorkspaceShell.handleOpenResource` 中处理 `kind: "input"` 分支
3. 调用后端 API 获取文件预览
4. 在 `ResourcePanel` 中将输入 `<div>` 改为 `<button onClick={...}>`

**影响评估**

| 问题 | 严重性 | 后果 |
|------|--------|------|
| 输入文件无法点击 | **P0** | 阻断性功能缺失——用户提交了文件但无法在工作台内预览 |
| 测试案例文件同样无法点击 | P1 | 开发者运行测试案例后无法验证输入文件是否正确 |
| ResourceOpenTarget 不覆盖输入 | P1 | 架构层面就不支持输入文件打开 |
| 输入文件名抽象化 | P2 | `INPUT_ROLE_LABELS` 把 `privacy_policy` 映射为"隐私政策.pdf"，但用户想确认具体是哪个文件时无法做到 |

## 补充发现：其他目录/树细节问题

### 064-1：IDE Tree 样式不区分输入/输出文件

```tsx
// ResourcePanel.tsx:173
className="ide-tree-row ide-tree-row-file"
```

输入和输出的文件节点使用相同的 `ide-tree-row-file` 样式类。用户无法从视觉上立即区分"这是输入还是输出文件"。

### 064-2：`inferLabelKey` 可能误匹配

```typescript
// frontend/src/features/resource-explorer/input-resources.ts:16-26
const inferLabelKey = (path: string, hint?: string): string | undefined => {
  // ...
  return Object.keys(INPUT_ROLE_LABELS).find((key) => {
    const escapedKey = key.replace(/[.*+?^${}()|[\]\\]/g, "\\$&");
    return new RegExp(`(?:^|[\\/_.-])${escapedKey}(?:[\\/_.-]|$)`).test(normalizedPath);
  });
};
```

如果文件名包含 `tia` 或 `dpia`，会被误匹配为对应的角色标签。例如 `negotiation.pdf` 不会误匹配（测试已验证），但 `dpia_report.pdf` 会被标为 `dpia` 材料，即使它是输出报告而非上传的 DPIA 材料。

### 064-3：`normalizeResourcePath` 的去重与路径解析冲突

```typescript
// frontend/src/features/resource-explorer/file-path.ts:7-31
export function normalizeResourcePath(value: string): string {
  // ... .和.. 段解析
  // ... 已知根截断
}
```

如果请求中有 `uploads/../outputs/report.pdf`，经过 `..` 解析后变成 `outputs/report.pdf`——这会与输出文件路径碰撞。`buildInputEntries` 中的 `outputPaths.has(identity)` 检查会将其排除（正确行为），但用户可能疑惑"为什么我的输入文件没显示"。

### 064-4：文件点击后预览的渲染路径交叉

当用户点击输出文件后：
1. `ResourcePanel.onOpenResource` → `WorkspaceShell.handleOpenResource`
2. 创建 `OpenedResource`，添加到 `resourceTabs`
3. 自动切换到该 tab
4. `useEffect` 触发 `fetchArtifactPreview(path)`
5. 后端 `/api/v1/artifacts/preview` 返回 `ArtifactPreview`

这个流程对输出文件有效，但对输入文件完全没有分支处理。整套逻辑都假设 `target.kind === "output"`。

## 总体根因总结

| 问题类别 | 根因 | 核心位置 |
|---------|------|---------|
| 输入文件无法点击 | `<div>` 而非 `<button>`；`ResourceOpenTarget` 不支持 input；无后端预览 API | `ResourcePanel.tsx:173`, `contracts.ts:31`, `WorkspaceShell.tsx:870` |

1. **P0 — 输入文件可点击**：
   - 扩展 `ResourceOpenTarget` 为 `{ kind: "input"; sourcePath: string; name: string }`
   - 在 `WorkspaceShell.handleOpenResource` 添加 `kind === "input"` 分支
   - 后端添加 `/api/v1/artifacts/preview?source=upload&path=...` 支持上传文件预览
   - 将 `ResourcePanel.tsx:173` 的 `<div>` 改为 `<button onClick={...}>`

2. **P1 — 输入文件建树**：
   - 将 `buildInputEntries` 的返回值改为携带目录层级信息
   - 或直接在 `ResourcePanel` 中对 `inputEntries` 调用 `buildPathTree` 按 `sourcePath` 建树

   - 保留抽象名作为主显示，但添加真实文件名的 secondary text
   - 或在 tooltip 中显示完整路径（当前已部分实现）

4. **P2 — 中间产物可选可见**：
   - 在 ResourcePanel 顶部添加"显示内部产物"开关
   - 或为每个内部文件类型添加独立可见性控制

5. **P2 — 运行批次改进**：
   - 在 `OutputArtifact` 中增加 `runId` 字段，直接关联运行记录
   - 避免依赖 timestamp 窗口猜测
