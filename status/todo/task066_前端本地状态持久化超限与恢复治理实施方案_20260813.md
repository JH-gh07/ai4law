## 一、问题结论

当前异常不是后端接口失败，也不是知识库 CSV 造成的。根因链路是：

```text
AppState 持有运行历史和响应正文
→ JSON.stringify(state)
→ localStorage.setItem("ai4law_app_state_v1", ...)
→ 快照超过浏览器配额
→ QuotaExceededError 未被捕获
→ AppStoreProvider effect 抛错
→ 页面可能白屏或状态层崩溃
```

## 二、当前数据边界

### 2.1 必须保留在运行时内存，但不写入 localStorage 的字段

以下字段可能包含完整请求、模型响应、报告正文、规则结果或长证据，不能继续无界写入浏览器 Storage：

- `ModuleRun.request`
- `ModuleRun.response`
- `ModuleRun.error` 中的长错误详情
- `EvidenceHit.snippet`
- `ConsistencyIssue.message` 中的长模型文本
- `RunSession.stages[].detail`
- 任何 Markdown、HTML、DOCX/PDF 内容或 Trace block 正文

类型依据：[domain.ts:44-67](../../frontend/src/lib/domain.ts:44)。其中 `ModuleRun.request/response` 当前是 `unknown`，不能假设体积可控。

### 2.2 可以写入 localStorage 的轻量字段

本地快照只用于启动前的界面恢复和无网络时的轻量显示，建议只保留：

- task space 的身份、标题、模块、法域、时间和布局信息；
- module run 的身份、模块、运行模式、开始/结束时间、成功状态、异步任务 ID、异步状态、短错误码；
- artifact 的身份、任务空间、类型、路径和时间，不保存文件内容；
- evidence/issue 的 ID、source、title、短摘要、级别和时间，单条摘要设长度上限；
- `panelState`、`onboarding`；
- 最近有限数量的 system message；
- 最近有限数量的已完成 run session 摘要，不保存 stage detail 大对象。

完整内容以服务端接口和产物接口为准。localStorage 只能是缓存，不能成为报告或任务事实的唯一来源。

## 三、总体设计

```text
后端 workspace/recovery/report API：权威事实和完整产物
             ↑
AppStore 运行时状态：完整交互数据，仅存在内存
             ↓
localStorage：版本化、裁剪后的轻量 UI/恢复快照
```

设计原则：

1. 写入失败不能打崩 React；
2. 本地快照和远程事实必须分层，不能把完整响应复制到两处；
3. 快照必须有 schema version 和大小预算；
4. 恢复优先使用远程状态，本地只作为启动占位和网络失败时的轻量 fallback；
5. 清理策略必须可测试、可解释，不能随机删除用户最近运行。

### T02：定义版本化轻量持久化 Schema

**目标：** 明确哪些字段可以落盘，避免直接 `JSON.stringify(AppState)`。

**建议类型：**

```ts
type PersistedAppStateV2 = {
  version: 2;
  savedAt: string;
  taskSpaces: PersistedTaskSpace[];
  moduleRuns: PersistedModuleRun[];
  artifacts: PersistedArtifact[];
  evidenceHits: PersistedEvidenceHit[];
  issues: PersistedIssue[];
  systemMessages: PersistedSystemMessage[];
  runSessions: PersistedRunSession[];
  panelState: PanelState;
  onboarding: OnboardingState;
};
```

**裁剪规则：**

- `ModuleRun.request/response` 不落盘；只保存 `requestHash`、状态和短摘要（如确有 UI 需要）；
- `EvidenceHit.snippet` 最长 600 字符；
- `ConsistencyIssue.message` 最长 1000 字符；
- `RunSession` 只保存最近 20 个，stage 只保存 id/name/status/timestamps/短 summary；
- 每个 task space 最多保留最近 20 个 module run、100 个 evidence、100 个 issue；
- 全局 system message 最多 200 条；
- 删除没有对应 task space 的孤立记录和重复 artifact。

**验收：**

- [ ] `toPersistedState()` 输出不包含完整 request/response/Trace detail；
- [ ] `fromPersistedState()` 对旧 v1、损坏 JSON、缺字段和未知版本 fail-soft；
- [ ] 正常快照在目标预算内，建议不超过 1 MB；
- [ ] schema version 改变时有显式迁移或丢弃策略。

**依赖：** T01。**可并行：** 类型设计和测试样例可以并行，合并需统一字段契约。

### T03：实现安全持久化和容量降级

**目标：** 任意 Storage 失败都不能让 `AppStoreProvider` 崩溃。

**涉及文件：**

- `frontend/src/lib/app-store.tsx`

**实现要求：**

1. `persistState()` 只写 `toPersistedState(state)`；

5. 可选写入 `ai4law_app_state_v2`，旧 v1 只读迁移，不再继续覆盖 v1；
6. 提供显式 `clearLocalSnapshot()`，只清理本地缓存，不删除后端数据。

**验收：**

- [ ] 页面运行态仍能 append run、artifact、evidence；

- [ ] `clearLocalSnapshot()` 不调用删除项目历史 API。

### T04：调整恢复优先级和重复合并

**验收：**

### 9.2 关键设计决策

- **写入 key 变更**：`ai4law_app_state_v1` → `ai4law_app_state_v2`，旧 v1 只读迁移后删除，不再覆盖 v1。
- **裁剪规则落地**：`request/response/error` 不落盘；`snippet` 上限 600 字符、`issue.message` 上限 1000、`systemMessage.text` 上限 2000、`stage` 丢弃 `detail/command/icon` 仅留 `summary`（上限 600）；每 task space 最多 20 run / 100 evidence / 100 issue；session 最多 20；全局 system message 最多 200。
- **降级顺序落地**：首次 QuotaExceededError → ① 旧 session 降到 5 → ② evidence/issues 降到 50 → ③ module runs 降到 5 → ④ 清空 system messages → 仍失败则 fail-soft 保留运行时状态。
- **恢复优先级**：`loadState` 仅作启动轻量占位；远程 `hydrate_remote_state` 仍是事实源，按 asyncTaskId/artifact id 去重合并；因本地快照已裁剪，不再把完整 `request/response` 合并回远程结果（T04 随 T02/T03 自然满足，无需额外改动恢复 effect）。
