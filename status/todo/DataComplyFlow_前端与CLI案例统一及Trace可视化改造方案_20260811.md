# DataComplyFlow 前端与 CLI 案例统一及 Trace 可视化改造方案

> 制定日期：2026-08-11
> 状态：待实施，仅限本地
> 继承并修正：`status/todo/DataComplyFlow_案例体系统一与强断言方案_20260806.md`
> 业务资料依据：
> - `resources/new/数规通功能路径描述（含reference）、流程描述、测试案例/`
> - `resources/new/数规通黄金标准与种子案例/种子案例及测试结果/`
>
> 本方案修正旧方案中“前端和 CLI 案例不需要合并”的结论。最新审核已经证明：只比较案例数量和断言数量，无法发现前端与 CLI 使用了不同公司、不同国家、不同数据规模或错误附件。新目标是统一案例事实，同时保留 CLI、API、浏览器各自必须承担的不同测试职责。

---

## 一、要解决的实际问题

### 1. 前端和 CLI 目前不是同一套案例

当前存在两份分别维护的案例：

- 前端开发者案例：`frontend/src/lib/dev-test-cases.ts`，当前实际为 26 个；
- CLI 案例：`backend/tests/<module>/cases/*.json`，当前为 20 个。

它们不仅数量不同，部分案例的公司、法域、接收方、数据规模、数据类型和附件也不同。因此可能出现：

```text
前端测试通过 + CLI 测试通过
但两边实际测试的不是同一件事
```

### 2. 部分前端案例本身不符合正式资料

现有 26 个前端案例的初步审核结果：

| 分类 | 数量 | 当前判断 |
|---|---:|---|
| 与正式资料直接匹配 | 12 | 核对字段后可以保留 |
| 有来源但经过改写或混合 | 5 | 恢复正式事实，或明确登记为派生案例 |
| 不匹配或没有明确来源 | 9 | 重写、降级为产品补充案例或删除 |

已确认的典型问题包括：

- `diagnosis` 第 3 例写成工业物联网向德国传输，但正式案例是匿名化地图数据豁免；
- `assessment` 的“智慧云联”没有在两套指定资料中找到对应案例；
- `eu_scc` 第 1 例改动了正式案例中的公司、国家、传输关系；
- `tia` 第 1 例是多个场景混合后的新案例；
- `pipia` 第 2 例没有保持“智付通向欧盟认证机构提供约 5 万商户信息”的原始事实；
- `us_14117` 没有完整覆盖正式资料中的红、黄、绿三类结果；
- 两个 `review` 案例都使用 `backend/tests/fixtures/cn/data_security_agreement.docx`，但页面分别声称审查隐私政策和个人信息出境标准合同；
- `cn_flow` 在正式业务资料中不是独立功能，它实际上是 `us_14117` 的旧接口兼容入口。

### 3. 当前案例门禁只看数量，不能证明事实一致

`scripts/check_case_parity.py` 当前主要检查：

- 每个模块有没有 CLI 案例；
- 前端大致有多少案例；
- CLI 断言数量是否达到下限。

它不能验证：

- 两边是否是同一个案例；
- 输入事实是否相同；
- 是否使用同一个附件；
- 预期结论是否来自正式资料；
- TypeScript builder 是否改变或漏掉了字段。

当前脚本还使用字符串方式解析 `DEV_TEST_CASES`，会把两行 TypeScript 结束代码误算为案例，使 26 个实际案例被报告为 28 个。

### 4. CLI 有 Trace，但终端不能实时看到执行过程

当前 CLI runner 会创建 `TraceRecorder`，并将事件写入：

```text
runs/<module>/<run_id>/trace/*.json
```

终端只显示最终汇总：

```text
status / duration / assertions / events / llm_calls / tokens / fallbacks
```

这意味着 Trace 已存在，但排查长时间运行、卡住步骤和 LLM 调用时，必须等运行结束或另外打开文件查看。对 Review、SCC 等耗时链路不够实用。

## 二、统一后的正确职责

### 1. 正式资料负责定义业务事实

正式路径文档和黄金种子案例是业务事实的最高依据，负责定义：

- 场景；
- 输入事实；
- 文件类型；
- 预期业务结论；
- 应当命中的主要法律规则。

程序当前输出不能反向修改正式预期。若程序与正式预期冲突，应先判定为实现问题或资料冲突，而不是让测试迁就程序。

### 2. 统一案例目录负责保存可执行事实

建议将审核通过的案例保存为与语言无关的结构化数据：

```text
benchmarks/cases/<module>/<case_id>/
  scenario.json
  expected.json
  fixtures/
```

职责如下：

| 文件 | 职责 |
|---|---|
| `scenario.json` | 公司、国家、人数、数据类型、业务关系、附件角色和来源信息 |
| `expected.json` | 正式预期路径、风险、规则、章节和明确禁止出现的结论 |
| `fixtures/` | 与案例真实匹配的输入文件，或对仓库公共 fixture 的明确引用 |

统一目录不负责实现业务逻辑，只保存经审核的事实和预期。

### 3. 前端负责把统一事实编译成真实 HTTP 请求

前端继续作为开发者查看和一键运行案例的主要入口：

```text
scenario.json
  → formDefaults
  → payload builder
  → HTTP API
```

前端必须验证：

- 表单能完整回填案例事实；
- builder 没有漏字段、错字段或默认补造事实；
- 文件上传及附件角色正确；
- 同步或异步 API 能正确执行；
- 页面状态、执行流、报告和引用跳转正确。

### 4. CLI 负责直接验证后端 Service

CLI 不经过浏览器和真实 HTTP 路由，主要验证：

```text
scenario.json
  → CLI adapter
  → 后端请求 Schema
  → 同一业务 Service
  → 强断言
```

CLI 与前端应使用相同案例事实和预期，但 CLI 不能替代以下验收：

- 前端表单；
- 认证和权限；
- 文件上传 API；
- 异步任务状态；
- SSE 实时事件；
- 浏览器展示；
- 下载和引用跳转。

### 5. `cn_flow` 只验证兼容适配

`cn_flow` 不再拥有独立业务案例。它与 `us_14117` 共用同一组红、黄、绿案例：

```text
同一 EO 14117 scenario
├── 直接构造 US14117Request
└── 构造旧 CNFlowRequest，再由兼容层转换
```

两条路径应比较：

- 关键输入事实；
- 红、黄、绿结论；
- 规则 ID；
- 法规条款；
- 命中状态；
- 缺失关键材料时的拒绝结果。

`cn_flow` 的测试数量可以单独显示为兼容测试，但不能算成新增业务功能案例。

## 三、案例来源和分类规则

每个案例必须包含以下来源字段：

```json
{
  "case_id": "稳定且有业务含义的编号",
  "module": "模块名",
  "provenance": {
    "classification": "source_exact | source_derived | product_extension",
    "source_file": "正式资料相对路径",
    "source_case": "案例编号或标题",
    "change_reason": "仅派生或补充案例需要"
  }
}
```

分类含义：

| 分类 | 含义 | 允许的修改 |
|---|---|---|
| `source_exact` | 正式资料原样案例 | 只能做字段格式转换，不得改变业务事实 |
| `source_derived` | 从正式案例派生，用于边界测试 | 必须逐项记录修改事实和修改原因 |
| `product_extension` | 产品需要但正式资料未定义 | 必须说明测试目的，不能宣称来自正式案例 |

禁止：

- 将多个来源案例拼接后标为 `source_exact`；
- 只写“参考历史资料”，不写具体文件和案例编号；
- 用程序当前输出填充 `expected.json`；
- 为了让测试通过而降低正式预期；
- 用 `known_defects` 隐藏本次应修复的不一致。

## 四、具体实施阶段

### 阶段 0：保存改造前基线

只保存本次涉及的文件，不能包含无关工作区改动：

- `frontend/src/lib/dev-test-cases.ts`；
- `backend/tests/*/cases/*.json`；
- `config/case_inventory.json`；
- `scripts/check_case_parity.py`；
- 相关 fixture 清单。

基线记录：

- 当前前端案例数；
- 当前 CLI 案例数；
- 每个案例的来源声明；
- 输入和附件哈希；
- 当前测试结果；
- 已知失败和耗时。

完成条件：能够明确比较改造前后发生了什么，不需要回退其他人的工作区修改。

### 阶段 1：建立正式案例总表

逐个读取两套正式资料，将所有案例登记为一行：

| 字段 | 内容 |
|---|---|
| 功能 | 正式资料中的功能名称 |
| 来源文件 | 精确 DOCX 相对路径 |
| 来源位置 | 任务号、案例号、标题或表格 |
| 输入事实 | 公司、国家、人数、数据、接收方和业务关系 |
| 输入附件 | 文件名、类型和用途 |
| 预期输出 | 路径、风险、规则、关键报告结构 |
| 当前前端案例 | 对应 ID 或缺失 |
| 当前 CLI 案例 | 对应 ID 或缺失 |
| 审核结论 | 保留、重写、补充或删除 |

完成条件：正式资料中的每个案例都有清晰去向；任何程序案例都能反向找到来源或产品补充理由。

### 阶段 2：先更正前端案例

处理顺序：

1. 保留并复核 12 个直接匹配案例；
2. 对 5 个部分匹配案例恢复正式事实，确需改变的登记为派生案例；
3. 重写、降级或删除 9 个不匹配案例；
4. 补齐 EO 14117 红、黄、绿覆盖；
5. 修复 Review 的隐私政策和标准合同 fixture；
6. 将 `cn_flow` 改成 EO 14117 兼容适配案例。

完成条件：前端显示的名称、描述、表单、payload 和附件表达的是同一场景。

### 阶段 3：建立统一案例数据

将审核通过的前端案例事实迁移到 `benchmarks/cases/`。前端通过明确的读取或生成步骤使用该数据，不再在 TypeScript 中重复写一整套事实。

需要保留 TypeScript builder，因为它负责将业务事实转换为 API 契约；但 builder 不是事实源。

完成条件：修改公司名称、人数或接收方时，只需要修改一个案例事实文件，前端和 CLI 同时感知变化。

### 阶段 4：重建 CLI 案例和强断言

CLI adapter 从统一 scenario 构造后端请求。每个案例至少验证：

- 请求 Schema 通过或按预期拒绝；
- 关键事实未丢失、未被默认补造；
- 路径或风险结论正确；
- 关键规则 ID 和法律依据正确；
- 关键报告章节存在；
- 正文引用和脚注对应；
- 输出角色和文件格式正确；
- 明确不应出现的结论确实不存在。

完成条件：CLI 断言来自正式预期，并且改变关键事实或结论会使测试真实失败。

### 阶段 5：增加 CLI 实时 Trace 输出

为 `backend.tests.harness.runner` 增加明确的可选参数：

```bash
uv run python -m backend.tests.harness.runner tia 01_minimal --no-llm --verbose-trace
```

#### 5.1 开关行为

| 模式 | 行为 |
|---|---|
| 默认模式 | 保持现有简洁汇总，不逐条打印 Trace |
| `--quiet` | 不打印案例过程和汇总明细，仅保留必要退出码 |
| `--verbose-trace` | Trace 产生时立即输出到终端，同时继续正常落盘 |
| `--quiet --verbose-trace` | 判定为参数冲突并给出明确提示，避免语义含糊 |

#### 5.2 实现边界

优先复用现有 `TraceRecorder.subscribe()` 机制，增加一个只负责终端展示的订阅者。禁止在每个业务 Service 中增加 `print()`。

依赖方向必须保持：

```text
CLI harness
  → terminal trace subscriber
  → TraceRecorder 公共订阅接口

业务 Service
  → TraceRecorder
  × 不依赖 CLI
```

#### 5.3 终端输出格式

每条事件至少显示：

```text
[时间] [序号] [事件类型] 摘要
```

有相关信息时追加：

- 阶段或步骤名；
- LLM 调用开始和结束；
- 模型名；
- 单次耗时；
- input/output/total token；
- fallback 或 warning；
- tool 名称；
- 最终状态。

示例：

```text
19:21:03 #001 status       开始 TIA 评估
19:21:04 #002 tool_start   检索适用法规
19:21:05 #003 tool_result  检索完成 duration=842ms results=6
19:21:05 #004 llm_start    生成风险分析 model=...
19:21:11 #005 llm_result   调用完成 duration=5.8s tokens=1240
19:21:12 #006 final        TIA 报告生成完成
```

默认只输出摘要和安全统计，不直接打印完整合同、个人信息、API 密钥、Authorization header 或完整提示词。需要详细输入输出时，应从本地 Trace 文件查看，并继续遵循现有脱敏规则。

#### 5.4 异常行为

即使业务执行异常，也必须：

- 实时打印最后一个已产生事件；
- 打印明确的失败类型和简短错误；
- 将完整 traceback 写入 `output/error.json`；
- 正常写入 `run_manifest.json`；
- 保留非零退出码；
- 不因为终端订阅者自身异常而中断业务执行。

#### 5.5 Trace 验收

必须新增测试证明：

1. 默认模式不逐条输出 Trace；
2. `--verbose-trace` 按事件产生顺序输出；
3. 终端事件数与落盘事件数一致；
4. warning、fallback、LLM token 和 final 能正确显示；
5. `--no-llm --verbose-trace` 显示 `llm_calls=0`，不会误报真实模型调用；
6. 敏感字段不会出现在终端；
7. 订阅者输出失败不会使业务案例失败；
8. `--quiet` 与 `--verbose-trace` 冲突时立即拒绝。

#### 5.6 明确不替代的验收

`--verbose-trace` 只证明：

```text
CLI 进程内确实产生了 TraceRecorder 事件
```

它不能证明：

- FastAPI 已将事件写入统一事件表；
- SSE 能正常推送；
- 浏览器能够订阅和重放；
- 前端执行流正确显示；
- 前端任务状态能正确从失败更新为成功。

因此 CLI Trace、API 事件测试和浏览器执行流验收必须分别保留。

### 阶段 6：重写案例一致性门禁

门禁不再解析 TypeScript 文本猜测案例数量。应读取结构化案例清单，并校验：

- `case_id`；
- 模块；
- 来源文件和案例编号；
- 来源分类；
- fixture 路径和哈希；
- 关键事实摘要；
- 前端 builder 输出；
- CLI adapter 输出；
- 标准化后的语义一致性。

标准化时允许忽略：

- 任务 ID；
- 用户 ID；
- 时间戳；
- 上传后的绝对路径；
- 输出目录。

不得忽略：

- 公司和主体；
- 国家和法域；
- 数据类型；
- 人数和数量级；
- 接收方角色；
- 处理目的；
- 交易类型；
- 附件角色；
- 业务预期结论。

完成条件：数量相同但事实不同必须失败；事实相同但传输字段不同可以通过。

### 阶段 7：完成三层本地验收

#### 第一层：资料与案例一致

```text
正式资料事实 = scenario.json
```

由案例总表、来源定位和字段对照证明。

#### 第二层：前端与 CLI 输入一致

```text
scenario.json
├── 前端 builder payload
└── CLI adapter payload

标准化后关键业务语义一致
```

#### 第三层：业务结果和用户链路正确

```text
CLI Service 结果
≈ 真实 HTTP API 结果
≈ 正式资料预期

浏览器另外验证表单、上传、任务、执行流、报告和引用跳转
```

完成条件：三层分别有可复查证据，不能用 CLI 全通过替代浏览器验收。

## 五、本地测试顺序

### 1. 静态和契约检查

```bash
uv run python scripts/check_case_parity.py
```

### 2. CLI 无模型回归

```bash
uv run python -m backend.tests.harness.runner all --no-llm
```

要求：

- 确定性规则和结构断言全部通过；
- Review 无模型模式不得发生任何真实 LLM 调用；
- 不允许通过修改预期掩盖业务错误。

### 3. CLI Trace 专项测试

```bash
uv run python -m backend.tests.harness.runner <module> <case_id> --no-llm --verbose-trace
```

检查终端事件顺序、落盘一致性、失败收尾和脱敏。

### 4. 后端全量测试

```bash
uv run --frozen pytest -q
```

### 5. 前端测试和构建

```bash
cd frontend
npm test
npm run build
```

### 6. 真实本地 HTTP 和浏览器验收

本地启动后端和前端，逐个执行已审核案例，检查：

- 表单回填；
- 文件上传；
- 请求内容；
- 同步或异步状态；
- 实时执行流；
- 失败后重新运行的状态更新；
- Markdown、DOCX 和 PDF；
- 引用跳转；
- 浏览器最终结果与 CLI 关键结论一致。

远程服务器不在本方案实施范围内。只有本地全部完成并经用户明确同意，才能另行制定部署步骤。

## 六、最终验收证据

在 `status/check/` 生成本方案对应的验收报告，每个案例必须列出：

| 项目 | 证据 |
|---|---|
| 正式来源 | 文件路径和案例编号 |
| 案例分类 | exact、derived 或 extension |
| 统一事实 | `scenario.json` |
| 前端请求 | 标准化 payload 和哈希 |
| CLI 请求 | 标准化 payload 和哈希 |
| 输入附件 | 文件名、用途和哈希 |
| 正式预期 | `expected.json` |
| CLI 结果 | run ID、断言结果、Trace 路径 |
| HTTP 结果 | endpoint、状态和任务 ID |
| 浏览器结果 | 截图和产物路径 |
| 最终结论 | 通过、失败或有明确阻塞项 |

同时记录以下总量，但总量不能替代逐例证据：

- 正式来源案例数；
- 前端可执行案例数；
- CLI 业务案例数；
- `cn_flow` 兼容案例数；
- exact、derived、extension 各自数量；
- 断言总数；

- [ ] 前端案例不再存在来源冒用、事实混写或附件错配；
