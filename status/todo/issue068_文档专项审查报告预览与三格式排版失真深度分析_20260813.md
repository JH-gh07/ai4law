# issue068：文档专项审查报告预览与三格式排版失真深度分析

> 日期：2026-08-13  
> 范围：`review` 文档专项智能审查的网页正文预览、DOCX 预览、PDF 预览与导出产物排版  
> 样本：用户提供的“文档专项智能审查 2026-08-12”工作区截图；本地历史产物 `tmp/review/`；代码当前工作区 `HEAD=ffe9f351` 及远程发布 release `ffe9f351`  
> 性质：问题分析和可验核整改方案；本 issue 不修改法律结论，不以截图推断未验证的业务事实

## 一、结论先行

这不是单纯的字体、卡片宽度或 CSS 美观问题，而是“审查结果没有保持结构化语义，进入三种载体后被重复降级为字符串”的系统性排版缺陷：

```text
ReviewIssue / MissingItem / Citation
        ↓
ReviewReportRenderer.build_sections()
        ↓  list[tuple[str, list[str]]]，finding、法规、建议、边界全部变成普通字符串
        ↓
DOCX：ReportService.create_docx_report() 每行 add_paragraph()
PDF ：ReportService._write_pdf() → Markdown 字符串 → ReportLab 逐行解析
网页：DOCX/PDF artifact API 抽文本；前端再按 Markdown 猜测渲染
        ↓
标题、问题卡片、风险标签、法规引用、修改建议、编号层级和分页语义丢失
```

因此，截图中看到的“一整段文字墙”“法规条文串成一长串”“PDF 与 Word 预览不像正式报告”“同一文件可能既显示正文又显示导出预览”，都来自同一条根因链，而不是互不相关的视觉瑕疵。

## 二、截图事实逐项核对

### 2.1 DOCX 预览截图

截图明确显示：

1. “文档正文预览”下是一段连续大文本，`一、二、三、四、五` 只是正文中的字符，不是可导航的报告章节；
2. `SECURITY_MEASURES`、`CONSENT_NOTICE` 等文档画像分类被平铺为普通行，没有类型标签或统计表；
3. 风险摘要、完整性缺口、逐条问题、法规依据和整改建议全部混在同一阅读流中；
4. `[HIGH]`、`[MEDIUM]`、`[LOW]` 只是字符串前缀，没有颜色、徽标、筛选或风险分组；
5. “导出文件预览”与“文档正文预览”视觉上是两个容器，缺少“这是结构化报告正文/这是原始文件抽取”的明确边界；
6. 左侧文件树显示“报告 Word 版”，但中央显示的是抽取文本，不是 Word 的 heading、段落间距、编号、表格和分页。

### 2.2 PDF 预览截图

截图明确显示：

1. 法规依据被压成连续长段，多个法规名称和条文号没有逐条分隔；
2. `《个人信息保护法》`、`《个人信息出境标准合同办法》` 等同一来源重复出现，阅读者无法判断是引用集合、条款列表还是问题逐条依据；
3. 页内只有文本流，没有章节标题、页眉页脚、页码、目录、风险摘要或问题边界；
4. PDF 画布展示的是文本层的排版结果，不是 Word 结构的忠实预览；
5. 45 页的历史 PDF（见 `tmp/review/pdf.pdf`）与截图中的内容形态一致，说明问题存在于真实产物，不是浏览器缩放造成的错觉。

### 2.3 右侧执行流

右侧执行流本身不是排版主因，但暴露了另一个信息层级问题：

- 同一 `任务状态更新` 重复显示 `PREPARING`、`SEGMENTING`、`CLASSIFYING` 的英文阶段值和中文标签；
- 事件内容重复，时间精度不足以区分真实阶段变化；
- 报告阅读区和执行流没有通过 `task_id`、终态和产物状态形成明确关联。

该部分属于 Trace/状态显示问题，应与报告排版分开治理，不能通过调整报告 CSS 解决。

## 三、代码依据与真实产物依据

### 3.1 业务结果在进入渲染前已被降级

代码：[review_report_renderer.py](../../backend/domains/cn/document_review/review_report_renderer.py)

`ReviewReportRenderer.build_sections()` 返回 `list[tuple[str, list[str]]]`。其 `_format_issue()` 将一个完整的 `ReviewIssue` 拆成多条前缀字符串：

```python
[
    f"--- 问题 {index} ---",
    f"编号：{issue.issue_id}",
    f"严重程度：{issue.severity.value} | 条款类型：{issue.clause_type.value}",
    f"标题：{issue.title}",
    f"问题类型：{issue.problem_type}",
    f"原文摘录：{issue.original_excerpt}",
    f"风险分析：{issue.risk_analysis}",
    f"法规依据：...",
    f"修改建议：...",
]
```

这一步没有保留 `issue_id`、severity、clause_type、original_excerpt、risk_analysis、citation_sources、recommendation 之间的结构关系，也没有形成 finding 节点、法规引用节点和建议节点。

另外，renderer 先生成“九、审查边界与置信度说明”，随后又追加标题为“九、附录”，造成章节编号重复。该问题直接来自 `review_report_renderer.py` 的固定字符串，而不是前端显示造成的。

### 3.2 DOCX 生成逻辑只创建普通段落

代码：[report_service.py](../../backend/services/report_service.py)

`ReportService.create_docx_report()` 当前逻辑是：

```python
for heading, paragraphs in sections:
    document.add_heading(heading, level=1)
    for paragraph in paragraphs:
        document.add_paragraph(paragraph)
```

它不会创建：

- 原生风险标签；
- finding 表格或 finding block；
- 法规引用列表；
- 多级编号；
- 原文/风险/依据/建议四区块；
- 页眉、页脚、页码和跨页重复表头；
- `keep_with_next`、`keep_together`、孤行控制。

因此 DOCX 只是“标题 + 普通段落集合”，不是结构化法律审查报告。

### 3.3 PDF 生成逻辑把全部内容再次拼成 Markdown 文本

代码：[document_review/service.py](../../backend/domains/cn/document_review/service.py)

```python
pdf_lines = [f"# {doc_type} 合同合规审查报告"]
for heading, paragraphs in sections:
    pdf_lines.extend([f"## {heading}", *paragraphs])
self.report_service.create_pdf_report(..., pdf_lines, ...)
```

随后 [report_service.py](../../backend/services/report_service.py) 通过 `"\n\n".join(lines)` 重新拼接，再交给通用 `render_pdf_report()`。这条路径没有使用 `ReviewIssue` 的结构字段，也没有生成 PDF 原生表格、目录、问题卡片、风险徽标或引用附录。

### 3.4 后端 artifact API 把 DOCX/PDF 降为文本

代码：[artifacts.py](../../backend/api/v1/endpoints/artifacts.py)、[file_parser.py](../../backend/common/storage/file_parser.py)

- `.pdf` 返回 `render_mode="pdf"`，同时把 `pypdf.extract_text()` 的文本放入 `content`；
- `.docx` 返回 `render_mode="text"`；
- `FileParser._parse_docx()` 只读取 `paragraph.text` 和表格单元格文本，并将表格行拼成 `" | "`；
- Word heading、样式、列表编号、段落间距、分页、页眉页脚、脚注、批注和表格边框全部丢失。

因此截图中的 DOCX“正文预览”本质上是 DOCX 文本抽取，不是 Word 视觉预览。

### 3.5 前端再把抽取文本按 Markdown 解释

代码：[WorkspaceShell.tsx](../../frontend/src/components/workspace/WorkspaceShell.tsx)

- `buildSectionsFromArtifactPreview()` 只返回一个 section，标题就是文件名；
- `renderTextArtifactPreview()` 对 docx 默认进入 `CitationMarkdownRenderer`/`ReactMarkdown`；
- `normalizeMarkdownForRender(content)` 会尝试把普通文本重新识别成 Markdown。

这形成了错误的二次解释：

```text
DOCX 结构 → 纯文本 → Markdown 猜测
```

它既不能恢复原 Word 结构，还可能把数字、管道符、短横线和法规定位号误判为列表或表格。

### 3.6 前端存在正文容器与导出预览容器双重展示

`WorkspaceShell.tsx` 同时渲染：

1. `reportPreviewSections`：报告正文章节；
2. `artifactPreview`：选中导出文件后的“导出文件预览”。

在没有结构化章节或恢复态只拿到文本 artifact 时，同一份报告文本可能同时出现在两个区域。即使截图没有完整截出重复全文，这条代码路径仍然客观存在。

## 六、根因链与边界

### 根因链

```text
ReviewIssue 结构化对象
  → build_sections() 转为 list[str]
  → DOCX 普通段落 / PDF Markdown 行
  → artifact API 抽纯文本
  → ReactMarkdown 二次猜测
  → 章节、finding、citation、风险级别、分页全部失去载体语义
```

### 不是本 issue 的问题

- 41 个问题、7 个缺失项和风险评分 72.2/100 是否符合法律事实：属于业务质量审查；
- LLM 是否调用、是否超时、是否降级：属于模型运行和状态语义；
- 右侧 Trace 是否实时、是否重复事件：属于 issue062/任务状态专项，但本 issue 记录其对阅读区的干扰；
- 远程服务器、Nginx、数据库：属于部署和运行环境，不是排版根因。

## 七、推荐整改方案（科学、可验核）

### P0：建立 Review Report IR，不再以 `list[str]` 作为唯一中间结果

新增/扩展现有 `DocumentIR`，至少表达：

```text
ReviewReportIR
├─ metadata: document_type / title / review_mode / completed_at
├─ executive_summary: rating / score / issue_counts / missing_counts
├─ document_profile: typed key-value items + clause_type_distribution
├─ findings[]: id / severity / title / clause / original / risk / citations / recommendation
├─ missing_items[]: id / severity / description / legal_basis / action
├─ remediation_actions[]
├─ citations[]: citation_id / source / article / locator / finding_refs
├─ confidence_and_scope
└─ render_contract: heading_order / numbering / page / locale
```

每个 finding 只能有一个完整主展示；摘要、风险矩阵和章节内引用只能引用 `finding_id`，不得复制整段 finding 文本。

### P1：三种载体全部从同一 IR 渲染

- Web：使用结构化 React renderer，finding 采用风险标签 + 原文 + 风险 + 依据 + 建议五区块；
- Markdown：生成可读的标题、列表、引用和附录，不把表格字符串塞入段落；
- DOCX：原生 heading、table、numbering、页眉页脚、页码和分页属性；
- PDF：从 IR 生成摘要表 + finding 纵向块，禁止 6 列长表格和逐字符断行；
- `document_ir_json` 只作为受控内部 artifact，不进入 `localStorage`。

### P2：DOCX/PDF 预览语义分离

前端应明确区分：

```text
报告正文：Report IR → Web renderer
PDF 预览：同一 IR 生成 PDF → PDF.js canvas
DOCX：下载/打开原文件；页面正文仍由 IR 展示
```

浏览器不应把 DOCX 抽纯文本后假装成忠实 Word 预览。若需要像素级 Word 预览，应部署受控 LibreOffice 转 PDF 服务，并把转换产物登记为独立 preview artifact。

### P3：修复章节编号和风险视觉层级

1. `ReviewReportRenderer` 使用枚举/常量生成章节 ID，禁止手写两个“九”；
2. `[HIGH]` 等字符串改为 typed severity badge；
3. 文档画像改为两列统计表；
4. 缺失项按 HIGH/MEDIUM/LOW 分组为独立列表；
5. 每个 finding 使用稳定锚点 `finding-{issue_id}`；
6. 引用按 citation ID 去重，并显示“支持哪些 finding”；
7. 统一中英文标签，不同时显示内部枚举和展示文案。

## 七-A、补充问题：CPRA/EO 输入摘要顺序、DPIA 三格式不一致与模拟输入消失

用户新增截图（`tmp/User attachment.png` 至 `tmp/User attachment6.png`）证明，问题不只存在于 Review：CPRA、EO 14117、DPIA 也共用“结构化结果 → 字符串 → 通用渲染/抽取预览”的缺陷。

### 7-A.1 CPRA PDF：输入摘要错误占据正式报告首屏

截图 `User attachment2.png` 的实际顺序是：标题 → 输入摘要 → JSON/键值长段 → 后续 CPRA 分析章节。输入摘要本身可以保留，但不能以原始 JSON 和长键值串占据正式结论之前的主要版面。

代码依据：`backend/domains/us/cpra/service.py` 将 payload 事实、章节和输出文件放入同一结果对象，并由模板变量组装报告；`backend/common/render/artifacts.py::render_pdf_report()` 只接收 `list[tuple[str, str]]`，没有 `INPUT_SNAPSHOT`、`EXECUTIVE_DECISION`、`FINDING` 等顺序化区块。

根因链：

```text
payload facts → input_summary 字符串 → 与章节共用模板变量池
→ renderer 按字符串字段顺序输出 → PDF 首屏出现 JSON/键值长段
```

目标顺序应固定为：标题/法域/日期 → 结论与风险摘要 → 适用范围与判断依据 → 风险与整改 → 法规依据 → 输入快照/附录。原始请求应进入受控 JSON 附件，不应直接写进正文。

### 7-A.2 EO 14117 DOCX：输入 JSON 与风险结论黏连

截图 `User attachment3.png` 显示 DOCX 先输出 `{"project_name": ...}` 等嵌套 JSON，再显示风险结论、附件解析和第一章。`attachments`、`recipient_entities`、`security_measures` 被压成一行，用户无法区分数据项、接收方、附件和安全措施。

依据：`backend/domains/us/eo14117_flow_review/schema.py` 仅登记 `output_files`，输入字段仍通过结果字符串传递；EO fallback/report 路径将结构化 payload 序列化后拼入正文；通用 DOCX renderer 没有把嵌套对象转成原生表格、列表和元数据区。

验收要求：DOCX XML 必须包含独立元数据表、结论段落和结构化数据表；第一个业务章节必须是“总体结论与传输可行性”，不能是 JSON 转储。

### 7-A.3 DPIA：Markdown 正常，DOCX/PDF 结构被压平

截图 `User attachment5.png`、`User attachment6.png` 显示 Markdown 结构相对清晰，但 Word/PDF 出现 `1 1`、`1 2`、`2 2.1` 等重复编号，标题与正文同为普通文本，段落和引用层级被压平。

依据：`backend/domains/eu/dpia/deterministic_chapters.py` 能生成结构化章节/Markdown；`backend/domains/eu/dpia/report_renderer.py` 同时生成多格式，但部分路径仍把 Markdown/纯文本交给旧 renderer；`backend/common/render/docx_renderer.py` 只有输入已是 `ReportDocument` 时才生成原生 heading/list/table；`backend/common/render/artifacts.py::_markdown_to_flowables()` 逐行猜测标题、列表和表格，无法可靠区分业务编号与章节编号。

根因是三种产物没有消费同一份 Report IR：

```text
DPIA facts/issues/evidence → deterministic_chapters → Markdown
→ DOCX/PDF 再从字符串猜标题/列表 → 编号、层级、分页、引用语义丢失
```

整改要求：章节、subsection、claim、citation、warning 先进入统一 IR；DOCX 使用 Heading 和原生列表/表格；PDF 使用 block renderer；编号只生成一次；三格式通过 IR hash、章节集合和引用集合门禁。

### 7-A.4 CPRA/EO/DPIA 模拟输入在工作台显示为 0

截图中三个模块左栏均显示“已提交材料 0 / 暂无已提交材料”，但右侧执行流和正文已经显示本次运行使用了模拟案例事实或附件。

依据：`frontend/src/lib/dev-test-cases.ts` 保存开发预置案例和 `backendFilePaths`，供 builder 构造请求；`frontend/src/components/workspace/ModuleRunPanel.tsx` 允许 `presetFilePaths` 参与提交；`frontend/src/components/workspace/ResourcePanel.tsx` 的材料树主要读取已登记的 `uploaded_files`；`frontend/src/lib/workspace.ts` 主要从 `response.output_files` 建立产物，不能把请求中的 `attachments/backendFilePaths`反向登记为输入材料。

根因链：

```text
dev preset/scenario attachment → builder 请求 JSON → 后端消费并生成报告
→ 未创建 UploadedFile/RunInputArtifact 登记 → ResourcePanel 查询得到 0
```

这不是“模拟案例没有输入”，而是“输入事实没有被建模为可追溯 artifact”。正确方案是创建 `RunInputManifest`，记录 `source_kind=dev_preset|uploaded|scenario`、文件名、角色、SHA-256、storage URI 和是否实际送入 service；左栏明确区分用户上传材料与开发预置材料；报告输入摘要只引用 manifest，不输出绝对路径和原始大 JSON。

## 七-B、补充问题：单个 finding 多法条引用只罗列无论证（I068-22）

用户对最新 DOCX 产物提出内容层不满意：**一个情况（finding）对应多个法条引用，这些引用只用「；」连成一行/一段，没有说明任何一条引用为什么适用于该情况，结果引用块直接占满大半页，却没有提供可审计的论证价值。** 本小节定位根因，属内容承载缺陷而非字体/断行类纯排版缺陷。

### 7-B.1 现象（真实产物证据）

BCR 基线样本 `outputs/bcr/4ab0776d9ddc49faba4d7bf89f30cd0a/outputs/GlobalTech_Inc._BCR审查报告_草案_20260813.docx` 中，18 个 finding 的「法律依据」列几乎全部是多引用堆叠，且**同一引用反复出现、无逐条论证**：

```text
BCR-C-1.1   → GDPR Article 47(1)(a) [1]；EDPB Recommendations 1/2022
BCR-C-1.3   → GDPR Article 47(2)(f) [1]；EDPB Recommendations 1/2022
BCR-C-1.8   → GDPR Chapter V；EDPB Recommendations 1/2022
转委托处理   → GDPR (EU) 2016/679 第46条 [1]；GDPR (EU) 2016/679 第47条
缺少法律文书 → GDPR (EU) 2016/679 第15条 [1]；EDPB Recommendations 01/2020 第Step 1条
```

`EDPB Recommendations 1/2022`、`GDPR Article 47` 在几乎所有 finding 里重复出现，但每条引用没有落到「本 finding 违反哪一款/哪一项、为什么」。

### 7-B.2 根因链

```text
数据模型层：法规依据被建模为「标签字符串列表」，而非「(引用, 论证) 对」
  ├─ ReviewIssue.citation_sources: list[str]            （backend/schemas/review.py:251）
  ├─ ReviewIssue.structured_citations 有 snippet/relevance，但无 per-citation 论证字段
  ├─ MissingItem.legal_basis: list[str]                 （backend/schemas/review.py:288）
  ├─ BCRFinding.legal_basis: list[str]                  （backend/domains/eu/bcr_review/schema.py:98）
  └─ FindingRecord.legal_basis: list[str]               （backend/common/reporting/schema/findings.py:45）
        ↓
渲染层：一律 "；".join(labels) 拼成一行/一段
  ├─ review：review_report_renderer.py:158-159  f"法规依据：{'；'.join(issue.citation_sources)}"
  ├─ review：review_report_renderer.py:179-180  missing item 同
  ├─ review：annotated_docx_builder.py:85        "；".join(issue.citation_sources[:3])
  ├─ BCR 六列表：service.py:88                  "；".join(f.legal_basis)
  └─ BCR IR DOCX：docx.py:372-374               "；".join(finding.legal_basis) + footnote markers
        ↓
一个 finding 的多条引用 → 裸标签罗列 → 无「要件→事实→结论」因果链 → 占满大半页
```

### 7-B.3 关键判断

1. **论证其实存在，但被放在了别处且未绑定到引用**：`ReviewIssue.risk_analysis`（整体风险分析）承载了 finding 的论证；`structured_citations.snippet` 承载了法条摘录；但 renderer 只取 `citation_sources` 标签做 `；` 拼接，导致「引用」与「为什么引用」在渲染层失联。
2. **这不是渲染器单独能修的**：`FindingRecord.legal_basis: list[str]` 本身就没有 per-citation 论证字段。修渲染只能把一行拆成多行（缓解文字墙），无法补出「每条引用为何适用」——论证必须由 adapter 从 `risk_analysis`/`structured_citations` 归因，renderer 只做呈现。
3. **不改判、不删减、不生成**：引用数量和法条本身不得因排版改造增减；论证只能来自既有业务字段的归因，不得由 renderer 或新增 LLM 调用生成法律结论。

### 7-B.4 优先级与验收

| 编号 | 问题 | 严重度 | 验收 |
|---|---|---:|---|
| I068-22 | 单 finding 多法条引用只罗列无论证 | P0 | 每条引用独立承载，含来源/条文定位/摘录与「为何适用」归因；无裸 `；` 标签墙；引用集合与 IR 相等 |


## 十二、最终判断

当前截图反映的是一个真实、可重复解释的架构问题：业务审查结果已经产生，但在“结构化结果 → 报告 IR → Web/DOCX/PDF”之间没有稳定的结构契约，导致最终用户看到的是可打开但不专业、可阅读但不可审计的文本堆叠。

修复的正确起点是 Review 专用 IR 和跨格式同源 renderer，不是继续调字体、边距或单个 CSS 选择器。只有结构门禁、DOCX XML、PDF 文本/字体和三 viewport 视觉验收全部通过后，才能把该问题标记为完成。
