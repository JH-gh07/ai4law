## 三、关键设计决策

### 3.1 Manifest 是 seed 唯一清单

`benchmarks/datasets/seed-cases-v1/manifest.json` 是 50 个原件的唯一文件集合。构建脚本不得以 glob 结果作为权威输入；文件名解析只能用于验证 manifest 的 `task/case/path/hash` 一致性。

必须拒绝以下情况：

- manifest 有而磁盘没有；
- 磁盘有而 manifest 没有；
- 数量不是 50；
- task/case 从文件名解析出的值与 manifest 不一致；
- SHA-256 与 manifest 不一致；
- 同一 source 被多个 case 引用但未声明为派生来源。

### 3.2 Seed 分两级，不把抽取记录冒充模块请求

```text
Level A：DOCX → 来源保真 extraction record（50/50）
Level B：extraction record → 模块 request schema → CLI/HTTP（仅已支持且已裁决案例）
```

Level A 只负责段落、表格、标记和来源 Hash；Level B 才能证明案例可进入业务模块。产品未支持或模块身份冲突的案例必须登记为 `gap`，不得硬塞到近似模块。

### 3.3 Report IR 的单一业务判断来源

facts、findings、decision、citations 只能由 Report IR 提供。Markdown、DOCX、PDF、HTML renderer 不得重新生成业务结论。

批注 DOCX 是例外边界：

- Report IR：唯一业务判断、finding、decision、citation 来源；
- 原始上传 DOCX：只提供原文、版式、段落/页码定位和批注承载；
- renderer：不得根据原始 DOCX 内容再次推导法律结论。

### 3.4 真实模型与确定性模型分离

确定性测试 LLM 只验证链路稳定性；真实 provider 运行才进入内容质量验收。两套结果必须拥有不同的运行标识、配置快照和证据目录，不能混写成同一通过结论。

## 七、风险、禁止操作和回滚

| 风险 | 防护 | 失败处理 |
|---|---|---|
| seed 文件被替换 | manifest 集合+Hash 强校验 | 立即停止，恢复来源后重跑 T02 |
| 任务映射被硬塞 | 必须有 reviewer、reason、gap 枚举 | 回退 T03，不接入 runner |
| 浏览器脚本测错事实 | 运行前比较 Scenario/request Hash | 删除该批证据，回到 T04 |
| 真实模型输出污染基线 | provider/config/Scenario 固定并隔离 | 标记无效，不修改 expected 迎合输出 |
| renderer 重复拼接结论 | IR provenance + 产物集合门禁 | 试点失败则不扩散到其他模块 |
| 区域法域污染默认索引 | `legal_index_intl` 条件检索 | 禁止发布索引，保留原件和 catalog |
| token/trace 泄露 | 脱敏 hook 和敏感扫描 | 删除未发布证据，轮换本地凭据 |
| 无关脏改动混入提交 | staged diff 文件归属清单 | 不提交，拆分候选变更 |

禁止：

1. 先生成 expected 再倒推事实；
2. 用 `source_derived` 冒充 `source_exact`；
3. 用 PIPIA 截图代表其他模块通过；
4. 用确定性 LLM 结果代表真实模型法律质量；
5. 用文件存在代替文件可打开、内容等价和视觉合格；
