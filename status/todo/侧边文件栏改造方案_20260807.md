## 一、设计原则

**核心一句话**：通过"抽象共性、封装能力、统一接口、配置差异"实现高内聚、低耦合和跨场景复用。

| 原则 | 含义 | 在此需求中的映射 |
|------|------|----------------|
| **职责清晰** | 每个模块只做一件事 | 收集/过滤/命名/渲染 分离 |
| **目录有序** | 目录层次反映架构 | 配置、逻辑、视图、契约分目录 |
| **命名统一** | 语义明确，无 new/v2/temp | `sample_contract.txt` → `个人信息出境标准合同【模板】.docx` |
| **边界明确** | 模块间通过稳定接口交互 | 每个环节定义清晰的输入/输出类型 |
| **依赖单向** | 业务依赖公共，不反向 | 视图 → 逻辑 → 配置 |
| **共性下沉** | 重复语义统一抽取 | 11 模块共用同一套输入收集+输出过滤+树构建 |
| **差异配置** | 业务差异通过配置表达 | 哪些文件展示、中文名映射，全部配置化 |
| **产物分离** | 源文件/配置/模板/产物分目录 | 输入端:测试案例 vs 模板 vs 占位；输出端:报告 vs 中间产物 |

## 二、现状诊断——不满足原则的地方

### 2.1 职责混乱

```
ResourcePanel.tsx (617行)
  ├── collectInputResources()     ← 数据收集逻辑，嵌在视图组件内
  ├── buildOutputDisplayName()    ← 命名逻辑，嵌在视图组件内
  ├── buildPathTree()             ← 树构建逻辑，嵌在视图组件内
  ├── inputEntries useMemo        ← 数据编排逻辑，嵌在视图组件内
  ├── outputEntries useMemo       ← 同上
  └── renderTreeNodes()           ← 视图渲染
```

**问题**：一个文件承载了数据收集、过滤、命名、树构建、渲染五层职责。如果要在另一个视图里复用文件列表展示（如 Mobile 端），无法直接复用。

### 2.2 差异硬编码


**问题**：命名规则、可见性规则**分散在 if/else 链中**，每增加一个模块就要改代码。本质上是配置信息，却用命令式代码表达。

### 2.3 命名与目录混乱

| 现状 | 问题 | 违反的原则 |
|------|------|----------|
| `benchmarks/sample-inputs/sample_contract.txt` | `sample_` 无业务含义 | 命名统一 |

| `dev-test-cases.ts` (1035行) 既有测试数据又有 payload builder | 测试数据与编译逻辑耦合 | 职责清晰 |

### 2.4 共性能力缺失

11 个模块需要同样的能力，但各自实现或完全没有：
- **输入文件扫描**：`collectInputResources` 宽度一刀切，无法按模块区分"用户文件"和"内部引用"
- **输出过滤**：完全缺失，所有 `output_files` 全部展示
- **命名映射**：`buildOutputDisplayName` 覆盖 6 种 kind，fallback 用文件名
- **docx 预览**：未验证

#### 4.2.3 `artifact-display-name.ts` — 文件名映射表

```typescript
// frontend/src/config/artifact-display-name.ts

import type { OutputArtifact } from "../lib/domain";

const EXT_LABEL_ZH: Record<string, string> = {
  md: "Markdown 版",
  pdf: "PDF 版",
  docx: "Word 版",
  zip: "打包下载",
  html: "预览页",
};

/**
 * 获取产物的用户可读中文名。
 * 优先级：kind 精确匹配 → 文件名关键词匹配 → 扩展名通用标签 → 文件名本身
 */
export function resolveArtifactDisplayName(artifact: OutputArtifact, lang: "zh" | "en"): string {
  const fileName = artifact.path.replace(/\\/g, "/").split("/").pop() ?? artifact.path;
  const lower = fileName.toLowerCase();
  const ext = lower.split(".").pop() ?? "";

  if (lang === "zh") {
    // kind 精确匹配
    if (artifact.kind === "report") {
      if (lower.includes("review_report")) return `审查报告（${EXT_LABEL_ZH[ext] ?? ext.toUpperCase()}）`;
      return `${fileName.replace(/\.[^.]+$/, "")}（${EXT_LABEL_ZH[ext] ?? ext.toUpperCase()}）`;
    }

    // 扩展名通用映射
    if (EXT_LABEL_ZH[ext]) return `${fileName.replace(/\.[^.]+$/, "")}（${EXT_LABEL_ZH[ext]}）`;
  }

  // 兜底：用文件名本身
  return fileName;
}
```

**原则体现**：命名规则从组件中抽离为纯函数，可独立测试。

#### 4.3.1 `resource-collector.ts` — 输入文件收集

```typescript
// frontend/src/lib/resource-collector.ts
//
// 职责：从 run.request JSON 中提取用户提交的文件路径
// 输入：run.request (unknown)
// 输出：InputFileCandidate[]

const isRecord = (value: unknown): value is Record<string, unknown> =>
  typeof value === "object" && value !== null && !Array.isArray(value);

/** 仅匹配用户提交的文件类型（docx/doc），不匹配内部引用（json/md/csv/xlsx） */
const isUserFile = (value: string): boolean => /\.(docx?)$/i.test(value.trim());

function looksLikeUserFilePath(value: string): boolean {
  const trimmed = value.trim();
  if (!trimmed) return false;
  if (isUserFile(trimmed)) return true;
  if (/^(storage\/|outputs\/|uploads\/)/.test(trimmed) && isUserFile(trimmed)) return true;
  return false;
}

export function collectUserInputFiles(payload: unknown): InputFileCandidate[] {
  const bag = new Map<string, InputFileCandidate>();

  function scan(value: unknown, keyHint?: string) {
    if (typeof value === "string") {
      if (looksLikeUserFilePath(value) && !bag.has(value)) {
        bag.set(value, { path: value });
      }
      return;
    }
    if (Array.isArray(value)) {
      value.forEach((item) => scan(item, keyHint));
      return;
    }
    if (!isRecord(value)) return;

    // 检查对象中的路径引用
    for (const prop of ["storage_uri", "path", "file_path"]) {
      const maybePath = value[prop];
      if (typeof maybePath === "string" && looksLikeUserFilePath(maybePath) && !bag.has(maybePath)) {
        bag.set(maybePath, { path: maybePath });
      }
    }
    Object.entries(value).forEach(([key, nested]) => scan(nested, key));
  }

  scan(payload);
  return Array.from(bag.values());
}
```

**与现状差异**：从 `ResourcePanel.tsx` 内联逻辑中抽离；正则从 `/\.(docx?|pdf|md|html|txt|csv|xlsx?|png|jpg|jpeg|json)$/i` 收缩为 `/\.(docx?)$/i`。

```typescript
// 职责：从全部 output artifacts 中筛选用户可见的

// 输出：OutputArtifact[]（只含报告文件、不含中间产物）

import type { OutputArtifact } from "./domain";
import { isUserFacingArtifact } from "../config/artifact-visibility";

export function filterUserFacingArtifacts(artifacts: OutputArtifact[]): OutputArtifact[] {
  const seen = new Set<string>();

    if (seen.has(a.path)) return false;
    const name = a.path.replace(/\\/g, "/").split("/").pop() ?? "";
    if (!isUserFacingArtifact(name)) return false;
    seen.add(a.path);
    return true;
  });
}
```

```typescript
// frontend/src/lib/resource-collector.ts

export function buildInputEntries(
  runs: ModuleRun[],
  lang: "zh" | "en",
): InputEntry[] {
  const entries: InputEntry[] = [];
  const seen = new Set<string>();

  for (const run of [...runs].sort((a, b) => (a.startedAt < b.startedAt ? 1 : -1))) {
    const candidates = collectUserInputFiles(run.request);
    for (const c of candidates) {
      if (seen.has(c.path)) continue;
      seen.add(c.path);
      const name = c.path.replace(/\\/g, "/").split("/").pop() ?? c.path;
      entries.push({
        id: `input-file-${c.path}`,
        name,
        kind: "file",
        sourcePath: c.path,
        createdAt: run.startedAt,
      });
    }
  }
  return entries;
}
```

### 4.5 产物目录分离

**关键发现**：

1. **种子案例 50 个**（10 任务 × 5 案例），但 dev-test-cases 只有  24 个，因为：

### 四、后端 CLI 测试案例与前端 dev 案例的关系

#### 4.1 独立但共享场景来源

| 对比维度 | 后端 CLI 案例 (JSON) | 前端 dev 案例 (TS) |
|---------|---------------------|-------------------|
| 位置 | `backend/tests/<module>/cases/*.json` | `frontend/src/lib/dev-test-cases.ts` |
| 格式 | `{ case_id, description, input: {...}, expected: { result_not_empty, fields_equal, min_counts, ... } }` | `{ name, description, jurisdiction, formDefaults, backendFilePaths, payload }` |
| 执行方式 | `python -m backend.tests.harness.runner <module> <case>` 或 pytest | 前端 HTTP POST 到 `/api/v1/<module>/generate` |
| LLM 依赖 | 可选 `--no-llm` 跳过 LLM 调用 | 始终使用真实 LLM |
| 断言方式 | `validators.py` 声明式断言（result_not_empty/fields_equal/min_counts） | 无自动化断言——前端只展示结果 |
| 输入字段 | 使用后端 Pydantic schema 字段名 | 使用前端表单 FormValues 字段名 |

#### 4.2 case_inventory.json 三方契约

`config/case_inventory.json` 声明 11 模块中每个模块应有多少个 CLI 案例和前端案例：

```json
{
  "pipia": {
    "module_id": "cn.pipia",
    "cli_cases": [{"case_id": "01_minimal", "assertions": 16}],  // 1 个
    "frontend_cases": 2                                           // 2 个
  }
}
```

两套**独立验证门**（gate）确保契约不被破坏：

- **后端门**：`scripts/check_case_parity.py` 扫描 `backend/tests/<module>/cases/` 目录，运行时重新计算 `cli_cases` 数量，与 `case_inventory.json` 比对
- **前端门**：`frontend/tests/contract/case-inventory.test.ts` 导入 `DEV_TEST_CASES` 对象，比对各模块 `length` 与 inventory 中 `frontend_cases`
- **变异测试门**：`backend/tests/harness/test_case_parity.py` 测试 gate 本身是否正确——例如删除一个 case 后 gate 必须报错

```bash
# CLI 执行（后端）
uv run python backend/tests/harness/runner.py all --no-llm  # 运行全部 17 个 CLI 案例
uv run python scripts/check_case_parity.py                  # 验证契约

# 前端执行
npx vitest run frontend/tests/contract/case-inventory.test.ts
```

#### 4.3 同源性验证

对比同一场景在 CLI 和前端 dev 中的表现——以 diagnosis "电商用户数据出境"为例：

| 字段 | CLI `diagnosis/cases/01_scc_path.json` | dev `diagEcommerce` |
|------|--------------------------------------|--------------------|
| 公司名 | `跨境优品科技有限公司` | `跨境优品` |
| 行业 | `跨境电商` | `电商零售` |

### 五、核心结论

1. **"测试案例按钮是否基于真实测试文档？"**
   - **是**——概念层面。dev-test-cases.ts 中全部 24 个案例的场景来源都是种子案例 docx（任务1-10），场景特征（行业、数据量级、出境目的、法域）与种子案例一致。
   - **但不完全**——数据层面。dev 案例的 formDefaults 是**重新构造**的（公司名、具体数据值可能不同），且使用了**与种子 docx 完全不同的 schema 字段体系**。seed docx 是自然语言 Q&A 格式，dev-test-cases 是结构化 form schema 格式。

2. **种子 docx → dev-test-cases.ts 的链路是手动转录，无自动化**。种子 docx 的 50 个案例中：
   - 24 个被转录为 dev 案例（7 个模块，每模块 1-3 个）
   - 26 个未转录（任务4/7/8 无对应模块；任务1/2/3 中只转录了部分）

3. **两套测试体系是独立的**——CLI harness 和前端 dev cases 虽共享场景来源，但数据格式不同、执行方式不同、断言方式不同。`case_inventory.json` 是保持两者一致性的唯一契约。如果你在 dev-test-cases.ts 中增删案例，必须同步更新 `case_inventory.json` 的 `frontend_cases`，否则 CI gate 会报错。

4. **对侧边栏改造的启示**：dev-test-cases 的 `backendFilePaths` 直接影响侧边栏显示的输入文件。当前 `pipiaSCCFiling` 仍用 `sample_contract.txt`，即使对应的种子案例（任务3）描述的是"已与美国子公司签订DPA"——这说明 dev 案例的文件配置**未同步更新**为真实测试文档。

### B.6 文件性质分类图例

| 标记 | 含义 | 用途 |
|------|------|------|
| 📋 功能说明 | 功能路径描述文档（含 Reference 标注） | 供开发者和法律专家理解功能设计 |
| 📋 测试说明 | "X测试案例及预期输出"文档 | 描述输入场景+植入风险点+预期审查结论，**不是**系统实际处理的输入文件 |
| 📄 法规参考 | 法规原文/操作手册 PDF | Runtime 不直接读取，作为 RAG 检索源 |
| 📄 参考文档 | 模板/样例，无 `{{}}` 占位但有完整指导文本 | 可作为系统输入的参考附加上下文 |
| ✅ 测试输入 | 系统实际处理的有内容文档 | `backendFilePaths` 的正确内容——用户上传的真实合同/协议/数据文件 |
| ❌ 纯模板 | 仅含 `{{variable}}` 占位符的空壳 | **不能**作为测试输入——后端收到全是变量名 |
| ❌ 无效占位 | Stub 文件（如图片路径引用） | 不能作为测试输入 |
