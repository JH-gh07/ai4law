## 一、背景与根因

前端各 Wizard 在开发者模式下并存 **三类开发期入口**，且部分入口**语义重复**：

| 类别 | 位置 | 行为 | 数据来源 | 处置 |
|---|---|---|---|---|
| **A 类** | 顶部「🧪 测试案例」（11 处） | 打开案例选择器 → 回填表单 + 回填附件 → **手动再运行** | `dev-test-cases.ts`（`tc.formDefaults` + `tc.backendFilePaths`） | ✅ **保留** |
| **B 类** | 底部「一键体验/一键运行」（10 处） | 注入预设表单 + 预设附件 → **直接调后端执行**（跳过人工确认） | `dev-presets.ts`（`preset.formDefaults` + `preset.backendFilePaths`） | ❌ 删除 |
| **C 类** | us_14117 底部额外的「🧪 测试案例」（1 处） | 与 A 类**完全相同**，仅因放在底部运行条而多出 | `dev-test-cases.ts` | ❌ 删除 |

**根因**：A 类（顶部）与 C 类（us_14117 底部）是同一入口的重复渲染；B 类（底部「一键」）与「顶部选案例回填后再运行」的完整流程能力重叠，且 B 类「跳过确认直接跑」与 Wizard 的「人工确认」交互语义冲突。

### 10.3 核心结论（为什么不能直接「改一行 import 就取代」）

1. `input.json` 是**自由文本抽取记录**，前端 Wizard 需要的是 `formDefaults`（表单字段值）+ `backendFilePaths`（附件路径），二者之间缺两层转换：
   - **Level B**：抽取记录 → 模块请求 schema（`requests/<case_id>.request.json`）——task074 落实后 **9 个成功**（task02_case4 + task04/06/07/08 各 case1/2），已按 task074 忠实化（DPIA 忠实提取 / TIA 走 `structured_input` / task04·06 附件派生），不再伪完整。
   - **Level C**：模块请求 → 前端 `DevTestCase`（`formDefaults` + `backendFilePaths`）——**已由 `build_seed_frontend_cases.py` 落实，产出38例**。
2. Level B 的 `rejected`（task074 落实后 30 个）**并非全部只能人工补**：其中代码可消除项（解析 bug `_parse_count`/`_parse_ynu`、可派生附件 task04/06、TIA 走错路径、DPIA 伪完整反向 false）**已由 task074 消除**，从 36 降到 30；再经**占位符主体名替换测试名**（task02/03 的公司名/接收方名，仅替换不影响业务的标识名，业务事实不碰），task02_case4 转 converted，`rejected` 降至 **29**。剩余 29 个才是真正需数据 owner 补的「原文没写的结构化字段」；gold 签署属验收阶段，不阻塞 Level B。适配器始终**禁止伪造**默认值。
3. task4/6/7/8 的 case3/4/5 共 12 个仍是 v1.0 旧内容（`pending_correction`），在改回 v2.0 前不能进入 Level B；这不是「无产品能力」，而是「旧内容待修正」。
4. 种子案例 **无 expected.json（0 gold）**，替换后前端案例「能跑、不能对答案」，原有 `benchmarks/cases/**/expected.json` 的验收 oracle 对种子案例不适用。
