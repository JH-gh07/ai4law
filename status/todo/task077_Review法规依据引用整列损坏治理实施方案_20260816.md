## 0. 修复原则（避免"打补丁式"返工）

1. **来源真相优先**：`regulation_articles.jsonl` 是派生产物，其真相是 `resources/legal/sources/cn/snapshots/*.html` 快照 + `sources.csv`。非法条号不能靠手工改 36 行，必须**修生成器 → 重新生成 → 门禁校验**。
2. **分层修复，逐层可验**：数据层 → 构建层 → 检索层 → 组装层 → 校验层，每层修完跑对应验证，不留"上游修了下游仍坏"的盲区。
3. **类型与用途强制分离**：法条（statute）、模板（template）、案例（case）必须分字段、分用途、分渲染；模板不得进入法规证据池，案例不得进入"法规依据"。
4. **先回滚基线，再改**：改动前 `git commit` 当前工作树作为回滚点（不 `git add .`，按文件归属逐文件暂存）。

### T02 数据层：修复非法条号"处罚-X-X"

**根因**：`scripts/fix_cn_law_001_duplicates.py:78` 把 `-处罚-{n}` 去重后缀写进了 `article_ref`。

**修复步骤**：

1. 修正 `fix_cn_law_001_duplicates.py`：不再改写 `article_ref` 为 `{old}-处罚-{n}`。去重信息写入独立的 `structured_payload`/新字段（如 `"role":"penalty_extension"` + `"disambiguation": n`），`article_ref` 保留为真实条号（从 `article_id` 或快照原文推导）。
2. 校验生成链 `scripts/build_regulation_articles.py`：确认其输出的 `article_ref` 只接受合法条号（`第N条` / `第N条第N款` / 纯阿拉伯数字），并确认是否存在同类后缀污染。
3. 从快照重新生成 `regulation_articles.jsonl`（真相源是 `resources/legal/sources/cn/snapshots/*.html`），而非手改 36 行。
4. 在 `scripts/check_citation_source_integrity.py` 增加**条号格式门**：`article_ref` 必须匹配合法条号正则；凡命中 `处罚-`、`-ext-`、`{原条号}-处罚` 或含非法前缀的，一律计为 `invalid_article_ref_count` 并 fail。

**验证命令**：

```bash
./.venv/bin/python scripts/check_citation_source_integrity.py
# 期望：invalid_article_ref_count = 0；处罚- 命中 0
grep -c '"article_ref": "处罚-' resources/legal/registry/regulation_articles.jsonl
# 期望：0
```

**验收**：`regulation_articles.jsonl` 中不再有以 `处罚-`/`-ext-` 开头的 `article_ref`；`check_citation_source_integrity.py` 在人为注入一条 `处罚-` 时能失败退出（负向用例）。

### T03 构建层：模板不再进入法规证据池

**根因**：`builders_v2.py:165` 硬编码 `layer="L1_regulatory_evidence"`；`source_registry.v1.json` 把模板归为 `source_kind=standard_clause`。

**修复步骤**：

1. `build_legal_chunks_cn()` 的 `layer` 改由 `registry_entry.layer`/`doc_type` 推导：`doc_type=template` → `L4_template`，`template_type=official_template`；法规/条例 → `L1_regulatory_evidence`。
2. 修正注册表 `_source_kind_from_row()`：`doc_type=template` → `template_slot`（不再是 `standard_clause`）。
3. 重新生成 `source_registry.v1.json`，使模板 `layer=L4_template`、`source_kind=template_slot`、`can_be_cited=false`。
4. `build_legal_chunks_cn()` 直接跳过 `doc_type=template` 的 `regulation_articles.jsonl` 条目，模板只由 `build_template_chunks_cn()` 生成并进入 `template_index_cn`。

**验收**：`legal_index_cn` 不再包含 CN-TPL-016/017 等模板来源；模板只出现在 `template_index_cn`。

### T04 检索层：全量展开限流

**根因**：`orchestrator.py:618-628` `_legal_by_reference_ids_for_index` 按 source_id 全量展开，`top_k`/`source_cap` 失效。

**修复步骤**：

1. 给 `_legal_by_reference_ids_for_index` 增加 `source_cap`（如每法源最多 N 条）与总量上限，避免一个 workflow 规则引用把整部法全部展开。
2. 优先按 `chunk_id`/`article_no` 精确匹配，而不是 `source_id` 全量；对确需整源引用的场景，走受控的"source overview"单块，而非逐条。
3. 展开结果仍须过 `UsagePolicyFilter.filter(usage="legal_grounding")`（模板已被 T03 排除，双重保险）。

### T05 组装层：案例分流、名称归一、精确引用

**根因**：`rag_provider.py:115-122` 案例混入 citations；`review_rulebook.json` 短名 vs RAG 全名未归一；`clause_reviewer.py:141-151` 全量盲贴。

**修复步骤**：

1. `rag_provider.py`：DeliLegal `search_cases` 结果写入独立字段 `reference_cases`（或 `config["reference_cases"]`），**不**拼入 `citations`；渲染层把案例放到"参考案例"区，而非"法规依据"。
2. 引用显示名归一：`_canonical_source_id` 命中后，用注册表 `title` 回写统一显示名（如统一为"中华人民共和国个人信息保护法"），消除短名/全名并存。
3. `clause_reviewer.py`：去掉"对所有无引用 issue 盲贴整份 config citations"的逻辑，改为按 clause_type 取 rulebook 的精确 citations + RAG 命中 top-k，去重并设单 issue 引用数上限（如 ≤ 8 条）。
4. `citation_sources` 只由 `structured_citations`（法条/法规类）生成，案例与模板不得进入。

### T06 校验层：空档修复 + 条号格式门 + 报告终检

**根因**：`service.py:399-402` + `citation_relevance_checker.py:89-94` 存在 `relevant=False` 但 `issues=[]` 空档；`_score_citation` 不做条号格式/数量校验。

**修复步骤**：

1. `CitationRelevanceChecker.check()`：当 `relevant=False` 时，若 `issues` 为空，回填默认说明（如"引用与问题类型相关性不足"），不再出现空白警告。
2. `_score_citation`：增加条号格式校验（`处罚-`/`-ext-` 直接判非法并记入 issues）。
3. 渲染前终检：`service.py` 或 `schema_first.py` 在生成报告前，若任一 issue 的 `citation_sources` 含非法条号、模板来源或超过上限数量，则 fail-closed（阻止产出错误报告）并写诊断。

## 4. 风险与回滚

- 数据重新生成依赖快照真相源；若某快照缺失导致无法还原正确条号，该来源保持隔离（`metadata_review_required`/`can_be_cited=false`）并记录待法律/数据签字，不强行猜测。
- 模板移出 `legal_index_cn` 可能影响其它模块检索，需全量回归确认无回归；若某模块确实依赖模板结构，改为通过 `template_index` 的 `structure_control` 用途获取。
- 每完成一个任务即本地提交一次（按文件归属逐文件暂存），保留可回滚粒度；任何门禁失败即停止，不跨任务推进。
