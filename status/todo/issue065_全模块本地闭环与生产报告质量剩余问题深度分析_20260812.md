## 一、结论先行

当前困难不是“PIPIA 还不能运行”，也不是“Review 仍未写 RunEvent”。截至本次核查：

- 11 个注册模块已有共享 Scenario 基础，CLI 语义门禁通过；
- PIPIA 3 条已登记共享场景（均由正式资料派生）已经完成本地 HTTP、上传、异步任务、SSE、报告、引用跳转和 PDF canvas 验收；
- Review 已接入统一 RunEvent/SSE，后端重启会把中断任务收尾为 `FAILED`，前端恢复按 `asyncTaskId` 归并；
- 原 `resources/new` 的 207 个有效文件已完成分层迁移，活动 Scenario/CLI/E2E/catalog 已切换规范路径，旧目录已删除；
- 资源迁移没有等同于案例验收完成：50 个种子案例原件和 Gold 已归位，但来源保真抽取记录、模块请求、法律审核 expected、rubric 和冲突任务映射仍未完成；
- 当前专项复验通过：后端认证、用户隔离、产物权限、Review、持久化事件 `23 passed`；前端任务恢复、事件合并和 workspace `11 passed`；
- 远程部署没有执行。

真正未闭环的是以下七类问题：

| 编号 | 问题域 | 当前状态 | 主要风险 |
|---|---|---|---|
| P1 | 全模块统一口径的真实浏览器验收 | PIPIA 完成，其他模块未按同一门禁全部完成 | 单元/CLI 通过但真实表单、上传、SSE、产物或引用失败 |
| P2 | 正式需求案例覆盖完整性 | 原始资料已迁入规范目录；11 模块有共享场景，但 50 个种子案例尚未完成抽取、模块请求转换和签署 | 用“文件已归位”冒充正式案例和法律 Gold 已可执行 |
| P3 | 生产模型法律内容质量 | 确定性测试 LLM 只证明链路 | 技术链路通过但正式法律报告重复、空泛或结论失真 |
| P4 | Report IR 与多格式同源渲染 | 新 Compiler 为增量门禁，旧 renderer 仍生效 | Markdown、DOCX、PDF 内容、结构和视觉不一致 |
| P5 | 任务状态、事件和失败重跑的跨模块一致性 | Review 已修复，尚未证明所有模块都满足 | 旧 `FAILED` 残留、任务空间重复、终态覆盖错误 |
| P6 | 认证和用户数据边界的浏览器验收 | 后端专项测试通过，前端无独立 auth 测试文件 | 刷新、失效 token、跨用户任务或产物访问未在浏览器证明 |
| P7 | 依赖、证据安全和脏工作区收尾 | 有明确边界，尚未完成最终提交整理 | 把 trace 中的 Authorization、临时产物或无关改动提交 |

必须区分三种证据等级：

```text
代码存在
≠ 自动化测试通过
≠ 真实登录态浏览器端到端通过
≠ 生产模型内容和正式文件质量通过
```

## 二、事实口径和证据等级

### 2.1 模块口径

当前共享场景目录实际有 22 个 Scenario，覆盖 10 个独立业务实现模块：


第 11 个注册模块 `cn_flow` 不建立新的业务事实源，而复用 `us_14117` 的红/黄案例验证旧接口兼容转换。代码和清单依据：

- `benchmarks/cases/`
- `config/dev_case_catalog.json`
- `config/case_inventory.json`
- `status/check/DataComplyFlow_统一Scenario全模块迁移验收_20260811.md`

## 三、P1：全模块真实浏览器闭环尚未完成

### 3.1 问题描述

现有历史截图、共享案例 builder 测试和 CLI 通过不能自动合并成完整浏览器验收。统一标准要求同一 Scenario 在浏览器内同时证明：

```text
共享 scenario
→ 前端表单回填
→ 前端 builder 最终请求深比较
→ 登录态 HTTP/附件上传
→ 后端同步或异步任务
→ SSE 事件与终态
→ 前端 store 回写
→ 报告/产物/引用跳转
→ CLI 与浏览器关键结论一致
```

### 3.2 代码依据与逻辑入口

- 前端模块请求转换：`frontend/src/features/module-runner/payload-builders/`
- 前端运行模型：`frontend/src/features/module-runner/model.ts`
- 任务恢复和 `taskSpaceId`/`asyncTaskId`：`frontend/src/lib/app-store.tsx`
- SSE token、manifest、stream：`frontend/src/api/events.ts`
- 工作区运行入口：`frontend/src/pages/WorkspacePage.tsx`
- 各模块异步管理器：`backend/common/tasks/manager.py`
- 事件发布和持久化：`backend/common/events/manager.py`、`backend/common/events/store.py`
- 统一事件 API：`backend/api/v1/endpoints/events.py`

PIPIA 当前完整实现证据：

- E2E：`frontend/tests/e2e/pipia-shared-cases-local.e2e.ts`
- 浏览器专用本地服务：`backend/tests/pipia_browser_app.py`
- 验收报告：`status/check/DataComplyFlow_PIPIA共享案例与浏览器本地验收_20260812.md`
- 截图和脱敏网络摘要：`status/check/phase3_pipia_shared_local/`

### 3.3 当前执行结果

PIPIA 最终本地结果：

```text
后端 + CLI + parity：45 passed
前端全量：153 passed, 2 skipped
case semantic gate：11 modules / 26 CLI cases / 603 leaf checks / 28 dev cases
浏览器完整套件：4 passed
```

EU SCC 和 TIA 已完成“共享事实 → CLI → 前端 builder 深比较”，但对应验收报告明确写明没有完成真实 HTTP/浏览器链路：

- `status/check/DataComplyFlow_EUSCC共享案例本地验收_20260811.md`
- `status/check/DataComplyFlow_TIA共享案例本地验收_20260811.md`

其他模块存在历史首跑报告，但历史首跑不一定同时包含当前共享 Scenario 请求深比较、失败重跑、SSE、引用和多格式检查，因此不能直接标为当前 L4 完成。

### 3.4 原因分析

这是测试覆盖层级不一致，不是单一组件故障。各模块的表单契约、附件、同步/异步入口和产物角色不同；复制 PIPIA 的页面点击脚本而不核对模块契约，会产生“页面跑完但测试了错误事实”的假通过。

### 3.5 关闭条件

每个模块至少选择正式 Scenario，保存：标准化前端请求及哈希、CLI 请求及哈希、任务 ID、SSE manifest、最终状态、产物清单、引用跳转结果和真实截图。失败后重跑必须证明旧终态被新运行正确替代，但历史运行仍可审计。

### 4.3 已确认缺口

- TIA 正式案例二“法国到英国充分性决定”尚未进入共享案例，见 `status/check/DataComplyFlow_TIA共享案例本地验收_20260811.md`。
- Review 第二个前端案例仍分类为 `product_extension`，`config/dev_case_catalog.json` 明确写明缺乏与正式文档专项审查案例的来源对应。
- `cn_flow` 是 `us_14117` 的兼容适配，不应被统计为一套新增正式业务案例。
- PIPIA 三例均登记为 `source_derived`，派生补值和附件 fixture 必须持续保留来源、原因和哈希，不能改写成 `source_exact`。
- 50 个 seed DOCX 已归位，但 `benchmarks/datasets/seed-cases-v1/inputs/` 和 `expected/` 当前均为 0；Gold 原件在 manifest 中仍标记为 `PENDING (requires rubric extraction)`。
- `scripts/build_seed_case_inputs.py` 已把 `SRC_DIR` 切到新目录，但仍使用旧文件名模式 `任务*_案例*_测试结果.docx`；新原件名为 `taskNN_caseM.docx`。2026-08-13 dry-run 实际结果是 `source DOCX found: 0 / ERROR expected 50 source files`。
- seed 任务 4/6/7/8 在脚本 `TASKS` 中仍为 `mapping_status=conflict` 且没有稳定 `module_id`，未裁决前不能接入正式 runner。

### 4.4 根因

过去案例分散在 TypeScript、CLI JSON、fixture 和文档中，数量门禁只能发现“有没有案例”，不能发现公司、国家、接收方、人数、数据类别或附件被改写。资源迁移解决的是物理位置和活动引用，不会自动完成 DOCX 语义抽取、模块身份裁决或法律 Gold 签署。

当前 seed 构建断链的具体原理是：

```text
迁移前中文文件名：任务1_案例1_测试结果.docx
→ 脚本 glob：任务*_案例*_测试结果.docx

迁移后规范文件名：task01/task01_case1.docx
→ glob 命中 0 个
→ 在 build_record() 解析任务号前即返回错误码 2
→ inputs 仍为 0，后续 seed expected 对齐与 runner 接线没有统一结构化输入
```

这说明迁移验收中的“脚本路径已切换、编译通过”只证明 import/语法成立，没有证明数据构建行为成立。该结论必须以实际 dry-run 纠正。

### 4.5 关闭条件

1. 原件抽取门禁：以 `manifest.json` 为唯一输入清单，修复 seed 构建器的文件发现和任务号解析，实现 `50 sources → 50 extraction records`；必须验证 manifest 条目数、路径、task/case、SHA-256 与磁盘文件集合完全相等，规范文件名解析只作一致性校验，禁止以 glob 代替清单；
2. 模块可执行门禁：裁决任务身份后，将产品已支持案例的通用 `input.paragraphs` 显式转换为对应模块请求 Schema，并通过 Schema、CLI 及 HTTP；产品未支持案例必须明确登记为 gap。不得把 50 个抽取记录称为 50 个可执行请求；
3. 裁决 seed 任务 4/6/7/8 的模块身份，不存在对应产品能力的不得硬塞到相近模块；
4. 从 Gold 原件独立生成有段落/表格 provenance 的 `rubric.v1.json`；该工作技术上不依赖 input 抽取，但 rubric 与 expected 均须经法域法律专家签署后才能发布；
5. 建立正式资料案例总表，每一条必须落入 `source_exact`、`source_derived`、`product_extension`、`compatibility_adapter` 或“明确不实施并说明原因”之一；任何正式案例都不能静默遗漏。

## 五、P3：真实生产模型报告质量尚未验收

### 5.1 问题描述

PIPIA 浏览器 E2E 使用确定性测试 LLM，证明的是 HTTP、任务、事件、报告回写和渲染链路，不证明真实模型法律文案达到需求和黄金样例标准。

### 5.2 代码与执行依据

- 确定性服务：`backend/tests/pipia_browser_app.py`
- PIPIA 逐章生成：`backend/domains/cn/pipia/service.py:156`
- 测试边界说明：`status/check/DataComplyFlow_PIPIA共享案例与浏览器本地验收_20260812.md`
- 内容/模板审计：`status/todo/060task/060task_02_生成内容与模板拼接重复审计_20260812.md`
- 理想报告方案：`status/todo/060task/060task_03_理想报告结构与统一渲染整改方案_20260812.md`

真实 PIPIA 逻辑目前为每个章节重复传入统一 `context_block` 并调用 `generate_chapter()`。这具有以下机制风险：

```text
同一企业/接收方/风险/法规上下文
→ 对七个章节分别调用模型
→ 每章都可能重新介绍背景、法律依据和总风险
→ 外层 renderer 再插入标题、摘要和问题表
→ 形成跨章同义重复或结论多次展示
```

同时，PIPIA 无模型分支当前直接写入“LLM未配置”占位内容，而同文件另有完整 `_render_rule_based_chapter()` 定义但当前逐章循环未调用。这说明“规则回退已定义”不等于“生产入口实际使用规则回退”。

### 5.3 当前能够和不能够下的结论

能够确认：三条 PIPIA 测试报告能经过浏览器展示、引用和 PDF canvas 渲染。

不能确认：真实模型输出不重复、法律判断准确、事实与建议分离、引用逐项支撑、章节长度合理、与黄金样例精神一致。

### 5.4 关闭条件

使用真实生产模型对固定共享 Scenario 运行，保存 prompt/Trace、章节原始输出、规则 findings、最终各格式文本；逐项对照需求和黄金样例，并设置事实保真、结论一致、引用支持、重复率、禁止内容和人工法律审核门禁。确定性 LLM E2E 与生产模型内容验收必须保持为两套测试。

## 六、P4：Report IR 尚未成为唯一产物源，多格式仍有系统性不一致

### 6.1 已证实的架构状态

`backend/common/reporting/compiler/core.py:1` 明确说明当前 Compiler 是增量 Stage A：只在旧 renderer 前验证 IR，尚未替换当前报告生成路径。

真实结构是：

```text
DocumentIR / Compiler 门禁
+
各模块旧 chapter / sections / template mapping
+
公共与模块专属 Markdown/DOCX/PDF renderer
```

代码地址：

- IR Schema：`backend/common/reporting/schema/document.py`
- Compiler：`backend/common/reporting/compiler/core.py`
- 公共渲染：`backend/common/render/`
- 报告登记和 PDF：`backend/services/report_service.py`
- 模块 adapter：`backend/domains/*/*/schema_first.py`
- 模块 renderer：`backend/domains/*/*/*report_renderer.py`

### 6.2 已证实的重复和不一致机制

1. BCR 在 `backend/domains/eu/bcr_review/service.py:468` 先构造 sections 和详细 findings 表，又在 471 行为了兼容重新构造 chapters，随后交给 `_render_document_driven()`；同一 finding 具备摘要、详细表、风险分类和整改路线图多次出现的条件。

### 8.2 当前执行结果和证据缺口

本次后端认证/用户范围/产物权限测试已通过，但 `frontend/src` 和 `frontend/tests` 中没有独立的 auth/AuthContext/ProtectedRoute 测试文件。PIPIA 浏览器测试证明一个本地测试用户可注册、上传和访问自己的报告，不等于以下场景已经全部验收：

- `remember=false` 关闭标签页后失效；
- `remember=true` 刷新和重开后恢复；
- token 过期或 `/me` 返回 401 后清理身份并跳转；
- 用户 A 无法读取用户 B 的任务、事件、报告和附件；
- logout 接口失败时本地 token 仍被清理且 UI 状态一致。

### 8.3 设计风险说明

`frontend/src/api/auth.ts:169` 的 `getCurrentUser()` 当前对所有异常执行同一处理：清除 token 并返回 `null`。因此真实 401、请求超时、后端暂时不可用和非 JSON 响应都会被解释为“身份失效”。根因链路是：

```text
/auth/me 瞬时网络错误或超时
→ requestJson 抛异常
→ getCurrentUser catch 不区分错误类型
→ clearToken()
→ AuthProvider user=null
→ ProtectedRoute 跳回登录页
```

此外，`apiFetch()` 只提供 transport 和超时，不包含全局 401 → AuthContext 状态同步；各 endpoint 显式组装鉴权头和处理错误。因此仍需验证“任务请求收到 401 时，页面用户状态是否同步清理”，不能只验证 `/auth/me`。

token 当前存于 Web Storage，前端 XSS 会扩大 token 泄露影响；这是既有架构事实，不应在本 issue 中未经设计直接改成 Cookie。短期验收必须确认敏感 trace、日志和截图不保存 Authorization；中期是否迁移 HttpOnly/SameSite Cookie 需单独安全设计和 CSRF 策略。

### 8.4 关闭条件

补齐 auth service、AuthContext、ProtectedRoute 单测和双用户浏览器 E2E；先区分 401/403 与网络/超时错误，再验证刷新、记住我、失效 token、登出、越权 API、SSE token 和产物下载。任何 401/403 都必须有明确 UI 终态，网络瞬时失败不得无提示销毁仍可能有效的本地身份。
