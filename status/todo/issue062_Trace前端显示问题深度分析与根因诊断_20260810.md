# issue062 — Trace 前端显示问题深度分析与根因诊断

> **日期**: 2026-08-10
> **关联范围**: `frontend/src/components/workspace/AssistantPanel.tsx`, `frontend/src/styles/app/workspace.css`, `frontend/src/lib/trace-adapter.ts`, `frontend/src/lib/useTaskEvents.ts`, `backend/common/trace/recorder.py`, `backend/common/events/manager.py`, `backend/api/v1/endpoints/events.py`
> **严重程度**: P1 (用户可感知的体验缺陷)
> **影响模块**: 全部 10 个模块的 Copilot 面板 Trace 实时显示

---

## 概述

Trace（执行追踪）是用户在执行法律工作流时评估进度、诊断错误的实时可视化工具。当前 Trace 在前端 Copilot 面板中存在三个明显问题：

1. **半截窗口**：Trace 面板仅占据 Copilot 聊天区的极小视口，大量节点被挤压在 ~288px 的可滚动盒内
2. **延迟显示**：部分操作中 Trace 不是立即出现的，而是存在 1-5 秒不等的延迟
3. **截断/省略**：关键信息（法律条文内容、检索结果、LLM 输出）被多处截断，用户难以获取完整上下文

以下逐一展开根因分析。

---

## Issue 062-1: Copilot 半截窗口 — Trace 面板仅占极小视口

### 问题描述

当用户在 Copilot 面板（右侧 300px 栏）运行工作流时，Trace 时间线被嵌入聊天消息流中，实际可用高度被限制在 `18rem`（约 288px）的可滚动小窗口内。对于包含 20+ 节点的典型工作流（如 CPRA、Assessment），用户只能看到 3-4 个节点，其余必须在该小窗口内滚动查看。这与工作区时间线标签页（全宽无限制）形成鲜明对比。

### 根因分析：三层 CSS 约束叠加

**第一层：右侧栏固定宽度 300px**

```css
/* frontend/src/styles/app/workspace.css:313 */
.workspace-grid.left-open.right-open {
  grid-template-columns: 260px 10px minmax(0, 1fr) 10px 300px;
}
```

AssistPane 被硬编码为 300px。在 300px 宽度内渲染包含 badge、stage、action、timestamp、duration、token、输入/输出块的 TraceNodeView，横向空间极度紧张。

**第二层：Trace 嵌入聊天流，被挤到 auto 行**

```css
/* frontend/src/styles/app/workspace.css:4150-4153 */
.assistant-mode-shell-chat {
  min-height: 0;
  display: grid;
  grid-template-rows: auto minmax(0, 1fr);
  gap: 0.44rem;
}

/* line 4165 */
.assistant-chat-shell {
  grid-row: 2 / -1;   /* ← 聊天流占据第二行（1fr 弹性空间）*/
}
```

布局为两行 grid：第一行 `auto`（标题栏），第二行 `1fr`（聊天流）。Trace 被直接插入 `assistant-chat-stream` 的 flex 流中（见下方代码），与消息气泡抢占空间。然而 `.copilot-trace-inline-body` 的 `max-height: 18rem` 强行将 Trace 截断，不与消息气泡公平竞争剩余空间。

**第三层：硬编码 max-height: 18rem**

```css
/* frontend/src/styles/app/workspace.css:4231-4239 */
.copilot-trace-inline-body {
  max-height: 18rem;       /* ← 288px 硬限制 */
  min-height: 0;
  min-width: 0;
  overflow-y: auto;        /* ← 超出则内部滚动，形成"盒中盒" */
  overflow-x: hidden;
  padding: 0.1rem 0.08rem 0.3rem;
  border-top: 1px solid rgba(217, 228, 241, 0.9);
}
```

### 代码执行路径

```
AssistantPanel.tsx:37
  → traceEvents = useTaskEvents(taskId)              // 订阅 SSE/轮询原始事件
  → traceNodes = adaptEvents(traceEvents, lang)       // 转换为 TraceNode[]
  → 渲染在 assistant-copilot-stream 内:

AssistantPanel.tsx:205-229
  <section className="assistant-copilot-stream">
    {/* Trace 被插入为流中的第一个子元素 */}
    <div className="copilot-trace-inline">
      <div className="copilot-trace-inline-body">      ← max-height: 18rem
        <div className="trace-timeline-line-embedded">
          {traceNodes.map(node => <TraceNodeView />)}   ← 20+ 节点挤在 288px
        </div>
      </div>
    </div>
    {/* 然后是聊天消息气泡 */}
    {messages.map(item => <article>...)}
  </section>
```

### 影响评估

- 典型 CPRA 工作流产生 15-35 个 TraceNode，每个节点在折叠态占约 60-90px
- 18rem (288px) 约容纳 3-4 个节点
- 用户需在小窗口内频繁滚动才能看到完整执行历史
- 对比工作区时间线标签页（全宽、无限高），体验严重降级

## Issue 062-2: Trace 延迟显示 — 执行已开始但前端无响应

### 问题描述

用户点击"运行"后，部分模块的后端工作已开始执行（日志可见），但 Copilot 面板中的 Trace 时间线在 1-5 秒后才开始显示节点。体验上表现为"卡顿"或"无响应"，与正常即时显示形成差异。

### 根因分析：五层延迟叠加

**因素 1：SSE 连接建立需两次网络往返**

```
前端 useTaskEvents.ts:276 → ensureSSE(taskId)
  ├─ 第一次往返: POST /api/v1/events/task/{taskId}/token     ← 获取 stream_token
  │   backend/api/v1/endpoints/events.py:112 → issue_stream_token()
  │   backend/common/events/manager.py:44 → token 有效期 5 分钟
  │
  └─ 第二次往返: GET /api/v1/events/task/{taskId}/stream?token=...&since=N
      backend/api/v1/endpoints/events.py:56 → task_event_stream()
      → 创建 asyncio.Queue, subscribe(), 回放 since 之后的历史事件
```

两次 HTTP 请求（token + EventSource 连接）在网络条件不佳时总计可能花费 1-2 秒。

```typescript
// frontend/src/lib/useTaskEvents.ts:183-222
async function ensureSSE(taskId: string): Promise<void> {
  // ... 已有连接或已终止则跳过
  pendingConnections.add(taskId);
  try {
    const { stream_token } = await fetchStreamToken(taskId);       // ← 网络请求 1
    // ...
    const es = new EventSource(                                     // ← 网络请求 2
      `${getTaskEventStreamUrl(taskId)}?token=...&since=...`
    );
    es.onopen = () => { stopPolling(taskId); };                    // ← 连接成功后停止轮询
    es.onmessage = (message) => { publishTaskEvents(taskId, [...]) };
    es.onerror = () => { /* close + scheduleReconnect */ };
    eventSources.set(taskId, es);
  } catch {
    scheduleReconnect(taskId);                                      // ← 失败走轮询
  }
}
```

**因素 2：轮询 fallback 有 3 秒初始延迟**

```typescript
// frontend/src/lib/useTaskEvents.ts:278-285
const INITIAL_FALLBACK_DELAY_MS = 3000;   // ← 3 秒后才启动轮询

const fallbackTimer = setTimeout(() => {
  if (hasTerminalEvent(taskId)) return;
  const es = eventSources.get(taskId);
  if (!es || es.readyState !== EventSource.OPEN) ensurePolling(taskId);
}, INITIAL_FALLBACK_DELAY_MS);
```

如果 SSE token 请求慢或 EventSource 握手失败，前端会等待 3 秒后才启动轮询 fallback。这 3 秒内，即使用户肉眼看到后端日志在输出，前端 Trace 也是空白。

**因素 3：轮询间隔 1500ms**

```typescript
// frontend/src/lib/useTaskEvents.ts:231, 237
let delayMs = 1500;                        // ← 默认 1.5 秒间隔
// ...
delayMs = data.has_more ? 0 : 1500;        // ← 有更多数据时立即拉取，否则等 1.5 秒
```

即使轮询已启动，每次轮询间隔至少 1.5 秒（除非服务端返回 `has_more: true` 触发紧接连拉）。

**因素 4：SSE 断线重连延迟 1000ms**

```typescript
// frontend/src/lib/useTaskEvents.ts:169-180
function scheduleReconnect(taskId: string): void {
  // ...
  const timer = setTimeout(() => {
    reconnectTimers.delete(taskId);
    void ensureSSE(taskId);
  }, 1000);                                // ← 1 秒后重连
  reconnectTimers.set(taskId, timer);
}
```

SSE 断开后（如网络波动、后端超时），前端 1 秒后才重新尝试建立连接。

**因素 5：事件回放机制 — 不会丢事件，但感知延迟存在**

```python
# backend/common/events/manager.py:85-96
def subscribe(self, task_id, queue, since=-1):
    self._task_queues[task_id].append(queue)
    for event in self.get_events_since(task_id, since):   # ← 回放历史事件
        queue.put_nowait(event)
```

SSEManager 在 `subscribe()` 时会回放 `get_events_since()` 的历史事件。同时 `prepare_run()` 也会在任务开始前注册订阅者：

```python
# backend/common/runtime/module_run.py:35-38
from backend.common.events.manager import get_ssemanager
sm = get_ssemanager()
trace.subscribe(sm.on_event)            # ← 确保所有后续 trace.record() 都推送 SSE
```

这意味着：事件本身不会丢失（若有 `SSEManager.on_event` 订阅者，`TraceRecorder._record_locked()` 会实时推送），但前端要到 SSE/轮询连接建立后才能收到。对于连接建立前已推送的事件，`subscribe()` 回放保证了完整性。

**延迟总结**：

| 阶段 | 最小延迟 | 典型延迟 | 最坏延迟 |
|------|---------|---------|---------|
| Token 请求 | ~50ms | ~300ms | ~2000ms |
| EventSource 握手 | ~20ms | ~200ms | ~1000ms |
| 轮询 fallback 等待 | 0ms | ~3000ms | ~3000ms |
| 第一次轮询 | 0ms | ~1500ms | ~1500ms |
| **合计（SSE 正常）** | **~70ms** | **~500ms** | **~3000ms** |
| **合计（SSE 失败 → 轮询）** | **~3070ms** | **~4700ms** | **~6000ms** |

### 影响评估

- SSE 正常时延迟在 500ms 内，用户感知不明显
- SSE 连接慢/失败时，3 秒空白期用户体验很差
- 快速完成的小任务（如 diagnosis, review）可能在 Trace 首次渲染前已经结束，用户只看得到最终状态（因为 `hasTerminalEvent` 会阻止新连接建立）

## Issue 062-3: Trace 截断/省略 — 关键信息被多处截断

### 问题描述

Copilot 面板的 Trace 节点中，法律条文引用、检索查询、LLM 输出文本等信息被多处截断，表现为：
- 超过 120 字符的文本被截断加 `…`
- 对象 detail 只显示前 8 个 key
- 数组只显示前 6 个元素
- 展开块仅预览前 8 行
- 非优先 key 被静默丢弃

### 根因分析：trace-adapter.ts 中的五处截断点

**截断点 1：`shorten()` — 文本 120 字符硬截断**

```typescript
// frontend/src/lib/trace-adapter.ts:37-39
function shorten(value: string | undefined, limit = 120): string | undefined {
  if (!value) return undefined;
  return value.length > limit ? `${value.slice(0, limit - 1)}…` : value;
}
```

影响范围：
- `summaryLine()` (line 408) — 所有节点的 `summary` 字段 → 截断到 120 字符
- `makeNode()` (line 422) — `description` 字段通过 `shorten(event.summary, 96)` 截断到 96 字符
- `semanticFromDetail()` (line 219, 275) — tool name 和 category 截断到 40/32 字符

**截断点 2：`detailToBlock()` — 展开块仅预览前 8 行**

```typescript
// frontend/src/lib/trace-adapter.ts:282-301
function detailToBlock(label, detail, lang, maxPreviewLines = 8): TraceBlock | undefined {
  if (!detail || Object.keys(detail).length === 0) return undefined;
  const content = formatDetailContent(detail);
  const lines = content.split("\n");
  const preview = lines.length > maxPreviewLines
    ? lines.slice(0, maxPreviewLines).join("\n") + "\n..."
    : content;
  return {
    label, content, preview,
    isTruncated: lines.length > maxPreviewLines,
    // ...
  };
}
```

`maxPreviewLines = 8` 是硬编码的默认值，在所有调用点（`mergeTool` line 453-455, `flushToolStart` line 479, `standaloneNode` line 491, `intermediateNode` line 504, `finalNode` line 514, `briefNode` line 524）均未覆盖此默认值。

注意：`TraceExpandableBlock` 组件提供了"展开更多"按钮（`TraceExpandableBlock.tsx:29-32`），用户可以点击查看完整内容。但问题在于 `max-height: 18rem` 的容器限制（Issue 062-1）使得展开后信息仍受限于小窗口。

**截断点 3：`formatDetailValue()` — 数组截断到 6 个元素**

```typescript
// frontend/src/lib/trace-adapter.ts:90
return value.slice(0, 6).map((item) => {
  // ...
});
```

RAG 检索结果、issues 列表、findings 数组等超过 6 项时，其余元素被静默丢弃，无任何提示。

**截断点 4：`formatDetailValue()` — 对象截断到 8 个 key**

```typescript
// frontend/src/lib/trace-adapter.ts:103-111
if (typeof value === "object") {
  const record = value as Record<string, unknown>;
  const entries = Object.entries(record);
  if (entries.length === 0) return ["{}"];
  return entries.slice(0, 8).flatMap(([key, nested]) => {
    // ...
  });
}
```

复杂 detail 对象（如 risk_assessment 包含 10+ 字段）的后半部分被静默丢弃。

**截断点 5：`formatDetailContent()` — 非优先 key 被排到末尾**

```typescript
// frontend/src/lib/trace-adapter.ts:143-162
function formatDetailContent(detail: Record<string, unknown>): string {
  const priority = [
    "tool", "agent", "provider", "model", "task", "query",

    "artifact_path", "preview", "files", "risks",
    "notices", "next_steps", "stats", "system", "user", "content",

  // 排序：优先 key 在前，其余按字母序
  // ...
  return orderedEntries.flatMap(([key, value]) => {
    const lines = formatDetailValue(value);
    // ...
  }).join("\n");

```

`priority` 列表定义 25 个"重要" key，不在列表中的 key 被排到末尾。但这并非直接丢弃 — 所有 key 都会显示，只是按优先级排序。真正导致信息丢失的是 `formatDetailValue` 内部的 6/8 截断。

额外注意：`summarizeArray()` 虽然只展示前 3 项，但会附加 `还有 N 项` 提示：

```typescript
// frontend/src/lib/trace-adapter.ts:56-73

  const preview = value.slice(0, 3).map(/* ... */).join(t.format.listJoiner);
  return value.length > 3 ? `${preview} ${t.format.moreItems(value.length)}` : preview;
}
```

### 影响评估

| 截断点 | 影响数据 | 用户后果 |
|--------|---------|---------|
| `shorten(120)` | legal_basis 文本、裁判摘要 | 法律条文被截断，无法确认引用完整性 |
| `detailToBlock(8行)` | LLM 输出、RAG 结果 | 报告草稿只看到开头 8 行，后续内容不可见（需展开） |
| `formatDetailValue(6项)` | 风险列表、finding 数组 | 只看到 6 个风险项，其余丢失且无提示 |
| `formatDetailValue(8 key)` | 复杂 detail 对象 | 后 8+ 个字段完全不可见 |
| `shorten(96)` description | 节点描述文本 | 长描述被截断，上下文不完整 |

## 总体根因总结

三个问题共享一个架构根源：**Copilot 面板被设计为紧凑的聊天界面，而非专业的工作流监控视图**。

| 问题 | 根因层级 | 核心代码位置 |
|------|---------|------------|
| 半截窗口 | CSS 三层约束：300px pane + grid auto + 18rem max | `workspace.css:313, 4150, 4232` |
| 延迟显示 | SSE/轮询双通道连接开销 + 3s fallback 等待 | `useTaskEvents.ts:279, 183, 231, 176` |
| 截断/省略 | `trace-adapter.ts` 5 处硬编码截断阈值 | `trace-adapter.ts:37, 90, 103, 143, 290` |

### 修复方向建议

1. **半截窗口**：
   - 增加 `.copilot-trace-inline-body` 的 `max-height` 至 `min(32rem, 50vh)`
   - 或提供"弹窗/抽屉"模式将 Trace 展开到独立视图
   - 考虑在右侧栏中为 Trace 分配单独的区域（不在聊天流中）

2. **延迟显示**：
   - 将 `INITIAL_FALLBACK_DELAY_MS` 从 3000ms 降至 800ms
   - 在 SSE 连接建立前先发起一次即时轮询获取已有事件（显示"正在连接..."骨架）
   - 添加 loading 骨架屏提升感知速度

3. **截断/省略**：
   - `shorten()` 默认 limit 从 120 提升至 300（或改为基于视口宽度动态计算）
   - `formatDetailValue()` 数组限制从 6 提升至 20，并附加 `还有 N 项未显示`
   - `formatDetailValue()` 对象 key 限制从 8 提升至 30
   - `detailToBlock()` 的 `maxPreviewLines` 从 8 提升至 15
