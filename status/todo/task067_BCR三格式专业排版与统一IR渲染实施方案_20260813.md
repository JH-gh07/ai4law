## 一、目标和完成定义

本方案不是“调整 CSS”或“换一个 DOCX 模板”，而是完成一个可验证的 BCR 垂直切片：

```text
BCR 结构化结果（findings / citations / remediation）
→ 仓库现有 DocumentIR 的版本化扩展
→ DocumentCompiler 结构与排版门禁
→ Web / Markdown / DOCX / PDF 分别消费同一 IR
→ render_manifest 证明同源、完整和可打开
→ 自动结构检查 + 浏览器/DOCX/PDF 真实视觉验收
```

task067 只有同时满足以下条件才算完成：

1. BCR 正式用户产物不再从 Markdown table/list 字符串反推结构；
2. 同一运行只生成一份权威 IR，Web、Markdown、DOCX、PDF 均消费该 IR；
3. 网页报告不存在 DOCX 纯文本冒充忠实预览或同一正文重复展示；
4. DOCX 使用 Word 原生 heading、table、numbering、页眉页脚和分页属性；
5. PDF 不再使用 A4 竖版六列长文本表格，ID、风险等级和英文单词不逐字符断裂；
6. 多级建议条款的编号和从属关系在三种格式中保持一致；
7. `render_manifest.json` 记录同一 IR hash、renderer 版本、文件 hash 和结构计数；
8. 单元、集成、API、前端、浏览器、DOCX XML、PDF 文本层和逐页截图门禁全部通过；
9. BCR 切换后旧模板字符串路径不再生成用户可见产物；
10. 未连接远程、未部署。

## 四、关键架构决策

### 4.1 扩展现有 DocumentIR，不新建平行 Report IR

仓库已有：

- `DocumentIR`；
- `SectionIR`；
- `ParagraphBlock`；
- `ClaimBlock`；
- `ListBlock`；
- `TableBlock`；
- `WarningBlock`；
- `DocumentCompiler`。

task067 必须沿用该包，并与 [060task_03](./060task/060task_03_理想报告结构与统一渲染整改方案_20260812.md) 的 v4 契约方向一致。不得新增 `bcr_report_ir.py` 之类的第二套长期真相源。

当前 v3 block 无法表达 finding 主展示、多级法律条款和分页语义，因此需按明确主版本升级补齐 BCR 垂直切片。新增字段必须是完整 v4 契约的组成部分，不得使用 BCR 私有自由字典绕过 Schema。

### 4.2 业务结果和排版结构分离

```text
BCRFinding / BCRResult：业务判断
DocumentIR：跨格式展示语义和引用关系
RenderProfile：字体、页面、间距、表格和分页规则
Renderer：只负责把 IR 放入对应载体
```

Renderer 禁止：

- 重新判断风险；
- 从字符串识别 finding；
- 从 Markdown 猜标题或列表；
- 合并、删除或新增业务 finding；
- 改写 citation；
- 根据版面容量截断正文。

### 4.3 三格式同源，不要求像素相同

必须一致：

- 章节 ID 和顺序；
- finding ID、顺序和风险；
- 条款编号及父子关系；
- citation 集合；
- 正文段落集合；
- IR hash。

允许不同：

- 网页使用折叠、锚点和响应式布局；
- DOCX 使用 Word 原生表格和多级编号；
- PDF 使用摘要表 + finding 纵向分块和固定分页。

### 4.4 IR 是内部渲染数据源，不是普通下载项

`document_ir_json` 继续从用户文件树隐藏，但报告页可以通过已授权 API 按需读取。不能把完整 IR 写入 localStorage。

推荐 API 契约：

```text
ArtifactPreviewResponse
├─ render_mode: html | pdf | text | download | report_ir
├─ content: string                  # 仅文本类
└─ structured_content: object|null  # 仅 report_ir
```

后端必须依据数据库中登记的 `artifact_type=document_ir_json` 决定 `report_ir`，不能仅凭任意 `.json` 文件名自动解析为 IR。

### 4.5 DOCX 点击行为不冒充忠实预览

浏览器没有原生 Word 排版引擎，当前环境也没有 LibreOffice 服务。task067 不引入一个无法保证忠实度的客户端 DOCX 猜测器。

报告页行为应为：

```text
正文 tab：始终渲染 Report IR
PDF tab：使用同 IR 生成的 PDF canvas，作为固定版视觉预览
DOCX artifact：提供下载/打开；说明其正文已在当前页面展示
```

如果以后要求 Word 像素级浏览器预览，应单独建设受控 LibreOffice 转换服务，不属于本任务。

### 4.6 Feature flag 只控制切换，不制造双真相

建议增加独立切换：

```text
BCR_REPORT_IR_RENDERING_ENABLED=false
```

阶段行为：

1. `false`：旧路径仍是用户产物，新路径可在测试/影子目录生成比对；
2. 影子比对通过：本地将 flag 设为 `true`；
3. `true`：用户产物只由 IR renderer 生成，旧 renderer 不再写正式输出路径；
4. 回滚只切回 flag，不删除新 IR 和证据；
5. 完成本地验收后删除 BCR 旧分支，避免永久双路径。

现有 `schema_first_bcr_enabled` 只控制是否生成/编译 IR，语义不等于“用户产物已由 IR 渲染”，不能复用同一个 flag 混淆状态。

## 五、目标 Report IR 排版契约

### 5.1 必须补齐的公共对象

task067 应从完整 v4 方案中落地以下最小完整纵向切片，而不是“最小示例”：

```text
DocumentIR v4
├─ identity
├─ lifecycle
├─ metadata
├─ findings[]
├─ actions[]
├─ citations[] / CitationRegistry
├─ sections[]
├─ blocks[]
├─ render_contract
├─ diagnostics[]
└─ integrity
```

BCR 排版所需的强类型 block 至少包括：

| Block | 用途 | 关键字段 |
|---|---|---|
| `KEY_VALUE` | 报告元数据和评级摘要 | typed items、列数、label/value |
| `FINDING_SUMMARY` | 简短摘要表 | finding_refs、允许列集合 |
| `FINDING_DETAIL` | finding 唯一完整主展示 | finding_ref、字段显示顺序 |
| `FINDING_REFERENCE` | 其他章节引用 | finding_ref，不复制全文 |
| `CLAUSE_GROUP` | 建议条款及多级子条款 | clause nodes、编号风格 |
| `LIST` | 普通列表 | 强类型嵌套 item，不再仅 `list[str]` |
| `PARAGRAPH/CLAIM` | 正文和带引用主张 | text + refs |
| `WARNING` | 边界或降级提示 | severity + refs |
| `PAGE_BREAK` | 明确分页点 | reason |
| `CITATION_NOTE` | 引用附录 | citation_refs |

### 5.2 多级条款结构

必须使用递归结构表达，而不是手写 `1.`、`(a)`：

```text
ClauseNode
├─ node_id
├─ label                 # 可选显示标签
├─ text
├─ numbering_style       # decimal / lower_alpha / lower_roman / none
├─ citation_refs[]
└─ children[]
```

强制约束：

- `node_id` 文档内唯一；
- 最大层级明确限制，例如 4 级；
- label 由 renderer 按 numbering style 计算，不允许在 text 中重复手写；
- children 顺序稳定；
- 三个 renderer 对同一节点产生相同的逻辑编号；
- 未知 numbering style 编译失败，不降级成普通段落。

### 5.3 finding 展示契约

详细 finding 不再用六列表格。目标结构：

```text
Finding header
  编号 | 风险 | 标题
Finding body
  现状
  证据/定位
  法律依据
  整改建议
  建议条款（如有）
```

摘要区域可以使用短表：

```text
编号 | 风险 | 主题 | 状态
```

强制约束：

- 每个 finding 恰好一个 `FINDING_DETAIL`；
- 摘要只引用 finding，不复制长正文；
- 不在一张表中同时放置长“现状/建议/法律依据”；
- finding 的字段缺失时省略对应行，不用空列占位；
- renderer 不改变 finding 顺序。

### 5.4 RenderProfile

新增公共、版本化、可测试的版式 profile，建议位置：

```text
backend/common/reporting/render_profiles/legal_report_a4_v1.py
或 config/report_render_profiles/legal-report-a4-v1.json
```

建议冻结值：

```yaml
profile_id: legal-report-a4-v1
page:
  size: A4
  margin_top_mm: 20
  margin_right_mm: 22
  margin_bottom_mm: 20
  margin_left_mm: 22
typography:
  body_pt: 10.5
  body_leading: 1.45
  heading_1_pt: 16
  heading_2_pt: 13.5
  heading_3_pt: 11.5
  table_pt: 9
paragraph:
  first_line_indent: 0
  space_after_pt: 6
table:
  repeat_header: true
  allow_long_text_columns: false
pagination:
  keep_heading_with_next: true
  keep_finding_header_with_first_field: true
  page_number: true
```

字体资产必须另附：来源、版本、许可证、SHA-256、覆盖字符集和 PDF 嵌入结果。不得只写字体名称而依赖某台机器已安装。

## 六、三种载体的目标版式

### 6.1 网页版

页面结构：

```text
报告标题 + 元数据
综合评级摘要
章节导航 / 风险筛选
finding 摘要
finding 详情列表
整改建议和多级条款
引用附录
导出文件区（MD / DOCX / PDF / ZIP）
```

明确要求：

- 正文内部容器最大可读宽度建议 `880-960px`，居中但不做浮动大卡片；
- finding 是重复工作单元，可使用 1px 分隔和标题行，不嵌套卡片；
- 正文不默认 `text-align: justify`，中英文混排使用自然左对齐；
- 摘要表可以横向滚动，详细 finding 不用六列长表；
- 风险使用图标/文本标签，但不只靠颜色；
- 三级列表有稳定缩进和编号；
- 移动端把摘要表降级为 finding 摘要列表，不缩成不可读小字；
- 报告正文与 artifact 预览只保留一个主展示；
- DOCX 不进入 Markdown renderer。

### 6.2 DOCX 版

页面和样式：

- A4；
- 上下 20mm、左右 22mm；
- 标题、Heading 1/2/3、Body、Caption、Table Header、Finding Title、Risk Label、Citation Note 使用命名 Word style；
- 页眉包含短报告名/草案状态，页脚包含页码；
- 标题与首段 `keep_with_next`；
- finding header 与首个字段保持同页；
- 摘要表使用 Word 原生 table，表头跨页重复；
- 详细 finding 使用段落结构或两列 key/value 表，不使用六列长表；
- 建议条款使用 Word 原生 numbering definitions；
- 不通过空格、Tab 或手写数字模拟缩进；
- 文件必须能被 `python-docx` 重新打开，OOXML ZIP 完整。

旧 `3.2_bcr_review_template_v0.docx` 不再承载正文内容。可保留为迁移参考，或重构为只提供封面/section/style 的母版；正文必须由 IR renderer 创建。

### 6.3 PDF 版

- 直接从 IR 构造 ReportLab flowables，不先生成 Markdown 再解析；
- 使用 `PageTemplate`/页眉页脚/页码；
- 标题、finding header 和首段使用 `KeepWithNext` 或等价策略；
- 摘要表最多 4 个短列；
- 详细 finding 纵向分块；
- 多级条款递归生成嵌套 `ListFlowable` 或显式编号段落；
- 中文字体显式注册并嵌入；
- 长英文禁止逐字符断裂；
- 不以缩小到 7-8pt 的方式保住六列表格；
- PDF 文本可复制、可检索；
- 页面 raster 后无裁切、重叠、空白页和孤立标题。

### 6.4 Markdown 版

Markdown 仍是用户产物之一，但只作为 IR renderer 输出：

- 标题由 SectionIR 生成；
- finding 摘要使用短表；
- finding 详情使用稳定 heading/definition layout；
- ClauseNode 递归输出正确缩进列表；
- renderer 不读取旧模板中的业务正文；
- Markdown 仅作为一种产物，不再作为 DOCX/PDF 的中间真相源。

- 最终一致性、真实视觉和切换必须串行收口。

### 16.2 关键设计决策

- **向后兼容而非破坏**：`DocumentIR` 保留 v3 必填 `document_id`/`report_type` 与内联 `SectionIR.blocks`，避免破坏 9 个既有 `schema_first.py` adapter 与跨模块契约测试 `test_schema_first_contracts.py`（34 项全过）。
- **单判别器 + `extra=forbid`**：`Block` 用 `type` 判别，所有模型 `extra="forbid"`，未知 block/profile 在解析/编译期即 fatal。
- **主展示次数由编译期推导**：`FindingRecord.primary_display_count` 不写入业务，由 `FindingValidationPass` 统计 `FINDING_DETAIL` 引用数并断言 `==1`。
- **clause 编号在 schema 表达、不在 text**：`ClauseNode.numbering_style` + `children` 表达多级编号，禁止手写 `1.`/`(a)`。
- **v3→v4 只迁移不并轨**：迁移 reader 只接受显式 v3.0 输入；新 BCR adapter 将在 T02 直接产出 v4 IR，不再长期并存私有 IR。
