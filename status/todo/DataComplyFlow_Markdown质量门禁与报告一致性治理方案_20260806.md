## 0. 一句话结论

报告中 12 类现象**不是 12 个独立缺陷**，而是 5 个结构性缺陷的外化。其中 3 个是"单点常量/单条正则"级别的错误，修复成本极低但影响面最大；只有 2 个需要结构性改造。因此本方案的核心判断是：

> **先修 5 个源头，再上 Markdown lint。**
> Lint 是回归围栏，不是修复手段。若 lint 先落地，会在几乎全部历史报告上飘红，而三源风险等级、正则截断等根因仍然存在，形成"红灯无人可修"的假门禁。

## 2. 逐类根因定位（含实测证据）

### 2.1 引用（高）

正文写"（本报告未引用法规依据索引）"而 citation_map.json 有 7 条。

根因与方案见 `DataComplyFlow_引用跳转闭环治理方案_20260806.md`，核心是：`chapter_generator.py:419-421` 的二选一分支使降级路径永不产出 `[n]` 脚注 → `registry.py:95` 因 `_global_numbering` 为空返回空索引提示 → `citations.py:217-238` 在读取时凭检索命中合成 7 条并回写磁盘。

本文档只承接其**门禁部分**：L6 脚注存在性、L5 与索引一致性（§3）。

### 2.2 结论一致性（高）— D1

同一份报告出现三个风险等级来源：

| # | 来源 | 代码坐标 | 报告中的呈现 |
|---|---|---|---|
| 1 | `diagnosis.risk_level`（规则引擎路径判断） | `service.py:341` → `risk_summary["risk_level"]` | 正文"整体风险等级为HIGH" |
| 2 | **字面量 `"MEDIUM"`** | `external_report_generator.py:100` | 标题"### 综合风险等级：MEDIUM" |
| 3 | `risk_level()` 依 profile 重算 | `common/risk/scoring.py:1`，经 `chapter_generator.generate()` 写入 `ChapterContent.risk_level` | 章节元数据 |

**触发链**：`report_renderer.py:148` 调用 `build_official_report_mapping(..., context_pack=None, ...)`。因 `context_pack` 为 None，`external_report_generator.py:93` 得到 `diagnosis = {}`，于是 `:100` 的 `diagnosis.get("risk_level", "MEDIUM")` 落到字面量默认值。

**关键结论**：标题里的 MEDIUM 并非"另一套算法算出的不同结论"，而是**从未被计算**。

**语料验证**：全量报告扫描出稳定特征 `HIGH=3 / MEDIUM=1`（标题 1 个 MEDIUM 默认值 + 正文 3 处真实 HIGH）。另一簇为 `HIGH=0 / MEDIUM=4`，对应 `path_warning` 非空时 `:101-102` 追加"（路径不匹配，本报告为强制生成的参考草案）"后的 MEDIUM。

### 2.3 换行破坏（中）— D2

`common/llm/postprocess.py:107`：

```python
line = re.sub(r"(?<!\n)(\(?\d+\)|\d+[、.])\s*(?=\S)", lambda m: f"\n{m.group(1)} ", line)
```

`\d+[、.]` 意在切分"1. 2. 3."式有序列表，但同时匹配技术术语内部的 `1.`。

**实跑复现**（`_explode_packed_line`）：

| 输入 | 输出 |
|---|---|
| `采用 TLS 1.3 加密传输。` | `['采用 TLS', '1. 3 加密传输。']` |
| `版本 v1.2.3 已上线。` | `['版本 v', '1.', '2. 3 已上线。']` |
| `符合 GB/T 35273-2020 标准。` | 未破坏（无点号） |
| `见 ISO 27001 认证。` | 未破坏（无点号） |
| `根据第38条第1款规定。` | 未破坏（"条"字阻断） |

这解释了为何该问题看似间歇：只有**含小数点的版本号/协议号**受害，标准号与条款号安全。

### 2.4 表格渲染（中）— D2

**实测修正用户描述**：带前导竖线的表格**能完整通过**归一化管线（含 `strip_markdown_inline` + `apply_citation_policy`），输出与输入逐字节一致。官方模板生成的表格（`official_risk_self_assessment_template.md:18-23, 29-35`）因此是正确的——实测语料中这些表格渲染正常。

真正受害的是**无前导竖线的表格**，即 LLM 常见输出形态：

```
项目 | 内容
--- | ---
企业名称 | 云帆
```

此时 `_MARKDOWN_PREFIX_RE`（`postprocess.py:15-17`）要求行首为 `|` 才判定为表格，不匹配 → 落入 `_explode_packed_line` 的中文序号/数字分支 → 结构被打散成纯文本，呈现为"项目内容企业名称…"。

**因此"项目内容企业名称"这一症状来自 LLM 自撰章节表格，不是模板表格。** 修复点在识别层而非模板层。

### 2.5 标题结构（中）— D2

`_classify_legal_block`（`postprocess.py:133-138`）的层级映射：

| 模式 | 产出 |
|---|---|
| `第X章` | `#`（H1） |
| `一、` | `##`（H2） |
| `（一）` | `###`（H3） |

而官方模板已占用 `#`(报告标题) / `##`(一、二、三) / `###`(（一）…（六）)。章节正文被注入 `###` 之下，若正文含"第X章"则产出 H1，出现**层级倒挂**（H1 嵌在 H3 内）。

另一面：降级路径产出的纯段落（`_build_fallback_chapter`）不含任何标题模式，全部落入 `paragraph`，因此章节内部零层级、可扫描性差——这正是"更像纯文本段落"的直接成因。

### 2.6 占位内容（中）— D3

`external_report_generator.py:130` 与 `:135`：

```python
content = "（该部分内容待补充，需基于申报材料进一步生成）"
```

在 `mapped_chapters` 取不到内容时兜底。而 `official_template_schema.json` 中 **2.6"其他情况"的 `mapped_chapters` 是空数组 `[]`**，因此该占位符**每一份报告必然出现**，不是偶发。

### 2.7 事实重复（中）— D3

两层重复叠加：

**模板映射层**（`official_template_schema.json`）：

| chapter_id | 被映射到 |
|---|---|
| `overview` | section 1（一、自评估工作情况）**和** section 2.1（（一）数据处理者基本情况） |
| `recipient_capability` | section 2.4（（四）境外接收方情况）**和** section 2.5（（五）法律文件…） |

`_build_section_content`（`external_report_generator.py:51-73`）逐 `mapped_chapters` 追加、**无去重**，故整段原文出现两次。实测语料中第一章三段与 2.1 三段逐字节相同；2.4 三段与 2.5 后半逐字节相同。

**降级模板层**：`_build_fallback_chapter` 把同一个 `issue_text` 变量插入 8 章中的 5 章（出境活动概述、出境必要性与合法性基础、境外接收方保障能力、安全措施与传输机制、剩余风险与整改建议），措辞前缀不同但载荷相同。

### 2.8 内部标记泄露（高）— D4

三类内部态文本进入对外稿：

| 泄露物 | 来源 |
|---|---|
| `ISSUE-missing-attachments（申报支撑材料缺失）：…` | `chapter_generator.py` `_build_fallback_chapter` 直接把 `issue.issue_id` 拼进散文 |
| `【待核验：缺少法规依据】` | `common/llm/postprocess.py:257-260` |
| `【已移除禁用措辞：完⋯全⋯合⋯规】` | `security_assessment/repair_generator.py:268`（DPIA 同构：`dpia/repair_generator.py:203`） |

第三类尤其不可交付：它把"系统曾试图写出禁用措辞"这一内部事实，以带混淆字符的形式暴露给客户。

### 2.9 法律表达（高）— D4

`apply_citation_policy` 的判定链（`postprocess.py:182-188, 250-267`）：

- `_LEGAL_RULE_RE` 匹配 `应当|必须|不得|禁止|依法|法定义务|法律要求|监管要求|违反|不符合|合规义务`
- `_RISK_JUDGMENT_RE` 匹配 `高风险|中风险|低风险|不合规|违规风险|剩余风险|风险等级|风险结论`
- 命中且无有效 `【依据：】` → 追加 `【待核验：缺少法规依据】`

两个后果：

1. **规则引擎输出被误判为法律主张**。"结合诊断结果，系统当前推荐路径为 security_assessment，整体风险等级为 HIGH。"命中 `风险等级`，被标"缺少法规依据"——但这是规则引擎的确定性输出，其依据是规则 ID 而非法条。
2. **已引用法条的句子仍被标注**。"应结合《个人信息保护法》第十三条、第三十八条、第三十九条等要求补充…"命中 `应`，但因降级路径不产出 `{{CIT-}}` marker，`valid_citations` 为空 → 照样追加标记。这就是"引用法律但仍统一标缺少法规依据"的机制。

### 2.10 降级说明（低）— D4

降级声明位于"综合评估结论"章节末段（`_build_fallback_chapter` 的 `综合评估结论` 列表最后一项）："本报告在当前模型不可用的情况下根据结构化输入、规则判断、问题项和证据链自动生成…"

内容正确，但**位置在全文末尾**，读者读完全部结论后才知道这是降级产物。

### 2.11 免责声明（中）— D4

当前仅模板末尾一行斜体：

```
*本报告由系统自动生成，仅供参考。正式提交前须经专业人员复核。*
```

**关于 PRD 固定文案的诚实说明**：仓库现存文件中**不存在** PRD 5.1.1 正文。可检索到的最接近权威文本是 `docs/archive/design-provenance/报告表达安全规范.md` §7.3 免责声明模板（含"本报告由 AI 合规辅助系统生成…引用的法规库版本为[版本号]"四段式），以及 §7.1 规定的对外报告六项结构性必备项、§7.2 审查边界说明模板。

**因此本方案不擅自冻结文案。** L7 门禁的落地前置条件是：由你确认以 §7.3 为准，或提供 PRD 原文。冻结错误文案比不冻结更糟。

### 2.12 文件命名（低）— D6

- 日期戳 `format_date_stamp()` 产出 `20260806`，无分隔符
- `safe_filename()` 保留原始公司名，产出中英文/下划线/点混排：`DataComply_Inc._CPRA_合规全景报告_草案_20260806.md`、`FitLife_AI_Inc._CPRA_合规全景报告_草案_20260806.md`

## 3. 统一 Markdown Lint 设计

### 3.1 类目与计数说明

你列举的门禁为"标题层级、表格、空章节、内部标记、风险等级唯一性、脚注存在性、免责声明、禁用措辞"共 **8 项**（原文称"七类"，推测将内部标记与禁用措辞合并计数）。本方案按 8 项独立实现——两者语义不同：内部标记是流程态泄露，禁用措辞是合规表达违规，处置动作与责任方均不同。

另新增 **L9 模板占位符残留**：`render_official_report_md`（`external_report_generator.py:161-165`）执行无校验的 `str.replace` 循环，mapping 缺键时字面 `{{section_2_6_content}}` 会直抵客户手中。当前无任何检查拦截。

### 3.2 规则表

| ID | 类目 | 判定 | 严重度 | 处置 |
|---|---|---|---|---|
| **L1** | 标题层级 | ① 存在 H1 嵌于 H2/H3 之后（层级倒挂）；② 跳级（H2→H4）；③ 单章节正文 > 800 字且零子标题 | ①②BLOCK ③WARN | ①②阻断出稿 |
| **L2** | 表格结构 | ① 检出 `X \| Y` 形态但无前导竖线；② 表头列数 ≠ 分隔行列数 ≠ 数据行列数；③ 缺分隔行 | BLOCK | 阻断 |
| **L3** | 空章节/占位内容 | 命中 `（该部分内容待补充`、`待补充，需基于`、`未提供` 单独成段、章节正文 < 30 字 | BLOCK | 阻断；2.6 类结构性空章节需显式声明豁免 |
| **L4** | 内部标记 | 命中 `ISSUE-[a-z-]+`、`【待核验`、`【已移除禁用措辞`、`CIT-[A-Z]`、`{{CIT-`、`chunk_id`、`source_kind`、`confidence_score` 等内部字段名 | BLOCK | 对外稿零容忍；内部稿允许 |
| **L5** | 风险等级唯一性 | 提取全文所有 `HIGH/MEDIUM/LOW` 与 `高风险/中风险/低风险` 上下文；同一报告内**风险等级结论**取值必须唯一，且必须等于 `diagnosis.risk_level` | BLOCK | 阻断 |
| **L6** | 脚注存在性 | ① 存在 `【依据：` 或法规名引用但 `[n]` 脚注数 = 0；② 正文出现"未引用法规依据索引"但 citation_map 非空（**跨产物一致性**） | BLOCK | 阻断 |
| **L7** | 免责声明 | 固定文案逐字匹配，且出现于三处指定位置（首部提示、正文专章、页脚） | BLOCK | **待文案确认后启用**，先以 WARN 观测 |
| **L8** | 禁用措辞 | 命中 `完全合规`、`可直接申报通过`、`零风险`、`保证通过`、`必然获批` 等（取 `writing_strategy.global_forbidden_expressions`） | BLOCK | 阻断 |
| **L9** | 占位符残留 | 正则 `\{\{[a-z_0-9]+\}\}` 命中 | BLOCK | 阻断 |

### 3.3 落点与实现位置

- **实现**：新增 `backend/common/quality/markdown_lint.py`，纯函数 `lint_markdown(text, *, profile: Literal["external","internal"], context) -> list[LintFinding]`
- **对外/对内双档**：`external` 档启用 L1–L9 全部；`internal` 档放宽 L4（允许 ISSUE 编号与待核验标记）、L7
- **调用点**：各 domain renderer 落盘前。落盘后校验会产生"已写坏文件再报错"的窗口，故必须前置
- **测试门禁**：接入既有 `backend/tests/harness/validators.py`（309 行，已有 `_op_*` 算子体系），新增 `_op_markdown_quality` 算子，走 `expected` 声明式断言，与现有 harness 一致
- **CI**：新增 workflow step 对 `outputs/**/*.md` 抽样跑 lint，或对 golden fixture 全量跑

### 3.4 Lint 不负责的事

L5 只能发现 HIGH 与 MEDIUM 并存，**不能修**三源问题；L6 只能发现脚注缺失，**不能修**断链。这两项的修复在 §4 的 P0，lint 是其回归围栏。

## 7. 风险与不做的事

**风险**

- P0-3 修改归一化正则会影响所有模块的正文排版，须以现状语料做前后 diff 回归，避免修好术语却打散真实有序列表
- P0-1 把"缺 `risk_level` 即抛错"引入后，任何未正确传递 context_pack 的调用点都会暴露为失败。这是期望行为，但会一次性暴露多个隐藏调用点，需预留排查时间
- L4 切 BLOCK 前必须先完成 P1-1，否则降级路径下所有报告将被门禁全量拦死

**明确不做**

- 不擅自冻结免责声明文案（§2.11）
- 不在本轮重写 LLM 提示词以提升章节质量——本方案只治确定性缺陷，生成质量属另一议题
- 不改动 DOCX/PDF 渲染器的表格实现，本轮只保证 Markdown 正确
- 不做 `outputs/` 历史语料的批量回填修复；历史产物保留为对比基线
