## 四、架构决策

### 4.1 单一 `DocumentIR v4`，不创建 `ReviewReportIR` 平行体系

Review 的专有语义通过 adapter 映射到现有对象：

```text
AggregatedReview.issues[]
  → FindingRecord[]
  → FINDING_DETAIL（每条恰好一次）
  → FINDING_SUMMARY / FINDING_REFERENCE（只引用 finding_id）

MissingItem[]
  → FindingRecord 或独立 typed block（依据业务语义冻结后选定）
  → ActionRecord[]

Citation source
  → CitationRecord[] + finding.citation_refs[]

文档画像/风险计数
  → KEY_VALUE / TABLE / FINDING_SUMMARY
```

若现有 `FindingRecord` 无法无损表达 `original_excerpt`、`clause_type`、`problem_type`，应在 `backend/common/reporting/schema/findings.py` 增加明确可选字段，而不是把它们重新塞回 `statement` 字符串。新增字段必须 `extra="forbid"`、有 schema 与 mutation test，并评估其对九模块 golden 的兼容性。

针对 I068-22，`FindingRecord.legal_basis: list[str]` 只承载标签列表，无法表达「每条引用为何适用」。新增**带论证的法规依据条目**，不新增法律结论、只归因既有业务字段：

```python
class FindingBasis(BaseModel):
    model_config = ConfigDict(extra="forbid")
    citation_ref: str | None = None   # 指向 CitationRecord；无登记引用时为空
    label: str                        # 人类可读法条标签（兼容旧 legal_basis）
    rationale: str = ""               # 「要件→事实→结论」归因，来自 risk_analysis/snippet，禁止生成
    is_primary: bool = False          # 是否主依据（可选，冻结后定）

FindingRecord.basis_entries: list[FindingBasis] = Field(default_factory=list)
```

`legal_basis` 保留为兼容 shim（九模块 golden 不破坏）；正式渲染只读 `basis_entries`。`rationale` 只能由 adapter 从 `ReviewIssue.risk_analysis` / `StructuredCitation.snippet` 归因，renderer 与 compiler 不得补写、不得调用 LLM。

### 4.2 adapter 决定业务语义，renderer 只决定载体表达

adapter 负责：

- finding 的身份、顺序、风险、原文、分析、法规、建议；
- 章节目的和唯一 section ID；
- citation 去重和关联；
- action 与 finding 的关系；
- 输入 manifest 引用及报告元数据；
- 是否 degraded、业务边界和置信度。

renderer 只负责：

- heading、列表、表格、卡片、分页和字体；
- citation 编号的稳定呈现；
- 同一 IR 在不同介质下的排版 profile；
- 不新增、合并、删减或改写法律结论。

### 4.3 `RunInputManifest` 是运行输入的唯一追溯清单

建议在公共 workflow/reporting 边界新增版本化契约，最终地址由现有模块边界审查确定，首选：

```text
backend/common/workflow/input_manifest.py
```

完整字段至少包括：

```text
RunInputManifest
├─ schema_version
├─ run_id / task_id / module_key / scenario_id
├─ created_at / request_hash
├─ entries[]
│  ├─ input_id / display_name / role
│  ├─ source_kind: uploaded | dev_preset | shared_scenario | inline
│  ├─ media_type / size_bytes / sha256
│  ├─ storage_uri（内部）/ public_locator（受控）
│  ├─ consumed_by_service / parser_status
│  └─ provenance: uploaded_file_id | scenario_path | preset_id
└─ integrity: canonicalization / manifest_hash
```

约束：

1. 绝对路径、访问 token 和原始大 JSON 不进入用户正文；
2. `sha256` 针对实际送入 service 的字节；inline 输入使用 canonical JSON hash；
3. manifest 与请求构建在同一次运行边界完成，不能由前端事后猜测；
4. 用户上传、预置案例、共享场景分别展示，不能把预置文件冒充用户上传；
5. manifest 持久化后由任务空间恢复 API 返回，不能只存在 React state；
6. 缺文件、hash 不符或 `consumed_by_service=false` 必须可见，不能算“已提交材料”。

### 4.4 报告正文、输入和产物四区分离

工作台稳定语义：

```text
报告正文     = DocumentIR → Web renderer
输入材料     = RunInputManifest → material tree
PDF 预览     = PDF artifact → PDF.js/canvas
DOCX 产物    = 下载/打开；可选服务端转换产物另登记为 docx_preview_pdf
原始附件预览 = 输入 artifact 专用 viewer
```

禁止把 DOCX 抽取文本命名为“Word 预览”。文本抽取可保留给搜索、可访问性 fallback 或调试，但 UI 必须标为“抽取文本”，且不能替代正式报告正文。

### 4.5 固定报告顺序契约

Review：

```text
封面与元数据
→ 执行摘要（评级、分数、风险计数、缺失项计数）
→ 审查范围与输入材料摘要
→ 文档画像
→ 高/中/低风险 finding 主展示
→ 全局缺失项
→ 整改行动清单
→ 审查边界与置信度
→ 法规引用附录
→ 技术附录/输入快照（不得包含原始大 JSON）
```

CPRA、EO、DPIA：

```text
封面与元数据
→ 总体结论/风险摘要
→ 适用范围与判断依据
→ finding/风险/整改
→ 法规与引用
→ 审查边界
→ 输入快照附录
```

第一业务章节不得是输入 JSON。章节序号由 IR 的 section/clause 关系生成一次，正文不得手写重复编号。

### 4.6 三格式同源不等于像素相同

必须相同：章节 ID 和顺序、finding ID/顺序/风险、action 关联、citation 集合和指向、结论文本、输入 manifest hash。

允许不同：分页、目录页码、Web 折叠交互、DOCX 样式细节、PDF 换页位置。任何介质适配都不得改变业务信息集合。

## 五、目标载体排版契约

### 5.1 Web

- 顶部为紧凑结论区，不用超大营销式标题；
- 风险摘要使用可扫描统计，不仅依赖颜色；
- finding 使用稳定 `finding-{id}` 锚点，展示原文、分析、依据、建议五区；
- citation 可跳转并反向显示支持的 finding；
- 单 finding 的法规依据逐条承载（`basis_entries`），每条含来源/定位/摘录与「为何适用」归因，不渲染裸 `；` 标签墙；
- 长章节可折叠，但 HIGH finding 默认展开；
- 报告正文和文件预览不嵌套成重复卡片；
- 右侧执行流不显示同一内部枚举和中文标签两遍；该项只消费 issue062 的规范化结果；
- 1440/1024/390 无横向溢出、遮挡、按钮文字截断或不可操作区域。

### 5.2 DOCX

- 使用原生 Heading 1/2/3、编号定义、表格、页眉页脚和页码字段；
- 封面、摘要、finding、附录有明确 page break 策略；
- finding 标题与首段 `keep_with_next`，单条 finding 避免标题孤立页尾；
- 原文引用和风险分析不是一个超长普通段落；
- citation 使用稳定编号和可核验定位，不复制同一法规全文；
- 单 finding 的法规依据渲染为 `basis_entries` 列表/段落块（每条：定位 + 摘录 + 归因），不使用 `"；".join()` 拼成一长段；无论证的纯标签条目只作为附录引用编号，不冒充论证；
- 表格跨页重复表头，禁止固定行高截断正文；
- 中文正文、英文/数字、等宽内容分别使用经许可的字体；
- OOXML 中必须能检查 heading、table、numbering、header/footer、page number 和分页属性。

### 5.3 PDF

- A4 固定页边距、页眉、页脚、页码；
- CJK 字体必须嵌入并记录许可证与 SHA-256；
- finding 用纵向块，不使用六列压缩长表；
- 法规依据逐条 `basis_entries` 渲染（定位 + 摘录 + 归因），不出现「一个 finding 多条引用拼成一长段」的文字墙；
- 标题、风险标签、原文块和建议块不可被逐字符断行；
- `pdftotext -layout` 的章节顺序与 canonical IR 一致；
- 文本可复制，中文不乱码，PDF canvas 不白屏；
- 若当前生成器不能提供 tagged PDF，验收报告须如实列残余可访问性风险，不得写成已满足 PDF/UA。

### 5.4 Markdown

- 使用已实现的 `backend/common/reporting/renderers/markdown.py`；
- 不生成六列 finding 表；
- 不残留 `{{...}}`、内部绝对路径、原始 JSON dump；
- 法规依据逐条 `basis_entries` 呈现，不把多条引用用 `；` 压成一行；无论证条目只保留引用编号并指向附录；
- 章节、finding 和 citation 集合与 IR 相等；
- Markdown 是正式可读产物之一，不作为 DOCX/PDF 的反向解析源。

## 十二、风险与控制

| 风险 | 控制 |
|---|---|
| task067 与 task068 同时修改公共 renderer | 公共能力单一 owner；task068 只增加纵向 fixture/adapter，不复制 renderer |
| v4 字段扩展破坏九模块 | 保持向后兼容、golden diff、跨模块 contract tests |

| PDF CJK 字体许可证不清 | 只接受明确可再分发字体，保存许可证和 hash |
| DOCX 在 Word/LibreOffice 表现不同 | OOXML 门禁 + LibreOffice 视觉 + 至少一次真实 Word 人工抽查 |
| 大报告 Web 性能下降 | finding 分组/折叠/虚拟化按测量引入，不牺牲可访问性与搜索 |
| 历史任务没有 v4 IR | 显式 legacy 状态和迁移 reader；不从 DOCX 文本伪造 canonical IR |
| shadow 写入造成用户混淆 | 隔离 artifact type/目录，不进入普通文件树 |
| 排版改造改变业务结论 | canonical business hash、集合对比、renderer 禁止业务推断 |
| 引用归因被误当作新论证生成 | `FindingBasis.rationale` 只允许 adapter 从 `risk_analysis`/`snippet` 归因，compiler 加非法生成内容门禁 |
