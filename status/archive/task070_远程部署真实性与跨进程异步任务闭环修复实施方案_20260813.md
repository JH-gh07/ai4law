# task070：远程部署真实性与跨进程异步任务闭环修复实施方案

> 日期：2026-08-13  
> 状态：待审核，尚未按本方案实施代码和生产迁移  
> 上游问题基线：`status/todo/issue070_远程部署版本配置与异步任务状态失真深度分析_20260813.md`  
> 目标环境：本地、CI、`tencentServer`；Cloud Studio 另按相同运行契约部署  
> 核心原则：数据库是任务事实源，API worker 不持有任务真相；发布结论必须由不可变证据证明

## 一、目标和完成口径

本方案解决的不是某一个模块的 404，而是同时闭合以下五条生产链路：

```text
代码提交 -> 构建产物 -> release -> systemd 进程 -> /version 运行证据

任务提交 -> 持久化 -> 执行租约 -> 心跳/取消/重试 -> 唯一终态

任务终态 -> RunEvent/SSE -> workspace recovery -> 前端唯一状态

Provider Secret -> 配置校验 -> 实际探测 -> 健康快照 -> 任务级 provider snapshot

业务结果 -> 文件原子发布 -> artifact 登记 -> 授权预览/下载 -> 可核验报告
```

完成不以“页面暂时不报错”为标准。只有以下条件同时满足，task070 才能关闭：

1. API 开启两个 worker 时，所有异步模块状态查询、重试和取消不再依赖进程内存；
2. 服务重启、worker 被杀、请求切换 worker 后，任务不会随机 404、重复执行或永久假 `RUNNING`；
3. `COMPLETED` 必须同时拥有合法结果、必要产物、成功终态事件和数据库终态；
4. `FAILED/CANCELED/TIMED_OUT/INTERRUPTED` 必须有结构化错误和相应终态事件；
5. 前端不得再把一次基础设施 404 固化为业务 `FAIL`，后端终态能够纠正旧假失败；
6. Provider 配置不存在 shell 文本污染，活动 Provider 通过真实最小生成探测；
7. 每次部署都能证明实际运行的是哪个 commit 和哪个构建产物；
8. US_14117、CPRA 以及其余共用异步框架的模块通过相同门禁。

## 二、范围与非目标

### 2.1 本方案范围

- `backend/common/tasks/` 的统一异步任务持久化、租约、执行和恢复；
- `async_tasks` 数据模型和 SQLite 兼容迁移；
- assessment、PIPIA、BCR、DPIA、TIA、CN Flow、EU SCC、CPRA、US_14117 的统一接入；
- Review 现有数据库任务链与统一任务状态契约的适配，不强行改成相同执行器；
- RunEvent/SSE 跨 worker 历史读取与终态一致性；
- 前端轮询、恢复、状态合并和旧错误记录纠偏；
- LLM runtime settings 校验、Secret 处理和生产健康门禁；
- release manifest、部署前置检查、灰度、回滚和生产验收；
- CPRA 非法 JSON、超时和渲染收尾专项。

### 2.2 非目标

- 不借本任务重写各模块法律规则或报告内容；
- 不用 Redis/Celery 作为未经评估的新依赖，当前规模优先复用 SQLAlchemy、SQLite、现有 RunEvent；
- 不把单 worker 当作最终架构；单 worker 只允许作为 P0 临时止血；
- 不提交 `.env`、API key、Bearer token、用户报告正文或生产数据库；
- 不自动把不确定法律判断改成 Gold 结论。

## 三、关键设计决策

### 3.1 发布真实性不再依赖 release 目录中的 `.git`

当前远程 `git rev-parse HEAD` 与目标 GitHub SHA 不一致，但 release 曾使用 `git archive`。如果旧 `.git` 被保留，`git rev-parse` 只能证明元数据失真，不能单独证明业务文件字节一定来自旧提交。

因此新增构建时生成的不可变发布清单：

```json
{
  "schema_version": 1,
  "git_commit": "<40-char SHA>",
  "git_tree": "<tree SHA>",
  "built_at": "<UTC ISO8601>",
  "builder": "ci/local-release",
  "frontend_bundle_sha256": "...",
  "backend_source_sha256": "...",
  "dependency_lock_sha256": "...",
  "developer_mode": true
}
```

建议文件：

- 新增 `scripts/build_release_manifest.py`；
- 产物根目录 `release-manifest.json`；
- 新增只读 `/api/v1/version` 或 `/version`，返回非敏感字段；
- systemd `Environment=AI4LAW_RELEASE_MANIFEST=...` 显式绑定当前 release。

部署成功必须满足：GitHub 目标 SHA、release manifest、后端 `/version`、前端嵌入版本四者一致。禁止继续用“目录名看起来是当天”或残留 `.git` 作为发布成功依据。

### 3.2 数据库是任务事实源

现有 `InMemoryTaskManager._tasks` 只能保留为执行句柄缓存，不得承担以下职责：

- 状态查询；
- 所有权判断；
- 重启恢复；
- 重试次数；
- 取消意图；
- 最终结果；
- 是否已经执行过。

以上全部由 `async_tasks` 和关联持久化记录决定。

### 3.3 API 与任务执行分离

目标进程拓扑：

```text
Nginx/OpenResty
  -> Uvicorn API workers x 2
       -> 创建任务/查状态/发取消请求：只读写数据库

systemd ai4law-task-worker x 1
  -> 原子领取任务
  -> 执行业务 Service
  -> 心跳、事件、产物和终态落库
```

选择独立执行进程的原因：

- API worker 重启不会直接杀死或复制任务执行语义；
- 不需要新引入 Redis/Celery；
- 单执行进程足以满足当前本地 SQLite 并发能力；
- 将来迁移 PostgreSQL 后可通过数据库租约扩展多个执行进程。

在独立 worker 完成前，生产 API 临时降为 `--workers 1`；该止血状态必须在部署台账中标记，不能视为 task070 完成。

### 3.4 使用租约而不是进程内锁避免重复执行

每次执行由数据库保存：

```text
lease_owner
lease_expires_at
heartbeat_at
execution_token
version
```

SQLite 领取任务必须在短事务内使用 `BEGIN IMMEDIATE`，检查状态和过期租约后更新；长时间 LLM 调用不得持有数据库写事务。

领取成功后只有持有相同 `execution_token` 的 worker 可以更新心跳和终态。旧 worker 即使恢复，也不能覆盖新 worker 的结果。

### 3.5 终态必须满足提交协议

成功顺序固定为：

```text
业务生成临时结果
-> 验证结果 Schema
-> 产物写临时目录
-> fsync/关闭文件并原子 rename 到正式目录
-> 登记 artifact（幂等）
-> 写 COMPLETED + result_json/result_path + finished_at
-> 写 COMPLETED RunEvent/final_brief
```

若任何一步失败，任务不得写 `COMPLETED`。终态事件不能早于正式产物和数据库成功终态。

## 四、目标数据模型

扩展 [backend/models/async_task.py](/Users/oujiazhan/Desktop/实验室/社团/代码/ai4law/backend/models/async_task.py)，建议字段如下：

| 字段 | 作用 | 约束 |
|---|---|---|
| `id` | 后端唯一任务 ID | 主键，不复用 taskSpaceId |
| `user_id` | 所有者 | 非空、索引 |
| `module` | 模块 | 受控枚举/注册表 |
| `status` | 权威状态 | 受状态机校验 |
| `attempts` | 已开始次数 | 非负 |
| `max_attempts` | 最大次数 | `>=1` |
| `request_json` | 可重放结构化输入 | JSON，禁止包含明文 Secret |
| `provider_snapshot_json` | 本次 Provider 非敏感快照 | 只存 ID、URL host、model、key digest |
| `result_json` | 终态结果 | `COMPLETED` 必填 |
| `result_path` | 兼容首个主产物 | `COMPLETED` 有产物时必填 |
| `error_code` | 机器错误码 | 失败类终态必填 |
| `error_message` | 脱敏错误 | 不得含 key/token/完整提示词 |
| `trace_manifest_path` | 运行清单 | 创建后固定 |
| `created_at` | 创建时间 | UTC |
| `started_at` | 首次执行时间 | RUNNING 后非空 |
| `heartbeat_at` | 最近心跳 | RUNNING 周期更新 |
| `finished_at` | 终态时间 | 终态必填 |
| `cancel_requested_at` | 取消意图 | 可空 |
| `lease_owner` | worker 标识 | 仅运行中使用 |
| `lease_expires_at` | 租约过期 | 仅运行中使用 |
| `execution_token` | 防旧 worker 回写 | 每次领取随机生成 |
| `version` | 乐观并发版本 | 每次更新递增 |

必须建立索引：

```text
(status, created_at)
(lease_expires_at)
(user_id, updated_at)
(module, updated_at)
```

状态枚举建议：

```text
QUEUED
RUNNING
CANCEL_REQUESTED
COMPLETED
FAILED
CANCELED
TIMED_OUT
INTERRUPTED
```

禁止转换示例：

- `COMPLETED -> RUNNING`；重跑必须产生新的 attempt 或新 task ID，并显式关联；
- `FAILED -> COMPLETED` 直接覆盖；
- 无租约 token 的 `RUNNING -> COMPLETED`；
- 无 `result_json` 的 `COMPLETED`；
- 无 `error_code` 的失败终态。

### T04：实现数据库任务仓储和状态机

**目标：** 用统一 Repository 取代模块直接查询 `_tasks`。

**涉及位置：**

- 新增 `backend/common/tasks/repository.py`
- 新增 `backend/common/tasks/state_machine.py`
- 调整 [backend/common/tasks/manager.py](/Users/oujiazhan/Desktop/实验室/社团/代码/ai4law/backend/common/tasks/manager.py)
- `backend/services/task_access.py`

**接口契约：**

```text
create_task(user_id, module, request, provider_snapshot)
get_task(task_id, user_id)
claim_next(worker_id, lease_ttl)
heartbeat(task_id, execution_token)
request_cancel(task_id, user_id)
complete(task_id, execution_token, result)
fail(task_id, execution_token, error_code, message)
requeue(task_id, user_id)
mark_expired_leases(now)
```

**要求：**

1. 创建任务和创建 ownership 在同一事务内完成，消除先执行后认领的竞态；
2. Repository 始终应用 `user_id` 权限条件，禁止先按 ID 查询再由调用者自行判断；
3. 状态转换集中在 `state_machine.py`，模块不得直接赋值字符串；
4. 所有写操作使用 `version` 或 execution token 防止旧写覆盖；
5. 持久化错误不得 `except Exception: pass`，应写结构化日志并使任务提交/收尾失败；
6. API 查询只读数据库，内存命中与否不影响响应；
7. 真正不存在返回 `TASK_NOT_FOUND`，无权访问统一返回 404 或现有安全策略规定的响应，避免枚举其他用户任务。

**验收：**

- [ ] 100 个并发 claim 中每个任务最多一个 winner；
- [ ] 旧 execution token 无法完成新租约任务；
- [ ] 非法状态转换全部失败且数据库不变化；
- [ ] 跨 Session/跨进程查询得到相同状态；
- [ ] 其他用户无法查询、取消、重试或订阅任务。

### T05：实现独立任务执行进程和恢复策略

**目标：** API 多 worker 下任务执行唯一、可取消、可恢复。

**涉及位置：**

- 新增 `backend/common/tasks/worker.py`
- 新增 `backend/common/tasks/module_registry.py`
- 新增 `scripts/run_task_worker.py`
- 新增 `deploy/systemd/ai4law-task-worker.service` 或受管模板

**要求：**

1. 模块注册表显式映射 `module -> request schema -> execution function`，禁止动态 import 任意字符串；
2. worker 启动时回收过期租约，根据 attempts/max_attempts 转 `QUEUED` 或 `INTERRUPTED`；
3. heartbeat 周期小于租约 TTL 的三分之一；
4. 取消采用数据库 flag + 现有 `current_cancel_event` 协作检查；无法立即中断的外部 HTTP 调用必须受请求 timeout 限制；
5. worker 收到 SIGTERM 后停止领取新任务，等待当前任务至宽限期，超时则保留可识别的过期租约；
6. 重试必须冻结原请求、增加 attempt，并生成新的 execution token；是否复用 task ID 在 API 契约中固定，不允许各模块不同；
7. worker 不接受来自 `request_json` 的模块导入路径、文件输出根目录或 Secret；
8. 任务级最大执行时间、单次 LLM timeout、最大 attempts 分层配置。

**验收：**

- [ ] kill API worker 不影响 task worker 正常完成；
- [ ] kill task worker 后租约过期，任务按策略恢复且不重复产物；
- [ ] 同时启动两个 task worker，任务仍至多执行一次；
- [ ] SIGTERM、SIGKILL、数据库短暂锁、Provider timeout 均有确定终态；
- [ ] CPU/内存/线程数量有上限，无无限积累线程。
