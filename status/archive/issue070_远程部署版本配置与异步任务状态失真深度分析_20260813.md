# issue070：远程部署版本、运行时配置与异步任务状态失真深度分析

日期：2026-08-13  
范围：`tencentServer` 生产实例 `https://datacomplyflow.site`，重点覆盖 US_14117、CPRA 以及所有使用统一异步任务管理器的模块。

## 1. 结论先行

本次现象不是一个业务模块的单点故障，而是远程部署契约未闭合后产生的复合故障：

```text
远程运行 release 不是目标 GitHub 版本
  -> systemd 以 --workers 2 启动
  -> 每个 worker 持有独立 InMemoryTaskManager
  -> 创建请求与轮询请求可能落到不同 worker
  -> 状态接口随机 200/404
  -> 前端把任意 404 固化为 FAIL
  -> 数据库虽写入 async_tasks，但模块状态接口不会从数据库恢复

同时：
错误的 runtime_settings.json 曾把 shell export 文本写进 API key，
且保留已下线的腾讯旧地址；这会在 provider 切换或回退时再次造成 401/连接失败。

CPRA 另有模型 JSON 输出解析异常和最终收尾风险，不能与状态 404 混为同一原因。
```

因此：

- US_14117 页面显示 `Task not found/FAIL` 与事实不符，后端已有成功产物；
- CPRA 页面显示 `FAIL` 首先由跨 worker 404 污染，但该任务随后仍无产物、数据库停在 `RUNNING`，还存在独立的执行收尾/模型输出问题；
- 仅改前端文案、仅重启服务或仅把 worker 改为 1，都不能构成完整修复。

## 3. 代码依据与根因链路

### 3.1 任务状态的真实存储边界

文件：[backend/common/tasks/manager.py](/Users/oujiazhan/Desktop/实验室/社团/代码/ai4law/backend/common/tasks/manager.py:68)

`InMemoryTaskManager` 在进程内保存：

```python
self._tasks: dict[str, _TaskRecord] = {}
```

提交任务时只把 `_TaskRecord` 写入当前进程内存（`:107-110`、`:170-184`），查询时只查当前进程（`:188-195`）：

```python
record = self._tasks.get(task_id)
if record is None:
    return None
```

每个 Uvicorn worker 都会导入并实例化自己的模块 Service，因而拥有自己的 `_tasks` 字典。worker A 创建的任务，worker B 不可能从该字典读到。

### 3.2 数据库目前是“只写不读”

启动时确实调用了：

- [backend/app.py](/Users/oujiazhan/Desktop/实验室/社团/代码/ai4law/backend/app.py:30)
- [backend/app.py](/Users/oujiazhan/Desktop/实验室/社团/代码/ai4law/backend/app.py:33)

并在 [manager.py](/Users/oujiazhan/Desktop/实验室/社团/代码/ai4law/backend/common/tasks/manager.py:451) 通过 `_persist_status()` 写入 `async_tasks`。

但该函数是 best-effort：异常被 `except Exception: pass` 吞掉（`:472-474`），且只记录状态、错误和首个产物路径；没有保存可重试所需的输入快照、runner 参数、provider 快照、attempts 或结果 JSON。

更关键的是，各模块状态查询仍直接访问内存：

- CPRA：[backend/domains/us/cpra/service.py](/Users/oujiazhan/Desktop/实验室/社团/代码/ai4law/backend/domains/us/cpra/service.py:424)
- US_14117：[backend/domains/us/eo14117/service.py](/Users/oujiazhan/Desktop/实验室/社团/代码/ai4law/backend/domains/us/eo14117/service.py:558)

两者都调用 `self.tasks.get_or_raise(task_id)`，没有数据库/manifest fallback。故“有数据库记录”不能阻止模块接口 404。

### 3.3 路由把内存 404 转成普通 HTTP 404

CPRA 路由：[backend/domains/us/cpra/router.py](/Users/oujiazhan/Desktop/实验室/社团/代码/ai4law/backend/domains/us/cpra/router.py:46)

US_14117 路由：[backend/domains/us/eo14117/router.py](/Users/oujiazhan/Desktop/实验室/社团/代码/ai4law/backend/domains/us/eo14117/router.py:53)

两者在捕获 `KeyError` 后统一返回 `HTTPException(status_code=404)`。响应没有说明：

- 任务是否在 `async_tasks` 中存在；
- 当前 worker 是否只是没有本地内存副本；
- 任务是否已有完成产物；
- 任务是否因服务重启而中断。

这使前端无法做可靠状态归因。

### 3.4 前端将基础设施 404 固化为业务 FAIL

文件：[frontend/src/api/modules.ts](/Users/oujiazhan/Desktop/实验室/社团/代码/ai4law/frontend/src/api/modules.ts:470)

`:485-491` 将任意异步状态 404 转成 `AsyncTaskNotFoundError`，文案直接指向“服务重启后旧任务失效”。工作台随后把该异常保存为 `asyncState=failed`，没有再次调用 `/me/tasks` 或 `/workspace-recovery` 以恢复数据库终态。

因此可能出现：

```text
数据库 COMPLETED + 产物存在
前端 module_run.success=false + errorCode=async_task_not_found
```

这正是 US_14117 当前事实。

### 3.5 runtime_settings 覆盖 .env

文件：[backend/app.py](/Users/oujiazhan/Desktop/实验室/社团/代码/ai4law/backend/app.py:54)

启动顺序是：

```text
Settings() 读取 .env
-> AppContainer
-> load_runtime_overrides(storage/runtime_settings.json)
-> apply_runtime_payload()
-> refresh_runtime_clients()
```

文件：[backend/core/runtime_settings.py](/Users/oujiazhan/Desktop/实验室/社团/代码/ai4law/backend/core/runtime_settings.py:65)

运行时文件路径由 `settings.storage_dir / runtime_settings.json` 决定（`:65-77`）。

远程该文件中，SiliconFlow 当前有效，但腾讯条目存在明确污染：

```text
api_key = 原始 key + 换行 + export TENCENT_API_URL=...
api_url = https://api.hunyuan.cloud.tencent.com/v1
```

这不是合法 API key，也不是当前 TokenHub 地址。`apply_runtime_payload()` 会无条件规范化并保存 payload（`:121-153`），没有拒绝换行、`export `、控制字符、旧域名或不匹配的 provider/model。

所以配置层存在隐患：当前活动 Provider 虽为 SiliconFlow，但一次后台保存、手工切换或故障回退都可能重新启用污染配置。

### 3.6 CPRA 的独立执行问题

CPRA 提交路径：[backend/domains/us/cpra/service.py](/Users/oujiazhan/Desktop/实验室/社团/代码/ai4law/backend/domains/us/cpra/service.py:413)

它把完整请求放入线程执行，并使用真实 LLM agent。远程日志出现：

```text
Agent cpra_spi_sharing_risk failed: Expecting ',' delimiter
Agent cpra_vendor_contract failed: Expecting ',' delimiter
```

Trace 随后出现“一致性审查完成”和 `final/final_brief`，但 `async_tasks` 仍为 `RUNNING`、无产物。这说明至少存在以下收尾风险之一：

- 某个后续渲染/打包步骤阻塞或未返回；
- 线程执行异常未到达 `_execute()` 的成功/失败收尾；
- 运行清单与数据库终态更新不在同一个不可分割操作中；
- 子 Agent 的降级结果没有被统一纳入任务级错误契约。

目前不能把 JSON 解析错误简单当作“可忽略 warning”，也不能把 Trace 的 final 事件当作文件已成功生成。

## 4. 为什么这不是单一功能故障

| 层 | 证据 | 影响 |
|---|---|---|
| 发布层 | 远程 HEAD 为旧 SHA | 线上未运行目标修复 |
| 进程模型 | `--workers 2` | 创建/查询随机跨进程 |
| 状态模型 | `_tasks` 内存字典 | worker/重启后接口 404 |
| 持久化设计 | `async_tasks` 只写不读 | 数据库记录无法恢复模块状态 |
| 配置层 | runtime JSON 含 `export` 污染 | provider 切换时 401/连接失败 |
| 前端状态层 | 任意 404 -> FAIL | 成功任务被显示失败 |
| LLM/业务层 | CPRA JSON 解析异常 | CPRA 结果链路可能降级或卡住 |
| 收尾层 | CPRA RUNNING 且无产物 | 任务终态与 Trace/文件不一致 |

任何只修其中一层的方案都会留下可复现缺陷。

## 5. 必须实施的修复方案

### P0：先恢复部署真实性和可用性

1. 从已确认 GitHub SHA 创建全新 release，不在旧目录原地覆盖。
2. 发布前记录并核对：Git SHA、前端 bundle hash、`.env` hash、启动命令 hash。
3. 清理 runtime settings，只保留已探测成功的 SiliconFlow；腾讯条目必须删除或修正为真实可用地址和独立合法 key。
4. 运行时配置禁止保存：换行、`export `、shell 语法、控制字符、旧域名和未验证模型。
5. 迁移期间将 worker 数设为 1 作为止血措施，但标记为临时措施；不能以此替代持久化修复。

### P1：统一异步任务的持久化状态机

新增持久化字段或等价的 manifest 存储：

```text
task_id, module, user_id, state, attempts, max_attempts,
created_at, updated_at, started_at, finished_at,
input_snapshot, provider_snapshot, result_json/result_path,
error_code, error_message, trace_manifest_path
```

状态查询、重试、取消必须优先读取数据库/manifest；内存只作为当前 worker 的执行句柄缓存。

必须定义并执行状态转换：

```text
CREATED -> RUNNING -> COMPLETED
                   -> FAILED
                   -> CANCELED
RUNNING -> INTERRUPTED（进程重启/租约过期）
```

状态写入必须具备幂等性和版本/时间戳保护，避免两个 worker 互相覆盖较新的终态。

### P1：修复路由与前端的状态归因

- 状态接口若内存无记录但数据库有记录，必须返回持久化状态，不得 404。
- 真正不存在才返回带明确 `error_code=TASK_NOT_FOUND` 的 404。
- 前端收到 404 后先调用恢复接口/`/me/tasks`，不能立即写 `FAIL`。
- 已有 `COMPLETED` + 产物的记录必须覆盖旧的假失败运行记录。
- `FAILED` 只能由后端持久化终态或明确业务错误生成。

### P1：CPRA 任务收尾与 LLM JSON 契约

- 所有 Agent JSON 响应使用严格解析 + 单次修复/重试，并记录 `LLM_INVALID_JSON`；不能只打印日志。
- 子 Agent 失败必须明确是“可降级继续”还是“任务失败”，纳入任务级策略。
- 线程执行设置最大时限和 watchdog；超过时限写 `FAILED/TIMEOUT`。
- 无论生成、渲染、打包哪一步异常，都必须写 `FAILED`、错误码、manifest 和 SSE 终态。
- `final` Trace 事件只有在结果对象、产物文件、数据库终态全部完成后才可作为成功摘要。

### P2：验收门禁

必须逐项记录请求、响应、数据库、manifest 和文件证据：

1. 单 worker 创建/轮询/完成。
2. 双 worker 创建后连续轮询 30 次，零错误 404。
3. 服务重启后查询仍返回 `RUNNING/COMPLETED/FAILED` 正确终态。
4. 任务创建 worker 与查询 worker 不同，仍能重试和取消。
5. 同一用户可访问自己的任务，其他用户返回 403；不存在任务返回明确 404。
6. Provider 探测成功；日志无新增 400/401；配置文件无密钥泄露和 shell 污染。
7. CPRA 非法 JSON、模型超时、渲染异常分别验证失败收尾。
8. SSE 历史事件、终态事件、manifest、产物下载与数据库状态一致。
9. 浏览器显示状态与 `/me/tasks`、任务状态接口和产物目录逐项一致。

## 6. 暂不应采用的伪修复

- 只把文案“Task not found”改成“任务执行中”；这会掩盖真实丢失。
- 只将 worker 改成 1；重启后仍然丢内存状态。
- 只清空前端 localStorage；数据库与后端任务仍不一致。
- 只重跑 CPRA；如果状态查询链路不修，重跑仍会随机 404。
- 只看到 Trace `final` 就标记成功；必须同时验证产物和持久化终态。
- 把完整 API key 写入 runtime JSON 或部署日志；应只通过受控 Secret/环境变量注入。

## 7. 当前状态与验收结论

截至本分析：

- 根因证据已闭环，未修改本地业务代码；
- 远程当前 release 版本不符合目标部署要求；
- SiliconFlow 当前探测成功，但 runtime 配置仍含污染的腾讯备用项；
- `--workers 2` 导致异步状态 404 已被日志复现；
- US_14117 后端已完成，页面状态失真；
- CPRA 仍为 `RUNNING` 且无产物，存在独立 JSON 解析和收尾缺陷；
- 在 P0/P1 修复并通过上述门禁前，不得宣称远程部署完成或全模块可用。
