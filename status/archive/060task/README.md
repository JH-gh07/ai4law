# 060 生成内容与报告模板专项审计

> 日期：2026-08-12
> 状态：现状分析与审计任务拆分阶段
> 范围：需求文档、黄金示例、业务规则、模型生成、章节拼接、报告模板和最终产物
> 原则：只在本地核验；Claude Code 的工作区改动必须经过独立审查后才能视为完成

## 本大阶段目标

确认系统最终生成的报告，是否真正符合最初需求文档和黄金示例的业务目的，而不是只满足“有章节、有文件、测试通过”。重点检查：

- 生成内容是否回答了正确的业务问题；
- 报告结论是否来自事实、规则和证据；
- 模型、规则和模板是否重复生成或重复拼接；
- 不同章节之间是否重复、矛盾或互相覆盖；
- Markdown、DOCX、PDF 和 JSON 是否来自同一份内容；
- 不同功能是否保留业务差异，而不是被同一模板强行同质化。

## 执行顺序

```text
任务 01：先确认事实和文件职责
    ↓
任务 02：再审核当前生成和拼接问题
    ↓
任务 03：最后确定目标格式和整改方案
    ↓
用户确认目标方案
    ↓
再修改代码和模板
```

## 设计方案的编制要求

### 1. 优先识别可以并行的任务

设计方案时必须先分析任务之间的依赖关系，再决定串行或并行。只要多个任务满足以下条件，应优先并行执行：

- 面向多个相互独立的业务功能执行同一种检查或改造；
- 使用同一套需求文档、审核标准或验收口径；
- 各任务的输入范围和输出文件边界清楚；
- 不会同时修改同一个核心文件或相互覆盖状态；
- 一个任务的结论不是另一个任务开始工作的必要前提。

典型适合并行的场景：

```text
同一审核指令 + 同一需求依据
├── 审核 SCC 的生成内容和模板
├── 审核 TIA 的生成内容和模板
├── 审核 PIPIA 的生成内容和模板
└── 审核 DPIA 的生成内容和模板
```

其他适合并行的场景包括：

- 同时读取不同模块的源码并追踪生成链路；
- 同时抽取不同模块的 Markdown、DOCX 和 PDF；
- 同时核对不同案例与正式需求文档；
- 同时运行互不占用同一状态的定向测试；
- 分别审查内容正确性、模板结构、引用完整性和视觉一致性。

### 2. 不为并行而强行拆分

以下情况应保持串行：

- 公共 Report IR 或报告目标结构尚未确定；
- 后续任务依赖前一步输出的数据契约或设计决定；
- 多个任务必须修改同一个核心文件，存在覆盖风险；
- 任务很小，拆分后的沟通和合并成本高于执行成本；
- 不同任务的业务语义强耦合，分开处理会导致结论不一致；
- 子任务无法独立形成可验核的结果。

并行不是目的。目标是在不破坏事实一致性、代码边界和验收完整性的前提下缩短执行时间。

### 3. 每个并行任务必须使用统一任务契约

并行任务开始前必须统一写明：

| 项目 | 要求 |
|---|---|
| 目标 | 具体要证明或修复什么 |
| 输入 | 使用哪些需求文件、源码、案例和产物 |
| 范围 | 允许读取和修改哪些目录或文件 |
| 禁止事项 | 不得改写哪些事实、预期或公共契约 |
| 输出 | 必须返回哪些表格、证据、代码或报告 |
| 验收 | 使用哪些命令、断言和人工检查 |
| 失败条件 | 哪些结果必须判定为失败或阻断 |

所有并行任务必须使用同一套术语、风险等级、finding 定义和验收格式。子任务无权为了让自身通过而修改共同标准。

### 4. 主任务负责汇合和独立复核

并行任务完成不等于大阶段完成。主任务必须：

1. 检查各子任务是否使用了相同事实来源和判断标准；
2. 比较不同模块是否产生冲突或重复设计；
3. 检查改动是否相互覆盖、形成循环依赖或重复能力；
4. 重新运行必要测试，不直接采信子任务的成功汇报；
5. 检查最终 Git diff、产物和验收文档；
6. 统一记录完成项、失败项、未验证项和剩余风险。

### 5. 方案必须科学、可验核、可复现

设计方案中的每个目标都必须能够通过证据判断成功或失败，禁止只写“优化”“完善”“增强”等无法验收的描述。

每个实施步骤至少要包含：

- 当前问题和复现证据；
- 出错代码和实际执行链路；
- 正确业务逻辑和依据文件；
- 计划修改的文件及职责；
- 修改前后的输入输出契约；
- 自动化测试和强断言；
- 浏览器或产物人工验收；
- 回归范围；
- 完成条件和失败条件；
- 对应的验收记录位置。

验收结论必须可以由另一名工程师在本地重新执行并得到相同结果。

### 5.1 公共数据契约不得用“最小示例”代替实施方案

涉及 Report IR、Schema、接口、产物清单或模块公共契约时，文档必须给出完整实施基线：所有必填顶层字段、字段来源、对象关系、枚举、版本、迁移规则、异常状态和跨对象约束都要明确。不得用“最小 Report IR 示例”“其余字段按需补充”作为实施设计，也不得用空数组隐藏未解决的事实、证据、finding、action、引用、运行和产物问题。

如果不同模块存在真实差异，应通过判别联合类型、模块扩展或配置表达，并明确每个模块的必填字段和输出格式；不能复制一套模糊对象，也不能把缺失字段默认成通过。

### 6. 不允许留下未说明的漏洞或缺陷

方案必须主动检查正常路径、异常路径、边界条件、回退路径和多格式一致性。至少覆盖：

- 输入缺失、错误附件和错误角色；
- 模型不可用、超时、返回空内容或错误结构；
- 规则结论与模型文字冲突；
- 不同章节重复、矛盾或覆盖；
- Markdown、DOCX、PDF 和 JSON 不一致；
- 引用缺失、错误跳转或脚注漂移；
- 任务失败后重跑状态未更新；
- 旧流程仍被调用或新旧逻辑同时生效；
- 并发任务覆盖文件、污染状态或产生不确定结果。

任何暂时不能修复或验证的问题，都必须：

1. 明确记录具体问题；
2. 标记影响范围和严重程度；
3. 给出阻断原因和后续处理条件；
4. 不得将对应功能标记为完成；
5. 不得用降低断言、修改正式预期或隐藏 `known_defects` 的方式绕过。

最终要求不是声称“绝对没有问题”，而是确保所有已知风险都有验证证据；所有未知或未验证部分都被明确暴露并阻止错误放行，不留下无法追踪的灰色区域。

## 当前不能直接下的结论

- 共享案例数量增加，不等于案例事实已经审核通过；
- CLI 通过，不等于报告内容符合黄金示例；
- DOCX/PDF 能生成，不等于模板内容合理；
- 章节数量一致，不等于章节职责没有重复；
- 模型输出有内容，不等于结论有证据支持。

## 总体验收口径

每个功能最终都要能回答：

```text
正式需求要求什么？
当前代码在哪一步处理？
当前报告实际生成什么？
是否重复或遗漏？
模板是否改变了含义？
最终产物是否与结构化结论一致？
```

本目录只记录方案和审计结果，不直接存放运行产物。运行产物继续放在 `tmp/` 或 `runs/`，验收结论放在 `status/check/`。
