# 060task 03：理想报告结构与统一渲染整改方案

> 日期：2026-08-12
> 状态：待确认目标方案
> 目标：先确认理想报告长相和格式，再决定代码和模板怎么改

## 一、推荐的统一报告结构

不同功能保留自己的专业章节，但统一外层结构：

### 1. 报告基本信息

- 功能名称；
- 企业和任务；
- 法域；
- 生成时间和版本；
- 输入文件及附件角色；
- 报告状态。

### 2. 执行结论

报告开头直接回答：

- 当前能否继续；
- 风险等级；
- 适用路径；
- 是否被材料门禁阻断；
- 缺少什么；
- 满足哪些条件后可以重新执行。

示例：

```text
当前结论：暂缓执行
风险等级：高
阻断原因：缺少签署版标准合同和第三国法律分析
下一步：补齐材料后重新运行
```

### 3. 输入事实

事实单独成表，不混入判断：

- 出口方；
- 接收方；
- 国家/地区；
- 角色关系；
- 数据类别；
- 数据规模；
- 处理目的；
- 传输频率；
- 文件和附件角色。

### 4. 路径和适用性判断

说明：

- 为什么进入当前功能；
- 适用哪条路径；
- 选择条件是否满足；
- 其他路径为什么不适用；
- 还有哪些前置条件。

### 5. 核心问题清单

每个问题只建立一条结构化主记录：

| 编号 | 问题 | 事实依据 | 法律依据 | 风险 | 状态 |
|---|---|---|---|---|---|

### 6. 模块专属分析

只放该功能独有的判断：

- SCC：模块、条款、Annex、TIA、批注建议；
- TIA：第三国法律、SCC 有效性、补充措施、残余风险；
- PIPIA：数据范围、合法性、告知同意、接收方、备案材料；
- DPIA：必要性、比例性、自动化决策、风险矩阵；
- CPRA：消费者权利、出售/共享、敏感信息、退出机制。

### 7. 整改清单

每项包括：

- 问题编号；
- 整改动作；
- 责任角色；
- 需要提交的证据；
- 完成判断方式；
- 复审时间。

### 8. 证据和引用

明确区分：

- 用户声明；
- 上传文件证据；
- 系统解析结果；
- 确定性规则；
- 法律检索结果；
- 模型解释。

### 9. 附录

- 结构化事实 JSON；
- findings/decision JSON；
- 文件清单和哈希；
- 引用 map；
- Trace 摘要；
- 产物清单。

## 二、推荐的格式关系

推荐采用“一份结构化报告，多种渲染格式”：

```text
Report IR / report.json
├── Markdown
├── DOCX
├── PDF
├── HTML（diagnosis 等需要网页预览的模块）
├── 批注 DOCX（review/SCC 等需要在原文上标注的模块）
└── 前端报告展示
```

推荐职责：

- JSON/Report IR：唯一机器事实和结论来源；
- Markdown：人工审核主版本；
- DOCX：正式交付版本；
- PDF：从同一 IR 渲染，不从另一份 DOCX 重新生成；
- HTML：只作为网页预览渲染，不得重新计算 decision 或 findings；
- 批注 DOCX：只在 IR 的 finding/evidence 已绑定后对原文添加批注，不得另造问题清单；
- 前端：读取同一结构化报告，不重新拼接业务结论。

不能要求 11 个模块都强制生成同一种文件。`diagnosis` 当前真实契约是 HTML/PDF，
`review` 当前真实契约是 DOCX/PDF，并可能额外生成带批注的 DOCX；是否增加独立
Markdown，必须由正式需求和用户交付场景确认，不能为了表面统一擅自增加产物。

## 三、生成职责建议

### 确定性代码负责

- Schema 校验；
- 事实归一化；
- 路径选择；
- 风险等级；
- finding；
- 材料缺口；
- decision；
- 引用绑定；
- 是否允许继续。

### 模型负责

- 解释规则结果；
- 把事实组织成可读文字；
- 生成模块专属分析；
- 提出基于已有 finding 的整改说明。

模型不应负责：

- 自己创建新的风险等级；
- 自己决定是否可以继续；
- 自己补造缺失事实；
- 自己生成另一套 findings；
- 改变确定性规则的结论。

## 四、重复控制规则

1. 一个 finding 只有一个完整主展示位置。
2. 摘要只能引用 finding 编号和短句。
3. 详细分析不能重新创建同义 finding。
4. 模板不能再写一遍模型已经生成的完整结论。
5. 所有章节使用同一个 `decision` 和风险等级。
6. 同一法规引用只绑定一个结构化引用身份。
7. 各模块声明的 Markdown、DOCX、PDF、HTML 和批注 DOCX 必须使用同一章节和表格数据；没有某种格式的模块不得被伪造出空产物。

## 五、建议的实施顺序

1. 先完成任务 01：逐模块现状与来源对照。
2. 再完成任务 02：对已有产物做重复和矛盾审计。
3. 由用户确认报告开头、章节顺序、表格样式和格式关系。
4. 先选一个模块做 Report IR 试点，建议从 TIA 或 SCC 开始。
5. 用同一 IR 输出该模块实际需要的格式（例如 TIA 的 Markdown/DOCX/PDF，diagnosis 的 HTML/PDF，review 的 DOCX/PDF/批注 DOCX）并做视觉验收。
6. 再把公共能力推广到其他模块。
7. 最后删除重复模板映射和旧渲染路径。

## 六、需要用户确认的内容

请确认以下默认提案是否作为后续标准：

- 是否采用“结论先行”；
- 是否要求事实和判断严格分离；
- 是否要求一个 finding 只保留一个完整主展示位置；
- 是否采用 Report IR 作为 JSON/Markdown/DOCX/PDF 的唯一来源；
- 是否允许不同模块拥有不同专属章节；
- 是否把“用户声明”和“文件已验证”分开显示；
- 是否把“草案条件性结论”和“当前证据门禁结论”同时保留。

在这些内容确认前，不建议直接大规模修改模板或删除旧生成路径。

## 七、目标方案对应的现状证据

### 1. 为什么需要 Report IR 作为唯一来源

当前 [DocumentCompiler](/Users/oujiazhan/Desktop/实验室/社团/代码/ai4law/backend/common/reporting/compiler/core.py:1) 仍是 additive 阶段，没有替代旧渲染路径；实际产物已经出现双标题和格式漂移。因此目标不能只增加新 compiler，而应最终形成：

```text
规则/事实层
→ 唯一 Report IR
→ 一次结构和引用校验
→ Markdown/DOCX/PDF/前端并行渲染
```

禁止再让模块模板在 IR 之后重新生成业务结论。

### 2. 为什么标题必须由 IR 管理

CPRA、SCC、PIPIA 实际产物已经证明 chapter title 和 chapter content 都可能携带标题。目标契约应规定：

```text
section.title：唯一章节标题
block.text：不得包含同级或更高级 Markdown 标题
```

编译门禁新增：正文 block 出现 `#` 标题且与 section.title 同义时，判定为错误而不是警告。

### 3. 为什么 finding 必须单一主展示

BCR 当前同时存在详细审查表、按风险分类章节和整改路线图。目标 Report IR 应使用 finding ID 建立引用关系：

```text
finding 主记录：完整事实、法律依据、风险、建议
执行摘要：只引用 finding ID + 一句话
整改清单：只引用 finding ID + 动作/责任人/证据
模块分析：只解释 finding，不复制完整记录
```

编译门禁统计每个 finding 的 `primary_display_count`，必须等于 1。

### 4. 为什么需要确定性 decision 入口

当前多个模块把相同上下文逐章交给模型，模型有机会重新描述风险和结论。目标 IR 中以下字段必须由确定性代码写入并锁定：

```json
{
  "decision": {
    "status": "suspend",
    "risk_level": "HIGH",
    "blocking_reasons": [],
    "conditions": []
  }
}
```

模型只能读取这些字段并生成解释，不能返回另一套 decision 覆盖它们。

## 八、完整 Report IR 契约（实施基线）

本节不是演示性质的最小对象，而是后续实现、迁移和验收必须共同遵守的完整契约。字段可以通过版本升级新增，但实施时不得擅自删除某一类信息，也不得把缺失字段藏回章节正文。

### 1. 当前 DocumentIR 为什么还不完整

当前 [DocumentIR](/Users/oujiazhan/Desktop/实验室/社团/代码/ai4law/backend/common/reporting/schema/document.py:43) 只有版本、metadata、sections、diagnostics、provenance 和哈希；[Block](/Users/oujiazhan/Desktop/实验室/社团/代码/ai4law/backend/common/reporting/schema/blocks.py:32) 只有 paragraph、claim、list、table、warning 五类。它可以验证“章节能否编译”，但还不能独立表达：

- 用户输入和上传文件；
- 事实及事实是否已经验证；
- 文件页码、条款、段落等证据定位；
- 唯一确定性 decision；
- finding、整改动作和两者关系；
- 本报告使用的全部引用记录；
- 11 个模块的专属业务结构；
- 模型调用、规则版本、知识库版本和降级状态；
- 每种输出格式的要求、产物哈希、页数和有效性检查；
- 内部报告与对外报告的信息边界；
- 人工复核、批准和完成状态。

因此目标不是在现有 `sections` 外面随便补几个数组，而是形成“业务事实层、判断层、展示层、产物层”职责完整的单一契约。

### 2. 顶层结构

| 顶层字段 | 必填 | 作用 | 禁止事项 |
|---|---|---|---|
| `schema` | 是 | Schema 名称、主版本、次版本、兼容范围 | 不允许只写一个无法迁移的自由字符串 |
| `identity` | 是 | report/run/task/module/tenant/user 身份 | `cn_flow` 和 `us_14117` 不得混用 module identity |
| `lifecycle` | 是 | 草稿、降级、阻断、完成、人工确认状态和时间 | 文件生成不等于业务完成 |
| `metadata` | 是 | 标题、企业、法域、语言、时区、保密等级、报告日期 | renderer 不得用文件名替代正式标题 |
| `inputs` | 是 | request 快照、字段来源、附件、哈希、解析状态 | 不得只保存附件路径而不保存角色和内容哈希 |
| `facts` | 是 | 规范化事实及其来源、置信度和证据状态 | 模型不得补造缺失事实 |
| `evidence` | 是 | 文件/用户声明/系统解析/规则结果的证据单元 | 没有 locator 的文件证据不得声称已精确核验 |
| `rules` | 是 | 命中的规则、版本、输入事实和输出 | 不得只把规则结论写进自然语言 |
| `decision` | 是 | 唯一结论、风险、路径、阻断项和条件 | 模型和 renderer 不得覆盖 |
| `findings` | 是 | 结构化问题主记录 | 同义问题不得生成多个主 finding |
| `actions` | 是 | 与 finding 关联的整改任务 | 不得存在无 finding 来源的整改动作 |
| `citations` | 是 | 本报告实际使用的完整 CitationRecord | 可检索但未使用的引用不得进入脚注表 |
| `sections` | 是 | 用户可见章节及语义块引用 | 正文不得携带 Markdown 顶层标题 |
| `module_payload` | 是 | 11 个模块之一的受控专属数据 | 禁止自由字典和跨模块字段混放 |
| `render_contract` | 是 | 本模块需要的格式、模板、版式和公开范围 | 模块不得自行复制 renderer |
| `artifacts` | 完成时必填 | 实际生成文件、哈希、大小、页数和验证结果 | 只有路径或 0 字节文件不得记为成功 |
| `execution` | 是 | Trace、模型、RAG、Token、耗时、重试和降级情况 | 不得隐藏模型失败或回退路径 |
| `diagnostics` | 是 | 结构、内容、引用、格式和视觉门禁结果 | fatal/error 未清零不得完成 |
| `approvals` | 是 | 自动检查、人工复核、批准和签署记录 | 未批准不得伪装成正式报告 |
| `integrity` | 是 | 输入、IR、引用表、各产物哈希及规范化算法 | 哈希算法和 canonicalization 必须有版本 |

### 4. Blocks 必须扩展为完整语义联合类型

目标 `Block` 不能继续只有五类通用文本块，至少应包括：

| block type | 用途 | 关键引用 |
|---|---|---|
| `PARAGRAPH` | 普通事实说明 | fact/evidence refs |
| `CLAIM` | 带核验状态的法律或业务主张 | fact/evidence/citation/finding refs |
| `DECISION_SUMMARY` | 唯一结论展示 | decision ref |
| `FINDING_TABLE` | finding 唯一主展示 | finding refs |
| `FINDING_REFERENCE` | 其他章节对 finding 的简短引用 | finding ref，不得复制完整 finding |
| `ACTION_TABLE` | 整改任务主展示 | action refs |
| `FACT_TABLE` | 输入事实展示 | fact refs |
| `EVIDENCE_TABLE` | 文件、段落和验证状态 | evidence refs |
| `CITATION_NOTE` | 法律依据或脚注 | citation refs |
| `KEY_VALUE` | 报告元数据和结论摘要 | typed values |
| `LIST` | 有序或无序清单 | item refs 可选 |
| `TABLE` | 非 finding 的通用表格 | column schema + rows |
| `WARNING` | 缺材料、降级、冲突提示 | diagnostic/finding refs |
| `PAGE_BREAK` | 明确分页 | 无业务结论 |
| `ATTACHMENT_REFERENCE` | 附件或原文定位 | attachment/evidence refs |
| `ANNOTATION_REFERENCE` | Review/SCC 批注映射 | finding/evidence/annotation refs |

所有 block 使用判别字段 `type`，`extra=forbid`。renderer 必须对所有类型穷尽处理；出现未知类型时失败，不能静默降级成普通文本。

`module_payload` 必须是以 `type` 为判别字段的联合类型，不使用万能 `dict`：

| `review` | `CN_DOCUMENT_REVIEW` | 文档类型、条款、分类、缺失项、原文 locator、批注映射 |
| `pipia` | `CN_PIPIA` | 标准合同/认证/HR 豁免路径、告知同意、接收方、备案材料 |

### 6. 强制跨对象约束

1. 所有 `*_ref` 必须解析到同一 IR 中存在且类型正确的对象。
2. `decision.source` 只能是确定性规则、人工决定或已批准的外部权威决定；不得是普通模型输出。
3. `decision.locked=true` 后，模型和 renderer 只能读取，不能修改。
4. 每个 blocking finding 必须同时出现在 `decision.blocking_finding_refs`，并至少有一个 action 或明确的不可整改原因。
5. 每个 action 至少引用一个 finding；每个 finding 必须引用事实、证据缺口、规则或引用中的至少一类依据。
6. `primary_display_count` 必须等于 1；其他章节只能使用 `FINDING_REFERENCE`。
7. Claim 的法律结论必须有 citation；用户声明必须标记 `USER_CLAIM_ONLY`，不能伪装为已核验事实。
8. `external_report_allowed=false` 的证据和引用不得进入对外可见 block。
9. `required_artifacts` 中的每个格式都必须有一个通过验证的 artifact；0 字节、打不开或缺字体的文件不得出现 `validation_status=PASSED`。
10. `diagnostics` 中存在 `blocks_completion=true` 的 error/fatal 时，`lifecycle.state` 不得是 `COMPLETED`。
11. `report_ir_hash` 在渲染期间保持不变；任何格式不得反向修改 IR。
12. 同一 run 的 Markdown、DOCX、PDF、HTML 和批注 DOCX 必须引用同一 `report_ir_hash`。
13. 旧对象迁移必须记录 `migrated_from_schema` 和迁移诊断；禁止无记录地猜测缺失字段。
14. 模块专属字段只能进入对应的 `module_payload` 类型；公共层不得反向依赖某一业务模块。

### 7. 版本和迁移原则

- `4.0.0` 表示引入完整业务对象和 blocks 联合类型，是一次明确的主版本升级。
- 当前 `3.0` DocumentIR 继续作为迁移输入，不和新契约并行成为两个长期真相源。
- 每个旧模块先通过 adapter 输出完整 v4 IR；只有 v4 compiler 和强制门禁通过后，才允许切换用户产物。
- adapter 对无法从旧章节恢复的事实必须写入 `diagnostics`，不能生成默认值冒充真实事实。
- 迁移顺序先试点，再逐模块替换；同一模块切换后，旧 renderer 不再对用户产物生效。

## 九、目标方案的强制验收指标

### 内容一致性

- `decision` 在 JSON 以及该模块实际生成的所有格式（Markdown、DOCX、PDF、HTML、批注 DOCX）中完全一致；
- 每个 finding 只有一个完整主展示；
- 每个 action 必须引用 finding；
- 每个法律结论必须引用 citation 或明确标记为用户声明；
- 模型输出不得新增未注册 finding ID。

### 结构一致性

- 不允许连续出现同义章节标题；
- 不允许章节层级跳跃；
- 不允许 block 正文包含同级顶层标题；
- 所有实际生成格式的章节 ID 和顺序一致；没有生成的格式不作为通过条件；
- 模板占位符和 citation marker 不得残留。

### 产物一致性

同一 run 必须保存：

```text
report_ir.json
markdown.md
report.docx
report.pdf
citation_map.json
render_manifest.json
```

`diagnosis` 和 `review` 的 manifest 必须额外记录真实格式契约：

```text
diagnosis: html, pdf
review: docx, pdf, [annotated_docx]
```

不能因为 `markdown.md` 不存在就漏掉这两个模块，也不能把尚未被正式需求要求的
Markdown 当成已完成条件。

`render_manifest.json` 记录每个产物的哈希、章节数、finding 数、action 数、citation 数和生成器版本。

### 重复控制

- 完全相同 block：0 个；
- 同义重复主结论：0 个；
- `primary_display_count != 1` 的 finding：0 个；
- 模板固定结论与模型结论重复：0 个；
- 无法追溯到 fact/finding/decision 的业务段落：0 个。

## 十、试点实施和失败条件

建议先选 TIA 或 SCC 做试点，因为两者已经有共享案例和结构化决策基础。

试点只有满足以下条件才能推广：

1. 正式需求与黄金示例逐项映射完成；
2. 当前产物重复问题能够稳定复现；
3. Report IR 能完整表达事实、decision、finding、action 和 citation；
4. 该模块声明的所有用户格式从同一 IR 生成；
5. 浏览器、CLI 和文件下载看到相同结论；
6. 旧渲染路径在该模块中不再生效；
7. 自动化门禁能故意注入重复、矛盾和缺失引用并正确失败。

出现以下任一情况必须停止推广：

- 为适配 IR 丢失模块专属语义；
- DOCX/PDF 仍依赖另一套模板重新生成内容；
- 模型可以覆盖确定性 decision；
- 同一 finding 仍需在多个位置手工复制；
- 只能靠人工目视判断格式一致性；
- 旧路径和新路径同时对用户可见。

### 2. 目标技术逻辑

```text
业务事实/规则/证据
→ Report IR（只含语义，不含 Markdown）
→ IR 结构门禁（标题、finding、decision、引用、表格）
→ DOCX renderer ─┐
→ PDF renderer  ─┼→ 同一 render_manifest
→ Markdown      ─┤
→ HTML/批注 DOCX ┘
```

DOCX/PDF renderer 都不得再做以下事情：

- 重新判断风险等级或结论；
- 从正文猜测章节标题；
- 从字符串重新识别 finding；
- 重新拼接模板固定法律说明；
- 通过转换另一种最终格式来生成自身。

### 3. DOCX 的成熟实现要求

- 统一页面规格：A4 或 Letter 只能由模块契约选择一次，明确页边距、正文宽度、页眉、页脚和页码。
- 统一样式：正文、标题 1/2/3、表头、风险标签、引用、脚注分别有固定 style，不靠字符串中的 `#`、`**` 或手工空格表达。
- 语义表格：固定列宽、单元格内边距、表头跨页重复、长文本自动换行、禁止表格溢出页面。
- 分页控制：标题与首段保持在一起，避免孤立标题、空白页、段落被截断；长 finding 和整改动作允许自然跨页。
- 模板替换保留 run 样式；无法保留时改为“模板只提供页面样式，内容由 IR renderer 写入”，禁止半模板半纯文本。
- 批注 DOCX 只接受已绑定 `finding_id` 和 `evidence_ref` 的批注，不允许在批注阶段临时生成新问题。

### 4. PDF 的成熟实现要求

- 直接从 IR 生成 Platypus flowables：`Paragraph`、`Table`、`KeepTogether`、`PageBreak`、`PageTemplate`。
- 中文字体必须显式注册并在构建后用 `pdffonts` 验证；字体不可用时构建失败，不得静默回退到无法覆盖中文字形的字体。
- 标题、列表、表格、引用和脚注分别使用独立样式；禁止把 Markdown 原文交给 PDF parser 猜测。
- 页眉页脚、页码、报告标题和版本信息由 renderer 的页面模板统一添加。
- 长表格必须重复表头；章节必须允许在合理位置分页；任何文字溢出、裁切、空白页和不可复制文本都判失败。

### 5. 必须执行的验收

同一 `run_id` 同时保存：

```text
report_ir.json
markdown.md（模块契约要求时）
report.docx（模块契约要求时）
report.pdf（模块契约要求时）
report.html（diagnosis 等模块）
annotated_docx（review/SCC 等模块）
render_manifest.json
```

机器验收：

- `decision`、`finding_id`、章节 ID 和引用数量跨实际生成格式一致；
- `pandoc report.docx -t plain` 与 IR 的正文事实一致；
- `pdftotext -layout report.pdf` 不含残留 `{{...}}`、内嵌 `##`、孤立 `#` 和乱码；
- `pdffonts report.pdf` 显示已注册的中文字体；
- DOCX XML 中标题使用 Heading 样式，表格存在固定列结构，页码关系存在；
- 每个 DOCX 非零、是有效 OOXML ZIP，并能被 `python-docx` 或 LibreOffice 重新打开；
- `render_manifest.json` 记录格式、哈希、页数、章节数、finding 数、citation 数和 renderer 版本。

视觉验收：

```text
DOCX → LibreOffice headless → PDF → pdftoppm PNG
PDF  → pdftoppm PNG
```

逐页检查标题层级、页边距、分页、表格宽度、文字截断、字体、页眉页脚、页码和空白页。任何一个实际生成格式视觉失败，都不能标记该模块完成。

### 6. 建议的可配置版式契约

不要把字号、边距和字体散落在各模块 Service 中。公共层维护 `RenderProfile`，模块只能选择或少量覆盖：

```yaml
profile_id: legal-report-a4-v1
page:
  size: A4
  margin_top_mm: 20
  margin_right_mm: 22
  margin_bottom_mm: 20
  margin_left_mm: 22
fonts:
  cjk_body: Source Han Serif SC
  cjk_heading: Source Han Sans SC
  latin_body: Arial
  embed_in_pdf: true
styles:
  body_pt: 10.5
  body_leading: 1.45
  heading_1_pt: 16
  heading_2_pt: 14
  heading_3_pt: 12
table:
  body_pt: 9
  repeat_header: true
  fixed_layout: true
footer:
  page_number: true
  report_id: true
```

这些数值是建议默认值，必须用正式需求示例和真实中文/英文混排报告试排后确认。模块差异应通过 profile 配置表达，例如正式审查报告允许批注和宽表格，诊断报告允许 HTML 预览；不得复制一套新的 renderer。
