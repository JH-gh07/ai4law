# SCC 完整本地首跑补验计划

> 日期：2026-08-08
>
> 约束：只在本地执行；不部署远端；旧的 no-LLM service 证据继续保留，不覆盖。

## 当前起点

已有证据只证明：`01_minimal.json` 内联文本在旧流程和 Schema-first 新流程下，可以禁用 LLM 生成 Markdown、DOCX、PDF、CitationMap、trace；新流程额外生成 DocumentIR。

它没有证明真实 SCC 文件参与核心审查，也没有证明 live LLM、正文脚注、引用跳转、HTTP、浏览器、token 和耗时展示。因此当前状态为“确定性 service 试跑通过，完整本地首跑未完成”。

## 本次路线

1. 固定当前最小案例的来源和哈希。
2. 增加来源明确的复杂案例，并使用真实 SCC 文档附件。
3. 先写失败测试，证明当前 service 没有把上传 SCC 文本作为核心审查输入。
4. 修复后运行 SCC 专项测试和案例一致性门禁。
5. 对最小案例、复杂案例分别运行旧流程和新流程 no-LLM。
6. 核对业务结论、MD/DOCX/PDF、批注 DOCX、DocumentIR、CitationMap、trace 和回退。
7. no-LLM 通过后，再运行本地 live provider，并记录 provider、model、token、耗时和事件。
8. 最后运行本地 HTTP/浏览器上传与引用点击；保存截图和网络证据。

## 验收清单

- [ ] 旧流程 no-LLM 通过。
- [ ] 新流程 no-LLM 通过，DocumentIR 编译无阻断诊断。

- [ ] live provider 调用、token、耗时和执行事件可核对。

- [ ] 最终报告明确区分通过项与未通过项。

## 已知风险与处理

| 风险 | 处理 |
|---|---|
| 仓库权威 SCC 原文件是旧 `.doc` | 转换为测试专用 DOCX，保留来源路径和哈希，不改原文件 |
| 当前 `uploaded_files` 没有文件角色 | 本轮只允许第一个可解析文档作为 SCC 主文档；后续再升级为结构化附件契约 |
| live 模型可能受代理或配额影响 | 先完成确定性链路；失败时保存 provider 错误，不能用 no-LLM 冒充 live 成功 |
| 当前 CitationMap 候选不准确且脚注为 0 | 作为阻断项单独修复，不以“候选数量大于 0”判通过 |
