## 6. 风险评级是否符合案例要求

原实现只按 26 项 finding 的平均分评级。三个核心 HIGH 缺陷被大量 MEDIUM finding 稀释，结果错误地成为“部分缺失”。

修复位置：`backend/domains/eu/bcr_review/bcr_risk_aggregator.py:34-40`。

当前规则：

- 类型明确冲突：高风险；
- 至少 2 个 HIGH finding：高风险；
- 否则再按总分阈值判断。

HealthData 案例最终发现 26 项，其中核心缺陷包括：

| requirement | 核心问题 | 结果 |
|---|---|---|
| `BCR-C-1.1` | 约束力文书不明确 | HIGH |
| `BCR-C-1.2` | 缺少第三方受益人权利 | HIGH |
| `BCR-C-1.3` | 未指定欧盟责任实体和赔偿责任 | HIGH |
| `BCR-C-1.9` | 缺少结构化第三国法律评估 | HIGH/MEDIUM 组合 |

因此“高风险”不是模型自由发挥，而是固定规则和案例预期共同支持的结果。

|---|---|---|
| 职责清晰 | 通过 | builder、文档审查、风险、RAG、引用、渲染和前端统计各自负责 |
| 目录有序 | 通过 | fixture、case、源码、运行产物和验收证据分离 |
| 命名统一 | 通过 | 新文件均使用 BCR 业务语义命名，没有 new/final/temp/misc |
| 边界明确 | 通过 | 浏览器 payload 显式进入 `uploaded_documents`；得理 API 未冒充本地 RAG |
| 依赖单向 | 通过 | BCR 域依赖公共 RAG/引用/报告能力，公共层不依赖 BCR |
| 共性下沉 | 通过 | Markdown 定位号修复和报告指标提取位于公共层 |
| 差异配置 | 通过 | BCR requirement 与引用选择保留在 BCR 域内 |
| 产物分离 | 通过 | 用户产物与 CitationMap/DocumentIR/trace 验收证据分目录 |
| 本地功能闭环 | 通过 | old/new/live/browser/citation/knowledge 均有证据 |
| 生产完成 | 未达到 | provider 超时、远端和旧流程退出尚未完成 |
| 远端部署 | 未执行 | 等用户明确同意后再部署 |

下一步按总方案进入剩余未完成模块；不要重复执行已经验收通过的 SCC、PIPIA 和 BCR，除非公共层回归发现新问题。
