```typescript
export function KnowledgeContentRenderer({ content, variant = "default", className }: KnowledgeContentRendererProps) {
  const variantClass = `kc-renderer-${variant}`;
  const combinedClass = ["kc-renderer", variantClass, className].filter(Boolean).join(" ");

  const components: Components = {
    a({ href, children, ...props }) {
```

**结论**: 基础 Markdown 元素可使用，但法律条文常见场景存在四个缺口：

**(a) 标题层级缺失** — 法律条文内部常以 `## 第二章 网络安全支持与促进` 等方式标注章节，但 `.kc-renderer` 未定义 h1-h6 样式，章节标题与正文无法区分。

**(b) 嵌套列表缩进** — 典型法律条文结构：
```markdown
1. 个人信息处理者应当：
   - 告知个人信息处理的目的
     - 收集目的
     - 使用目的
   - 取得个人同意
```
当前 `ul`/`ol` 仅设 `padding-left: 1.5rem`，CSS 不区分层级，三层嵌套的视觉深度完全相同。

**(c) 条文正文无段落间距** — 法律条文每"款"之间应有空行，但 `.kc-renderer` 对 `<p>` 无 margin 定义。ReactMarkdown 对连续文本生成的是单个 `<p>`，若 content 本就是纯文本则只剩一个块。

**(d) variant 枚举但仅影响 font-size** — 
```css
.kc-renderer-evidence { font-size: 0.9375rem; line-height: 1.7; }
.kc-renderer-compact { font-size: 0.875rem; line-height: 1.6; }
```
三个 variant (`default`, `evidence`, `compact`) 仅改字号和行高，`evidence` 变体无高亮或边框区分。

### 1.3 law-viewer-article-body 的 white-space 问题

```css
/* pages.css:1231 */
.law-viewer-article-body {
  white-space: pre-wrap;
  overflow-wrap: anywhere;
}
```

`white-space: pre-wrap` 保留了源码换行。当 `KnowledgeContentRenderer` 输出 ReactMarkdown 生成的 HTML（如 `<p>...</p><ul><li>...</li></ul>`）时，ReactMarkdown 不生成换行符 — `pre-wrap` 不影响。但当后端返回含 `\n` 的纯文本时（例如从 HTML 快照提取的 `_clean_source_text`），`pre-wrap` 会保留每一个硬换行，可能导致渲染结果与实际文档意图不符。

## 三、条文内容格式分析

### 3.1 JSONL 数据结构

**文件**: `resources/legal/registry/regulation_articles.jsonl`

```json
{
  "article_id": "CN-LAW-001-001",
  "jurisdiction": "cn",
  "law_name": "中华人民共和国网络安全法（2025修正）",
  "article_ref": "第一条",
  "content": "第一条 为了保障网络安全，维护网络空间主权和国家安全...",
  "source_id": "CN-LAW-001",
  "doc_type": "law"
}
```

**关键问题**: `content` 字段为**纯文本字符串**，不包含任何 Markdown 标记。这意味着：

1. `KnowledgeContentRenderer` 将其喂给 `ReactMarkdown`，后者将整段文本视为单个 `<p>` 段落
2. 法律条文"款/项/目"的层级结构（如：第一款的第二个小项）完全扁平化
3. 条文编号（如 `（一）、（二）`、`1.、2.`）在文本中保留但无 HTML 语义

**实际流**:
```
"第一条 为了...\n\n网络安全工作坚持..."
  → ReactMarkdown → <p>第一条 为了...<br/>网络安全工作坚持...</p>
```
ReactMarkdown 将 `\n\n` 解析为新段落，但 `\n` 在 `<p>` 内被合并。最终"款"之间无视觉分界。

### 3.2 文本截断问题

查看 JSONL sample，第 4 条 content 结尾：
```
"第四条 国家坚持网络安全与信息化发展并重，遵循积极利用、科学发展、依法管理、确保安全的方针，推进网络基础设施建设和互联互通，鼓励网络技术创新和应用，支持培养网络"
```
**内容在 "支持培养网络" 处截断**，疑似采集时字数限制。需逐个 source 核验是否存在类似截断。

### 3.3 _clean_source_text 的副作用

**文件**: `backend/services/knowledge_index.py:353-393`

`_clean_source_text()` 对 HTML 快照执行多重清洗：
- 提取 `<article>`/`<main>` 等语义段 (`_extract_primary_html_segment`)
- HTML 标签剥离 (`_extract_text_from_html`)
- 中文换行重连（`re.sub(r"([一-鿿])\n([一-鿿])", r"\1\2", normalized)`）

对中文段落来说行重连是正确的，但当源文档存在空行分隔段落时，重连逻辑将所有相邻汉字行合并为一个块。这可能导致原文的章节/分条结构丢失（若原文的快照格式不同）。

`_parse_articles_from_text()` (line 287-350) 尝试用正则匹配中文"第X条"、EU "Article X"、US "§1798.XXX" 来恢复分条结构，作为 JSONL 未覆盖来源的 fallback。**但对日文、韩文、越南文的条文结构完全不支持**（无对应的 header 正则）。

### 3.4 formatLegalLocator 的局限性

**文件**: `frontend/src/lib/legal-locator.ts:17-25`

```typescript
export function formatLegalLocator(rawValue, language = "zh") {
  const value = String(rawValue ?? "").trim();
  if (!value) return "";
  if (!NUMERIC_ARTICLE_RE.test(value)) return value;  // \d+[A-Za-z]?(?:[-–]\d+[A-Za-z]?)?
  return language === "zh" ? `第${value}条` : `Article ${value}`;
}
```

**支持**: `"13"` → `"第13条"`, `"45"` → `"Article 45"`, `"1798.100"` → `"Article 1798.100"`

**不支持**:
- `"first"` / `"首先"` — 未进入 numeric 分支，返回原文
- `"1-2"` — regex 支持，OK
- `"13A"` — regex 支持，OK
- `"１３"`（全角数字）— **regex 不匹配**，返回原文 `"１３"`

全角数字在日文/中文法律中常见，当前无法正确格式化。

## 五、条文前后导航分析

### 5.1 当前实现

**文件**: `frontend/src/pages/LawViewerPage.tsx:246-279`

`LawViewerPage` 接收 URL 参数 `?source=CN-LAW-001&article=13`，调用 `fetchArticleDetail(sourceId, articleNo)`，渲染三个 section：

```
┌───────────┐
│ 上一条     │ ← prev_article_no + prev_article_content
├───────────┤
│ 当前条文   │ ← article_no + article_content + "当前查看条文" 标记
│ (高亮边框) │
├───────────┤
│ 下一条     │ ← next_article_no + next_article_content
└───────────┘
```

### 5.2 缺失功能

**(a) 无全法条文目录** — 用户无法看到一部法律的完整条文列表并跳转到任意条。当前只能看到 ±1 条前后文。

**(b) 无条号跳转输入框** — 无法输入"第38条"直接跳转，必须通过外部 URL 或引用链接进入。

**(c) 无分页/无限滚动** — 浏览上下条后无法持续向前后滚动（需逐条点击）。

**(d) prev/next 边界处理** — 当 `prev_article_no === null` 时，前一节不渲染（正常行为）。但用户无提示"这是第一条"。

### 5.3 后端 support 范围

`get_article_detail()` 同时支持 JSONL registry（精确查询，含 prev/next）和文本解析 fallback（`_parse_articles_from_text` 返回全部条文 dict）。理论上后端已有全文数据，前端只需一次获取并按页码/条号切分。

## 六、引用联动分析

### 6.1 当前实现

**文件**: `frontend/src/pages/EvidenceCenterPage.tsx:755-783` (citation tab)

```
用户输入: "数据出境安全评估办法第4条"
  → fetchKnowledgeCitation(query)
  → GET /api/v1/knowledge/citation?query=...
  → resolve_user_citation() [knowledge_projection.py:474-486]
    → 遍历 build_user_source_catalog() 全部 source_id 和 title
    → 如果 query 中包含 source_id 或 title（子串匹配）→ 返回该行
```

### 6.2 根因

```python
def resolve_user_citation(query: str) -> dict[str, str] | None:
    text = (query or "").strip().lower()
    rows = build_user_source_catalog()
    for row in rows:
        source_id = (row.get("source_id") or "").lower()
        title = (row.get("title") or "").lower()
        if source_id and source_id in text:
            return row
        if title and title in text:
            return row
    return None
```

**缺乏条文号解析能力**：查询"网络安全法第13条"时，算法尝试匹配 source_id="CN-LAW-001" 或 title 中是否包含 "网络安全法13条"。但 `source_id` 是代码（不在 query 中），`title` 是"中华人民共和国网络安全法（2025修正）"（不包含"第13条"）。

**实际结果**: 依赖子串匹配 `"网络安全法" in title` 命中来源，但对于"个人信息保护法"和"个人信息保护法实施条例"的歧义，可能返回错误的匹配或不返回结果。

### 6.3 引用联动用法

前端 EvidenceCenterPage 的引用联动与 CitationPopover 的"点击跳转到知识库中心查看原文"按钮配合使用：

### 9.4 条文截断分析

**影响**: 长条文（如 EU-LAW-001 GDPR 第 99 条，或 CPRA §1798.100 约 3000+ 字符的条款）将被截断，用户只能看到前半部分。

**正常管线 (V3 multi-index)**:

**影响范围**：
- `write_sources_csv()`（写 `sources.csv` 元数据行）**不受影响**——它不读 PDF，只写元数据；因 51 个 source_id 已全部在 CSV 中，重跑会显示 `no new sources to add`。
- `write_articles_jsonl()`（抽取条文写 `regulation_articles.jsonl`）**完全失效**——51 个 PDF 全部找不到，新增条文数为 0。好在历史 JSONL 中已有的 ~1347 条区域条文不受影响（磁盘文件未动），只是**无法再增量重建/补齐**这些法域的条文。

> 说明：`PDF_VN`/`PDF_SG` 两个常量被 VN/SG 来源的 `pdf_subpath` f-string 实际引用，是**必须**修正的活跃路径；而 `PDF_JP`/`PDF_KR`/`PDF_HK`/`PDF_MO`/`PDF_TW`/`PDF_MY` 这 6 个常量**定义后从未被引用**（对应法域的来源在 `pdf_subpath` 里直接写了中文路径字符串，随后又被 `_PDF_PATH_FIXES` 覆盖），属死代码——真正的 JP/KR/HK/MO/TW/MY 路径修正在 `_PDF_PATH_FIXES` 上。但为一致性和可读性，这 6 个常量也应一并更新。
