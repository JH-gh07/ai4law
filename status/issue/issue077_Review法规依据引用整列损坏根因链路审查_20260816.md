# issue077：Review（SCC 合同审查）"法规依据"引用整列损坏根因链路审查

> 审查日期：2026-08-16
>
> 触发症状：文档专项智能审查（`doc_type=scc_contract`）产出的报告，每个问题的"法规依据"字段整列错误——法条全量堆砌、出现非法条号"处罚-X-X"、模板样例与法院判决书被当成法规依据、同一部法出现两种名称、且出现空白的"引用相关性警告"。
>
> 审查范围：`regulation_articles.jsonl` 数据层 → 知识库构建层 → RAG 检索层 → review 模块引用组装层 → 引用相关性校验层。
>
> 审查性质：运行事实与根因审查；本次不修改业务代码、不重建索引、不清理数据库。

## 1. 结论摘要

六个症状不是同一个故障，而是一条引用生成链路上的六个独立缺口，且都发生在 review（文档专项智能审查）模块，不在 task073 控制平面覆盖的 Diagnosis / Assessment 两个 pilot 内。

| 缺陷 | 事实结论 | 根因层级 | 根因证据（代码/数据地址） |
|---|---|---|---|
| 法条全量堆砌 | 每个 issue 的"法规依据"都含《个人信息保护法》第 1~74 条 + 《个人信息出境标准合同办法》第 1~13 条 | 检索层 | `backend/common/rag/orchestrator.py:618-628` 按 `source_id` 全量展开，不受 `top_k`/`source_cap` 限制 |
| 非法条号"处罚-X-X" | 报告出现"处罚-17-1/40-1/35-1/3-1/2-1"等 | 数据层 | `scripts/fix_cn_law_001_duplicates.py:78` 把 `-处罚-{n}` 后缀直接写进 `article_ref` |
| 模板当法条 | 《数据处理协议样例》《个人信息出境标准合同模板》被当作"法规依据" | 构建层 | `builders_v2.py:165` layer 硬编码 `L1_regulatory_evidence`；`source_registry.v1.json` 把模板归为 `source_kind=standard_clause` |
| 判决书当法规依据 | 法院判决书与法条并列出现在"法规依据" | 组装层 | `rag_provider.py:115-122` DeliLegal 案例检索结果直接拼进 citations |
| 名称重复 | 《个人信息保护法》与《中华人民共和国个人信息保护法》并存 | 组装层 | `review_rulebook.json` 短名 vs RAG 全名，未归一 |
| 空"引用相关性警告" | 多处出现"｜ 引用相关性警告："后无内容 | 校验层 | `service.py:399-402` + `citation_relevance_checker.py:89-94` 存在 `relevant=False` 但 `issues=[]` 的空档 |

## 2. 根因链路（自上而下五层）

引用从数据源到报告的完整链路：

```text
regulation_articles.jsonl（数据层）
   → build_legal_chunks_cn()（构建层）
   → _retrieve_cn_review() + _legal_by_reference_ids()（检索层）
   → rag_provider.lookup() + clause_reviewer（组装层）
   → CitationRelevanceChecker（校验层）
   → review_report_renderer / schema_first（渲染层）
```

### 2.1 数据层：`article_ref` 被 `-处罚-{n}` 污染

证据文件：`resources/legal/registry/regulation_articles.jsonl`（共 1968 行）。

实际统计（命令：`grep -oE '"article_ref": "处罚-[0-9]+-[0-9]+"' ... | sort | uniq -c`）：

| source_id | 法名 | 损坏条目数 |
|---|---|---|
| CN-LAW-001 | 中华人民共和国网络安全法（2025修正） | 16 |
| CN-REG-008 | 网络数据安全管理条例 | 6 |
| CN-LAW-002 | 中华人民共和国数据安全法 | 5 |
| CN-LAW-003 | 中华人民共和国个人信息保护法 | 4 |
| CN-TPL-016 | 个人信息出境标准合同模板 | 4 |
| CN-TPL-017 | 数据处理协议样例 | 1 |
| **合计** | | **36** |

个人信息保护法（CN-LAW-003）具体损坏条目：

```text
CN-LAW-003-029 → 处罚-17-1
CN-LAW-003-038 → 处罚-40-1
CN-LAW-003-045 → 处罚-35-1
CN-LAW-003-052 → 处罚-3-1
```

污染源头代码：`scripts/fix_cn_law_001_duplicates.py:76-78`

```python
for ext_n, idx in enumerate(others, start=1):
    old_ref = str(rows[idx].get("article_ref", ""))
    new_ref = f"{old_ref}-处罚-{ext_n}" if ext_n == 1 else f"{old_ref}-ext-{ext_n}"
```

根因说明：该脚本本意是给"同一法条号下的续接片段/处罚条款"做去重，但它把去重后缀 `-处罚-{n}` **直接写进了 `article_ref` 字段**，而不是写到独立的 `disambiguation`/`role` 字段。于是 `article_ref` 从合法条号（如"第十七条"）被改写成非法条号（"处罚-17-1"）。下游把 `article_ref` 当作 `citation_anchor` 使用，最终把"处罚-17-1"原样渲染进报告。

复核要点：`scripts/check_citation_source_integrity.py` 没有拦住它——`_normalize_article_lookup_key("处罚-17-1")` 返回原串 `"处罚-17-1"`（非空、含数字），被当成"可解析/唯一"的正常条目，存在校验盲区。

### 2.2 构建层：模板被当成 L1 法规证据

证据文件：`backend/common/knowledge/builders_v2.py:109-192`（`build_legal_chunks_cn`）。

关键代码：`builders_v2.py:165`

```python
layer="L1_regulatory_evidence",
```

`build_legal_chunks_cn()` 把 `regulation_articles.jsonl` 中**所有**条目（含 `doc_type=template` 的 CN-TPL-016/017）都构建为 `layer="L1_regulatory_evidence"`，没有按 `doc_type`/`layer` 区分模板层。

同时，缓存注册表把模板错误归类：`resources/legal/registry/source_registry.v1.json`

```json
{"source_id":"CN-TPL-016","doc_type":null,"layer":"L1_regulatory_evidence",
 "source_kind":"standard_clause","can_be_cited":false,
 "allowed_usage":["structure_control","internal_review"]}
```

模板本应是 `layer=L4_template` + `source_kind=template_slot`，实际却是 `L1_regulatory_evidence` + `standard_clause`。这使模板条文进入 `legal_index_cn` 的法规证据池。

模板来源原始登记（`resources/legal/catalog/sources.csv:21-22`）明确写有"用于结构参照，不直接作为法律依据"，但该约束在构建层没有被执行：

```text
CN-TPL-016,template_assets,cn,review,template,个人信息出境标准合同模板,...用于结构参照，不直接作为法律依据...
CN-TPL-017,template_assets,cn,review,template,数据处理协议样例,...用于结构参照，不直接作为法律依据...
```

### 2.3 检索层：`_legal_by_reference_ids` 全量展开，导致法条堆砌

证据文件：`backend/common/rag/orchestrator.py:618-628`

```python
def _legal_by_reference_ids_for_index(self, chunks, index_name):
    ref_ids = {ref for chunk in chunks for ref in chunk.reference_ids}
    if not ref_ids:
        return []
    entries = self._load_entries(index_name)
    results = []
    for entry in entries:
        chunk = _payload_to_chunk(entry.payload)
        if chunk.source_id in ref_ids or chunk.chunk_id in ref_ids:
            results.append(chunk)
    return self._dedupe_chunks(results)
```

问题：workflow 规则携带的 `reference_ids` 只要指向某个法源（如 `CN-LAW-003`），该函数就把该法源的**全部条文 chunk**（个人信息保护法 74 条）一次性展开，`top_k`/`source_cap` 在这里完全失效。

调用点：`orchestrator.py:234`（`_retrieve_cn_review` 内）

```python
legal.extend(self._legal_by_reference_ids(bundle.workflow_rules))
```

运行证据：`runs/review/20260811_145224_787679_01_minimal/trace/002_tool_start.json`，LLM 请求 prompt 的"适用法规参考"段：

```text

- 《个人信息保护法》第17条
- 《数据处理协议样例》第四条
- 《数据处理协议样例》第十条
- 《网络数据安全管理条例》第二十一条
- 《中华人民共和国个人信息保护法》第一条, 第二条
- 《中华人民共和国个人信息保护法》第三条
...
- 《中华人民共和国个人信息保护法》第二十九条, 处罚-17-1
...
```

这证明：① 模板条文（《数据处理协议样例》）已混入；② 全量法条被展开；③ 非法条号"处罚-17-1"已被透传。

### 2.4 组装层：案例与法条混排、名称不归一、全量盲贴

**（a）判决书混入 citations**

证据文件：`backend/domains/cn/document_review/rag_provider.py:115-122`

```python
if self.legal_api_service and self.legal_api_service.enabled and should_enrich:
    hits = self.legal_api_service.search_cases(clause_text[:80], size=2)
    if hits:
        external_citations = [f"{item['source']}: {item['title']}" for item in hits]
        citations = list(dict.fromkeys([*citations, *external_citations]))
```

`search_cases` 返回的是法院判决书（`backend/integrations/delilegal.py:74-123`，字段为 `title`/`source`/`summary`），却被直接拼进"法规依据"的 `citations` 列表，没有区分"法条 vs 案例"类型。报告里的"《大理白族自治州中级人民法院: 赵某；董某…判决书》"即由此而来。

**（b）名称不归一**

`resources/rules/cn/review_rulebook.json` 里规则用短名 `个人信息保护法`，RAG 命中用全名 `中华人民共和国个人信息保护法`，两者在 `rag_provider.lookup()` 合并后并存。`clause_reviewer._canonical_source_id()`（`clause_reviewer.py:570-575`）只把标题映射到 `source_id`，不回写统一的显示名，所以报告中两种名称同时出现。

**（c）全量 citations 盲贴到所有 issue**

证据文件：`backend/domains/cn/document_review/clause_reviewer.py:141-151`

```python
for issue in issues:
    if not issue.structured_citations:
        issue.structured_citations = self._build_structured_citations(config.get("citations", []))
    if not issue.citation_sources:
        issue.citation_sources = [f"《{c.source_title}》{c.article}".strip() for c in issue.structured_citations]
```

所有"没有自带引用"的 issue（DSL 规则、SPEC 专项、RULE 兜底等）都被无条件贴上一整份 `config["citations"]`（已含全量堆砌 + 模板 + 案例），这是"每个问题都带同一份 74 条法条"的直接原因。

### 2.5 校验层：相关性校验存在空档，拦不住堆砌

证据文件：`backend/domains/cn/document_review/service.py:397-402`

```python
for issue in issues:
    relevance = self.citation_checker.check(issue)
    if not relevance.get("relevant", True):
        issue.risk_analysis += f" ｜ 引用相关性警告：{'; '.join(relevance.get('issues', []))}"
```

证据文件：`backend/domains/cn/document_review/citation_relevance_checker.py:50-94`

`check()` 的逻辑空档：当 `structured_citations` 存在、每条相关性分数都 ≥ 0.3（故不追加 `issues`），但平均分 `< 0.4` 时，会置 `relevant=False` 而 `issues` 仍为空，于是渲染出"｜ 引用相关性警告："后无内容的空字段。

更关键的是，`_score_citation`（`citation_relevance_checker.py:96-115`）只做关键词重叠打分，**不校验条号格式、不校验来源身份、不限制引用数量**，因此既拦不住"处罚-17-1"，也拦不住"74 条全量堆砌"。

## 3. 现状边界

- 本缺陷发生在 review（文档专项智能审查）模块的引用组装/接地层，不在 task073 控制平面覆盖的两个 pilot 内；task073 的 Citation Validity（来源身份/资格门）即使跑在这条链路上，也拦不住"全量堆砌、非法条号、名称重复"这类"引用内容正确性"问题。
- 模板治理（`can_be_cited=false`）已存在于注册表，但 review 检索链路未按 `source_kind`/`layer` 正确隔离模板，且缓存注册表本身把模板误归类为 `standard_clause`。
- 上述六个缺口需要分层修复：数据层（锚点）+ 构建层（模板 layer/source_kind）+ 检索层（展开限流）+ 组装层（案例分流、名称归一、按 clause 精确引用）+ 校验层（条号格式门 + 相关性空档），对应方案见 `status/todo/task077_Review法规依据引用整列损坏治理实施方案_20260816.md`。
