## 模块总览

系统包含五个业务模块，分为两条使用路线：

```
使用路线一（合规路径导向）：
  模块1 路径诊断 ──诊断结论──→ 模块2 安全评估路径
                            └──→ 模块3 认证/标准合同路径

使用路线二（独立工具）：
  模块4 通用服务（TIA/尽调/备忘录等）── 独立入口
  模块5 文档智能审查 ── 独立入口

注：所有模块均可从服务面板独立进入，模块1 是模块2/3 的可选前置引导。
```

## 模块一：合规路径诊断

### 功能目标

帮助企业回答一个核心问题：**我应该走哪条数据出境合规路径？**

中国法律框架下有三条路径：
- 路径一：数据出境安全评估（向网信办申报）
- 路径二：标准合同备案（与境外方签标准合同，向省级网信办备案）
- 路径三：个人信息出境认证（向认证机构申请）

### 用户操作流程

```
用户进入诊断页面
    │
    ▼
回答 Q1：是否为关键信息基础设施运营者（CIIO）？
    │
    ├── 是 → 结论：必须申报安全评估（流程结束）
    └── 否/不确定 → 继续
           │
           ▼
回答 Q2：是否涉及重要数据出境？
    │
    ├── 是 → 结论：必须申报安全评估
    └── 否/不确定 → 继续
           │
           ▼
回答 Q3：累计出境普通个人信息数量？
    │
    ├── >= 100万人 → 结论：必须申报安全评估
    └── < 100万人 → 继续
           │
           ▼
回答 Q4：累计出境敏感个人信息数量？
    │
    ├── >= 1万人 → 结论：必须申报安全评估
    └── < 1万人 → 结论：建议走标准合同备案或认证
           │
           ▼
回答 Q5：出境目的？（预填后续报告字段）
    │
    ▼
生成《合规路径诊断报告》(PDF/HTML)
```

### 工作原理

- **决策引擎**：前端 JavaScript 状态机，所有判定逻辑在浏览器本地执行，不调用后端或 AI
- **为什么不用 AI**：路径判定规则由法律明文规定（CIIO → 安全评估，100万人 → 安全评估），是完全确定性的，不存在模糊地带。使用规则引擎保证了三点：确定性（相同输入必然相同输出）、低延迟（毫秒级响应）、可解释性（每步判定透明可追溯）
- **AI 的唯一使用场景**：最终生成诊断报告文本时，调用 LLM 将规则判定结果转化为自然语言说明，并附加法条引用

### 输出物

《合规路径诊断报告》(PDF/HTML)：用户回答摘要、路径判定结论、法规依据引用、后续行动清单

### 使用的技术

| 层级 | 技术 | 作用 |
|---|---|---|
| 前端 | XState / 自定义状态机 | 决策树节点转移、回退、终态判定 |
| 前端 | React + Zustand | 问答状态管理、回退历史、结果缓存 |
| 前端 | React Hook Form + Zod | 每步问题输入校验 |
| 前端 | DecisionTreeStepper 组件 | 步进式问答 UI（进度条+卡片选项） |
| 后端 | FastAPI + PostgreSQL | 保存诊断会话记录 |
| 后端 | WeasyPrint | 渲染 PDF/HTML 诊断报告 |
| 后端 | Redis + SessionService | 将诊断结果传递给下游模块预填 |
| AI | LLM（腾讯元宝） | 仅用于生成诊断说明文本和条文引用补充 |

## 模块二：安全评估路径（报告生成）

### 功能目标

帮助企业生成**《数据出境风险自评估报告》**，这是向网信办申报安全评估时必须提交的核心文件。

### 用户操作流程

```
1. 填写表单（公司信息、出境场景、数据类型等）
2. 上传业务材料（合同 PDF、数据清单、架构说明等）
3. 点击"生成报告"
4. 等待 AI 生成（30s~2min，实时显示进度）
5. 在线预览报告（分章节展示 + 引用气泡 + 风险标注）
6. 下载 docx 文件 / ZIP 整包
7. 交给律师做最终审核
```

### 工作原理：五步生成流程

```
用户表单 + 上传文件
        │
        ▼
┌──────────────────────────────────────────────┐
│ Step 1: 材料理解                               │
│ 解析上传文件（PDF/Word → 文本）                  │
│ LLM 从文本中抽取关键信息 → 生成结构化企业画像      │
│ 输出：CompanyProfile JSON                      │
│ （公司名/行业/CIIO判定/出境场景/数据类型/规模）    │
└──────────────────┬───────────────────────────┘
                   ▼
┌──────────────────────────────────────────────┐
│ Step 2: 法规检索与匹配                          │
│ 将企业画像转化为法律检索查询                      │
│ 向量检索（语义匹配）+ 全文检索（精确匹配）          │
│ 结果融合（RRF）+ 重排序（Cross-Encoder）          │
│ 得理 API 补充检索 + 来源标注                      │
│ 输出：8~12 条带元数据的法规条文对象                │
└──────────────────┬───────────────────────────┘
                   ▼
┌──────────────────────────────────────────────┐
│ Step 3: 逐章节推理生成                          │
│ 按官方报告模板的 8 个章节，逐章调用 LLM：          │
│ 每章输入 = Prompt模板 + 企业画像 + 相关法规片段     │
│ LLM 生成内容 + 引用链 + 风险标注                  │
│ JSON Schema 约束输出格式                         │
│ 输出：ChapterContent[] JSON                     │
└──────────────────┬───────────────────────────┘
                   ▼
┌──────────────────────────────────────────────┐
│ Step 4: 一致性校验                              │
│ 检查各章节交叉引用是否一致                        │
│ 检查结论与引用依据是否匹配                        │
│ 检查数据量/类型等是否前后一致                      │
│ 标记需人工复核的条目                              │
│ 输出：校验报告 + 复核清单                         │
└──────────────────┬───────────────────────────┘
                   ▼
┌──────────────────────────────────────────────┐
│ Step 5: 渲染与输出                              │
│ 读取官方 docx 模板                              │
│ python-docx 将 JSON 填充到模板对应位置            │
│ 自动生成引用脚注 + 风险批注                       │
│ 输出：最终 docx 文件 + ZIP 打包                   │
└──────────────────────────────────────────────┘
```

### 关键原理

- **为什么分五步而非一步到位**：让 LLM 直接从原始材料生成完整报告，格式不可控、内容难测试、错误难定位。分步执行后，每步产出结构化 JSON 中间态，可自动校验、可断点恢复、可独立评测
- **引用链强制**：Prompt 明确要求每条结论必须引用法规原文，引用为空则降低置信度并标记人工复核
- **门控机制**：AI 不确定时（置信度低、引用为空、涉及敏感判定）必须标记"需人工复核"，而非硬给答案
- **两级编排**：腾讯元器负责五步工作流编排（Tier 1），自建 Python 组件负责各步具体执行（Tier 2）

### 使用的技术

| 层级 | 技术 | 作用 |
|---|---|---|
| 前端 | React Hook Form + Zod + JSON Schema | 多步表单校验与分段提交 |
| 前端 | Zustand | 步骤状态、草稿、上传元信息、生成进度 |
| 前端 | FormWizard / FileUploader / ReportPreview 组件 | 多步表单 + 文件上传 + 报告预览 |
| 前端 | 轮询 / WebSocket | 报告生成进度实时展示 |
| 后端 | FastAPI | 统一 API 入口 |
| 后端 | Celery + Redis | 异步任务调度（报告生成耗时 30s~2min） |
| 后端 | PostgreSQL | 存储表单、企业画像、任务状态 |
| 后端 | MinIO / 腾讯云 COS | 存储上传材料和输出文档 |
| 后端 | python-docx | 生成官方风格 docx 报告 |
| 编排 | 腾讯元器 (Tier 1) | 五步工作流编排与调度 |
| AI | 腾讯元宝 (LLM) | 材料理解、章节推理生成、一致性校验 |
| AI | 自建 RAG 管线 (Tier 2) | 查询改写 + 混合检索 + RRF + Reranker |
| AI | Milvus/Qdrant | 向量检索（语义匹配） |
| AI | Elasticsearch | 全文检索（精确匹配） |
| AI | 得理 API | 补充法规/案例检索 |
| AI | Jinja2 | Prompt 模板渲染 |
| AI | JSON Schema | 结构化输出约束与校验 |

## 模块三：认证 / 标准合同路径（报告生成）

### 功能目标

帮助企业生成**《个人信息保护影响评估报告》(PIPIA)**以及认证自检清单，用于标准合同备案或认证申请。

### 用户操作流程

与模块二基本相同（填表单 → 上传材料 → AI 生成 → 预览下载），差异在于：
- 表单字段侧重认证/标准合同相关信息
- 如果从模块一跳转而来，诊断阶段收集的信息会自动预填

### 工作原理

**与模块二共享同一条五步生成管线**（材料理解→法规检索→逐章生成→一致性校验→渲染输出），差异在于配置层面：

| 差异维度 | 模块二（安全评估） | 模块三（认证/标准合同） |
|---|---|---|
| 输出报告 | 《数据出境风险自评估报告》 | 《个人信息保护影响评估报告》(PIPIA) |
| 报告模板 | 遵循《安全评估申报指南》 | 遵循《标准合同备案指南》 |
| 评估重点 | 国家安全、公共利益风险 | 个人信息权益保护 |
| 法规检索侧重 | 出境评估办法 + 重要数据标准 | 个保法 + 标准合同办法 + GB/T 46068 |
| Prompt 模板 | `prompts/assessment/` | `prompts/scc/` |
| 输出 Schema | 安全评估报告结构 | PIPIA 报告结构 |
| docx 模板 | 安全评估模板 | PIPIA 模板 |

### 关键原理

- **复用底座，独立配置**：底层工具插件（file_parser, rag_search, report_renderer 等）完全复用模块二，但 Schema、Prompt、模板各自独立维护
- **不是复制 AssessmentService 改名字**：而是两个 Service 调用相同的底层组件，各自维护独立的业务配置

### 使用的技术

与模块二完全相同的技术栈（共享底座），区别仅在于业务配置文件（Schema/Prompt/模板）不同。

## 模块四：通用服务（插件化文书生成）

### 功能目标

生成数据跨境合规实务中常用的辅助文书，包括：
- **TIA**（跨境传输影响评估）：评估向特定国家传输数据的风险
- **尽调报告**：对境外数据接收方的合规能力进行调查评估
- **合规备忘录**：汇总合规差距，提出整改建议
- **风险与整改建议清单**：可操作的整改行动计划

### 用户操作流程

```
1. 进入通用服务页面
2. 选择文书类型（TIA / 尽调报告 / 备忘录 / 风险清单）
3. 系统根据文书类型动态加载对应的表单
4. 填写表单 + 上传相关材料
5. 点击"生成"
6. 预览 + 下载 docx 文件
```

### 工作原理：插件化文书生成框架

核心设计是**文书类型只是配置，不是硬编码逻辑**：

```
用户选择文书类型（如 TIA）
        │
        ▼
DocumentTypeRegistry 查找该类型的注册配置
        │
        ├── 输入 Schema (tia_input.json) → 动态渲染表单
        ├── Prompt 模板 (general/tia.*.j2) → 指导 LLM 生成
        ├── 输出 Schema (tia_output.json) → 校验 LLM 输出
        └── docx 模板 (tia.docx) → 渲染最终文件
        │
        ▼
BaseDocumentGenerator 统一管线执行
        │
        ├── 1. 接收用户输入 + 解析文件
        ├── 2. RAG 检索相关法规（按文书类型过滤）
        ├── 3. LLM 推理生成结构化内容
        ├── 4. 风险分级 + 引用链生成
        └── 5. 渲染为 docx 文件
        │
        ▼
最终文书文件 (docx)
```

### 各文书类型的具体原理

**TIA（跨境传输影响评估）**：
1. 用户指定目的地国家 → 2. RAG 检索该国数据保护法律框架 → 3. LLM 对比中国法律与目的地国保护水平 → 4. 输出风险评估 + 补充保护措施建议

**尽调报告**：
1. 用户提供接收方信息/数据保护政策 → 2. RAG 检索该国法律环境 → 3. LLM 按尽调清单逐项评估 → 4. 输出尽调报告 + 风险发现

**合规备忘录 / 风险清单**：
1. 整合用户在本系统中的历史风险发现 → 2. LLM 按"发现→依据→等级→建议→优先级"结构生成清单 → 3. 输出可操作的整改计划

### 关键原理

- **扩展新文书类型无需改代码**：只需准备 JSON Schema + Prompt 模板 + docx 模板 + 在注册表中登记
- **前端也无需改动**：统一的 FormWizard 根据 Schema 动态渲染表单

### 使用的技术

| 层级 | 技术 | 作用 |
|---|---|---|
| 前端 | FormWizard + JSON Schema 驱动 | 根据文书类型动态渲染表单 |
| 后端 | DocumentTypeRegistry | 文书类型注册中心，配置驱动路由 |
| 后端 | BaseDocumentGenerator | 统一生成管线基类（解析→检索→推理→渲染） |
| 后端 | TIA/DD/Memo/GapAnalysis Generator | 各文书类型的 Generator（继承基类） |
| 后端 | FastAPI + Celery | API 入口 + 异步任务调度 |
| 后端 | python-docx | docx 报告渲染 |
| AI | 腾讯元宝 (LLM) | 内容推理生成 |
| AI | 自建 RAG 管线 | 法规检索（按文书类型过滤） |
| AI | Jinja2 + JSON Schema | Prompt 模板 + 结构化输出约束 |

## 模块五：文档智能审查

### 功能目标

对企业现有的法律文件进行**逐条合规审查**，找出合规风险点并给出修改建议。可审查的文件包括：
- 《数据出境标准合同》
- 《隐私政策》
- 《数据处理协议》
- 《云服务协议》

### 用户操作流程

```
1. 上传法律文件（PDF/Word）
2. 等待系统审查（实时显示条款审查进度）
3. 查看审查结果：
   - 左栏：原文结构（条款树）
   - 右栏：该条款的审查意见
   - 点击问题项 → 高亮原文对应位置
   - 按 HIGH/MEDIUM/LOW 筛选问题
4. 导出 docx 格式审查报告
```

### 工作原理：四阶段条款级审查管线

**为什么不把整份文件一次送入 AI**：法律文件通常数十页，LLM 上下文窗口有限且注意力分散。逐条处理保证每个条款都被认真审查，且可以为不同类型的条款匹配不同的审查策略。

```
上传文档
    │
    ▼
┌──────────────────────────────────────────────┐
│ Stage 1: 条款切分 (ClauseSegmenter)            │
│                                               │
│ 按标题编号/段落结构/表格边界切分为独立条款单元     │
│ 保留原文定位信息（页码/段号/条款号）              │
│ 输出：Clause 对象列表                          │
└──────────────────┬───────────────────────────┘
                   ▼
┌──────────────────────────────────────────────┐
│ Stage 2: 条款分类 (ClauseClassifier)           │
│                                               │
│ 识别每条条款的类型：                             │
│ - 数据处理条款（处理目的、范围、方式）             │
│ - 同意与告知条款                                │
│ - 安全措施条款                                  │
│ - 数据出境条款                                  │
│ - 权利行使条款                                  │
│ - 违约责任条款                                  │
│                                               │
│ 目的：不同类型的条款需要对照不同的法规审查         │
└──────────────────┬───────────────────────────┘
                   ▼
┌──────────────────────────────────────────────┐
│ Stage 3: 逐条审查 (ClauseReviewer) -- 可并行    │
│                                               │
│ 对每条条款独立执行：                             │
│ 1. 根据条款类型选择检索过滤条件                   │
│ 2. RAG 检索"该类条款应该包含什么"               │
│ 3. LLM 对比条款内容与法规要求                    │
│ 4. 输出 ReviewIssue：                          │
│    - 条款定位（文件/页码/条款号）                 │
│    - 问题类型（缺失/模糊/冲突/限制过度...）       │
│    - 风险等级（HIGH/MEDIUM/LOW）                │
│    - 法规依据（引用链）                          │
│    - 具体修改建议文本                            │
└──────────────────┬───────────────────────────┘
                   ▼
┌──────────────────────────────────────────────┐
│ Stage 4: 汇总报告 (ReviewAggregator)           │
│                                               │
│ 1. 合并所有条款的审查意见                        │
│ 2. 按风险等级排序（HIGH 优先）                   │
│ 3. 计算总体合规评级                             │
│ 4. 生成优先整改建议排序                          │
│ 5. 渲染为 docx 审查报告                         │
└──────────────────────────────────────────────┘
```

### 关键原理

- **条款分类的价值**：同意条款需对照《个保法》第39条检查告知是否充分，安全措施条款需对照第38条检查保护措施是否到位。分类后可为每类条款精准匹配检索策略和审查 Prompt
- **并行审查**：多个条款同时送入 Stage 3 并发执行，提高吞吐量
- **同类缓存**：同一文档中相同类型条款的法规检索结果可缓存复用
- **渐进返回**：前端通过 WebSocket 逐条接收已完成的审查结果，无需等待全部完成

### 使用的技术

## 贯穿所有模块的核心技术

### RAG（检索增强生成）

所有涉及法规引用的模块（模块2/3/4/5）共享同一套 RAG 管线：

```
查询类型路由 → 查询改写 → 混合检索(向量+全文) → RRF融合 → Reranker重排序
→ 上下文组装 → 得理API补充 → 来源标注 → 审计日志
```

### 结构化中间态

LLM 输出永远先落地为 JSON 对象，再渲染为最终文档。六种核心中间态对象：

| 对象 | 产生环节 | 用途 |
|---|---|---|
| `DiagnosisResult` | 模块一 | 路径判定、法规依据、行动建议 |
| `CompanyProfile` | 模块二/三 Step 1 | 企业画像 |
| `RegulationHit` | 模块二/三/四/五 | 法规命中记录 |
| `ChapterContent` | 模块二/三/四 Step 3 | 报告章节内容 + 引用链 |
| `RiskFinding` | 模块二/三/四 | 风险发现 |
| `ReviewIssue` | 模块五 | 条款审查意见 |

### 引用链与风险分级

- 每条合规结论必须引用法规原文（引用为空 → 标记人工复核）
- 风险三级：HIGH（明确违规/红色）、MEDIUM（灰色地带/黄色）、LOW（基本合规/绿色）
- 门控机制：AI 不确定时必须说"我不确定"，标记人工复核

### 评测框架

三层分离评测：L1 检索层（法规找对了吗）→ L2 抽取层（企业画像抽对了吗）→ L3 生成层（报告质量如何）。用 Golden Set 做回归测试，确保每次修改不引入新问题。
