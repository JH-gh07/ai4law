# 模块⑤新版“双模式合同审查”搭建规划文档

## Summary

模块⑤需要从当前的“文档智能审查 / 单一审查报告输出”升级为**双模式合同审查平台**，目标对齐你提供的更新需求材料与录屏效果：

- `模式A：文本分析 / 审查报告版`
  - 输入合同后，输出标准化《数据出境合同合规审查报告》
  - 不改原文，强调问题、风险、法规依据、修改建议
- `模式B：合同审查 / 批注修订版`
  - 输入合同后，直接在合同文本层面生成修订后的完整合同
  - 输出应尽量贴近“批注修订版”效果，包含正文修订、缺失条款补全、附录补全、可核对的修订痕迹或差异说明

本次规划保持原有总体架构原理不变：
- 模块⑤仍然属于 ReviewService 体系
- 仍然以“条款切分 + 条款级审查 + 聚合输出”为核心底座
- 仍然使用 RAG + LLM 协同，但从“单一分析输出”扩展为“分析链路”和“改写链路”两条编排分支
- 前端体验升级为更接近录屏中的“合同审查工作台”，增加 `适用场景 / 审查立场 / 自定义规则 / 模式切换`

## Key Changes

### 1. 产品形态升级为“双模式合同审查工作台”
- 模块⑤入口仍为独立入口，但进入后不再只是“上传文档 -> 出报告”。
- 新版页面需具备以下输入项：
  - 合同文件上传
  - `适用场景`
    - 首版至少支持：`通用合同`、`个人信息出境标准合同`、`数据处理协议`、`隐私政策/规则`
  - `审查立场`
    - `甲方`
    - `乙方`
  - `自定义审查规则`
    - 可选预设规则包
    - 可附加自由文本规则
  - `输出模式`
    - `审查报告版`
    - `批注修订版`
- 结果页需根据模式切换两种视图：
  - 审查报告视图
  - 修订合同 / 差异视图

### 2. 后端从单链路 ReviewService 升级为双链路 Review Orchestrator
- 现有 `ReviewService` 保留为底座，但改造成统一编排器，内部拆成共享阶段 + 模式分支：
  - 共享阶段
    - `DocumentParser`
    - `ClauseSegmenter`
    - `ClauseClassifier`
    - `ClauseKnowledgeRetriever`
    - `IssueExtractor`
    - `ReviewAggregator`
  - 模式A 分支
    - `ReviewReportBuilder`
    - 输出结构化审查报告
  - 模式B 分支
    - `ClauseRevisionPlanner`
    - `ClauseRewriter`
    - `DocumentRecomposer`
    - `RevisionDiffBuilder`
    - 输出修订版合同及差异说明
- 关键原则：
  - 两种模式共享同一份条款切分、分类、法规检索和问题识别结果，避免重复计算
  - `批注修订版` 不是“重新从头生成整份合同”，而是基于原合同条款单元做“定位 -> 诊断 -> 定向改写 -> 重新拼装”
  - 附录属于独立子文档单元，必须纳入同一条款图谱和重组流程，不能只处理正文

### 3. 核心中间态升级

- 现有模块五的中间态需要扩展为以下对象：
  - `ReviewWorkspace`
    - 本次审查会话的统一上下文，包含文件元数据、模式、立场、规则包、解析结果
  - `Clause`
    - 条款单元，需支持正文 / 附录 / 表格 / 标题层级
  - `ClassifiedClause`
    - 增加 `section_type`、`appendix_id`、`party_bias`
  - `ReviewIssue`
    - 模式A/B共享的问题对象，至少包含：
      - 条款定位
      - 问题类型
      - 风险等级
      - 法规依据
      - 审查立场相关性
      - 修改建议
  - `RevisionInstruction`
    - 只用于模式B
    - 描述该条款是“保留 / 局部修改 / 整段重写 / 新增条款 / 新增附录”
  - `RevisedClause`
    - 改写后的条款文本
  - `ReviewReport`
    - 模式A最终结构化报告
  - `RevisedContractArtifact`
    - 模式B最终合同文件 + 差异信息

### 4. 新版 pipeline 设计

#### 模式A：文本分析 / 审查报告版
- `Step 1: 文件解析`
  - 解析 docx/pdf
  - 保留页码、段号、条号、附录结构
- `Step 2: 条款切分与结构建模`
  - 将合同拆为正文条款、附录条款、表格项
  - 构建合同结构树
- `Step 3: 条款分类`
  - 判断条款属于：定义、处理范围、告知、同意、安全措施、第三方共享、跨境条款、权利行使、责任、争议解决、附录说明等
- `Step 4: 规则/法规检索`
  - 根据合同类型、场景、条款类别、审查立场、自定义规则进行检索
- `Step 5: 问题识别`
  - 逐条识别缺失、模糊、冲突、限制过度、监管要求缺位、备案义务缺失、PIA 要素缺失等问题
- `Step 6: 聚合与排序`
  - 按风险等级排序
  - 计算总体合规评级
  - 汇总重点整改建议
- `Step 7: 审查报告渲染`
  - 输出标准化审查报告 docx
  - 支持前端结构化展示

#### 模式B：合同审查 / 批注修订版

- `Step 1~5`
  - 复用模式A的共享链路，先得到结构树、问题对象和法规依据
- `Step 6: 修订策略生成`
  - 对每个问题生成 `RevisionInstruction`
  - 决定是补一句、替换整条、插入新条、生成附录补充
- `Step 7: 条款级改写`
  - 在保留原合同主体结构前提下，逐条生成修订版文本
  - 改写时必须受以下约束：
    - 保持原合同条款编号体系尽量稳定
    - 不擅自删除商业背景信息
    - 对缺失内容优先“新增补充”而非全盘重写
    - 附录按独立模板补足
- `Step 8: 合同重组`
  - 将修订后的正文、附录、补充条款重新拼接为完整合同
- `Step 9: 差异输出`
  - 至少输出一种可核对形式：
    - 逐条“原文 / 修订后 / 修订理由”
  - 若后续支持真正 Word 批注或修订模式，可作为增强项
- `Step 10: 修订版文档渲染`
  - 输出 `.docx`
  - 同时输出结构化差异 JSON 供前端展示

### 5. 审查立场与自定义规则的实现
- `审查立场（甲方/乙方）` 不是 UI 装饰项，必须进入检索与审查逻辑：
  - 同一条款在甲方视角可能判定为“权利保护不足”
  - 在乙方视角可能判定为“责任过重”或“义务失衡”
- `自定义规则` 分为两层：
  - 预设规则包
    - 例如：`数据出境标准合同备案重点`、`甲方风险优先`、`乙方谈判优化`
  - 自定义文本规则
    - 进入检索过滤和 Prompt 上下文
- 这意味着中间态和 API 必须显式携带：
  - `contract_type`
  - `review_stance`
  - `custom_rule_set_ids`
  - `custom_rule_text`

### 6. API 与接口契约升级
- 在保持现有 `/review/tasks` 主资源不变前提下，接口应升级为：
  - `POST /api/v1/review/tasks`
    - 新增请求字段：`review_mode`、`contract_type`、`review_stance`、`custom_rule_text`、`custom_rule_ids`
  - `POST /api/v1/review/tasks/{id}/files`
  - `POST /api/v1/review/tasks/{id}/analyze`
    - 可保留，但内部根据 `review_mode` 分流
  - `GET /api/v1/review/tasks/{id}/status`
  - `GET /api/v1/review/tasks/{id}/issues`
  - `GET /api/v1/review/tasks/{id}/report`
    - 对模式A返回 `ReviewReport`
  - `GET /api/v1/review/tasks/{id}/revised-contract`
    - 对模式B返回修订版文档元数据
  - `GET /api/v1/review/tasks/{id}/diff`
    - 返回结构化差异数据
  - `WS /api/v1/review/ws/tasks/{id}`
    - 进度与阶段更新
- 关键公开类型新增：
  - `ReviewMode`
  - `ContractType`
  - `ReviewStance`
  - `CustomRuleInput`
  - `RevisionInstruction`
  - `RevisedClause`
  - `RevisionDiffItem`
  - `RevisedContractResponse`

### 7. 与现有模块五原理的一致性要求
- 必须保留的原理：
  - 按条款处理，而不是整份合同一次性丢给 AI
  - RAG 按条款类型检索法规
  - 审查结果必须能定位到原文
  - 输出必须带法规依据和建议
- 升级后的变化：
  - 从单输出形态升级为双输出形态
  - 从“条款问题清单”扩展到“条款问题清单 + 条款改写计划 + 完整合同重组”
  - 从“单一审查上下文”扩展到“合同类型 + 审查立场 + 自定义规则”的多维上下文

## Test Plan

- `输入配置测试`
  - `review_mode` 为 `REPORT` / `REDLINE` 两种模式都能创建任务
  - `contract_type`、`review_stance`、`custom_rule_text` 正确入库并进入任务上下文
- `共享底座测试`
  - 同一份合同可成功解析为正文 + 附录结构
  - 条款切分保留条号、附录编号、原文位置
  - 条款分类覆盖至少：定义、跨境、第三方、PIA、备案、权利、责任、附录
- `模式A 测试`
  - 能输出标准化审查报告
  - 报告必须包含：
    - 文件概要
    - 审查依据
    - 总体合规评级
    - 条款级问题清单
    - 风险分析
    - 法规依据
    - 修改建议
- `模式B 测试`
  - 能输出完整修订版合同 docx
  - 能处理正文与附录，不只改正文
  - 输出同时附带结构化差异数据
  - 对同一个问题，修订动作可追溯到原条款
- `立场差异测试`
  - 同一输入合同在 `甲方` / `乙方` 视角下，至少部分问题排序或建议内容发生变化
- `规则增强测试`
  - 自定义规则文本会进入最终问题识别与建议输出
  - 预设规则包会影响检索过滤或 Prompt 指令
- `回归样例`

- `验收标准`
  - 模式A能稳定复现“审查报告版”的核心效果
  - 模式B能产出“可核对、可继续修改、包含附录”的完整修订合同
  - 前端工作台的输入项与录屏中的主要控制项对齐

## Assumptions

- “达到视频中的效果”解释为：产品形态、输入控制项、双模式输出能力、结果呈现方式与录屏方向一致；不要求首版 1:1 复制第三方产品 UI。
- 本轮规划覆盖双模式都做，但工程上优先级应为：
  - 先把共享底座与模式A做稳定
  - 再在同一底座上扩展模式B
- 批注修订版首版可接受“结构化差异 + 重组合同文档”，不强制要求完全等同 Word 原生修订痕迹；若后续需要真正批注/修订显示，可作为增强项单独实现。
- 审查报告版仍是更容易稳定交付的主线能力；批注修订版是新版模块五的关键增强能力，但实现复杂度显著更高。
- 若视频中的某些交互细节与现有项目文档冲突，以“模块五双模式合同审查平台”的能力目标为准，不改变系统总架构的四层分层与 ReviewService 主体定位。
