## 1 系统总览

### 1.1 一句话定位

基于 AI 大模型的数据跨境合规自动检测与风险评估工具 -- 将企业非结构化业务材料转化为可直接用于监管申报的标准化合规资产。

### 1.2 高层架构图（四层）

```
┌─────────────────────────────────────────────────────────────────┐
│                        表现层 Presentation                       │
│  科普首页 │ 场景选择 │ 路径诊断 │ 报告生成 │ 文档审查 │ 报告预览  │
└──────────────────────────┬──────────────────────────────────────┘
                           │  HTTP / WebSocket
┌──────────────────────────▼──────────────────────────────────────┐
│                      应用服务层 Application                      │
│  路径诊断引擎 │ 报告生成引擎 │ 文档审查引擎 │ 通用服务引擎       │
│  用户会话管理 │ 文件处理服务 │ 导出与打包服务                     │
└──────────────────────────┬──────────────────────────────────────┘
                           │  内部 RPC / 消息队列
┌──────────────────────────▼──────────────────────────────────────┐
│                     AI 推理层 AI Engine                          │
│  LLM 编排器(Agent) │ RAG 检索管线 │ Prompt 模板库 │ 引用链生成器 │
│  结构化输出解析器  │ 风险分级器    │ 置信度评估器                 │
└──────────────────────────┬──────────────────────────────────────┘
                           │  向量检索 / 全文检索
┌──────────────────────────▼──────────────────────────────────────┐
│                      数据层 Data                                 │
│  法规知识库 │ 案例库 │ 模板库 │ 信源管理 │ 用户会话存储 │ 文件存储 │
└─────────────────────────────────────────────────────────────────┘
```

### 1.3 核心设计原则

| 原则 | 说明 |
|---|---|
| 可追溯 | 每条合规结论必须回指到法规条文、指南原文或案例要点，形成完整引用链 |
| 结构化 | 所有输出（报告、审查结果）均先以 JSON Schema 约束，再渲染为 docx/PDF |
| 分层解耦 | 表现层、应用层、AI 层、数据层严格分离，便于独立迭代与替换 |
| 门控安全 | 对不确定/高风险结论强制降低置信度，标记"建议人工复核" |
| 多法域可扩展 | 以中国框架为 P0 打穿，架构上预留欧盟/美国/英国法域扩展槽位 |

## 3 表现层（Frontend）

### 3.1 技术选型

| 项目 | 选择 | 理由 |
|---|---|---|
| 框架 | React 18 + Next.js 14 (App Router) | SSR/SSG 优化首屏加载，适合科普页面 SEO |
| UI 组件库 | Ant Design 5 / shadcn/ui | 表单密集场景成熟；或轻量可定制 |
| 状态管理 | Zustand | 轻量、适合中等复杂度 |
| 状态机 | XState / 轻量自定义状态机 | 路径诊断决策树、多步表单流程的显式状态建模，比 if/else 更清晰可维护 |
| 表单引擎 | React Hook Form + Zod + JSON Schema 驱动 | 复杂表单校验 + 声明式表单定义（表单结构与渲染分离，新增文书类型只需配置 Schema） |
| 文件上传 | 分片上传 + 进度条 | 支持大文件（合同PDF等） |
| 文档预览 | react-docx-preview / PDF.js | 在线预览生成的报告 |

### 3.2 页面结构

```
/                           → 首页（科普 + 法域场景选择）
/jurisdiction/cn            → 中国大陆→境外 服务面板（五大模块入口）
/jurisdiction/cn/diagnosis  → 合规路径诊断（动态问答流）
/jurisdiction/cn/assessment → 安全评估路径（表单+上传+报告生成）
/jurisdiction/cn/scc        → 认证/标准合同路径（表单+上传+报告生成）
/jurisdiction/cn/general    → 通用服务（TIA/尽调/备忘录）
/jurisdiction/cn/review     → 文档智能审查（上传+审查报告）
/report/:id                 → 报告在线预览与下载
```

### 3.3 关键交互设计

**路径诊断模块**：采用步进式问答（Stepper），顶部进度条显示当前题号，支持前进/后退，选项以卡片式 RadioGroup 呈现，底部灰色小字提供法律术语 Tooltip 释义。问答逻辑由前端状态机驱动（决策树），无需每步请求后端。

**表单收集模块**：采用多步表单（Multi-step Form），左侧导航显示填写进度，支持"暂存草稿"（localStorage + 服务端持久化），文件上传区支持拖拽 + 格式校验 + 进度展示。

**报告预览模块**：分章节可折叠展示，每段结论旁附"引用来源"气泡，点击可展开法规原文；提供"下载 docx"和"下载 ZIP 整包"按钮。

### 3.4 Schema-Driven 表单系统

五个模块的表单需求各异，但共享同一套表单基础设施。借鉴 PAR-DPIA Form 项目的声明式配置思路，采用 **Schema 驱动表单**架构：

```
表单定义层                      表单渲染层
──────────                    ──────────
diagnosis-schema.json          ┌──────────────────┐
assessment-schema.json    ───> │  FormWizard 组件   │ ───> 动态渲染表单
scc-schema.json                │  (统一渲染引擎)     │
general-tia-schema.json        └──────────────────┘
general-memo-schema.json
```

每种文书类型的表单由独立的 JSON Schema 文件定义字段、校验规则、步骤分组和条件跳转逻辑。新增文书类型时只需添加 Schema 配置文件，无需修改前端渲染代码。

### 3.5 共用前端组件

五个模块共享以下基础 UI 组件，在各模块页面中按需组合：

| 组件 | 职责 | 使用模块 |
|---|---|---|
| `FormWizard` | 多步表单渲染引擎，支持步骤导航、暂存/恢复、条件跳转 | 全部模块 |
| `FileUploader` | 分片上传、格式校验、进度展示、拖拽支持 | 安全评估、认证/SCC、文档审查 |
| `ReportPreview` | 分章节可折叠报告预览、引用气泡、下载按钮 | 安全评估、认证/SCC、通用服务 |
| `CitationBubble` | 法规引用悬浮卡片，点击展开法规原文与元数据 | 全部报告/审查模块 |
| `RiskBadge` | 风险等级标签（HIGH/MEDIUM/LOW），颜色编码 + 图标 | 全部报告/审查模块 |
| `DecisionTreeStepper` | 决策树步进器，进度条 + 选项卡片 + 返回支持 | 路径诊断 |

## 4 应用服务层（Backend）

### 4.1 技术选型

| 项目 | 选择 | 理由 |
|---|---|---|
| 运行时 | Python 3.11+ / FastAPI | AI 生态丰富，异步支持好，适合 LLM 调用 |
| 任务队列 | Celery + Redis | 报告生成为耗时任务（30s~2min），需异步处理 |
| 文件处理 | python-docx / WeasyPrint | 生成 docx 报告 + PDF 导出 |
| 文件解析 | PyMuPDF / pdfplumber / python-docx | 解析用户上传的 PDF/Word 合同与材料 |
| 对象存储 | MinIO / 腾讯云 COS | 存储用户上传文件与生成的报告文件 |
| 数据库 | PostgreSQL 15 | 结构化业务数据（用户、会话、报告元数据） |
| 缓存 | Redis | 会话上下文缓存、诊断状态暂存、任务状态 |
| API 文档 | FastAPI 自动生成 OpenAPI 3.0 | 前后端联调与第三方对接 |

│   ├── 材料解析编排            # 调度文件解析 → 文本提取 → 分块
│   └── 报告生成编排            # 调度 AI 推理层 → 结构化输出 → docx 渲染

### 4.3 通用服务插件化架构

GeneralService 采用**插件化文书生成框架**，每种文书类型作为配置注册，而非硬编码接口。扩展新文书类型时只需注册一组配置，无需修改核心代码。

```
文书类型注册表（DocumentTypeRegistry）

┌───────────────┬──────────────────┬─────────────────┬──────────────────┬───────────────┐
│   文书类型      │   输入 Schema     │   输出 Schema    │   Prompt 模板     │   docx 模板    │
├───────────────┼──────────────────┼─────────────────┼──────────────────┼───────────────┤
│ TIA           │ tia_input.json   │ tia_output.json │ general/tia.*   │ tia.docx      │
│ 尽调报告       │ dd_input.json    │ dd_output.json  │ general/dd.*    │ dd.docx       │
│ 合规备忘录     │ memo_input.json  │ memo_output.json│ general/memo.*  │ memo.docx     │
│ 风险清单       │ gap_input.json   │ gap_output.json │ general/gap.*   │ gap.docx      │
│ (未来扩展...)  │ ...              │ ...             │ ...             │ ...           │
└───────────────┴──────────────────┴─────────────────┴──────────────────┴───────────────┘
```

每类文书共享 `BaseDocumentGenerator` 提供的统一管线（文件解析 → 法规检索 → LLM 推理 → 风险分级 → 报告渲染），但各自拥有独立的输入/输出 Schema、Prompt 模板和 docx 模板。未来新增文书类型仅需：(1) 编写 Schema 文件；(2) 编写 Prompt 模板；(3) 准备 docx 模板；(4) 在注册表中登记。

### 4.4 API 设计概要

所有接口均遵循 RESTful 风格，核心资源与路由划分如下：

```

GET    /api/v1/assessment/tasks/{id}/status       # 查询生成进度
GET    /api/v1/assessment/tasks/{id}/report       # 获取报告（预览/下载）

# 认证/标准合同路径

GET    /api/v1/general/tasks/{id}/report         # 获取报告

# 文档智能审查
POST   /api/v1/review/tasks                      # 创建审查任务
POST   /api/v1/review/tasks/{id}/files           # 上传待审查文档
POST   /api/v1/review/tasks/{id}/analyze         # 触发审查（异步）

### 4.5 异步任务与进度反馈

报告生成属于耗时操作（涉及多轮 LLM 调用），采用异步任务模式：

```
前端                    后端 API                Celery Worker           AI 推理层
 │                        │                        │                      │
 │  POST /generate        │                        │                      │
 │───────────────────────>│  创建 task_id           │                      │
 │<───────────────────────│  返回 task_id           │                      │
 │                        │───────────────────────>│  入队执行              │
 │  GET /status (轮询)    │                        │                      │
 │───────────────────────>│  查 Redis 任务状态      │                      │
 │<───────────────────────│  progress: 40%         │                      │
 │                        │                        │─────────────────────>│
 │                        │                        │  多轮 LLM 调用       │
 │                        │                        │<─────────────────────│
 │                        │                        │  更新进度 → Redis     │
 │  GET /status           │                        │                      │
 │───────────────────────>│  progress: 100%        │                      │
 │<───────────────────────│  status: completed     │                      │
 │  GET /report           │                        │                      │
 │───────────────────────>│  返回报告              │                      │
 │<───────────────────────│                        │                      │
```

进度分阶段上报：材料解析(10%) → RAG检索(30%) → LLM推理(70%) → 报告渲染(90%) → 完成(100%)。

## 5 AI 推理层（AI Engine）

### 5.1 整体架构与编排分层

AI 推理层采用**两级编排**架构：顶层由腾讯元器负责工作流编排与外部插件调度，底层由自建 Python 组件负责细粒度的数据处理、检索、推理与输出解析。

```
┌──────────────────────────────────────────────────────────────────┐
│                          AI 推理层                                │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │          Tier 1: 元器工作流编排（顶层调度）                 │    │
│  │  ┌────────────┐  ┌─────────────┐  ┌──────────────────┐  │    │
│  │  │ 工作流节点  │  │ 得理API插件  │  │ 自建工具插件      │  │    │
│  │  │ (Step编排)  │  │ (法规/案例   │  │ (RAG/文件解析/   │  │    │
│  │  │            │  │  智能检索)   │  │  报告渲染)       │  │    │
│  │  └────────────┘  └─────────────┘  └──────────────────┘  │    │
│  └──────────────────────────┬───────────────────────────────┘    │

**两级职责划分**：

| 层级 | 承担者 | 职责 | 不做什么 |
|---|---|---|---|
| Tier 1 顶层编排 | 腾讯元器 | 定义多步工作流（Step 1→2→3→4→5）；调度得理 API 插件获取法规/案例；调用自建工具插件执行具体任务；管理步骤间的数据流转 | 不做文件解析、不做报告渲染、不做复杂 RAG 细节 |
| Tier 2 执行层 | 自建 Python | RAG 检索管线（查询改写/混合检索/重排序）；结构化输出解析与校验；引用链生成与风险分级；文件解析（PDF/Word → 文本）；报告渲染（JSON → docx） | 不做顶层步骤编排（交给元器） |

这种分层的好处：元器提供可视化的工作流编排界面，便于法学团队理解和调整流程顺序；自建组件处理元器无法覆盖的细粒度逻辑；同时满足比赛对腾讯工具链展示的要求。

### 5.2 元器工作流设计（Tier 1）

以"安全评估报告生成"为例，元器中配置的工作流：

```
元器工作流：安全评估报告生成

Step 1: 材料理解（调用自建工具插件）
  输入 → 企业基本信息 + 上传文件文本
  工具 → file_parser + profile_extractor
  输出 → 结构化企业画像（行业、规模、数据类型、出境场景摘要）

Step 2: 法规检索与匹配（调用得理API插件 + 自建RAG工具）
  输入 → 企业画像 + 出境场景
  工具 → 得理API插件（案例/法规检索）+ rag_search（自建向量+全文混合检索）
  输出 → 候选法规片段集合（含来源定位）

Step 3: 逐章节推理生成（调用自建工具插件，循环执行）
  遍历报告模板的每个章节：
    输入 → 章节模板要求 + 企业画像 + 相关法规片段
    工具 → chapter_generator（内部调用 LLM + 引用链生成器 + 风险分级器）
    输出 → 章节内容（结构化 JSON）+ 引用链 + 风险标注
    约束 → 必须引用至少一条法规/指南，否则降低置信度

Step 4: 一致性校验（调用自建工具插件）
  输入 → 全部章节的结构化输出
  工具 → consistency_checker
  输出 → 校验报告 + 需人工复核的标记列表

Step 5: 渲染与输出（调用自建工具插件）
  输入 → 校验通过的结构化 JSON
  工具 → report_renderer（python-docx 渲染）
  输出 → 最终报告文件（docx）
```

元器工作流中的每个 Step 通过"工具插件"（Tools/Plugins）调用自建 Python 后端暴露的 API 接口，实现编排层与执行层的解耦。

### 5.3 自建 Python 执行层（Tier 2）

自建组件以 FastAPI 接口形式暴露给元器调用，同时也可被后端应用层直接调度（如异步任务场景）。

**LLM 适配层**：优先使用腾讯元宝（比赛要求），通过统一接口封装，预留切换其他模型的能力：

```python
class LLMAdapter:
    async def complete(
        self,
        messages: list[Message],
        schema: JSONSchema | None,    # 结构化输出约束
        temperature: float = 0.1,     # 法律场景低温度
        max_tokens: int = 4096,
        retry: int = 3,               # 失败重试次数
    ) -> LLMResponse
```

**错误处理与重试策略**：

| 异常场景 | 处理方式 |
|---|---|
| LLM 调用超时/网络错误 | 指数退避重试（最多3次），超限后标记该章节为"生成失败，需人工补充" |
| 结构化输出 JSON 解析失败 | 自动追加格式约束提示后重试；3次仍失败则降级为纯文本输出 + 人工复核标记 |
| RAG 检索返回空结果 | 扩大检索范围（放宽阈值）重试一次；仍为空则标记"未找到相关法规依据"并降低置信度 |
| 得理 API 不可用 | 降级为仅使用自建知识库检索，在报告中标注"部分检索来源暂不可用" |
| 报告生成中途失败 | 记录已完成的章节，支持断点恢复（从失败章节重新开始） |

### 5.4 RAG 检索管线

```
用户查询/企业画像
       │
       ▼
┌──────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  查询类型路由  │────>│  查询改写     │────>│  混合检索     │────>│  重排序       │
│  QueryType   │     │  Query       │     │  Hybrid      │     │  Reranker    │
│  Router      │     │  Rewrite     │     │  Search      │     │              │
└──────────────┘     └──────────────┘     └──────────────┘     └──────┬───────┘
                                                                      │
                      ┌───────────────────────────────────────────────┘
                      ▼
               ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
               │  上下文组装   │────>│  来源标注     │────>│  审计日志记录  │
               │  Context     │     │  Citation    │     │  Retrieval   │
               │  Assembly    │     │  Tagging     │     │  Audit Log   │
               └──────────────┘     └──────────────┘     └──────────────┘
```

**查询类型路由（QueryType Router）**：

不同业务场景的检索需求差异显著，系统根据查询来源自动路由到不同的检索策略（参考 Legal-RAG 的 query-type routing 思路）：

| 查询类型 | 来源模块 | 检索策略差异 |
|---|---|---|
| 路径判断类 | 路径诊断 | 以全文检索为主（精确命中数量门槛条款），向量检索为辅；过滤标签：法域=中国, 主题=出境条件 |
| 报告生成类 | 安全评估/SCC | 向量+全文均衡混合；按章节需求动态调整检索关键词；过滤标签：法域+路径+报告章节 |
| 条款审查类 | 文档审查 | 以向量检索为主（条款语义匹配），补充全文精确查找；过滤标签：文书类型（标准合同/隐私政策/DPA） |
| 整改建议类 | 通用服务 | 扩大检索范围（含行业标准/最佳实践/案例），降低 Top-K 阈值以提高召回 |

**元数据过滤**：

所有检索请求均支持按以下元数据标签预过滤，避免跨法域/跨路径的噪声结果：

| 过滤维度 | 可选值 | 说明 |
|---|---|---|
| 法域 | `cn`, `eu`, `us`, `uk`, ... | 限定目标法律体系 |
| 路径 | `assessment`, `scc`, `certification` | 限定合规路径相关法规 |
| 文书类型 | `regulation`, `guideline`, `case`, `standard` | 限定知识类型 |
| 权威性等级 | `official`, `authoritative`, `reference` | 按可靠度筛选 |
| 时效性 | 按生效日期范围过滤 | 排除已废止/未生效的法规 |

**检索策略细节**：

| 阶段 | 方法 | 说明 |
|---|---|---|
| 查询改写 | LLM 将用户业务描述转化为法律检索查询 | 补充法律术语同义词，拆分多意图查询 |
| 向量检索 | Embedding + 余弦相似度，Top-K=20 | 语义匹配，捕获意图相近的法规条文 |
| 全文检索 | BM25 关键词匹配，Top-K=20 | 精确匹配法条编号、专有名词 |
| 混合融合 | RRF (Reciprocal Rank Fusion) | 合并向量与全文结果，去重排序 |
| 重排序 | Cross-Encoder Reranker，Top-K=8 | 精排，提升与查询最相关的法规片段 |
| 上下文组装 | 父条文回溯 + 关联条文扩展 | 保留法规条文的层级上下文（条→款→项），并加载交叉引用条文 |
| 来源标注 | 为每个片段附加元数据 | 法规名称、条文编号、发布日期、来源URL |

**可审计检索**：

每次检索均完整记录以下信息，支持事后审计和检索质量分析：

```
RetrievalAuditLog {
  query_id, timestamp, query_type,
  original_query, rewritten_queries,
  metadata_filters,
  vector_results: [{article_id, score}],
  fulltext_results: [{article_id, score}],
  rrf_merged: [{article_id, combined_score}],
  reranked_final: [{article_id, reranker_score}],
  deli_api_results: [{article_id, source}],
  total_candidates, final_count
}
```

**得理 API 集成**：通过得理开放平台 API（元器插件）进行案例与法规的智能检索，作为自建知识库的补充信源。调用链路：

```
RAG 管线 → 得理 API 插件（元器） → 返回法规/案例片段 → 去重合并入检索结果集
```

### 5.7 风险分级与门控

**风险三级标准**：

| 等级 | 触发条件 | 系统行为 |
|---|---|---|
| HIGH | 明确违反现行法规、缺失必要合规步骤、涉及重要数据/敏感个人信息 | 标红高亮 + 强制标记"需人工复核" |
| MEDIUM | 法规适用存在灰色地带、行业标准尚不明确、企业信息不完整 | 标黄提示 + 建议补充信息或咨询律师 |
| LOW | 已满足基本合规要求、仅有优化空间 | 绿色标记 + 给出最佳实践建议 |

**门控触发规则**：当满足以下任一条件时，系统自动标记"建议人工复核"：
- 引用链为空（无法找到支撑依据）
- 置信度低于 0.7
- 涉及"重要数据"认定（法律定义模糊）
- 涉及"出境必要性"判断（需业务上下文）
- 多条法规结论冲突

## 6 统一 JSON Schema 中间态层

系统在各模块间、以及 AI 推理层与报告渲染层之间，采用**统一的 JSON Schema 中间态**作为数据交换契约。所有 LLM 输出必须先填充为结构化 JSON 对象，校验通过后再渲染为 docx/PDF 交付物。这一设计确保了输出的可预测性、可测试性和可审计性。

### 6.1 核心中间态对象定义

```
CompanyProfile               企业画像
├── company_name             公司名称
├── industry                 所属行业
├── is_ciio                  是否 CIIO
├── data_exit_scenarios[]    出境活动列表
│   ├── scenario             场景描述
│   ├── data_types[]         数据类型列表
│   ├── data_volume          数据量（人数）
│   ├── sensitive_data       是否含敏感个人信息
│   ├── receiver             境外接收方
│   ├── receiver_country     接收方所在国
│   ├── purpose              出境目的
│   └── legal_basis          合法性基础
├── important_data_involved  是否涉及重要数据
└── diagnosis_id             关联的诊断会话 ID（可选）
```

```
RegulationHit                法规检索命中
├── article_id               条文级对象 ID（关联 RegulationArticle）
├── source_type              类型（regulation/guideline/case/standard）
├── title                    法规名称
├── article_number           条文编号（如"第三十八条第一款"）
├── quote                    命中原文摘录
├── relevance_score          检索相关性得分
├── retrieval_method         检索来源（vector/fulltext/deli_api）
├── publish_date             发布日期
└── url                      来源 URL
```

```
ChapterContent               报告章节内容
├── chapter_id               章节序号
├── chapter_title            章节标题
├── content                  正文内容（结构化文本）
├── citations[]              引用链（RegulationHit 列表）
├── risk_findings[]          本章节风险发现列表
│   ├── finding_id           发现 ID
│   ├── description          风险描述
│   ├── risk_level           风险等级（HIGH/MEDIUM/LOW）
│   ├── confidence           置信度（0~1）
│   ├── supporting_citations 支撑引用
│   ├── needs_human_review   是否需人工复核
│   └── review_reason        复核原因
└── metadata                 章节元数据（生成耗时、LLM token 用量等）
```

```
ReviewIssue                   审查意见对象
├── issue_id                 意见 ID
├── clause_location          条款定位（文件名/章节/页码/条款号）
├── original_text            原文摘录
├── issue_type               问题类型（缺失条款/定义模糊/责任限制过度/与法规冲突/与实践不一致）
├── risk_level               风险等级（HIGH/MEDIUM/LOW）
├── risk_analysis            风险分析说明
├── legal_basis[]            法规依据（RegulationHit 列表）
├── suggestion               修改建议
├── suggested_text           建议修改文本（可选）
└── confidence               置信度
```

### 6.2 中间态流转路径

```
模块入口                   中间态对象                 最终交付物
────────                 ──────────                ────────
路径诊断问答      ───>   DiagnosisResult JSON     ───>  诊断报告 PDF/HTML
安全评估表单+文件  ───>   CompanyProfile JSON      ───>
                         + RegulationHit[] JSON   ───>
                         + ChapterContent[] JSON  ───>  自评估报告 docx
认证/SCC 表单+文件 ───>   CompanyProfile JSON      ───>
                         + ChapterContent[] JSON  ───>  PIPIA 报告 docx
通用服务表单       ───>   场景画像 JSON             ───>  TIA/尽调/备忘录 docx
文档审查上传       ───>   ReviewIssue[] JSON       ───>  审查报告 docx
```

每层转化均有明确的 JSON Schema 约束，LLM 输出如不符合 Schema 则触发重试或降级处理。中间态 JSON 同时持久化到数据库，支持：
- 断点恢复（任务中断后从最后完成的中间态继续）
- 人工修正（律师可修改中间态 JSON 后重新渲染报告）
- 版本对比（同一任务多次生成的中间态可 diff 比较）
- 评测度量（中间态 JSON 可作为评测输入，自动化计算质量指标）

`RegulationArticle` 是知识库的核心实体，以**法条**为最小单位存储，而非固定 token 长度的 chunk。每条法规条文作为独立对象，保留完整的层级路径（编→章→节→条→款→项）和丰富元数据，支持精确的条文级检索与引用。

`DocumentTemplate` 将文书模板配置化，每种文书类型对应一条注册记录，包含输入/输出 Schema、Prompt 模板路径和 docx 模板路径，支持通用服务模块的插件化架构。

`ReviewFinding` 存储文档审查的逐条发现结果，与 Section 6 中定义的 `ReviewIssue` JSON Schema 对应。

### 7.4 法规文档处理管线

法规原文入库采用**条文级对象化**处理（参考 Legal-RAG 的 statute-centric 设计），以法条为最小单位生成 `RegulationArticle` 对象：

```
原始文档（PDF/Word/HTML）
      │
      ▼
┌──────────────┐
│ 1.格式归一化  │  统一转为 Markdown/纯文本
└──────┬───────┘
       ▼
┌──────────────┐
│ 2.条文级切分  │  按"法规 → 编/章/节 → 条 → 款 → 项"层级切分
│              │  每个条文生成独立的 RegulationArticle 对象
│              │  保留完整层级路径（如：个保法 → 第四章 → 第三十八条 → 第一款）
└──────┬───────┘
       ▼
┌──────────────┐
│ 3.元数据标注  │  法规名称、简称、发布机关、发布/生效日期、条文编号
│              │  适用主题标签（如：出境条件、同意告知、安全措施）
│              │  权威性等级（OFFICIAL / AUTHORITATIVE / REFERENCE）
│              │  交叉引用解析（条文中"依照本法第X条"→ 关联目标条文 ID）
└──────┬───────┘
       ▼
┌──────────────┐
│ 4.交叉引用    │  解析条文间的引用关系，构建法条引用图
│   图构建      │  支持检索时沿引用链扩展关联条文
└──────┬───────┘
       ▼
┌──────────────┐
│ 5.双重索引    │
│  ┌─────────┐ │  每个 RegulationArticle：
│  │向量索引  │ │  → 生成 Embedding，写入 Milvus/Qdrant（语义检索）
│  └─────────┘ │
│  ┌─────────┐ │
│  │全文索引  │ │  → 写入 Elasticsearch（条文编号精确查询 + 关键词高亮）
│  └─────────┘ │
└──────────────┘
```

与传统固定 token 长度的 chunk 切分相比，条文级切分的优势：

| 维度 | 固定 token chunk | 条文级对象 |
|---|---|---|
| 切分粒度 | 按 500/1000 token 固定切分 | 按法律文本的自然结构（条/款/项）切分 |
| 上下文完整性 | 可能将一个条文切断 | 每个条文作为完整语义单元 |
| 引用精度 | 引用到"第 N 段"（无法律意义） | 引用到"第 X 条第 Y 款"（法律引用标准） |
| 检索可审计性 | 难以解释为什么命中 | 可精确追溯到具体条文 |
| 交叉引用 | 不支持 | 支持条文间引用链扩展 |

### 7.5 信源管理与知识更新

为保证知识库时效性，系统设计如下更新机制：

| 更新方式 | 频率 | 信源 | 说明 |
|---|---|---|---|
| 手动导入 | 按需 | 网信办官方文件、法规正式文本 | 法学团队人工审核后入库 |
| 半自动爬取 | 每日 | 网信办/人大/国务院官网、地方网信办 | 抓取新发布文件 → 人工确认 → 入库 |
| 得理 API 同步 | 实时 | 得理开放平台 | 案例/法规检索结果缓存与索引 |
| 白皮书/研报 | 季度 | 行业白皮书、律所研报 | 人工筛选可靠来源后入库 |

每条知识条目均记录：来源URL、入库时间、最后验证时间、可靠度评级（官方 > 权威律所 > 行业研报 > 其他）。

## 9 安全与合规

### 9.1 数据安全

| 措施 | 说明 |
|---|---|
| 传输加密 | 全站 HTTPS（TLS 1.3），API 通信强制加密 |
| 存储加密 | 数据库透明加密（TDE）；对象存储服务端加密（SSE） |
| 文件隔离 | 每个用户/任务的上传文件与报告存储在独立路径，通过 task_id 鉴权访问 |
| 敏感信息脱敏 | 报告预览接口对企业名称、法人信息等字段支持脱敏展示 |
| 定期清理 | 超过保留期的用户上传文件与临时文件自动清理 |

### 9.2 应用安全

| 措施 | 说明 |
|---|---|
| 认证 | JWT Token（短期有效）+ Refresh Token |
| 授权 | 基于角色的访问控制（RBAC）：管理员 / 普通用户 |
| 输入校验 | 所有接口参数通过 Pydantic Schema 严格校验 |
| 限流 | Redis 令牌桶限流，防止 LLM 调用滥用 |
| 文件安全 | 上传文件格式白名单（PDF/DOCX/JPG/PNG）+ 大小限制 + 病毒扫描 |

### 9.3 合规声明与免责

系统在以下位置强制展示免责声明：
- 首页底部：工具定位说明（辅助工具，不构成法律意见）
- 报告首页：免责条款（生成内容仅供参考，最终合规方案应咨询专业律师）
- 诊断结果页：路径判断基于用户输入，不保证准确性
- 高风险结论旁：明确标注"建议人工复核"

### 9.4 审计日志

系统记录以下关键操作的完整审计链：

```
AuditLog {
  id, timestamp, user_id, action, resource_type, resource_id,
  input_summary, output_summary, llm_model, llm_token_usage,
  citations_count, risk_flags, human_review_required
}
```

支持按时间、用户、操作类型、风险等级查询审计记录。

## 11 评测与质量保证框架

系统质量不能仅靠主观演示判断，需要建立可量化、可重复的评测体系。参考 LegalBench 和 LegalBench-RAG 的评测方法论，系统采用**三层评测框架**，分别度量检索、抽取和生成三个环节的质量。

### 11.1 三层评测架构

```
┌───────────────────────────────────────────────────────────┐
│                      评测框架                                │
│                                                           │
│  ┌─────────────────┐  ┌─────────────────┐  ┌───────────┐ │
│  │ L1: 检索层评测    │  │ L2: 抽取层评测    │  │ L3: 生成层 │ │
│  │                 │  │                 │  │    评测    │ │
│  │ 法规检索质量     │  │ 事实抽取准确度   │  │ 报告质量   │ │
│  │ (自动化)        │  │ (自动化)        │  │ (自动+人工)│ │
│  └─────────────────┘  └─────────────────┘  └───────────┘ │
│                                                           │
│  输入：标注好的测试用例集（Golden Set）                        │
│  输出：各层指标数值 + 回归分析 + 质量趋势                      │
└───────────────────────────────────────────────────────────┘
```

### 11.2 各层评测指标

**L1 检索层评测** -- 评估 RAG 管线的法规检索质量

| 指标 | 定义 | 目标 |
|---|---|---|
| Precision@K | Top-K 结果中相关法规的占比 | >= 0.75 |
| Recall@K | 所有相关法规被检索到的占比 | >= 0.85 |
| MRR | 第一条相关法规的排名倒数均值 | >= 0.80 |
| 条文级精确匹配率 | 检索到的条文编号与标注答案完全匹配的比例 | >= 0.70 |
| 得理 API 增益 | 加入得理 API 后相比纯自建 RAG 的 Recall 提升 | > 0 |

**L2 抽取层评测** -- 评估企业画像抽取的准确度

| 指标 | 定义 | 目标 |
|---|---|---|
| 字段准确率 | 结构化画像中各字段与标注值一致的比例 | >= 0.90 |
| CIIO 判定准确率 | CIIO 是/否判定与标注答案的一致率 | >= 0.95 |
| 数据分类准确率 | 数据类型（个人信息/敏感个人信息/重要数据）分类的 F1 值 | >= 0.85 |
| 出境场景覆盖率 | 从材料中识别出的出境场景数 / 标注出境场景总数 | >= 0.90 |

**L3 生成层评测** -- 评估报告生成的最终质量

| 指标 | 定义 | 目标 | 评测方式 |
|---|---|---|---|
| 章节完整性 | 报告是否包含模板要求的所有章节 | 100% | 自动（Schema 校验） |
| 引用正确率 | 报告中法规引用与原文一致的比例 | >= 0.95 | 自动（比对知识库原文） |
| 引用覆盖率 | 每条结论是否附有至少一条引用 | >= 0.90 | 自动（引用链非空检查） |
| 风险一致性 | 风险等级判定与专家标注的一致率 | >= 0.80 | 人工（法学团队评审） |
| 律师可编辑性 | 律师在报告草案基础上修改量 / 总量的比值（越低越好） | <= 0.30 | 人工（律师反馈） |
| 门控正确率 | "需人工复核"标记的准确率（不漏标高风险、不误标低风险） | >= 0.85 | 人工 |

### 11.3 Golden Set 构建

评测需要一组标注好的测试用例（Golden Set），包含：

| 用例类型 | 数量（P0 目标） | 内容 |
|---|---|---|
| 路径诊断用例 | >= 20 | 企业场景描述 + 标注的正确路径判定 |
| 安全评估用例 | >= 5 | 企业材料 + 标注的企业画像 + 标注的应检索法规 + 标注的报告关键结论 |
| SCC/认证用例 | >= 3 | 同上 |
| 文档审查用例 | >= 5 | 待审查文档 + 标注的条款级问题列表 |

Golden Set 由法学团队人工标注，每季度迭代更新。

### 11.4 评测执行与回归

```
评测触发时机：
  - 每次 Prompt 模板修改后
  - 每次 RAG 管线参数调整后
  - 每次知识库批量更新后
  - 每次 LLM 模型切换/升级后

执行流程：
  Golden Set → 系统全流程执行 → 收集中间态 JSON → 自动计算 L1/L2/L3 指标 → 与基线对比 → 生成回归报告

告警规则：
  - 任一 L1 指标下降 > 5% → 阻断上线，排查检索问题
  - 任一 L2 指标下降 > 5% → 阻断上线，排查抽取/Prompt 问题
  - L3 引用正确率下降 > 3% → 阻断上线，排查生成/引用链问题
```

   功能：生成报告单章节（含引用链+风险标注）

5. consistency_checker → POST /api/v1/tools/check-consistency
   功能：校验全部章节的交叉引用一致性

   功能：将结构化 JSON 渲染为 docx 文件

## 附录 C：关键决策记录

| 编号 | 决策 | 原因 | 备选方案 |
|---|---|---|---|
| D1 | 路径诊断采用前端决策树而非 LLM | 规则确定、响应快、无幻觉风险 | 后端 LLM 判断 |
| D2 | 报告生成采用异步任务 | 多轮 LLM 调用耗时长，需避免 HTTP 超时 | SSE 流式推送 |
| D3 | 混合检索（向量+全文） | 兼顾语义匹配与精确检索 | 纯向量检索 |
| D4 | Prompt 模板化（Jinja2） | 便于版本管理、A/B 测试、多法域扩展 | 硬编码 Prompt |
| D5 | 结构化 JSON 中间层 | 统一输出格式，便于渲染和评测 | 直接生成 docx |
| D6 | 引用链强制约束 | 法律场景核心差异点，避免幻觉 | 可选引用 |
| D7 | 两级编排：元器顶层编排 + 自建Python执行层 | 元器满足比赛工具链展示要求、提供可视化流程编辑；自建组件处理RAG细节、文件解析、报告渲染等元器无法覆盖的逻辑 | 纯元器方案（受限于插件能力） / 纯自建方案（无法展示工具链） |
| D8 | 得理API作为补充信源而非唯一信源 | 自建知识库可控性强、支持离线运行；得理API提供增量覆盖 | 纯得理API（依赖外部服务可用性） |
| D9 | 统一 JSON Schema 中间态层 | 所有模块间数据交换采用 Schema 约束的 JSON 对象，确保输出可预测、可测试、可审计；支持断点恢复和人工修正 | 自由格式文本传递（不可控） |
| D10 | 法规库采用条文级对象而非固定 token chunk | 法律文本以条/款/项为自然语义单位，条文级切分保留完整引用信息，支持交叉引用图谱；固定 chunk 会切断条文、丢失引用精度 | 固定 500/1000 token chunk（引用精度差） |
| D11 | 三层评测框架（检索/抽取/生成） | 分层度量避免端到端黑箱评测；自动化指标 + 人工评审结合；Golden Set 支持回归分析，每次 Prompt/RAG 变更可量化影响 | 纯主观演示评估（不可重复） |
| D12 | Schema-driven 表单系统 | 表单定义与渲染分离，新增文书类型只需配置 Schema 文件；减少前端代码重复，便于法学团队直接维护字段定义 | 每种表单硬编码前端组件（扩展成本高） |
| D13 | 通用服务插件化文书生成框架 | 文书类型作为配置注册而非硬编码接口；共享基类管线（检索→推理→渲染），各文书仅配置 Schema/Prompt/模板；扩展新文书零代码修改 | 每种文书独立接口和服务（重复代码多） |
