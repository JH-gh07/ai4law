# AI4Law 开发文档

## 1. 文档说明
本文档用于从项目整体视角说明 `AI4Law` 的产品定位、模块体系、端到端流程、前后端设计思路、AI 编排方式、输入输出机制以及当前阶段的交付效果。

本版内容综合参考了当前项目代码、项目内开发文档，以及外层参考资料中的 `pipeline` 与结构类文档。其中，历史资料主要用于帮助理解产品演进方向；若与当前版本存在差异，均以当前代码与现行开发文档为准。

---

## 2. 项目定位
AI4Law 是一个面向跨境数据合规场景的企业级 AI 合规操作系统。它的目标不是停留在法律问答层，而是围绕企业真实任务，将“规则判断、材料准备、文书起草、文本审查、风险整改、结果交付”组织成可执行的工作流。

从应用场景看，项目重点覆盖三大法域：

- 中国大陆到境外的数据出境合规
- 欧盟相关跨境传输与文书义务
- 美国对外数据流动与隐私合规专题

从产品形态看，AI4Law 强调三件事：

- 以任务为入口，而不是以单次聊天为入口
- 以结构化交付物为结果，而不是只给一段分析文字
- 以工作区协同为核心，而不是把能力拆成彼此割裂的独立工具

## 3. 整体模块体系
参考现有 `pipeline` 与结构文档，项目采用“法域 - 能力 - 专题”的三级组织方式。

### 3.1 一级：法域

- 中国
- 欧盟
- 美国

### 3.2 二级：能力

- 诊断
- 起草
- 审查
- 整改

### 3.3 三级：专题模块

当前已形成或已规划的专题模块主要包括：

- 中国 / 诊断 / 合规路径诊断
- 中国 / 起草 / 安全评估报告草案
- 中国 / 起草 / PIPIA 报告草案
- 中国 / 审查 / 文档专项智能审查
- 中国 / 整改 / 风险与整改建议清单
- 欧盟 / 审查 / SCC 审查
- 欧盟 / 审查 / BCR 审查
- 欧盟 / 起草 / DPIA 草案生成
- 欧盟 / 起草 / TIA 草案生成
- 美国 / 审查 / EO14117 相关风险分析
- 美国 / 起草 / CPRA 合规全景报告

这种结构的价值在于：

- 对用户来说，入口更贴近业务目标，理解成本更低
- 对产品来说，不同法域下的能力层可以保持一致，便于扩展
- 对开发来说，专题模块可独立迭代，又能共享基础能力与工作区框架

## 4. 产品功能设计
本项目不是单点工具，而是围绕企业合规任务设计了一组可串联的功能。

### 4.1 首页与任务入口
首页承担的不只是展示作用，而是完成产品价值表达、法域引导、能力说明和任务入口承接。它需要让用户在很短时间内知道：

- 这个系统解决什么问题
- 支持哪些法域和模块
- 最终能产出什么结果
- 应该从哪里开始

### 4.2 任务空间与工作区
项目核心不是“页面集合”，而是一个任务驱动的工作区。工作区把一次合规任务拆成几个协同区块：

- 左侧资源区：任务概览、输入材料、步骤状态、附件清单
- 中部运行区：表单录入、模块执行、阶段式响应
- 右侧协同区：Copilot 对话、状态流、运行摘要、产物清单

这意味着用户不必频繁跳出任务上下文，而是在同一空间内完成输入、分析、查看结果和追问。

### 4.3 诊断类功能
诊断类功能负责回答“应该走哪条路径”。例如中国法域下的合规路径诊断，会根据企业是否涉及 CIIO、是否包含重要数据、个人信息规模、出境场景等因素，判断应优先进入安全评估、标准合同/认证，或可适用豁免路径。

### 4.4 起草类功能
起草类功能负责把信息输入转化为结构化交付物，典型包括：

- 数据出境风险自评估报告草案
- PIPIA 报告草案
- DPIA 草案
- TIA 草案
- 合规备忘录、尽调报告、风险整改清单等通用文书

这一类功能强调输出结果的章节结构、依据引用、可下载性和后续交付可用性。

### 4.5 审查类功能
审查类功能面向已存在文本，例如：

- 标准合同
- DPA
- 隐私政策
- 内部制度
- SCC / BCR 类文书

系统会围绕条款层级识别问题，输出风险等级、法规依据、问题清单与修改建议。对文档智能审查模块，还进一步支持生成“批注修订版”文档，使输出更贴近真实法务协作方式。

### 4.6 整改类功能
整改类功能负责把问题沉淀为下一步动作，包括：

- 风险优先级排序
- 补充材料建议
- 修订动作清单
- 后续申报或审查准备项

即使部分整改能力当前仍嵌在诊断、起草、审查模块的输出中，它在产品设计上已经被明确为一个独立能力方向。

### 4.7 Copilot 协同功能
Copilot 不是单独聊天页，而是工作区里的智能协作助手。它需要结合任务名称、当前阶段、阻塞原因、运行情况和已有产物，为用户提供：

- 上下文解释
- 任务追问
- 材料提醒
- 下一步建议
- 结果理解辅助

这使得 Copilot 更像“工作区协作者”，而不是泛泛的问答机器人。

## 5. 核心 Pipeline 设计
外层 `pipeline.md` 和项目内 pipeline 文档都强调，AI4Law 的关键不只是模块数量，而是端到端流程的连通性。

### 5.1 总体流程

1. 用户进入首页，理解产品能力并选择法域或专题任务
2. 用户创建任务，进入工作区
3. 在任务内完成表单填写、材料上传或文档提交
4. 后端根据模块类型执行对应分析流程
5. AI 与规则引擎共同生成结构化结果
6. 系统输出报告、批注文档、风险清单或下一步建议
7. 用户在工作区继续追问、补充材料、下载成果或进入下游模块

### 5.2 诊断类 Pipeline
以“合规路径诊断”为例：

1. 用户填写结构化问卷
2. 前端提交标准化字段
3. 后端归一化为诊断输入对象
4. 规则引擎先做路径判断与风险分层
5. LLM 对规则结果做专业化解释与建议补充
6. 系统返回诊断结论、法规依据、行动建议
7. 若命中后续路径，系统可将结果作为 handoff 传递给安全评估或 SCC/PIPIA 等模块

### 5.3 起草类 Pipeline
以“安全评估报告草案”或 “PIPIA 报告草案”为例：

1. 用户填写结构化表单并上传附件
2. 系统提取文件文本与关键信息
3. RAG 检索相关法规、模板、指南和案例
4. LLM 按章节生成结构化内容
5. 系统执行一致性校验与章节聚合
6. 模板渲染为 `docx / markdown / 预览内容`
7. 用户在工作区预览、下载或继续补充

### 5.4 审查类 Pipeline
以“文档专项智能审查”或 “SCC 审查”为例：

1. 用户上传待审文档
2. 系统解析文档文本与结构
3. 进行条款切分与条款分类
4. 按条款调用规则与 LLM 进行问题识别
5. 聚合生成总体风险等级和问题清单
6. 输出审查报告
7. 对可编辑文档进一步生成批注修订版 `docx`

### 5.5 通用服务 Pipeline
对于尽调备忘录、整改建议清单、TIA 等通用服务，产品设计上采取“文书类型注册 + 统一生成底座”的方式，让不同文书共享一套生成链路，只在输入 schema、prompt 和模板层做差异化。

## 6. 系统结构设计
从结构文档可以看到，项目整体采用四层思路：表现层、应用服务层、AI 推理层、数据层。

### 6.1 表现层
表现层主要对应前端界面与交互，包括：

- 首页
- 任务空间
- 工作区
- 报告中心
- 知识库入口
- Copilot 面板

这一层负责把模块能力组织成用户可操作的产品体验。

### 6.2 应用服务层
应用服务层主要负责：

- 模块路由与任务创建
- 表单接收与校验
- 文件上传与文本提取调度
- 模块执行编排
- 报告生成与产物管理
- 会话状态、任务状态与上下文传递

它是前端工作区与底层 AI / 规则能力之间的桥梁。

### 6.3 AI 推理层
AI 推理层是整个系统的智能核心，负责：

- Prompt 编排
- RAG 检索
- 法规 / 案例引用
- 风险分析
- 结构化输出解析
- 输出一致性控制

这层并不直接面对用户，而是为应用服务层提供可复用的推理能力。

### 6.4 数据层
数据层主要包括：

- 法规知识库
- 案例与指引资料
- 模板库
- 用户任务与会话数据
- 上传文件与生成文件

对于这个项目来说，数据层不只是存储，更是“法规依据”和“模板交付物”生成的基础。

## 7. 前端设计与实现思路
这部分保持必要说明，但不再过度占比。

### 7.1 前端承担的职责
前端不是简单的页面展示层，而是要承接完整任务体验，主要职责包括：

- 组织首页、任务空间、工作区等页面结构
- 提供多模块统一入口
- 渲染表单、步骤、状态流和产物面板
- 处理文件上传、结果展示和下载入口
- 连接 Copilot 与任务上下文
- 通过主题化样式表达不同模块类型

### 7.2 主要实现方式
从当前项目结构看，前端采用现代 React 工程化方式组织，技术要点可概括为：

- React + TypeScript 负责组件化与类型约束
- Vite 负责前端构建
- 组件拆分方式支持首页、工作区、模块适配等多层复用
- 通过任务模板和模块适配器将不同法域 / 专题映射到统一工作区框架
- 通过 CSS 变量和模块主题样式控制界面视觉一致性

### 7.3 前端设计重点

- 把多法域、多模块能力统一装进一个工作区框架
- 让输入、运行、结果、Copilot 同屏协同
- 在不破坏结构的前提下，持续打磨标题、注释、卡片、列表和流程可读性
- 让报告、文件产物和状态信息更接近真实交付界面，而不是演示页面

## 8. 后端设计与实现思路
这一版重点补强后端部分，使文档更平衡。

### 8.1 后端承担的职责
后端主要负责：

- 提供模块 API
- 承接工作区提交的表单和文件
- 进行任务编排与状态返回
- 调用规则引擎、知识检索与 LLM
- 生成结构化结果和最终文档
- 管理产物文件、报告元数据和上下文信息

### 8.2 主要技术方式
从当前项目代码与文档看，后端整体以 Python 技术栈为核心，典型技术包括：

- FastAPI：提供 API 能力
- Pydantic：定义输入输出 schema
- python-docx：生成和加工 Word 文档
- 文件处理组件：负责文本提取、上传文件处理和产物落盘
- 模块化服务层：按诊断、SCC、审查、Copilot 等功能拆分

### 8.3 后端模块化设计
当前后端明显采用“模块服务 + 通用服务”的组合方式，例如：

- 诊断服务
- SCC / 文档审查服务
- 报告服务
- 文件服务
- Copilot 服务

这种设计的好处是：

- 每个专题模块可以独立演进
- 通用文件处理、报告渲染、输出管理可以复用
- 更适合后续继续扩展法域和文书类型

### 8.4 文档生成与交付
后端不是只返回 JSON，而是以交付物为目标进行输出，典型包括：

- 结构化结果对象
- `markdown` 草稿
- `docx` 报告
- `pdf` 报告
- `zip` 打包产物
- 带批注的修订版 `docx`

这使系统从“会分析”进一步走向“会交付”。

### 8.5 文档智能审查的后端增强
文档智能审查部分的关键增强之一，是把原先的审查报告输出扩展为批注型交付。其思路可概括为：

1. 解析用户上传的原始 `docx`
2. 基于审查结果生成结构化批注内容
3. 将批注信息写入 OpenXML 结构
4. 生成带评论锚点和批注内容的新版文档
5. 与审查报告一并作为产物输出

这类能力明显提升了系统在真实合同审查、制度审查场景中的可用性。

## 9. AI 与知识能力设计
AI4Law 的智能性并不只来自大模型本身，而是来自“规则、知识、流程、模型”的协同。

### 9.1 规则与模型协同
项目在关键判断上并不完全交给 LLM，而是采用：

- 规则先行做基础判断
- LLM 做专业解释、补充推理和自然语言生成

这样做的原因是：

- 路径判断和风险分层需要稳定性
- 结果解释和文书生成需要表达能力
- 规则与模型结合，更适合合规场景

### 9.2 RAG 与知识库
项目相关文档明确体现出知识库思路，尤其是法规、案例、模板资料已经形成较完整的文档基础。其价值包括：

- 为模型提供法规依据
- 为报告生成提供模板和章节参考
- 为审查模块提供条款判断依据
- 为 Copilot 提供更可靠的任务语境

### 9.3 智能体 / 工作流编排
从结构文档与项目设想来看，AI 层并不是单次 prompt，而是更接近工作流编排：

- 上层负责决定执行顺序和步骤协同
- 下层负责具体检索、解析、生成和渲染

这种设计比纯聊天式调用更适合复杂的文书生成与审查任务。

## 10. 输入与输出设计
这一部分是产品和研发都很关心的基础能力。

### 10.1 输入类型
项目整体输入大致分为三类：

1. 结构化表单输入
例如企业名称、法域、出境目的、数据类型、接收方信息、处理场景、风险控制措施等。

2. 文档与材料输入
例如合同、隐私政策、DPA、制度文件、数据清单、主体清单、申报材料、证明附件等。

3. 自然语言输入
主要用于 Copilot 对话、用户补充说明、任务追问与过程辅助。

### 10.2 输出类型
项目输出并不单一，而是围绕实际交付场景提供多种结果：

- 路径诊断结论
- 风险等级
- 法规依据
- 章节化报告内容
- 问题清单
- 整改建议
- Markdown 草稿
- Word 报告
- PDF 报告
- ZIP 打包产物
- 批注修订版文档

### 10.3 输入输出设计价值

- 对用户来说，输入方式贴近真实工作资料
- 对系统来说，输出结果可直接进入审阅、流转和交付
- 对后续扩展来说，不同模块可以复用同一套输入输出治理框架

## 11. 项目打磨与优化方向
这部分不再只写当前线程，而是总结项目层面的打磨。

### 11.1 产品结构打磨

- 将首页从普通说明页提升为产品入口页
- 将模块能力从散点工具整理为法域 - 能力 - 专题结构
- 强化“任务空间 - 工作区 - 结果交付”的主线

### 11.2 交互流程打磨

- 优化新建任务和引导模式衔接
- 修正跳过引导后未自动进入工作区的问题
- 让工作流更符合真实任务推进习惯

### 11.3 工作区体验打磨

- 强化左右侧栏与中部运行区的协同关系
- 优化结果展示、文件产物和状态流呈现
- 让工作区更像企业级操作台，而不是单次表单页

### 11.4 Copilot 体验打磨

- 从模板化答复提升为可自然交流的对话能力
- 让 Copilot 能读取任务上下文并给出更贴近当前阶段的回答
- 与工作区状态流、任务信息、产物结果建立联动

### 11.5 交付结果打磨

- 强化报告输出结构
- 增加更接近真实法务协作方式的批注修订版文档
- 让输出结果不仅能“看”，还能“交付”和“复用”

## 16. 总结
AI4Law 的核心价值，不在于单次回答某个法律问题，而在于尝试构建一个面向企业跨境数据合规任务的 AI 工作平台。

它通过法域组织、模块化能力、任务工作区、智能审查、报告生成、批注交付和 Copilot 协同，把“判断、起草、审查、整改、交付”串成一条更接近真实业务流程的产品链路。

从开发视角看，项目已经形成了相对清晰的模块结构、前后端协作方式、AI 编排思路和交付导向设计。后续随着法域能力补齐、输出规范统一和智能体流程增强，具备继续向更完整企业级合规产品演进的基础。
