# 一、路径层



路径层解决的问题是：



```Plain Text
企业当前场景到底适用哪类合规要求？
是否应当进入某个具体业务模块？
```



路径层目前包括：



```Plain Text
1. 中国路径诊断 diagnosis report
2. 美国 EO14117 对华数据流动适用性判断
3. 欧洲路径判断，暂时待设计
```



路径层的处理逻辑是：



```Plain Text
用户输入业务情况
→ 系统按规则判断是否命中
→ 检查法规依据是否存在
→ AI 做一致性复核
→ 输出路径适用性报告
```



这里的主判断必须来自规则，不由 AI 直接决定。



AI 的作用是复核：



```Plain Text
规则结论是否和用户事实矛盾；
是否存在缺失信息；
是否存在过度判断；
报告表达是否稳妥。
```



路径层最后输出：



```Plain Text
推荐路径
命中规则
未命中规则
缺失事实
法规依据
一致性复核结果
下一步建议
```

# 二、功能层



功能层分三类：



```Plain Text
1. 合同审查类
2. 填表格类
3. 草案模板生成类
```



---



## 1\. 合同审查类



包含：



```Plain Text
review
SCC
BCR
```



合同审查类解决的问题是：



```Plain Text
企业已经有合同、协议、制度或条款文本，
系统帮助企业判断原文哪里有问题、为什么有问题、应该怎么改。
```



业务流程是：



```Plain Text
用户上传合同或条款文本
→ 系统读取原文
→ 拆分成可审查条款
→ 判断每条条款属于什么类型
→ 匹配 GDPR / SCC / BCR / 数据保护法规依据
→ 审查每条条款是否合理、模糊、缺失或不合规
→ 生成风险等级和修改建议
→ 输出审查报告或批注版文件
```



它要回答的问题是：



```Plain Text
哪里写得不清楚？
哪里义务不完整？
哪里可能不合法？
哪里需要补充？
应该怎么改？
依据是什么？
```



输出形式包括：



```Plain Text
原文定位
问题类型
风险等级
修改建议
法规依据
审查报告
批注版 / 对照版
```



一句话：



```Plain Text
合同审查类 = 审已有文本，给修改建议。
```



---



## 2\. 填表格类



包含：



```Plain Text
CPRA
```



填表格类解决的问题是：



```Plain Text
企业用自然语言或问卷描述业务情况，
系统把这些信息转换成一张合规差距表或整改清单。
```



业务流程是：



```Plain Text
用户填写企业数据处理情况
→ 系统识别涉及哪些 CPRA 义务
→ 判断每项义务是否满足
→ 生成 gap_items 差距项
→ 给每个差距项风险等级
→ 生成整改建议
→ 输出 Excel 表格和可选摘要报告
```



它要回答的问题是：



```Plain Text
企业有哪些 CPRA 义务？
哪些已经满足？
哪些没有满足？
缺什么材料或机制？
风险等级是多少？
下一步怎么整改？
```



输出形式包括：



```Plain Text
CPRA 义务清单
差距项
风险等级
整改建议
Excel 表格
摘要报告
```



一句话：



```Plain Text
填表格类 = 用户描述进来，合规清单出去。
```



---



## 3\. 草案模板生成类



包含：



```Plain Text
assessment
PIPIA
DPIA
TIA
CN Flow
```



草案模板生成类解决的问题是：



```Plain Text
企业没有完整文书，
系统根据用户输入和固定模板，生成合规文书草案。
```



业务流程是：



```Plain Text
用户填写业务事实和上传材料
→ 系统整理企业事实
→ 检索法规依据
→ 识别风险和问题
→ 组装证据链
→ 形成生成上下文包
→ AI 按固定模板生成章节正文
→ 系统做一致性检查
→ 输出正式草案文件
```



它要回答的问题是：



```Plain Text
这份文书应该怎么写？
哪些事实可以写？
哪些地方证据不足？
哪些表述需要保守？
哪些地方有风险？
哪些整改建议应当放进报告？
```



这里 AI 基于系统整理好的依据写：



```Plain Text
企业事实
风险问题
法规依据
证据链
模板章节
```



输出形式包括：



```Plain Text
docx 文书草案
markdown 预览
pdf
xlsx 风险清单
zip 输出包
中间产物 JSON
trace 留痕
```



一句话：



```Plain Text
草案模板生成类 = 用户输入业务事实，系统按模板生成文书。
```

# 三、引用展示



所有路径层和功能层都要逐步支持引用展示。



目标是：



```Plain Text
报告正文中的法规引用可以悬停查看来源，
点击后查看原文或来源卡片。
```



展示形式包括：



```Plain Text
行内引用
citation popover
source preview card
```



它的作用是：



```Plain Text
让用户知道每个判断依据来自哪里；
让报告结论可以追溯；
减少 AI 编造法规依据的风险。
```

# 四、引用交互的目标形态



这里的“引用展示”不是报告末尾统一列参考文献，也不是只在 JSON 里保留 citation 字段。



真正要实现的是一套 **正文内联引用交互链路**：



```Plain Text
正文中的判断 / 风险 / 建议
→ 行内显示可交互引用标记
→ 鼠标悬浮时展示来源预览卡片
→ 点击后跳转知识库中的对应法规 / 指南 / 模板原文
→ 尽可能直接定位到对应条文、章节或条款
```



## 4.1 行内引用的展示对象



以下内容原则上都应支持内联引用：



```Plain Text
1. 合规结论
2. 风险判断
3. 整改建议
4. 条款修改理由
5. 路径命中 / 不命中依据
6. 证据不足或需要补充材料的判断
```



引用应绑定到具体判断单元，而不是整章共享一组模糊引用。



目标关系是：



```Plain Text
issue / finding / recommendation
    ↓
evidence
    ↓
legal_basis / source
    ↓
inline citation anchor
```



## 4.2 行内引用的视觉形态



引用在正文中优先以 **轻量 pill / 标签 / 小锚点** 的形式出现，视觉上更接近“可点附件标签”或“文内来源标签”，而不是粗糙的纯文本 `[1]`。



目标效果类似：



```Plain Text
一句正文判断 + 右侧轻量引用标签
悬浮时出现白色或浅色浮层卡片
卡片中可预览来源标题、条文号、摘录和类型
点击后跳转至知识库原文
```



也就是说，前端交互预期更接近：



```Plain Text
“SCC审查测试案例及预期输出” 这样的可悬浮标签
而不是单纯的脚注编号
```



## 4.3 悬浮交互要求



悬浮时应弹出一个 **轻量预览卡片**，至少包含：



```Plain Text
来源标题
条文 / 条款号
核心摘录 snippet
来源类型（法律 / 指南 / 模板 / 用户材料 / 案例）
权威等级或约束力等级
该引用在当前判断中的用途说明（可选）
```



悬浮卡片的目标不是替代阅读原文，而是帮助用户快速判断：



```Plain Text
这条引用是什么？
为什么会出现在这里？
它够不够支撑当前结论？
```



## 4.4 点击后的行为



点击引用后，不应只是打开本地浮层，而应进入知识库中的对应来源页面。



理想链路是：



```Plain Text
点击行内引用
→ 打开知识库对应来源
→ 自动定位到对应 article / clause / section
→ 用户可继续浏览前后文
```



如果知识库已接入条文级索引，则应优先直达条文；
如果暂时只有来源级页面，则至少打开来源详情页，并高亮目标条目。



这里需要进一步明确：



```Plain Text
点击后默认行为 = 跳转到知识库页面
而不是停留在当前报告页内只打开一个本地抽屉
```



也就是说，悬浮预览负责“快速看”，点击负责“进入知识库继续看”。



目标跳转对象包括：



```Plain Text
1. 具体法律条文页面
2. 具体行政法规条文页面
3. 官方指南对应章节页面
4. 模板 / 标准合同 / BCR / SCC 对应条款页面
5. 其他已接入知识库的正式来源页面
```



跳转时应尽可能携带精确定位参数，例如：



```Plain Text
source_id
article_no
clause_id
section_id
anchor
```



从而做到：



```Plain Text
点引用
→ 进入知识库对应来源
→ 自动滚动到对应条文
→ 高亮当前条文
→ 用户继续查看上下文
```



如果某条引用暂时无法定位到条文级内容，也应至少跳转到该来源在知识库中的详情页，而不能退化成“没有反应”或“只展示一段静态文本”。



## 4.5 引用的分层



平台中的引用不能混为一类，应区分：



```Plain Text
1. 法规依据引用
2. 官方指南 / 模板要求引用
3. 案例或背景参考引用
4. 用户材料引用
5. 系统内部证据链引用
```



这些层级的目的不同：



```Plain Text
法规依据：支撑法律判断
官方指南 / 模板：支撑实务要求或文书结构
案例参考：支撑背景理解，不直接替代强制法依据
用户材料：支撑事实来源
系统内部证据链：支撑系统为什么这样判断
```



## 4.6 外部可见与内部可见的边界



引用还要区分对外和对内的可见级别：



```Plain Text
客户视图：
仅展示可对外表达的法规 / 指南 / 模板引用

内部视图：
可额外展示用户材料、内部证据链、置信度不足的引用、被丢弃的引用
```



这样可以避免把仅供内部审查的检索命中、未验证引用、草稿级证据直接暴露给客户。

# 五、运行过程可观测



平台不应只是“点一次生成，最后吐一个文件”，而应逐步升级为 **可观察执行工作台**。



目标是让用户在程序运行过程中看到：



```Plain Text
当前执行到哪一步
正在调用什么工具 / Agent / 检索 / 规则
每一步产出了什么中间结果
哪里存在阻塞、缺材料或不确定项
最终结论是如何形成的
```



## 5.1 运行过程展示的三层内容



### 第一层：状态层



```Plain Text
任务已创建
正在执行
正在检索
正在生成
正在审稿
已完成 / 已阻塞 / 已失败
```



它回答的是：



```Plain Text
系统现在处在哪个阶段？
```



### 第二层：执行层



```Plain Text
规则命中
Agent 执行
工具调用
RAG 检索
附件解析
中间文件生成
```



它回答的是：



```Plain Text
系统刚刚具体做了什么？
```



### 第三层：解释层



```Plain Text
为什么先做这一步
为什么得出这个结论
为什么某项风险被保留 / 被降低 / 被阻断
```



它回答的是：



```Plain Text
系统为什么这么判断？
```



## 5.2 运行过程中的“思考”展示边界



平台可以展示“思路摘要”，但不应直接暴露模型原始 chain-of-thought。



建议展示的是：



```Plain Text
思路摘要 / reasoning summary
```



例如：



```Plain Text
先检查路径硬门槛，再读取上传合同与同意材料，
随后核对接收方与合法性基础，最后检索法规并生成章节。
```



而不应直接展示：



```Plain Text
原始 prompt
原始内部推理全文
未清洗 observation
不适合外发的内部判断草稿
```



## 5.3 可观测结果的前端形态



目标前端不是单一聊天框，而是一个可切换的工作台，至少包括：



```Plain Text
1. 对话
2. 执行流时间线
3. 中间结果查看
4. 最终结果简报
```



其中“执行流时间线”应尽量接近：



```Plain Text
Thought / Tool / Read / Retrieval / Rule Hit / Intermediate Result / Final Result
```



每个节点都可以展开查看更多内容。



## 5.4 中间结果的保留原则



路径层和功能层都应尽可能输出结构化中间结果，例如：



```Plain Text
facts
issues
evidence_chain
path_diagnosis
report_review
clarification
material_gaps
filing_readiness
retrieval_hits
trace_manifest
```



这些结果的作用不是单纯调试，而是：



```Plain Text
支撑可解释性
支撑引用追溯
支撑前端中间态展示
支撑客户简报生成
支撑人工复核
```

# 六、执行完成后的结果简报



工作流执行完之后，系统不应只给用户一堆文件路径，还应自动生成一份 **简单、稳定、可对客户汇报的执行结果摘要**。



## 6.1 简报的目标



它要解决的问题是：



```Plain Text
本次到底做完了什么？
最后结论是什么？
系统生成了哪些交付物？
哪些地方仍然要注意？
建议下一步怎么做？
```



## 6.2 简报的固定结构



建议所有模块统一输出以下四块：



```Plain Text
1. 执行结果
2. 本次生成文件
3. 需要注意的点
4. 建议下一步
```



具体可展开为：



```Plain Text
执行结果：
本次已完成哪类审查 / 生成 / 评估；
当前结论是可继续推进、需补材料、需整改后再推进，还是不建议继续。

本次生成文件：
报告、草案、批注版、Excel、PDF、ZIP、trace 等。

需要注意的点：
高风险问题、证据不足、合同缺口、合法性基础偏弱、路径阻断项等。

建议下一步：
补什么材料、修什么条款、是否重新运行、是否进入人工法务复核。
```



## 6.3 内部简报与客户简报



这里也必须分层：



```Plain Text
内部简报：
可包含中间判断、不确定项、内部证据链、调试信息

客户简报：
仅保留稳定结论、交付文件、注意事项、下一步建议
```



客户简报不应直接暴露：



```Plain Text
原始推理
内部调试 trace
prompt / observation
未验证的引用
纯内部材料缺陷描述
```



## 6.4 简报的生成原则



简报不应由每个模块随意自由生成，而应尽量基于结构化结果统一组装。



推荐输入来源：



```Plain Text
risk_level / overall_rating
issues / consistency_issues
evidence_chain
output_files
filing_readiness / path_diagnosis / report_review
```



这样简报才会：



```Plain Text
稳定
可控
可追溯
适合多模块复用
```

# 七、整体交付体验目标



平台最终希望形成的不是“黑箱生成器”，而是一个对业务用户和法务顾问都友好的 **透明合规工作台**。



完整体验链路应是：



```Plain Text
用户进入路径或功能模块
→ 填写事实 / 上传材料
→ 系统实时展示执行流和中间结果
→ 正文中的引用可悬浮预览、点击跳知识库原文
→ 系统生成正式报告 / 草案 / 审查结果
→ 运行结束后自动给出客户可读的结果简报
→ 用户继续补材料、整改、复跑或人工复核
```



最终要求是：



```Plain Text
所有结论都应当有规则、事实、法规依据和引用链支撑；
所有关键过程都应当可追溯；
所有最终输出都应当能被内部团队和客户快速理解。
```

# 八、整体



```Plain Text
路径先判断，
再按任务类型进入合同审查、表格清单或草案模板生成，
过程中应支持可观测执行流与中间结果展示，
正文中的引用应支持悬浮预览与点击跳知识库原文，
执行完成后应自动给出客户可读的结果简报，
所有结论都要有规则、事实、法规依据和可追溯引用支撑。
```
