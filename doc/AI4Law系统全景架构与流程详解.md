## 1. 系统概览：这是什么系统？

**AI4Law**（前端品牌名 **DataComply Flow**）是一个 **AI 驱动的跨境数据合规文书生成平台**。

### 它解决什么问题？

当一家中国企业需要将数据传输到境外（如将用户数据传到海外服务器），中国法律要求企业必须完成合规手续——可能是向网信办申报"数据出境安全评估"，也可能是签订"标准合同"并备案，还可能是取得"个人信息保护认证"。

但问题是：

- **该走哪条路径？** 不同情况对应不同的合规路径，判断规则复杂。
- **怎么写合规文书？** 自评估报告通常上万字，需要引用法律条文、描述数据处理情况、论证风险可控。
- **怎么保证不写错？** 合规文书有严格的格式和内容要求，遗漏关键信息可能导致被驳回。

AI4Law 就是解决这些问题的：用户填写一份表单，系统自动判断合规路径，然后 **AI 检索法规、分析事实、生成完整报告**，并输出问题清单、证据链等中间产物，让用户能追溯每一句结论的来源。

### 支持哪些法域？

| 法域 | 主要法规 | 系统模块 |
|------|---------|---------|
| 🇨🇳 中国（CN） | 《个人信息保护法》《数据出境安全评估办法》《促进和规范数据跨境流动规定》 | 安全自评估、数据流合规检查、标准合同审查 |
| 🇪🇺 欧盟（EU） | GDPR | SCC审查、DPIA、TIA |
| 🇺🇸 美国加州（US） | CPRA | CPRA 合规检查 |

### 核心能力一览

1. **路径诊断**：交互式问答，判断用户该走哪条合规路径
2. **事实提取**：将用户填写的表单信息、上传的文件内容，提取为标准化的"事实项"
3. **法规检索**：从 15 个向量知识库中检索相关法规条文
4. **问题识别**：基于规则引擎，自动识别合规风险点
5. **证据链构建**：为每个结论建立"事实 → 法规 → 结论"的完整证据链
6. **报告生成**：AI 撰写专业的合规报告（Markdown / Word / 压缩包）
7. **一致性校验**：自动检查报告中是否存在矛盾或遗漏
8. **实时可视化**：前端实时展示执行进度和中间产物

## 2. 核心设计思想

### 2.1 中间产物驱动架构（核心创新）

传统 AI 生成报告的流程是：

```
用户输入 → 拼接提示词 → 大模型直接生成报告 → 输出文件
```

这是一个 **"黑箱"模型**：用户不知道报告里每句话的依据是什么，也无法验证结论是否正确。

AI4Law 采用了完全不同的 **"中间产物驱动"架构**：

```
用户输入 → 提取事实 → 检索法规 → 识别问题 → 构建证据链 → 生成上下文包 → AI生成报告 → 一致性校验 → 修复 → 输出
              ↑                        ↑                        ↑
         事实清单                  问题清单+证据链              校验报告
         (可查看)                  (可查看)                   (自动修复)
```

**每一层中间产物都是可见、可验证、可追溯的**。报告的每一句话都能追溯到对应的证据链节点 → 问题项 → 法规条文 → 原始事实。

### 2.2 三链合一（可追溯性的基石）

系统中的每个合规结论都由三条链交叉验证：

```
事实链（Fact）：这个数据从哪里来的？
    ↓
规则链（Rule）：触发了哪条法律条文？
    ↓
证据链（Evidence）：为什么这样判断？支持力度如何？
```

每条链上的每个节点都有唯一编号，节点之间通过编号互相引用，形成完整的追溯网络。

### 2.3 分层架构

系统分为四个层次：

| 层次 | 目录 | 职责 |
|------|------|------|
| **基础平台层（L1）** | `backend/common/` | 通用工作流引擎、中间产物定义、RAG检索、LLM调用、可追溯记录 |
| **模块层（L2）** | `backend/modules/` | 13个具体合规产品，每个封装自己的业务逻辑 |
| **服务层（L3）** | `backend/services/` | 跨模块的共享服务：认证、文件管理、任务调度、WebSocket |
| **接口层（L4）** | `backend/main.py` | FastAPI 路由注册，对外暴露 REST API |

### 2.4 表达安全（防法律风险措辞）

系统内置了"禁止表达规则"（Forbidden Expression Rules），防止 AI 生成的报告中出现法律上危险的措辞：

- **不能断言"完全合规"**：系统只能说"符合某法某条规定"，不能说"企业已完全满足所有法律要求"
- **不能替用户做承诺**：如 "本企业承诺已建立完善的安全管理体系"——这类承诺性表述必须由用户自己确认
- **缺失信息不能假设**：缺少材料时，必须写"需补充"，不能假设"材料齐备"

## 4. 核心概念：中间产物体系

系统定义了一套标准化的数据结构，作为各模块之间的"通用语言"。

### 4.1 事实项（FactItem）—— "我们知道了什么"

事实是系统的 **最小原子信息单元**。用户的每个输入都会被拆解为独立的事实项。

每一条事实都记录了：

| 属性 | 含义 | 示例 |
|------|------|------|
| 事实编号 | 唯一标识 | `F-001` |
| 来源类型 | 信息从哪里来的？ | 用户表单字段 / 上传文件提取 / 诊断结果 / 规则推导 |
| 字段路径 | 对应表单的哪个字段？ | `请求.个人信息数量` |
| 原始值 | 用户填了什么？ | `500000` |
| 标准化值 | 转换后的统一格式 | `500000`（"50万" → 500000） |
| 置信度 | 这个信息有多可靠？ | 用户直接填写的 = 1.0；AI 推断的 ≈ 0.6 |
| 证据状态 | 有没有证明材料？ | 仅有用户声明 / 部分证据 / 有文件证明 / 经第三方验证 |
| 能否作为对外正面断言 | 可以写在报告里吗？ | 用户声明但无证明的 = 不能 |
| 是否需要用户确认 | AI推断的需确认 | 是 / 否 |

**来源类型的优先级**（当多个来源对同一信息有不同说法时，按此顺序采纳）：
1. 用户手动确认的（最高优先级）
2. 从上传文件中提取的
3. 用户表单填写的
4. AI 辅助推断的（中等置信度）
5. 规则引擎推导的
6. 系统默认值（最低优先级）

### 4.2 问题项（IssueItem）—— "发现了什么问题"

问题项是系统识别的合规风险点。它连接了"事实"和"规则"，形成风险判断。

| 属性 | 含义 | 示例 |
|------|------|------|
| 问题编号 | 唯一标识 | `I-001` |
| 标题 | 简短描述 | "企业为CIIO，触发安全评估路径" |
| 详细描述 | 问题详述 | "该企业被标识为关键信息基础设施运营者，按照《数据出境安全评估办法》第四条，CIIO向境外提供数据应当申报安全评估。" |
| 分类 | 属于哪个领域？ | 路径问题 / 数据范围 / 同意 / 接收方 / 合同 / 安全措施 / 文件缺失 等（共30+种分类） |
| 严重程度 | 有多严重？ | 低 / 中 / 高 / 阻断（BLOCKER） |
| 确定性 | 有多确定？ | 已确认问题 / 疑似问题 / 建议复核项 |
| 关联事实 | 基于哪些事实？ | `["F-001", "F-003"]` |
| 关联规则 | 依据哪些法规？ | `["法规引用编号-001", "诊断:CIIO必须申报安全评估"]` |
| 建议措施 | 用户该怎么办？ | "建议补充与境外接收方签订的数据处理协议" |
| 影响输出 | 影响哪些章节？ | `["第2章", "第4章"]` |
| 缺失材料 | 需要补什么？ | `["与境外接收方的数据处理协议"]` |

**三级确定性分类**决定了报告中的措辞：
- **已确认问题** → 报告中用肯定语气："经核实，企业的数据处理协议缺少再转移约束条款"
- **疑似问题** → 报告中用保留语气："尚无法确认企业是否已建立完善的数据分类分级制度"
- **建议复核项** → 报告中用建议语气："建议核验境外接收方所在国家/地区的数据保护法律环境"

### 4.3 证据项（EvidenceItem）—— "为什么这样判断"

证据项是连接"事实+法规 → 结论"的完整推理链。每个证据项回答："基于这些事实和这些法规，得出这个结论，可信度是多少？"

| 属性 | 含义 |
|------|------|
| 证据编号 | 唯一标识 |
| 主张（Claim） | 具体断言的结论 |
| 关联事实 | 依赖哪些事实项 |
| 关联规则 | 依据哪些法规条文 |
| 关联问题 | 支撑或反驳哪些问题项 |
| 法律依据 | 直接支撑结论的法规引用（带支持力度标记） |
| 辅助依据 | 提供背景但不能独立支撑的引用 |
| 文件引用 | 上传文件中的具体位置（第几页、第几段） |
| RAG查询记录 | 用哪个查询检索到的这些法规 |
| 结论 | 基于事实和法规的最终判断 |
| 使用约束 | 这个证据能用在哪？"只能支撑路径判断，不能用于违法定性" |
| 置信度 | 整体可信度（0~1） |
| 被哪些章节使用 | 证据被报告的哪些部分引用 |

**法规引用支持力度**分四级：
- **完全支撑**：法条直接适用于此问题，可独立作为法律依据
- **部分支撑**：法条部分相关，需与其他条文组合使用
- **仅背景**：只提供上下文，绝不能作为唯一依据
- **不相关**：已检索到但确认不相关，不得出现在报告中

### 4.4 生成上下文包（GenerationContextPack）—— "给AI的完整信息包"

这是传给大模型生成报告的唯一信息源。它把前几个中间产物聚合成一个结构化包：

```
生成上下文包包含：
├── 模块标识（哪个产品模块）
├── 请求编号（哪个任务）
├── 事实清单（所有 FactItem）
├── 诊断结果（路径判断）
├── 法规检索结果
├── 问题清单（所有 IssueItem）
├── 证据链（所有 EvidenceItem）
├── 路径警告（如果路径不匹配）
├── 风险摘要
├── 附件备注（从上传文件中提取的信息）
├── 法律依据上下文
├── 工作流规则上下文
├── 模板上下文
└── 输出要求
```

**核心原则**：大模型生成报告时，**不能使用上下文包之外的任何信息**，这是防止 AI "编造"事实的机制。

## 5. 流水线引擎：14步标准工作流

`WorkflowPipeline` 是所有合规模块共享的执行引擎。它定义了标准化的 14 步处理流程，每个模块通过"插件式"注册自己的业务函数来参与。

### 5.1 14步流程图

```
步骤 1: 提取企业画像（CompanyProfile）
   ↓    将用户请求中的结构化字段提取为统一的企业信息对象
步骤 2: 路径诊断（Diagnosis）
   ↓    判断应走哪条合规路径（安全评估/标准合同/认证）
步骤 3: 路径校验
   ↓    检查诊断路径是否与当前模块匹配，不匹配时生成警告
步骤 4: 构建事实清单（Facts Built）
   ↓    将请求+企业画像+诊断结果转换为标准 FactItem 列表
步骤 5: 法规检索（Retrieval Hits）
   ↓    从知识库中检索相关法规、工作流规则、模板
步骤 6: 提取附件备注
   ↓    从用户上传的文档中提取有用信息
步骤 7: 构建问题清单（Issues Built）
   ↓    基于事实+诊断+法规，用规则引擎生成 IssueItem 列表
步骤 8: 构建证据链（Evidence Built）
   ↓    为每个问题建立"事实→法规→结论"的证据链，并回填问题项的引用
步骤 9: 针对问题的补充检索（可选）
   ↓    对高严重度/阻断级别的问题进行额外的精准法规检索
步骤10: 组装生成上下文包（Context Pack Built）
   ↓    将所有中间产物聚合为传给大模型的结构化信息包
步骤11: AI 生成报告章节（Chapters Generated）
   ↓    大模型根据上下文包逐章撰写报告正文
步骤12: 一致性检查（Consistency Issues）
   ↓    检查报告内容是否与事实、问题、证据一致
步骤13: 对齐检查（Alignment Issues）
   ↓    检查报告是否覆盖了用户输入中的关键信息（如CIIO、重要数据声明）
步骤14: 修复轮次（Repair Pass）
   ↓    对发现的一致性问题尝试自动修复（最多3轮），修不了的标记为阻断
步骤15: 渲染最终产物（Render Artifacts）
   ↓    生成 Markdown 报告、Word 报告、问题清单 Excel、证据链 Excel、材料清单、ZIP 打包
步骤16: 写入可追溯清单（Trace Manifest）
   ↓    将所有步骤的可追溯事件索引写入 manifest.json
```

### 5.2 每个步骤都可追溯

每个步骤执行完成后，会将输入/输出写入独立的可追溯文件中：

```
outputs/安全自评估/{任务编号}/trace/
├── 001_用户请求.json         ← 记录了用户提交的原始请求
├── 002_企业画像提取结果.json   ← 提取后的企业信息
├── 003_诊断结果.json          ← 路径诊断结果
├── 004_路径校验.json          ← 路径校验结果
├── 005_事实清单.json          ← 构建的标准事实清单
├── 006_法规检索结果.json      ← 检索到的法规条文
├── 007_问题清单.json          ← 识别的问题列表
├── 008_证据链.json            ← 构建的证据链
├── 009_上下文包.json          ← 传给AI的完整信息包
├── 010_生成章节.json          ← AI生成的报告章节
├── 011_一致性问题.json        ← 一致性检查发现的问题
├── 012_对齐问题.json          ← 对齐检查发现的问题
├── 013_修复轮次.json          ← 修复尝试记录
└── manifest.json              ← 总索引，指向以上所有文件
```

### 5.3 修复机制（Repair Pass）

当一致性检查发现问题时（如报告写了"材料齐备"但系统知道附件缺失），修复轮次会：

1. 将问题反馈给大模型
2. 大模型针对性修改相关章节
3. 重新运行一致性检查
4. 如果问题解决，修复成功；如果仍有问题，再试（最多3轮）
5. 3轮后仍有问题的，标记为"阻断"（REPAIR_BLOCKED），报告输出被阻断

## 6. 知识检索系统（RAG）

### 6.1 多索引体系

系统维护了 **15 个向量索引**，按三个维度组织：

```
        中国法域(CN)    欧盟法域(EU)    美国法域(US)
法律条文    ✓               ✓               ✓
工作流规则  ✓               ✓               ✓
标准条款    ✓               ✓               ✓
模板       ✓               ✓               ✓
测试用例    ✓               ✓               ✓
```

每个索引包含：
- **数据文件**（`.jsonl`）：存储条文/规则/模板的分块文本
- **向量文件**（`.vector.json`）：存储对应的向量表示

### 6.2 混合检索策略

检索时同时使用两种方式，综合打分：

1. **语义向量检索**：计算用户查询与知识库条文的语义相似度
2. **关键词词汇检索**：精确匹配关键词

两种方式各有权重，综合得分后进行重排序。

### 6.3 检索流转

```
用户查询
  ↓
预处理（识别法域、合规路径提示、改写查询）
  ↓
过滤无关话题
  ↓
路由到对应法域的多个索引
  ↓
混合检索（语义+关键词）
  ↓
重排序（去重、按相关度排列）
  ↓
使用策略过滤（按模块允许的使用范围过滤）
  ↓
组装检索结果包
  ↓
（可选）调用外部 DeliLegal API 补充检索
```

### 6.4 知识库管理与使用策略

系统有一套完整的知识库生命周期管理：

- **文档解析**：支持 PDF、Word、Markdown 等格式
- **文本分块**：将长文档切分为适合检索的语义块
- **向量化**：使用嵌入算法生成向量
- **使用策略过滤**：每个知识源标记了允许哪些模块、哪些阶段使用

### 7.2 模块一：数据出境安全自评估（assessment）⭐ 主模块

**功能**：为中国企业生成符合《数据出境安全评估办法》要求的《数据出境风险自评估报告》。

**适用场景**：企业需要向国家网信办申报数据出境安全评估时。

**用户需要填写的信息**：
- 企业名称、所属行业

- 是否涉及重要数据出境
- 个人信息数量、敏感个人信息数量

- 数据资产清单（每条数据的类型、是否重要数据、必要性等）
- 境外接收方信息（名称、角色、安全认证等）
- 下游处理者信息
- 法律文件审查（数据出境协议的六大核心条款是否完备）
- 安全能力信息（管理措施、技术措施、认证情况）
- 合规历史（是否有过处罚）
- 个人信息保护措施（单独同意情况、告知内容）
- 系统链路信息（国内外系统、传输链路）
- 自评估工作信息（起止日期、参与部门）

**报告包含的8个章节**：
1. **自评估工作概述**：评估背景、范围、过程
2. **数据出境涉及业务和信息规模**：哪些数据、多少条、来源
3. **数据出境必要性及合法正当性**：为什么需要出境、法律依据

8. **自评估结论**：综合判断和建议

## 8. 路径诊断引擎

### 8.1 诊断流程

在生成任何报告之前，用户首先需要完成"路径诊断"——这是系统最独特的交互式模块。

**核心问题**：企业应该走哪条合规路径？

中国法律规定了三条主要路径：
1. **安全评估**（最严格）：适用于 CIIO、重要数据出境、大量个人信息出境
2. **标准合同备案**（中等）：适用于中等规模个人信息出境
3. **个人信息保护认证**（较宽松）：适用于特定情况

### 8.2 诊断决策树

诊断引擎基于一份结构化的决策树（JSON 文件），通过问答逐步缩小范围：

```
问：企业的行业类型？
  ├── 属于 CIIO 重点行业（金融、能源、交通等）→ 高概率安全评估
  ├── 不属于 → 继续
  │
问：是否涉及重要数据出境？
  ├── 是 → 触发安全评估
  ├── 否 → 继续
  ├── 不确定 → 启动"重要数据判断代理"（AI辅助判断）
  │
问：涉及多少个人信息？
  ├── ≥ 100万人 → 触发安全评估
  ├── 10万~100万人（含敏感个人信息 ≥ 1万人）→ 触发安全评估
  ├── 1万~10万人 → 标准合同备案
  ├── < 1万人 → 可走认证或其他路径
  │
问：是否涉及个人信息？
  ├── 不确定 → 启动"个人信息分类代理"（AI辅助判断）
  │
问：出境场景？
  ├── 员工人力资源管理（境外母公司）→ 可能有豁免
  ├── 跨境购物/订机票/酒店 → 可能有豁免
  ├── 其他 → 启动"豁免判断代理"
```

### 8.3 四个 AI 辅助诊断代理

当用户对某些问题回答"不确定"时，系统不会简单地走最高风险路径（那样会增加企业不必要的合规成本），而是启动 AI 代理进行辅助判断：

| 代理 | 功能 | 触发条件 |
|------|------|---------|
| **重要数据判断代理** | 根据行业、数据描述、处理目的判断是否涉及重要数据 | 用户无法确认是否涉及重要数据 |
| **个人信息分类代理** | 判断涉及的数据是否属于个人信息/敏感个人信息 | 用户无法确认是否涉及个人信息 |
| **豁免判断代理** | 判断特定场景是否可能适用豁免规则 | 场景为"其他"或非标场景 |
| **澄清代理** | 对模糊回答进行追问和澄清 | 回答模糊或矛盾 |

### 8.4 诊断结果

诊断完成后，系统给出：
- **推荐路径**：安全评估 / 标准合同 / 认证
- **风险等级**：高 / 中 / 低
- **诊断理由**：为什么推荐这条路径（引用的法律依据和触发条件）
- **匹配的规则编号**：触发了决策树中的哪条规则

这个诊断结果会作为后续报告生成的重要输入之一。

## 10. 可追溯与审计体系

### 10.1 三层可追溯

系统的可追溯体系分为三层：

**第一层：步骤可追溯**
- 每个流水线步骤的输入/输出都记录为独立的 JSON 文件
- 文件名按序号排列，时间线一目了然
- `manifest.json` 索引所有可追溯文件

**第二层：引用可追溯**
- 每个事实、问题、证据都有唯一编号
- 问题 → 事实（`事实引用列表`）
- 问题 → 规则（`规则引用列表`）
- 证据 → 事实 + 规则 + 问题
- 报告中的每句结论都标注了引用来源

**第三层：操作可追溯**
- 用户何时提交了请求
- 大模型何时被调用、输入了什么、输出了什么
- 何时进行了修复、修复了什么

### 10.2 可追溯记录器（TraceRecorder）

可追溯记录器是系统的"黑匣子"：

- **写入机制**：每个步骤完成后，自动将数据序列化为 JSON 文件
- **订阅模式**：支持实时订阅可追溯事件，用于 WebSocket 推送到前端
- **上下文变量**：使用 Python 的 `ContextVar` 机制，确保多任务并行时互不干扰
- **清单生成**：所有步骤完成后，自动生成 `manifest.json` 总索引

### 10.3 引用注册表（CitationRegistry）

法规引用有专门的管理系统：

- **注册**：每条法规引用在生成时被注册
- **编号**：自动分配格式为 `CIT-{模块}-{序号}` 的唯一编号
- **审计**：记录每条引用的创建时间、创建者、使用位置
- **后处理**：报告中的引用占位符 `{{CIT-xxx}}` 在最终渲染时被替换为规范的脚注格式

## 11. 完整运行案例

让我们以一个真实案例走通整个流程，帮助理解系统如何运作。

### 案例背景

**某金融科技公司**（假设名称："星辰支付科技有限公司"）：
- 行业：金融科技
- 被认定为 CIIO（关键信息基础设施运营者）
- 向新加坡的母公司传输 80 万条用户交易数据
- 数据中包含 5 万条敏感个人信息（支付记录）

## 附录：技术术语对照表

| 技术名词 | 通俗解释 |
|---------|---------|
| **RAG**（检索增强生成） | 在让 AI 回答之前，先从知识库中检索相关资料，把资料和问题一起交给 AI，这样 AI 的回答更准确、有依据 |
| **向量索引** | 将文本转化为数学向量（一串数字），相似的文本向量距离近，检索时找距离最近的 |
| **流水线（Pipeline）** | 将复杂的处理过程拆分为多个按顺序执行的步骤，每个步骤做一件事 |
| **中间产物** | 流水线执行过程中产生的半成品数据（如事实清单、问题清单），不是最终报告但对用户有参考价值 |
| **LLM**（大语言模型） | 就是常说的 "AI 大模型"，如 GPT、Claude 等，用来理解和生成文本 |
| **CIIO** | 关键信息基础设施运营者——法律对运营关键信息基础设施的企业的特殊称谓 |
| **PII** | 个人信息——能识别到具体个人的信息（姓名、身份证号、电话等） |
| **SPI** | 敏感个人信息——一旦泄露可能严重危害个人权益的信息（银行卡号、健康信息、行踪轨迹等） |
| **重要数据** | 中国法律概念，指一旦遭到篡改、破坏、泄露可能危害国家安全、经济运行、社会稳定的数据 |
| **SCC** | 标准合同条款（Standard Contractual Clauses）——用于规范数据出境双方权利义务的标准合同文本 |
| **BCR** | 约束性公司规则（Binding Corporate Rules）——跨国公司内部的数据保护规则 |
| **DPIA** | 数据保护影响评估（GDPR 要求） |
| **TIA** | 传输影响评估（GDPR 对数据跨境传输的要求） |
| **PIPIA** | 个人信息保护影响评估（中国《个人信息保护法》要求） |
| **CPRA** | 加州隐私权法案（California Privacy Rights Act） |
| **WebSocket** | 一种保持长连接的通信协议，前端和后端可以实时互发消息，不需要前端反复轮询 |
