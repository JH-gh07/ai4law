## 系统总览：两层架构

AI4Law 系统在业务上分为两层：

```
第一层：路径层 —— 判断"企业应该走哪条合规路径"
第二层：功能层 —— 根据路径和任务类型，生成审查意见、表格清单或文书草案
```

**第一层先跑，第二层后跑**。路径层的判断结果会传递到功能层，作为功能层执行业务逻辑的重要输入。

系统支持的三个法域：

| 法域 | 路径层 | 功能层模块 |
|------|--------|----------|
| 中国（CN） | 中国路径诊断 | 安全自评估、数据流检查、标准合同审查、PIPIA、通用合同审查 |
| 欧盟（EU） | 待设计 | EU SCC审查、BCR审查、DPIA、TIA |
| 美国（US） | EO14117 适用性判断 | CPRA 合规诊断 |

## 第一层：路径层

路径层解决的核心问题是：

> 企业当前业务场景到底适用哪类合规要求？是否应当进入某个具体业务模块？

路径层的处理逻辑统一为：

```text
用户输入业务情况
  → 系统按规则判断是否命中
  → 检查法规依据是否存在
  → AI 做一致性复核
  → 输出路径适用性报告
```

关键原则：**主判断必须来自规则引擎，不由 AI 直接决定**。AI 的作用是复核——检查规则结论是否与用户事实矛盾、是否存在缺失信息、是否存在过度判断、报告中的表述是否稳妥。

### 1. 中国路径诊断（diagnosis）

**解决的问题**：中国企业向境外传输数据时，该走三条路径中的哪一条？

- **安全评估**（最严格）：需向国家网信办申报
- **标准合同备案**（中等）：签订标准合同并向省级网信办备案
- **个人信息保护认证**（较宽松）：通过专业机构认证

#### 1.1 输入：用户回答的诊断问卷

系统收集的诊断信息分五个模块：

**核心阈值判断（4题）**：
- 是否属于关键信息基础设施运营者（CIIO）
- 是否向境外提供重要数据
- 近12个月累计向境外提供的个人信息人数
- 近12个月累计向境外提供的敏感个人信息人数

以上4题均支持三态：是 / 否 / 不确定。

**场景判断（扩展题）**：
- 出境数据是否不含个人信息且不涉及重要数据
- 本次数据出境的主要业务场景（履行合同/人力资源管理/紧急情况/履行法定职责/其他商业目的）
- 境外数据接收方类型（集团内部关联公司/独立第三方）
- 出境目的简述

**业务基础信息**：企业名称、行业、业务渠道、服务对象、公司规模。

**数据处理核心信息**：是否处理个人信息、个人信息类型列表、敏感信息类型列表、是否处理重要数据、重要数据类型列表、数据来源、处理活动、数据体量范围、留存期限等。

**数据流转与共享信息**：是否向第三方共享、第三方类型、是否跨境传输、跨境目标地区、是否有数据商业化、是否有委托处理、授权方式。

**业务系统与技术架构**：业务系统列表、已部署的安全措施、已有的合规文件、是否有过处罚或投诉。

#### 1.2 处理流程：三层递进

**第一层：数据规范化**

系统在运行规则之前，先对用户的回答做一轮智能补全。这一步不使用 AI，而是基于确定性规则：

- 用户说"不确定"是否涉及重要数据，但如果他在数据处理模块明确填了重要数据类型，系统自动将"不确定"校正为"是"
- 用户说"不确定"是否涉及个人信息，但如果他填了个人信息类型列表，系统校正为"是"
- 用户没填个人信息数量，但选了数据体量范围（如"100-1000万条"），系统自动估算一个中间值
- 用户没填敏感个人信息数量，但填了敏感信息类型，系统按体量范围推算
- 用户选了"独立第三方"作为接收方类型，但实际上既没有向第三方共享也没有委托处理，系统校正为"集团内部"

这一步的目的是**让规则引擎能基于尽量完整的信息做判断**，而不是因为用户漏填或选错就直接掉到兜底路径。

**第二层：AI 代理辅助澄清**

当规范化之后仍有关键字段为"不确定"时，系统不会直接走兜底逻辑，而是启动 AI 代理做辅助判断。三个 AI 代理按优先级触发：

| 代理 | 触发条件 | 做什么 |
|------|---------|--------|
| **重要数据判断代理** | 用户不确定是否涉及重要数据 | 根据行业、数据描述、处理目的、数据类型，判断是否可能涉及重要数据，给出建议值和置信度 |
| **个人信息分类代理** | 用户不确定是否涉及个人信息 | 根据数据描述、行业、使用场景，判断数据是否构成个人信息、是否存在重识别风险 |
| **豁免判断代理** | 用户选择的场景为"其他" | 根据出境目的、数据描述、接收方类型、是否集团内传输，判断是否可能适用某种豁免情形 |

代理的输出会回填到问卷中（如将"不确定"改为代理建议的"是"或"否"），然后规则引擎基于更新后的问卷重新判断。

**第三层：决策树规则匹配**

规则定义在一个结构化的决策树中，按优先级从高到低逐条匹配，命中第一条即返回。

决策树的10条规则按匹配顺序为：

```
优先级 1：豁免规则（先看能不能免）
  ├── 规则1：不含个人信息且不涉及重要数据 → 豁免，无需申报
  ├── 规则2：为履行合同/向消费者提供服务所必需 + 规模未达门槛 → 豁免
  ├── 规则3：跨国公司内部人力资源管理 + 集团内传输 + 规模未达门槛 → 豁免
  ├── 规则4：紧急情况保护自然人生命健康财产 + 非CIIO + 非重要数据 → 豁免
  └── 规则5：履行法定职责或法定义务 + 非CIIO + 非重要数据 → 豁免

优先级 2：强制安全评估规则
  ├── 规则6：是 CIIO → 安全评估
  ├── 规则7：涉及重要数据出境 → 安全评估
  ├── 规则8：个人信息 ≥ 100万人 → 安全评估
  └── 规则9：敏感个人信息 ≥ 1万人 → 安全评估

优先级 3：兜底规则
  └── 规则10（默认）：以上都不命中 → 标准合同备案或认证路径
```

**第四层：AI 推测兜底**

当以上三层都无法给出可靠结论时（关键字段大量为"不确定"且缺乏结构化信号），系统进入 AI 推测模式。此时系统会构造一个结构化提示词，让 AI 基于已有信息给出推测性结论。推测结论会明确标注"结论来源 = AI推测"、"置信度 = 低"，并要求用户补充信息后重新判定。

**第五层：AI 生成专业解释**

规则命中后，系统会用 AI 将规则的简短描述扩展为 2-3 句专业的合规解释，包括：指出关键触发点、给出一句行动建议。如果 AI 不可用，则使用预设的中文解释模板。

#### 1.3 输出：路径诊断结果

诊断完成后输出：

| 输出字段 | 含义 | 示例 |
|---------|------|------|
| 推荐路径 | 企业应走的合规路径 | `security_assessment`（安全评估）/ `scc_or_certification`（标准合同或认证）/ `exemption`（豁免） |
| 法律依据 | 触发了哪些法规条文 | `["个人信息保护法 第40条", "数据出境安全评估办法 第4条"]` |
| 判定理由 | 为什么推荐这条路径 | "企业被识别为CIIO，按照《数据出境安全评估办法》第四条，CIIO向境外提供个人信息和重要数据应当申报安全评估。" |
| 行动建议 | 下一步该做什么 | 安全评估路径 → 整理数据出境清单、生成自评估报告、准备申报材料；标准合同路径 → 确定实施路径、生成PIPIA报告、准备备案材料 |
| 风险等级 | 综合风险评级 | 高 / 中 / 低（由规则引擎根据 CIIO、重要数据、个人信息规模、敏感信息规模综合计算） |
| 结论来源 | 判断是怎么来的 | `rule`（规则命中）/ `ai_inference`（AI推测） |
| 置信度 | 判断有多可靠 | 规则命中 = 高；AI推测 = 低或中 |
| 匹配的规则编号 | 触发了决策树中哪条规则 | `ciio` / `important_data` / `pii_threshold` 等 |
| 不确定性说明 | 有哪些不确定因素 | AI代理的判断记录、缺失的信息项 |
| 最终解释 | 面向用户的完整解释 | AI生成的2-3句专业中文说明 |

### 2. 美国 EO14117 对华数据流动适用性判断（us_14117）

**解决的问题**：判断特定数据交易是否受到美国第14117号行政令（"防止受关注国家获取美国人大量敏感个人数据和政府相关数据"）的管辖。

#### 2.1 输入

- 企业名称、交易描述、交易类型
- 涉及的数据类别（含各类别的美国主体数量）
- 涉及的实体信息（名称、国别、是否属于"受覆盖主体"）
- 附件材料

#### 2.2 处理流程

**第一步：规则引擎先行**

与美国 EO14117 相关的判断核心是一个确定性的规则引擎。规则引擎会：

- 逐项判断每个实体是否属于"受覆盖主体"（covered person）
- 逐项判断每类数据是否触及批量阈值（bulk threshold）
- 判断交易类型是否属于受限制交易类别
- 给出交通灯信号（红/黄/绿）

这一步不使用 AI，完全基于确定的规则逻辑。

**第二步：AI 边界复核**

规则引擎运行完成后，AI 代理介入对"边界模糊"的情况进行复核：

- 哪些实体被判定为"受覆盖主体"但置信度不足 85%？
- 哪些数据类别的美国主体数量刚好在阈值边界（±10%）？
- 交易类型是否为"其他"（规则难以明确分类）？

AI 代理会逐项给出建议：某些实体是否需要标记为"需人工复核"。

**第三步：接入标准工作流**

规则引擎的结果作为一个特殊的"诊断结果"，注入后续的标准流水线：事实提取 → 法规检索 → 问题构建 → 证据构建 → 上下文包 → AI 生成章节 → 一致性校验 → 输出。

**第四步：RAG 检索时 AI 辅助改写查询**

在法规检索阶段，AI 代理会根据规则引擎的命中摘要、数据类别、交易类型，生成更精准的检索查询语句，替代简单的关键词拼接。

#### 2.3 输出

- **交通灯信号**：红（受限制/禁止）/ 黄（需审查/有条件允许）/ 绿（不受限）
- **风险矩阵**：逐实体、逐数据类别的详细风险分布
- **规则命中清单**：触发了哪些具体规则
- **合规报告**（4章）：总体结论与传输可行性 → 风险详情与分析 → 合规措施建议与行动清单 → 附件与持续监控

### 3. 欧洲路径判断（待设计）

当前系统中欧盟法域没有独立的路径诊断模块。现有的 EU SCC、BCR、DPIA、TIA 模块均假设用户已经知道需要进入该模块。

未来设计方向与中国路径诊断类似：通过交互式问答判断企业应进入哪个欧盟合规模块。

### 路径层的输出规范

无论是哪个法域的路径层，最终都应输出一份结构化的路径报告：

```text
推荐路径
命中规则（哪些规则被触发）
未命中规则（哪些规则被检查但未触发，说明为什么不适用）
缺失事实（哪些信息用户没有提供，影响判断的完整性）
法规依据（每个命中规则对应的法律条文）
一致性复核结果（AI 对规则结论的复核意见）
下一步建议（建议进入功能层的哪个模块）
```

## 第二层：功能层

功能层在路径层之后运行。根据任务性质分为三类：

---

### 第一类：合同审查类

> **一句话定义**：审已有文本，给修改建议。

企业已经有合同、协议、制度或条款文本，系统帮助判断原文哪里有问题、为什么有问题、应该怎么改。

**共同业务流程**：

```text
用户上传合同或条款文本
  → 系统读取原文
  → 拆分成可审查的条款单元
  → 判断每条条款的业务类型
  → 匹配合规要求（GDPR / 标准合同办法 / BCR 要求 / 数据保护法规）
  → 逐条审查：哪里写得不清楚、义务不完整、可能不合法、需要补充
  → 生成风险等级和修改建议
  → 输出审查报告或批注版文件
```

**共同要回答的问题**：

```text
哪里写得不清楚？
哪里义务不完整？
哪里可能不合法？
哪里需要补充？
应该怎么改？
依据是什么（哪条法律/标准）？
```

#### 1.1 通用合同审查（review）

**适用场景**：用户上传任意数据保护相关的合同、隐私政策、数据处理协议，系统自动识别文档类型并按对应标准审查。

**处理流程**：

**第一步：文档分类**

系统首先判断上传的文档属于什么类型：
- 隐私政策（Privacy Policy）
- 数据处理协议（DPA）
- 标准合同（SCC）
- 数据安全协议（Data Security Agreement）

分类基于文档内容特征（关键词、条款结构），结合 AI 语义判断。

**第二步：场景提取**

从文档中提取业务场景信息：涉及哪些数据处理活动、数据流向哪里、涉及哪些参与方角色（控制者/处理者/子处理者）、数据传输是否跨境。

**第三步：条款拆分**

将文档按条款结构拆分为独立的审查单元。每个条款单元包含：条款标题、条款正文、条款在原文中的位置。

**第四步：条款分类**

对每个条款单元进行分类，判断它属于哪类合规要求：
- 数据处理目的与范围
- 数据主体权利
- 安全保障措施
- 再转移/分包管理
- 数据泄露通知
- 数据删除与留存
- 审计权
- 法律责任与赔偿
- 管辖法律与争议解决

**第五步：条款级审查**

对每个条款逐一审查。审查逻辑是"规则引擎 + 专项审查器"的组合：

- **专项审查器**：针对不同文档类型有专门配置的审查规则。例如隐私政策审查器会检查是否包含13类必要告知项；SCC合同审查器会检查是否包含中国标准合同办法要求的6大核心条款。
- **规则引擎**：加载审查规则手册，逐项比对条款内容与规则要求，标记"满足/部分满足/不满足/未涉及"。

审查时会同时检索相关的法规依据（中国法、GDPR等），将法规条文与条款内容做关联。

**第六步：交叉文档一致性检查**

如果用户同时上传了多份文档（如隐私政策 + DPA + 标准合同），系统会做交叉一致性检查：
- 隐私政策中描述的数据处理目的是否与DPA中的一致
- 不同文档中对"个人数据"的定义是否一致
- 标准合同中的分包条款是否与DPA中的一致
- 是否存在互相矛盾的义务描述

**第七步：引用相关性校验**

对审查中使用的法规引用做相关性校验——判断引用的法规条文是否真的适用于当前条款，避免"看起来相关但其实无关"的引用。

**第八步：输出**

输出分两种形式：

- **审查报告**：按文档/条款组织，每条问题包含：原文定位（第几条第几款）、问题类型（缺失/模糊/不合法/冗余）、风险等级、修改建议、法规依据。
- **批注版文档**：在原文档上叠加批注（Word批注格式），直接在有问题的地方标注问题和建议，用户可以对照原文查看。

涉及多文档时还输出一份交叉一致性报告。

#### 1.2 中国标准合同审查（SCC）

**适用场景**：企业已经起草了标准合同（或已有合同文本），系统审查该合同是否符合《个人信息出境标准合同办法》的要求。

**处理流程采用 9 个 AI 代理 + 规则引擎的架构**：

**代理1：路径诊断代理**

审查的第一步是再次确认用户的合规路径是否正确。即使用户选择进入了SCC模块，路径诊断代理也会基于用户填写的信息（是否CIIO、是否涉及重要数据、个人信息和敏感信息数量、接收方类型和国别、行业、是否人力资源管理、是否认证机构等），独立判断用户实际上应该走安全评估、标准合同还是认证路径。

如果代理判断用户实际应走安全评估路径但用户选择了标准合同，会在后续报告中标记路径不匹配风险。

**代理2：数据分类代理**

对用户填写的每个数据字段做逐字段级别的审查：该字段是否构成个人信息、是否构成敏感个人信息、出境必要性评估。这个代理为后续的条款审查提供数据基础。

**代理3：合同审查代理**

这是整个模块最核心的代理。系统会从用户上传的文件中提取合同正文（优先匹配文件名包含"scc"、"contract"、"合同"、"协议"、"dpa"的文件），然后由代理逐条审查：

- 合同是否包含标准合同办法要求的必备条款
- 每项条款的表述是否规范、是否有模糊之处
- 数据出境目的、方式、范围是否明确
- 境外接收方的义务是否完整
- 再转移约束条款是否存在
- 数据安全事件通知机制是否明确
- 争议解决和法律适用条款是否合理

**代理4：合法性基础审查代理**

审查企业主张的每项合法性基础（同意/合同必需/法定义务/正当利益等）是否成立：
- 如果是"同意"：隐私政策中是否有相应告知？同意记录是否留存？
- 如果是"合同必需"：合同摘要是否支持这一主张？
- 如果是"人力资源管理"：员工手册和集体协议是否覆盖？
- 代理人会结合用户上传的隐私政策摘要、合同摘要、员工手册摘要、集体协议摘要、同意记录摘要做交叉验证。

**代理5：证据核验代理**

针对用户做出的每项主张（如"已取得80万人的个人信息主体同意"、"标准合同草案已按要求编制"、"满足人力资源管理豁免条件"），代理会检查：
- 是否有对应的上传材料支撑？
- 材料摘要中是否提及相关内容？
- 主张与材料之间是否存在矛盾？

**代理6：RAG 检索规划代理**

在完成问题识别后，代理会根据路径类型、已识别的问题列表、行业、接收方国别、数据类型、风险点，规划哪些法规条文需要精准检索，生成结构化的检索计划（而非简单关键词拼接）。

**代理7：报告生成**

基于以上所有产出，按4个章节生成审查报告：
1. 审查依据说明
2. 总体合规评级
3. 条款级问题清单
4. 修订建议与行动计划

**代理8：报告审稿代理**

生成报告后，代理对报告做审稿复核，检查报告中的结论是否有依据支撑、修改建议是否具体可操作、是否有遗漏的风险点。

**代理9：澄清代理**

在流程的任何阶段，如果发现用户输入存在模糊或矛盾，澄清代理会生成需要用户澄清的问题。

**规则引擎**：

除了代理外，模块还有两个确定性规则组件：
- **硬门槛评估**：检查 CIIO、重要数据、个人信息规模是否触发安全评估强制申报的门槛
- **路径确定**：基于硬门槛评估结果，给出最终的路径判断

**容错设计**：所有代理的失败都不会阻断流水线——代理报错时静默回退到基于规则的结果。

**最终输出**：
- 审查报告（Word + Markdown）
- 批注版合同文档
- PIPIA 报告（如适用）

#### 1.3 欧盟标准合同条款审查（EU SCC）

**适用场景**：企业使用欧盟标准合同条款（SCC）作为数据传输工具时，审查SCC文件的完整性和合规性。

**处理流程**：

**第一步：SCC 文档解析**

使用专门的 SCC 解析器，从用户提供的文本中识别：
- 使用的 SCC 模块类型（模块一：控制者→控制者 / 模块二：控制者→处理者 / 模块三：处理者→子处理者 / 模块四：处理者→控制者）
- 导出方角色、导入方角色
- 各条款的原文内容
- 可选条款（Docking Clause、 redress 机制等）的选用情况

**第二步：AI 文档结构补全**

文档结构代理会检查解析结果，对缺失的字段和条款进行补充推断：
- 如果用户没有声明导出方/导入方角色，代理从文档内容中推断
- 如果某些必要条款在解析时被遗漏，代理从原始文本中定位

**第三步：传输链路构建**

基于导出方角色、导入方角色、SCC模块类型，构建数据传输链路图。链路包含每一跳的参与方角色和关系。

**第四步：AI 传输链路推理**

传输链路代理对链路做深度分析：
- 链路中每一跳的法律关系是否合理
- 是否存在隐含的子处理关系未被文档覆盖
- 给出链路中的风险提示（如"第三国传输缺少充分性认定依据"）

**第五步：EU SCC 规则引擎**

规则引擎对 SCC 文档做逐条款的合规检查：
- 必要条款是否完整
- 可选条款的选用是否合理
- 是否有与 GDPR 要求冲突的条款
- 传输影响评估（TIA）是否已包含
- 补充措施是否充分

**第六步：接入标准工作流**

后续走标准流水线：事实提取 → 法规检索 → 问题构建 → 证据构建 → 上下文包 → AI 生成章节 → 一致性校验 → 输出。

**最终输出**（4章报告）：
1. 文件概要
2. 总体合规评级
3. 条款级审查发现
4. 法规依据与修改建议

#### 1.4 约束性公司规则审查（BCR）

**适用场景**：跨国公司制定了约束性公司规则（BCR），系统审查BCR文件是否符合GDPR第47条的要求。

**BCR 的背景**：BCR 是跨国公司内部的数据保护规则，经欧盟数据保护机构批准后，集团内部的数据跨境传输可以依赖 BCR 而非 SCC。BCR 分为 BCR-C（控制者版）和 BCR-P（处理者版），两者的义务要求不同。

**处理流程——6阶段文书驱动审查**：

**阶段1：文档解析**

将上传的 BCR 文档解析为结构化表示：章节结构、条款内容、附件列表。支持同时上传多份文档（如主文 + 附件）。

**阶段2：BCR 类型识别**

BCR 类型分类器通过关键词和结构特征判断文档属于 BCR-C 还是 BCR-P。如果类型不明确（分类器给出的实际类型为 unknown），AI 类型推理代理会对全文进行分析，统计 BCR-C 和 BCR-P 各自的特征证据数量，给出类型判断。

如果在类型不确定的情况下用户声明了某个类型，代理还会检查声明与实际内容是否一致。不一致时标记为风险项。

**阶段3：场景提取**

从文档中提取业务场景信息：
- 集团公司名称和结构
- 数据传输的范围和目的
- 在欧盟境内的责任实体（EU liable entity）

AI 角色识别代理会对文档中的实体进行分析：当正则表达式无法定位欧盟责任实体时，代理从文档上下文中推断。

**阶段4：清单式逐项审查**

这是 BCR 审查的核心步骤。

系统内置了一份 BCR 规则手册，包含 GDPR 第47条要求的全部必备要素（如 BCR-C 有10项核心要求）。审查清单检查器会逐项比对文档内容：

- **完全覆盖**：文档中明确包含了该项要求的内容
- **部分覆盖**：文档中提到了但不完整
- **模糊覆盖**：文档中有相关内容但不够明确
- **缺失**：文档中完全未涉及

对于"部分覆盖"和"模糊覆盖"的高严重度要求项，AI 覆盖分析代理会深度阅读匹配到的条款原文，判断是否需要生成问题发现。

除了核心清单，还有三个专项检查器：
- **TIA（传输影响评估）检查器**：检查 BCR 是否包含对第三国法律环境的评估
- **再转移检查器**：检查 BCR 对再转移（onward transfer）的保护标准是否充分
- **责任分配检查器**：检查 BCR 中的责任和赔偿条款是否清晰

**阶段5：AI 代理深度审查（5个代理并行）**

| 代理 | 触发条件 | 做什么 |
|------|---------|--------|
| **再转移推理代理** | 文档中有再转移相关条款但保护标准偏弱 | 判断再转移条款是否提供了充分保护，是否需要补充SCC或其他保障 |
| **TIA 完整性推理代理** | 文档中有TIA章节 | 检查TIA是否完整（是否涵盖政府访问风险、是否引用 Schrems II 和 EDPB 指南） |
| **证据覆盖代理** | 核心要求项的覆盖来源不明确 | 判断关键义务是写在BCR正文中还是仅写在附件中（附件中的约束力弱于正文） |
| **条款不匹配代理** | BCR类型与条款内容不一致 | 检测 BCR-C 文档中是否包含了本应属于 BCR-P 的处理者条款（或反之） |
| **类型推理代理** | 已在上文阶段2触发 | 判断 BCR 的准确类型 |

**阶段6：法律检索与输出**

对识别出的问题逐项检索相关 GDPR 条文和 EDPB 指南，然后：
- 风险评估聚合器对所有问题进行综合评分
- 报告渲染器生成最终审查报告

**如果用户没有上传文档怎么办？**

系统有一个基于表单的兜底审查模式。用户填写企业基本信息和数据流转情况，系统基于规则手册做简化的清单检查，生成基础审查报告。

#### 2.1 加州 CPRA 合规全景诊断

**适用场景**：企业需要了解自身在加州隐私权法案（CPRA）下的合规状态，系统生成一份"差距分析表"——哪些义务已满足、哪些有差距、差距有多大、怎么整改。

**输入**：
- 企业名称、业务模型描述、数据生命周期描述
- 适用性信息（年收入、加州消费者数量、是否买卖个人信息等）
- 告知与同意机制的描述
- 消费者权利响应机制的描述
- 数据项清单（每项含类别、是否敏感、是否出售/共享）
- 供应商清单
- Opt-out 和 Sale/Sharing 机制描述
- 隐私政策附件、数据地图附件、供应商清单附件

**处理流程——三层递进 + 规则引擎 + 代理组合**：

**第一层：附件事实提取**

用户上传的附件先经过附件提取器做结构化提取：从隐私政策中提取告知项清单，从数据地图中提取数据流转关系，从供应商清单中提取供应商信息。

然后事实提取代理对提取结果做 AI 增强：根据业务模型和数据生命周期，判断附件的完整性、识别附件中未覆盖的领域。

**第二层：事实合并**

事实合并器将"用户表单填写的信息"和"从附件中提取的信息"合并为统一的事实视图：
- 同一信息如果两处都有，按"用户表单优先"原则选择
- 一处有一处无的，标记来源
- 合并后的结果包含：适用性判断的依据、数据项完整清单、供应商完整清单、权利机制的完整描述

**第三层：规则引擎 + 代理深度审查**

**规则引擎**（确定性规则，不依赖 AI）：

对以下4个领域做确定性检查：

| 检查领域 | 检查内容 | 如何判断 |
|---------|---------|---------|
| 告知与同意 | 隐私告知是否完整、同意机制是否存在 | 检查告知文本中是否缺少关键告知项；检查是否存在"缺失/无/none"等信号词 |
| 消费者权利 | DSR（数据主体请求）响应机制是否到位 | 检查是否明确了45天响应时限、是否有Web表单/邮箱/电话三种渠道 |
| Opt-out 机制 | 如果存在数据出售/共享，是否有退出机制 | 检查出售/共享声明与退出机制的匹配性；检查"请勿出售/共享我的个人信息"链接 |
| 供应商管理 | 供应商合同是否包含 DPA 条款 | 检查供应商管理描述中是否含有 DPA/服务商条款 |

规则引擎给出的每项差距项包含：所属领域、风险等级（高/中/低）、差距描述、法律依据、整改建议、整改阶段（短期/中期/长期）、证据来源。

**敏感信息共享风险评估代理**（AI代理）：

在规则引擎之外，AI 代理对敏感个人信息（SPI）的共享风险做专门评估：
- 哪些敏感信息被哪些供应商访问？
- 每个供应商的SPI访问权限是否合理？
- 是否存在未声明的SPI共享路径？
- 用户的数据主体请求机制是否能覆盖所有SPI共享场景？

代理输出的是"差距候选项"——可能存在的差距，经差距合并器与规则引擎的结果合并。

**供应商合同合规审查代理**（AI代理）：

AI 代理对供应商合同做深度合规审查：
- 供应商清单中的每个供应商是否有对应的数据处理协议？
- 合同中的数据处理条款是否满足 CPRA 的服务商/第三方管理要求？
- 数据出售/共享是否在合同中明确界定？

代理输出的也是"差距候选项"，同样经差距合并器合并。

**一致性审查代理**（AI代理）：

在所有差距项生成后，一致性审查代理做整体复核：
- 报告的结论是否与事实一致？（如报告说"SPI 管理完善"但附件中缺少 SPI 清单）
- 高风险差距是否在报告中得到了足够强调？
- 各章节之间的风险评级是否一致？

**第四层：法规引用匹配**

对每个差距项（特别是高风险和中风险的），系统从CPRA法律知识库中检索匹配的法规条文：
- 优先做逐差距的精准检索（按差距的领域和描述定制查询）
- 精准检索无结果的，做领域级的兜底检索
- 确保低风险项也有法规引用覆盖

**第五层：报告生成与输出**

AI 按6章结构生成全景报告：
1. 执行摘要
2. 企业适用性与范围
3. 数据处理活动合规分析
4. 消费者权利保障评估
5. 敏感信息与第三方管理
6. 行动清单与优先级

**最终输出文件**：
- 合规全景报告（Word + Markdown + PDF）
- 整改路线图 Excel（按差距项的领域、风险等级、差距描述、法律依据、整改建议、整改阶段、证据来源分列）

**综合风险评级**：有任何一个 HIGH → 整体 HIGH；无 HIGH 但有 MEDIUM → 整体 MEDIUM；全部 LOW → 整体 LOW。

### 第三类：草案模板生成类

> **一句话定义**：用户输入业务事实，系统按模板生成合规文书草案。

企业没有完整文书，系统根据用户输入和固定模板，生成合规文书草案。

**共同业务流程**：

```text
用户填写业务事实和上传材料
  → 系统整理企业事实（FactItem 列表）
  → 检索法规依据（从知识库）
  → 识别风险和问题（IssueItem 列表）
  → 组装证据链（EvidenceItem 列表）
  → 形成生成上下文包（GenerationContextPack）
  → AI 按固定模板生成章节正文
  → 系统做一致性检查
  → 修复通过后输出正式草案文件
```

**与合同审查类的核心区别**：

| 维度 | 合同审查类 | 草案模板生成类 |
|------|----------|-------------|
| 用户有什么 | 已有合同/条款文本 | 只有业务事实描述 |
| 系统做什么 | 审查已有文本，找问题 | 从零生成完整文书 |
| AI 的角色 | 辅助审查、解释问题 | 主笔撰写文书正文 |
| 关键产出 | 审查意见 + 批注 | 正式文书草案 + 风险清单 |
| 核心风险 | AI 漏审问题 | AI 编造事实或违规表述 |

正因为 AI 负责主笔撰写，这类模块对 AI 有严格的约束：
- **不得编造用户在事实中未提供的信息**
- **缺失材料的地方必须写"需补充"，不能假设"材料齐备"**
- **不确定的判断必须用保留措辞**
- **报告中不能出现法律上危险的断言**

---

#### 3.1 数据出境安全自评估（assessment）

这是系统中最完整、最成熟的草案生成模块。它的任务是生成一份符合《数据出境安全评估办法》要求的《数据出境风险自评估报告》。

**输入信息**（结构化表单）：

- **基础字段**：企业名称、行业、是否CIIO、是否涉及重要数据、个人信息数量（PII）、敏感个人信息数量（SPI）、出境目的、接收方国家/地区、上传文件列表
- **数据资产清单**：每条数据的名称、描述、数据主体、信息类型、是否重要数据候选、必要性说明、体量、留存期限
- **境外接收方信息**：名称、国别/地区、角色（接收方/实际处理者/子处理者）、与企业的关系、安全认证、审计报告、法律环境摘要、处理目的和方式、存储位置
- **下游处理者信息**：名称、国别、角色、处理活动、是否被合同覆盖、再转移约束
- **法律文件审查**：已签署的法律文件名称、6大核心条款的覆盖情况（目的方式范围、境外留存位置期限、再转移约束、法律环境变化应对、违约赔偿争议解决、安全事件和个保权利）、缺失项
- **安全能力**：管理措施、技术措施、认证情况
- **合规历史**：是否有过处罚、处罚时间和原因、整改状态
- **个人信息保护**：单独同意状态、告知内容、权利响应机制
- **系统链路**：国内系统、传输链路、中转地、境外系统
- **自评估工作信息**：起止日期、参与部门、初步结论

**路径校验模式**：

系统支持三种路径校验模式：
- **仅生成**：不做路径校验，任何路径都能生成报告
- **警告但不阻断**：路径不匹配时在报告中加入警告，但仍生成
- **不匹配则阻断**：路径不匹配时拒绝生成报告

**处理流程——标准16步流水线**（由工作流引擎编排）：

```
步骤1：提取企业画像
  将用户提交的结构化字段提取为统一的企业信息对象（CompanyProfile），
  包含所有基础字段和结构化子对象的完整信息。

步骤2：路径诊断
  创建一个诊断存根（DiagnosisStub），声明推荐路径为"安全评估"。
  实际的路径诊断已在上游诊断模块完成，这里的存根是为流水线提供统一接口。
  如果用户在上游诊断中被判为非安全评估路径，但仍选择使用本模块，
  则路径校验（步骤3）会根据校验模式决定如何处理。

步骤3：路径校验
  检查诊断存根中的推荐路径是否与当前模块匹配。
  如果推荐路径不是"安全评估"但用户强行使用本模块：
  - 仅生成模式：静默通过
  - 警告但不阻断：生成路径警告文本
  - 不匹配则阻断：抛出阻断异常

步骤4：构建事实清单
  调用模块专属的事实构建器，将请求、企业画像和诊断结果转换为
  标准化的 FactItem 列表。系统将每个输入字段拆解为独立的事实项，
  每条事实标记来源类型（用户表单/附件提取/诊断结果/规则推导）、
  置信度、证据状态、能否作为对外的正面断言。

  至少生成的事实项包括：企业名称、行业、CIIO状态、重要数据状态、
  个人信息数量、敏感个人信息数量、出境目的、接收方国家/地区、
  上传文件列表、诊断推荐路径、诊断理由、数据资产条目、
  境外接收方信息、下游处理者、法律文件审查结果、安全能力、
  合规历史、个人信息保护措施、系统链路、自评估信息。

步骤5：法规检索
  调用模块专属的检索器，从中国法域知识库中检索相关法规。
  检索关键词会综合企业画像中的行业、目的、接收方国家/地区、
  CIIO和重要数据状态来构造。
  支持本地向量检索和外部法律API（DeliLegal）补充检索。
  返回结构化的法规命中列表（来源编号、法规标题、条文号、内容摘要）。

步骤6：提取附件备注
  从用户上传的文件中提取文本摘要，用于补充事实信息。
  提取结果供后续的问题构建和上下文包使用。

步骤7：构建问题清单
  调用模块专属的问题构建器（基于确定性规则，不依赖AI）。
  基于事实清单 + 诊断结果 + 检索到的法规 + 附件备注，
  用规则逐项检查是否触发合规问题。

  至少生成以下问题（规则驱动）：
  - CIIO = 是 → 触发安全评估路径问题
  - 重要数据 = 是 → 触发重要数据高风险问题
  - 个人信息 ≥ 100万 或 敏感个人信息 ≥ 1万 → 触发规模门槛问题
  - 上传文件为空 → 触发申报材料缺失问题
  - 接收方国家为空 → 触发境外接收方信息不足问题
  - 出境目的为空 → 触发出境目的不明确问题
  - 路径不匹配 → 触发路径警告问题

  每个问题都具有完整的三链引用（关联事实、关联规则、影响输出章节）。

步骤8：构建证据链
  调用模块专属的证据构建器。为每个问题构建"事实 → 法规 → 结论"的
  完整推理链。证据构建完成后，会将证据编号回填到对应的问题中。

  至少生成以下证据：
  - CIIO → 安全评估路径判断（法律依据：安全评估办法第4条）
  - 重要数据 → 安全评估路径判断（法律依据：安全评估办法第4条）
  - 个人信息规模 → 安全评估路径判断（法律依据：安全评估办法第4、5条）
  - 敏感个人信息规模 → 高风险判断
  - 接收方国家 → 境外接收方风险判断
  - 附件缺失 → 材料完整性风险判断

  每条证据包含：主张、关联事实编号、关联规则编号、法律依据（含支持力度：
  完全支撑/部分支撑/仅背景/不相关）、结论、置信度、使用约束。

步骤9：按问题补充检索（可选）
  对高严重度（HIGH/BLOCKER）的问题，逐问题构造精准查询再做一轮检索，
  确保高风险问题有充分的法规依据支撑。

步骤10：组装生成上下文包
  将前面所有中间产物聚合为一个结构化的上下文包（GenerationContextPack）：
  - 模块标识、请求编号
  - 事实清单
  - 诊断结果
  - 法规检索结果
  - 问题清单
  - 证据链
  - 路径警告（如有）
  - 附件备注
  - 法律依据上下文（由法律依据构建器从法规检索结果中提炼）
  - 写作策略（由写作策略构建器生成：哪些事实可以作为正面断言、
    哪些表述需要保守、哪些地方证据不足）
  - 生成基础包（由生成基础构建器整理：模板结构、章节要求、输出规格）

  这是传给 AI 的唯一信息源。大模型生成报告时，不能使用上下文包之外的
  任何信息——这是防止 AI "编造"事实的核心机制。

步骤11：AI 生成报告章节
  大模型从上下文包中提取与各章节相关的信息：
  - 筛选 affects_outputs 包含当前章节的问题
  - 筛选 used_by 包含当前章节的证据
  - 提取与当前章节相关的法规条文和写作策略

  生成8个章节：
  第1章 - 自评估工作概述（评估背景、范围、过程）
  第2章 - 数据出境涉及业务和信息规模（涉及哪些数据、多少条、来源）
  第3章 - 数据出境必要性及合法正当性（为什么需要出境、法律依据）
  第4章 - 境外接收方数据安全保护能力（接收方的管理和技术措施）
  第5章 - 对个人信息权益的影响（对用户权利的评估）
  第6章 - 数据安全保护措施（已采取的技术和管理措施）
  第7章 - 风险应对措施（发现的风险点和整改方案）
  第8章 - 自评估结论（综合判断和建议）

  提示词中明确要求 AI：
  - 不得编造事实清单中没有的信息
  - 每个风险判断必须引用问题编号或法规引用
  - 材料缺失处必须写"需补充"，不得假设已具备

步骤12：一致性检查
  系统对生成的报告内容做三个维度的一致性检查：

  维度1——上下文包内部引用完整性：
  每个问题引用的"事实编号"是否都能在事实清单中找到？
  每个问题引用的"规则编号"是否都能在法规检索结果中找到？
  每个证据引用的"事实编号"和"规则编号"是否都存在？

  维度2——报告内容与上下文包的一致性：
  HIGH/BLOCKER 级别的问题是否在报告正文中被提及？
  如果附件缺失问题存在，报告是否写了"材料齐备"（这是矛盾）？
  如果路径警告存在，报告是否包含了路径提示或风险说明？

  维度3——报告内容与用户输入的对齐：
  报告是否明确提及了 CIIO 状态？
  报告是否明确提及了重要数据的状态？
  报告中的个人信息数量是否与用户输入一致？
  报告是否覆盖了用户填写的境外接收方所在的国家/地区？

步骤13：一致性修复
  如果一致性检查发现了问题，系统不会直接输出，而是进入修复流程：
  1. 将问题描述和受影响的章节发送给大模型
  2. 大模型针对性修改相关章节
  3. 重新运行一致性检查
  4. 最多修复3轮
  5. 3轮后仍有未解决的问题 → 标记为"修复阻断"，
     报告中加入阻断警告，告知用户需要人工介入

步骤14：渲染最终产物
  生成完整的输出文件包：
  - Markdown 格式报告
  - Word 格式报告
  - 问题清单（JSON + Excel）
  - 证据链（JSON + Excel）
  - 材料补充清单（Excel）
  - ZIP 完整打包（包含以上所有文件）

步骤15：写入可追溯清单
  将以上所有步骤的输入输出写入可追溯文件夹中，
  生成一份总结清单文件（manifest）索引所有步骤记录。
```

**8个内置 AI 代理**（用于辅助特定子任务，不参与主线判断）：

| 代理 | 作用 |
|------|------|
| 附件解析代理 | 从上传的PDF/Word中提取结构化信息 |
| 受控修复代理 | 在修复流程中，按修复策略修改章节内容 |
| 数据分类代理 | 辅助判断数据资产清单中的分类是否合理 |
| 文书规划代理 | 规划报告各章节的写作策略和侧重点 |
| 表达校准代理 | 检查报告措辞是否符合表达安全规则 |
| 输入规范化代理 | 将用户自然语言输入标准化为结构化信息 |
| 法律引用代理 | 补充和验证法规引用 |
| 合规推理代理 | 辅助构建事实→法规→结论的合规推理链 |

#### 3.2 数据流合规检查（CN Flow）

**适用场景**：企业还不确定是否触发合规义务时，先用此模块检查数据流场景，判断触及了哪些监管约束，得到风险评级。

**输入**：与安全自评估类似的结构化表单（企业信息、数据处理情况、数据流转路径等），但侧重于数据流的路径分析而非评估材料完整性。

**处理流程**：

同样接入标准工作流引擎，流程为：提取企业画像 → 路径诊断 → 路径校验 → 事实构建 → 法规检索 → 附件备注提取 → 问题构建 → 证据构建 → 上下文包组装 → AI 生成章节 → 一致性检查 → 修复 → 输出。

**独特之处**：

- 事实构建器的关注点是"数据从哪里来、经过哪里、到哪里去"，而不是"有哪些申报材料"
- 问题构建器更侧重于"触及了哪些监管约束"（如跨境传输、第三方共享、目的限制等），而非"材料是否齐全"
- 每个风险项同时带有风险等级，便于快速分级

**报告章节**（4章）：
1. 场景定义与适用范围（这次检查覆盖什么场景）
2. 数据类型与实体结构分析（涉及哪些数据、哪些参与方）
3. 限制条件命中分析（触发了哪些法规限制）
4. 风险分级与处置建议（总体风险评级和行动建议）

---

#### 3.3 个人信息保护影响评估（PIPIA）

**适用场景**：企业在处理敏感个人信息、委托处理、向第三方提供、跨境传输、自动化决策等场景，需要生成 PIPIA 报告。

这是中国《个人信息保护法》第55条的要求，目前是系统中最简单的草案生成模块（基本架构已搭建，待完善）。

---

#### 3.4 数据保护影响评估（DPIA）

**适用场景**：企业在欧盟 GDPR 下，使用新技术或大规模处理可能对自然人权利自由造成高风险时，需要完成 DPIA。

**内置9个 AI 代理**：覆盖触发判断、处理活动描述、必要性比例性分析、风险识别与评估、风险缓解措施映射、DPO咨询建议、内部审查、外部草稿、一致性修复。

---

#### 3.5 传输影响评估（TIA）

**适用场景**：企业在 GDPR 下将个人数据传输到第三国时，需要评估第三国法律环境对数据保护的影响，并识别需要的补充措施。

**典型流程**：评估接收国的数据保护水平 → 识别传输链路中每段的风险 → 判断现有合同和技术措施是否充分 → 推荐需要补充的保障措施。

## 跨层能力

以下三个能力横跨路径层和功能层，是所有模块共享的基础设施。

---

### 一、引用展示与可追溯

平台的目标不是只在报告末尾列一串参考文献，而是实现 **正文内联引用交互链路**：

```text
正文中的判断 / 风险 / 建议
  → 行内显示可交互的引用标记
  → 鼠标悬浮时展示来源预览卡片
  → 点击后跳转到知识库中对应的法规/指南/模板原文
  → 尽可能直接定位到对应条文、章节或条款
```

#### 引用的分层（五种类型，不能混用）

| 引用类型 | 用途 | 示例 |
|---------|------|------|
| 法规依据引用 | 支撑法律判断 | 《个人信息保护法》第38条 |
| 官方指南/模板要求引用 | 支撑实务要求或文书结构 | 《数据出境安全评估申报指南（第二版）》 |
| 案例或背景参考引用 | 支撑背景理解，不替代强制法依据 | 某省网信办安全评估案例 |
| 用户材料引用 | 支撑事实来源 | 用户上传的《数据处理协议》第5条 |
| 系统内部证据链引用 | 支撑系统为什么这样判断 | 证据链节点 E-003 |

#### 引用的可见级别

系统区分对内和对外的可见级别：

**客户视图**：仅展示可对外表达的法规/指南/模板引用。不暴露内部推理过程、未验证的引用、被丢弃的引用。

**内部视图**：额外展示用户材料引用、内部证据链、置信度不足的引用、检索到但被判定为不相关的引用。

#### 后端支撑机制

- **引用注册表**：每条法规引用在生成时被注册，分配唯一编号，记录创建时间和使用者
- **引用后处理**：报告正文中的引用占位符在最终渲染时被替换为规范的脚注格式
- **审计日志**：记录每条引用的创建、修改和使用历史

---

### 二、运行过程可观测

平台不是"点一次生成，最后吐一个文件"的黑箱，而是可观察的执行工作台。

#### 三层可观测内容

**第一层：状态层**（系统处在哪个阶段）

```text
任务已创建 → 正在执行 → 正在检索 → 正在生成 → 正在审稿 → 已完成/已阻塞/已失败
```

**第二层：执行层**（系统具体做了什么）

```text
规则命中、AI代理执行、工具调用、RAG检索、附件解析、中间文件生成
```

**第三层：解释层**（系统为什么这样判断）

```text
为什么先做这一步？
为什么得出这个结论？
为什么某项风险被保留/被降低/被阻断？
```

#### 展示边界

**可以展示的**：思路摘要（如"先检查路径硬门槛，再读取上传合同与同意材料，随后核对接收方与合法性基础，最后检索法规并生成章节"）

**不应直接展示的**：原始系统提示词、AI 的原始推理全文、未清洗的工具调用日志、不适合外发的内部判断草稿

#### 后端支撑机制

- **可追溯记录器**：流水线每一步的输入输出都记录为独立的 JSON 文件，支持实时订阅推送到前端
- **执行时间线**：按序号排列的步骤事件，前端可以读取并渲染为时间线组件
- **中间产物保留**：事实清单、问题清单、证据链等作为结构化文件保留，不是只存在于内存中

---

### 三、执行完成后的结果简报

工作流执行完之后，系统自动生成一份结构化的执行结果摘要，而不是只给用户一堆文件路径。

#### 简报的四块固定结构

```text
1. 执行结果
   本次已完成哪类审查/生成/评估；
   当前结论是可继续推进、需补材料、需整改后再推进，还是不建议继续。

2. 本次生成文件
   报告、草案、批注版、Excel、PDF、ZIP压缩包、可追溯记录 等。

3. 需要注意的点
   高风险问题、证据不足项、合同缺口、合法性基础偏弱、路径阻断项。

4. 建议下一步
   补什么材料、修什么条款、是否重新运行、是否进入人工法务复核。
```

#### 内部简报与客户简报的分层

**内部简报**：可包含中间判断、不确定项、内部证据链、调试信息。

**客户简报**：仅保留稳定结论、交付文件列表、注意事项、下一步建议。不暴露原始推理、内部调试记录、系统提示词、未验证的引用、纯内部材料缺陷描述。

#### 简报生成的输入来源

简报不是由每个模块随意撰写，而是基于结构化结果统一组装：

```text
风险等级 / 总体评级
问题清单 / 一致性问题
证据链
输出文件列表
路径诊断结果 / 报告审稿结果
```

这样简报才能做到：稳定、可控、可追溯、适合多模块复用。
