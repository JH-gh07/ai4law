# "数规通"整体开发文档

> 本文档面向开发者和技术评审，系统性记录"数规通"（AI4Law）从设计目标到工程实现的完整技术全景。
> 文档共 12 章，覆盖目标定义、系统设计、知识库、AI 工作流、工程实现、部署运行、测试质量到价值总结。

---

## 第1章 项目目标与系统边界

### 1.1 问题定义

企业数据跨境合规是一项兼具高度专业性和强时效性要求的法律合规工作。当前实践中，企业在处理数据出境合规事务时面临四类典型痛点。

**路径判断复杂。** 中国大陆现行数据出境合规体系由《数据安全法》《个人信息保护法》《网络安全法》《数据出境安全评估办法》《个人信息出境标准合同办法》等多部法规交叉构成，不同企业类型（是否 CIIO）、数据类型（重要数据 / 个人信息 / 敏感个人信息）、规模阈值（100 万 / 10 万 / 1 万条等）决定了完全不同的合规路径。法务人员需要同时掌握多部法规并进行逐层判断，人工处理单次路径诊断通常需要 20–30 分钟，且难以保证判断的一致性和可追溯性。

**文书产出成本高。** 数据出境安全评估申报材料、个人信息保护影响评估报告、标准合同合规审查报告等核心文书，需要将企业实际业务信息与法规要求一一对应，逐章起草、逐条引用。人工起草一份标准的安全评估报告草案通常需要 3–5 个工作日，且因模板不统一，报告质量高度依赖起草人的专业水平。

**审查不可规模化。** 企业在签署数据处理协议（DPA）、数据共享协议、跨境数据传输合同等法律文件之前，需要对文件中的合规条款逐一核查。这一工作高度依赖人工，律师或法务人员审查一份 10–15 页的 DPA 通常需要 2–4 小时，且难以在短期内同步处理多份合同。

**结论不可追溯。** 传统 AI 工具或通用 LLM 在生成合规文书时，其法律依据来源于模型训练数据，无法精确到具体条文，也无法保证法规引用的时效性和准确性。一旦输出内容被质疑，无法提供清晰的法规溯源链路。

现有解决方案均存在明显短板：纯人工处理效率低且成本高；通用 LLM 缺乏法律领域精确性，法规引用无法验证；垂直 SaaS 产品通常仅覆盖单一功能（如合同管理），无法打通从路径诊断到文书生成的完整闭环。

### 1.2 设计目标

本系统的核心切入点是打通"路径诊断 → 文书生成 → 文件审查"完整合规工作闭环，同时满足以下量化设计目标。

**效率目标：** 路径诊断响应时间 < 2 秒（规则引擎直接判断，无 LLM 调用延迟）；合规报告生成时间 30–120 秒（视报告类型和输入材料复杂度）；文件审查时间 60–180 秒（视文件页数和条款数量）。

**质量目标：** 所有 LLM 输出须通过 Pydantic v2 的 JSON Schema 校验方可进入渲染层；每个生成章节必须包含至少 1 条法规引用（`references` 字段 `minItems: 1`），保证可追溯性；结构化输出字段完整率（`risk_level` 非空、`content` 长度 ≥ 100 字符）作为持续监控指标。

**安全目标：** 风险评级采用 HIGH / MEDIUM / LOW 三级标注体系；LOW 置信度（`low_confidence: true`）或 HIGH 风险内容自动附加人工复核标记（`review_required: true`），程序化阻止草案直接用于正式申报；系统 Prompt 明确限制 LLM 角色范围，不回答监管执法预测、诉讼策略等超出合规辅助范畴的问题。

### 1.3 系统边界与不做什么

**覆盖法域：** P0 优先级覆盖中国大陆数据出境合规全链路（路径诊断 + 全类型报告生成 + 文件审查）；P1 扩展覆盖欧盟 GDPR 相关路径（BCR、DPIA、TIA、SCC-EU 模块）和美国加州 CPRA 合规分析；暂不覆盖其他法域。

**系统定位：** 本系统定位为"合规辅助工具"，不提供具有法律效力的最终法律意见。所有输出为草案，须经具备相应资质的律师或法务人员复核后方可用于正式申报或外部交付。

**明确不覆盖的场景：** 监管执法趋势预测（如"监管部门会否立案"类问题）；诉讼策略建议；合同谈判策略；法规解释争议仲裁；个人信息主体投诉处理；超出数据跨境合规范畴的其他法律领域。



## 第2章 系统总体架构

### 2.1 四层技术架构总览

系统采用前后端分离的四层架构，各层职责边界清晰。

**表现层** 由 React 18 主界面（TypeScript + Vite + Tailwind CSS）和 Streamlit 辅助仪表盘（用于本地调试和数据可视化）构成。React 主界面承载全部用户交互，包括路径诊断问答流程、报告生成工作台的双栏布局、文件审查结果展示。Streamlit 仪表盘仅供开发测试使用，不面向最终用户。

**应用服务层** 由 FastAPI 提供统一服务入口，所有接口统一挂载于 `/api/v1` 路径前缀。FastAPI 负责参数校验（Pydantic v2）、任务调度（异步任务提交与状态查询）、错误处理（统一错误响应格式）、文件服务（上传接收、报告下载）。

**AI 推理层** 由三个组件协同构成：腾讯混元 LLM（`hunyuan-turbos-latest`，OpenAI 兼容接口）负责自然语言理解与生成；自建 RAG 引擎（`HashingEmbedder` + 混合检索 + 得理 API 补充）负责法规知识检索；腾讯元器工作流编排负责五步流水线的顶层流程调度。

**数据层** 由 SQLite 数据库（通过 SQLAlchemy ORM 访问）和本地 JSON 向量索引（`storage/rag/regulation_index_v2.json`）构成。选择 SQLite 而非云端数据库，是为满足敏感业务数据不出本地服务器的安全要求。

### 2.2 关键设计决策

**为什么选择前后端分离（React + FastAPI）而非一体化框架。** 合规报告生成属于计算密集型异步任务（30–120 秒），需要前端独立的进度追踪 UI 和后端独立的任务状态机。一体化框架（如 Streamlit 全栈）无法优雅地支持长时任务的异步轮询、结果分页加载、引用链的交互式展开等交互需求。前后端分离使表现层和服务层可以独立迭代。

**为什么使用本地 JSON 向量索引而非云端向量数据库。** 本系统的法规知识库规模固定（1011 条条文，约 2–3 万 token），全量加载至内存进行余弦相似度计算的延迟可控（< 100ms）。使用云端向量数据库（Pinecone、Weaviate 等）会引入网络延迟、API 依赖和数据上传的安全风险，对本场景没有增量价值。

**为什么路径诊断不走 LLM。** 法律合规路径判断有确定性要求：相同的企业情况必须永远对应相同的合规路径，不允许模型幻觉或随机性干扰。同时响应时间要求 < 2 秒，LLM 无法满足。规则引擎（`decision_tree.json`）将判断逻辑与法规依据显式绑定，每条规则可独立审查和修改，完全满足法律可追溯性要求。

**为什么使用 JSON Schema 中间态而非直接生成文档文字。** 直接让 LLM 输出 Word 格式或带样式的文档文字，无法程序化验证输出质量（如是否包含法规引用、风险等级是否合法、内容是否达到最低字数）。JSON Schema 中间态将"内容生成"与"格式正确"解耦：LLM 负责生成符合 Schema 的 JSON 对象，Pydantic 负责校验结构完整性，Python 渲染层负责格式转换。三者职责明确，任一环节均可独立测试和替换。

## 第3章 功能模块划分

### 3.1 模块全景表

系统共包含 10 个核心功能模块，按法域和功能类型分类：

| 模块标识 | 功能名称 | 对应法域 | 输入物 | 输出物 |
|----------|----------|----------|--------|--------|
| `diagnosis` | 合规路径诊断 | 中国大陆 | 五问答 JSON | 路径诊断报告（PDF + docx） |
| `assessment` | 数据出境安全评估 | 中国大陆 | 表单 + Excel + docx | 安全评估报告草案 |
| `scc` | 标准合同合规审查 | 中国大陆 | 表单 + 合同文件 | SCC 合规审查报告草案 |
| `pipia` | 个人信息保护影响评估 | 中国大陆 | 表单 + 业务材料 | PIPIA 报告草案 |
| `bcr` | 约束性公司规则审查 | EU | 表单 + BCR 草案 | BCR 审查报告草案 |
| `dpia` | 数据保护影响评估 | EU | 表单 + 业务描述 | DPIA 草案 |
| `tia` | 传输影响评估 | EU | 表单 + 接收方信息 | TIA 报告草案 |
| `cn_flow` | 数据流转风险评估 | 中国大陆 | 表单 + 数据流图 | GB/T 41817 数据流转评估报告 |
| `cpra` | 加州隐私权法合规分析 | 美国 | 表单 + 隐私政策 | CPRA 合规全景报告 |
| `review` | 文件智能审查 | 多法域 | Word/PDF 文件 | 审查报告 + 问题清单 Excel |

`copilot`（AI 合规助手）作为对话式入口，通过 RAG 检索 + LLM 生成提供交互式合规咨询，与上述报告生成模块共享同一 LLM 客户端和 RAG 引擎。

### 3.2 模块间依赖与共享组件

各模块共享以下公共组件，均定义于 `backend/common/` 目录：

- **LLM 客户端**（`backend/common/llm/client.py`）：封装腾讯混元 API 调用，统一管理 API Key、请求重试、超时配置，所有模块通过此客户端调用 LLM，不直接访问第三方 API。
- **RAG 检索引擎**（`backend/common/rag/`）：提供统一的法规检索接口（`search(query, top_k, domain)`），封装向量检索、关键词召回、重排序和外部补充检索的完整链路。
- **文档渲染器**（`backend/common/renderer/`）：接收 JSON 中间态，输出 docx / PDF / HTML / ZIP 格式文档，统一处理官方申报模板加载、引用链样式标注、风险等级高亮。
- **模块生成器**（`backend/common/llm/module_generator.py`）：维护各模块的系统 Prompt 库和章节指令库，为报告生成提供统一的 Prompt 装配接口。

模块间上下文传递机制：`diagnosis` 模块的输出（`result_json` 中的 `context` 字段）通过 URL 参数 `context_session_id` 传递至下游报告模块，触发表单预填逻辑，企业类型、数据规模等字段自动从诊断结论中抽取并填充至目标模块的输入表单。

各模块遵循独立运行原则：任意模块可在不经过路径诊断的情况下单独调用，`context_session_id` 为可选参数，缺失时跳过预填逻辑。

### 3.3 统一分层结构

所有功能模块遵循相同的四层分层结构：

- **路由层**（`backend/modules/{module}/router.py`）：FastAPI Router 定义，处理 HTTP 请求/响应格式转换，挂载至 `/api/v1/{module}/` 路径前缀。
- **服务层**（`backend/modules/{module}/service.py`）：业务逻辑核心，编排任务状态机转换、调用 AI 推理层、触发文档渲染，不直接访问数据库和外部 API。
- **存储层**（`backend/models/`）：SQLAlchemy ORM 模型定义，各模块数据通过统一的数据库会话管理，不各自维护独立数据库连接。
- **AI 推理层**（`backend/common/`）：LLM 调用、RAG 检索、Prompt 装配，作为服务层的依赖，通过依赖注入（`backend/core/container.py`）提供给各模块服务层。

## 第4章 数据流转与处理流程

### 4.1 路径诊断数据流

**输入结构：** 路径诊断接受五字段 JSON 作为标准输入，字段均为枚举类型，无自由文本输入：

```json
{
  "company_type": "non_CIIO | CIIO",
  "data_type": "important_data | personal_info | sensitive_personal_info | mixed",
  "volume_normal": "<10w | <100w | <1000w | >=1000w",
  "volume_sensitive": "<1w | <10w | >=10w",
  "transfer_purpose": "intra_group | partner_collab | user_service | other"
}
```

**规则引擎处理：** 输入 JSON 由 `backend/modules/diagnosis/service.py` 传入规则引擎，读取 `decision_tree.json` 执行三组规则的顺序匹配（豁免层→强制层→兜底层），耗时 < 2 秒，全程无 LLM 调用。

**输出结构：** 规则引擎返回路径结论 JSON，同步写入 `diagnosis_sessions` 表：

```json
{
  "path": "standard_contract | security_assessment | certification | exempted",
  "confidence": "HIGH | MEDIUM | LOW",
  "reasons": [{"description": "...", "law_ref": "..."}],
  "caveats": ["..."],
  "next_steps": [{"module": "scc", "label": "前往标准合同审查模块"}],
  "context": {"company_type": "...", "recommended_path": "...", "prefill": {...}}
}
```

**数据库持久化：** `diagnosis_sessions` 表字段：`id`（UUID）、`status`、`answers_json`（输入五问）、`result_json`（完整路径结论）、`context_json`（供下游预填的企业画像摘要）、`created_at`。

### 4.2 文书生成数据流

**输入：** 用户通过前端工作台提交企业信息表单（JSON）和附件（Excel 数据清单 + Word/PDF 协议文件）。

**中间态节点：**

1. **`CompanyProfile` JSON**（Pydantic Schema 定义）：LLM 从上传附件中抽取的结构化企业画像，字段定义见附录 B。经 Pydantic v2 校验后写入 `report_artifacts` 表（`artifact_type: "company_profile"`）。

2. **RAG 检索结果**（`List[RegulationChunk]`）：按章节关键词检索本地知识库，每章召回 Top-12（重排后保留 Top-8），结果作为 Prompt 上下文注入，不单独持久化。

3. **章节 JSON 对象**（`ChapterOutput` Schema 约束）：每个章节独立生成，经 Pydantic 校验（最多 3 次重试）后，写入 `report_artifacts` 表（`artifact_type: "chapter_draft"`），支持断点续生成。

**输出：** Python 渲染层将所有章节 JSON 合并，生成 docx（官方申报模板样式）+ PDF + ZIP，写入 `storage/outputs/` 目录，路径写入 `report_artifacts`（`artifact_type: "final_report"`）。

**任务状态机：** 任务生命周期由 `report_artifacts` 表的 `status` 字段追踪，状态转移路径为：

```
CREATED → PARSING → RETRIEVING → GENERATING → VALIDATING → RENDERING → COMPLETED
                                                                      → FAILED
```

前端通过轮询 `/api/v1/{module}/tasks/{task_id}` 获取当前状态和进度百分比。

### 4.3 文件审查数据流

**输入：** Word（.docx）或 PDF 文件，上传后写入 `uploaded_files` 表（含 `storage_path` 和 `extracted_text` 字段），文件原文永不上传至外部服务。

**中间态节点：**

1. **`Clause` 列表：** 文档解析后按语义边界切分的条款单元，每条含 `clause_text`、`page_num`、`para_index`、`clause_id`，以 JSON 列表形式写入 `review_tasks` 表的 `clauses_json` 字段。

2. **`ClauseReview` 列表：** 逐条审查结果，每条含 `issue_type`、`risk_level`、`law_ref`、`suggestion`、`suggestion_example`，经 JSON Schema 校验后写入 `review_tasks` 表的 `issues_json` 字段。

**输出：** 审查报告 docx/PDF（执行摘要 + 完整问题清单 + 整改建议）+ 问题清单 Excel（含整改状态追踪列）。

**多轮审查机制：** `review_tasks` 表记录每条条款的最后审查版本哈希，再次上传时通过 diff 比对识别已修改条款，仅对变更条款重新调用 LLM 审查，保持未修改条款的审查结论稳定不变，同时减少 LLM 调用成本。

**`review_tasks` 表九态状态机：** `CREATED → UPLOADED → PARSING → PARSED → REVIEWING → REVIEWED → RENDERING → COMPLETED → FAILED`

## 第5章 知识库构建与检索策略

### 5.1 法规收录范围与来源

RAG 知识库收录 15 部核心法规，共 1011 条条文，按法域分类如下：

- **中国大陆（394 条）：**《数据安全法》《个人信息保护法》《网络安全法》《数据出境安全评估办法》《个人信息出境标准合同办法》及配套国家标准（GB/T）
- **欧盟（398 条）：** GDPR（2018 年版）、标准合同条款 SCCs（2021 年版）、BCR 指南（EDPB 发布）、DPIA 指南（WP29/EDPB 发布）
- **美国（219 条）：** CPRA（加州隐私权法，2023 年施行）、CCPA 修正案（2023 年版）

所有法规文本来源于官方发布渠道：中国大陆法规来源为国家互联网信息办公室官网（www.cac.gov.cn）和全国人大官网（www.npc.gov.cn）；欧盟法规来源为 EUR-Lex（eur-lex.europa.eu）；美国法规来源为加州隐私保护局官网（cppa.ca.gov）。

知识库版本管理：法规更新时，通过 `scripts/build_regulation_index.py` 重新处理更新的法规文本并生成新索引文件，以新文件覆盖 `storage/rag/regulation_index_v2.json`，系统下次启动时自动加载新索引。

### 5.2 条文切分与索引构建

**条文切分规则：** 以"第 X 条"为最小切分单元，每条条文作为独立的检索文档（`RegulationChunk`）。每个 Chunk 保留以下元数据：`law_name`（法律名称）、`article_number`（条文编号）、`article_text`（条文全文）、`domain`（法域，P0/P1/P2 优先级标注）、`tags`（人工标注的关键词标签，用于关键词召回）。

**向量化：** 使用 `HashingEmbedder`（`backend/common/rag/embedder.py`）将条文文本转换为 384 维稀疏向量。`HashingEmbedder` 基于词频哈希（Feature Hashing / Hashing Trick）实现，将中文分词后的词元映射到固定长度的哈希空间，生成确定性嵌入向量（相同输入永远产生相同输出）。该实现不依赖神经网络嵌入模型，无模型下载和推理延迟，适合本地轻量化部署场景。

**索引存储：** `regulation_index_v2.json` 存储所有条文的元数据和预计算的嵌入向量，文件格式为 JSON 数组，每条记录对应一个 `RegulationChunk`。系统启动时（`backend/app.py` lifespan 事件）一次性加载全量索引至内存，检索时无磁盘 I/O 开销。

### 5.3 混合检索策略

针对每次检索请求，RAG 引擎执行以下四步处理：

**Step 1 候选召回（向量 + 关键词并行）：**
- 向量检索：对查询文本执行 `HashingEmbedder` 编码，与内存中所有条文向量计算余弦相似度，取分数 ≥ 0.05 的候选集（`candidate_pool_size: 24`）；
- 关键词召回：对查询提取中文关键词，与各条文的 `tags` 字段执行词频匹配，词频分 ≥ 2.0 的条文进入候选集；
- 合并去重：两路召回结果合并，生成最多 24 条的候选池。

**Step 2 混合重排序：**
综合评分公式：`score = vector_score × 0.7 + lexical_score_normalized × 0.3 + priority_bonus`

其中 `priority_bonus` 由条文的 `domain` 字段决定：P0（中国大陆）法规额外加权，优先在混合分 ≥ 0.1 时进入最终结果。

**Step 3 质量过滤：**
重排后取 Top-12，过滤规则：混合分必须 ≥ 0.1；若前 12 中无 P0 或 P1 优先级文档，触发外部补充检索。

**Step 4 外部补充检索（条件触发）：**
触发条件：本地结果数量 < 3 条，或结果集中无任何 P0/P1 优先级条文。触发时调用得理开放平台 API（RESTful 接口），以原始查询关键词检索公开法规数据库，将返回结果（法规条文摘要 + 来源信息）追加至本地检索结果集，最终返回前 8 条供 Prompt 注入。

## 第6章 规则引擎设计

### 6.1 设计选择：规则引擎 vs LLM

路径诊断采用规则引擎而非 LLM 的根本原因在于法律判断的三项核心要求：

**确定性。** 法律合规路径判断要求相同的输入条件永远产生相同的判断结论。LLM 的随机采样特性（temperature > 0）使其无法满足这一要求，即使 temperature = 0 也无法排除因模型版本更新导致的输出漂移风险。规则引擎通过显式的条件-结论映射保证了绝对的输出一致性。

**可追溯性。** 监管合规场景要求每一条判断结论都能对应到具体的法规条文编号。规则引擎中每条规则直接绑定法规依据字段，判断链路完全透明，可随时向监管机构解释。LLM 的"黑盒"判断无法提供这一保证。

**低延迟。** 路径诊断要求 < 2 秒响应，LLM API 调用延迟（通常 2–10 秒）无法满足。规则引擎在本地执行，无网络请求，典型响应时间 < 50ms。

系统设计结论：将"路径判断"与"判断解释"解耦——规则引擎负责判断（输出结构化 JSON 结论），LLM 仅负责将结论 JSON 渲染为诊断报告中的自然语言说明段落。

### 6.2 三组规则树详细设计

规则引擎从 `backend/modules/diagnosis/decision_tree.json` 加载规则，按三组顺序执行，命中第一条匹配规则即停止（短路求值）：

**第一组：豁免层（9 条规则）**

豁免层规则命中时，系统判定本次数据出境活动豁免于合规申报，输出"无需申报"结论。典型规则（名称取自 JSON 中的 `rule_id` 字段）：

| 规则 ID | 触发条件 | 法规依据 |
|---------|---------|---------|
| `no_personal_info` | 出境数据不含任何个人信息 | 《个人信息保护法》第 2 条（适用范围） |
| `exemption_contract` | 出境为履行个人作为一方当事人的合同所必需 | 《个人信息保护法》第 13 条第 1 款 |
| `exemption_hr` | 出境为依法制定劳动规章或履行劳动合同所必需 | 《个人信息保护法》第 13 条第 2 款 |
| `exemption_emergency` | 出境为应对突发公共卫生事件、保护生命安全所必需 | 《个人信息保护法》第 13 条第 3 款 |
| `exemption_legal_duty` | 出境为依法履行法定职责所必需 | 《个人信息保护法》第 13 条第 4 款 |

（其余 4 条豁免规则覆盖公益研究、新闻报道、个人信息主体公开发布等场景）

**第二组：强制层（4 条规则）**

强制层规则命中时，系统判定本次出境必须走安全评估路径（数据出境安全评估申报）：

| 规则 ID | 触发条件 | 法规依据 |
|---------|---------|---------|
| `ciio` | `company_type == CIIO` | 《数据出境安全评估办法》第 4 条第 3 款 |
| `important_data` | `data_type == important_data` | 《数据出境安全评估办法》第 4 条第 1 款 |
| `pii_threshold` | `volume_normal >= 100w`（历史累计） | 《数据出境安全评估办法》第 4 条第 2 款 |
| `spi_threshold` | `volume_sensitive >= 1w` | 《数据出境安全评估办法》第 4 条第 2 款 |

**第三组：兜底（1 条规则）**

`SCC_OR_CERTIFICATION`：豁免层和强制层均未命中时的默认路径，推荐标准合同备案（《个人信息出境标准合同办法》第 3 条）或个人信息出境认证，依据接收方关系（集团内部 / 境外合作方 / 终端用户服务）进一步细化推荐优先级。

### 6.3 不确定输入处理

用户在五问中选择"不确定"时，系统采用保守原则处理：

- **量化字段不确定**（如不知道数据量规模）：将该字段视为"可能触发阈值"，向更严格方向偏移（如规模不确定时，按可能达到阈值处理，推荐安全评估路径）；
- **类型字段不确定**（如不确定是否属于重要数据）：在结论的 `caveats` 字段中添加"需专业法务人员确认"标记，同时附上字段的法律定义说明和自检建议；
- **置信度标注**：含不确定字段的诊断结论，`confidence` 字段自动降级（从 HIGH 降为 MEDIUM 或 LOW），提示用户该结论的不确定性范围。

### 6.4 规则可维护性设计

规则树以 JSON 格式外置（`decision_tree.json`），与 Python 判断逻辑解耦。每条规则包含 `rule_id`、`conditions`（结构化条件表达式）、`conclusion`（结论类型）、`confidence`、`law_refs`（法规依据列表）字段。法规更新时，只需修改 JSON 文件中的对应规则，无需改动 Python 代码，修改后的规则可独立进行单元测试验证。

## 第7章 AI 推理层设计

### 7.1 LLM 职责边界

系统对 LLM 的使用严格限制在三类任务：

**企业画像抽取（`profile_extractor`）：** 解析用户上传的 Excel 数据清单和 Word 协议文件，抽取结构化企业画像（`CompanyProfile` Schema）。LLM 扮演"文档理解"角色，输出须经 Pydantic 校验。

**章节内容生成（`chapter_generator`）：** 在企业画像和 RAG 法规上下文的约束下，逐章生成合规报告正文。LLM 扮演"专业写作"角色，输出须符合 `ChapterOutput` Schema（含引用链、风险等级、人工复核标记）。

**条款审查（`clause_reviewer`）：** 对每个条款单元执行合规性比对，输出 `ClauseReview` 格式的审查结论。LLM 扮演"法律审阅"角色，依据来自 RAG 检索，不依赖模型训练记忆。

LLM 明确不负责的任务：路径判断（规则引擎）、格式校验（Pydantic v2）、文档渲染（Python 渲染层）、任务调度（FastAPI 异步任务框架）。

### 7.2 五步文书生成流水线

文书生成工作流由服务层（`service.py`）驱动，按以下五步顺序执行，每步完成后更新 `report_artifacts` 状态字段：

**Step 1 材料解析（状态：PARSING）**
`python-docx` 解析 Word 文件，`pypdf` 解析 PDF，提取纯文本后按段落结构化存储（`uploaded_files.extracted_text`）。

**Step 2 企业画像抽取（状态：PARSING → RETRIEVING）**
LLM（Hunyuan，温度 0.2）基于提取的文档文本，按 `CompanyProfile` Schema 生成结构化企业画像 JSON。Schema 校验不通过时最多重试 2 次，重试仍失败则标记 `low_confidence: true` 并跳过未识别字段（填写 `"unknown"`）。

**Step 3 法规检索（状态：RETRIEVING → GENERATING）**
对报告的每个章节，依据章节类型从 `module_generator.py` 的 `CHAPTER_SEARCH_QUERIES` 字典获取预设检索词，调用 RAG 引擎检索，为每章注入 Top-8 法规片段作为生成上下文。

**Step 4 逐章节生成（状态：GENERATING → VALIDATING）**
每章独立调用 LLM（温度 0.3，`max_tokens: 2048`），Prompt 由三段组成：系统级 Prompt（角色约束 + 格式约束）+ 企业画像 JSON + 章节指令（含 RAG 法规片段和 `ChapterOutput` Schema）。LLM 输出经 Pydantic 校验（最多 3 次重试）；重试耗尽后，将该章节标记为低置信度，附加 `review_required: true`。

**Step 5 一致性校验与渲染（状态：VALIDATING → RENDERING → COMPLETED）**
对全部章节 JSON 执行跨章节一致性检测（检查企业名称、数据量等关键字段在不同章节的表述是否一致），标注矛盾点。随后 Python 渲染层调用官方模板，生成 docx + PDF + ZIP，写入 `storage/outputs/`。

### 7.3 四步文件审查流水线

**Step 1 文档解析（UPLOADED → PARSING）**
格式判断 → 解析提取 → 按规则边界（句号、分号、条款编号）初步切分 → 语义合并（将同一逻辑条款的拆分句合并为完整条款单元）→ 生成 `Clause` 列表，写入 `review_tasks.clauses_json`。

**Step 2 条款分类（PARSING → PARSED → REVIEWING）**
LLM 将每个 `Clause` 归类至预定义合规要求类别（数据收集目的与范围、数据主体权利、跨境传输要求、数据安全措施、第三方共享、数据保留期限、泄露通知义务、合同终止与数据销毁等）。

**Step 3 逐条审查（REVIEWING）**
对每个 `Clause`，RAG 引擎按其分类标签检索对应法规要求，注入 LLM Prompt，输出 `ClauseReview` JSON（含问题类型、风险等级、法规依据、修改建议和参考改写示例）。全程法规依据来自 RAG，不依赖模型记忆。

**Step 4 聚合输出（REVIEWED → RENDERING → COMPLETED）**
按风险等级（HIGH → MEDIUM → LOW）排序 `ClauseReview` 列表，生成综合审查报告 docx/PDF 和结构化问题清单 Excel，更新 `review_tasks.issues_json` 和最终文件路径。

### 7.4 Prompt 设计原则与关键示例

Prompt 设计遵循五大原则：

1. **角色约束：** 系统 Prompt 开头明确声明 LLM 的角色范围（"法律合规辅助工具"）和禁区（禁止回答监管执法预测、诉讼策略类问题）。
2. **输出格式约束：** 每个任务 Prompt 包含目标 JSON Schema，明确字段名、类型、枚举值和 `minItems` 等约束，LLM 必须严格按 Schema 输出，不允许添加 Schema 外的字段。
3. **引用约束：** Prompt 明确要求"法规引用必须来自提供的参考材料，不得依赖训练记忆中的法规内容"，并要求关键结论必须引用至少 1 条具体法规依据（含法律名称和条文编号）。
4. **风险标注：** Prompt 要求对每个章节或条款评定 HIGH/MEDIUM/LOW 风险等级，并在不确定时设置 `low_confidence: true`。
5. **范围限定：** Prompt 明确要求"若企业提供材料不足以支撑某项分析，在对应字段填写说明并将 `low_confidence` 设为 true，禁止编造企业信息或捏造法规内容"。

三类核心模块的 Prompt 结构分别定义于 `backend/common/llm/module_generator.py`，通过 `STRICT_CONSTRAINT`（系统级通用约束）和各模块 `SYSTEM_PROMPTS` 字典（模块级角色约束）组合装配。

### 7.5 腾讯元器工作流编排

腾讯元器（Yuanqi）在系统中承担五步文书生成流水线的顶层编排角色：定义节点连接关系（材料解析节点 → 画像抽取节点 → 法规检索节点 → 章节生成节点组 → 一致性校验节点 → 渲染输出节点）、节点间变量映射和异常分支处理。Python 服务层负责各节点内的具体计算逻辑（解析、向量检索、LLM 调用、Pydantic 校验），元器编排层不直接执行计算。

异常处理机制：单节点失败时，元器触发重试（最多 3 次），超限后标记该节点为低置信度并继续执行后续节点（优雅降级）；任务整体失败时，将 `report_artifacts.status` 设为 `FAILED`，前端显示失败原因。

## 第8章 工程实现

### 8.1 存储层

**SQLite 数据库（通过 SQLAlchemy ORM）**

系统使用 SQLite 作为关系型数据库，数据库文件路径由 `AI4LAW_DATABASE_URL` 环境变量配置（默认 `sqlite:///./ai4law.db`）。四张核心表：

| 表名 | 主要用途 | 关键字段 |
|------|---------|---------|
| `diagnosis_sessions` | 路径诊断记录 | `id`, `status`, `answers_json`, `result_json`, `context_json` |
| `review_tasks` | 文件审查任务 | `id`, `status`（9 态）, `progress`, `clauses_json`, `issues_json`, `summary_json` |
| `uploaded_files` | 上传文件记录 | `id`, `task_id`, `filename`, `content_type`, `storage_path`, `extracted_text` |
| `report_artifacts` | 报告生成产物 | `id`, `owner_type`, `owner_id`, `artifact_type`, `file_path`, `preview_json` |

`report_artifacts` 通过 `owner_type + owner_id` 实现多态关联（可关联任意模块的任务 ID），`artifact_type` 枚举区分不同阶段的产物（`company_profile` / `chapter_draft` / `final_report`）。

**向量索引存储**

`storage/rag/regulation_index_v2.json` 为 JSON 数组格式，每条记录包含 `RegulationChunk` 全部字段（含预计算的 384 维嵌入向量）。系统启动时通过 `backend/app.py` 的 lifespan 事件一次性加载至内存，后续检索操作无磁盘 I/O。

**文件存储目录结构**

```
storage/
  uploads/          # 用户上传的原始文件
  outputs/          # 系统生成的报告文件（docx/PDF/ZIP）
  rag/
    regulation_index_v2.json   # 法规向量索引（启动时加载至内存）
```

### 8.2 接口层

**FastAPI 路由组织**

所有模块路由统一挂载于 `/api/v1/` 前缀，各模块 Router 独立定义后在 `backend/app.py` 中集中注册。典型路由结构：

```
POST   /api/v1/{module}/tasks          # 提交任务（立即返回 task_id）
GET    /api/v1/{module}/tasks/{id}     # 查询任务状态和进度
GET    /api/v1/{module}/tasks/{id}/download   # 下载生成文件
POST   /api/v1/review/tasks            # 提交审查任务（含文件上传）
GET    /api/v1/diagnosis/sessions/{id} # 获取诊断结论
```

**异步任务调度**

用户提交生成任务后，FastAPI 立即返回 `task_id`（UUID），任务由 Python `asyncio` 协程在后台执行。前端通过 `/tasks/{task_id}` 轮询获取状态：

- 轮询间隔：50ms
- 最大轮询次数：120 次（即最长等待 6 秒触发超时提示，但任务继续在后台运行）
- 终止状态集合：`{"succeeded", "completed", "failed", "cancelled", "canceled"}`
- 状态字段同时返回 `progress`（0–100 百分比）供前端进度条展示

**错误处理**

统一错误响应格式：`{"detail": "错误描述", "error_code": "ERROR_TYPE"}`。LLM 调用失败（超时、API 限流、JSON 解析失败）的降级策略：首次失败自动重试（最多 3 次，指数退避），重试耗尽后将对应章节或条款标记为 `low_confidence: true` 并继续执行后续步骤，整体任务不因单章节生成失败而中止。

### 8.3 前端层

**双栏工作台组件结构**

报告生成和文件审查模块采用统一的双栏布局：左侧为输入区（表单填写 + 文件上传），右侧为结果区（章节预览 / 审查意见）。组件通过 `frontend/src/lib/module-adapter.ts` 中定义的 `ModuleAdapter` 接口统一适配各模块差异，使 10 个报告模块可共用同一套工作台 UI 组件。

**异步任务进度追踪**

前端在任务提交后启动轮询循环（`setInterval`，50ms），向 `/api/v1/{module}/tasks/{taskId}` 发请求，接收响应后更新进度条和状态标签。命中终止状态（`succeeded` / `failed` 等）后清除定时器，切换至结果展示或错误提示 UI。

**引用链悬浮标注**

报告预览区使用自定义 React 组件将 `references` 数组中的每条法规引用渲染为可点击的行内标注。用户悬停或点击时，弹出浮层显示法律名称、条文编号和引用原文全文，实现条款级溯源交互。

**风险等级高亮与人工复核标记**

`risk_level: "HIGH"` → 红色高亮背景；`risk_level: "MEDIUM"` → 橙色高亮；`review_required: true` → 黄色警示图标（⚠）+ "需人工复核"文字标签。三类标注均支持在报告预览页按风险等级筛选，方便法务人员快速定位高优先级问题节点。

### 8.4 依赖与配置管理

**后端核心依赖**

| 库 | 用途 |
|----|------|
| `fastapi` | Web 框架 + 异步服务器 |

## 第9章 使用说明

> 本章为摘要索引，完整操作指引请参见《项目使用说明书》（`doc/doc4comp/docmd/05-项目使用说明书.md`）。

### 9.1 产品定位与适用对象

数规通（AI4Law）面向企业法务合规团队、律所合规团队和企业数据保护官（DPO）三类用户，提供数据跨境合规的 AI 辅助处理能力。产品定位为合规辅助工具，不提供最终法律意见。

### 9.2 路径诊断操作流程

用户在场景面板选择出境方向后，依次回答 5 个标准化问题（每题均为枚举选项，附字段说明），点击提交后 < 2 秒返回路径判断结论。结论页可下载诊断报告（PDF + docx），并提供"前往 [路径名] 模块"的一键跳转入口，携带上下文自动预填目标模块表单。

（详细步骤见《项目使用说明书》§2.2）

### 9.3 文书生成操作流程

进入对应报告模块后，用户填写企业信息表单并上传附件（数据清单 Excel + 协议文件 Word/PDF），点击"生成报告"提交异步任务。任务执行期间前端实时显示五步进度，完成后展示报告预览（含引用链、风险标注、人工复核提示），支持 docx / PDF / ZIP 三格式下载。

（详细步骤见《项目使用说明书》§2.3）

### 9.4 文件审查操作流程

上传待审查合同文件（Word/PDF），选择审查类型和适用法律，系统自动执行条款切分和逐条审查，完成后在双栏界面展示左侧原文定位 + 右侧审查意见（含风险等级 + 法规依据 + 修改建议）。支持按 HIGH/MEDIUM/LOW 筛选，可下载审查报告和 Excel 问题清单。修改文件后可再次上传进行第二轮迭代审查，系统仅重审已修改条款。

（详细步骤见《项目使用说明书》§2.4）

### 9.5 输出物与使用注意事项

所有下载文件名含"草案"字样。经法务人员复核修改后，需手动更新文件名和文档内的草案声明。HIGH 风险标注和人工复核标记（⚠）的内容节点须重点关注，不得直接用于正式申报。

（详细说明见《项目使用说明书》§5 + §6.3）

### 10.5 安全边界设计

**接口安全：** API Key 通过环境变量管理，代码中无硬编码；生产环境建议在反向代理层配置接口认证（如 Bearer Token 或 IP 白名单），防止未授权访问。

**内容安全：** 所有 LLM 调用的系统 Prompt 包含 `STRICT_CONSTRAINT`，明确禁止 LLM 回答监管执法预测、诉讼策略、合同谈判等超出合规辅助范畴的问题；输出必须遵守 JSON Schema 约束，防止 Prompt Injection 攻击导致非结构化有害内容输出。

**法律场景安全：** HIGH 风险或低置信度内容通过程序化门控（`review_required: true` + 前端强制标注）阻止草案内容被直接误用于正式申报；报告文件名强制包含"草案"字样。

**数据安全：** 用户上传的原始文件存储于 `storage/uploads/` 本地目录，仅将解析后的文本内容（`extracted_text`）传输至腾讯混元 LLM API，原始文件不上传至任何第三方服务；业务数据不离开本地服务器（向量检索在本地内存执行）。

## 第11章 测试与质量保障

### 11.1 三层自动化评测体系

系统设计了三层评测体系，各层针对不同质量维度，互补而非重复：

**L1 检索层：** 验证"法规依据找对了吗"。对 Golden Set 中的查询，评测 RAG 引擎的检索结果质量，使用 NDCG@3、NDCG@5、MRR@5、Recall@5 四项指标量化评测（脚本：`scripts/qa_rag_eval_v2.py`）。

**L2 抽取层：** 验证"结构化信息提取准确吗"。对 Golden Set 中的标准输入文档，评测 LLM 抽取 `CompanyProfile` 的 Pydantic 首次通过率，识别模型在特定字段类型上的结构化输出能力瓶颈。

**L3 生成层：** 验证"生成内容满足最低质量要求吗"。检测三项指标：
- **引用链覆盖率：** 生成章节中 `references` 数组长度 ≥ 1 的章节占比（目标 > 95%）
- **风险字段完整率：** `risk_level` 字段非空且为合法枚举值的章节占比（目标 100%）
- **内容长度达标率：** `content` 字段长度 ≥ 100 字符的章节占比（目标 > 98%）

### 11.2 Golden Set 回归测试机制

Golden Set 基线数据集存储于 `qa/baseline/` 目录，按功能分三类：

- **RAG 评测集**（`qa/baseline/rag_queries.json`）：法规检索查询样本，每条含标准查询文本和预期相关条文 ID 列表；
- **L2 抽取评测集**（`qa/baseline/profile_extractions/`）：标准输入文档 + 预期 `CompanyProfile` JSON 键值对；
- **L3 生成评测集**（`qa/baseline/report_samples/`）：标准输入 → 生成报告的质量基线（引用数、风险分布等指标）。

回归测试通过 `scripts/qa_rag_eval_v2.py` 执行（RAG 层），每次重大代码变更后建议运行：

```bash
PYTHONPATH=. python scripts/qa_rag_eval_v2.py
```

回归测试结果与 `qa/regression/` 目录中的历史基线对比，若 NDCG@5 或 MRR@5 下降超过 5%，需在合并代码前分析原因。

### 11.3 单元测试与集成测试

pytest 单元测试覆盖以下关键模块（测试文件位于 `backend/` 对应模块目录下的 `tests/` 子目录）：

- **规则引擎：** 对 `decision_tree.json` 全部规则组合进行覆盖性测试，保证每条规则的触发条件和结论正确；
- **RAG 引擎：** 测试各评分函数（余弦相似度、混合重排序）和触发外部检索的边界条件；
- **Pydantic Schema：** 对 `CompanyProfile`、`ChapterOutput`、`ClauseReview` 三类 Schema 进行边界值校验测试；
- **渲染层：** 对 JSON → docx 的渲染正确性进行回归测试（含引用链格式、风险等级样式）。

运行所有测试：

```bash
PYTHONPATH=. pytest backend/
```

## 第12章 价值、创新与局限

### 12.1 核心价值

**量化效率提升：**

| 功能 | 人工处理时长 | 系统处理时长 | 效率提升 |
|------|------------|------------|---------|
| 路径诊断 | 20–30 分钟 | < 2 秒 | 约 600–900 倍 |
| 报告生成（草案） | 3–5 个工作日 | 30–120 秒 | 约 2000–3000 倍 |
| 文件审查（10–15 页） | 2–4 小时 | 60–180 秒 | 约 80–160 倍 |

**质量可见性：** 引用链标注使每条法律结论都可溯源至具体条文编号，法规来源可独立验证；HIGH/MEDIUM/LOW 三级风险标注 + 人工复核强制标记构成完整的可审计质量链路；`low_confidence` 字段程序化标注系统的不确定边界，避免过度自信的错误输出。

**可交付性：** 报告格式参照国家互联网信息办公室官方申报模板，章节结构与监管要求一一对应；法务人员复核后可直接作为申报材料的工作底稿，无需大幅重写。

### 12.2 技术创新点

**确定性路径诊断：** 法律路径判断与 LLM 完全解耦，规则引擎保证相同输入永远产生相同输出，判断链路可对任意一方完整解释，满足法律合规场景的可追溯性和一致性要求。

**JSON Schema 中间态：** LLM 不直接生成文档文字，而是先生成满足 Schema 约束的 JSON 中间态，Python 渲染层负责格式转换。这一设计将"格式正确"与"内容生成"解耦，Pydantic 校验作为质量门控，程序化保证结构规范性，任一环节均可独立测试。

**引用链强制覆盖：** 系统在 Prompt 层（明确要求引用必须来自 RAG 检索结果）和 Schema 层（`references` 字段 `minItems: 1`）双重强制，拒绝产出无依据的法律判断。每条结论可逐条验证，防范 LLM 幻觉产生的虚假法规引用。

**三层评测体系：** 针对法律 AI 场景的特殊质量要求（不仅需要"生成流畅"，还需要"引用准确"和"结构完整"），分别设计 L1（检索准确性）/ L2（抽取完整性）/ L3（生成质量）三层评测，各层针对不同质量维度，形成互补的全面质量保证机制。

### 12.3 现阶段局限

**知识库时效性：** 法规更新后需人工触发 `build_regulation_index.py` 重建索引并重启服务，暂无法规变更自动监测和增量同步机制。

**嵌入模型精度：** 当前 `HashingEmbedder` 为词频哈希实现，对语义近似但词汇差异大的查询（如"数据出境"与"跨境传输"的等价检索）精度有限。计划升级为 BGE-M3 等神经网络嵌入模型以提升跨语言和语义检索精度。

**法域覆盖深度：** EU/US 模块处于 P1 阶段，知识库条文数量和报告模板完整度不及中国大陆 P0 模块，部分章节生成质量有待提升。

**大文件处理：** 超长法律文件（> 100 页）的条款语义切分质量随文件长度下降，原因是当前语义合并算法未考虑段落在全文中的位置信息，难以区分跨节引用和独立条款。

**并发能力：** 当前基于 SQLite 的存储方案和 asyncio 异步框架支持中低并发（估计 10–20 个并发任务），高并发场景需迁移至 PostgreSQL + 消息队列（Celery / RQ）架构。

### 12.4 后续优化方向

- **RAG 升级：** 向量嵌入模型升级为 BGE-M3，提升跨语言（中英）和语义检索精度，预期 NDCG@5 提升 15%–20%；
- **知识库自动同步：** 接入法规变更监测 API（如国家法律法规数据库更新推送），实现法规变更时自动触发索引重建；
- **路径扩展：** 增加 EU→CN、US→CN 等更多跨境方向的路径判断规则，覆盖境外企业向中国大陆传输数据的合规场景；
- **产品化：** 历史报告管理（报告中心）、任务模板复用（常用企业信息保存）、企业画像持久化（避免重复抽取）；
- **并发与可靠性：** 迁移至 PostgreSQL + Celery 异步任务队列，支持更高并发和任务失败重试；
- **商业化路径：** 订阅制（报告生成次数 / 月）/ API 接入（B2B 集成）/ 企业私有化部署（含本地嵌入模型）。

| BCR | 约束性公司规则（Binding Corporate Rules） |
| DPIA | 数据保护影响评估（Data Protection Impact Assessment） |
| TIA | 传输影响评估（Transfer Impact Assessment） |
| DPA | 数据处理协议（Data Processing Agreement） |
| HashingEmbedder | 系统自建的词频哈希嵌入器，将文本映射为 384 维确定性稀疏向量，不依赖神经网络模型 |
| CompanyProfile | 系统从输入材料中抽取的企业画像结构化 JSON 对象 |
| ChapterOutput | 每个报告章节的生成结果 Schema，含内容、引用链、风险等级等字段 |
| ClauseReview | 文件审查中每个条款单元的审查结果 Schema |
| Golden Set | 用于回归测试的基线数据集，包含标准输入和预期输出质量指标 |
| JSON Schema 中间态 | LLM 不直接生成文档文字，而是先生成满足 Schema 的 JSON 对象，程序化校验后再渲染为文档 |
| report_artifacts | 报告生成模块的多态产物表，以 artifact_type 区分不同阶段产物 |
| HashingTrick | 特征哈希（Feature Hashing）技术，将高维离散特征映射到固定长度哈希空间的方法 |
| NDCG | 归一化折损累积增益（Normalized Discounted Cumulative Gain），RAG 检索质量评测指标 |
| MRR | 平均倒数排名（Mean Reciprocal Rank），RAG 检索第一个相关结果位置的评测指标 |
