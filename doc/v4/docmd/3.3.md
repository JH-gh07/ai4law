# 3.3 DPIA草案生成

## 3.3.1 模块定位

DPIA 草案生成模块面向欧盟 GDPR 场景下的高风险个人数据处理活动，核心目标不是替代企业完成最终法律判断，而是基于用户提交的项目背景、处理活动说明、数据流、合法性基础、风险识别和缓释措施等信息，按照标准 DPIA 模板自动生成一份结构完整、内容可编辑、便于 DPO 与法务进一步审核的 **《DPIA草案》**。

本模块的输出结构严格对齐 ICO DPIA template 的七步法：先识别是否需要 DPIA，再描述处理活动，之后说明咨询过程、必要性与相称性，识别和评估风险，提出降险措施，最后记录签署、DPO 意见和后续复审安排。

## 3.3.4 系统处理逻辑

### 第一步：按模板步骤建立采集框架

系统不是把所有字段混在一个大表里收，而是先按 ICO 模板七步法建立逻辑顺序。先判断项目是否需要 DPIA，再让用户描述处理活动，再进入咨询、合法性、风险与缓解措施。这样生成的结果天然贴合最终文档结构，而不是后期硬拼。

### 第二步：将用户输入转成“叙述 + 表格”双层结构

DPIA 不是纯表单，也不是纯说明文。
所以系统会把输入分成两类处理：

- 对项目目标、必要性、合理预期、咨询过程、DPO 意见这类内容，生成正式叙述段落；
- 对风险项、可能性、严重性、降险措施、批准状态这类内容，生成标准表格。

这样既符合 DPIA 文档阅读习惯，也方便后续审查。

### 第三步：做必填项完整性和一致性检查

系统会先检查核心字段是否齐全，例如：

- 是否说明了为什么需要 DPIA；
- 是否描述了数据流、数据类型、保存期限和数据主体规模；
- 是否写明合法性基础；
- 是否给每个中高风险配置了缓解措施；
- 是否填写了 DPO 意见与后续复审安排。

同时还会检查前后是否矛盾，例如：

- 前面说“不涉及敏感数据”，后面风险里却写了健康数据；
- 前面说“不会跨境”，后面又写到第三国接收方；
- 前面说“已征询用户意见”，后面却没有意见处理结果。

### 第四步：自动补全文书化表达

很多用户会给出“原始事实”，但不会写成 DPIA 文书。
系统会把事实自动改写成模板化、正式化表达，例如：

- 把“做推荐系统，用浏览点击历史训练模型”
  改写成“本处理活动旨在基于用户历史交互数据构建画像与推荐模型，以提升个性化服务能力”；
- 把“风险是画像可能太细”
  改写成“若画像粒度过高或缺乏透明说明，可能导致数据主体对自动化分析缺乏可预见性，并对其自主决策和隐私期待造成不利影响”。

### 第五步：自动生成风险矩阵与残余风险判断

系统对每项风险都要求至少有：

- 风险来源
- 对个人的影响
- 可能性
- 严重性
- 当前措施
- 剩余风险

然后自动形成 DPIA 中的风险矩阵。
如果残余风险仍然较高，系统会在 Step 7 中自动加入升级提示，提醒在继续推进前考虑咨询监管机构，这与 ICO 模板原文逻辑一致。

### 第六步：生成可编辑草案并保留人工复核接口

最终输出不是“最终定稿”，而是：

- 结构完整；
- 表述规范；
- 风险与措施成对；
- 可继续补充、删改、签署的 **DPIA 草案**。

DPO、法务、信息安全和业务负责人可以在此基础上进行最终确认。

### 3.3 DPIA草案生成

#### 3.3.1 用户输入

本模块以 DPIA 模板所要求的事实信息为输入基础，围绕项目名称、项目目标、开展 DPIA 的原因、数据流与处理活动、数据类型、特殊类别数据、数据主体规模、保存期限、跨境传输、咨询过程、合法性基础、必要性与相称性说明、风险识别、风险等级、缓解措施、签署记录和 DPO 意见等内容进行结构化采集。系统支持短文本、段落文本、下拉选择、多选、列表输入和文件上传等多种输入方式，并允许用户上传数据流图、项目说明、隐私政策、风险清单等补充材料。整体采集逻辑严格对应 ICO DPIA template 的七个步骤，以保证后续输出结果与标准 DPIA 结构一致。

#### 3.3.2 系统处理逻辑

系统首先依据 ICO DPIA template 的步骤顺序，对用户输入进行归类和校验：先识别项目为何需要 DPIA，再描述处理活动的性质、范围、背景与目的，然后整理咨询过程、合法性基础与相称性分析，进一步形成风险清单、风险矩阵和降险措施表，最后补入签署记录、DPO 意见和复审安排。在处理过程中，系统不仅检查字段是否填写完整，还会校验前后内容是否一致，并将用户提供的原始事实自动转化为正式 DPIA 文书语言，生成叙述段落与风险表格相结合的草案文本。对于中高风险处理活动，系统会强制要求填写对应缓解措施，并自动输出剩余风险判断。
