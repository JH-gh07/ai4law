## 四、模块体系（统一分类）

本系统采用三级模块体系组织功能：

* **一级：法域**
  按适用法律体系划分为中国、欧盟、美国。

* **二级：能力**
  按系统提供的核心动作划分为诊断、起草、审查、整改。

* **三级：具体专题**
  在每一法域与能力下，进一步落到具体业务专题，例如安全评估报告起草、PIPIA 报告起草、SCC 审查、TIA 起草等。

采用该结构后，平台能够同时满足两项目标：
一是同一法域下的模块组织更加清晰；
二是不同法域之间的能力层级可以横向比较，避免出现中国按流程分、欧盟按工具分、美国按法规分的口径不统一问题。

## 五、各专题流程、输入与输出（按统一分类重写）

本部分按“法域 → 能力 → 专题”的顺序描述各模块流程、输入与输出。
其中：

* **诊断**：负责判断适用路径、触发义务、风险等级及后续建议；
* **起草**：负责生成合规报告、评估文书或说明性材料草案；
* **审查**：负责分析已有文本或事实场景，识别问题并输出审查意见；
* **整改**：负责汇总风险、形成整改路线图与行动清单。

### 5.1 中国

#### 5.1.1 诊断 / 合规路径诊断

**定位**：
根据企业数据出境场景，判断应适用的中国法路径，并输出风险等级、法律依据和后续建议。

**流程**：
用户填写 8 题问卷 → 决策树评估 → LLM 生成专业说明 → 调用得理 API 补充法规与案例 → 返回推荐路径。

**核心判断结果**：

* `security_assessment`
* `scc_or_certification`
* `exemption`

**输入**：

```json
{
  "q1_is_ciio": "yes|no|unknown",
  "q2_has_important_data": "yes|no|unknown",
  "q3_pii_count": 0,
  "q4_spi_count": 0,
  "q5_no_personal_info": "yes|no",
  "q6_scenario": "contract_performance|hr_management|emergency|legal_duty|other",
  "q7_receiver_type": "intra_group|third_party",
  "q8_purpose": "出境目的简述"
}
```

**输出**：

```json
{
  "recommended_path": "security_assessment|scc_or_certification|exemption",
  "risk_level": "HIGH|MEDIUM|LOW",
  "rationale": "LLM 生成的专业说明",
  "legal_basis": ["..."],
  "action_items": ["..."]
}
```

#### 5.1.2 起草 / 安全评估报告起草

**定位**：
面向中国数据出境安全评估路径，自动生成《数据出境风险自评估报告》草案。

**流程**：
输入表单 → ProfileExtractor → AssessmentRetriever（本地 RAG + DeliLegal 补充）→ AssessmentChapterGenerator（LLM × 8 章）→ ConsistencyChecker → 渲染 DOCX/MD。

**8 章结构**：

1. 出境活动概述
2. 数据类型与规模
3. 出境必要性与合法性基础
4. 境外接收方保障能力
5. 个人信息权益影响分析
6. 安全措施与传输机制
7. 剩余风险与整改建议
8. 综合评估结论

**输入**：

* 公司名称、行业、是否 CIIO、是否含重要数据
* 出境目的、接收方名称/国家地区
* PI/SPI 规模
* 应急预案、安全保障措施
* 数据处理协议及其他上传文件

**输出**：

* `assessment_report.docx`
* `assessment_report.md`
* 任务结果 JSON（含章节内容、状态、进度）

#### 5.1.4 审查 / 合同审查

**定位**：
对用户上传的合同文本进行条款切分、分类、问题识别和审查报告生成。

## 七、整体设计现状与核心问题（按统一结构重写）

### 7.1 当前完成度总结

从统一结构看，系统当前已基本覆盖中国、欧盟、美国三个法域，并已形成“诊断 / 起草 / 审查”三类核心能力；“整改”能力已在多个模块中以章节或建议项形式存在，但尚未被统一抽象为独立模块。

当前可概括为：

* **中国法域**：诊断、起草、审查能力已形成较完整闭环；
* **欧盟法域**：起草与审查能力较强，但缺少统一诊断入口；
* **美国法域**：起草与审查已有基础实现，但整体仍偏轻量，诊断与整改层尚未独立成型。

---

### 7.2 当前开发阶段定位

当前系统处于 **v1（LLM 接入阶段）**：

* 各法域主要专题的 API、数据模型、表单输入、报告渲染链路已建立；
* 真实 LLM 已接入各起草与审查模块；
* 知识库与外部法搜 API 已纳入 RAG 链路；
* 端到端流程已可生成具有实质内容的报告与审查意见。

但从统一结构看，当前仍存在以下明显差距：

1. **诊断层不平衡**
   中国已有独立诊断模块，欧盟和美国仍缺统一前置入口。

2. **整改层未独立**
   多数专题已能输出建议，但尚未形成统一的整改能力层。

3. **专题命名与层级曾存在混用**
   旧版本中中国按流程分、欧盟按工具分、美国按法规分，现已通过统一三级结构进行规范化整理。

---

### 7.3 当前核心问题

#### （1）结构问题：旧分类口径不统一

旧版本使用 `2.x / 3.x / 4.x` 平铺模块，导致中国、欧盟、美国各法域的组织方式不一致，影响理解与横向比较。
本次调整后，已统一为“法域 → 能力 → 专题”的三级体系。

#### （2）能力问题：整改层仍弱

虽然各模块已有：

* `action_items`
* `recommendation`
* `整改计划`
* `行动清单`
  但这些内容仍分散在起草与审查专题中，尚未成为一个统一输出层。

#### （3）法域问题：欧美诊断入口不足

中国法域已有较成熟的合规路径诊断；欧盟与美国仍缺少类似的统一前置判断模块，导致用户一开始就必须自行选择具体专题。

#### （4）检索问题：知识库治理仍需加强

知识库总量已基本满足当前模块使用，但仍存在：

* 英文 PDF 断词/OCR 噪声
* `path/doc_type` 标签细化不足
* 欧盟/美国执法口径和行业案例仍不够充分
  这些问题会影响部分专题的检索精度与输出质量。

#### （5）工程问题：合同审查仍未完成双模式

当前合同审查仅实现审查模式（Mode A），尚未实现：

* 修订合同生成
* diff 展示
* 更丰富的交互参数
  这使其距离“完整合同协作工具”仍有差距。
