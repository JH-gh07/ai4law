# 《"数规通"项目解决方案》

## 1. 项目技术实现方案

### 1.1 系统总体架构设计

"数规通"采用四层技术架构，从用户界面到底层数据形成完整的技术栈闭环。

**表现层**由两套前端界面构成：主交互界面基于 React 18 + TypeScript 构建，提供双栏工作台（左侧输入/右侧结果）、场景面板导航、异步任务进度追踪等完整产品体验；辅助仪表盘基于 Streamlit 构建，面向开发调试场景提供数据概览与模块测试能力。

**应用服务层**采用 FastAPI（Python）构建 RESTful API，统一挂载于 `/api/v1` 网关之下，负责请求路由、参数校验、异步任务调度与状态管理。报告生成类接口均采用异步任务模式：提交请求后立即返回 `task_id`，前端通过轮询 `/tasks/{task_id}` 接口获取进度，避免长时 HTTP 连接超时。

**AI 推理层**由三个子系统协作构成：腾讯混元大模型（通过 OpenAI 兼容 API 接入）承担核心推理任务（抽取、生成、审查、校验）；自建 RAG 检索引擎维护 1011 条法规条文向量索引（384 维），支持向量检索与关键词召回的混合检索；腾讯元器平台负责顶层工作流编排，将各推理步骤串联为可配置的有向流水线。

**数据层**以 SQLite 数据库持久化三类核心业务状态：诊断会话（`diagnosis_sessions`）、报告任务（`report_tasks`）、文件审查会话（`review_sessions`）；向量索引以 JSON 格式存储于 `storage/rag/regulation_index_v2.json`，系统启动时加载至内存。

### 1.2 功能模块设计

系统按业务领域划分为 11 个独立功能模块，各模块均遵循统一的分层结构（路由层 → 服务层 → 存储层 → AI 推理层），并通过统一 API 网关对外提供服务：

| 模块标识 | 功能名称 | 对应法域 | 输出物 |
|----------|----------|----------|--------|
| `diagnosis` | 合规路径诊断 | 中国大陆 | 路径诊断报告 |
| `assessment` | 安全评估报告生成 | 中国大陆 | 数据出境风险自评估报告 |
| `scc` | 标准合同合规审查 | 中国大陆/EU | SCC 合规审查报告 |
| `pipia` | 个人信息保护影响评估 | 中国大陆 | PIPIA 报告 |
| `bcr` | 约束性公司规则审查 | EU | BCR 审查报告 |
| `dpia` | 数据保护影响评估 | EU | DPIA 草案 |
| `tia` | 传输影响评估 | EU | TIA 报告 |
| `cn_flow` | 数据流转风险评估 | 中国大陆 | 14117 数据流转风险评估 |
| `cpra` | 加州隐私权法合规全景 | 美国 | CPRA 合规全景报告 |
| `review` | 文件智能审查 | 多法域 | 条款级合规审查报告 |
| `copilot` | AI 合规助手 | 多法域 | 对话式合规咨询 |

每个模块均可独立运行，共享底层的 LLM 客户端、RAG 检索引擎、文档渲染器与风险评估器等公共组件。

### 1.3 核心业务流程设计

以安全评估报告生成为例，系统执行以下七步核心流程：

1. **材料解析**（`file_parser`）：用户提交表单数据与附件（数据清单 Excel、数据处理协议 Word/PDF），系统调用 python-docx/pypdf 解析附件，提取结构化文本。
2. **企业画像抽取**（`profile_extractor`）：LLM 基于解析文本抽取 `CompanyProfile` JSON 对象，包含企业名称、业务类型、数据处理目的、数据出境规模、境外接收方信息等字段，输出须通过 Pydantic Schema 校验。
3. **法规检索**（`rag_search`）：混合检索引擎根据当前报告类型和章节关键词，对本地 1011 条法规索引执行向量检索与关键词召回，重排序后取 Top-N 条文作为生成上下文；置信度不足时触发得理开放平台 API 补充检索。
4. **逐章节生成**（`chapter_generator`）：LLM 接收企业画像 + 法规片段，按报告章节模板逐章生成内容。每章输出经 JSON Schema 校验（引用数量 ≥1、风险等级非空、内容长度合理），校验不通过则自动重试（最多 3 次）。
5. **一致性校验**（`consistency_checker`）：LLM 对全文进行跨章节检查，识别数据量描述矛盾、风险定性不一致等问题，自动在问题位置插入高亮标记。
6. **渲染输出**（`report_renderer`）：将 JSON 中间态渲染为多格式交付物：python-docx 生成可编辑 Word 文件（保留官方模板样式）、PDF 版本、Markdown 纯文本，最终打包为 ZIP。
7. **任务状态更新**：每步完成后更新 `report_tasks` 表中的任务状态，前端通过轮询接口实时获取进度并更新界面显示。

## 2. AI 工作流设计

### 2.1 合规路径诊断工作流

路径诊断工作流的核心特点是**不依赖 LLM 推理**，采用前端确定性规则状态机实现，确保判断结果的稳定性和可解释性。

用户依次回答五个结构化问题：企业类型（CIIO/非CIIO）、涉及数据类型（重要数据/个人信息/敏感个人信息/混合）、个人信息数量规模、敏感个人信息数量规模、出境目的（集团内部/合作方/用户服务/其他）。规则状态机按优先级顺序执行判断：

- 若属于关键信息基础设施运营者（CIIO），强制适用安全评估路径；
- 若涉及重要数据，强制适用安全评估路径；
- 若普通个人信息规模 ≥100 万条或敏感个人信息 ≥10 万条，适用安全评估路径；
- 其余情况，视接收方关系推荐标准合同备案或个人信息出境认证。

每条判断规则均关联具体的法规依据（如《数据出境安全评估办法》第 4 条），判断结论以 JSON 结构输出，包含推荐路径、置信度、法规依据列表、注意事项，并携带企业画像预填信息供后续模块直接复用。AI 仅参与最终诊断报告的说明文字生成，不参与核心路径判断。

### 2.2 合规文书生成工作流

文书生成工作流以腾讯元器为顶层编排器，Python 执行层实现各节点的具体逻辑，形成五步 AI 流水线。

**步骤一：材料理解。** LLM 扮演"合规材料分析助手"角色，从用户上传的业务材料中抽取结构化企业画像（`CompanyProfile`），字段包括企业基本信息、数据处理目的、跨境场景描述、数据量规模、境外接收方情况等。输出须通过 Pydantic Schema 校验，不确定字段填 `unknown`，不允许捏造。

**步骤二：法规检索。** RAG 引擎根据报告类型预设检索关键词，对本地 1011 条法规索引执行混合检索，重排序后返回 Top-N 条文作为生成上下文，确保每个章节都有精准的法规依据支撑。

**步骤三：逐章节生成。** LLM 基于企业画像与法规片段，按预定义章节模板逐章生成报告内容。每章输出须满足：关键结论包含至少 1 条法规引用、风险等级字段非空、内容长度达到最低要求。校验不通过则自动重生成，最多重试 3 次后标记为低置信度。

**步骤四：一致性校验。** 所有章节生成完毕后，LLM 对全文执行跨章节一致性检查，识别数据量描述前后矛盾、风险定性不一致、重复引用等问题，在报告中高亮标注，供人工复核重点关注。

**步骤五：渲染输出。** Python 渲染层将 JSON 中间态转换为 docx/PDF/HTML/ZIP 多格式文件，Word 文件采用官方申报模板样式，文件名按 `[企业简称]_[报告类型]_草案_[日期]` 规范命名。

### 2.3 合规文件审查工作流

文件审查工作流针对上传的合同、隐私政策、数据处理协议等法律文件，执行四步 AI 处理流水线。

**步骤一：文档解析。** 系统根据文件格式调用对应解析器（Word 用 python-docx，PDF 用 pypdf），提取结构化文本后执行条款切分——先按句号、分号、条款编号（"第 X 条"）进行规则切分，再对语义连续的片段进行合并，最终为每个条款单元附加原文文本、文档位置（页码 + 段落序号）等元数据。

**步骤二：条款分类。** LLM 对每个条款单元进行类型识别，将其归入预定义的合规要求类别：数据收集目的、数据主体权利、跨境传输要求、数据安全措施、第三方共享、数据保留期限等，为后续精准审查提供依据。

**步骤三：逐条审查。** LLM 将每个条款的内容与其所属类别的法规要求进行比对（法规依据来自 RAG 检索，不依赖模型记忆），识别缺失要素、表述不清、与法规冲突等问题，输出问题类型、风险等级（HIGH/MEDIUM/LOW）、法规依据（含条文编号）和具体修改建议（含参考改写示例）。输出须通过 JSON Schema 约束。

**步骤四：聚合输出。** 系统将所有条款的审查结果按风险等级排序，生成两种输出：一是结构化问题清单（JSON/Excel 格式，便于整改管理）；二是综合《合规审查报告》（docx/PDF），包含执行摘要、完整问题清单、整改优先级建议，附"需律师/法务复核"声明。

## 3. AI 工具使用说明

### 3.1 腾讯元器的使用方式

腾讯元器在本项目中承担**顶层工作流编排**职责。在元器平台上，报告生成全流程被配置为一个结构化工作流，各执行节点（文件解析、画像抽取、法规检索、章节生成、一致性校验、渲染输出）以有向图形式连接，节点间通过变量映射传递中间数据。

元器工作流的主要价值在于：①提供可视化的流程配置界面，降低流程调整成本；②内置条件分支与异常处理逻辑，处理重试、跳过等边界情况；③执行日志完整保留，便于定位问题节点。Python 执行层作为各节点的实际计算引擎，负责 RAG 检索、LLM 调用、Schema 校验、文档渲染等具体操作，元器负责编排调度。

### 3.2 得理开放平台 API 的接入与应用

得理开放平台（DeliLegal）提供专业的法律法规检索与司法案例查询能力，在本项目中作为自建 RAG 知识库的**补充信源**接入。

接入方式：通过 DeliLegal RESTful OpenAPI 发起检索请求，API Key 经环境变量注入，代码中无硬编码。当 RAG 本地向量索引的检索相关度得分低于预设阈值时，系统自动触发得理 API 补充检索，将返回的法规条文和司法案例摘要纳入 LLM 生成上下文，提升对小众法规场景的覆盖能力。

### 3.3 CodeBuddy 在开发过程中的作用

腾讯 CodeBuddy 在项目开发全程提供 AI 编程辅助，主要体现在四个方面：

**代码生成：** 快速生成 FastAPI 路由框架、Pydantic Schema 定义、SQLAlchemy 模型代码，节省重复性编码工作；生成前端 React 组件的基础结构与 TypeScript 类型定义。

**代码调试：** 辅助定位 LLM 输出不符合 JSON Schema 导致的 ValidationError；协助排查 RAG 检索返回格式异常及向量索引加载问题。

**文档生成：** 根据代码逻辑自动生成 API 接口文档注释（符合 FastAPI/OpenAPI 规范）；辅助生成单元测试用例框架。

**重构优化：** 对 RAG 检索模块（混合检索策略）和报告渲染模块（模板引擎）提供代码优化建议，提升可维护性。

## 4. 提示词设计与控制策略

### 4.1 提示词设计原则

本项目 Prompt 工程围绕法律场景的特殊性建立了五大设计原则：

**角色约束原则：** 所有模块的系统 Prompt 均明确将 AI 角色限定为"法律合规辅助工具"，而非法律专业人士。Prompt 显式声明：不给出最终法律意见，所有输出结论均须经律师或法务人员复核确认后方可使用。

**输出格式约束原则：** 所有生成任务均强制要求按 JSON Schema 输出，在 Prompt 中内嵌目标 Schema 定义，并说明字段缺失时的重试机制。这是确保 LLM 输出可被程序化解析、进而驱动后续渲染流程的关键设计。

**引用约束原则：** 每个生成任务的 Prompt 均明确要求，所有关键法律结论必须包含至少 1 条具体法规引用（含法律名称、条文编号、引用原文），禁止依赖 LLM 训练记忆中的法规内容，法规依据必须来自输入的 RAG 检索结果。

**风险标注原则：** 输出 Schema 中强制包含 `risk_level`（枚举：HIGH/MEDIUM/LOW）和 `review_required`（布尔型）字段，Prompt 说明触发 HIGH 风险和"需人工复核"标记的场景：依据不足、判断存在专业争议、输入材料信息缺失等。

**范围限定原则：** 系统 Prompt 明确列出 AI 禁止回答的问题类型（如预测监管执法结果、给出具体诉讼策略等），将助手能力边界限定在合规辅助范围内，避免幻觉扩散至高风险决策领域。

### 4.2 各模块核心提示词结构

**企业画像抽取 Prompt（`profile_extractor`）：**
系统角色设定为"合规材料分析助手"，任务为从用户提供的业务材料（表单文本 + 附件解析文本）中抽取结构化 `CompanyProfile` JSON。Schema 约束包含企业名称、统一社会信用代码（如有）、业务类型、数据处理目的描述、跨境场景描述、普通个人信息数量、敏感个人信息数量、境外接收方名称与所在国/地区等字段。质量要求：字段内容不确定时填 `"unknown"`，不允许捏造信息；若某字段在材料中明确不存在，填 `null`。

**章节生成 Prompt（`chapter_generator`）：**
系统角色设定为"数据跨境合规报告生成助手"，输入包含企业画像 JSON 和 RAG 检索返回的法规片段列表。任务说明针对每个章节类型单独定制（如"个人信息出境必要性分析"章节要求分析业务必要性、最小必要性原则、法律依据三个维度）。Schema 约束包含章节正文、引用列表（每条引用含法律名称/条文编号/引用原文）、风险等级、低置信度标记、人工复核标记及复核原因。

**条款审查 Prompt（`clause_reviewer`）：**
系统角色设定为"法律文档条款审查助手"，输入为单条条款原文 + 同类法规要求片段（来自 RAG 检索）。输出约束：问题类型（缺失要素/表述不清/与法规冲突/符合要求）、风险等级（HIGH/MEDIUM/LOW）、依据法规（条文编号）、修改建议（含参考改写示例）。禁止事项：不得编造法规依据，无充分依据时明确标记"需人工复核"。

### 4.3 输出约束与质量控制机制

系统建立了贯穿 LLM 调用链路的三层质量控制体系：

**L1 检索层：** 对 RAG 检索返回结果进行相关度评分，低于阈值时触发得理开放平台 API 补充检索；若补充检索后相关度仍不足，在对应章节的生成上下文中插入提示，要求 LLM 降低置信度标记。

**L2 抽取层：** 所有 LLM JSON 输出经 Pydantic Schema 校验，字段类型错误、枚举值超范围、必填字段缺失均触发自动重试（最多 3 次）。超过重试次数后，该步骤结果标记为低置信度（`low_confidence: true`），并要求人工复核。

**L3 生成层：** 章节内容生成后执行规则性检查：`references` 列表长度 ≥1、`risk_level` 字段非空且为合法枚举值、`content` 字段字符数达到最低要求。不达标触发重生成。每次重大代码变更后，自动执行 Golden Set 回归测试（基线数据集），比对与标准输出的偏差，防止能力退化。

## 5. 素材、接口与工具说明

### 5.1 法律规则与文书素材来源

**法规知识库：** RAG 索引收录 15 部核心法规，共 1011 条条文，覆盖三大法域：

- **中国大陆（394 条）：** 《数据安全法》（2021）、《个人信息保护法》（2021）、《网络安全法》（2017）、《数据出境安全评估办法》（2022）、《个人信息出境标准合同办法》（2023）及配套规定；
- **欧盟（398 条）：** GDPR（2018）、标准合同条款（SCCs 2021 版）、约束性公司规则（BCR）指南、数据保护影响评估（DPIA）指南（WP29/EDPB）；
- **美国（219 条）：** CPRA（加州隐私权法）及 CCPA 修正案（2023）。

所有法规文本来源于官方发布渠道（中国：国家互联网信息办公室官网/全国人大官网；EU：EUR-Lex；US：CPPA 官网），并附有 7 个基于公开报道的数据出境合规实践案例。

**文书模板：** 报告生成使用的章节模板基于官方申报文书规范结构化处理：安全评估报告参照国家互联网信息办公室《数据出境安全评估申报指南（第一版）》；PIPIA 报告参照全国信息安全标准化技术委员会相关标准；标准合同文本参照《个人信息出境标准合同》官方文本。

### 5.2 接口与第三方能力说明

系统接入三类第三方接口，所有密钥均通过环境变量统一管理，代码中无硬编码：

| 接口 | 调用方式 | 用途 |
|------|----------|------|
| 腾讯混元 LLM API | OpenAI 兼容格式（`/v1/chat/completions`） | 核心推理：画像抽取、章节生成、条款审查、一致性校验 |
| 得理开放平台 API | RESTful API（HTTP GET/POST） | 法规条文与司法案例补充检索 |

## 6. 技术亮点与关键难点

### 6.1 不清晰输入下的路径判断设计

**问题背景：** 企业用户（尤其是非专业法务人员）在描述自身数据情况时往往模糊，如"我们有一些用户信息要传到海外子公司"，难以直接映射到法规规定的判断标准（CIIO 身份、数据类型、具体数量、出境目的）。

**挑战：** 若完全依赖 LLM 理解模糊自然语言输入进行路径判断，结果不确定性高，法律场景无法接受；若强制要求用户精确填写专业字段，使用门槛过高、流失严重。

**解决方案：** 将路径判断与信息收集彻底分离。信息收集阶段，将复杂专业判断拆解为 5 个"最小可回答问题"，每个问题提供有限选项（如数量规模提供"10 万以下/10-100 万/100 万以上"等区间选项）并附字段说明，用户无需理解法律定义即可完成填写。路径判断阶段，完全采用确定性规则状态机执行，不经过 LLM，保证相同输入始终产生相同输出。对于选择"不确定"的字段，系统触发追问提示并在最终报告中标注"需专业法务人员确认"。

**效果：** 路径判断过程零歧义，结论严格可追溯至具体法规条文，判断延迟 <2 秒。

### 6.2 有约束文书生成设计

**问题背景：** 合规报告要作为监管申报材料使用，对格式规范性、内容可追溯性和风险可识别性均有严格要求，普通 LLM 自由生成无法满足。

**挑战：** LLM 自由生成容易产生"语义合理但法律存疑"的内容，且事后难以验证；申报文书格式错误可能导致审核不通过，法律后果严重。

**解决方案：** 设计"JSON Schema 中间态约束"架构。每类报告的每个章节预先定义精确的 JSON Schema（含必填字段、枚举值约束、引用格式规范、风险等级枚举），LLM 不直接生成文档文字，而是生成满足 Schema 的 JSON 结构化对象。程序化校验通过后，Python 渲染层将 JSON 转换为文档格式。此方案将"格式正确"与"内容生成"解耦，确保每份报告的结构、引用格式、风险标注均符合预定规范，同时支持对校验失败内容的精确重试。

**效果：** 报告格式标准化，引用链强制覆盖，所有高风险节点程序化标记，全程可审计。

### 6.3 多轮审查与修正闭环设计

**问题背景：** 企业合规实践中，文件审查不是一次性任务，而是"审查→整改→再审查"的迭代过程，需要系统支持多轮闭环。

**挑战：** 多轮审查需要保证口径一致（不能每次审查同一条款得出不同结论）；同时需要支持"仅重审已修改的条款"以避免重复计算；还需追踪整改进度，让用户知道哪些问题已处理、哪些尚未处理。

**解决方案：** 以 `review_session` 为核心状态单元，在数据库中持久化保存条款切分结果（`clauses_json`）和完整审查记录（`review_result_json`）。用户提交修改版文件时，系统执行 diff 比对，仅对内容发生变化的条款触发重新审查，未变化条款直接复用上一轮结论，保证审查口径稳定。前端支持对每条问题标记处理状态（待处理/已整改/不适用），形成可追踪的整改进度视图，配合"发现问题→修复→复核"的完整操作闭环。

**效果：** 支持多轮迭代审查，条款粒度追踪整改进度，审查口径跨轮次保持一致。
