# 《"数规通"项目 AI 工作流与提示词附录》

## 1. 工作流总体说明

### 1.1 核心工作流总览

"数规通"系统包含三条核心 AI 工作流和一条辅助工作流，共同支撑产品的完整业务闭环：

| 工作流 | 触发条件 | 主要步骤 | 输出物 |
|--------|---------|---------|--------|
| 路径诊断工作流 | 用户提交五问答案 | 规则引擎判断（无 LLM） | 路径诊断 JSON + PDF 报告 |
| 文书生成工作流 | 用户提交表单与附件 | 材料理解→法规检索→章节生成→一致性校验→渲染 | docx/PDF/ZIP 合规报告草案 |
| 文件审查工作流 | 用户上传合同/政策文件 | 文档解析→条款切分→条款分类→逐条审查→聚合输出 | 审查报告 + 问题清单 |
| AI 助手工作流 | 用户发起对话 | 意图识别→RAG 检索→生成回答 | 带引用链的合规咨询回复 |

工作流间存在上下文传递关系：路径诊断工作流的输出（推荐路径 + `context_json`）可直接作为文书生成工作流的输入上下文，企业画像信息自动预填至对应报告模块，避免用户重复输入。

> [待补充] 工作流总览图

### 1.2 模块间数据流转关系

各模块间数据以 JSON 格式传递，通过任务 ID（UUID）在 SQLite 数据库中持久化存储，支持断点续传和异步状态查询：

- **诊断模块 → 报告生成模块：** 路径诊断结论 JSON（包含推荐路径类型、置信度、企业画像预填信息）通过 URL 参数或 `context_json` 字段携带至对应报告模块，触发表单自动预填；
- **报告生成模块内部：** 企业画像（`CompanyProfile` JSON）在五步流水线各节点间传递，每步完成后写入 `report_tasks` 表，前端通过轮询 `/tasks/{task_id}` 获取进度；
- **文件审查模块：** 以 `review_session_id` 为核心状态单元，`clauses_json`（条款切分结果）和 `review_result_json`（审查记录）持久化保存于 `review_sessions` 表，支持多轮迭代审查时仅重审已修改条款。

## 2. 路径诊断工作流

### 2.1 输入结构设计

路径诊断工作流的输入为五个标准化字段的 JSON 对象：

```json
{
  "company_type": "non_CIIO",
  "data_type": "personal_info",
  "volume_normal": "<100w",
  "volume_sensitive": "<1w",
  "transfer_purpose": "intra_group"
}
```

各字段枚举值定义：

| 字段 | 枚举值 | 含义 |
|------|-------|------|
| `company_type` | `CIIO` / `non_CIIO` | 是否为关键信息基础设施运营者 |
| `data_type` | `important_data` / `personal_info` / `sensitive_personal_info` / `mixed` | 出境数据类型 |
| `volume_normal` | `<10w` / `<100w` / `<1000w` / `>=1000w` | 普通个人信息数量规模 |
| `volume_sensitive` | `<1w` / `<10w` / `>=10w` | 敏感个人信息数量规模 |
| `transfer_purpose` | `intra_group` / `partner_collab` / `user_service` / `other` | 出境目的 |

追问机制：若用户选择"不确定"，系统触发追问提示，向用户展示字段的法律定义说明和自检建议，用户确认输入后继续执行判断。对于仍无法确定的字段，最终结论中附加"需专业法务人员确认"标记。

### 2.2 追问与判断逻辑

判断规则树按优先级顺序执行五层决策，每层规则均关联具体法规条文：

- **第 1 层：** `company_type == CIIO` → 强制走安全评估路径（依据：《数据出境安全评估办法》第 4 条第 3 款）
- **第 2 层：** `data_type == important_data` → 强制走安全评估路径（依据：《数据出境安全评估办法》第 4 条第 1 款）
- **第 3 层：** `volume_normal >= 100w` 或 `volume_sensitive >= 10w` → 安全评估路径（依据：《数据出境安全评估办法》第 4 条第 2 款）
- **第 4 层：** `volume_normal >= 10w` 或 `volume_sensitive >= 1w` → 推荐标准合同备案，认证可选（依据：《个人信息出境标准合同办法》第 3 条）
- **第 5 层：** 其余情况 → 推荐标准合同备案或个人信息出境认证（依据接收方关系和出境目的进一步推荐）

上述判断逻辑完全由前端规则状态机执行，不调用 LLM，相同输入永远产生相同输出，判断延迟 <2 秒。

### 2.3 输出结构设计

路径诊断工作流的输出 JSON 结构如下：

```json
{
  "path": "standard_contract",
  "confidence": "HIGH",
  "reasons": [
    {
      "description": "企业属于非CIIO普通企业，不适用强制安全评估条款",
      "law_ref": "《数据出境安全评估办法》第4条第3款"
    },
    {
      "description": "普通个人信息规模50-100万条，未达100万条安全评估阈值",
      "law_ref": "《数据出境安全评估办法》第4条第2款"
    }
  ],
  "caveats": ["需确认接收方是否与数据处理者属于同一企业集团"],
  "next_steps": [
    {"module": "scc", "label": "前往标准合同审查模块"}
  ],
  "context": {
    "company_type": "non_CIIO",
    "recommended_path": "standard_contract",
    "prefill": {
      "enterprise_type": "普通企业（非CIIO）",
      "transfer_volume_normal": "50万–100万条"
    }
  }
}
```

AI 仅参与最终诊断报告说明文字的生成（将 JSON 结构转换为自然语言段落），不参与核心路径判断逻辑。

## 3. 文书生成工作流

### 3.1 模板调用逻辑

系统为每类报告维护独立的章节模板（`chapter_template`），定义该报告所有章节的标题、写作要求和 JSON Schema。以安全评估报告为例，包含 8 个主要章节：

1. 基本情况说明
2. 个人信息出境必要性分析
3. 数据处理者基本情况
4. 境外接收方情况
5. 个人信息安全措施
6. 第三方审计情况
7. 综合风险评估
8. 声明与承诺

每个章节的生成 Prompt 从对应模板中动态加载，确保不同任务、不同时间生成的同类报告格式保持一致。章节模板存储于 `backend/templates/` 目录下，以 YAML 格式定义章节结构和每节的输出 Schema 约束。

### 3.2 事实填充与内容组织逻辑

内容生成采用"事实注入 + 规则引导"模式，具体分三层注入：

**事实层（CompanyProfile）：** 从企业画像 JSON 中提取与当前章节相关的字段注入 Prompt（如生成"境外接收方情况"章节时注入接收方名称、所在国/地区、数据接收目的等字段）。

**法规层（RAG 检索结果）：** 根据每个章节类型预设检索关键词，对本地 1011 条法规索引执行混合检索，重排序后取 Top-N（通常 5–8 条）作为法规上下文注入 Prompt，确保每个章节都有精准的法规依据支撑。

**约束层（Prompt 规则）：** Prompt 明确要求：①事实性内容必须基于输入材料，不得凭空捏造；②法规引用必须来自 RAG 检索结果，不得依赖 LLM 训练记忆；③不确定字段填 `"unknown"`，不允许猜测填写。

### 3.3 结果输出逻辑

生成结果经三步处理后输出至用户：

**Step 1 JSON Schema 校验（Pydantic）：** 检查所有必填字段、枚举值（`risk_level` 必须为 HIGH/MEDIUM/LOW）、引用格式（`references` 列表 `minItems: 1`）、内容长度（`content` 字段 `minLength: 100`）。校验不通过则自动重试，最多 3 次，超限后标记为低置信度（`low_confidence: true`）。

**Step 2 渲染前处理：** 将 JSON 中的 Markdown 语法转换为文档格式标记，处理引用列表格式（法律名称、条文编号、引用原文三段式），为 HIGH 风险内容和人工复核标记添加文档样式标记。

**Step 3 多格式渲染：** 使用 `python-docx` 渲染 Word 格式（加载官方申报模板 `.docx` 样式文件）；生成 PDF 版本；同步生成 Markdown 纯文本版本；最终打包为 ZIP。文件名按 `[企业简称]_[报告类型]_草案_[日期]` 规范命名。

## 4. 文件审查工作流

### 4.1 文档解析逻辑

支持格式：PDF（`pypdf` 解析）、Word（`python-docx` 解析）、纯文本（直接读取）。

解析后执行两阶段条款切分：

**规则切分阶段：** 按句号（。）、分号（；）、条款编号（"第 X 条"、"(x)"、罗马数字）等规则边界进行初步切分，生成候选条款单元列表。

**语义合并阶段：** 对候选单元执行语义连续性判断，将属于同一逻辑条款的相邻句子合并（如"第 3 条 当事人应……该义务包括：(a)…(b)…(c)…" 应合并为一个条款单元而非拆分为四个）。

最终每个条款单元附加元数据：原文文本（`clause_text`）、文档位置（`page_num` + `para_index`）、识别到的条款编号（`clause_id`，如"第 10 条"）。

### 4.2 风险识别逻辑

对每个条款单元依次执行以下四步分析：

**条款类型识别：** LLM 将条款归类到预定义的合规要求类别，包括：数据收集目的与范围、数据主体权利（知情权/删除权/更正权/可携带权）、跨境传输要求、数据安全措施、第三方共享、数据保留期限、泄露通知义务、合同终止与数据销毁等。

**合规性比对：** LLM 将条款内容与对应类别的法规要求进行比对，法规依据来自 RAG 检索（不依赖模型训练记忆），识别问题类型：缺失要素 / 表述不清 / 与法规冲突 / 符合要求。

**风险评级：** 基于问题严重程度（直接违规 / 潜在风险 / 形式瑕疵）、违规可能性和潜在法律后果综合评定 HIGH / MEDIUM / LOW 三级。

**修改建议生成：** 对 HIGH 和 MEDIUM 风险问题生成具体可操作的修改建议，包含参考改写示例文本和所依据法规条文编号。所有分析结果输出须通过 JSON Schema 约束，保证字段完整性。

### 4.3 审查报告生成逻辑

审查完成后生成两类输出：

**条款级问题清单（结构化 JSON / Excel）：** 按风险等级排序，每条记录包含：条款原文（`clause_text`）、文档位置（`page_num`）、问题类型（`issue_type`）、风险等级（`risk_level`）、法规依据（`law_ref`，含条文编号）、修改建议（`suggestion`，含参考改写示例）。Excel 格式额外包含"整改状态"列（待处理 / 已整改 / 不适用），便于整改管理。

**综合审查报告（docx / PDF）：** 包含执行摘要（HIGH 风险问题数量、总体合规评估）、完整问题清单（按风险等级分组展示）、整改优先级建议（HIGH 问题逐条列出整改要点）、审查使用的法规清单附录。报告末尾附有"需律师/法务人员复核"声明，明确不作为最终法律意见。

## 5. 典型提示词示例

### 5.1 系统级提示词

以下为所有模块共用的通用系统 Prompt 基础版本：

```
你是"数规通"法律合规AI助手，专注于企业数据跨境合规领域。
你的职责是辅助法务人员和企业合规团队处理数据跨境合规事务，
包括合规路径分析、合规文书草案生成、合规文件审查等任务。

重要限制：
1. 你只提供合规分析辅助，不提供最终法律意见，所有输出须经律师/法务人员复核确认；
2. 法规引用必须来自提供的参考材料，不得依赖训练记忆中的法规内容；
3. 不确定或无充分依据的结论，必须明确标记"需人工复核"并说明原因；
4. 输出必须严格符合指定的JSON Schema格式。
```

### 5.2 任务级提示词

以下为报告章节生成的完整 Prompt 示例（以"个人信息出境必要性分析"章节为例）：

```
你是数据跨境合规报告生成助手。请基于以下信息生成"个人信息出境必要性分析"章节内容。

## 企业基本信息
{company_profile_json}

## 相关法规参考
{rag_retrieved_regulations}

## 生成要求
1. 分析个人信息出境的业务必要性，结合企业实际业务场景说明出境的具体原因
2. 对照《个人信息保护法》第38-43条及《数据出境安全评估办法》第3条，说明出境的法律依据
3. 评估出境是否符合最小必要性原则（仅传输业务必需的数据类型和数量）
4. 识别潜在风险点，评定风险等级（HIGH/MEDIUM/LOW）

## 输出格式要求（严格按以下JSON Schema输出）
{chapter_schema_json}

重要：每个关键结论必须引用至少1条具体法规依据（含法律名称和条文编号）。
若企业提供材料不足以支撑某项分析，在对应字段填写说明并将low_confidence设为true。
禁止编造企业信息或捏造法规内容。
```

以下为条款审查的完整 Prompt 示例（`clause_reviewer` 模块）：

```
你是法律文档条款审查助手。请对以下合同条款进行合规性审查。

## 待审查条款
条款原文：{clause_text}
条款类型（已识别）：{clause_type}
文档位置：第{page_num}页，第{para_index}段

## 适用法规要求
{rag_retrieved_regulations}

## 审查任务
对照上述法规要求，评估该条款的合规性，输出以下内容：
- 问题类型：缺失要素 / 表述不清 / 与法规冲突 / 符合要求（四选一）
- 风险等级：HIGH / MEDIUM / LOW
- 依据法规：具体条文编号
- 具体问题描述（如有）
- 修改建议（含参考改写示例，如有）

## 约束
- 不得编造法规依据，无充分依据时明确标记"需人工复核"
- 输出必须符合以下JSON Schema：
{review_schema_json}
```

### 5.3 输出约束提示词

以下为章节生成结果的 JSON Schema 定义（`chapter_schema_json` 实际内容）：

```json
{
  "type": "object",
  "required": ["chapter_title", "content", "references", "risk_level", "review_required"],
  "properties": {
    "chapter_title": {"type": "string"},
    "content": {"type": "string", "minLength": 100},
    "references": {
      "type": "array",
      "minItems": 1,
      "items": {
        "type": "object",
        "required": ["law_name", "article_number", "quote"],
        "properties": {
          "law_name": {"type": "string"},
          "article_number": {"type": "string"},
          "quote": {"type": "string"}
        }
      }
    },
    "risk_level": {"type": "string", "enum": ["HIGH", "MEDIUM", "LOW"]},
    "low_confidence": {"type": "boolean"},
    "review_required": {"type": "boolean"},
    "review_reason": {"type": "string"}
  }
}
```
