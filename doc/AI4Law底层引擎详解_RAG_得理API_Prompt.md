# 第一部分：RAG 知识检索系统

## 1.1 什么是 RAG，系统用 RAG 做什么

**RAG**（检索增强生成）的核心思想很简单：**在让 AI 写东西之前，先从知识库中检索相关资料，把这些资料和用户的问题一起交给 AI。** 这样 AI 的回答不是凭记忆"编"的，而是有据可查的。

AI4Law 是一个法律合规系统，对准确性要求极高。如果 AI "编造"了一条不存在的法规，后果可能是企业做了错误的合规判断。所以系统的 RAG 承担了关键角色：

> **AI 写的每一句法律判断，都必须有检索结果作为支撑。**

具体来说，RAG 系统要做三件事：

1. **给定一个业务场景（如"金融科技公司向新加坡传输用户交易数据"），找出相关的中国法律条文。**
2. **找出相关的工作流规则（如"CIIO 必须申报安全评估"的判定逻辑）。**
3. **找出相关的报告模板和标准条款，告诉 AI 文书应该长什么样。**

---

## 1.2 知识库的组织结构：15 个索引 × 4 层知识

系统不是把所有条文扔进一个"大池子"，而是精确地分类存储。

### 15 个向量索引

知识库按两个维度组织：**法域** × **知识类型**。

| | 中国法域（CN） | 欧盟法域（EU） | 美国法域（US） |
|---|---|---|---|
| **法律条文** | 法律条文_中国 | 法律条文_欧盟 | 法律条文_美国 |
| **工作流规则** | 工作流规则_中国 | 工作流规则_欧盟 | 工作流规则_美国 |
| **标准条款** | 标准条款_中国 | 标准条款_欧盟 | 标准条款_美国 |
| **报告模板** | 报告模板_中国 | 报告模板_欧盟 | 报告模板_美国 |
| **测试用例** | 测试用例_中国 | 测试用例_欧盟 | 测试用例_美国 |

共计 **3 × 5 = 15 个独立的向量索引**。每个索引包含一个 `.jsonl` 文件（存储原文）和一个 `.vector.json` 文件（存储向量）。

### 为什么要分 15 个索引？

因为不同模块需要不同组合的知识。例如：

- **中国安全自评估模块**需要：中国法律条文 + 中国工作流规则 + 中国报告模板
- **欧盟 SCC 审查模块**需要：欧盟法律条文 + 欧盟标准条款 + 欧盟工作流规则
- **美国 CPRA 合规模块**需要：美国法律条文 + 美国工作流规则 + 美国标准条款

分索引的另一个好处是：**不会把中国的《个人信息保护法》条文错误地检索给欧盟 GDPR 的审查任务。**

### 四层知识架构（L1-L4）

不仅按法域和类型分，每条知识还有一个"层级"标记，控制它的使用权限：

| 层级 | 名称 | 包含内容 | 谁可以用 | 能用于对外报告吗 |
|------|------|---------|---------|----------------|
| **L1** | 法规证据层 | 法律条文、行政法规、官方指南、标准条款 | 所有模块 | ✅ 可以（标记为"可引用"的） |
| **L2** | 业务规则层 | 工作流规则、诊断逻辑、判定阈值（如"CIIO → 安全评估"） | 内部审查、风险解释 | ❌ 不能（这是系统内部规则，不是法律条文） |
| **L3** | 测试用例层 | 评测用的测试案例 | 仅在评测模式中使用 | ❌ 绝对不能（纯内部测试数据） |
| **L4** | 模板层 | 报告模板、章节结构、文书格式要求 | 控制报告结构、内部起草 | ❌ 不能（模板是格式指引，不是法律依据） |

**使用策略过滤器**会根据"当前处于什么环境（生产/开发/评测）"和"当前需要什么用途（对外报告/内部审查/评测）"，自动过滤掉不合适的知识条目。例如：

- 对外写报告时，自动排除 L2 业务规则、L3 测试用例、L4 模板 —— 只保留 L1 法规证据
- 内部审查时，可以使用 L1 + L2
- 评测模式下，才允许使用 L3 测试用例
- **生产环境下，L3 测试用例绝对不可见**

## 1.3 检索原理：从查询到结果的完整链路

系统使用的不是神经网络语义理解，而是一种**纯本地的、确定性的混合检索方式**。

### 第一步：文本向量化（把文字变成可比较的数学表示）

系统使用一种叫"哈希嵌入"的方法。举个例子：

```
查询文本："金融科技公司向境外传输个人金融信息"

处理过程：
1. 分词：["金融科技", "公司", "境外", "传输", "个人", "金融", "信息"]
2. 对每个词取中文字符：["金","融","科","技","公","司","境","外","传","输","个","人","信","息"]
3. 生成字符组合：单个字 + 连续两个字（如"金融"）+ 连续三个字（如"金融科"）
4. 对每个字符组合做哈希计算：hash("金融") % 384 → 位置 127
5. 统计每个位置出现了多少次，归一化处理
6. 最终得到一个 384 个数字组成的向量 → [0, 0, 0.15, 0, 0.08, ...]
```

这个方法的优点是：**完全离线运行，不需要连接任何外部 AI 服务**。缺点是：它不理解语义——"数据出境"和"跨境传输" 如果字面上不共享词汇，就匹配不上。所以系统还需要下面两种方式来弥补。

### 第二步：词汇检索（关键词硬匹配）

同时，系统使用 SQLite 的全文本搜索引擎（FTS5），对知识库内容做关键词级别的精确匹配。比如查询"个人信息保护法第38条"，能精确匹配到包含这个短语的知识条目。

FTS5 专门为中文做了优化——支持单字符索引，所以搜索"个保法"也能匹配到含有"个人信息保护法"的内容。

### 第三步：混合融合（RRF 融合算法）

向量检索给出一个排序（语义相似但可能不精确），词汇检索给出另一个排序（精确但不理解语义）。系统使用 **RRF（倒数排名融合）** 把两个排序合并：

```text
RRF得分 = 1/(60 + 向量排名) + 1/(60 + 词汇排名)

举例：
  条目A: 向量排名第2，词汇排名第5 → RRF = 1/62 + 1/65 = 0.0161 + 0.0154 = 0.0315
  条目B: 向量排名第1，词汇排名第20 → RRF = 1/61 + 1/80 = 0.0164 + 0.0125 = 0.0289
  → 条目A 综合排名更高（因为两种方式都排名靠前）
```

这种方法的核心思想是：**只有两种检索方式都认可的结果才排在最前面。** 如果某个条目向量排名很高但词汇完全匹配不上，它的综合分会被拉低。

### 第四步：启发式重排序

融合后的结果还会经过一轮启发式重排序，根据手工规则调整分数：

| 加分条件 | 加多少 | 逻辑 |
|---------|--------|------|
| 查询词出现在知识条目的标题中 | +2.0 | 标题匹配说明高度相关 |
| 查询词出现在法条编号中 | +1.2 | 法条编号匹配说明精确命中 |
| 查询词与知识条目内容有词汇重叠 | 每个词 +0.15（上限 +2.4） | 内容越匹配加分越多 |
| 知识条目的法域与查询法域一致 | +0.4 | 法域过滤 |
| 知识条目的合规路径与查询路径一致 | +0.4 | 路径匹配 |

### 第五步：使用策略过滤

重排序后，系统调用"使用策略过滤器"，逐条检查每个检索结果：
- 当前是生产环境吗？→ 排除 L3 测试用例
- 当前要写对外报告吗？→ 排除 L2 业务规则、L4 模板
- 当前是评测模式吗？→ 只保留 L3 测试用例
- 这条知识的法域对吗？→ 错误的法域直接排除
- 这条知识的权威等级够吗？→ 背景参考资料不能作为主要法律依据

过滤后，最终返回给模块使用的检索结果才会确定。

### 第六步：跨索引关联

这是系统的一个精妙设计。当工作流规则索引中的一个条目通过引用编号指向某个法律条文时，系统会自动到法律条文索引中查找并附带原文。

```text
工作流规则"安全评估路径触发：CIIO"
  → reference_ids 包含 ["个人信息保护法-第40条"]
  → 自动到法律条文索引中查找 → 带回第40条全文
```

这样，检索一份工作流规则也就同时带回了支撑它的法律条文。

## 1.4 双轨制：V2 传统路径 vs V3 编排器路径

系统实际上有**两套**检索机制，新老并存。

### V3 编排器（当前主力）

V3 是系统的主力检索路径。它的核心组件是 **RetrievalOrchestrator（检索编排器）**。

编排器的工作方式是"按模块分派"——不同的业务模块触发不同的检索策略：

```text
中国诊断模块 → 只检索 中国工作流规则
中国安全自评估 → 检索 中国工作流规则 + 中国法律条文 + 中国模板
中国标准合同审查 → 检索 中国工作流规则 + 中国法律条文 + 中国标准条款 + 中国模板
欧盟 SCC 审查 → 检索 欧盟工作流规则 + 欧盟法律条文 + 欧盟标准条款 + 欧盟模板
欧盟 BCR 审查 → 同上
欧盟 DPIA → 同上
欧盟 TIA → 同上
美国 EO14117 / CPRA / 供应商审查 / 隐私审查 → 美国对应的所有索引
```

每个模块的检索策略都是精心配置的——不是检索全部 15 个索引，而是只检索和当前任务相关的 3-5 个索引。这样可以避免"中国的法律条文出现在欧盟审查报告里"这类法域污染。

此外，编排器使用 **LRU 缓存**（最近最少使用缓存）：每个索引首次加载后缓存在内存中，下次访问直接使用，不需要重新从磁盘读取。只有在索引文件发生变化（版本号不同）时才重新加载。

### V2 传统检索器（兜底路径）

V2 是更早期的实现，将所有法律条文放在一个单一索引中。它提供：
- 纯向量检索
- 纯词汇检索（FTS5）
- 增强混合检索（向量 + 词汇 + RRF 融合，仅在显式启用时）

V2 当前的角色是**兜底**：如果 V3 编排器不可用或返回空结果，系统回退到 V2。

### V3 vs V2 对比

| 维度 | V3 | V2 |
|------|-----|-----|
| 索引数量 | 15 个 | 1 个 |
| 按模块分派 | ✅ 每个模块有专属的检索策略 | ❌ 所有模块共享 |
| 跨索引关联 | ✅ 工作流规则自动关联法律条文 | ❌ 不支持 |
| 使用策略过滤 | ✅ 按 4 层知识 + 环境过滤 | ✅ 简化版 |
| 性能 | 多次检索但只在内存中 | 单次检索 |
| 当前状态 | 主力路径 | 兜底路径 |

## 1.5 知识是如何建立和维护的

### 知识来源

| 知识类型 | 来源 | 示例 |
|---------|------|------|
| 法律条文 | 人工整理的法规数据库 | 《个人信息保护法》第1-74条，逐条存储 |
| 工作流规则 | 法务团队手工编写的判定逻辑 | "CIIO的条件是..."，"安全评估门槛是..." |
| 标准条款 | 法规原文中的标准合同条款 | 《个人信息出境标准合同》必备条款清单 |
| 报告模板 | 法务团队按官方要求设计的模板结构 | 安全自评估报告的8章大纲 |
| 测试用例 | QA团队编写的评测案例 | "某金融CIIO向新加坡传输80万条数据"→应判定为安全评估 |

### 索引构建流程

索引不是实时更新的，而是**按需一次性构建**：

1. **读取源数据**：从 JSONL 文件中读取所有知识条目
2. **文本预处理**：提取标题、法条号、正文、关键词
3. **向量化**：对每条知识做哈希嵌入，生成 384 维向量
4. **存入索引文件**：向量数据写入 `.vector.json`，原文写入 `.jsonl`
5. **添加版本标记**：在元数据中写入 `"schema_version": "v3.1"`

构建完成后，15 个索引文件存储在本地磁盘中。系统启动时检查索引文件是否存在，不存在则自动构建。

### 知识的更新策略

工作流规则是**硬编码在代码中的**（如"CIIO 阈值是 100 万人"）。这意味着这些规则的更新需要修改代码。

法律条文数据存储在 `doc/knowledge/` 目录下的 JSONL 文件中。更新条文后需要重新构建索引（删除旧索引文件，系统下次启动时自动重建）。

值得一提的是，系统的嵌入方法是**纯哈希**，不依赖任何外部模型或 API —— 这意味着升级"嵌入模型"不涉及重新训练或 API 迁移，只需要在代码中改变哈希维度。

## 1.6 检索效果评测体系

系统内置了一套完整的检索评测框架，可以自动检测检索质量。

### 检索评测（测找得准不准）

评测数据位于专门的评测文件中，每条评测用例包含：
- **查询文本**：模拟用户实际会产生的查询
- **必须检索到的知识条目编号**：该查询"必须"返回这些结果
- **绝对不能检索到的知识条目编号**：该查询"绝对不能"返回这些结果
- **不能检索的层级**：如 L3 测试用例绝对不能出现
- **不能跨法域污染**：中国法域查询不能返回欧盟法域结果

评测指标：

| 指标 | 含义 | 计算方式 |
|------|------|---------|
| **召回率@K** | 前 K 个结果中包含了多少"必须找到"的知识 | 命中的必须条目数 / 全部必须条目数 |
| **MRR**（平均倒数排名） | 第一个正确结果平均排在第几位 | 第一个相关结果的排名的倒数的平均值 |
| **禁用层级泄漏率** | 不该出现的知识层级出现了多少次 | 违规条目数 / 总条目数 |
| **跨法域污染率** | 检索到了错误法域的知识 | 跨法域条目数 / 总条目数 |

### 生成评测（测最终报告质量）

除了测检索，系统还测"检索结果最终有没有进入 AI 生成的报告"：

| 指标 | 含义 |
|------|------|
| **问题发现召回率** | 系统发现了多少"应该发现"的合规问题 |
| **引用正确率** | 报告中的法规引用有多少是正确的 |
| **禁用来源泄漏** | 报告中是否出现了不应该出现的知识来源（如 L3 测试用例） |
| **无支撑断言率** | 报告中是否出现了没有法规支撑的判断 |

## 1.7 完整检索案例：安全自评估模块查询"金融行业数据出境法规"

下面以中国安全自评估模块的一次真实检索为例，完整走一遍流程。

### 背景

用户填写的信息：
- 企业：某金融科技公司
- 行业：金融科技
- 出境目的：向新加坡母公司传输交易数据用于统一风控
- 接收方国家：新加坡
- 是 CIIO，涉及 80 万条个人信息，5 万条敏感个人信息

### 系统做了什么

**第 1 步：构造查询**

系统的检索器不是直接把用户填的"金融科技"作为查询词扔进去，而是从企业画像中提取关键信息，拼接成有意义的检索语句：

```
查询 = "金融科技 industry 向新加坡传输 data 个人信息 重要数据 安全评估 CIIO"
```

这条查询包含了行业、目的、接收方国家、数据类型、CIIO状态等多个维度，确保覆盖全面。

**第 2 步：V3 编排器分派**

安全自评估模块 → 匹配到 `cn_assessment` 检索策略 → 并行检索 4 个索引：
- 中国工作流规则索引
- 中国法律条文索引
- 中国模板索引
- 中国测试用例索引

**第 3 步：每个索引内混合检索**

以"中国法律条文索引"为例：

- 向量检索：将查询文本做哈希嵌入，与索引中 500+ 条法律条文的向量逐一计算相似度
- 词汇检索：FTS5 全文搜索匹配 "个人信息"、"安全评估"、"数据出境"、"CIIO" 等关键词
- RRF 融合：两个排序合并

各索引的排名靠前结果：

```
中国法律条文索引：
  第1名: 《数据出境安全评估办法》第四条 — "CIIO...向境外提供个人信息和重要数据的，应当...申报数据出境安全评估"
  第2名: 《数据出境安全评估办法》第五条 — "数据处理者向境外提供数据，符合下列情形之一的，应当...申报数据出境安全评估：（一）向境外提供重要数据..."
  第3名: 《个人信息保护法》第三十八条 — "个人信息处理者...确需向境外提供个人信息的，应当具备下列条件之一..."
  第4名: 《数据出境安全评估申报指南（第二版）》— 申报材料清单及要求
  第5名: 《个人信息保护法》第四十条 — "关键信息基础设施运营者...向境外提供个人信息，应当...通过安全评估"

中国工作流规则索引：
  第1名: CIIO判定规则 — "q1_is_ciio=yes → path=security_assessment"
  第2名: 安全评估材料清单 — 申报安全评估需要提交的10项材料
  第3名: 重要数据阈值规则 — "contains_important_data=true → security_assessment"

中国模板索引：
  第1名: 安全自评估报告第2章模板 — "数据出境涉及业务和信息规模"章节结构
  第2名: 安全自评估报告第3章模板 — "数据出境必要性及合法正当性"

中国测试用例索引：被使用策略过滤器排除（生产环境不允许使用测试用例）
```

**第 4 步：跨索引关联**

工作流规则中第 1 名"CIOO 判定规则"在数据中标记了引用编号 `["个人信息保护法-第40条", "数据出境安全评估办法-第4条"]`。

系统自动到法律条文索引中查找这两个条文，带回了全文内容。这样，工作流规则的检索结果也就有了法律条文的支撑。

**第 5 步：使用策略过滤**

当前是生产环境，要生成对外报告 → 过滤规则：
- L3 测试用例 → 排除（禁止在生产环境使用）
- L4 模板 → 保留（生成报告需要模板结构指引）
- L2 工作流规则 → 排除（不在对外报告中直接引用）
- L1 法律条文 → 保留（可以在报告正文中引用）

**第 6 步：最终返回给模块的检索结果**

过滤后的结果：
- 5 条法律条文（L1，可用于报告正文引用）
- 2 条报告模板章节结构（L4，用于指导 AI 写报告格式）
- 2 条工作流规则（L2，用于规则引擎内部判断）

这些结果会在后续步骤中被放入"生成上下文包"，成为 AI 写报告时的法律依据来源。

# 第二部分：得理法律 API 集成

## 2.1 得理 API 是什么，系统用它做什么

**得理**（DeliLegal，网址 `openapi.delilegal.com`）是一个第三方法律数据开放平台，提供中国法律法规和司法案例的搜索服务。

系统把得理 API 定位为**本地知识库的补充和兜底**：

```text
本地 RAG 知识库：系统自有、离线可用，但覆盖范围有限（约几百条核心法规条文）
得理 API：在线、覆盖面广（全量法规数据库），但依赖网络且速度慢
```

两者的关系是：**本地 RAG 先行，得理 API 兜底**。

得理 API 在四个场景下被调用：

| 场景 | 调用方式 | 目的 |
|------|---------|------|
| 本地检索结果不足（少于3条） | 自动兜底 | 补充检索更多法规条文 |
| 路径诊断时 | 每次诊断都调用 | 补充相关的案例参考和法规条文 |
| 高风险问题需要更多法规支撑 | 按需调用 | 为 HIGH/BLOCKER 级别的问题寻找更多法规证据 |
| 合同审查时 | 按需调用 | 查找与具体条款相关的司法案例 |

---

## 2.2 API 的认证与连接方式

得理 API 使用**静态凭据认证**，不需要 OAuth 令牌或定期刷新。

每个请求都会在 HTTP 头部中附带两个字段：

```
appid: <应用ID>
secret: <密钥>
```

凭证通过项目的环境变量配置：

```
AI4LAW_DELILEGAL_BASE_URL=https://openapi.delilegal.com
AI4LAW_DELILEGAL_APP_ID=QthdBErlyaYvyXul
AI4LAW_DELILEGAL_SECRET=EC5D455E6BD348CE8E18BE05926D2EBE
```

如果这两个凭证为空，得理 API 功能自动禁用，系统仅依赖本地 RAG。

---

## 2.3 两个搜索接口详解

得理 API 提供两个搜索接口，系统都使用了。

### 接口一：法规条文搜索

```
POST /api/qa/v3/search/queryListLaw
```

**这个接口查找的是法律法规条文**——《个人信息保护法》第几条写了什么。

请求内容（简化为通俗描述）：
- 页码：第 1 页
- 每页条数：5 条
- 排序方式：按相关度降序
- 搜索关键词：用户查询（如"数据出境 安全评估 CIIO 金融"）
- 搜索模式：语义搜索

返回结果中，系统提取三个字段：
- **法规标题**：如《数据出境安全评估办法》
- **来源**：如"全国人大常委会"或"国家互联网信息办公室"
- **内容摘要**：法规条文的核心内容

### 接口二：司法案例搜索

```
POST /api/qa/v3/search/queryListCase
```

**这个接口查找的是司法案例**——与"数据出境"相关的实际判决或行政决定。

请求内容：
- 页码：第 1 页
- 每页条数：3 条（比法规查得少，因为案例通常作为参考而非主要依据）
- 排序方式：按相关度降序
- 搜索关键词：用户查询

返回结果中，系统提取三个字段：
- **案例标题**：如"某金融科技公司数据出境安全评估案"
- **来源法院**：如"国家互联网信息办公室"
- **内容摘要**：案例的核心事实和结论

### 响应解析的鲁棒性

得理 API 的响应格式可能因接口版本不同而略有变化。系统做了多层次的兜底解析：
- 先尝试从 `body.data` 路径提取
- 如果不行，尝试 `data` → `result` → `records` → `list` → `rows`
- 如果还不行，在返回体中递归搜索数组
- 如果完全无法解析，返回空列表

每个 API 调用设置了 **10 秒超时**，超时后自动返回空结果，不影响主流程。

## 2.4 四个使用场景：API 在哪些地方被调用

### 场景一：RAG 检索的兜底补充

**触发条件**：本地 RAG 检索返回的法规条文少于 3 条。

**调用方式**：
- 调用法规条文搜索接口
- 搜索关键词 = 用户原始查询
- 取 `top_k - 已有条数 + 2` 条结果
- 结果标记为"得理法搜"来源，与本地结果合并
- 按标题去重（本地已有同样的法规则不重复加入）

**示例**：用户查询"区块链企业数据出境合规要求"，本地 RAG 只找到 2 条相关法规（因为这个领域的法规较少）。系统自动调用得理 API 搜索，补充找到 3 条，最终返回 5 条给业务模块。

### 场景二：路径诊断时的引用补充

**触发条件**：每次路径诊断都调用。

**调用方式**：
- 搜索案例：`search_cases("数据出境 {出境目的}", 2条)`
- 搜索法规：`search_laws("数据出境 {出境目的} 合规路径", 3条)`
- 搜索结果附加到诊断报告的"引用"部分
- 每条引用标注"来自得理法搜的补充检索结果"

**示例**：用户完成诊断后，系统自动搜索与"向新加坡母公司传输交易数据"相关的法规和案例，将这些引用附在诊断报告中，增强报告的权威性。

### 场景三：高风险问题的强化检索

**触发条件**：安全自评估模块中，问题严重度为 HIGH 或 BLOCKER。

**调用方式**：
- 对每个高风险问题，使用"问题标题 + 问题描述"作为搜索关键词
- 搜索法规 3 条 + 案例 2 条
- 结果合并到法律依据中，标注为"得理 API 检索"
- 法规结果置信度设为 0.85，案例结果置信度设为 0.75

**示例**：系统识别出一个 BLOCKER 级别的问题——"企业为 CIIO 但未完成安全评估"。系统自动调用得理 API 搜索相关的法规和案例，找到《数据出境安全评估办法》第四条原文和一份相关行政决定案例，补充为这个问题的法律依据。

### 场景四：合同审查时的条款级案例查找

**触发条件**：合同审查模块中，对具体条款做深度审查时。

**调用方式**：
- 取条款正文前 80 个字作为搜索关键词
- 搜索司法案例 2 条
- 将找到的案例信息格式化为引用文本，附加在审查意见中

**示例**：审查一份数据出境协议的第 5 条"再转移条款"，系统取条款前 80 字"境外接收方不得将数据再转移给第三方，除非获得数据处理者事先书面同意且与第三方签订不低于本协议保护标准的书面协议..."，搜索相关司法案例，看中国法院对类似条款是如何认定的。

## 2.5 运行时热切换：不停机更换 API 凭证

系统支持在运行时更换得理 API 的凭证，不需要重启服务器。这是通过前端"系统设置"页面实现的。

流程如下：

```
用户在前端设置页面修改 API 凭证
  → 前端发送 PUT 请求到 /api/v1/system/settings/runtime
  → 后端将新凭证保存到配置文件 (storage/runtime_settings.json)
  → 后端创建新的得理 API 客户端实例
  → 注入到所有使用得理 API 的服务中：
      - 诊断服务
      - 安全自评估服务
      - RAG 检索器
      - 合同审查服务
      - 所有其他模块服务
  → 完成，后续调用使用新凭证
```

## 2.6 错误处理与降级策略

得理 API 是外部依赖，网络不稳定、API 服务故障、凭证过期等都可能导致调用失败。系统的降级策略是：

| 故障类型 | 系统反应 |
|---------|---------|
| API 未配置凭证 | 自动禁用，所有调用不执行，不影响主流程 |
| 网络超时（10秒） | 返回空结果，`last_error` 记录"请求超时" |
| API 返回错误 | 返回空结果，`last_error` 记录错误信息 |
| API 响应格式异常 | 尝试多种路径解析，最终返回空结果 |
| 合同审查中调用失败 | 错误信息直接写入审查意见："得理 API 暂时不可用：{错误原因}" |

核心原则：**得理 API 是锦上添花，不是必需品。任何时候它失败了，系统都能继续工作。** 最坏情况是少了几个外部检索的法规引用，但本地 RAG 仍能保证基本的法规支撑。

# 第三部分：Prompt 提示词体系

## 3.1 系统如何与大模型对话：七个角色

系统在调用大模型时，会先给它分配一个"角色"。角色决定了 AI "以什么身份"来回答问题。系统中定义了 11 个不同的角色：

## 3.2 提示词的五层构造方式

系统传给 AI 的提示词不是简单的一句话，而是由五个层次精密构造的：

### 结构示意

```
┌──────────────────────────────────────────────────────┐
│ 第一层：角色定义（系统提示词）                          │
│ "你是一名专注于中国数据出境安全评估领域的资深律师..."    │
├──────────────────────────────────────────────────────┤
│ 第二层：章节指令                                      │
│ "你正在撰写《数据出境风险自评估报告》的第2章..."        │
│ "本章应当覆盖以下内容：..."                           │
├──────────────────────────────────────────────────────┤
│ 第三层：结构化上下文                                    │
│ 【企业事实】企业名称: XX / 行业: 金融科技 / CIIO: 是... │
│ 【诊断结果】推荐路径: 安全评估 / 风险: 高...            │
│ 【法规依据】《数据出境安全评估办法》第四条: ...          │
│ 【识别问题】I-001 [阻断] CIIO触发安全评估...             │
│ 【证据链】E-001: CIIO数据出境的路径判断，置信度0.95...   │
│ 【写作策略】问题I-001: 对外表述为"企业作为CIIO，应当..." │
├──────────────────────────────────────────────────────┤
│ 第四层：严格约束                                       │
│ 1. 仅使用上述上下文中的信息，不得添加任何事实              │
│ 2. 缺失信息写"未提供"或"需补充"，不得假设                  │
│ 3. 猜测必须标注【推测】                                  │
│ 4. 每段结尾必须引用法规（格式：【依据：法规标题+条款】）    │
│ 5. 不得使用以下表述："完全合规"、"无风险"、"已充分证明"...│
├──────────────────────────────────────────────────────┤
│ 第五层：输出指令                                       │
│ "请直接输出章节正文，不需要前言和说明..."                │
└──────────────────────────────────────────────────────┘
```

### 第一层：角色定义

让 AI 知道"我是谁、我懂什么"。使用系统提示词（system prompt）实现。这是大模型 API 中持久性的角色设定。

### 第二层：章节指令

告诉 AI "你现在在写报告的哪一章、这一章要写什么"。例如对于安全自评估报告的第 2 章"数据出境涉及业务和信息规模"：

```text
你现在正在撰写《数据出境风险自评估报告》的第2章：数据出境涉及业务和信息规模。

本章要求：
- 列明本次出境涉及的数据类型、数据主体范围
- 说明各类数据的体量（个人信息条数、敏感个人信息条数）
- 明确数据来源和信息处理的目的
- 如果涉及重要数据，需单独说明
- 注意：本章只陈述事实，不进行法律判断。法律判断留给后续章节。
```

### 第三层：结构化上下文

这是最核心的一层——将所有中间产物组织成 AI 能理解的结构化信息。不同模块构造方式不同：

**对于复杂模块（安全自评估）**：使用专门的"上下文构建器"，从"生成上下文包"中提取信息。按章节筛选：
- 筛选"影响输出章节"包含当前章节的问题
- 筛选"被哪些章节使用"包含当前章节的证据
- 提取与当前章节相关的法规条文
- 附加该章节适用的写作策略

**对于一般模块**：使用 `module_generator.py` 中的通用方法，上下文是一个文本块，包含企业信息、合规差距摘要和风险等级。

### 第四层：严格约束

每个提示词结尾都附带一份强约束，限制 AI 的行为。通用约束包括：

1. **仅使用提供的上下文**，不得添加事实
2. **缺失信息写"未提供"**，不得假设"材料齐备"
3. **猜测必须标注【推测】**
4. **每段结尾必须引用法规**，格式为 `【依据：法规标题+条款】`
5. **标题必须独立成行**，禁止粘连式标题
6. **使用 Markdown 格式**（`#`、`##`、`###`、`1.`、`-`）

安全自评估模块还有额外的增强约束：
7. **使用 `{{CIT-xxx}}` 标记格式做引用**（系统在后期渲染时替换为规范脚注）
8. **对外报告只能使用 `external_expression`**，不能使用 `internal_expression`
9. **禁止使用全局禁用的表达式**（如"完全合规"）
10. **证据不足的问题必须使用谨慎表述**
11. **仅有用户声明而无证据支持的事实**不能作为外部结论的唯一依据

### 第五层：输出指令

最后一句通常为：`"请直接输出章节正文，不需要前言和解释说明。"` 这确保 AI 不输出"好的，我来为您写第2章..."这类废话。

## 3.3 法律文书的专用约束体系

法律文书不同于一般文章，有些话绝对不能说。系统的约束体系包括：

### 三层嵌套约束

```
全局通用约束（所有模块共享）
  └── 模块专属约束（某类报告的限制）
        └── 问题级约束（针对特定合规问题的措辞限制）
```

### 按问题确定性分级决定措辞

| 问题确定性 | 对外报告中的措辞策略 | 示例 |
|-----------|-------------------|------|
| 已确认问题 | 肯定语气 | "经核实，企业的数据处理协议缺少再转移约束条款" |
| 疑似问题 | 保留语气（模糊措辞） | "尚无法确认企业是否已建立完善的数据分类分级制度" |
| 建议复核项 | 建议语气 | "建议核验境外接收方所在国家/地区的数据保护法律环境" |

### 按证据成熟度决定断言程度

| 证据状态 | 对外报告中可以怎么写 | 不能怎么写 |
|---------|-------------------|-----------|
| 仅有用户声明 | 不能说"具备"、"已完成" | 只能写"用户声明..." |
| 有部分证据 | 可以说"用户提供了...材料"，但需注明不完整 | 不能说"已充分证明" |
| 有文件证明 | 可以说"根据...文件，企业已建立..." | 需要引用文件位置 |
| 经第三方验证 | 可以做肯定断言 | 仍需标注验证来源 |

## 3.4 表达安全机制

这是系统最独特的防线——**禁止表达规则（Forbidden Expression Rules）**。

法律合规领域有一个铁律：**绝对不能对用户说"你违法了"**。因为系统的判断可能出错，而且"违法"是一个法律定性，只有监管机关和法院才有权做出。系统只能判断"与某法律要求不一致"。

同样，系统也不能替用户做承诺。报告不能写"本企业已建立完善的安全管理体系"——这等于在对外发文中替用户做了声明。

### 10 条中国法域强制禁止表达

这些规则标记为 **BLOCKER**（阻断级），在输出前会自动检测和替换：

| 编号 | 禁止的表述 | 原因 | 应替换为 |
|------|----------|------|---------|
| 001 | "违反" | 系统不能做违法定性 | "与……存在不一致" |
| 002 | "违法" | 同上 | "可能不符合……相关要求" |
| 003 | "违规" | 同上 | "需要进一步满足……规定" |
| 004 | "已经构成" | 系统不能做法律定性 | "可能存在……风险" |
| 005 | "完全合规" | 任何系统都不能担保完全合规 | "在现有材料条件下，基本满足……要求" |
| 006 | "已充分证明" | 系统不能替用户做判断 | "用户已提供……材料" |
| 007 | "确保不会" | 不能做绝对保证 | "有助于降低……风险" |
| 008 | "不存在任何风险" | 不存在零风险的情况 | "在当前材料范围内，未发现额外风险点" |
| 009 | "应立刻停止" | 不能替监管机关做决定 | "建议审慎评估是否继续该处理行为" |
| 010 | "已完成全部" | 不能说"全部"，系统不知道有多少 | "已完成……方面的合规工作" |

### 两层表达：对外 vs 对内

每个合规问题都有两套表述：

**对内表述**（内部审查视图）：直接描述问题，不修饰。例如：
> "用户声称已取得全部个人信息主体的同意，但上传的同意记录文件仅覆盖 2025 年 1-3 月，缺少 4-6 月的记录。实际情况可能未取得完整的同意。"

**对外表述**（写入正式报告的客户端视图）：使用合法、稳妥的措辞。例如：
> "涉及个人信息出境的，应进一步补充告知、单独同意或适用豁免情形的说明及佐证材料，确保符合《个人信息保护法》第十三条、第三十九条的相关要求。"

对内表述告诉法务顾问"真实情况可能是什么"，对外表述告诉客户"你需要做什么、依据是什么"。

## 3.5 AI 代理的提示词设计

系统中有 30+ 个 AI 代理，每个代理有自己的专属提示词。代理之间通过精心设计的提示词来保证输出质量。

### 代理提示词的统一模式

所有代理都遵循三要素结构：

```
1. 角色声明（一句话）："You are a Chinese data protection lawyer specializing in..."
2. 任务描述（2-3句）：具体需要代理分析和判断什么
3. 输出格式（必须）："Output ONLY valid JSON. No other text."

JSON 格式示例：
{
  "field1": "value",
  "field2": ["value1", "value2"],
  ...
}
```

### 要求 JSON 输出的原因

所有代理都被要求**只输出 JSON 格式**，不允许输出自然语言解释。这样做的原因：

1. **机器可解析**：JSON 可以被代码直接读取，不需要再"理解"AI 的自然语言回答
2. **字段严格**：如果 AI 漏了某个必填字段，代码能立即检测到并提示重试
3. **降低随机性**：要求结构化输出时，AI 的"创造性"被限制在固定的框架内，减少跑偏的可能性
4. **容错设计**：如果 AI 返回的 JSON 无法解析（格式错误），代理返回 None，系统回退到确定性规则——不会因为一个代理的失败而阻断整个流程

### 代理容错原则

**任何代理失败都不能阻断主流程。** 这是系统的一条铁律。

设计上：
- 所有 AI 代理的调用都被包裹在"尝试-捕获"中
- 代理失败/超时/返回垃圾数据 → 返回 None 或默认值
- 主流程使用代理结果（如果成功）增强质量，但不依赖代理结果来保证基本功能
- 禁用 AI 时，所有代理不能运行，但系统仍能基于确定性规则引擎正常工作

## 3.6 LLM 输出的后处理

AI 的输出不是直接写入报告的。它要经过三道后处理工序：

### 工序一：引用补全

AI 可能在某些段落遗漏了法规引用。后处理会检查每一段：
- 如果段落末尾已有 `【依据：...】` 标记 → 保留
- 如果段落末尾没有 → 从该章节的法规引用列表中取最多 3 条，追加到段末
- 如果完全没有引用可用 → 追加 `【依据：未检索到相关法规依据】`

### 工序二：法律文书格式规范化

AI 输出的格式经常不规范——标题粘连、空格混乱、编号不统一。后处理会：

- 将 `第一章......一、......（一）......` 这种粘连的标题拆分成独立行
- 将中文序号 `一、` / `二、` 转换为 Markdown 的 `##` 标题
- 将中文括号序号 `（一）` / `（二）` 转换为 Markdown 的 `###` 标题
- 将 `【依据：...】` 块放在独立行上
- 规范化多余的空白行

### 工序三：引用标记替换

在 AI 生成报告时，使用的是占位符格式的引用标记 `{{CIT-xxx}}`（如 `{{CIT-PIPL-ART13-P1}}`），而不是直接写"《个人信息保护法》第13条"。这样做的原因是：

- 同一个法规可能被引用多次，使用占位符可以保证全文引用编号一致
- 后期可以批量替换为脚注格式，如 `[1]`, `[2]`
- 引用注册表（CitationRegistry）管理所有引用的全局编号

后处理会扫描全文，将每个 `{{CIT-xxx}}` 替换为统一的脚注编号 `[1]`, `[2]`, `[3]`...

## 3.7 完整 Prompt 构造案例：生成报告第2章

下面完整展示安全自评估模块生成报告第 2 章"数据出境涉及业务和信息规模"时的完整 Prompt。

### 组装过程（分 8 步）

**步骤 1：确定角色**

```text
系统提示词：你是一名专注于中国数据出境安全评估领域的资深律师。
你精通《个人信息保护法》《数据安全法》《数据出境安全评估办法》
《数据出境安全评估申报指南》等法规，
能够为企业撰写专业的数据出境风险自评估报告。
```

**步骤 2：附加章节指令**

```text
你现在正在撰写《数据出境风险自评估报告》的第2章：数据出境涉及业务和信息规模。

本章是整份报告中最"事实密集"的一章，需要客观、准确地列明：
1. 出境数据的业务背景和场景
2. 涉及的数据类型与分类（个人信息/敏感个人信息/重要数据/一般数据）
3. 各类数据的规模（条数、涉及人数）
4. 数据来源和收集渠道
5. 数据在境内外的处理链路概要

写作要求：
- 基于提供的事实数据如实撰写，不做主观判断
- 如果某项信息缺失，注明"需补充"，不得推断或假设
- 涉及个人信息数量时，注明统计口径和时间范围
```

**步骤 3：填充结构化上下文**

```text
【基本信息】
模块: 安全自评估
请求编号: a7b3c9d1-e2f3-4567-89ab-cdef01234567
推荐路径: security_assessment

【企业事实】
F-001 | 企业名称 = "星辰支付科技有限公司" | 来源: 用户表单 | 置信度: 1.0
F-002 | 行业 = "金融科技" | 来源: 用户表单
F-003 | 是否CIIO = 是 | 来源: 用户表单
F-005 | 个人信息数量 = 800000条（近12个月累计） | 来源: 用户表单
F-006 | 敏感个人信息数量 = 50000条（银行卡号、交易记录等） | 来源: 用户表单
F-007 | 出境目的 = "向新加坡母公司传输交易数据用于统一风险控制管理"
F-008 | 接收方国家 = "新加坡"
F-011 | 数据资产条目1 = "用户交易流水" | 类型: 含敏感个人信息 | ...

【附件解析】
- 数据处理协议.pdf: 包含数据传输条款（第5条），缺少再转移约束条款
- 等保测评报告.pdf: 企业通过等保三级测评，有效期至2026年12月

【相关法规依据】
1. 《数据出境安全评估办法》第四条: "关键信息基础设施运营者...向境外提供个人信息和重要数据的，应当...申报数据出境安全评估。"
2. 《数据出境安全评估办法》第五条: "数据处理者向境外提供数据，符合下列情形之一的，应当...申报数据出境安全评估..."

【本章相关问题】（筛选 affects_outputs 包含"data_scope"的问题）
I-003 | 标题: "个人信息规模触发安全评估门槛" | 严重度: HIGH | 确定性: 已确认
      事实依据: F-005(PII=80万)，F-006(SPI=5万)
      建议措施: 该规模已远超法定门槛，确认需走安全评估路径

【写作策略】（本章适用的问题措辞策略）
问题 I-003 (对外表述): "根据《数据出境安全评估办法》第四条规定，
企业处理个人信息规模已达到申报安全评估的法定门槛。
企业应在自评估报告中如实披露个人信息和敏感个人信息的处理规模、
出境目的及境外接收方情况。"
禁止表述: "必然触发"、"自动进入"、"一定需要"
```

**步骤 4：附加严格约束**

```text
【严格约束 - 必须遵守】
1. 仅使用上述上下文中的信息。不得添加任何上下文未提供的事实、数据或企业情况。
2. 缺失的信息写"未提供"或"需补充"，不得假设"已完成"或"材料齐备"。
3. 任何基于推测的内容必须标注【推测】。
4. 每段结尾必须引用法规依据，格式为 {{CIT-xxx}} 标记。
5. 标题必须独立成行。
6. 对外报告只能使用 external_expression 中的表述，不得使用 internal_expression。
7. 绝对不得使用以下表述：完全合规、无风险、已充分证明、必然合法。
8. user_claim_only 的事实不能作为外部结论的唯一依据。
```

**步骤 5：附加输出指令**

```text
请直接输出第2章的正文，不要输出章节标题（系统会另行添加），也不需要前言。
```

**步骤 6：调用大模型**

```text
llm_client.chat(
    system = "你是一名专注于中国数据出境安全评估领域的资深律师...",
    user = "你现在正在撰写...\n\n【基本信息】...\n\n请直接输出章节正文...",
    temperature = 0.2,    # 低温度 = 更确定、更少"创造性"发挥
    max_tokens = 800       # 限制输出长度
)
```

**步骤 7：后处理 AI 输出**

AI 返回的内容：
```markdown
星辰支付科技有限公司（以下简称"本公司"）作为一家金融科技企业，
在日常经营中通过其支付平台收集并处理大量用户的交易数据。
本次评估涉及的出境数据主要为本公司向位于新加坡的母公司——
新加坡XX金融控股有限公司传输的用户交易数据，
用于集团统一风险控制管理和反洗钱合规审查。

本次出境涉及的数据类型包括：
1. 用户基本身份信息：包括用户姓名、身份证号码、手机号码等，
   属于个人信息，涉及约80万人。
2. 用户交易信息：包括银行卡号、交易金额、交易时间、交易对手等，
   其中银行卡号及交易记录属于敏感个人信息，涉及约5万条。
3. 关于是否涉及重要数据出境，目前尚无法确认{{CIT-REG-003}}。
   建议公司尽快完成数据分类分级工作，
   明确交易数据是否构成金融行业重要数据。

根据《数据出境安全评估办法》第四条及第五条规定{{CIT-REG-001}}{{CIT-REG-002}}，
本公司作为关键信息基础设施运营者（CIIO），
且个人信息处理规模已达到申报数据出境安全评估的法定门槛，
应当依法申报数据出境安全评估。
```

后处理：
1. **引用补全**：第3段末尾没有引用，系统自动从该章引用列表中追加了 `{{CIT-REG-003}}`
2. **格式规范化**：标题结构正常，无需处理
3. **引用标记替换**：`{{CIT-REG-001}}` → `[1]`，`{{CIT-REG-002}}` → `[2]`，`{{CIT-REG-003}}` → `[3]`

**步骤 8：写入报告**

后处理完成后的章节正文被写入报告文件中，与其他 7 章一起构成完整的自评估报告。

### 到这个案例结束

这个大模型调用展示了系统的核心能力：

- AI 没有编造任何上下文之外的事实
- AI 对不确定的信息（重要数据状态）使用了保留措辞
- AI 对缺失的信息没有假设"已具备"
- 每个关键判断都有法规引用
- 8 步的构造过程确保了输出的合规性和专业性
