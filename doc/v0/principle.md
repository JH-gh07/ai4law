## 1 核心原理：为什么 AI 能做数据跨境合规？

### 1.1 合规工作的本质

数据跨境合规工作的本质是**在"企业事实"与"法律规则"之间进行匹配**：

```
企业事实                                法律规则
──────────                            ──────────
我是不是 CIIO？                        《个保法》第40条
出境的是什么数据？                      《数安法》第21条
出境了多少人的个人信息？                《促进和规范数据跨境流动规定》
出境的目的是什么？                      《数据出境安全评估办法》
境外接收方在哪个国家？                  各省市申报指南
有没有签标准合同？                      GB/T 46068
隐私政策写了什么？                      行业数据分类分级标准
        │                                      │
        └──────────── AI 匹配 ────────────────┘
                         │
                    合规结论 + 引用依据
                    风险等级 + 整改建议
                    标准化报告文件
```

这个匹配过程具备三个特征，使其天然适合 AI：

1. **强规则性** -- 法律条文是确定的文本，合规路径的判定标准是明确的（CIIO → 必须安全评估，100万人 → 必须安全评估……），可以转化为决策树或规则引擎
2. **强推理性** -- 部分法律概念存在模糊地带（如"重要数据"的界定、"出境必要性"的判断），需要 AI 阅读行业标准、权威指南等长文本材料进行推理
3. **强结构性** -- 合规输出物（自评估报告、影响评估报告）有固定的官方模板，可以用结构化方式（JSON Schema）约束 AI 输出，再渲染为标准 docx 文件

### 1.2 系统做了什么

简单来说，系统做了三件事：

```
① 帮企业判断 "你该走哪条合规路径"   →  路径诊断（规则引擎）
② 帮企业生成 "申报需要的标准文件"   →  报告生成（LLM + RAG + 模板渲染）
③ 帮企业审查 "现有文件合不合规"     →  文档审查（LLM + 逐条比对）
```

### 1.3 与传统律师服务的对比

| 维度 | 传统律师服务 | 本系统 |
|---|---|---|
| 时间 | 数周到数月 | 数分钟生成草案 |
| 成本 | 数万到数十万 | 极低边际成本 |
| 一致性 | 依赖个人经验，质量波动 | 模板约束 + 引用链强制，输出一致 |
| 可追溯 | 依赖律师个人记录 | 每条结论自动附带法规引用 |
| 定位 | 最终法律意见 | 辅助工具，生成草案供律师/法务审核 |

## 3 模块一：合规路径诊断 -- 原理详解

### 3.1 问题：企业面对三条路径，不知道该走哪条

中国法律框架下，数据出境有三条合规路径：

| 路径 | 适用条件 | 需要做什么 |
|---|---|---|
| 路径一：数据出境安全评估 | CIIO 出境数据；重要数据出境；个人信息超100万人；敏感个人信息超1万人 | 向网信办申报安全评估，提交《数据出境风险自评估报告》 |
| 路径二：个人信息出境标准合同备案 | 非CIIO，个人信息10万~100万人，或敏感个人信息不满1万人 | 与境外接收方签订标准合同，向省级网信办备案，提交《个人信息保护影响评估报告》 |
| 路径三：个人信息出境认证 | 同路径二的适用条件 | 向认证机构申请认证 |

企业（尤其是没有专业法务团队的中小企业）往往搞不清自己应该走哪条路径。

### 3.2 解决方案：规则驱动的决策树

路径诊断模块**不使用 LLM**，而是使用确定性的决策树规则引擎。原因：

- 路径判定的规则是完全确定的（法律明文规定），不存在模糊地带
- 规则引擎响应即时（毫秒级），无需等待 LLM 推理
- 不存在幻觉风险，结论 100% 可追溯到法条

### 3.3 决策树逻辑

```
                        开始
                         │
                         ▼
                ┌────────────────┐
                │  Q1: 是否 CIIO？│
```

**关键设计**：决策树在前端用 JavaScript 状态机实现，每一步判定在本地完成，不请求后端。只有最终生成诊断报告时，才将完整问答记录发送到后端，由 LLM 生成结构化的诊断报告文本。

### 3.4 输出物

诊断完成后生成《合规路径诊断报告》(PDF/HTML)，包含：
- 用户回答摘要
- 路径判定结论及法规依据（引用到具体法条编号）
- 决策逻辑树可视化
- 核心风险提示
- 后续行动清单（"接下来你需要做什么"）

## 4 模块二/三：合规报告生成 -- 原理详解

这是系统最核心的功能，也是技术含量最高的部分。以"安全评估路径 → 生成《数据出境风险自评估报告》"为例详解。

### 4.1 整体原理

```
企业材料                  法律知识库              AI 推理引擎              标准报告
(非结构化)               (结构化)               (理解+匹配+生成)          (结构化)
───────                 ────────              ──────────────           ────────
合同文本     ──┐         法规条文     ──┐         ┌───────────┐          .docx
数据清单     ──┤ 解析     指南原文     ──┤ 检索     │  Step 1   │ 渲染     报告草案
架构说明     ──┤ 提取     行业标准     ──┤ 匹配     │  Step 2   │ 输出     ┌──────────┐
隐私政策     ──┤         案例要点     ──┤         │  Step 3   │────────>│ 自评估报告│
表单信息     ──┘         模板结构     ──┘         │  Step 4   │         │ (严格遵循 │
    │                       │                    │  Step 5   │         │  官方模板) │
    │                       │                    └───────────┘         └──────────┘
    │                       │                         │
    └───────── 输入 ────────┘──────── 上下文 ─────────┘
```

核心思路：**把非结构化的企业材料，通过 AI 理解和法规匹配，转化为严格遵循官方模板的标准化报告**。

### 4.2 五步生成流程（详解每一步在做什么）

#### Step 1: 材料理解 -- "读懂企业在做什么"

**输入**：用户填写的表单信息 + 上传的业务文件（合同、数据清单等）

**AI 做了什么**：
1. 对上传文件进行文本提取（PDF → 文本，Word → 文本）
2. 调用 LLM 从提取的文本中抽取关键信息，生成**结构化企业画像**

**输出示例**：

```json
{
  "company_name": "XX科技有限公司",
  "industry": "互联网/电子商务",
  "is_ciio": false,
  "data_exit_scenarios": [
    {
      "scenario": "用户个人信息传输至新加坡总部 CRM 系统",
      "data_types": ["姓名", "手机号", "邮箱", "订单记录"],
      "data_volume": "约50万人",
      "receiver": "XX集团新加坡总部",
      "receiver_country": "新加坡",
      "purpose": "集团统一客户关系管理",
      "legal_basis": "履行合同所必需"
    }
  ],
  "sensitive_data_involved": false,
  "important_data_involved": false
}
```

**为什么需要这一步**：后续所有步骤都依赖这个结构化画像，它是"企业事实"的标准化表达。LLM 不是直接从原始文件生成报告，而是先"理解"，再"推理"。

#### Step 2: 法规检索与匹配 -- "找到适用的法律依据"

**输入**：Step 1 输出的企业画像

**AI 做了什么**：
1. **查询改写**：将企业画像中的业务描述转化为法律检索查询。例如：
   - 业务描述："用户个人信息传输至新加坡"
   - 改写为检索查询："个人信息出境 安全评估 适用条件 50万人"+"非CIIO 个人信息出境 标准合同 10万人以上"
2. **混合检索**：同时执行两种检索
   - 向量检索（语义匹配）：捕获"意思相近"的法规条文
   - 全文检索（关键词匹配）：精确命中法条编号、专有名词
3. **结果融合与重排序**：将两种检索结果合并、去重，用 Cross-Encoder 模型精排出最相关的 Top-8 法规片段
4. **得理 API 补充**：同步调用得理开放平台 API 检索案例与法规，将结果合并入候选集
5. **来源标注**：为每个法规片段标注元数据（法规名称、条文编号、发布日期、来源URL）

**输出示例**：

```
检索到 8 个相关法规片段：

[1] 《促进和规范数据跨境流动规定》第七条
    "非CIIO...自当年1月1日起累计向境外提供100万人以上个人信息...
     应当申报数据出境安全评估"
    来源: https://www.cac.gov.cn/...  发布日期: 2024-03-22

[2] 《个人信息保护法》第三十八条
    "个人信息处理者因业务等需要，确需向中华人民共和国境外提供个人信息的，
     应当具备下列条件之一..."
    来源: 全国人大常委会  发布日期: 2021-08-20

[3] 《数据出境安全评估申报指南（第三版）》第二章
    "适用条件...累计向境外提供个人信息（不含敏感个人信息）或者
     1万人以上敏感个人信息..."
    来源: 国家网信办  发布日期: 2025-06-27

... (共 8 条)
```

**为什么需要 RAG 而不是让 LLM 直接回答**：
- LLM 的训练数据有截止日期，无法保证包含最新法规（如2025年发布的申报指南第三版）
- 法律场景要求**精确引用**到具体条文编号，LLM 直接回答容易"编造"条文（幻觉）
- RAG 确保每条结论都有真实法规片段支撑，实现可追溯

#### Step 3: 逐章节推理生成 -- "按官方模板逐章写报告"

**输入**：企业画像 + 检索到的法规片段 + 报告模板结构要求

**AI 做了什么**：

报告模板有固定的章节结构（由网信办《数据出境安全评估申报指南》规定）。系统按章节逐一生成，每个章节独立调用 LLM：

```
报告模板章节                      AI 在该章节的工作
─────────────                   ─────────────────
一、申报企业基本情况                ← 从企业画像直接填充（几乎无需推理）
二、数据出境活动说明                ← 从出境场景摘要生成描述性文字
三、出境数据情况                   ← 分析数据类型、规模、敏感程度
四、数据出境目的与必要性分析         ← 结合法规片段，论证出境的合法性基础
五、境外接收方基本情况              ← 从表单信息填充 + 补充该国数据保护水平分析
六、数据出境风险分析                ← 核心推理：逐要件匹配事实与法规，识别风险点
七、数据安全保护措施                ← 基于企业现有措施 + 法规要求，分析差距并建议
八、结论与建议                     ← 汇总风险等级、整体结论、整改行动清单
```

**每个章节的生成逻辑**：

```
                    ┌──────────────────┐
                    │ Prompt 模板       │
                    │ (Jinja2 渲染)     │
                    │                  │
                    │ 系统角色定义       │
                    │ + 章节写作要求     │
                    │ + 企业画像数据     │
                    │ + 相关法规片段     │
                    │ + 输出JSON Schema │
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │ LLM（腾讯元宝）   │
                    │                  │
                    │ temperature=0.1  │  ← 法律场景用低温度，减少随机性
                    │ 结构化输出约束     │  ← JSON Schema 强制输出格式
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │ 输出解析 + 校验    │
                    │                  │
                    │ 1. JSON 格式校验  │
                    │ 2. 引用链非空校验  │  ← 没有引用 → 降低置信度
                    │ 3. 风险分级标注   │
                    │ 4. 门控判断       │  ← 是否需要人工复核？
                    └──────────────────┘
```

**核心约束 -- 引用链强制**：

Prompt 中明确要求 LLM："你的每一条合规结论都必须引用至少一条法规条文或指南原文作为依据。如果无法找到依据，请明确说明'暂未找到直接法律依据'并标记为低置信度。"

这是本系统区别于普通"AI 法律问答"的核心差异点。

#### Step 4: 一致性校验 -- "自我检查，减少矛盾"

**输入**：Step 3 生成的全部章节的结构化 JSON

**AI 做了什么**：
1. **交叉引用一致性**：检查不同章节中引用的同一法规条文，结论是否一致
2. **结论与依据匹配度**：检查每个风险结论是否有对应的引用链支撑
3. **数据一致性**：检查不同章节中提到的数据量、数据类型等是否前后一致
4. **门控汇总**：标记所有需要人工复核的条目，生成复核清单

**输出**：校验报告 + 需人工复核的标记列表

#### Step 5: 渲染与输出 -- "把 JSON 变成 Word 文档"

**输入**：校验通过的结构化 JSON

**做了什么**（非 AI 步骤，纯工程实现）：
1. 读取官方报告 docx 模板（格式：四号仿宋/Times New Roman，行距26磅）
2. 用 python-docx 将 JSON 中的各章节内容填充到模板对应位置
3. 在引用处自动生成脚注或尾注
4. 在风险标注处自动添加批注（Word 批注功能）
5. 生成最终 docx 文件 + 可选 PDF 导出
6. 将 docx + 附件打包为 ZIP

### 4.3 认证/标准合同路径的差异

认证/标准合同路径的生成流程与安全评估路径基本相同（五步流程），差异在于：

| 差异点 | 安全评估路径 | 认证/标准合同路径 |
|---|---|---|
| 输出报告 | 《数据出境风险自评估报告》 | 《个人信息保护影响评估报告》(PIPIA) |
| 报告模板 | 遵循《数据出境安全评估申报指南》模板 | 遵循《个人信息出境标准合同备案指南》模板 |
| 重点评估内容 | 国家安全、公共利益风险 | 个人信息权益保护 |
| RAG 检索侧重 | 出境评估办法 + 重要数据标准 | 标准合同办法 + 个人信息保护认证要求 |
| Prompt 模板目录 | `prompts/assessment/` | `prompts/scc/` |

### 4.4 从"非结构化输入"到"结构化输出"的转化链

这是理解整个系统原理的关键视角：

```
Layer 1: 原始输入（非结构化）
  用户上传的合同 PDF、手工填写的表单、自由文本描述
                        │
                        ▼  文件解析 + LLM 理解
Layer 2: 结构化企业画像（JSON）
  企业基本信息、出境场景列表、数据类型与规模
                        │
                        ▼  RAG 检索 + 来源标注
Layer 3: 法规上下文（带元数据的法规片段）
  法条原文、条文编号、发布日期、来源URL
                        │
                        ▼  LLM 推理 + JSON Schema 约束
Layer 4: 结构化报告内容（JSON）
  各章节内容、引用链、风险等级、置信度、门控标记
                        │
                        ▼  模板渲染（python-docx）
Layer 5: 最终交付物（docx / PDF / ZIP）
  严格遵循官方模板格式的报告文件
```

每一层的转化都是确定性的（或有约束的），而不是让 LLM 一步到位从原始材料直接生成报告。这种分层转化设计是保证输出质量和可追溯性的关键。

## 5 模块四：通用服务 -- 原理详解

通用服务模块生成的文件不限于某一特定合规路径，而是数据跨境合规实务中常用的辅助文书。

### 5.1 TIA（Transfer Impact Assessment，跨境传输影响评估）

**做什么**：评估将数据传输到特定目的地国家/地区的风险。

**原理**：
1. 用户指定目的地国家（如新加坡、美国）
2. RAG 检索该国的数据保护法律框架、执法实践、政府访问数据的权力
3. LLM 对比中国法律要求与目的地国法律保护水平，评估"等效性"
4. 输出风险评估结论 + 建议的补充性保护措施

### 5.2 尽调报告（境外接收方尽职调查）

**做什么**：对境外数据接收方的数据保护能力进行调查评估。

**原理**：
1. 用户提供接收方的基本信息、数据保护政策等
2. RAG 检索该国/地区的法律环境
3. LLM 按照尽调清单逐项评估接收方的合规水平
4. 输出尽调报告 + 风险发现 + 建议措施

### 5.3 合规备忘录 / 风险与整改建议清单

**做什么**：基于前序模块（路径诊断、报告生成、文档审查）的结果，汇总合规差距，提出整改建议。

**原理**：
1. 整合用户在本系统中所有会话的风险发现
2. LLM 按"发现 → 依据 → 风险等级 → 整改建议 → 优先级"的结构生成清单
3. 输出可操作的整改行动计划

### 5.4 插件化框架原理："文书类型只是配置"

通用服务模块面临的核心矛盾是：文书类型多且会持续扩展（TIA、尽调、备忘录、风险清单、未来可能还有更多），但每种文书的生成管线高度相似。

解决思路是**将文书类型做成配置，而非硬编码逻辑**：

```
所有文书共享的"骨架"流程          每种文书独有的"配置"
──────────────────────          ──────────────────
1. 接收用户输入                  → 输入字段由 JSON Schema 定义
2. RAG 检索相关法规              → 检索过滤器由配置指定（法域/主题/文书类型）
3. LLM 推理生成内容              → Prompt 模板由独立文件提供
4. 风险分级 + 引用链生成          → 风险规则共用
5. 渲染为 docx 文件              → docx 模板由独立文件提供
```

这意味着新增一种文书类型时，不需要写新的后端代码或前端页面，只需要准备四样东西：
1. 一份输入/输出 JSON Schema（定义"这种文书需要收集哪些信息"和"输出什么字段"）
2. 一组 Prompt 模板（定义"LLM 在这种文书中应该怎么推理"）
3. 一份 docx 模板（定义"最终 Word 文件长什么样"）
4. 在注册表中登记（让系统知道有这种新文书）

这个设计的核心原理借鉴了 PAR-DPIA Form 项目的声明式配置思想：**把业务逻辑的变化部分提取为数据（Schema/模板），把稳定的技术流程固化为代码**。

## 6 模块五：文档智能审查 -- 原理详解

### 6.1 审查什么

用户上传现有的法律文件，系统逐条审查其合规性：

- 《数据出境标准合同》-- 是否包含法定必备条款？
- 《隐私政策》-- 是否充分告知了数据出境事项？
- 《数据处理协议》-- 是否明确了境外接收方的义务？
- 《云服务协议》-- 数据存储地点和安全措施是否合规？

### 6.2 审查原理

审查流程分为四步（而非将整份文件一次性送入 LLM），核心原因是：法律文件通常较长（数十页），LLM 上下文窗口有限且注意力分散，逐条处理能保证每个条款都被认真审查。

```
上传文档
    │
    ▼
┌──────────────────────────────────────────┐
│ Step A: 条款切分 (ClauseSegmenter)         │
│                                          │
│  按标题层级、编号模式、段落结构切分          │
│  → 每个条款成为独立审查单元                 │
│  → 保留原文定位信息（页码/段号/条款号）      │
└────────────────┬─────────────────────────┘
                 │
                 ▼
┌──────────────────────────────────────────┐
│ Step B: 条款分类 (ClauseClassifier)        │
│                                          │
│  识别每个条款的类型，以便匹配正确的审查策略：  │
│  - 数据处理条款（处理目的、范围、方式）       │
│  - 同意与告知条款（单独同意、告知内容）       │
│  - 安全措施条款（技术/管理保护措施）          │
│  - 数据出境条款（传输目的地、接收方义务）      │
│  - 权利行使条款（个人权利保障、投诉渠道）     │
│  - 违约责任条款（数据泄露、赔偿）            │
│  - 其他（与数据合规无直接关联的条款）         │
└────────────────┬─────────────────────────┘
                 │
                 ▼
┌──────────────────────────────────────────┐
│ Step C: 逐条审查 (ClauseReviewer)          │
│                                          │
│  对每个条款独立执行：                       │
│                                          │
│  条款原文 + 条款类型                        │
│       │                                  │
│       ▼                                  │
│  RAG 检索"该类条款应包含什么"               │
│  （按条款类型路由检索策略）                  │
│       │                                  │
│       ▼                                  │
│  LLM 逐维度比对分析                        │
│       │                                  │
│       ▼                                  │
│  输出结构化 ReviewIssue 对象：              │
│  - 条款定位（文件/章节/页码/条款号）         │
│  - 原文摘录                               │
│  - 问题类型（缺失/模糊/冲突/限制过度/...）   │
│  - 风险等级 + 风险分析                      │
│  - 法规依据（引用链）                       │
│  - 具体修改建议文本                         │
└────────────────┬─────────────────────────┘
                 │
                 ▼
┌──────────────────────────────────────────┐
│ Step D: 汇总报告 (ReviewAggregator)        │
│                                          │
│  1. 合并所有条款的 ReviewIssue              │
│  2. 按风险等级排序（HIGH → MEDIUM → LOW）   │
│  3. 计算总体合规评级                        │
│  4. 生成优先整改建议（按影响程度排序）        │
│  5. 汇总引用的法规清单                      │
│  6. 渲染为 docx 审查报告                    │
└──────────────────────────────────────────┘
```

**为什么需要"条款分类"这一步**：不同类型的条款需要对照不同的法规要求审查。比如"同意条款"需要对照《个保法》第39条检查告知是否充分，而"安全措施条款"需要对照《个保法》第38条检查保护措施是否到位。分类后可以为每类条款精准匹配检索策略和审查 Prompt，避免"一个大 Prompt 审所有条款"导致的遗漏。

### 6.3 审查维度（以隐私政策为例）

LLM 在审查时逐项检查的合规要点：

| 审查维度 | 检查内容 | 法律依据 |
|---|---|---|
| 告知充分性 | 是否告知了境外接收方名称、联系方式、处理目的、处理方式？ | 《个保法》第39条 |
| 单独同意 | 是否设置了数据出境的单独同意机制？ | 《个保法》第39条 |
| 数据出境说明 | 是否说明了出境的数据种类和范围？ | 《个保法》第39条 |
| 权利行使途径 | 是否告知了个人向境外接收方行使权利的方式和程序？ | 《个保法》第39条 |
| 合法性基础 | 处理个人信息的合法性基础是否充分（同意/合同必需/法定义务）？ | 《个保法》第13条 |
| 安全措施 | 是否说明了保障出境数据安全的技术和管理措施？ | 《个保法》第38条 |

## 7 RAG（检索增强生成）原理详解

RAG 是整个系统的技术核心，贯穿报告生成和文档审查两大模块。

### 7.1 为什么需要 RAG

```
纯 LLM 方案的问题                     RAG 方案的解决
─────────────────                    ───────────────
法规可能过时（训练数据截止日期）      → 实时检索最新入库的法规
条文编号可能"编造"（幻觉）           → 从知识库精确命中真实条文
无法引用到具体来源                   → 每个片段附带元数据（法规名/条号/URL）
无法覆盖地方性文件                   → 知识库收录各省市指引
答案不可审计                        → 检索结果可回溯、可验证
不同问题需要不同检索策略              → 查询类型路由，按场景优化检索
```

### 7.2 知识库是怎么建的

法规原文入库的标准化管线：

```
原始法规文档（PDF/Word/HTML）
         │
         ▼
┌────────────────────────────────────────────────┐
│  1. 格式归一化                                   │
│     PDF → 文本提取（PyMuPDF）                    │
│     Word → 文本提取（python-docx）               │
│     HTML → 文本提取（BeautifulSoup）             │
└────────────────────┬───────────────────────────┘
                     ▼
┌────────────────────────────────────────────────┐
│  2. 结构化切分                                   │
│     按法规的层级结构切分：                         │
│     法规 → 编/章/节 → 条 → 款 → 项               │
│                                                │
│     例：《个保法》第38条第1款第3项                 │
│     → 独立片段，保留层级路径                      │
└────────────────────┬───────────────────────────┘
                     ▼
┌────────────────────────────────────────────────┐
│  3. 元数据标注                                   │
│     每个片段附加：                                │
│     - 法规全称、简称                             │
│     - 发布机关                                   │
│     - 发布日期、生效日期                          │
│     - 条文编号（结构化：chapter/article/clause）  │
│     - 来源 URL                                   │
│     - 可靠度评级（官方 > 律所 > 研报 > 其他）      │
└────────────────────┬───────────────────────────┘
                     ▼
┌────────────────────────────────────────────────┐
│  4. 双重索引                                     │
│     ┌──────────────┐    ┌───────────────────┐  │
│     │ 向量索引      │    │ 全文索引           │  │
│     │ (Milvus)     │    │ (Elasticsearch)   │  │
│     │              │    │                   │  │
│     │ 文本→Embedding│    │ 文本→倒排索引      │  │
│     │ 支持语义检索  │    │ 支持精确检索       │  │
│     └──────────────┘    └───────────────────┘  │
└────────────────────────────────────────────────┘
```

### 7.3 条文级检索 vs chunk 级检索

传统 RAG 系统通常按固定 token 长度（如500或1000 token）切分文档，但法律文本有其特殊性：

```
传统 chunk 方式的问题                   条文级检索的解决
──────────────────                    ────────────────
固定长度切分可能将一个条文一分为二   → 每个条文（条/款/项）作为完整语义单元
检索结果是"第 N 段"，无法律意义     → 检索结果是"《个保法》第38条第1款"
无法精确引用到具体法条编号          → 直接引用到条文对象，精确到款项
无法表达条文之间的引用关系          → 支持交叉引用图谱（"依照本法第X条"）
无法按法域/主题/时效过滤           → 每个条文附带丰富元数据标签
```

所以本系统的知识库不是"一堆文本块"，而是**一组结构化的法条对象**（`RegulationArticle`），每个对象保留完整的层级路径、元数据和交叉引用关系。详见 [architecture.md](architecture.md) Section 7.4。

### 7.4 查询类型路由：不同问题用不同检索策略

系统面对的检索需求来自不同模块，问题性质差异很大。一个"路径判断"问题需要精确命中数量门槛条款，而一个"报告生成"问题需要语义匹配相关法规。用同一套检索参数处理所有问题，必然导致部分场景效果差。

```
查询类型路由原理：

用户查询
    │
    ▼
┌─────────────────────┐
│  识别查询类型         │
│                     │
│  来自路径诊断？       │ ──→ 路径判断类策略（全文检索为主）
│  来自报告生成？       │ ──→ 报告生成类策略（向量+全文均衡）
│  来自条款审查？       │ ──→ 条款审查类策略（向量检索为主）
│  来自通用服务？       │ ──→ 整改建议类策略（扩大范围+案例）
└─────────────────────┘
```

各类型的策略差异：

| 查询类型 | 向量检索权重 | 全文检索权重 | Top-K | 过滤标签 | 原因 |
|---|---|---|---|---|---|
| 路径判断 | 低 | 高 | 较少 | 法域+出境条件 | 需精确命中"100万人""CIIO"等数量门槛条款 |
| 报告生成 | 均衡 | 均衡 | 中等 | 法域+路径+章节 | 需同时匹配语义相关和精确引用 |
| 条款审查 | 高 | 低 | 较多 | 文书类型 | 条款语义匹配为主，需找到"类似条款应包含什么" |
| 整改建议 | 均衡 | 均衡 | 较多 | 范围更广 | 需涵盖法规+案例+行业标准+最佳实践 |

### 7.5 检索全流程示例

```
用户查询："该企业向新加坡传输50万用户的个人信息，需要做安全评估吗？"
                    │
                    ▼
          ┌──────────────────┐
          │ 查询类型路由       │  识别为"路径判断类" → 全文检索权重调高
          └───────┬──────────┘
                  │
                  ▼
          ┌──────────────────┐
          │ 查询改写 (LLM)    │
          │                  │
          │ 改写为：          │
          │ Q1: "非CIIO 个人  │
          │ 信息出境 50万人   │
          │ 安全评估 适用条件" │
          │                  │
          │ Q2: "个人信息出境 │
          │ 标准合同 10万人   │
          │ 备案条件"        │
          └───────┬──────────┘
                  │
                  │  元数据过滤：法域=CN, 主题=出境条件
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
 ┌──────────────┐   ┌──────────────┐
 │ 向量检索      │   │ 全文检索      │
 │ (语义匹配)    │   │ (关键词匹配)  │
 │ Top-20       │   │ Top-20       │
 └──────┬───────┘   └──────┬───────┘
        │                   │
        └─────────┬─────────┘
                  ▼
        ┌──────────────────┐
        │ RRF 融合          │  将两路结果按倒数排名融合
        │ 去重 + 合并排序    │
        └────────┬─────────┘
                 ▼
        ┌──────────────────┐
        │ Cross-Encoder    │  用更精准的模型重新打分
        │ 重排序 Top-8      │  选出最相关的 8 个条文对象
        └────────┬─────────┘
                 ▼
        ┌──────────────────┐
        │ 上下文组装        │  对每个条文对象：
        │                  │  - 沿层级路径回溯父级条文（保证上下文）
        │                  │  - 加载交叉引用的关联条文
        │                  │  - 附加元数据（法规名/条号/日期/URL）
        └────────┬─────────┘
                 ▼
        ┌──────────────────┐
        │ 得理 API 补充     │  同步调用得理检索
        │ 结果合并          │  去重合并入候选集
        └────────┬─────────┘
                 ▼
        ┌──────────────────┐
        │ 检索审计日志       │  完整记录本次检索过程
        │                  │  （查询/改写/过滤/各阶段结果/最终输出）
        │                  │  支持事后审计和检索质量分析
        └────────┬─────────┘
                 ▼
          最终法规上下文
          (8~12 个带元数据的条文对象)
          → 送入 LLM 作为推理依据
```

### 7.6 可审计检索

法律场景中，"AI 为什么引用了这条法规"不是可选信息，而是核心要求。系统的每一次检索都完整记录以下信息：

- 原始查询文本和改写后的查询
- 使用的元数据过滤条件
- 向量检索的候选结果及分数
- 全文检索的候选结果及分数
- RRF 融合后的排序
- 重排序后的最终选择
- 得理 API 的补充结果

这些记录支持三个用途：
1. **审计**：律师可以查看"系统为什么引用了这条法规而没引用那条"
2. **调优**：开发团队可以分析检索失败的 case，优化检索参数
3. **评测**：Golden Set 的 L1（检索层）指标计算依赖这些记录

## 8 引用链与风险分级 -- 原理详解

### 8.1 引用链：确保"言之有据"

系统的核心承诺是：**每一条合规结论都能追溯到法规原文**。

实现方式：在 LLM 的 Prompt 和输出 JSON Schema 中强制要求 `citations` 字段。LLM 必须从 RAG 检索到的法规片段中选择依据，而不能自行"编造"法条。

```
                    LLM 推理
                       │
                ┌──────┴──────┐
                │ 结论 + 引用链  │
                └──────┬──────┘
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
    ┌───────────┐ ┌───────────┐ ┌───────────┐
    │ 引用 1     │ │ 引用 2     │ │ 引用 3     │
    │           │ │           │ │           │
    │ 法规名称  │ │ 法规名称  │ │ 法规名称  │
    │ 条文编号  │ │ 条文编号  │ │ 条文编号  │
    │ 原文摘录  │ │ 原文摘录  │ │ 原文摘录  │
    │ 发布日期  │ │ 发布日期  │ │ 发布日期  │
    │ 来源 URL  │ │ 来源 URL  │ │ 来源 URL  │
    └───────────┘ └───────────┘ └───────────┘
         │              │             │
         └──────────────┴─────────────┘
                        │
                  可回溯验证
            （点击引用可查看法规原文）
```

### 8.2 风险分级：让用户一眼看到重点

| 等级 | 含义 | 触发条件 | 在报告中的呈现 |
|---|---|---|---|
| HIGH | 存在明确的合规违反或重大风险 | 违反现行法规、缺失必要步骤、涉及重要数据/敏感信息 | 红色高亮 + "需人工复核" |
| MEDIUM | 存在不确定性或灰色地带 | 法规适用不明确、企业信息不完整、行业标准尚未出台 | 黄色标注 + "建议补充信息" |
| LOW | 基本合规，有优化空间 | 已满足法定要求、仅有最佳实践层面的建议 | 绿色标记 + 优化建议 |

### 8.3 门控机制：什么时候必须提醒人工介入

```
AI 生成结论
     │
     ▼
┌──────────────────────────────┐
│          门控检查              │
│                              │
│  引用链为空？        ──── 是 ──→ 标记"需人工复核"
│  置信度 < 0.7？      ──── 是 ──→ 标记"需人工复核"
│  涉及"重要数据"认定？ ──── 是 ──→ 标记"需人工复核"
│  涉及"出境必要性"？  ──── 是 ──→ 标记"需人工复核"
│  多条法规结论冲突？   ──── 是 ──→ 标记"需人工复核"
│                              │
│  以上均否 ─────────────────────→ 正常输出
└──────────────────────────────┘
```

这个门控机制的设计原则是：**AI 不确定的时候，必须明确说"我不确定"，而不是硬给一个答案**。这在法律场景中至关重要。

## 9 结构化中间态：为什么不让 AI 直接生成最终文档

### 9.1 核心原理

系统的一个关键设计决策是：**LLM 的输出永远先落地为结构化 JSON 对象，再由独立的渲染模块转化为最终 docx/PDF 文件**。LLM 绝不直接生成最终文档。

```
                  不采用的方案                    采用的方案
                  ──────────                    ──────────
企业材料 + 法规 → LLM 直接生成 Word 文本     企业材料 + 法规 → LLM 生成 JSON 对象
                      │                                          │
                      ▼                                          ▼
              最终 docx 文件                           JSON Schema 校验
              (格式不可控、                                    │
               内容难测试、                              校验通过？
               错误难定位)                              ├── 是 → 模板渲染 → 最终 docx
                                                       └── 否 → 重试/降级/标记
```

### 9.2 为什么要这么做

**理由一：格式与内容分离**

官方报告模板有严格的格式要求（四号仿宋、行距26磅、特定页边距）。让 LLM 同时关注"写什么内容"和"怎么排版"，会导致两方面都做不好。分离后，LLM 专注生成内容（JSON），python-docx 专注处理格式（docx 模板填充），各司其职。

**理由二：可测试性**

JSON 对象可以用 JSON Schema 自动校验，比如：
- 每个章节是否都有 `citations` 字段且非空？
- `risk_level` 是否为 HIGH/MEDIUM/LOW 之一？
- `confidence` 是否在 0~1 之间？

这些校验在 LLM 输出阶段就能执行，无需等到 docx 生成后再人工检查。

**理由三：断点恢复**

报告生成涉及多章节、多轮 LLM 调用。如果第6章生成失败，系统可以从前5章的 JSON 中间态恢复，只重新生成第6章，而不是从头开始。

**理由四：人工修正**

律师如果对某个章节的 AI 生成结论不满意，可以修改对应的 JSON 中间态，然后重新渲染 docx。不需要直接编辑 Word 文件再"喂回"系统。

**理由五：评测支撑**

中间态 JSON 可以直接与 Golden Set 的标注答案做自动化比对，计算引用正确率、字段准确率等指标。如果只有最终 docx 文件，自动化评测几乎不可能。

### 9.3 六种核心中间态对象

系统定义了六种标准化的 JSON 中间态对象，贯穿所有模块：

| 中间态对象 | 产生环节 | 用途 |
|---|---|---|
| `CompanyProfile` | Step 1 材料理解 | 企业画像：公司信息、出境场景列表、数据类型与规模 |
| `RegulationHit` | Step 2 法规检索 | 法规命中记录：条文原文、编号、来源、相关性得分 |
| `ChapterContent` | Step 3 章节生成 | 报告章节：正文、引用链、风险发现、置信度 |
| `RiskFinding` | Step 3/4 风险分析 | 风险发现：描述、等级、依据、是否需人工复核 |
| `ReviewIssue` | 文档审查 | 审查意见：条款定位、问题类型、修改建议 |
| `DiagnosisResult` | 路径诊断 | 诊断结果：路径判定、法规依据、行动建议 |

所有中间态对象均由 JSON Schema 严格约束。LLM 输出如不符合 Schema，系统会在 Prompt 中追加格式修正指令后重试，最多3次；仍然失败则降级为纯文本输出并标记"需人工复核"。

## 10 评测与质量保证 -- 原理详解

### 10.1 为什么需要系统化评测

法律 AI 系统不能只靠"演示看起来不错"来判断质量。原因：

1. **法律后果严重**：一条错误的合规建议可能导致企业受到行政处罚
2. **幻觉难以察觉**：LLM 编造的法条往往"看起来像真的"，非专业人员很难发现
3. **改一处可能坏一片**：修改一个 Prompt 模板可能影响所有报告的引用质量
4. **比赛答辩需要证据**：评审方不会只看一个 demo，会问"你怎么知道引用是对的"

### 10.2 三层评测框架

系统将评测拆分为三个独立层次，分别度量不同环节的质量：

```
┌──────────────────────────────────────────────────────────────┐
│  L1: 检索层                                                    │
│  评测问题：法规找对了吗？有没有漏掉关键条文？                      │
│  评测方式：自动化（比对检索结果与标注答案）                        │
│  核心指标：Precision@K, Recall@K, 条文精确匹配率                 │
├──────────────────────────────────────────────────────────────┤
│  L2: 抽取层                                                    │
│  评测问题：企业画像抽取准确吗？CIIO判定、数据分类对了吗？           │
│  评测方式：自动化（比对JSON字段与标注答案）                        │
│  核心指标：字段准确率, CIIO判定准确率, 数据分类F1值                │
├──────────────────────────────────────────────────────────────┤
│  L3: 生成层                                                    │
│  评测问题：报告完整吗？引用对吗？风险判断准确吗？律师能用吗？        │
│  评测方式：自动化 + 人工评审                                     │
│  核心指标：章节完整性, 引用正确率, 风险一致性, 律师可编辑性          │
└──────────────────────────────────────────────────────────────┘
```

**为什么要分层而非端到端评测**：

如果只看最终报告质量（端到端），当质量下降时无法定位问题出在哪个环节。分层后：
- L1 下降 → 检索参数或知识库有问题
- L2 下降 → 材料理解的 Prompt 或文件解析有问题
- L3 下降但 L1/L2 正常 → 报告生成的 Prompt 或一致性校验有问题

这种分层诊断能力在快速迭代中至关重要。

### 10.3 Golden Set 与回归测试

评测依赖一组人工标注的测试用例（Golden Set），由法学团队准备：

- **路径诊断用例**：给定企业场景，标注正确的路径判定
- **安全评估用例**：给定企业材料，标注正确的企业画像、应检索的法规、报告关键结论
- **文档审查用例**：给定法律文件，标注每个条款的合规问题

每次修改 Prompt、调整 RAG 参数或更新知识库后，系统用 Golden Set 重新跑一遍全流程，自动计算三层指标并与上一次基线对比。如果任何指标显著下降，阻断上线并排查。

这种回归测试机制确保系统"越改越好"而不是"改出新问题"。

## 11 端到端流程示例

以一个完整用例串联全部原理：

**场景**：XX电商公司，非 CIIO，将约50万用户个人信息传输至新加坡总部的 CRM 系统。

```
1. 用户进入首页
   → 选择"从中国大陆向境外传输数据"

2. 路径诊断
   → Q1: 不是 CIIO
   → Q2: 不含重要数据
   → Q3: 50万人（10万~100万之间）
   → Q4: 无敏感个人信息
   → 结论：建议走"标准合同备案"或"认证"路径
   → 生成《合规路径诊断报告》

3. 用户选择"认证/标准合同路径"
   → 系统自动预填诊断阶段收集到的信息

4. 用户补充填写表单
   → 公司信息、境外接收方信息（新加坡总部）
   → 上传：现有数据处理协议、CRM 系统架构说明

5. 系统开始生成 PIPIA 报告
   → Step 1: 解析上传文件，生成企业画像
   → Step 2: RAG 检索出《个保法》第38/39条、《标准合同办法》、
             《备案指南（第二版）》、新加坡 PDPA 相关条文
   → Step 3: 逐章节生成报告内容（每章引用2~4条法规）
   → Step 4: 校验引用一致性，标记1个 MEDIUM 风险点
             （"CRM 系统是否涉及间接收集供应商员工信息，需确认"）
   → Step 5: 渲染为 docx

6. 用户预览报告
   → 在线查看各章节，点击引用气泡查看法规原文
   → 看到 MEDIUM 风险标注："建议确认 CRM 是否涉及间接收集"
   → 下载 docx 文件 + ZIP 整包

7. 用户将报告草案交给律师审核
   → 律师基于草案做最终调整
   → 正式提交备案
```

