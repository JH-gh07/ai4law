## 一、问题定义

### 1.1 核心矛盾

合规系统的报告有两类读者，两种截然不同的需求：

```text
对内（内部审查）：
  "真实风险是什么？证据够不够？要不要建议暂缓？"
  → 可以直说、可以推测、可以说"估计会出问题"

对外（申报草案 / 客户交付）：
  "在现有材料下，能得出什么结论？还缺什么？下一步怎么办？"
  → 不能直说"违法"、不能说"肯定没事"、不能把推测写成确认
```

### 1.2 这个规范管什么

```text
本规范管辖：
  ✅ 外部报告（docx/md/pdf）中的每一句中文表达
  ✅ 批注版 DOCX 中面向用户的批注文字
  ✅ 材料补充清单中的说明文字
  ✅ 内部审查报告中的表达（可以更直接，但仍受部分约束）

本规范不管：
  ❌ 系统内部日志和 Trace
  ❌ 开发者调试信息
  ❌ 后端 JSON 中间产物
```

### 1.3 与平台数据流图的关系

本规范是数据流图中 **阶段 ⑧ (WritingPlan) 和阶段 ⑩ (QA/Alignment)** 的具体执行标准。每个 `ExpressionStrategy` 和 `ForbiddenExpressionRule` 的实例化都必须依据本规范。

## 二、证据门槛 → 表达强度映射

### 2.1 核心映射表

这是本规范最重要的规则表。报告中的**每一句正面断言**必须跨过对应的证据门槛：

```
证据成熟度                    外部报告可用的表达强度
─────────────────────────────────────────────────────────────
verified_evidence              ✅ 可以使用 affirmative（肯定式）
（经第三方审计或官方认证）         "经XX认证机构审计，……"

documented_evidence            ✅ 可以使用 affirmative（肯定式）
（有上传文档/合同/政策支撑）       "根据上传的《数据保护协议》第X条，……"

partial_evidence               ⚠️ 只能使用 cautious（审慎式）
（有部分证据但不完整）            "用户已提供部分……但仍需补充……"

user_claim_only                ⚠️ 只能使用 conditional / deferred
（仅用户声称，无任何证据）         "用户说明……尚无法独立验证……"
                                 "在现有材料条件下，建议……"

NO evidence / missing material 只能使用 deferred（待补充式）
（材料缺失）                      "当前尚未提供……建议补充……"
```

### 2.2 反面：不同证据门槛下的禁止表达

```
证据状态               禁止的表达（即使在上下文中看起来"合理"）
─────────────────────────────────────────────────────────────
user_claim_only        ❌ "已建立完善的……体系"
                       ❌ "具备充分的……能力"
                       ❌ "完全满足……要求"
                       ❌ "已经落实……措施"

partial_evidence        ❌ "已充分证明……"
                       ❌ "不存在……风险"
                       ❌ "确保不会……"

即使 documented          ❌ "完全合规"
                        ❌ "不存在任何风险"
                        ❌ "无需进一步改进"
```

### 2.3 复合断言的证据门槛

当一句话包含多个断言时，取最弱的证据状态：

```
"企业已建立数据安全管理制度（user_claim_only），并通过ISO 27001认证（verified_evidence）。"
→ 前半句不能用 affirmative，必须改写。
→ 正确写法：
  "企业已通过ISO 27001认证。用户另说明已建立数据安全管理制度，建议补充制度文件。"
```

## 三、四级表达风格卡片

### 3.1 affirmative（肯定式）

```text
适用条件：
  - 所有依赖的 FactItem.evidence_status ≥ documented_evidence
  - 结论不涉及 forbidden_expressions 中的任何表达

典型句式：
  "根据上传的《XX协议》第X条，YY义务已被覆盖。"
  "经XX机构认证（证书号：XXX），YY系统符合ZZ标准。"
  "合同明确约定了AA的BB义务，包括CC和DD。"

禁止搭配：
  "完全" "充分" "完善" "确保" "不存在任何"
  （这些修饰词即使在 documented_evidence 下也禁止，参见第四章）

示例：
  ✅ "根据《数据处理协议》第5.2条，乙方应在服务终止后30日内删除或返还全部个人数据。"
  ✅ "该协议第7条覆盖了安全事件通知义务，约定通知时限为48小时。"
  ❌ "该协议已充分覆盖全部安全义务。"  （"充分""全部"→ 过度承诺）
```

### 3.2 cautious（审慎式）

```text
适用条件：
  - 至少有一条依赖的 FactItem.evidence_status = partial_evidence
  - 或 Agent 推断（confidence 0.65-0.85）

典型句式：
  "用户已说明……但仍需补充……以进一步佐证。"
  "在现有材料基础上，……但建议在正式申报前完善……"
  "当前材料显示……尚无法充分确认……"

示例：
  ✅ "用户已提供同意记录截图样本，说明已取得50万目标用户的单独同意。但当前样本仅覆盖部分用户，建议补充完整的批量同意记录清单或统计报告。"
  ✅ "隐私政策第3条描述了跨境传输场景，但未明确境外接收方的具体名称和联系方式，建议补充。"
  ❌ "企业已取得全部用户同意。"  （仅有截图样本 → user_claim_only 事实被写成确认句）
```

### 3.3 conditional（条件式）

```text
适用条件：
  - 核心依赖的 FactItem.evidence_status = user_claim_only
  - 或 Agent 推断（confidence < 0.85）
  - 或结论依赖于一个尚未确认的前提

典型句式：
  "若用户提供的……信息属实，则……"
  "基于当前信息假设……如果该前提不成立，结论可能需要调整。"
  "在……得以确认的前提下，可以认为……"

示例：
  ✅ "若用户确认乙方服务器全部位于境内、不存在境外远程访问，则本次数据处理不构成数据出境。建议取得并留存乙方服务器部署位置证明。"
  ✅ "基于当前信息假设乙方符合跨境人力资源管理豁免条件，但该结论依赖员工手册和集体合同中数据出境条款的完备性。"
  ❌ "本次数据处理不构成数据出境。"  （依赖未确认的前提 → 写成了确定结论）
```

### 3.4 deferred（待补充式）

```text
适用条件：
  - 材料缺失（missing_material）
  - 或所有依赖的 FactItem.evidence_status ≤ user_claim_only
  - 或 issue_certainty = default_review_item

典型句式：
  "当前尚未提供……建议在正式申报前补充……"
  "由于缺少……相关材料，本节内容暂无法完整评估。"
  "建议补充……后再行复核本节内容。"

示例：
  ✅ "当前尚未提供境外接收方的安全认证或审计报告，建议在正式申报前补充以支撑接收方安全保障能力论证。"
  ✅ "由于未提供与境外接收方的法律文件，本节暂无法评估合同条款的完整性和合规性。建议上传相关协议后重新生成本报告。"
  ❌ "境外接收方安全保障能力待确认。"  （太模糊 → 应具体说明缺什么材料）
```

## 四、完整禁止表达目录

### 4.1 违法定性类（共 5 条）

任何情况下，外部报告中不得出现以下表达或其近义词：

| 规则 ID | 禁止表达 | 替代表达 | 严重度 |
|---------|---------|---------|:---:|
| `CN-FORBIDDEN-001` | 违反、触犯 | 与……存在不一致 | BLOCKER |
| `CN-FORBIDDEN-002` | 违法、不合法的 | 可能不符合……相关要求 | BLOCKER |
| `CN-FORBIDDEN-003` | 违规行为、不合规 | 需要进一步满足……规定 | BLOCKER |
| `CN-FORBIDDEN-004` | 已经构成（违法/违规） | 可能存在……风险 | BLOCKER |
| `CN-FORBIDDEN-005` | 违法/违规 风险极高 | 在……方面存在需要关注的法律风险 | BLOCKER |

**原因**：不具法律执业资格的系统不能作出违法定性。这是法律意见的边界。

### 4.2 过度承诺类（共 7 条）

| 规则 ID | 禁止表达 | 替代表达 | 严重度 |
|---------|---------|---------|:---:|
| `CN-FORBIDDEN-006` | 完全合规 | 在现有材料条件下，基本满足……要求（但……方面仍需补充） | BLOCKER |
| `CN-FORBIDDEN-007` | 已充分证明 | 用户已提供……（材料名称） | BLOCKER |
| `CN-FORBIDDEN-008` | 材料齐备、材料完整齐备 | 已收到……等材料（仍需补充……） | BLOCKER |
| `CN-FORBIDDEN-009` | 确保不会、杜绝 | 有助于降低……风险 | HIGH |
| `CN-FORBIDDEN-010` | 不存在任何风险 | 在当前材料范围内，未发现额外风险点（但材料缺失可能隐藏风险） | BLOCKER |
| `CN-FORBIDDEN-011` | 无风险、无合规风险 | 当前评估范围内暂未发现高风险项 | HIGH |
| `CN-FORBIDDEN-012` | 必然合法、确定合规 | 从现有材料看，该安排具备一定合规基础 | HIGH |

### 4.3 事实外推类（共 6 条）

当证据仅来自用户声称时，以下表达禁止：

| 规则 ID | 禁止表达（在仅 user_claim_only 时） | 替代表达 | 严重度 |
|---------|---------|---------|:---:|
| `CN-FORBIDDEN-013` | 企业已建立完善的（制度/体系） | 用户说明已建立……（建议补充制度文件） | BLOCKER |
| `CN-FORBIDDEN-014` | 数据已经完全匿名化 | 用户主张数据已经过匿名化处理（建议补充技术验证材料） | BLOCKER |
| `CN-FORBIDDEN-015` | 具备充分的安全保障能力 | 用户已说明具备一定安全保障能力（建议补充认证/审计材料） | BLOCKER |
| `CN-FORBIDDEN-016` | 已取得全部用户的（同意/授权） | 用户提供了部分同意记录（完整性尚需核验） | HIGH |
| `CN-FORBIDDEN-017` | 不存在数据出境 | 协议中未明确提及数据出境（建议结合服务器部署情况进一步确认） | HIGH |
| `CN-FORBIDDEN-018` | 接收方完全符合（标准/要求） | 用户已说明接收方遵循相关标准（建议补充具体认证信息） | HIGH |

### 4.4 系统越权类（共 4 条）

| 规则 ID | 禁止表达 | 替代表达 | 严重度 |
|---------|---------|---------|:---:|
| `CN-FORBIDDEN-019` | 企业应立刻停止 | 建议审慎评估是否继续该处理行为 | BLOCKER |
| `CN-FORBIDDEN-020` | 必须（做某事）、务必 | 建议、推荐 | BLOCKER |
| `CN-FORBIDDEN-021` | 不得（做某事）、严禁 | 建议避免、慎重考虑 | HIGH |
| `CN-FORBIDDEN-022` | 否则将面临（处罚/法律后果） | 可能引发……方面的合规风险 | HIGH |

### 4.5 状态错配类（共 5 条）

| 规则 ID | 禁止表达（在未实施时） | 替代表达 | 严重度 |
|---------|---------|---------|:---:|
| `CN-FORBIDDEN-023` | 已完成（当实际为 planned 时） | 计划采取、建议落实 | BLOCKER |
| `CN-FORBIDDEN-024` | 已落实（当实际为 planned 时） | 拟于XX阶段实施 | BLOCKER |
| `CN-FORBIDDEN-025` | 已上线（当实际未上线时） | 规划中、开发中 | HIGH |
| `CN-FORBIDDEN-026` | 已完成全部整改 | 已完成……方面的整改（仍有……待完成） | HIGH |
| `CN-FORBIDDEN-027` | 已备案 / 已通过 | 用户说明已完成……（建议核实备案状态） | HIGH |

## 五、Issue 确定性 → 报告句式映射

### 5.1 三类 Issue 的不同表达策略

```
confirmed_issue
  → 外部报告：直接陈述问题和影响
  → 句式："经审查，[定位]处的条款/安排 [问题描述]。这可能导致[风险后果]。"
  → 示例："经审查，附录二第4条约定了'以集团主协议为准'的优先适用条款，
           这可能导致标准合同正文的个人信息保护义务被架空。"

suspected_issue
  → 外部报告：陈述系统发现的信号，但明确标注不确定性
  → 句式："系统初步识别到[位置]可能存在[问题类型]。由于[材料/信息缺失]，
           尚无法最终确认。建议补充[具体材料]后进一步核查。"
  → 示例："系统初步识别到乙方数据处理地点可能涉及新加坡服务器。
           由于协议未明确约定处理地理位置，尚无法最终确认是否构成数据出境。
           建议补充乙方服务器部署位置证明。"

default_review_item
  → 外部报告：作为建议项提出，不陈述为"问题"
  → 句式："根据[法规/模板]要求，建议在正式申报前核验[事项]。"
  → 示例："根据《数据出境安全评估办法》第九条，建议核验与境外接收方的
           法律文件是否覆盖目的方式范围、保存期限、再转移约束、法律环境变化应对、
           违约责任和应急处置六项核心条款。"
```

### 5.2 三种 certainty 在报告章节中的排布规则

```
执行摘要：
  - confirmed_issue (HIGH/BLOCKER) → 必须出现
  - suspected_issue (HIGH) → 必须出现，以"需进一步确认"语气
  - default_review_item → 不出现在摘要中

逐条问题（报告正文）：
  - confirmed_issue → 以"问题 N：……"编号列出
  - suspected_issue → 以"待确认事项 N：……"编号列出
  - default_review_item → 以"建议核验项 N：……"编号列出

整改路线图 / 行动建议：
  - confirmed_issue → P0/P1 优先级
  - suspected_issue → P1 优先级（标注"需先确认是否存在"）
  - default_review_item → P2 优先级
```

## 六、分场景表达模板库

### 6.1 缺失材料场景

```text
模板 1 — 完全缺失关键文件：
  "当前尚未提供[文件名称]。该文件是[法规/模板名称]第[X]条/项要求的必备材料，
   用于支撑[报告章节/判断事项]。建议尽快补充，补充后可重新生成本节内容。"

模板 2 — 有关键文件但缺辅助材料：
  "已收到[已有文件名]，但尚需补充[缺失材料名]才能充分证明[事项]。"

模板 3 — 材料存在但质量不足：
  "用户已上传[文件名]，但其内容为[摘要/截图/片段]，尚未覆盖[具体缺口]。
   建议补充完整版本或[具体条款/章节]。"
```

### 6.2 合同条款缺失/不足场景

```text
模板 4 — 完全缺失某类条款：
  "经审查，[文件名]中未检索到关于[条款事项]的约定。
   根据[法规依据]，该事项为必备条款。建议新增相关约定。"

模板 5 — 条款存在但表述过泛：
  "[文件名]第[X]条提到了[条款事项]，但表述为'[原文摘录]'。
   该表述过于概括，未达到[法规/指南]要求的具体性和可执行性。
   建议细化为[建议的具体内容]。"

模板 6 — 条款与法规冲突：
  "[文件名]第[X]条约定'[冲突原文]'。
   该约定与[法规名称]第[Y]条的要求存在不一致。
   建议修改为：[建议文本]。"
```

### 6.3 用户声称但无证据场景

```text
模板 7 — 通用：
  "用户说明[声称内容]。在现有材料中，[证据状态描述]。
   建议补充[具体材料]以支撑该表述。在材料补足前，本报告对该事项采用审慎表述。"

模板 8 — 涉及人数/规模的用户声称：
  "用户填写[字段名]为[数值]。该数据为用户自行填报，系统未对其准确性进行独立验证。
   根据该数值，[判断结论]。如实际数据与填报存在差异，判断结论可能发生变化。"

模板 9 — 涉及技术措施的声称：
  "用户说明已采取[措施名称]。建议补充该措施的技术实现说明、配置记录或第三方评估报告，
   以支撑'[措施名称]能够有效[防护目标]'的论证。"
```

### 6.4 隐含风险场景

```text
模板 10 — 文档未提但背景暗示风险：
  "协议文本本身未明确提及[风险事项]。然而，考虑到[背景事实]，
   存在[风险描述]的可能性。
   建议取得[确认材料]后，重新评估本节内容。"

模板 11 — 多文档信息矛盾：
  "关于[事项]，《[文件A]》第[X]条显示[内容A]，
   而《[文件B]》第[Y]条显示[内容B]。
   两项表述存在不一致，可能影响[合规判断]的成立。
   建议统一相关表述并明确以哪份文件为准。"
```

## 七、外部报告中必须出现的内容

### 7.1 每份外部报告的结构性必备项

```
 1. 文件概要（本文档是什么、基于什么输入生成）
 2. 总体合规评级（由规则引擎计算，附带评级说明）
 3. 核心发现/问题清单
 4. 审查边界说明（必须写清楚哪些结论是确定的、哪些依赖未验证前提）
 5. 待补充材料清单
```

## 八、外部报告中绝对禁止的结构性写法

### 8.1 禁止的章节写法

```text
❌ 以"综上所述"开头后直接写"企业合规"或"风险可控"
   → 必须首先回顾审查边界、材料缺失和不确定事项

❌ 在缺少材料的情况下写"经评估……"
   → 缺少材料时只能写"在现有材料条件下，初步判断……"

❌ 把整改建议写成"已完成"
   → 整改建议必须标注当前状态（planned / in_progress / 待落实）

❌ 把"建议"写成"要求"
   → 系统只能建议，不能要求。用"建议""推荐"，不用"必须""应当"
```

### 8.2 禁止的段落写法

```text
❌ 连续 3 个以上正面断言而无任何证据引用或保留条件
   → 每段最多 2 个正面断言，之后必须跟证据引用或保留条件

❌ 把同一事实在不同章节中写成不同措辞导致含义变化
   → 同一事实在全文中的措辞必须一致

❌ 在结论章中出现正文未提及的新事实或新判断
   → 结论章只能汇总，不能新增
```

### 8.3 禁止的数字表达

```text
❌ "约 XX 万" 但实际上用户填了精确数字
   → 使用用户填写的精确数字（"1,200,000 人"），不自行取整

❌ 把阈值写成"远低于""远高于"
   → 只陈述客观数值和阈值关系（"X 人，低于 Y 人门槛"）

❌ 在数值上使用"仅""才""只"
   → 不用主观修饰词修饰数值（"仅 5 万" → "5 万人"）
```

## 九、QA 检查清单

### 9.1 自动化检查（每次生成后必须运行）

```text
[ ] 报告是否包含 forbidden_expressions 中的任何词汇？
    → 全量正则扫描，命中即 BLOCKER

[ ] 每个 HIGH/BLOCKER issue 是否出现在报告中？
    → issue_id 和 title 至少出现一次

[ ] confirmed_issue 是否使用了和 suspected_issue 相同的肯定句式？
    → 对 suspected_issue 的段落检查是否缺少"可能""尚无法确认""建议补充"等标记

[ ] user_claim_only 事实是否被写成了确认句？
    → 检查每个 user_claim_only FactItem 的 value 是否在报告中被"已""充分""完善"修饰

[ ] 报告是否包含审查边界说明？
    → 检查是否存在"审查边界"或类似标题

[ ] 报告是否包含免责声明？
    → 检查是否存在"免责声明"或类似标题

[ ] 报告中是否出现了"违法""违规""违法""完全合规""不存在任何风险"等 BLOCKER 级禁止词？
    → 全量扫描

[ ] 报告中所有的数字是否和 FactItem 中的数值一致？
    → 提取报告中的数字与 FactItem.normalized_value 比对

[ ] internal review 中的表达是否泄露到了 external report 中？
    → 检查是否存在"内部审查"章节的原文片段
```

### 9.2 人工抽检（至少每 10 次生成抽检 1 次）

```text
[ ] 执行摘要的语气是否与 issue 严重度和确定性一致？
[ ] 每个"建议"是否具体、可执行、有明确的负责方提示？
[ ] 待补充材料清单是否按优先级排列？
[ ] 整体报告的阅读体验：是否能 30 秒内找到"结论是什么、风险在哪里、下一步做什么"？
```
