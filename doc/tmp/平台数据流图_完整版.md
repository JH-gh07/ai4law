## 二、阶段 ⑳：原始输入层 (Raw Input)

### 2.1 输入来源

```
用户直接输入
    ├── 结构化表单（字段因模块而异）
    ├── 自由文本（业务描述、数据处理说明、论证文本）
    └── 补充问答（"不知道"子流程的交互结果）

文件上传
    ├── DOCX（合同、隐私政策、DPA、SCC、BCR、制度文件）
    ├── PDF（扫描件、正式文本）
    ├── XLSX/CSV（数据清单、供应商列表）
    ├── URL（在线隐私政策）
    └── 图片（UI 截图、Cookie 弹窗截图）

系统上下文（非用户直接输入，但进入事实层）
    ├── 上游路径判断结果（从 PathDiagnosis 模块传入）
    ├── 文件元数据（文件名、大小、格式、上传时间）
    └── 自动检测的文档类型
```

### 2.2 当前各模块的输入模型（现状一览）

| 模块 | Request Model | 唯一字段数 | 文件支持 | 结构化子模型数 |
|------|:---|:---:|:---:|:---:|
| **诊断** | `DiagnosisAnswers` | 40+ | ❌ | 0 |
| **安全评估** | `AssessmentRequest` | 20+ | ✅ | 9 (DataInventoryItem, RecipientInfo, DownstreamProcessor...) |
| **CN SCC** | `SCCRequest` | 30+ | ✅ | 4 (DataFieldItem, PathDiagnosisInput, LegalBasis...) |
| **EU SCC** | `SCCReviewRequest` | 15+ | ✅ | SCCParty, SCCAnnexIA, SCCAnnexIB... |
| **CPRA** | `CPRARequest` | 12+ | ✅ | 5 (CPRAApplicabilityInfo, CPRADataItem, CPRAVendorInfo...) |
| **BCR** | `BCRRequest` | 10+ | ✅ | BCRUploadedDocument, BCRScenarioContext, BCRReviewConfig |
| **DPIA** | `DPIARequest` | 25+ | ❌ | RiskInput, MitigationInput |
| **文档审查** | `ReviewRequest` | 8+ | ✅ | 文档文本 + 类型标记 |

**观察**：输入模型的"粗细"差异巨大。安全评估和 CN SCC 已经拆了子模型，CPRA 有结构化字段但缺附件解析 Agent，DPIA 和诊断仍以纯字段为主。

### 2.3 统一后的输入层目标结构

不追求一个万能 Request，而是定义三层：

```
L1 RawInput (平台基类)
    ├── jurisdiction: "CN" | "EU" | "US" | "MULTI"
    ├── company_name: str
    ├── raw_files: RawFile[]
    └── raw_form_snapshot: dict  (保留原始表单，审计用)

L2 JurisdictionInput (法域扩展)
    ├── CNInput
    │   ├── is_ciio: bool
    │   ├── has_important_data: bool
    │   ├── pii_count: int
    │   └── ...
    ├── EUInput
    │   ├── dpia_trigger_signals: list[str]
    │   ├── transfer_destinations: list[str]
    │   └── ...
    └── USInput
        ├── ca_consumer_count: int
        ├── sell_share_revenue_ratio: float
        └── ...

L3 ModuleInput (模块专有)
    ├── SecurityAssessmentInput (继承 CNInput)
    ├── StandardContractInput (继承 CNInput)
    ├── DPIAInput (继承 EUInput)
    ├── BCRInput (继承 EUInput)
    └── CPRAInput (继承 USInput)
```

## 三、阶段 ①：文档解析层 (Document Parsing)

### 3.1 本层职责

把原始文件变成可搜索、可定位、可引用的结构化文档对象。**本层不做法律判断。**

### 3.2 产出对象

```
StructuredDocument
    ├── doc_id: str
    ├── file_name: str
    ├── file_type: "docx" | "pdf" | "xlsx" | "url" | "image"
    ├── detected_doc_kind: "contract" | "privacy_policy" | "scc" | "dpa" | "bcr" | "policy" | "consent_record" | "certification" | "audit_report" | "data_inventory" | "employee_handbook" | "other"
    ├── parsed_pages: int
    ├── raw_text: str
    └── sections: DocumentSection[]

DocumentSection
    ├── section_id: str
    ├── title: str
    ├── page_start: int
    ├── page_end: int
    ├── raw_text: str
    └── child_clauses: ParsedClause[]

ParsedClause
    ├── clause_id: str
    ├── clause_number: str  (如 "第3条", "Clause 15(a)", "附录二 第4条")
    ├── clause_type: str  (23种 ClauseType 之一，解析阶段初步分类)
    ├── text: str
    ├── page: int
    ├── paragraph_range: (int, int)
    └── table_cells: list[dict]  (如条款存在于表格中)

ParseResult
    ├── structured_document: StructuredDocument
    ├── parsing_warnings: list[str]  ("表格跨页可能导致切分错误", "PDF 第4页疑似扫描件")
    ├── parsing_confidence: float
    └── ocr_metadata: dict | None  (扫描件 OCR 时记录引擎、置信度)
```

### 3.3 现状

| 能力 | 哪些模块已有 | 成熟度 |
|------|:---|:---:|
| DOCX 段落+表格解析 | 文档审查, BCR, EU SCC | ⭐⭐⭐ |
| PDF 文本提取 | 文档审查, EU SCC | ⭐⭐ |
| 条款切分 (by 条/章/节) | 文档审查, BCR, EU SCC | ⭐⭐⭐ |
| 文档类型自动识别 | 文档审查, BCR, CPRA(附件角色) | ⭐⭐ |
| 扫描件 OCR | ❌ 无 | — |
| 中英混合文档正确处理 | 部分支持 | ⭐ |
| 解析置信度标记 | ❌ 无 (全局缺失) | — |

### 3.4 关键缺口

1. **没有统一的 DocumentParser**：文档审查、EU SCC、BCR 各写了一套解析逻辑。
2. **解析结果不带 confidence**：下游代码无法区分"解析到了"和"解析对了"。
3. **没有扫描件 OCR 能力**：图片型 PDF 直接失败。
4. **中英混合切分不稳定**。

## 四、阶段 ②：路径诊断层 (Path Diagnosis)

### 4.1 本层职责

判断用户应该走哪条合规路径。**这是全局入口，不是某个模块的内部功能。** 所有文书生成模块只消费路径结果，不自行判断。

### 4.2 产出对象

```
PathDiagnosisResult
    ├── recommended_path: "security_assessment" | "standard_contract" | "certification" | "exemption" | "scc_eu" | "bcr" | "dpia" | "cpra_gap" | "uncertain"
    ├── jurisdiction: "CN" | "EU" | "US" | "MULTI"
    ├── alternative_paths: list[str]
    ├── confidence: float  (0.0-1.0)
    ├── rationale: str
    ├── triggered_conditions: list[TriggerCondition]
    │   ├── condition_id: str  (如 "CN-PII-100W-THRESHOLD")
    │   ├── condition_name: str
    │   ├── status: "triggered" | "not_triggered" | "uncertain"
    │   └── basis: str
    ├── blocking_issues: list[str]
    ├── exemption_assessment: ExemptionAssessment | None
    │   ├── candidate_exemptions: list[str]
    │   ├── confirmed: bool
    │   └── missing_evidence: list[str]
    ├── uncertain_facts: list[UncertainFact]
    │   ├── field: str
    │   ├── current_best_guess: str
    │   └── impact_on_path: "BLOCKER" | "MAY_CHANGE" | "LOW_IMPACT"
    └── next_questions: list[ClarificationQuestion]
        ├── priority: "HIGH" | "MEDIUM" | "LOW"
        ├── question: str
        └── why: str
```

### 4.3 路径诊断的决策树（规则为主，Agent 辅助）

```
Step 1: CIIO? ──YES──→ security_assessment (BLOCKER, 规则判断)
    ↓ NO/UNKNOWN
Step 2: 重要数据? ──YES──→ security_assessment (BLOCKER, 规则+Agent辅助)
    ↓ NO/UNKNOWN
Step 3: 是否含个人信息?
    ├── NO ──→ exemption (no_personal_info)
    ↓ YES/UNKNOWN
Step 4: 豁免情形?
    ├── 合同履行必需 ──→ exemption (需 Agent 核验)
    ├── HR 管理 ──→ exemption (需 Agent 核验证据)
    ├── 紧急情况 ──→ exemption
    └── 均不适用 ──→ 继续
    ↓
Step 5: SPI 人数 > 1万 或 PII 人数 > 100万? ──YES──→ security_assessment
    ↓ NO
Step 6: PII 人数 10万-100万? ──YES──→ standard_contract or certification
    ↓ NO
Step 7: < 10万 ──→ standard_contract (可自由选择)
```

### 4.4 现状

| 能力 | 哪个模块在做 | 问题 |
|------|:---|------|
| 核心路径判断 | 诊断模块 (`decision_tree.json`) | ✅ 第一条命中即返回，缺少全量扫描 |
| 路径复核 | 安全评估模块内部 | ❌ 职责错位，文书模块不应重新判路径 |
| CN SCC 路径判断 | CN SCC (`path_diagnosis_agent.py`) | ⚠️ 与诊断模块存在功能重复 |
| 多法域路径 | ❌ 无 | 架构空白 |

### 4.5 目标

```
PathDiagnosisService (全局唯一)
        ↓
    PathDiagnosisResult
        ↓
    传入各文书模块（作为上游上下文，仅供消费）
```

## 五、阶段 ③：事实抽取与标准化层 (Fact Extraction & Normalization)

### 5.1 本层职责

把所有输入（表单、文档、Agent 推断）转换成统一格式的结构化事实。**每个事实必须标注来源类型和证据强度。**

### 5.2 核心对象：FactItem

这是平台最重要的共享对象。当前 `backend/common/workflow/facts.py` 已有定义：

```
FactItem
    ├── fact_id: str                    唯一标识
    ├── source_type: Literal[          事实来源类型
    │       "schema"                    ─ 用户表单填写
    │       "attachment"                ─ 从上传文档抽取
    │       "user_text"                 ─ 用户自由文本
    │       "diagnosis"                 ─ 来自路径诊断结果
    │       "derived"                   ─ 系统规则派生
    │       ]
    ├── source_ref: str | None         具体来源引用 (字段路径/文件名/规则名)
    ├── field_path: str | None         字段路径
    ├── value: Any                     原始值
    ├── normalized_value: Any | None   标准化后的值
    ├── confidence: float              置信度 (0.0-1.0)
    ├── notes: str | None              补充说明
    ├── evidence_status: Literal[      证据成熟度
    │       "user_claim_only"           ─ 仅用户声称，无证据
    │       "partial_evidence"          ─ 有部分证据但不完整
    │       "documented_evidence"       ─ 有文档/材料支撑
    │       "verified_evidence"         ─ 经第三方审计或官方认证
    │       ]
    ├── supporting_material_refs: list[str]  支撑材料引用
    └── can_support_external_positive_claim: bool  是否可用于外部报告的正面表述
```

### 5.3 FactPack（模块级事实集合）

```
FactPack (每个模块构建自己的事实集合)
    ├── module: str
    ├── jurisdiction: str
    ├── facts: list[FactItem]
    ├── fact_count_by_source: dict[str, int]
    ├── fact_count_by_evidence_status: dict[str, int]
    └── extraction_warnings: list[str]
```

### 5.4 事实抽取的三条路径

```
路径 A：表单字段 → 事实
    DiagnosisAnswers / SCCRequest / AssessmentRequest → FactItem (source_type="schema")
    confidence ≥ 0.8 (用户主动填写)
    evidence_status = "user_claim_only" (未经验证)

路径 B：文档解析 → 事实
    StructuredDocument / ParsedClause → FactItem (source_type="attachment")
    confidence = parsing_confidence (取决于文档质量和解析准确率)
    evidence_status = "documented_evidence" 或 "partial_evidence"
    必须带 source_ref 指向原文档页码/段落

路径 C：Agent 推理 → 事实 (进入下一层)
    Agent 推理 → FactItem (source_type 待定)
    confidence = agent_confidence
    evidence_status ≤ "partial_evidence" (Agent 不能产生 verified_evidence)
    标记 requires_user_confirmation = True
```

### 5.5 Fact Merger 的优先级策略

当多个来源对同一字段产生矛盾事实时：

```
合并优先级：
1. user_confirmed（用户人工确认的）→ 最高
2. document_extracted（从权威文件抽取的）→ 次高
3. user_declared（用户表单填的）
4. agent_assisted（Agent 推断的）
5. rule_inferred（规则派生的）
6. system_default（系统默认值）→ 最低

合并时必须保留冲突记录：
FactMergeLog
    ├── field_path: str
    ├── sources: list[(source_type, value, confidence)]
    ├── winner: source_type
    └── reason: str
```

### 5.6 现状

| 能力 | 哪些模块已有 | 成熟度 |
|------|:---|:---:|
| `FactItem` 通用模型 | `backend/common/workflow/facts.py` | ⭐⭐⭐⭐ |
| 表单字段 → FactItem | CN SCC (`fact_builder.py`) | ⭐⭐⭐ |
| 附件文本 → FactItem | CN SCC (部分), CPRA (附件extractor) | ⭐⭐ |
| Agent 增强 → FactItem | ❌ 无统一的 Agent→Fact 回填机制 | — |
| Fact Merger (多源冲突处理) | ❌ 无 | — |
| `evidence_status` 四级分级使用 | CN SCC 已标注, 其他模块未统一使用 | ⭐⭐ |
| `can_support_external_positive_claim` | CN SCC 已定义，其他模块未用 | ⭐ |

## 六、阶段 ④：Agent 推理增强层 (Agent Reasoning)

### 6.1 本层职责

Agent 不改变路径判断和规则结论，只负责：
- 从非结构化材料中抽取事实（补充路径 B）
- 对模糊事实做辅助判断
- 做条款级语义比对
- 解释"为什么这么判"

### 6.2 7 个平台级 Agent 及其产出

```
┌─────────────────────────────────────────────────────────────────┐
│ Agent 1: FactExtractionAgent                                     │
│ 职责：从合同中抽取结构化信息，补充 schema/attachment 未能覆盖的事实   │
├─────────────────────────────────────────────────────────────────┤
│ 输入：StructuredDocument + ParsedClause[]                        │
│ 产出：AgentFactExtractionResult                                  │
│   ├── extracted_facts: list[FactItem]  (source_type="attachment")│
│   ├── evidence_spans: list[EvidenceSpan]                         │
│   │   ├── fact_id: str                                           │
│   │   ├── source_file: str                                       │
│   │   ├── page: int                                              │
│   │   ├── quote: str                                             │
│   │   └── confidence: float                                      │
│   ├── extraction_warnings: list[str]                             │
│   └── fallback_used: bool  (LLM不可用时降级为规则提取器)          │
│                                                                   │
│ 复用模块：安全评估, SCC(CN+EU), CPRA, DPIA, BCR, 文档审查        │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ Agent 2: DataClassificationAgent                                 │
│ 职责：判断个人信息/敏感个人信息/重要数据/匿名化有效性               │
├─────────────────────────────────────────────────────────────────┤
│ 输入：FactItem[] (原始字段事实) + DataFieldItem[]                 │
│ 产出：DataClassificationResult                                   │

### 6.3 Agent 编排约束

```
规则：
1. 所有 Agent 输出必须包含 confidence 字段
2. confidence < 0.65 → 不进规则输入，仅入 trace
3. 0.65 ≤ confidence < 0.85 → 进规则但标记 source="agent_assisted"
4. confidence ≥ 0.85 → 进规则但仍保留原始用户输入可回溯
5. 每个 Agent 必须有 fallback (LLM不可用时降级为规则/关键词)
6. Agent 不能改变规则引擎的路径判断
7. Agent 不能将 planned_measure 写成 implemented_measure
```

### 7.3 规则引擎的"不可 Agent 化"清单

以下判断永远属于规则，Agent 只能给建议值：

| 判断项 | 模块 | 原因 |
|--------|------|------|
| CIIO 最终判定 | 诊断/CN | 法律定义的确定性判断 |
| 重要数据最终判定 | 诊断/CN | 依赖主管部门目录，确定性优先 |
| 100万/10万/1万人阈值 | 诊断/CN SCC | 纯数值比较 |
| 2500万美元/10万消费者/50%收入 | CPRA | 纯数值比较 |
| HIPAA/GLBA/COPPA 豁免范围 | CPRA | 法律定义的确定性判断 |
| 标准合同条款不可克减性 | CN SCC/EU SCC | 强制法律规则 |
| SCC Module 适用性 | EU SCC | 强制法律规则 |
| 风险等级最终计算 | 全部 | 确定性聚合，不能由 Agent 拍板 |
| 路径最终决策 | 全部 | 规则引擎统一计算 |

## 八、阶段 ⑥：Issue 与 Risk 生成层 (Issue & Risk)

### 8.1 本层职责

把规则命中、Agent 发现、Fact 状态综合成合规问题。**每个 Issue 必须能追溯到支撑它的 Fact 和 Rule。**

### 8.2 核心对象：IssueItem

当前 `backend/common/workflow/issues.py` 已有定义：

```
IssueItem
    ├── issue_id: str
    ├── title: str
    ├── description: str
    ├── category: IssueCategory  (30+ 种分类)
    ├── severity: "LOW" | "MEDIUM" | "HIGH" | "BLOCKER"
    ├── fact_refs: list[str]  → 必须引用 FactItem.fact_id
    ├── rule_refs: list[str]  → 必须引用 RuleHit.rule_id
    ├── evidence_refs: list[str]  → 必须引用 EvidenceItem.evidence_id
    ├── recommended_action: str
    ├── affects_outputs: list[str]
    ├── missing_materials: list[str]
    ├── internal_review_required: bool
    └── external_report_strategy_required: bool
```

### 8.3 Issue 三级分类（必须加到 IssueItem 中）

当前 `IssueItem` 缺失一个关键字段 —— issue 的"确定性类型"：

```
需要在 IssueItem 中增加：
    issue_certainty: "confirmed_issue" | "suspected_issue" | "default_review_item"
```

这三种类型在报告中的表达完全不同：

| 类型 | 含义 | 报告表达 |
|------|------|---------|
| `confirmed_issue` | 已确认问题（有规则命中 or 文档证据明确缺失） | "当前法律文件未覆盖……" |
| `suspected_issue` | 疑似问题（Agent 推断，证据不充分） | "由于未提供相关材料，尚无法确认……" |
| `default_review_item` | 默认审查项（模板必须检查，但因缺材料无法判断） | "建议在正式申报前核验……" |

### 8.4 Issue 和 Fact/Evidence 的引用链

```
IssueItem
    ├── fact_refs → FactItem.fact_id → 用户原始输入 / 文档原文
    ├── rule_refs → RuleHit.rule_id → 法规 / 标准 / 规则
    └── evidence_refs → EvidenceItem.evidence_id → RAG片段 / 文档引用
```

这个三角形引用链是平台最重要的"可信基础"。报告中的每一句结论必须能沿着这条链回溯。

### 8.5 现状

| 能力 | 哪些模块有 | 成熟度 |
|------|:---|:---:|
| `IssueItem` 通用模型 | `backend/common/workflow/issues.py` | ⭐⭐⭐⭐ |
| Issue → Fact 引用 | CN SCC (`issue_builder.py`) | ⭐⭐⭐ |
| Issue → Rule 引用 | CN SCC, 安全评估 | ⭐⭐ |
| Issue → Evidence 引用 | EU SCC | ⭐⭐ |
| `issue_certainty` 三级分类 | 安全评估 (schema 里定义了但未在 IssueItem 中使用) | ⭐ |
| 默认审查项与确认问题的区分 | ❌ 当前几乎所有 issue 都等价表达 | — |

### 9.4 CitationRegistry

```

    ├── citations: dict[str, CitationEntry]
    ├── last_updated: str

### 9.5 RAG 的引用约束

```
外部报告只能使用 support_level 为 exact_support 或 partial_support 的引用。
background_only 引用只能在内部审查中出现。
irrelevant 引用必须从报告中移除。

每个外部报告中的引用句子必须：
  1. 明确标注来源（法规名称 + 条文号）
  2. 不被用于超出其 support_level 的结论
  3. 标注法规生效时间
```

### 10.3 ExpressionStrategy（表达策略）

```
ExpressionStrategy
    ├── claim: str  (要表达的主张)
    ├── fact_status: "user_claim_only" | "partial_evidence" | "documented_evidence" | "verified_evidence"
    ├── allowed_expression: str  (允许的表达方式)
    ├── forbidden_expressions: list[str]  (禁止的表达方式)
    └── recommended_wording: str  (推荐的表达措辞)

示例：
{
  "claim": "境外接收方具备数据安全保障能力",
  "fact_status": "user_claim_only",
  "allowed_expression": "用户已说明境外接收方具备一定安全保障能力",
  "forbidden_expressions": [
    "境外接收方已充分具备安全保障能力",
    "境外接收方的安全措施完善",
    "已通过安全审计确认"
  ],
  "recommended_wording": "用户已说明境外接收方具备一定数据安全保障能力，但当前材料尚未提供认证报告、审计结论或安全制度文件，建议在正式申报前补充相关证明材料。"
}
```

### 10.4 全局禁止表达库

```
FORBIDDEN_EXPRESSIONS = [
    # 违法定性类
    "违反",     # → 用 "与……存在不一致"
    "违法",     # → 用 "可能不符合……要求"
    "违规",     # → 用 "需要进一步满足……规定"
    "已经构成",  # → 用 "可能存在……风险"

    # 过度承诺类
    "完全合规",  # → 用 "在现有材料条件下，基本满足……要求"
    "已充分证明", # → 用 "提供了……材料支撑"
    "确保不会",  # → 用 "有助于降低……风险"
    "已全部完成", # → 用 "已完成……方面的合规工作"

    # 事实外推类
    "企业已建立完善的", # 如果只有声明而无制度文件
    "数据已经完全匿名化", # 如果只有用户声称无技术证明
    "不存在任何风险",   # 永远不能写

    # 系统越权类
    "企业应立刻停止",    # → 用 "建议审慎评估是否继续"
    "必须向监管机构申报", # → 用 "根据……规定，建议启动申报程序"
]
```

## 十一、阶段 ⑨：报告生成层 (Report Generation)

### 11.1 本层职责

按 WritingPlan 生成章节正文。生成的不是"自由作文"，而是按模板、策略和约束严格生成的合规文书。

### 11.2 产出对象

```
Chapter
    ├── chapter_no: int
    ├── title: str
    ├── content: str
    ├── citations: list[str]
    ├── risk_level: str
    ├── footnote_map: dict | None  (引用 → 脚注编号映射)
    └── used_fact_ids: list[str]  (本章使用了哪些 Fact)

ReportDraft
    ├── module: str
    ├── template_id: str
    ├── chapters: list[Chapter]
    ├── overall_rating: RiskLevel
    ├── executive_summary: str
    ├── used_citations: list[str]  (去重后的全部引用)
    ├── uncertain_facts_disclosed: bool  (是否披露了不确定事实)
    └── generation_metadata: dict  (模型、时间、token)
```

### 11.3 双层报告结构

```
对内报告 (Internal Review)
    ├── 真实风险水平
    ├── 证据不足项
    ├── 系统怀疑但未确认的风险
    ├── 建议暂缓/否决的理由
    └── 禁止发给用户的内容

对外报告 (External Draft)
    ├── 基于 template + WritingPlan 生成
    ├── 禁止使用内部表达
    ├── 禁止把 suspected 写成 confirmed
    ├── 禁止把 user_claim 写成 system_verified
    └── 每个正面结论都有 evidence_status ≥ documented_evidence 的支撑
```

### 11.4 报告生成环节的 LLM 约束

```
输入给 LLM 的 context 必须包含：
  ✅ WritingPlan 中的 allowed_facts
  ✅ WritingPlan 中的 forbidden_claims
  ✅ 本节要求的 citations
  ✅ expression_style

不允许 LLM 使用的：
  ❌ 超出 WritingPlan assigned_facts 之外的事实
  ❌ 不在 CitationRegistry 中的法规引用
  ❌ forbidden_expressions 中的任何表达
  ❌ user_claim_only 状态的事实写成正面确认句
```

## 十二、阶段 ⑩：质检与审校层 (QA & Alignment)

### 12.1 本层职责

生成后的最终质量门禁。**不通过的不能输出为最终报告。**

### 12.2 检查项清单

```
1. 事实一致性检查
   ├── 报告是否引用了用户未提供的事实？→ new_fact_injection
   ├── 报告是否遗漏了必须披露的 issue？→ missing_risk_item
   ├── 报告是否把 "user_claim_only" 写成了确认句？→ unsupported_positive_claim
   └── 报告中的数字/单位/阈值是否与 Fact 一致？→ numeric_inconsistency

2. 风险覆盖检查
   ├── 所有 HIGH/BLOCKER issue 是否进入摘要？→ high_risk_not_in_summary
   ├── 所有 MissingItem 是否进入缺失项章节？→ missing_item_not_reported
   └── 风险评级是否和 issue 严重度一致？→ inconsistent_rating

3. 引用质量检查
   ├── 每个法律判断是否有对应 citation？→ missing_citation
   ├── citation 是否真正支撑该判断？→ irrelevant_citation
   ├── 是否使用了 background_only 引用支撑核心结论？→ weak_citation
   └── 是否引用了过期法规？→ superseded_citation

4. 表达安全检查
   ├── 是否出现 forbidden_expressions？→ forbidden_expression
   ├── 是否把内部表达泄露到外部报告？→ internal_expression_leak
   ├── 是否把 planned measure 写成 implemented？→ measure_status_misrepresentation
   └── 是否把 system_inferred 写成 user_confirmed？→ fact_source_misrepresentation

5. 模板完整性检查
   ├── 官方模板要求的每个章节是否存在？→ template_section_missing
   ├── 每个章节是否覆盖了模板要求的子项？→ template_content_missing
   └── 章节顺序是否与模板一致？→ template_order_mismatch

6. 跨文档一致性检查
   ├── 同一事实在不同章节表达是否一致？→ cross_chapter_inconsistency
   ├── 引用列表和正文引用是否一致？→ citation_list_mismatch
   └── 不同法域结论是否冲突？→ cross_jurisdiction_conflict
```

### 12.3 Repair 规则

```
Repair 的允许范围（受控修复）：
  ✅ 补引用
  ✅ 补充遗漏的 issue
  ✅ 改写过度正面/违规的表达
  ✅ 补充缺失的模板章节
  ✅ 修正数字/单位错误

Repair 的禁止范围：
  ❌ 新增事实（new fact injection）
  ❌ 删除风险（risk removal）
  ❌ 降低风险等级（risk downgrade）
  ❌ 把缺失材料改成已具备（material fabrication）
  ❌ 新增法规引用（citation fabrication）
  ❌ 修改规则引擎的结论

修复后必须运行的二次检查：
  - diff check (修改了什么)
  - new fact injection check
  - risk downgrade check
  - citation drift check
```

|------|:---|:---:|

## 附录 B：关键设计决策记录

| 决策 | 结论 | 理由 |
|------|------|------|
| Fact 模型是否统一为一个万能类？ | **否**。L1 基类 + L2 法域扩展 + L3 模块专有 | 法域差异太大，强统一会丢信息 |
| PathDiagnosis 是否全局唯一？ | **是**。其他模块只消费，不重复判断 | 避免用户体验前后矛盾 |
| Agent 能否改变规则引擎结论？ | **否**。Agent 只能给建议值，规则拥有阻断权 | 可解释性、可审计性是合规系统生命线 |
| RAG 定位是什么？ | **证据绑定系统**，不只是检索上下文 | "有引用 ≠ 引用正确" |
| Report 生成是否直接 LLM？ | **否**。必须先有 WritingPlan | 防止 LLM 自由发挥，导致报告不可控 |
| Agent 个数？ | **7 个平台级 Agent**，不是 64 个模块 Agent | 减少重复，提高复用 |
| Trace 是全量还是分层？ | **两层**。审计层必存，调试层按需 | 全量存储成本太高 |
