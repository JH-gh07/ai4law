## 一、为什么需要这个矩阵

### 1.1 当前架构的盲区

```text
当前状态：
  诊断模块 ──→ 判断 CN 法域下的路径
  EU SCC模块 ──→ 审查 EU 法域下的标准合同
  CPRA模块  ──→ 评估 US 法域下的合规差距

  每个模块独立运行，互不知晓。
  一个跨国企业的同一个"数据出境行为"会被三个模块分别分析，
  但没有任何层来协调三者之间可能冲突的结论。
```

### 1.2 跨法域冲突的真实性

这不是理论上的担忧。任何涉及两个及以上法域的企业都会遇到：

```text
例 1：中国电商用 AWS 新加坡节点服务欧洲用户
  → CN：安全评估 or 标准合同？
  → EU：SCC + TIA（新加坡有充分性认定吗？AWS 美国呢？）

例 2：美国 SaaS 公司的中国子公司处理员工数据
  → CN：HR 豁免是否适用？
  → US：CPRA 是否适用？（如果员工中包含加州居民）

例 3：德国车企在中国收集车联网数据，传回慕尼黑
  → CN：重要数据？汽车数据安全管理规定？
  → EU：GDPR 充分性认定？中国不属于充分性国家
```

### 1.3 矩阵的用途

```text
1. 设计跨法域协调器时的参考输入
2. 测试用例的素材来源
3. 产品演示时的多法域场景库
4. 发现平台架构盲区的工具
```

## 二、法域义务速查表

### 2.1 CN 法域 — 中国个人信息保护法体系

```
触发条件（满足任一）：
  - 在中国境内处理个人信息
  - 向境外提供在中国境内收集的个人信息
  - 处理 100 万人以上个人信息 or 1 万人以上敏感个人信息

核心义务：
  路径判断：
    - CIIO → 必须安全评估
    - 重要数据 → 必须安全评估
    - ≥100万PII or ≥1万SPI → 必须安全评估
    - 10万-100万PII → 标准合同 or 认证
    - <10万PII → 标准合同/认证（自由选择）
    - 豁免情形（合同必需/HR管理/紧急/法定义务）→ 豁免

  安全评估申报（如触发）：
    - 提交数据出境风险自评估报告
    - 与境外接收方签署法律文件（含六项核心条款）
    - 网信办审批

  标准合同备案（如选择）：
    - 签署个人信息出境标准合同
    - 完成个人信息保护影响评估 (PIPIA)
    - 向省级网信办备案

  认证（如选择）：
    - 通过专业认证机构认证
    - 认证机构须为中国网信部门认可

关键时间线：
  - 安全评估：提交后 45 工作日内完成（可延长）
  - 标准合同备案：签署后 10 工作日内备案
  - 认证：持续有效，定期监督

数据本地化：
  - CIIO 的个人信息和重要数据原则上境内存储
  - 确需出境的，通过安全评估
```

### 2.2 EU 法域 — GDPR 体系

```
触发条件（满足任一）：
  - 在欧盟境内设立的数据控制者/处理者
  - 向欧盟境内的数据主体提供商品或服务
  - 监控欧盟境内数据主体的行为

核心义务：
  国际传输基础：
    - 充分性认定（Adequacy Decision）→ 自由传输
    - 适当保障措施（SCC / BCR / 行为准则 / 认证）→ 需额外措施
    - 克减情形（明确同意/合同必需/公共利益等）→ 例外使用

  SCC（标准合同条款）：
    - 4 个 Module（C2C/C2P/P2P/P2C）
    - 必须完成 TIA（传输影响评估）
    - Schrems II 补充措施（技术+合同+组织）

  BCR（约束性公司规则）：
    - 集团内部传输
    - 需主管监管机构批准
    - 包含第三方受益人权利

  DPIA（数据保护影响评估）：
    - 高风险处理时必须
    - 自动化决策/大规模处理/特殊类别数据/系统性监控等

关键时间线：
  - SCC 签署：签署即生效（但 TIA 和补充措施应先完成）
  - BCR 批准：数月
  - DPIA：处理活动开始前完成

数据传输限制：
  - 无"数据本地化"的硬性要求
  - 但对第三国传输有严格限制
  - Schrems II 要求逐案评估第三国法律
```

### 2.3 US 法域 — CPRA 体系

```
触发条件（满足任一）：
  - 在加州经营
  - 年收入 > 2500万美元 OR 处理 ≥10万消费者个人信息 OR 50%+收入来自出售/共享个人信息

核心义务（与中国/EU最不同的点）：
  无"跨境传输"概念：
    - CPRA 不限制数据跨州或跨国传输
    - 关注的是"出售/共享"行为，不论接收方在境内还是境外
    - 供应商（service provider/contractor）的合同约束

  消费者权利：
    - 知情权（Right to Know）
    - 删除权（Right to Delete）
    - 更正权（Right to Correct）
    - 选择退出权（Opt-Out of Sale/Sharing）
    - 限制敏感信息使用权（Limit Use of SPI）
    - 非歧视权

  企业义务：
    - 隐私政策（完整告知）
    - DSR 响应机制（45天+45天延长期）
    - 供应商合同管理（DPA + 审计权）
    - opt-out 链接（Do Not Sell or Share + Limit SPI）
    - GPC（全球隐私控制）信号识别
    - 暗模式禁止
    - 数据最小化和保留期限限制

关键时间线：
  - DSR 响应：45天内（可延长45天）
  - opt-out：15天内生效
  - 执法：CPPA 自 2024 年起

与中国/EU最关键差异：
  - CPRA 没有"重要数据"概念
  - CPRA 没有"安全评估"机制
  - CPRA 没有"标准合同备案"要求
  - CPRA 的"敏感个人信息"范围与 GDPR 特殊类别数据、中国敏感个人信息都有差异
```

## 三、场景 1：中国电商出海 — CN + EU 冲突

### 3.1 事实背景

```text
企业：ShopChina（中国注册的跨境电商平台）
业务：中国卖家 → 欧洲消费者（德国/法国为主）
数据流：
  - 消费者下单 → 数据进入 ShopChina 杭州 AWS 中国区
  - 订单履行 → 数据传至 ShopChina 法兰克福仓库系统
  - 客服支持 → 菲律宾外包团队远程访问
  - 推荐算法 → 数据传至美国 AWS 进行模型训练

数据内容：
  - 消费者姓名、地址、电话、邮箱（PII）
  - 购买历史、浏览记录（PII）
  - 支付信息（SPI）
  - 消费者数量：约 30 万欧洲用户 + 200 万中国用户
```

### 3.2 各法域判定

```
CN 法域判定：
  - CIIO？→ 否（电商平台不属于 CIIO）
  - 重要数据？→ 涉及 200 万中国用户，但消费者购买数据通常不构成重要数据
  - PII 出境人数？→ 约 30 万（传给法兰克福） + 可能传给美国 AWS
  - SPI 出境人数？→ 支付信息算 SPI，约 30 万 → 触发安全评估！
  - 路径：安全评估（因 SPI ≥ 1 万人触发）
  - 义务：提交安全评估申报 + 签署法律文件 + 完成自评估报告

EU 法域判定：
  - 适用 GDPR？→ 是（向欧盟消费者提供商品）
  - 数据传至中国杭州？→ 中国不属于充分性认定国家
  - 数据传至美国 AWS？→ 美国不属于充分性认定国家
  - 数据传至菲律宾？→ 菲律宾不属于充分性认定国家
  - 路径：SCC（Module Two: C2P）+ TIA + Schrems II 补充措施
  - 义务：签署 SCC + 完成 TIA × 3（中/美/菲）+ 补充措施 + DPIA

US 法域判定：
  - 适用 CPRA？→ 取决于是否有加州消费者
  - 场景假设：欧洲用户为主，加州消费者忽略不计 → 不适用 CPRA
```

### 3.3 冲突点

```
冲突 1：数据本地化的矛盾倾向
  CN：CIIO 才需要数据本地化，ShopChina 不是 CIIO → 没有硬性本地化要求
      BUT 安全评估审批可能要求限制出境数据范围
  EU：无硬性本地化要求
      BUT Schrems II 要求如果第三国法律（含中国法）可能妨碍 SCC 履行，
      则需要额外补充措施甚至暂停传输
  → 隐含冲突：中国监管可能要求数据留存境内，欧盟监管可能质疑中国法律环境

冲突 2：安全评估 vs SCC 的时间线冲突
  CN：安全评估申报 → 等待网信办审批（45工作日+）→ 批准后才可出境
  EU：SCC 签署即生效 → 但需先完成 TIA 和补充措施
  → 企业实际流程：先等中国安全评估批准，同时准备 SCC（两个管线并行）

冲突 3：对"SCC"的不同定义
  CN："标准合同" = 中国个人信息出境标准合同（向中国网信办备案）
  EU："SCC" = EU 2021/914 标准合同条款
  → 两份完全不同的法律文件！
  → 企业需要同时签署：中国版标准合同 & EU SCC

冲突 4：接收方约束可能矛盾
  CN 法律文件（六项核心条款）要求：
    - 境外接收方受中国法管辖
    - 争议解决在中国法院
  EU SCC Clause 18 要求：
    - 管辖法律为欧盟成员国法律
    - 争议解决在欧盟成员国法院
  → 两份合同的管辖条款直接冲突！

冲突 5：安全评估报告 vs DPIA
  CN 要求：数据出境风险自评估报告（按中国官方模板）
  EU 要求：DPIA（按 GDPR Art.35 + WP248 指南）
  → 评估维度不同、格式不同、语言不同
  → 不能合并为一份文件
```

### 3.4 系统应该如何处理

```text
正确的多法域协调输出：

"您的数据出境活动同时触发中国法和欧盟 GDPR 下的合规义务。

【中国法】
  - 路径：安全评估申报（敏感个人信息出境超过1万人）
  - 需完成：自评估报告 + 法律文件 + 网信办申报
  - 预计周期：45-60工作日

【欧盟 GDPR】
  - 路径：SCC（Module Two: C2P）+ TIA + Schrems II 补充措施
  - 需完成：签署 EU SCC + 完成 3 份 TIA（中国/美国/菲律宾）
  - 预计周期：4-8周（不含监管审批）

【并行推进建议】
  1. 立即启动中国安全评估申报准备（约需 2-4 周准备材料）
  2. 同步签署 EU SCC 并启动对中国、美国、菲律宾的 TIA
  3. 注意：中国标准合同和 EU SCC 是两份不同文件，不能混淆
  4. 注意：两份合同的管辖条款存在潜在冲突，建议在 EU SCC 中明确不得排除中国法强制性要求

【关键风险提示】
  - 安全评估审批时间不可控，建议预留 3-6 个月
  - 菲律宾客服外包可能构成额外的子处理者链，需要补充 DPA
  - 美国 AWS 涉及 FISA 702 风险，需要端到端加密 + EU 持钥
  - 中国法律环境可能被欧盟监管视为 TIA 中的风险因素"
```

## 四、场景 2：SaaS 平台跨国运维 — CN + EU + US 冲突

### 4.1 事实背景

```text
企业：DataFlow Analytics（新加坡注册，全球运营）
产品：企业级数据分析 SaaS 平台

数据处理流：
  - 中国客户：上传业务数据至 DataFlow 上海节点
  - 欧洲客户：上传业务数据至 DataFlow 法兰克福节点
  - 所有客户的元数据和匿名化的使用统计 → 传至新加坡总部
  - 模型训练：传至美国 AWS（弗吉尼亚）进行模型训练
  - 全球运维：印度团队可远程访问所有节点的运维数据

数据类型（以中国客户为例）：
  - 客户上传的原始业务数据（可能包含客户终端用户的个人信息）
  - DataFlow 的角色：处理者（为客户处理数据）
  - 元数据：客户企业信息、使用统计
  - 运维数据：日志、错误报告（可能含少量个人数据）

规模：
  - 中国客户：约 500 家企业
  - 欧洲客户：约 300 家企业
  - 美国客户：约 200 家企业（含部分加州企业）
  - 终端用户数据量：涉及数百万自然人
```

### 4.2 各法域判定

```
CN 法域判定：
  - DataFlow 是处理者还是控制者？
    → 客户数据：处理者（按客户指令处理）
    → 元数据和运维数据：可能构成独立的控制者
  - 数据是否出境？
    → 客户数据存储在上海，未出境 → CN 法不触发（但需确认新加坡团队和印度团队是否可访问）
    → 如果印度团队远程访问上海节点 → 构成数据出境
  - 路径（如构成出境）：
    → PII 规模巨大（数百万）→ 触发安全评估
    → 如果仅为运维访问且可主张豁免 → 需具体分析

EU 法域判定：
  - 适用 GDPR？→ 是（处理欧盟客户数据）
  - 数据传至新加坡？→ 新加坡无充分性认定（但 EU-新加坡 DPF 在讨论中，暂未生效）
  - 数据传至美国 AWS？→ 如为模型训练，可能无 EU 个人数据
    但如果元数据包含个人数据 → 需要 EU-US DPF or SCC + TIA
  - 印度运维团队远程访问 → 需要 SCC（印度无充分性认定）
  - 路径：SCC（如适用）+ 多份 TIA + Schrems II 措施

US 法域判定：
  - 适用 CPRA？→ 如果 DataFlow 处理加州消费者的个人信息 → 适用
  - 关键问题：DataFlow 是 service provider 还是 business？
    → 对客户数据而言：service provider（按合同处理）
    → 对自己的元数据/运维数据：business（独立决定处理目的）
  - 义务：sp 需签署 DPA + 协助客户 DSR + 审计支持
```

### 4.3 冲突点

```
冲突 1：同一个数据流可能在不同法域被不同定性
  CN："数据出境"的关键是——数据是否离开中国境内
  EU："国际传输"的关键是——数据是否传至非充分性认定第三国
  US：根本没有"跨境传输"概念——只关心是否"出售/共享"

  → 同一个行为（印度运维团队访问上海服务器）：
    CN 法：构成"数据出境"
    EU 法：构成"向第三国传输"
    US 法：可能完全不触发任何义务（如 DPA 覆盖）

冲突 2：角色识别的法域差异
  CN：处理者 vs 控制者的区分主要影响合同义务分配
  EU：处理者 vs 控制者的区分影响责任承担、DPA 要求和直接义务
  US：service provider vs contractor vs third party 的区分影响合同约束方式

  → DataFlow 在 CN 法下是"受托处理者"
  → DataFlow 在 EU 法下是"processor"
  → DataFlow 在 US 法下可能是"service provider"
  → 本质相似但法律要求不同 → 不能简单统一处理

冲突 3：SaaS 平台的"运维访问"是否构成受限制的传输
  CN：如果运维访问可查看原始个人数据 → 构成数据出境
      如果仅访问脱敏/聚合日志 → 可能不构成
  EU：任何第三国可访问个人数据即为国际传输
  US：不关心地理位置，只关心合同约束

冲突 4：三个法域各自要求不同的合同文件
  CN（如触发安全评估）：
    - 与客户签署法律文件：含六项核心条款
  EU：
    - 与客户签署 DPA（GDPR Art.28）
    - 与子处理者签署 SCC 或等效协议
  US（CPRA）：
    - 与客户签署 DPA（含 CPRA 特定条款：prohibit sale/share,
      协助 DSR, 审计权, 删除返还, opt-out/GPC 承接）

  → 需要三份不同的 DPA 还是可以合并？
  → 条款可能存在矛盾（如管辖法律的选择）
```

### 4.4 系统应该如何处理

```text
"您的 SaaS 业务同时受中国、欧盟和美国（加州）三个法域的管辖。
系统按法域分别给出合规分析和建议。

【中国法】— 如印度运维团队可访问上海节点的个人数据
  - 构成数据出境
  - PII 规模可能触发安全评估（数百万人）
  - 建议：（1）确认印度团队是否实际可访问原始个人数据；
```

## 五、场景 3：跨国集团内部 HR 数据 — CN + EU 豁免冲突

### 5.1 事实背景

```text
企业：GlobalCorp（德国注册，全球 50+ 国家运营）
中国子公司：GlobalCorp China（上海，员工 3000 人）

HR 数据流：
  - 中国子公司员工的薪酬、绩效、培训记录 → 传至德国总部 SAP HR 系统
  - 总部全球 HR 分析 → 使用所有国家员工数据
  - IT 支持 → 印度 Infosys 外包团队可访问 SAP 系统运维

HR 数据内容：
  - 员工姓名、身份证号、手机号
  - 薪酬、奖金、银行账号（SPI）
  - 绩效评估、培训记录
  - 员工手册和集体合同（已有中文版，含数据出境条款）
```

### 5.2 各法域判定

```
CN 法域判定：
  - 是否涉及个人信息？→ 是
  - 是否涉及重要数据？→ 否
  - 适用豁免？→ 需判断是否符合"跨境人力资源管理"豁免
    条件：跨国集团内部 + 按依法制定的劳动规章制度和集体合同
  - 员工手册已含数据出境条款 + 集体合同 → 可能满足条件
  - 路径：
    如果员工手册和集体合同证据充分 → HR 豁免
    如果证据不足 → 按 PII 规模判断：3000 人 → 标准合同 or 认证
  - SPI（薪酬银行账号）：3000 人 → 未达到 1 万人安全评估门槛
  → 最终路径：人力资源管理豁免 或 标准合同

EU 法域判定：
  - 数据传至德国总部 → 德国在 EU 内 → 无国际传输问题（GDPR 直接适用）
  - 数据传至印度 Infosys → 印度不属于充分性认定国家
  - 印度团队的访问需 SCC（Module Three: P2P）或 BCR
  - 员工数据属于 HR 数据 → GDPR 下有特殊保护
  - DPIA 要求？→ 3000 人的 HR 数据可能触发

关联问题：
  - GlobalCorp 是否有 BCR？
  - 如果没有 → 对印度传输需 SCC
```

### 5.3 冲突点

```
冲突 1：CN HR 豁免 ≠ EU HR 处理合法
  CN 法：符合 HR 豁免 → 不需要安全评估/标准合同
  EU 法：HR 数据在 GDPR 下是普通个人数据（有特殊保护但不豁免）
         不存在"HR 豁免"概念
  → 企业在中国法下走了豁免路径
  → 但在 GDPR 下仍需满足合法性基础（通常为合同履行或法定义务）
  → 两份合规论证完全独立

冲突 2：CN 标准合同 vs EU BCR/SCC
  如果 GlobalCorp 有 BCR：
    - CN 法：BCR 不是中国法认可的出境路径
    - EU 法：BCR 是合法的集团内传输机制
  → 不能互相替代

冲突 3：印度运维访问
  CN：印度团队访问中国员工数据 → 构成数据出境
  EU：印度团队访问 → 需 SCC 或 BCR
  → 两个法域都认为需要合规，但合规路径不同

冲突 4：员工同意的有效性
  CN：HR 管理场景下通常依赖"依法制定的劳动规章制度"
      不需要单独取得每个员工的同意
  EU：HR 数据处理通常依赖"合同履行"或"法定义务"
      而不是同意（雇佣关系下的同意通常被认为不是自由给出的）
  → 两个法域都不依赖同意，但理由不同
  → 如果在其中一个法域需要同意（如特殊类别数据），
    处理方式完全不同
```

### 5.4 系统应该如何处理

```text
"【中国法】— 人力资源管理豁免
  - 前提条件：员工手册和集体合同中已包含数据出境条款
  - 系统初步判断该豁免可能适用（confidence: MEDIUM）
  - 建议：（1）确认员工手册是否已按民主程序制定；
         （2）确认集体合同是否依法签订；
         （3）留存劳动规章制度和集体合同作为豁免证明材料

【欧盟 GDPR】— 中国员工数据传输不构成"国际传输"（传至德国总部）
  但印度 Infosys 运维团队访问 SAP 系统 → 构成向第三国传输
  - 建议：（1）确认 GlobalCorp 是否已有 BCR；
         （2）如无 BCR，与印度 Infosys 签署 EU SCC（Module Three）；
         （3）完成针对印度的 TIA；
         （4）评估 DPIA 必要性

【并行推进】
  - CN 豁免路径和 EU SCC 是两个独立管线，可并行推进
  - 注意：印度运维团队的合同需同时考虑中国法（构成数据出境）
    和欧盟法（第三国传输）的要求
  - 如果 GlobalCorp 将来在中国申请 BCR，不能替代中国标准合同备案"
```

## 六、场景 4：美国健康科技公司入华 — CN + US 冲突

### 6.1 事实背景

```text
企业：FitLife Inc.（加州注册的健康科技公司）
产品：AI 健身 App

数据流：
  - 中国用户使用 App → 数据存储在上海 AWS 中国区
  - 用户健康数据（心率、睡眠、运动）→ 去标识化后传至加州总部用于 AI 模型训练
  - 营销推荐 → 第三方健康保险合作伙伴 QuickInsure（加州）

数据内容：
  - 用户姓名、手机号、邮箱（PII）
  - 心率、睡眠、运动记录（SPI — health data）
  - GPS 运动路线（SPI — precise geolocation）
  - 中国用户数：约 80 万

组织架构：
  - FitLife Inc. 总部：加州
  - 无中国子公司（通过 App Store 直接面向中国用户）
  - AWS 中国区作为云服务商
```

### 6.2 各法域判定

```
CN 法域判定：
  - 在中国境内处理个人信息？→ 是（App 收集中国用户数据）
  - 向境外提供个人信息？→ 是（去标识化数据传至加州）
  - CIIO？→ 否
  - 重要数据？→ 健康数据汇聚后可能涉及（特别是 80 万人的心率/睡眠数据）
  - PII 出境 80 万人 + SPI 出境 80 万人 → 触发安全评估！
  - 路径：安全评估
  - 额外问题：无中国实体 → 如何申报？如何签署法律文件？
    → 可能需要指定中国境内代表

US 法域（CPRA）判定：
  - 适用 CPRA？→ 是（在加州经营 + 年收入超 2500万美元 +
    处理 >10 万消费者个人信息）
  - 健康数据（心率/睡眠/运动）→ 敏感个人信息
  - 健康数据传给 QuickInsure → 构成"共享"（share）
  - 用户是否有 opt-out？→ 如没有 → HIGH gap
  - 用户是否有 limit SPI？→ 如没有 → HIGH gap

关键冲突预判：
  CN 法要求：安全评估 → 可能限制向境外传输
  US 法：不限制跨境传输 → 但需要 opt-out 和 limit SPI

  更深层的冲突：
  CN 安全评估要求：完整描述数据接收方（QuickInsure）
  US CPRA 要求：用户可 opt-out of sharing with QuickInsure
  → 中国安全评估批准了向 QuickInsure 的传输
  → 但美国用户 opt-out 后，QuickInsure 不应再接收数据
  → 两者不矛盾但需要协同管理
```

### 6.3 冲突点

```
冲突 1：CN "重要数据" vs US "无此概念"
  CN：80 万人的健康数据汇聚 → 可能构成重要数据 → 安全评估
  US：健康数据受 CPRA SPI 保护，但没有"重要数据"概念
  → 同一批数据在两个法域下的风险标签完全不同
  → 中国监管可能认为这是"重要数据"而限制出境
  → 美国监管只关心消费者是否有 opt-out

冲突 2：无中国实体的合规主体问题
  CN：安全评估申报需要"数据处理者"提交
      FitLife 在 CN 没有法律实体
      → 需要指定中国境内代表或设立中国子公司
  US：FitLife 是加州公司 → 直接适用 CPRA
  → 为了 CN 合规，FitLife 可能需要在中国设立法律存在
  → 这个决策超出了系统的建议范围
  → 但系统必须标明"当前无中国实体 → 安全评估申报主体待定"

冲突 3：去标识化在美国可以共享，在中国可能仍受限制
  US：CPRA 不限制去标识化数据的内部使用
      但"共享"（与 QuickInsure）仍需遵守 opt-out
  CN：去标识化数据如果可重识别 → 仍是个人信息 → 仍需安全评估
      "匿名化"数据才不再属于个人信息
  → 同一批"去标识化"数据：
    US 视角：可以用于模型训练，共享需要 opt-out
    CN 视角：如果可重识别，出境仍需安全评估

冲突 4：两套完全不同的整改要求
  CN 要求：
    - 提交安全评估申报（自评估报告 + 法律文件）
    - 可能需数据本地化或限制出境数据范围
    - 与 QuickInsure 签署含六项核心条款的法律文件
  US 要求：
    - 上线 Do Not Sell or Share 链接
    - 上线 Limit Use of SPI 链接
    - 补充 opt-out 机制
    - 修订与 QuickInsure 的合同（CPRA 服务提供商条款）
```

### 8.2 各法域判定

```

US 法域判定：
  - 适用 CPRA？→ 加州 2 万消费者 → 未达到 10 万门槛

  - 义务：隐私政策、opt-out、limit SPI、DPA 与加州办事处/服务提供商
```

### 8.3 冲突点

```
冲突 1：CN 数据本地化 vs 全球研发需求
  CN：车辆重要数据 → 境内存储原则
      向慕尼黑传输 → 需安全评估批准
  EU：ADAS 算法训练需要实际驾驶数据 → 需要从中国传至慕尼黑
  → CN 批准可能附条件（如限制可出境数据范围、去标识化要求）
  → 可能影响 EU 研发中心的算法训练效果
  → 两法域目标直接冲突

冲突 2：对"敏感数据"的不同定义影响合规策略
  CN：行踪轨迹 = 敏感个人信息
      1 万人以上 → 安全评估
  EU：位置数据属于特殊类别数据的前提是"揭示种族、政治观点、

      纯粹的驾驶行为轨迹通常不属于特殊类别

  US：precise geolocation = SPI
      需要 limit SPI 入口
  → 同一批 GPS 数据：
    CN：高风险（敏感个人信息 + 可能重要数据）
    EU：中等风险（大规模处理 + 需 DPIA）
    US：需提供 limit SPI + opt-out
  → 三个法域对同一数据的风险标签和合规要求完全不同

冲突 3：管辖与执法权

  EU SCC 签署 + TIA → 受 EU 监管机构（如德国 DPA）监督
  US CPRA → 加州 CPPA 执法

  → 如果出现数据泄露：
    CN 网信办可能处罚
    德国 DPA 可能处罚（GDPR 罚款可达全球营收 4%）
    CPPA 可能处罚
  → 三个监管机构独立行动、独立处罚
  → 企业的合规漏洞可能在三个法域同时暴雷

冲突 4：整改建议可能互相矛盾
  CN 整改建议：限制出境数据范围，优先境内存储
  EU 整改建议：签署 SCC，完成 TIA
  US 整改建议：上线 opt-out 和 limit SPI

  → 这些建议在操作层面没有直接矛盾
  → 但资源分配和优先级会有冲突：
    CN 安全评估是第一优先级（不通过不能出境）
    EU SCC 也需要推进（慕尼黑研发中心依赖数据）
    US CPRA 优先级相对低（2 万加州用户规模有限）
```

### 8.4 系统应该如何处理

```text
"您的业务同时触发中国、欧盟和美国（加州）三法域的合规义务。
鉴于义务范围广、互相独立，系统建议按以下优先级并行推进：

【第一优先级：中国法 — 安全评估申报】BLOCKER
  - 触发原因：敏感个人信息（行踪轨迹）出境超1万人 + 可能涉及重要数据
  - 路径：安全评估
  - 关键行动：
    1. 确认是否被认定为 CIIO（需联系行业主管部门）
    2. 梳理车辆数据中哪些属于"重要数据"（对照汽车数据安全管理规定）
    3. 启动安全评估自评估报告准备
    4. 与慕尼黑子公司和加州办事处签署含六项核心条款的法律文件
  - 预计周期：3-6个月（含材料准备和审批等待）

【第二优先级：欧盟 GDPR — SCC + TIA】HIGH
  - 触发原因：向中国（非充分性国家）传输欧盟车主数据
  - 路径：SCC + TIA + Schrems II
  - 关键行动：
    1. GreenAuto 北京总部与慕尼黑子公司签署 EU SCC
    2. 完成针对中国的 TIA（评估中国数据安全法律环境）
    3. 实施 Schrems II 补充措施（端到端加密）
    4. 完成车辆数据处理 DPIA
  - 预计周期：4-8周

【第三优先级：美国 CPRA — 差距评估与整改】MEDIUM
  - 触发原因：年收入超2500万美元 + 处理加州消费者SPI（精确位置）
  - 关键行动：
    1. 更新隐私政策以覆盖 CPRA 要求
    2. 上线 Do Not Sell/Share 和 Limit SPI 链接
    3. 与加州办事处签署 DPA（CPRA 服务提供商条款）
  - 预计周期：短期可完成

【综合提示】
  - 整改措施本身不矛盾，但在数据流向管控上需协同设计
  - 建议建立统一的数据分类分级标准（覆盖三个法域的最高要求）
  - 建议指定跨法域数据合规负责人，协调三条管线的推进节奏"
```

## 九、冲突类型学：四类常见冲突模式

从以上 6 个场景中，可以归纳出四类跨法域冲突模式：

### 类型 A：义务叠加（同一行为触发多法域义务）

```text
定义：同一个数据处理行为在多个法域同时触发合规义务。
特征：合规义务不矛盾，但需要同时满足。
例子：场景 1——中国电商同时需要安全评估（CN）和 SCC（EU）

处理策略：
  - 各法域分别评估，输出"逐法域合规路线图"
  - 标注义务之间的依赖关系（如：安全评估通过后 SCC 才能执行）
  - 如果两个法域都要求签署法律文件，分析是否可以合并为一份
```

### 类型 B：路径排斥（同一行为在不同法域走不同路径）

```text
定义：同一数据处理方式在法域 A 下合法，在法域 B 下不合法（或需要额外条件）。
特征：需要"就高不就低"——满足最严格法域的要求。
例子：场景 3——CN HR 豁免可行，但 EU 仍需 SCC/TIA

处理策略：
  - 明确指出各法域下的路径差异
  - 推荐以满足最严格法域的要求为基线
  - 如果最严格法域的要求与其他法域冲突（如数据本地化），标注为"需企业决策"
```

### 类型 C：定义冲突（同一术语在不同法域下含义不同）

```text
定义：法域 A 和法域 B 使用相同或相似的术语，但法律含义不同。
特征：容易误导企业和开发者。
例子：
  - "标准合同/SCC"在 CN 法和 EU 法下指向完全不同的法律文件
  - "敏感个人信息"在 CN、EU、US 三法域的范围不完全重叠
  - "控制者/处理者"在 CN 和 EU 下的责任分配存在差异
  - "匿名化"在不同法域下的法律标准不同

处理策略：
  - 系统内部使用法域前缀区分术语（如 CN_standard_contract vs EU_SCC）
  - 面向用户的报告中不使用简称，始终写明全称和法域
  - 建立术语对照表
```

### 类型 D：管辖冲突（同一合同的管辖条款不能同时满足多法域）

```text
定义：法域 A 要求争议解决在 A 地，法域 B 要求争议解决在 B 地。
特征：无法同时满足，必须做出选择（通常是商业决策而非技术判断）。
例子：场景 1——CN 法律文件要求中国法院管辖，EU SCC 要求 EU 法院管辖

处理策略：
  - 系统不替企业做选择
  - 明确指出冲突
  - 列出常见的商业解决方案供参考（如分层争议解决条款）
  - 标注"该事项建议征求专业法律意见"
```

## 十、跨法域协调器的设计约束

### 10.1 协调器的角色定位

```text
跨法域协调器 (Cross-Jurisdiction Orchestrator)：

职责：
  ✅ 识别同一数据出境行为涉及的法域
  ✅ 将同一个 FactPack 分发给各法域引擎
  ✅ 收集各法域的独立结论
  ✅ 检测冲突（按上述四种类型分类）
  ✅ 生成"逐法域合规路线图"

不负责：
  ❌ 不合并各法域的结论为一个结论
     （三个法域的结论应该独立展示）
  ❌ 不替企业选择合规路径
     （系统提供选项和影响分析，企业决策）
  ❌ 不自动消解矛盾
     （管辖冲突是企业商业决策，系统不能替代）
```

### 10.2 协调器的输入输出

```text
输入：
  - FactPack（跨法域共享的同一套事实）
  - 法域列表：["CN", "EU", "US"]

处理：
  for each jurisdiction in ["CN", "EU", "US"]:
    1. 过滤 FactPack 中与该法域相关的事实
    2. 检查是否有对应的模块（diagnosis/scc_eu/cpra）
    3. 如果有 → 运行该模块的分析
    4. 如果无 → 标记 "该法域暂不支持自动分析"

  收集各法域结果后：
    1. 提取每个法域的 recommended_path
    2. 提取每个法域的 blocking_issues
    3. 检测冲突类型 A/B/C/D
    4. 按优先级排序整改建议

输出：
  CrossJurisdictionReport
    ├── jurisdictions_triggered: ["CN", "EU", "US"]
    ├── per_jurisdiction: [
    │     { jurisdiction: "CN", path: "security_assessment", ... },
    │     { jurisdiction: "EU", path: "scc_eu", ... },
    │     { jurisdiction: "US", path: "cpra_gap", ... },
    │   ]
    ├── conflicts: [
    │     { type: "path_conflict", ... },
    │     { type: "terminology_conflict", ... },
    │     { type: "jurisdiction_conflict", ... },
    │   ]
    ├── unified_remediation_roadmap: [
    │     { priority: "P0", jurisdiction: "CN", action: "..." },
    │     { priority: "P0", jurisdiction: "EU", action: "..." },
    │     { priority: "P2", jurisdiction: "US", action: "..." },
    │   ]
    └── matters_requiring_legal_advice: [...]
```

### 10.3 当前实现的差距

```text
现状：
  - 每个模块可以独立运行
  - 但没有任何层来识别和协调跨模块冲突
  - 没有统一的 FactPack 分发机制
  - 没有冲突检测逻辑

需要建设的：
  1. CrossJurisdictionOrchestrator 类
  2. FactPack 的分发和过滤机制
  3. 冲突检测规则（按四种类型）
  4. 统一的 CrossJurisdictionReport 输出模型
  5. 前端展示：逐法域合规路线图（不是单一结论）

优先级：P1（等各法域模块的 Agent 接入稳定后实现）
```
