## 一、前端整体架构

### 1.1 技术选型

| 层级 | 技术 | 选择原因 |
|------|------|---------|
| 框架 | React 18 | 成熟稳定的组件化 UI 框架 |
| 语言 | TypeScript 5（严格模式） | 法律数据字段多，必须有编译期检查防止字段名拼写错误 |
| 构建 | Vite 5 | 极快的开发热更新 |
| 样式 | Tailwind CSS 3 | 原子化 CSS，适合快速迭代 UI |
| 路由 | React Router 6 | 标准 SPA 路由方案 |
| 富文本 | react-markdown + remark-gfm | 报告以 Markdown 格式存储，前端实时渲染 |
| 状态管理 | React Context + useReducer | 无需引入 Redux 等外部库，应用状态量可控 |

前端开发时，Vite 将 `/api` 请求代理到本地的 Python 后端（`localhost:8000`），所以前端开发者不需要单独配置后端地址。

### 1.2 四大设计原则

**原则一：中间产物可见**。后端的每一步（事实提取、问题识别、证据构建）都有对应的前端标签页展示。用户不是只看最终报告，而是可以追溯报告的每一个判断依据。

**原则二：实时反馈**。模块运行时，前端通过 WebSocket（降级为 HTTP 轮询）实时显示后端执行到哪一步。没有"转圈等 2 分钟"的黑箱体验。

**原则三：三栏工作台**。模拟 IDE 的布局——左侧文件管理、中间编辑区、右侧辅助面板，让合规工作像写代码一样有条理。

**原则四：状态持久化**。用户在任务空间中的所有操作（新建任务、运行模块、折叠面板、展开产物）都会自动保存到后端和浏览器本地，刷新页面后状态完全恢复。

---

### 1.3 全局状态管理：一份数据，多处响应

前端没有使用 Redux 或 Zustand 这类外部状态库，而是用 React 原生的 `useReducer` + Context 实现全局状态管理。

整个应用的所有状态都在一个大的状态对象中，通过一个 reducer 函数来修改。这个设计类似于 Redux 的模式，但更轻量。

#### 状态包含哪些数据

```
全局状态
├── 任务空间列表          <- 用户创建的所有合规项目
├── 模块运行记录          <- 每次点击"运行"的历史（含结果）
├── 输出产物清单          <- 运行产生的所有文件
├── 证据链命中记录        <- 法规检索的命中结果
├── 一致性问题列表        <- 系统发现的所有问题
├── 运行会话              <- 当前正在执行的运行（含实时阶段）
├── 面板布局状态          <- 左侧栏多宽、是否折叠等
├── 系统消息              <- 应用内通知
└── 引导覆盖层状态        <- 新手引导到了第几步
```

#### 状态的三个来源

1. **浏览器本地存储**：页面刷新时，先从 `localStorage` 恢复状态
2. **后端 API 同步**：页面加载时，从后端拉取最新的任务列表、报告列表、工作区快照
3. **用户操作触发**：创建任务、点击运行、折叠面板等操作通过 dispatch 修改状态

#### 状态的持久化

每次状态变更后，系统会以 500ms 的防抖延迟（即连续多次变更只保存最后一次）将状态自动同步到后端。这样用户换一台电脑登录，任务空间依然完整。

#### 为什么不用 Redux/Zustand？

因为这个应用的状态量不大（几十个任务、几百个文件），用 React 原生方案完全够用。引入外部状态库反而增加了依赖和维护成本。

---

### 1.4 路由与页面组织

整个应用是一个单页面应用（SPA），所有页面切换不刷新浏览器。

```
访问路径                   → 渲染哪个页面          → 是否需要登录
/                         → 品牌首页              → 否
/login                    → 登录页                → 否
/register                 → 注册页                → 否
/jurisdictions/:code      → 法域枢纽页            → 否
/tasks                    → 任务空间页            → 是
/workspace                → 工作台（自动跳最近）    → 是
/workspace/:taskId        → 工作台（指定任务）      → 是
/reports                  → 报告中心              → 是
/evidence                 → 证据中心              → 是
/knowledge/laws/:sourceId → 法律查看器             → 是
/settings                 → 系统设置              → 是
/profile                  → 个人中心              → 是
```

需要登录的页面会被 `ProtectedRoute` 组件保护——未登录用户访问时自动跳转到登录页，登录成功后自动跳回。

#### 全局监控

无论用户在哪个页面，前端都在后台维持两项全局监控：

1. **后端健康检查**：每 30 秒 ping 一次后端，如果后端挂了，在页面顶部显示红色横幅提醒
2. **异步任务轮询**：每 5 秒检查一次是否有正在后台运行的模块任务，如果有且已完成，自动将结果吸收到全局状态中

## 二、核心页面与用户旅程

### 2.1 首页：从品牌认知到行动入口

首页是一张完整的品牌落地页，不只是一个"点击进入"的跳板。

**内容结构**：

- **Hero 区域**：大字标题"DataComply Flow"，副标题"跨境数据合规 · 数规通"，主行动号召按钮"开始合规"
- **痛点展示**：四个痛点卡——路径不清、文书繁重、法条碎片、审查盲区
- **四步时间线**：诊断 → 起草 → 审查 → 整改，每步配一句话说明
- **三法域卡片**：中国 / 欧盟 / 美国，引导用户按法域进入
- **底部 CTA**：再次引导登录

未登录用户点击"开始合规"会跳转登录页；已登录用户直接进入任务空间。

### 2.2 任务空间页：管理所有合规工作

任务空间是用户的主要入口。进入后看到的是所有已创建的合规项目列表。

**页面布局**：

```
顶部：
  [搜索框] [法域筛选: CN/EU/US/全部]          [+ 快速创建]

中间：
  法域快速创建卡片（CN/EU/US 各一块，每块列出该法域的可用模块）
  
  任务列表：
  ┌─────────────────────────────────────────────────────┐
  │ 任务名称        │  最近运行状态  │  法域  │  操作     │
  ├─────────────────────────────────────────────────────┤
  │ 星辰支付-安全评估 │  ✓ 已完成     │  CN   │ 进入 删除 │
  │ XX集团-SCC审查   │  ⏳ 运行中    │  CN   │ 进入 删除 │
  │ YY公司-CPRA合规  │  ✗ 失败       │  US   │ 进入 删除 │
  └─────────────────────────────────────────────────────┘
```

**核心操作**：

- **新建任务**：点击法域卡片 → 弹出配置弹窗 → 填写任务名称 + 选择模板 → 创建
- **进入任务**：点击"进入" → 跳转到 `/workspace/:taskId`
- **重命名**：双击任务名称即可编辑
- **删除**：点击删除按钮 + 确认弹窗（会同时清空后端关联的所有报告文件）

## 三、工作台：三栏布局的设计哲学

### 3.1 为什么要三栏

传统的"表单 + 下载"模式有一个致命问题：用户提交后只能等着，看不到中间过程。系统到底检索了哪些法规？发现了哪些问题？报告中的每一句话依据是什么？这些都是黑箱。

三栏布局的灵感来自 IDE（集成开发环境），它把合规工作拆成三种并行活动：

```
左侧：管理材料        中间：运行和审查产品      右侧：AI 辅助
我在处理什么文件？     系统产出了什么？          AI 对当前任务有什么建议？
我有哪些中间产物？     报告哪句话有问题？        当前步骤的含义是什么？
                       我现在该看哪个标签页？
```

### 3.2 左侧栏：证据架（ResourcePanel）

左侧栏是一个**分层文件树**，按两部分组织：

**输入部分**（用户提交了什么）：
- 表单数据：用户填写的结构化问卷内容（可展开查看具体字段）
- 上传文件：用户上传的 PDF/Word/图片（显示文件名和解析状态）

**输出部分**（系统产出了什么）：
- 中间产物文件：事实清单 JSON、问题清单 JSON、证据链 JSON、材料清单 XLSX
- 最终报告：Markdown 报告、Word 报告、ZIP 打包
- 可追溯记录：每个流水线步骤的执行快照

用户点击任何一个文件，中央区域就会打开一个新的资源标签页，展示文件内容。例如点击"问题清单 JSON"，中央区域会展示一张结构化的表格，每行一个问题。

**左侧栏的交互特性**：
- 可折叠：点击面板边缘的小箭头收起，腾出更多中央空间
- 可拖拽调整宽度：鼠标拖动面板右边界可改变宽度
- 状态持久化：折叠状态和宽度会保存，刷新不丢失
- 任务摘要卡片：顶部常驻当前任务的基本信息

### 3.3 中央区域：起草工作区

中央区域是用户停留时间最长的地方。它是一个**多标签页系统**，不同的标签页对应不同的工作阶段：

| 标签页 | 什么时候用 | 展示什么 |
|--------|----------|---------|
| **运行**（默认） | 刚进入任务空间，准备运行模块 | 完整的表单界面，填写业务信息后点击运行 |
| **画布** | 运行完成后或运行中 | 5 步工作流进度 + 指标统计 |
| **报告** | 报告生成后 | Markdown 报告渲染（带可点击引用） |
| **时间线** | 想看系统每一步做了什么 | 实时执行轨迹，每步可展开 |
| **终端** | 调试或查看原始日志 | 聚合的运行日志文本 |
| **文档** | 不确定这个模块是做什么的 | 模块说明 + 输入/输出提示 |
| **资源标签页** | 从左侧栏点击了某个文件 | 文件内容渲染（JSON 表格、Markdown 预览、文本预览） |

**标签页和左侧栏的联动**：

当用户在左侧栏点击某个输出文件时，中央区域动态创建一个新的资源标签页。例如点击"issue_list.xlsx"，标签页中显示一个只读的表格，列包括：问题编号、标题、严重度、分类、关联法规、建议措施。

关闭标签页后，不会删除文件——文件仍然在左侧栏的文件树中，随时可以再打开。

### 3.4 右侧栏：实时助手（AssistantPanel）

右侧栏是一个 **AI Copilot 对话面板**，但它不是普通的聊天机器人。

**与普通聊天机器人的区别**：

1. **上下文感知**：Copilot 知道当前用户在哪个任务空间、运行了哪个模块、当前处于哪个步骤。用户不需要向 AI 解释"我在做什么"。
2. **实时状态跟随**：当中央区域的模块开始运行时，Copilot 会实时显示"正在提取事实..."、"正在检索法规..."等进度。
3. **嵌入执行轨迹**：Copilot 面板内嵌了一个执行轨迹视图，显示当前运行的每一步。

**Copilot 的三个信息来源**：
- 用户当前的任务空间（企业名称、模块类型、法域）
- 当前运行的实时状态（执行到第几步、产出了什么）
- 用户输入的对话消息

用户可以向 Copilot 提问，如"这个问题的法规依据是什么？""为什么推荐安全评估路径？""我还需要补充什么材料？"

### 3.5 三栏协作的完整流程

以一个典型场景串联三栏的协作：

```
用户进入工作台
        │
左侧栏：选中任务"星辰支付-安全评估"
        │
中央区域：默认显示"运行"标签页
        │ 用户填写企业信息、数据清单等
        │ 点击"开始生成"
        │
中央区域：自动切换到"时间线"标签页
        │ 显示 16 步执行进度
        │
右侧栏：同时显示实时进度
        │"正在提取企业画像..." ✓
        │"正在检索法规..." ⏳
        │
中央区域：运行完成，自动切换到"报告"标签页
        │ 展示 Markdown 报告
        │
左侧栏：文件树自动更新
        │ 出现新文件：报告.md、问题清单.json、证据链.json...
        │
用户点击左侧栏"问题清单.json"
        │
中央区域：新标签页"问题清单"
        │ 表格：6行问题，每行可展开
        │
用户点击某个问题的"证据编号"
        │
中央区域：跳转到"证据链"标签页
        │ 高亮对应的证据项

整个过程，三栏信息始终互补，不冗余。
```

## 四、模块运行：从填表到出报告

### 4.1 ModuleRunPanel：12个模块的统一运行面板

`ModuleRunPanel` 是系统中最复杂的组件之一，它负责为 12 个合规产品模块各自提供专属的表单界面。

**每个模块的表单包含**：

- 基础字段：企业名称、行业等（跨模块通用）
- 专属字段：每个模块特有的业务字段。例如：
  - 安全自评估：CIIO 状态、个人信息数量、数据资产清单、接收方信息等
  - 标准合同审查：上传合同文件、合同摘要、合法性基础等
  - CPRA 合规：业务模型描述、隐私政策描述、供应商列表等
- 文件上传：支持拖拽上传 PDF/Word/图片
- 运行模式选择：同步 / 异步

**开发者便利功能**：

系统内置了一套"开发者预设"——一键填充测试数据。例如选择"金融CIIO场景"，自动填入"星辰支付科技、CIIO=是、PII=80万、SPI=5万、金融科技行业、向新加坡传输"等完整预设。

还有一个完整的测试用例库，覆盖了 12 个模块的 30+ 个典型场景（正常场景、缺失材料场景、边缘场景等），方便开发者和法务人员进行功能验证。

### 4.2 同步与异步两种运行模式

**同步模式**（默认）：

```
前端发送请求 → 等待后端完整执行完成 → 收到完整结果 → 一次性更新界面
```

适用于生成耗时较短（< 10 秒）的模块，如路径诊断。

**异步模式**：

```
前端发送请求 → 后端立刻返回"已接受" + 任务编号
    ↓
前端开始轮询（每 1.5 秒问一次"好了吗？"）
    ↓
后端完成 → 前端收到最终状态 + 完整结果
```

适用于生成耗时较长（> 30 秒）的模块，如完整的安全自评估报告（需要调用大模型生成 8 个章节）。

**异步模式的轮询有两个来源**：

1. **页面内轮询**：当前工作区页面内的定时器
2. **全局轮询**：一个全局组件每 5 秒扫描所有"运行中"的任务——即使用户切换到其他页面，后台任务也不会被遗忘，完成后结果会被自动吸收

### 4.3 实时进度推送：SSE + HTTP 轮询双通道

**主要通道：SSE（Server-Sent Events，服务器推送事件）**

SSE 是一种让服务器主动向浏览器推送消息的技术。前端和后端之间建立一个长连接：

```
前端: 连接到 /api/v1/events/task/{任务编号}/stream
后端: 每当流水线完成一步，就推送一条消息
      消息格式：{ "事件类型": "stage_done", "阶段名": "facts_built", "摘要": "事实清单构建完成" }
前端: 收到消息 → 更新执行时间线 → 切换标签页到时间线 → 用户看到实时进度
```

**降级通道：HTTP 轮询**

SSE 在某些网络环境（如企业代理）下可能不可用。前端有自动降级机制：

```
如果 SSE 连接成功但 3 秒内没收到任何消息：
    → 自动启动 HTTP 轮询（每 1.5 秒问一次）
    → 同时继续尝试 SSE 连接
    → 哪个先返回有效数据就用哪个

如果 SSE 连接失败：
    → 直接切换到 HTTP 轮询
```

这种双通道设计保证了在不同的网络环境下都能获得实时反馈。

### 4.4 运行完成后的结果吸收

运行完成后，前端不是简单地把结果"展示"出来，而是把结果**拆解吸收**到全局状态中：

```
后端返回的完整响应
    │
    ├── 报告文件 → 添加到"输出产物清单"
    │              左侧栏文件树自动更新
    │
    ├── 中间产物（facts/issues/evidence）→ 添加到对应的状态列表
    │              中央区域的时间线可展开每步的详细内容
    │
    ├── 一致性问题 → 添加到"一致性问题列表"
    │              中央区域的"画布"标签页更新风险计数
    │
    ├── 法规引用 → 添加到"证据链命中记录"
    │              右侧栏 Copilot 可引用这些法规
    │
    └── 执行轨迹 → 添加到"运行会话"历史
                   中央区域的"时间线"标签页可回放
```

这种"拆解吸收"的设计意味着：用户运行了 5 次模块后，不仅能看到 5 份报告，还能看到 5 次的完整执行轨迹、所有中间产物的历史版本、所有一致性问题的汇总。

## 五、中间产物展示：让黑箱透明化

### 5.1 AssessmentIntermediatesPanel：10个标签页

这是后端"中间产物驱动架构"在前端的对应实现。当安全自评估模块运行完成后，中间产物面板有 10 个标签页：

| 标签页 | 数据来源 | 展示形式 |
|--------|---------|---------|
| **事实识别** | 后端返回的 facts JSON | 表格：编号、来源类型、字段路径、值、置信度、能否对外断言 |
| **路径判断** | 后端返回的 diagnosis JSON | 文本卡片：推荐路径、风险等级、判定理由 |
| **问题清单** | 后端返回的 issues JSON | 表格：问题编号、标题、严重度（颜色标记）、类别、关联事实、建议措施 |

| **证据链** | 后端返回的 evidence JSON | 卡片列表：每条证据嵌套展示主张、法规依据、结论、置信度 |

## 六、引用展示与可追溯交互

### 6.1 引用在正文中的渲染方式

后端生成的报告正文中，法规引用以特定标记格式存在：

```
后端的格式：
  依据《数据出境安全评估办法》第四条第（一）项的规定...
  使用 {{CIT-REG-001}} 标记

前端渲染后：
  依据《数据出境安全评估办法》第四条第（一）项[1]的规定...
  其中 [1] 是一个可点击的蓝色小标签
```

前端有一个专门的 Markdown 渲染组件，它在渲染报告正文时做了三件事：

1. **识别引用块**：识别 `【依据：...】` 格式的引用声明
2. **识别脚注**：识别 `[1]`、`[2]` 等脚注编号
3. **高亮风险信号**：识别并加粗显示风险等级关键词（如"高风险""阻断""需补充"）

### 6.2 悬浮预览与点击跳转

当用户把鼠标悬停在正文中的引用标记（如 `[1]`）上时，会自动弹出一个**轻量预览卡片**：

```
┌─────────────────────────────────┐
│ 《数据出境安全评估办法》          │← 来源标题
│ 第四条第（一）项                  │← 条文号
│                                 │
│ "数据处理者向境外提供数据，有     │← 核心摘录
│  下列情形之一的，应当...申报     │
│  数据出境安全评估..."           │
│                                 │
│ 来源类型：法律条文               │← 来源类型
│ 约束力：强制性规定               │← 权威等级
│ 用途：支撑路径判断结论           │← 用途说明
└─────────────────────────────────┘
```

如果用户**点击**引用标记，系统会尝试打开知识库中对应的法规原文页面：

```
点击 [1]
  → 如果知识库中有该法规的条文级索引
    → 新标签页打开 /knowledge/laws/{来源编号}?article=第四条
    → 自动滚动到该条文位置并高亮
  → 如果知识库中只有来源级页面
    → 新标签页打开该法规的详情页
  → 如果知识库中完全没有
    → 在当前页面打开一个侧边抽屉，展示引用的原文摘录
```

这就是业务文档中要求的"悬浮看摘要，点击看原文"。

### 6.3 引用来源卡片

在证据中心页面，每条法规来源都有一个详情卡片，展示：

- 标题、发布机构、生效日期、最近修订日期
- 法域、权威等级（法律/行政法规/部门规章/国家标准/官方指南）
- 约束力（强制性/推荐性/参考性）
- 允许的使用场景（对外报告/内部审查/结构控制等）
- 关联的模块列表（哪些业务模块会用到这条法规）
- 被引用次数（在所有报告中被引用过多少次）

## 七、国际化与多语言

系统支持中文和英文双语界面切换。

**实现方式**：不是使用第三方 i18n 库（如 react-i18next），而是手工维护了一套约 534 条翻译消息的字典。每条消息有一个唯一的键名，并提供中英文两个版本。

```
示例键值对：
  "nav.tasks"    → { zh: "任务空间", en: "Tasks" }
  "nav.workspace" → { zh: "工作台", en: "Workspace" }
  "run.start"    → { zh: "开始生成", en: "Generate" }
```

**语言检测**：页面首次加载时，按以下优先级检测：
1. 浏览器 `localStorage` 中保存的语言偏好
2. 浏览器的语言设置（`navigator.language`）
3. 默认中文

**切换方式**：顶部导航栏右侧有一个语言切换按钮，点击即可在中英文之间切换。切换后所有界面文字即时更新。
