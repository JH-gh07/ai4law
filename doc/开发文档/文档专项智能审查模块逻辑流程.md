# 文档专项智能审查模块 — 逻辑流程文档

## 一、模块概述

文档专项智能审查（`review` 模块）是一个**增强型 8 阶段合规审查流水线**，对上传的法律文档（隐私政策、标准合同、数据处理协议等）进行自动化合规审查。系统采用 **DSL 规则引擎 + LLM 深度审查 + 专项审查器** 三层审查架构，支持中英文文档，覆盖 23 种条款类型，输出 9 节专业审查报告。

**核心路径**：`backend/services/review_service/`（服务层）+ `backend/api/review.py`（API 层，10 个端点）+ `backend/schemas/review.py`（数据模型）

## 三、数据模型层次

### 3.1 核心枚举

## 四、8 阶段增强流水线详细逻辑

### Stage 0：PREPARING（文档理解，0-10%）

**目的**：识别文档类型、提取业务场景上下文、解析文档结构。

**子步骤**：

1. **StructuredDocumentParser 解析**
   - 支持 DOCX（段落 + 表格结构）、PDF（分页）、纯文本
   - 提取附录字段（SCC 附件 I 的 14 种字段类型：处理目的、个人信息规模、境外接收方等）
   - 输出 `StructuredDocument`（含 plain_text、pages、appendix_fields、tables）

2. **DocumentClassifier 分类**
   - 策略优先级：用户指定类型（置信度 ≥ 0.5 时确认） → 关键词启发式（4 类信号：隐私政策/SCC/DPA/其他） → LLM 轻量分类
   - 同时检测法域（cn/eu/us）：基于中英文关键词 + 文档类型推断
   - 输出 `DocumentClassification`（document_type、confidence、evidence、detected_jurisdiction）

3. **ScenarioExtractor 场景提取**
   - 正则启发式提取：公司名称、数据类别（12 类）、敏感数据（7 类）、跨境指标（6 类）、处理目的、接收方国家
   - 不确定事实检测（4 种条件性表述模式）
   - **ScenarioGraphBuilder**：构建 结构化参与者-数据流图（actors、data_flows、legal_grounds、cross_border_indicators）
   - 合并用户提供的 `ReviewScenarioContext`

**输出**：
- `document_type`（确定的文档类型）
- `scenario_ctx`（ReviewScenarioContext，含业务事实）
- `structured_docs`（结构化文档集合）
- `detected_jurisdiction`（检测到的法域）

---

### Stage 1：SEGMENTING（条款切分，10-25%）

**目的**：将文档全文切分为独立的条款单元。

**ClauseSegmenter 核心逻辑**：

1. **粗粒度切分**
   - 中文：正则 `第X条` / `X.` / `X、` / `附录X`
   - 英文：正则 `Article X` / `Section X` / `Clause X` / `Appendix X`
   - 自动检测语言倾向（统计前 4000 字符中的中/英文标记数）

2. **子条款切分**
   - 对 ≥ 200 字符的条款，按 `；` / `;` 拆分为子条款
   - 仅当每个子部分 ≥ 60 字符时执行

3. **结构信息提取**
   - 层级提取：章/节/条/附录（8 种模式）
   - 条款编号提取（6 种模式）
   - 表格内容检测（Markdown 表格、TSV）
   - 附录内容检测
   - 结构噪声过滤（11 种模式：页码、签名块、分隔符、URL、邮箱等）

4. **ObligationSplitter 义务拆分**（后处理）
   - 对 ≥ 50 字符且含 `；`/`。` 的条款，拆分为独立义务单元
   - 确保每项义务可独立审查

**输出**：`list[Clause]`，每个 clause 含完整结构元数据

---

### Stage 2：CLASSIFYING（条款分类，25-45%）

**目的**：将每个条款归类到 23 种条款类型中的一种或多种。

**ClauseClassifier 核心逻辑**：

1. **关键词匹配（主要路径）**
   - 遍历所有条款类型，统计每种类型在条款文本中的关键词命中数
   - 主类型 = 命中数最多的类型
   - 次类型 = 命中数 ≥ 2 的其他类型
   - 置信度公式：`min(0.4 + matched/total × 0.5, 0.95)`

2. **交叉标签检测**
   - 通过 `multi_label_keywords` 映射检测关联类型
   - 例如：跨境传输条款可能同时触发安全措施标签

3. **LLM 兜底分类**
   - 无关键词匹配且条款 ≥ 200 字符时，调用 LLM 判断类型
   - system prompt："中国数据合规专家"，输出类型枚举值

4. **OTHER 类型默认**
   - 最终兜底为 OTHER，置信度 0.3

**输出**：`list[ClassifiedClause]`，每个含主类型、次类型、匹配关键词、置信度

---

### Stage 3：MISSING_CHECK（全局缺失检测，45-55%）

**目的**：检测文档中完全缺失的必要条款类型。

**MissingItemChecker 核心逻辑**：

1. **静态需求检查**
   - 从规则手册获取该文档类型的 `required_clause_types`（必须）和 `recommended_clause_types`（建议）
   - 检查已分类条款（主类型 + 次类型，置信度 ≥ 0.3）的覆盖情况

2. **条件性需求检查**（场景驱动）
   - 根据 `conditional_required` 规则动态增加必需类型：
     - `has_cross_border=True` → 增加跨境传输、政府访问、补充措施
     - `has_sensitive_pi=True` → 增加敏感个人信息、单独同意
     - `has_minor_data=True` → 增加未成年人保护
     - `has_third_party_sharing=True` → 增加第三方共享
     - `has_entrusted_processing=True` → 增加委托处理

3. **严重程度分级**
   - 完全缺失 → 配置的 severity 或默认 HIGH
   - 仅在次类型中覆盖 → MEDIUM
   - 建议类型缺失 → LOW

**输出**：`list[MissingItem]`，每个含法规依据（citation_strings）和修改建议

---

### Stage 4：REVIEWING（条款审查，55-80%）

这是流水线的核心阶段，采用**三层审查架构**。

#### 4.1 LLM 候选条款选择

**`_select_llm_candidates()` 优先级机制**：

| 优先级分数 | 条件 |
|-----------|------|
| 12 | 含高风险短语（"香港法院"/"责任总额不超过"/"暂缓处理"等 10 种） |
| 10 | HIGH_PRIORITY_TYPES（跨境传输/敏感个人信息/未成年人等） |
| 5 | MEDIUM_PRIORITY_TYPES + 文本 ≥ 120 字符 |
| 3 | review_depth=deep（所有条款） |
| 1 | 其他 |

按优先级降序选取，受 `max_llm_clauses`（默认 20）上限约束。

#### 4.2 ClauseReviewer 审查

对每个可审查条款（非噪声、非空），依次执行：

**层次一：DSL 规则检查（始终执行）**

- 从规则手册加载 `dsl_checks`（正则模式匹配）
- 支持正向匹配（pattern）和反向匹配（pattern_missing）
- 也检查次类型的 DSL 规则
- 生成 `DSL-{check_id}-{uuid}` 格式的问题，review_method=RULE

**层次一点五：标准条款差异检查**

- `StandardClauseLocator`：从 RAG 检索到的标准条款候选中，按类型 + 文本相似度匹配最相关标准条款
- `StandardClauseDiffer`：对比当前条款与标准条款，检测：
  - **义务缺失**（missing_obligations）：标准条款要求的义务未出现
  - **义务弱化**（weakened_obligations）：关键义务被酌情化/上限化
  - **高风险修改**（added_risky_modifications）：含"以本协议为准""责任总额不超过"等 9 种风险表述
- 生成 `STD-MISS-`/`STD-WEAK-`/`STD-RISK-` 前缀的问题

**层次二：专项审查器（按文档类型）**

| 文档类型 | 审查器 | 检查内容 |
|---------|--------|---------|
| privacy_policy | PrivacyPolicyReviewer | 隐私政策特有 DSL 检查 |
| scc_contract | SccContractReviewer | SCC 正文 + 附录完整性检查 |
| dpa | DpaReviewer | 委托处理协议特有检查 |
| other | DataSecurityAgreementReviewer | 数据安全协议通用检查 |

**层次三：LLM 深度审查**

- 仅对入选 `llm_clause_ids` 的条款执行
- System prompt："中国个人信息保护合规资深律师"
- 输入：条款类型 + 文本 + 法规参考 + 业务场景
- 输出：结构化 JSON 数组（severity、title、problem_type、risk_analysis、recommendation、suggested_revision、facts_uncertain）
- 失败时 降级到规则兜底审查

**层次三点五：规则兜底审查**

- 必需要素组检查：条款中是否包含所有必需关键词组
- 模糊表述检测：5 种模糊关键词（"尽最大努力""必要时""酌情""根据情况""包括但不限于"）

#### 4.3 审查后处理

- 为每个 issue 构建 **结构化引文**（StructuredCitation）：
  - 从 rulebook 静态引文 + RAG 动态引文 + 标准条款引文
  - 通过 `_SOURCE_TITLE_TO_IDS` 映射到规范化 source_id
- 同步 `citation_sources` 字段确保向后兼容
- **CitationRelevanceChecker**：验证每个 issue 的法规引用是否与问题类型匹配
  - 检查关键词重叠度、约束力分类（法律/条例/办法/标准/指南）
  - 不相关时附加引用警告

**输出**：`list[ReviewIssue]`

---

### Stage 5：CROSS_DOC_CHECK（跨文档一致性，80-85%）

**目的**：检查多文档之间的条款一致性。

**CrossDocConsistencyChecker 核心逻辑**：

仅在 `enable_cross_document_check=True` 且文件数 > 1 时执行。

1. **文档画像提取**（9 个维度）
   - 是否提及跨境、保存期限、争议管辖地、数据类型、处理目的
   - 第三方共享、权利响应时间、事件通知时限、存储地点

2. **关键字段对比**（10 项检查）
   - 隐私政策声称无跨境 vs 合同包含跨境条款 → 矛盾
   - 保存期限在不同文档中不一致
   - 争议管辖地冲突
   - 数据类型/处理目的不一致
   - 第三方共享接收方不对应

3. **LLM 深层检查**
   - 当规则检查未发现足够警告时（< 5 条），调用 LLM 做语义层面的跨文档一致性分析

**输出**：`list[str]` 一致性警告

---

### Stage 6：AGGREGATING（结果聚合，85-92%）

**ReviewAggregator 核心逻辑**：

1. **去重**：按 `(clause_id, problem_type, title)` 去重
2. **排序**：按 severity（HIGH → MEDIUM → LOW）→ title 排序
3. **风险评分**（RiskScorer）：
   - 单 issue 评分公式：`base_weight × severity_weight + bonus`
   - 跨境类 bonus +15、敏感数据 bonus +15、未成年人 bonus +15、SCC 冲突 bonus +20
   - 总体评分：所有 issue 的平均分 + 缺失项扣分（HIGH 缺失 ×8、MEDIUM 缺失 ×4）
   - 评分上限 100
4. **评级映射**：≥ 70 = 高风险、40-69 = 中风险、< 40 = 低风险
5. **优先行动生成**：基于 HIGH 问题数、缺失项、中风险问题、跨文档警告
6. **文档画像**：文档类型、条款数、已分类数、问题数、缺失项数
7. **条款分布统计**：各 ClauseType 的计数

**输出**：`AggregatedReview`（完整聚合结果）

---

### Stage 7：RENDERING（报告渲染，92-100%）

**ReviewReportRenderer** 生成 9 节专业报告：

| 节号 | 标题 | 内容 |
|------|------|------|
| 一 | 执行摘要 | 风险评级、评分、问题数量概览 |
| 二 | 审查概况与方法 | 审查模式、文档信息、自动化流程说明 |
| 三 | 文档画像 | 条款类型分布 |
| 四 | 整体风险评估 | HIGH/MEDIUM/LOW 分布、跨文档警告 |
| 五 | 完整性检查结果 | 全局缺失项按 HIGH/MEDIUM/LOW 分级 |
| 六 | 逐条问题清单 | 每个 issue 的完整信息（含建议替换文本） |
| 七 | 优先整改路线图 | 优先行动列表 |
| 八 | 法规依据汇总 | 去重后的法规引用清单 |
| 九 | 审查边界与置信度说明 | 已确认问题/待确认风险/低置信度/未覆盖范围 |
| 十 | 附录 | 审查限制说明、建议补充材料 |

**额外产物**：
- **DOCX 报告**：通过 `ReportService.create_docx_report()` 生成
- **Annotated DOCX**：通过 `AnnotatedDocxBuilder` 在源文档中以内联批注方式标注问题

**输出文件**：
- `review_report.docx`：正式审查报告
- `annotated_{filename}.docx`：带批注的源文档

## 五、审查架构三层模型

```
条款进入审查
    │
    ├── 第一层：DSL 规则引擎 (始终执行)
    │   ├── rulebook.json → dsl_checks[] (正则模式匹配)
    │   ├── 标准条款对比 (StandardClauseLocator + Differ)
    │   └── review_method = RULE, confidence = 0.85
    │
    ├── 第二层：专项审查器 (按文档类型)
    │   ├── PrivacyPolicyReviewer → 隐私政策特有规则
    │   ├── SccContractReviewer → SCC 正文+附录完整性
    │   ├── DpaReviewer → 委托处理协议
    │   └── review_method = RULE, confidence = 0.9
    │
    └── 第三层：LLM 深度审查 (风险触发)
        ├── 仅对 HIGH/MEDIUM 优先级条款
        ├── System: 中国数据合规律师
        ├── 输出: JSON 结构化问题清单
        ├── 失败时降级到规则兜底
        └── review_method = LLM, confidence = 0.85
```

## 六、RAG 知识库检索

**LocalRegulationKnowledgeBase** 为每个条款提供法规支持：

1. **法域解析**：从条款文本检测 cn/eu/us 法域
2. **模块路由**：
   - cn → `cn_review`
   - eu + BCR → `eu_bcr`
   - eu + 补充措施 → `eu_tia`
   - eu + SCC/跨境 → `eu_scc`
   - us + EO14117 → `us_eo14117`
   - us + 隐私政策 → `us_privacy_review`
3. **双重检索**：
   - `issue_discovery` 阶段（top_k=4）：检索法规条文 + workflow_rules
   - `clause_compare` 阶段（top_k=4）：检索标准条款（standard_clauses）
4. **外部 API**（DeliLegal）：检索相关案例（size=2）
5. **结果缓存**：按 `(jurisdiction:module:clause_type, text[:160], enrich)` 缓存

## 七、规则手册体系

**`review_rulebook.json`** 结构：

```json
{
  "clause_types": {
    "CROSS_BORDER_TRANSFER": {
      "display_name": "数据出境",
      "keywords": ["境外", "跨境", "SCC", "标准合同", ...],
      "required_groups": [["境外接收方", "接收方名称"], ["处理目的"]],
      "citations": [{"source": "个保法", "article": "第38条"}],
      "dsl_checks": [{"id": "...", "pattern": "...", "severity": "HIGH", ...}],
      "multi_label_keywords": {"SECURITY_MEASURES": ["加密", "安全"]},
      "priority": 1,
      "checklist_requirement": {"missing_severity": "HIGH"}
    }
  },
  "document_type_checklists": {
    "scc_contract": {
      "required_clause_types": ["CROSS_BORDER_TRANSFER", "ONWARD_TRANSFER", ...],
      "recommended_clause_types": ["DPIA_OBLIGATION", ...]
    }
  },
  "conditional_required": {
    "rules": [
      {"condition_field": "has_cross_border", "condition_value": true,

    ]
  },
  "risk_weights": {"CROSS_BORDER_TRANSFER": 5, "SENSITIVE_PI": 5, ...},
  "severity_weights": {"HIGH": 5, "MEDIUM": 3, "LOW": 1},
  "HIGH_PRIORITY_TYPES": ["CROSS_BORDER_TRANSFER", "SENSITIVE_PI", ...],
```

**RulebookLoader** 提供：
- 类型化访问（get_keywords / get_dsl_checks / get_citations / ...）

## 十、关键设计决策

1. **三层审查而非单一 LLM**：DSL 规则 + 专项审查器 + LLM 的三层架构确保 LLM 不可用时仍可降级到规则兜底，同时规则引擎提供确定性的合规检查

2. **风险触发 LLM 选择机制**：不是对所有条款调 LLM，而是按条款类型优先级 + 高风险短语 + 文本长度智能选择最多 20 个条款进行 LLM 审查，兼顾质量与成本

3. **标准条款知识库对比**：通过 RAG 检索标准条款原文，将用户文档与标准模板逐项对比（义务缺失/弱化/高风险修改），这是 SCC 审查的最高价值功能

4. **场景驱动的缺失项检测**：不仅检查静态 checklists，还根据文档自动提取的业务事实（是否有跨境、是否有敏感数据等）动态增加必需条款类型

5. **多法域支持**：通过文本特征自动检测 cn/eu/us 法域，路由到对应的 RAG 知识库模块，实现一套流水线覆盖多法域

6. **实时进度推送**：WebSocket 在每个阶段完成时推送 `{task_id, status, progress}` 到前端，支持 10 个阶段的细粒度进度展示

7. **知识库人工复核闭环**：ingest → review_pending → reviewed → published 的完整生命周期，发布时自动构建 FTS5 全文索引供后续搜索使用
