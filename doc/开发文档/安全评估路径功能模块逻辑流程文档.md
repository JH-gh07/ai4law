## 二、公共 workflow 基础设施

### 模块 3：WorkflowPipeline — 策略模式管道

**文件**：`backend/common/workflow/pipeline.py`

**类**：`WorkflowPipeline`

**架构**：构造函数注入 14 个 callable 函数，`run()` 方法按固定顺序执行。

**构造函数参数**（14 个注入点）：

```python
extract_profile           ← 企业画像提取
evaluate_diagnosis        ← 合规路径诊断
validate_path             ← 路径校验
build_facts               ← 事实构建
retrieve_regulations      ← 法规检索
build_attachment_notes    ← 附件解析整理
build_issues              ← 问题识别
build_evidence            ← 证据链构建
retrieve_per_issue        ← [可选] 逐issue外部法律API检索
build_context_pack        ← 统一上下文包构建
generate_chapters         ← 章节生成
check_consistency         ← 一致性检查
check_alignment           ← 输入对齐检查
repair_chapters           ← [可选] 章节修复
render_artifacts          ← 产物渲染
```

**`run()` 方法 — 16 步执行时序**：

```
① trace.record("assessment_request", payload)
② profile = extract_profile(payload)
③ trace.record("profile_extracted")
④ diagnosis = evaluate_diagnosis(payload)
⑤ trace.record("diagnosis")
⑥ path_warning = validate_path(payload, diagnosis.recommended_path, diagnosis.rationale)
⑦ trace.record("path_validation")
⑧ facts = build_facts(payload, profile, diagnosis)
⑨ trace.record("facts_built")
⑩ regulations = retrieve_regulations(profile)
⑪ trace.record("retrieval_hits")
⑫ attachment_notes = build_attachment_notes(profile)
⑬ issues = build_issues(facts, diagnosis, regulations, attachment_notes)
⑭ trace.record("issues_built")
⑮ issues, evidence_chain = build_evidence(facts, issues, regulations, diagnosis)
⑯ trace.record("evidence_built")
   ── [可选] retrieve_per_issue(issues, profile, regulations) ──
⑰ trace.record("per_issue_rag")
⑱ context_pack = build_context_pack(task_id, diagnosis, facts, regulations,
                                     issues, evidence_chain, path_warning,
                                     attachment_notes, per_issue_rag)
⑲ trace.record("context_pack_built")
⑳ chapters = generate_chapters(profile, regulations, context_pack)
㉑ trace.record("chapters_generated")
㉒ consistency_issues = check_consistency(profile, chapters, context_pack)
㉓ trace.record("consistency_issues")
㉔ alignment_issues = check_alignment(report_content, profile)
㉕ trace.record("alignment_issues")
㉖ [可选] chapters, consistency_issues, blocked = repair_chapters(...)
    － 修复 → 重新检查 → 无法修复时阻断
㉗ trace.record("repair_pass")
㉘ outputs = render_artifacts(task_id, payload, profile, regulations, chapters, ...)
㉙ 返回 WorkflowRunResult
```

**输出**：`WorkflowRunResult { diagnosis, profile, regulations, chapters, consistency_issues, outputs, facts, issues, evidence_chain, context_pack }`

```python
WorkflowPipeline(
    extract_profile       → self.extractor.extract
    evaluate_diagnosis    → _evaluate_diagnosis
    validate_path         → _validate_path
    build_facts           → build_assessment_facts
    retrieve_regulations  → self.retriever.search

```

**路径校验模式（_validate_path — 3 种模式）**：

```
generate_only:
  recommended_path != "security_assessment" → 记录warning，继续生成

warn_only:
  recommended_path != "security_assessment" → 记录warning，继续生成

block_on_mismatch:
  recommended_path != "security_assessment" AND !force_override_path
    → raise ValueError 阻断生成
  force_override_path=true → 记录warning，继续生成
```

**内部步骤详解**：

#### 步骤 1：诊断评估（_evaluate_diagnosis）

```python
def _evaluate_diagnosis(payload):
    return DiagnosisService().evaluate(
        DiagnosisAnswers(
            q1_is_ciio          = YES/NO
            q2_has_important_data = YES/NO
            q3_pii_count        = payload.pii_count
            q4_spi_count        = payload.spi_count
            q6_scenario         = TransferScenario.OTHER
            q7_receiver_type    = ReceiverType.THIRD_PARTY
            q8_purpose          = payload.transfer_purpose
        )
    )
```

输出：`diagnosis`（含 `recommended_path`, `risk_level`, `rationale`, `matched_rule_id` 等）

#### 步骤 2：逐 issue 外部法律 API 检索（_retrieve_per_issue — 新增）

```python
for issue in issues:
    if issue.severity in {"HIGH", "BLOCKER"}:
        query = f"{issue.title} {issue.description}"
        laws = self.legal_service.search_laws(query, size=3)
        cases = self.legal_service.search_cases(query, size=2)
        enriched[issue.issue_id] = {"laws": laws, "cases": cases}
```

#### 步骤 3：统一上下文包构建（_build_context_pack — 增强）

```
① RAG检索legal_grounding上下文（regulation条文、guide、template）
② 构建legal_grounding + case_grounding（法律依据映射）
③ 构建writing_strategy（写作策略：禁止表述/内部表述/对外表述/语气）
④ 构建generation_basis_pack（逐章节的facts/issues/evidence/法律依据/写作策略）
⑤ 构建CitationRegistry（引用注册表）
⑥ 组装GenerationContextPack（含所有上述产物 + 知识上下文）

GenerationContextPack = LLM生成章节时的唯一数据源
```

#### 步骤 4：章节修复（_repair_chapters — 新增）

```python
def _repair_chapters(chapters, consistency_issues, profile, context_pack):
    return run_repair_pass(
        chapters, consistency_issues, profile, context_pack,
        llm_client, max_retries=3,
    )
```

修复逻辑：
```
一致性检查发现可修复问题 → LLM 重写对应章节 → 重新检查
无法修复 → 阻断(repair_blocked=True)
```

### 模块 9：issue_builder.py — 合规问题识别

**文件**：`backend/modules/assessment/issue_builder.py`

**函数**：`build_assessment_issues(facts, diagnosis_result, regulations, attachment_notes) → list[IssueItem]`

**逻辑**：基于事实和阈值规则，识别 17 类合规问题。

#### 组 1：路径判断（2 个）

| Issue ID | 触发条件 | 严重度 |
|---------|---------|--------|
| `ISSUE-path-mismatch` | `diagnosis.recommended_path != "security_assessment"` | HIGH |
| `ISSUE-ciio-security-assessment` | `is_ciio == True` | HIGH |

#### 组 2：数据范围（4 个）

| Issue ID | 触发条件 | 严重度 |
|---------|---------|--------|
| `ISSUE-important-data` | `contains_important_data == True` | HIGH |
| `ISSUE-pii-threshold` | PII ≥ 100万 | HIGH |
| `ISSUE-spi-threshold` | SPI ≥ 1万 | HIGH |
| `ISSUE-missing-transfer-purpose` | 出境目的为空 | HIGH |

#### 组 3：接收方/法律文件（4 个）

| Issue ID | 触发条件 | 严重度 |
|---------|---------|--------|
| `ISSUE-missing-receiver-country` | 接收国家为空 | HIGH |
| `ISSUE-recipient-security-evidence-missing` | 始终触发 | HIGH |
| `ISSUE-legal-document-gaps` | 始终触发 | HIGH |
| `ISSUE-onward-transfer-unclear` | 始终触发 | MEDIUM |

#### 组 4：同意/匿名化（4 个）

| Issue ID | 触发条件 | 严重度 |
|---------|---------|--------|
| `ISSUE-spi-classification-uncertain` | SPI > 0 | HIGH |
| `ISSUE-necessity-argument-generic` | 始终触发 | MEDIUM |
| `ISSUE-consent-evidence-missing` | 始终触发 | HIGH |
| `ISSUE-anonymization-uncertain` | 始终触发 | MEDIUM |

#### 组 5：材料/审批（3 个）

| Issue ID | 触发条件 | 严重度 |
|---------|---------|--------|
| `ISSUE-missing-attachments` | uploaded_files为空 | MEDIUM |
| `ISSUE-attachments-not-parsed` | 有文件但无解析摘要 | LOW |
| `ISSUE-material-checklist-incomplete` | 始终触发 | MEDIUM |
| `ISSUE-internal-approval-missing` | 始终触发 | MEDIUM |

**关键设计**：9 个始终触发的问题体现了保守合规假设——材料缺失时不假设合规。

每个 Issue 的 `affects_outputs` 字段指定了该问题影响哪些报告章节（overview / data_scope / necessity_legal_basis / recipient_capability / rights_impact / security_measures / risk_remediation / conclusion）。

### 模块 10：evidence_builder.py — 证据链构建

**文件**：`backend/modules/assessment/evidence_builder.py`

**函数**：`build_assessment_evidence(facts, issues, regulations, diagnosis_result) → (updated_issues, evidence_chain)`

**逻辑**：

```
遍历所有issue：

① 过滤有效的fact_refs（只保留在facts中实际存在的）
   无有效fact_refs → 跳过该issue

② 从预定义 _EVIDENCE_WORDING 字典查 claim + conclusion 文案（20+条预置）

③ 构建 rule_refs:
   - 优先用 issue 自带的 rule_refs
   - 材料类 issue (_MATERIAL_ISSUE_IDS) → 不给法规引用（避免误导）
   - 否则取 regulation.source_id（最多3条）
   - 兜底用 diagnosis.matched_rule_id

④ 置信度计算:
   HIGH/BLOCKER + 有法规引用 → 0.9
   HIGH/BLOCKER + 无法规引用 → 0.8
   MEDIUM → 0.75
   其他 → 0.6

⑤ 生成 EvidenceItem:
   evidence_id, claim, fact_refs, rule_refs, conclusion, confidence, used_by

⑥ 回填 issue.evidence_refs
```

  "你是一名专注于中国数据跨境合规的资深律师，深度掌握《个人信息保护法》
   《数据安全法》《数据出境安全评估办法》《数据出境安全评估申报指南（第三版）》等法规。
   请严格按照《数据出境风险自评估报告》的行文规范，用专业、严谨的中文撰写报告章节内容。"

Strict Constraint:
  "写作约束：仅使用上下文提供的事实与法规条文，不得新增行业、国家/地区、主体、规模或场景。
   若上下文缺失，请写'未提供'。如需推测，请明确标注【推测】。
   每段末尾需引用至少一条法规依据，格式为'【依据：法规标题+条款】'。
   每个风险判断必须引用上下文中的 issue_id 或法规 citation。"

参数：temperature=0.2, max_tokens=800
```

**8 个章节**：

| 中文标题 | chapter_id | LLM 生成指令 |
|---------|-----------|-------------|
| 出境活动概述 | `overview` | (1)企业基本情况；(2)数据出境业务背景；(3)出境活动的必要性说明 |
| 数据类型与规模 | `data_scope` | (1)出境个人信息的具体类型(普通/敏感)及字段清单；(2)累计出境规模；(3)是否触发重要数据认定 |
| 出境必要性与合法性基础 | `necessity_legal_basis` | (1)业务必要性论证；(2)合法性基础(个保法第13条、第38条)；(3)单独同意 |
| 境外接收方保障能力 | `recipient_capability` | (1)接收方基本情况；(2)所在地法律环境分析；(3)保护制度和技术措施；(4)处理范围是否超出约定 |
| 个人信息权益影响分析 | `rights_impact` | (1)知情同意权保障；(2)查阅/更正/删除/转移权行使；(3)可能影响及风险等级 |
| 安全措施与传输机制 | `security_measures` | (1)加密技术；(2)访问控制；(3)数据最小化和去标识化；(4)数据处理协议/标准合同主要条款；(5)应急响应预案 |
| 剩余风险与整改建议 | `risk_remediation` | (1)列举已识别合规风险点(≥3项)；(2)每项成因/影响/等级；(3)具体整改措施和时间表；(4)法规依据 |
| 综合评估结论 | `conclusion` | (1)总体合规评级；(2)核心结论(≤150字)；(3)申报建议；(4)有效期说明(通常2年) |

**issue-章节关联**：每章通过 `chapter_id in issue.affects_outputs` 筛选相关问题，无匹配时兜底取所有 HIGH/BLOCKER 级别 issue。

**LLM 不可用时**：降级为占位文本。

### 模块 12：consistency_checker.py — 一致性检查

**文件**：`backend/modules/assessment/consistency_checker.py`

**类**：`ConsistencyChecker`

**方法**：`check_with_context(profile, chapters, context_pack) → list[str]`

**6 类检查**：

```
① 基础章节检查 (check)
   - 每章必须有法规引用(citation)
   - 高风险条件下最后一章风险等级必须为HIGH

② Context Pack引用完整性 (check_context_pack_consistency)
   - Issue 引用的 fact_id 是否在 facts 中存在
   - Issue 引用的 rule_ref 是否在 regulations 中或为 "diagnosis:" 前缀
   - Issue 引用的 evidence_id 是否在 evidence_chain 中存在
   - Evidence 引用的 fact_id / rule_ref 是否存在
   - Evidence 的 used_by 中的 issue_id 是否存在

③ 报告 vs 上下文对齐 (check_report_against_context)
   - HIGH/BLOCKER issue 是否在报告中被提及
   - 有附件缺失 issue 时，报告是否还能写"材料齐备"
   - 重要数据状态 unknown 时，报告是否写"不涉及重要数据"
   - 路径不匹配时，报告是否标注"强制生成"/"参考草案"

④ 禁止表述检测 (check_forbidden_expressions)
   从 writing_strategy 中提取 global_forbidden_expressions
   和各 issue 级别的 forbidden_expressions
   检查外部报告中是否出现这些表述

⑤ 内部表述泄露检测 (check_internal_expression_leakage)
   检查 internal_expression（内部审查用语）是否泄露到外部报告
   ≥15字的句子逐句比对

⑥ 用户声称事实滥用检测 (check_user_claim_positive_statement)
   检查 evidence_status="user_claim_only" 的事实值
   是否在报告中与正面断言标记词（"已充分证明"/"完全合规"/"不涉及重要数据"等）
   在500字范围内同时出现
   防止将用户未证实的主张作为正面结论的依据
```

### 模块 13：writing_strategy_builder.py — 写作策略

**文件**：`backend/modules/assessment/writing_strategy_builder.py`

**函数**：`build_writing_strategy(issues) → dict`

**逻辑**：

```
为每个 issue 生成：
  issue_id / issue_type / risk_level
  internal_expression:  内部审查表达（可包含材料缺失/风险不确定性等完整描述）
  external_expression:  对外报告表达（严格受控，材料缺失写"需补充"而非假设材料齐备）
  forbidden_expressions: 该issue对外报告中不得出现的词语
  tone:                 对外报告的语气约束
  can_enter_external_report: 该issue是否可以写入对外报告

全局字段：
  global_external_tone:           全局对外报告语气
  global_forbidden_expressions:   全局禁止表述
  require_all_claims_supported:   所有正面主张必须区分材料佐证状态
```

**核心原则**：

```
- user_claim_only 事实 → 只能用于内部审查和待确认提示，不能作为对外报告的正面断言
- partial_evidence 事实 → 可以用"基于初步材料"等审慎表述
- documented_evidence 事实 → 可以正常引用
- verified_evidence 事实 → 可以作为确定性结论
```

## 七、模块间衔接关系

```
ProfileExtractor ──→ FactBuilder (extracted_notes → attachment事实)
FactBuilder ──→ IssueBuilder (fact_id索引 → 阈值检查触发)
IssueBuilder ──→ EvidenceBuilder (fact_refs筛选 → 预置文案映射)
全部产物 ──→ ContextPack (LLM生成的唯一数据源)
ContextPack ──→ ChapterGenerator (chapter_id筛选issue)
ChapterGenerator ──→ ConsistencyChecker (报告vs上下文对齐)
ContextPack ──→ ReportRenderer (writing_strategy决定对内/对外表述)

## 八、关键设计决策

| 维度 | 实现方式 |
|------|---------|
| 管线架构 | WorkflowPipeline — 策略模式，14个callable注入 |
| 事实分类 | schema → attachment → diagnosis 三种来源，4级证据成熟度 |
| 合规假设 | 保守策略 — 9个issue始终触发，材料缺失时不假设合规 |
| LLM约束 | 系统prompt + strict_constraint + 缺失写"未提供" + 每段引用法规 |
| 对内/对外表达分离 | writing_strategy控制内部审查 vs 外部报告的表述差异 |
| 路径安全阀 | block_on_mismatch模式 + force_override路径 |
| 引用完整性 | 6类一致性检查 + CitationRegistry + 审计日志 |
| 修复机制 | repair_pass — 可修复问题LLM重写，不可修复阻断输出 |
| 全链路trace | 每步JSON事件记录，支持追溯审计 |
| 知识增强 | RAG 多路检索 + 外部法律API逐issue检索 |
