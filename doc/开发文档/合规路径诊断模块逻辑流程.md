## 一、总体架构概览

### 1.1 模块定位

合规路径诊断是整个 ai4law 平台的**入口模块**，功能是：用户通过智能问答填写企业的数据处理信息后，系统根据中国法律规则判定其应走哪条合规路径（安全评估 / 标准合同备案或认证 / 豁免）。

与 us_14117 / eu_scc 等审查模块不同，诊断模块**不使用 WorkflowPipeline**，而是直接串联调用：规则引擎 → LLM 解释 → 报告渲染。

### 1.2 执行流程

```
前端用户填写诊断问卷
        │
        ▼
POST /diagnosis/evaluate     (纯规则判定，无需认证)
POST /diagnosis/report        (完整报告，需认证)
        │
        ▼
DiagnosisService.evaluate(answers)
        │
        ├─[1] _normalize_answers()     → 用扩展问卷数据补全核心字段
        ├─[2] _rule_match()            → 按优先级匹配 decision_tree.json 中的 9 条规则
        ├─[3] _build_rule_result()     → 构造 DiagnosisResult + LLM 生成解释
        ├─[4] _needs_ai_inference()    → 判断是否需要 LLM 兜底诊断
        ├─[5] _build_ai_inference_result() → LLM 兜底路径推荐
        └─[6] 默认 → scc_or_certification
        │
        ▼
DiagnosisReportRenderer.render()
        │
        ├─ LLM 生成摘要（可选）
        ├─ _build_template_markdown()  → 8 节结构化中文报告
        ├─ _build_html_doc()           → HTML 预览
        └─ render_pdf_report()         → PDF 正式版
        │
        ▼
DiagnosisReportResponse
  { report_path, html_report_path, pdf_report_path, result }
```

### 1.3 与其他模块的关系

```
diagnosis（路径诊断）
    │
    ├─ security_assessment → assessment 模块（安全评估报告生成）
    ├─ scc_or_certification → scc 模块（标准合同备案审查）或 pipia 模块（PIPIA 评估）
    └─ exemption           → 无需进一步合规动作（但建议记录评估过程）
```

#### 2.2.2 规则结构

每条规则的 JSON 结构:
```json
{
  "id": "rule_id",
  "description": "规则描述",
  "when": {
    "q1_is_ciio": ["yes"],
    "q3_pii_count_gte": 1000000,
    "q4_spi_count_lt": 10000,
    "q6_scenario": ["contract_performance"],
    ...
  },
  "then": {
    "path": "security_assessment",
    "legal_basis": [...],
    "rationale": "..."
  }
}
```

`when` 条件支持以下操作符:
- `字段名: [允许值列表]` — 值在列表中即匹配
- `字段名_gte: 数字` — 大于等于
- `字段名_lt: 数字` — 小于

### 2.3 `service.py` — 核心诊断服务

**文件**: `backend/modules/diagnosis/service.py`
**行数**: 331 行
**核心类**: `DiagnosisService`

#### 2.3.1 构造函数

```python
class DiagnosisService:
    def __init__(self, llm_client=None):
        self.llm_client = llm_client or LLMClient(get_settings())
        # 加载 decision_tree.json
        self._tree = json.loads(Path(__file__).parent.joinpath("decision_tree.json").read_text())
```

#### 2.3.2 主入口 `evaluate(answers) → DiagnosisResult`

```
1. _normalize_answers(answers)
   → 用模块3/4/5的扩展问卷数据补全 q1-q8 核心字段

2. 遍历 self._tree["rules"] 数组（按优先级顺序）
   对每条规则:
     _rule_match(rule["when"], answers)
       如果匹配:
         return _build_rule_result(rule, answers)

3. 如果所有规则都不匹配:
   _needs_ai_inference(answers)
     如果返回 True:
       return _build_ai_inference_result(answers)
     如果返回 False:
       return _build_rule_result(default_rule, answers)
       → 推荐路径为 scc_or_certification
```

#### 2.3.3 `_normalize_answers(answers)` — 智能补全

这是诊断模块的关键智能层。由于用户可能在问卷中只填写了扩展模块字段而遗漏了核心 q1–q4 字段，此函数负责**反向推演**:

```
1. 重要数据推断:
   if q2_has_important_data in (unknown, no):
       if m3_processes_important_data == yes OR m3_important_data_types 非空:
           q2_has_important_data = yes

2. 个人信息推断:
   if q5_no_personal_info == unknown:
       if m3_processes_personal_info == no AND m3_personal_info_types 为空:
           q5_no_personal_info = yes
       elif m3_processes_personal_info == yes OR m3_personal_info_types 非空:
           q5_no_personal_info = no

3. PII 数量推断:
   从 m3_data_volume_range 推断近似值:
     "1000万条以上"       → q3_pii_count = 10000000
     "500万-1000万条"     → q3_pii_count = 7000000
     "100万-500万条"      → q3_pii_count = 3000000
     "50万-100万条"       → q3_pii_count = 700000
     "10万-50万条"        → q3_pii_count = 300000
     "1万-10万条"         → q3_pii_count = 50000
     "1000-1万条"         → q3_pii_count = 5000
     "1000条以下"         → q3_pii_count = 500

4. SPI 数量推断:
   如果 m3_sensitive_info_types 非空:
       存在敏感信息，保守估算为 1000
   如果 q3_pii_count 已推断且较大（如 > 10万）:
       敏感信息比例按 ~1% 估算

5. 接收方类型推断:
   从 m4_share_to_third_party 和 m4_entrusted_processing 推断:
     - 有委托处理且无第三方分享 → intra_group
     - 有第三方分享 → third_party
```

#### 2.3.4 `_rule_match(when_conditions, answers)` — 规则匹配引擎

```
对 when 字典中的每个条件:
  1. 值为列表类型:
     从 answers 取对应字段值
     检查值是否在允许列表中
     匹配: "yes" in ["yes"] → True

  2. 后缀 _gte (大于等于):
     字段值 >= 条件值 → True

  3. 后缀 _lt (小于):
     字段值 < 条件值 → True

全部条件都满足 → 返回 True
任一条件不满足 → 返回 False
```

#### 2.3.5 `_build_rule_result(rule, answers)` — 构造诊断结果

```
1. 提取规则的 path / legal_basis / rationale
2. 根据路径生成 action_items:
   security_assessment:
     - 准备安全评估申报材料
     - 在出境前完成安全评估
     - 提交至省级网信办
   scc_or_certification:
     - 标准合同备案或认证
     - 完成个人信息保护影响评估(PIPIA)
     - 签署标准合同并备案
   exemption:
     - 记录豁免依据
     - 持续监控数据变化
3. 如果 LLM 已启用:
     调用 _build_rule_explanation() 生成 2-3 句中文自然语言解释
     如果 LLM 返回为空，使用规则内置 rationale
4. 调用 risk_level() 计算风险等级:
     CIIO / 重要数据 / PII≥100万 / SPI≥1万 → HIGH
     PII≥10万 → MEDIUM
     其他 → LOW
5. 返回 DiagnosisResult(
     conclusion_source = "rule",
     confidence = "HIGH",
     matched_rule_id = rule["id"],
     final_explanation = LLM 解释或规则 rationale,
     ...
   )
```

#### 2.3.6 `_needs_ai_inference(answers)` — 判断是否需要 LLM 兜底

```
触发条件（全部满足时才触发）:
  1. q1_is_ciio == unknown
  2. q2_has_important_data == unknown
  3. q5_no_personal_info == unknown
  4. q3_pii_count == 0  AND  q4_spi_count == 0
     （数量信号弱）
  5. 模块3没有强结构化信号（未触发重要数据或个人信息正推断）

返回 True: 所有核心字段都不确定，规则引擎无法可靠判断
返回 False: 至少有一条强信号可以用于规则判断
```

#### 2.3.7 `_build_ai_inference_result(answers)` — LLM 兜底诊断

```
1. 如果 LLM 未启用:
     → 保守返回 scc_or_certification, confidence="LOW"
       解释: "核心字段信息不足，默认推荐标准合同/认证路径"

2. 构造 LLM 提示:
   System: "你是一名数据合规专家，根据用户提供的企业数据处理信息，
            输出推荐合规路径。"
   User: 将 DiagnosisAnswers 格式化为中文描述文本
         要求LLM返回 JSON:
         { "recommended_path": "security_assessment|scc_or_certification|exemption",
           "confidence": "HIGH|MEDIUM|LOW",
           "rationale": "...",
           "action_items": [...] }

3. 调用 self.llm_client.chat(system, user, temperature=0.1)
4. _parse_json_object(raw) 解析 LLM 返回的 JSON:
   - 尝试直接 json.loads()
   - 失败则用正则 r'\{[\s\S]*\}' 提取
5. 验证 recommended_path 是否合法
6. 限制 action_items 最多 4 条
7. 返回 DiagnosisResult(
     conclusion_source = "ai_inference",
     confidence = LLM 返回的置信度,
     matched_rule_id = None,
     uncertainty_notes = ["AI推断结果，建议人工复核"]
   )
```

#### 2.3.8 `_parse_json_object(raw)` — 鲁棒 JSON 提取

```
1. 尝试 json.loads(raw)
2. 失败 → 正则搜索 r'\{[\s\S]*\}' (从文本中提取第一个 JSON 对象)
3. 再次 json.loads()
4. 仍失败 → 返回 {} (调用方会 fallback)
```

#### 2.4.1 主入口 `render(company_name, answers, result)`

```
1. AI 摘要生成（如果 LLM 启用）:
   调用 LLM 以专业中文语气生成 2-3 句摘要，说明:
     - 诊断结果
     - 推荐的合规路径
     - 下一步建议

2. 调用 _build_template_markdown() 生成完整的结构化中文报告

3. 报告保存:
   _build_html_doc(html_text) → {filename}.html
     用纯 HTML 包装: <html><head><meta charset=utf-8><style>...</style></head>
     <body>{html_content}</body></html>
     CSS 包含完整排版样式（表格、列表、标题、风险标签颜色等）

   render_pdf_report(pdf_path, title, sections)
     → 用 reportlab + STSong-Light 中文字体渲染
     → 5 个 sections: "企业回答", "诊断结果", "AI 摘要", "模板化报告", "机器可读附录"

4. 返回 {"html": Path, "pdf": Path}
```

#### 2.4.2 `_build_template_markdown()` — 8 节结构化报告

**第一节 — 基本信息**
```
诊断编号: DIAG-{yyyymmdd}-{序号}
生成时间: 2026-06-03 12:00:00
适用管辖区: 中国大陆
企业名称: XXX
适用场景: 合同履约 / HR管理 / 紧急 / 法定 / 其他
```

**第二节 — 诊断结论摘要**
```
路径结论: 安全评估 / 标准合同或认证 / 豁免
必要性: 必须 / 建议 / 非必须
置信度: HIGH / MEDIUM / LOW
风险等级: LOW / MEDIUM / HIGH
AI 摘要: (LLM 生成)
```

> 如果结论来源为 `ai_inference`，额外标注 `⚠️ AI 辅助判断，建议复核`

> 风险等级用颜色标签: HIGH=红色、MEDIUM=橙色、LOW=绿色

**第三节 — 关键判断依据**
```
事实依据:
  - CIIO 状态: 是 / 否 / 未知
  - 重要数据: 是 / 否 / 未知
  - 个人信息数量: XXX
  - 敏感个人信息数量: XXX

法律依据: (逐条列出)

规则触发链条:
  条件1 → 条件2 → 条件3 → 触发规则 {rule_id}
```

**第四节 — 路径判定说明**
```
为什么推荐此路径:
  逐条解释规则匹配逻辑

为什么不推荐其他路径:
  安全评估: 未触发CIIO/重要数据/100万PII/1万SPI阈值
  标准合同/认证: [如果推荐的是安全评估] PII/SPI已触发安全评估阈值
  豁免: 不满足豁免条件（非合同/HR/紧急/法定场景或数量超限）
```

**第五节 — 核心风险提示**
```
风险项 | 说明 | 人工复核建议

根据 result.risk_level 和具体字段动态生成:
  - HIGH: CIIO/重要数据触发 → "必须完成安全评估后方可出境，不得先行传输"
  - MEDIUM: PII≥10万 → "建议尽快完成合规动作，注意备案时限"
  - LOW: 数量较少 → "当前为低风险，但仍需按路径完成合规要求"
```

**第六节 — 缺口与待补充信息**
```
生成缺口分析表:
  字段         | 状态    | 影响               | 建议
  CIIO         | 未知    | 影响路径判断        | 确认是否属于CIIO
  重要数据      | 未知    | 影响路径判断        | 完成数据分类分级
  个人信息数量  | 已填写  | 用于阈值判断        | 定期更新
  跨境传输事实  | 未知    | 影响适用性判断      | 确认是否实际出境
```

**第七节 — 建议后续行动**
```
下一模块建议:
  security_assessment → assessment 模块（安全评估报告生成）
  scc_or_certification → scc 模块（标准合同）或 pipia 模块（PIPIA评估）
  exemption → 无需进一步系统操作，建议保存诊断记录

准备材料清单:
  - 数据出境安全评估申报书
  - 数据处理协议副本
  - 个人信息保护影响评估报告(PIPIA)
  ...

优先级行动清单:
  P0: (截止期限前) ...
  P1: (1个月内) ...
  P2: (持续) ...

定制5步计划:
  1. 确认数据类型和数量统计口径
  2. 完成数据分级分类
  3. ...
```

> 截止期限由 `m2_deadline` 字段决定，如为 "紧急" 或 "整改" 则压缩时间线
> 企业规模 (`m1_company_size`) 影响建议强度: "微型/小型" → 最简方案、"大型/特大型" → 批量合规方案

## 八、关键设计特征

1. **规则优先级**: 豁免规则优先（先判定是否不需要做），然后强制规则（安全评估触发条件），最后默认（标准合同）
2. **智能补全**: `_normalize_answers()` 从 5 个模块的扩展字段反向推演核心字段，减少用户未填写时的漏判
3. **双引擎判断**: 规则引擎 + LLM 兜底。规则能判断时以规则为准（`conclusion_source="rule"`），信息不足时 LLM 才介入（`conclusion_source="ai_inference"`）
4. **报告与判定分离**: `evaluate()` 只负责判定，`render()` 只负责报告。两个端点 (`/evaluate` 和 `/report`) 可以独立调用
5. **同步执行**: 诊断是实时问答，不使用异步任务机制——用户需要立即看到结果
6. **不使用 WorkflowPipeline**: 诊断是单步决策，不需要多步流水线中的 facts/issues/evidence 中间产物
