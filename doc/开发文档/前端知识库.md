可以，下面我给你一版“**前端知识库中心统一到新知识中枢之后**”的**具体、详细、面向产品的预期落实逻辑流程**。核心原则只有一句：

**底层统一到后端分层 RAG 中枢，前台呈现始终保持正式、面向用户、可理解、可操作。**

---

**一、目标状态**

统一完成后，前端“知识库中心”不再是一个单纯读 `csv` 的目录页，也不是后端结构的可视化外壳，而是一个正式的用户产品模块，承担 4 件事：

- 给用户查法规、案例、模板、适用说明
- 给用户解释系统结论背后的依据
- 给用户提供按任务场景组织的知识入口
- 给业务结果页、报告页、引用抽屉提供统一知识联动

用户看到的是：

- `法规依据`
- `官方指南`
- `实务案例`
- `官方模板`
- `适用场景`
- `是否可作为正式依据`
- `适用模块`
- `生效状态`

用户看不到的是：

- `L1/L2/L3/L4`
- `chunk_id`
- `reference_ids`
- `RetrievalBundle`
- `usage_policy_debug`
- 原始 JSON 和索引结构

---

**二、整体逻辑流程**

统一后的完整链路应该是：

1. 知识源进入后端知识治理底座
2. 后端构建分层 chunk 和多索引
3. 后端新增“前端知识中心投影视图层”
4. 前端知识库中心只调用“用户视角 API”
5. 结果页、报告页、引用抽屉复用同一套知识视图
6. 所有正式展示内容都遵守 usage policy 和法域规则

也就是说，真实流程不是：

`前端 -> 直接读后端 chunk`

而是：

`前端 -> 用户视角 API -> 投影视图层 -> 知识治理/索引/编排层`

这里最关键的是中间这层：

**投影视图层。**

它负责把后端内部知识对象翻译成前端用户可读的产品对象。

---

**三、后端侧预期落实流程**

### 1. 知识源治理仍然走现有中枢

底层仍然以这些为真源：

- `source_registry.v1.json`
- `module_catalog.v1.json`
- `normalized/regulation_articles.jsonl`
- `storage/rag/v3/*.jsonl`
- `storage/rag/v3/*.vector.json`

也就是：

- 条文、指南、模板、案例先进入 registry
- 再被 builder 切成分层 chunk
- 再被 ingest 建成多索引
- orchestrator 决定不同模块和阶段用哪些内容

这一层不直接给前端。

---

### 2. 新增“Knowledge Center Projection”投影视图层

这是统一里最重要的新层。

它的职责是把后端内部结
构转成前端产品语言。

它应该做的事：

- 把 `L1_regulatory_evidence` 翻译成“法规依据 / 官方指南 / 标准条款”
- 把 `L2_business_rule` 翻译成“适用说明 / 审查规则 / 判断逻辑说明”
- 把 `L3_testcase` 翻译成“实务案例 / 典型场景参考”
- 把 `L4_template` 翻译成“官方模板 / 参考模板”

同时把内部字段翻译成用户字段：

- `authority_level` -> `权威级别`
- `binding_force` -> `约束力`
- `status` -> `现行有效 / 已失效 / 待确认`
- `can_be_cited` + `can_enter_external_report` -> `是否可作为正式依据`
- `modules` + `scenario_tags` -> `适用场景`
- `template_type` -> `官方模板 / 参考模板`

这一层还要做聚合：

- chunk 级别数据要聚成 source 级别卡片
- 同一个法规的多个条文要能形成一个“法规详情页”
- 同一个模板的多个 section 要能形成一个“模板详情页”
- 同一案例的结构化字段要能形成一个“案例详情页”

所以这层不只是翻译字段，更是在做：

**从运行时 chunk 视图 -> 用户产品视图的重建。**

---

### 3. 后端用户视角 API 需要重做

现在的 `/api/v1/knowledge/*` 基本是轻量目录接口，后面应升级成正式产品 API，但仍然对前端隐藏内部结构。

建议最终拆成 5 类接口。

**1. 知识中心首页接口**
用途：
- 返回统计
- 返回推荐入口
- 返回最近重点更新
- 返回主要知识分类

前端用它渲染：
- 法规依据
- 官方模板
- 实务案例
- 热门场景
- 最近更新

**2. 目录检索接口**
用途：
- 搜索法规、模板、案例、场景说明
- 按法域、适用场景、知识类型、权威级别过滤

它返回的应该是用户卡片对象，不是 chunk。

卡片字段应该像：
- 标题
- 副标题
- 类型
- 法域
- 权威级别
- 适用场景
- 生效状态
- 摘要
- 是否可正式引用

**3. 详情页接口**
用途：
- 查看单个法规/案例/模板/指南详情

例如法规详情页应返回：
- 基本信息
- 文件简介
- 关键条文目录
- 关联场景
- 适用模块
- 正式引用说明
- 相关法规
- 相关模板
- 相关案例

**4. 条文阅读接口**
这个保留 `LawViewerPage` 的思路，但后端数据源改成统一底座。
用途：
- 查看某部法规某一条
- 上下条切换
- 看来源和适用说明

**5. 结果联动接口**
用途：
- 从报告、结论、引用点跳到知识中心
- 返回“该结论参考了哪些正式依据”
- 返回“为什么系统这样判断”

这类接口给：
- 报告引用抽屉
- 审查结果侧栏
- 工作台结果解释面板

---

**四、前端侧预期落实流程**

### 1. 页面结构重组为正式用户产品

前端知识库中心不再按后端存储结构组织，而按用户任务组织。

建议最终页面结构是：

- `法规依据`
- `官方指南`
- `实务案例`
- `官方模板`
- `适用场景`

而不是：

- `sources`
- `cases`
- `citation demo`
- `articles`

这些内部型 tab 应该被产品化改名和重构。

---

### 2. 用户进入页面时的逻辑

用户进入知识库中心后，前端应该：

1. 请求首页接口
2. 渲染几个正式入口区块
3. 默认展示推荐内容，而不是空白表格
4. 提供搜索框和筛选器
5. 所有展示项都以卡片、目录、详情页形式出现

默认首页可以看到：

- 常用法规依据
- 重点模板
- 热门适用场景
- 最近更新的规范
- 常见跨境问题入口

这才是面向用户的知识中心，而不是开发索引中心。

---

### 3. 用户搜索时的逻辑

用户输入关键词后，前端不应关心底层是 source 还是 chunk。

流程应是：

1. 前端发起统一搜索请求
2. 后端投影视图层决定搜索哪些知识类型
3. 检索结果按用户类型分组
4. 前端展示为分组结果页

比如搜“BCR”后，用户看到的应该是：

- 法规依据
- 官方指南
- 适用说明
- 典型案例
- 模板与材料

而不是一堆原始 chunk。

---

### 4. 用户进入详情页时的逻辑

详情页必须是“阅读页”，不是字段页。

例如法规详情页：
- 标题
- 文件来源
- 发布机关
- 生效状态
- 权威级别
- 适用范围
- 适用场景
- 重点条文目录
- 关联解释
- 相关模板
- 相关案例

例如模板详情页：
- 模板名称
- 是否官方模板
- 适用场景
- 使用说明
- 章节结构
- 填写重点
- 关联法规依据

例如案例详情页：
- 场景简介
- 风险点
- 适用模块
- 关联法规
- 参考价值
- 是否可作为正式依据说明

---

### 5. 结果联动时的逻辑

这是统一后非常重要的一段。

以后 assessment/review/workspace 里的结果，如果引用了知识内容，应统一跳转到前端知识库中心视图，而不是展示原始字段。

例如：

- 报告里的法规引用
  点击后打开法条阅读抽屉或法规详情页
- 审查问题里的“依据说明”
  点击后打开对应法规依据 + 适用说明
- 模板结构来源
  点击后打开模板详情页
- “为什么推荐这个路径”
  点击后打开对应适用说明页

也就是说，知识库中心不仅是独立页面，还应成为：

**整个工作台、结果页、报告页的统一知识解释层。**

---

**五、统一时最关键的翻译规则**

这是落地成败的关键，必须明确。

### 1. 内部概念到用户概念的翻译

内部字段不能原样上屏。

应做这样的映射：

- `L1_regulatory_evidence` -> `法规依据` / `官方指南`
- `L2_business_rule` -> `适用说明` / `审查规则说明`
- `L3_testcase` -> `典型案例`
- `L4_template` -> `官方模板` / `参考模板`

- `can_be_cited=true` -> `可作为正式依据`
- `can_be_cited=false` -> `仅供参考`
- `can_enter_external_report=false` -> `不直接写入正式报告`

### 2. 内部调试字段不进入正式界面

这些不应在正式界面出现：

- `chunk_id`
- `reference_ids`
- `allowed_usage`
- `usage_policy_debug`
- `rejected_chunk_ids`
- `workflow_rules` 原始数组
- `RetrievalBundle.debug`

如果以后需要调试，只能做：
- 内部开发模式
- 管理员隐藏视图
- 本地开发开关

不能污染正式前端产品。

---

**六、统一的代码落实顺序**

### Step 1
先保留前端页面形态，但替换后端数据底座。

也就是先改：
- `backend/api/knowledge.py`
- `backend/services/knowledge_index.py`

让它们不再只读 `sources.csv/cases.csv`，而是逐步改成读：
- `source_registry`
- `module_catalog`
- `v3 jsonl`
- 统一检索能力

这一步前端几乎不动，先保证数据统一。

### Step 2
新增投影视图层，把后端内部对象翻译成正式前端对象。

这一步是关键新增模块，建议单独做 service，不要把翻译逻辑散在 API 路由里。

### Step 3
重构前端 `EvidenceCenterPage`。

把当前的技术性 tab 和字段改成正式产品信息架构：
- 首页入口区
- 分类目录区
- 搜索结果页
- 知识详情页
- 法条阅读页

### Step 4
把 `LawViewerPage` 接到统一知识底座。

保留它的阅读体验，但底层 metadata、条文来源、关联信息都改走统一后端视图。

### Step 5
把工作台、报告、引用抽屉统一接入知识中心。

让知识中心成为全站统一知识解释入口。

---

**七、验收时应该达到的效果**

统一完成后，用户感受到的应该是：

- 知识库中心是一个正式知识产品，不是后台数据页
- 搜到的法规、模板、案例和系统实际使用的是同一套知识底座
- 结果页里的依据跳转后，看到的是正式可读内容，不是原始结构
- 用户能够理解“这条依据是什么、为什么适用、能不能正式引用”
- 页面上不会出现工程字段、JSON 结构、后端调试概念

---

**一句话总结这版落实流程**

最终应落实为：

**后端用分层 RAG 中枢统一知识真源，前端通过投影视图层把这些知识重新组织成法规依据、适用说明、实务案例、官方模板四类正式用户内容，并让知识中心成为全站结果解释和依据联动的统一入口。**
