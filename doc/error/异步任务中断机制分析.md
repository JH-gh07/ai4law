# 异步任务执行中断机制分析

## 现象

用户在前端点击"执行"启动异步任务后，切换到其他页面（或点击其他子页面/标签）时，任务执行流中断。表现形式包括：
- Timeline 不再刷新新事件
- 任务状态卡在 "RUNNING" 不再更新
- 轮询停止，后续结果丢失

## 全链路追踪

### 第一条链：执行链路（页面内）

```
ModuleRunPanel.tsx:execute()
  │
  ├─ buildPayload()                            ← 构造请求体（可能含文件上传）
  └─ runWithPayload(requestPayload)
       │
       ├─ runModule(definition, payload, "async", timeoutMs, onProgress, onEvent, onTaskDiscovered)
       │     │
       │     ├─ POST asyncSubmitEndpoint        ← 提交异步任务，获得 taskId
       │     ├─ onTaskDiscovered(taskId)        ← → handleTaskCreated()
       │     │   └─ dispatch(append_run + asyncState:"running")
       │     │   └─ setOpenTabs(timeline)        ← 跳到 Timeline 标签
       │     │
       │     ├─ new EventSource(SSE stream)     ← 打开 SSE 长连接监听实时事件
       │     │   └─ onmessage → onEvent(event)  ← 每收到一个事件回调
       │     │
       │     ├─ while (not timeout) {            ← 轮询循环（与 SSE 并行）
       │     │     fetch status endpoint
       │     │     if FINAL_STATE → return result
       │     │     sleep 1500ms
       │     │   }
       │     │
       │     └─ return { response, asyncTaskId } ← 执行完成
       │
       └─ onRunDone(result)                     ← 回填结果到 store
```

### 第二条链：页面内轮询链路（WorkspaceShell 独立 useEffect）

```
WorkspaceShell.tsx
  │
  ├─ useEffect(… latestRun …)
  │     if (!latestRun.asyncTaskId) return
  │     if (!isRunInProgress && !noResponse) return  ← 第一次运行后也检查
  │
  │     fetchModuleTaskStatus(module, taskId)
  │       │
  │       └─ if final state → dispatch(append_run) with result
  │                              → 更新 success / response / error
  │                              → 更新 finishedAt
  │
  ├─ useEffect(… activeTaskId, latestRun …)
  │     如果 activeTaskId 未设置但 latestRun 正在运行 → 恢复 activeTaskId
  │
  └─ <TaskEventBridge taskId={activeTaskId} />       ← SSE → store (timeline)
```

### 第三条链：SSE 事件桥接链（全局模块级）

```
useTaskEvents.ts (全局单例)
  │
  ├── eventSources:  Map<taskId, EventSource>       ← 全局级别，不绑定组件
  ├── listeners:     Map<taskId, Set<callback>>      ← 多组件可订阅同一 taskId
  ├── eventBuffers:  Map<taskId, RunEvent[]>         ← 累计缓冲区
  │
  ├── connectSSE(taskId):
  │     es = new EventSource(`/api/v1/events/task/${taskId}/stream`)
  │     es.onmessage → push to buffer → notify all listeners
  │     es.onerror   → es.close() + delete from map
  │
  ├── startPolling(taskId, since):                  ← SSE 失败时的回退
  │     while(active):
  │       fetch /events?since=X
  │       push to buffer → notify all listeners
  │       sleep 1500ms
  │
  └── useTaskEvents(taskId):
        useEffect:
          注册 listener
          如果 EventSource 不存在 → connectSSE
          3秒后如果缓冲区仍空 → startPolling
        cleanup:
          注销 listener
          如果当前组件是最后一个 listener → 不关 EventSource
```

## 中断的五个根因

### 根因 1：`runModule()` 的轮询循环绑定在调用它的组件生命周期上

```ts
// module-adapter.ts:335-411
export async function runModule(
  module: ModuleDefinition,
  payload: unknown,
  runMode: RunMode,
  timeoutMs = 180000,
  onProgress?: (update: ModuleRunProgress) => void,
  onEvent?: (event: RunEvent) => void,
  onTaskDiscovered?: (taskId: string) => void,
): Promise<ModuleRunResponse> {
  // ...
  const es = new EventSource(...)     // SSE 连接
  // ...
  while (Date.now() - startedAt < timeoutMs) {  // ← 轮询循环
    const statusResponse = await requestJson(...)
    if (FINAL_STATES.has(state)) {
      es?.close()
      return ...
    }
    await sleep(1500)
  }
  es?.close()
  throw new Error("Async task timeout")
}
```

**`runModule()` 返回的是一个 Promise。** 这个 Promise 在 ModuleRunPanel 的 `runWithPayload()` 中通过 `await` 挂起。如果 `ModuleRunPanel` 组件被卸载（用户切换到其他页面/子标签），`await` 不会被 React 自动 abort —— **它继续运行，但回调函数 (`onProgress`, `onEvent`, `onTaskDiscovered`) 引用的 state setter 操作的是一个已卸载的组件，React 会忽略这些 setState，但不抛异常。**

**关键：`runModule` 自身没有 `AbortController`，也没有检查组件是否仍挂载。** 它内部的 `requestJson` fetch 调用也没有 `signal: abortController.signal`。

### 根因 2：WorkspaceShell 的 useEffect 依赖 `latestRun` 来触发轮询检测

```ts
// WorkspaceShell.tsx:934-965
useEffect(() => {
  if (!latestRun?.asyncTaskId) return;
  const shouldSync = isRunInProgress(latestRun) || !latestRun.response;
  if (!shouldSync) return;

  let cancelled = false;
  const moduleDefinition = findModule(latestRun.module);

  const syncStatus = async () => {
    try {
      const status = await fetchModuleTaskStatus(moduleDefinition, latestRun.asyncTaskId!);
      if (cancelled) return;               // ← 防竞态
      if (status.state in final states) {
        dispatch({ type: "append_run", payload: { ...latestRun, finishedAt, ... } });
      }
    } catch { /* best-effort */ }
  };

  void syncStatus();
}, [dispatch, latestRun]);
```

**这个 useEffect 只执行一次**（`[]` 依赖为空）。它只是检查 `latestRun` 是否是终态，**不做持续轮询**。

**如果用户切换到其他页面再回来：**
1. `WorkspaceShell` 被卸载 → 然后重新挂载
2. `useEffect` 重新执行
3. 此时 `latestRun` 从 Redux store 中读取，仍然是 `asyncState: "running"`
4. `fetchModuleTaskStatus` 执行一次，如果此时后端任务已完结 → 回填成功 ✅
5. **但如果用户很快又切走，这次 fetch 可能也被丢弃，且没有下次机会**

**关键：缺少一个持续轮询的 interval。这里设计上是"单次检查"，不是"一直等到结束"。**

### 根因 3：ModuleRunPanel 的 onProgress/onEvent 回调在组件卸载后变成死引用

```ts
// ModuleRunPanel.tsx:3639-3643
const result = await runModule(
  definition,
  requestPayload,
  preferredRunMode,
  timeoutMs,
  (progress) => setAsyncRunProgress(progress),      // ← 如果组件卸载，setState 无效果但无警告
  (event) => setRecentEvents((prev) => [...prev.slice(-19), event]),  // ← 同上
  (taskId) => onTaskCreated?.(taskId, moduleKey, requestPayload),     // ← 这个每次都会执行
);
```

**`onTaskCreated` 调用的是 `WorkspaceShell.handleTaskCreated`，这不受 ModuleRunPanel 卸载影响**——它调用 dispatch（Redux store 是全局的）。所以：

- ✅ 异步任务提交成功 → taskId 一定写入 store
- ❌ `runModule` 后续轮询完成后的 `onRunDone()` → 如果 ModuleRunPanel 组件已卸载，`ModuleRunPanel.runWithPayload` 不会调到下面那行 `onRunDone(...)`

**这意味着：如果用户在 `runModule` 的 while 循环期间离开页面，`runModule` 返回时 `runWithPayload` 已经没人等了。**

**等等——async function 不会因为调用方组件卸载而中断。** `runModule` 的 while 循环会继续执行，轮询会继续，直到超时或完成。但是 `runWithPayload` 中的 `await runModule(...)` 之后的代码（`setResponseData`, `onRunDone`）**会执行**，这些 setState 在卸载组件上是无害的，`onRunDone` 调用 dispatch，**实际上仍然会写入 store**。

让我重新审视这个问题。实际上 `async/await` 不绑定在组件生命周期上：

```ts
const runWithPayload = async (requestPayload: unknown) => {
    setLoading(true);
    setError(null);
    const result = await runModule(...)   // ← 这个 Promise 独立于组件存活
    // 以下代码在组件卸载后仍会执行：
    setResponseData(result.response);     // ← React 静默忽略（已卸载）
    onRunDone({ ... });                    // ← dispatch → store ✅ 仍生效
  };
```

**所以 `onRunDone` 中的 `dispatch(append_run)` 实际上会执行。** 但有一个微妙的问题：

`onRunDone` 的闭包捕获了 `taskSpace.id` 等局部变量，这些变量在组件卸载后仍然有效（闭包持有引用）。

**那么真正的断点在哪里？**

回到 `ModuleRunPanel`，如果用户切换到了**另一个 taskSpace 的页面**（比如跳转到 `/tasks` 再打开另一个任务），`WorkspaceShell` 会为**新的 taskSpace** 挂载一个新的实例。`runModule()` 的轮询仍在后台运行，完成后调用 `onRunDone`，dispatch 写入的是**旧 taskSpaceId 的 run**。这部分的 store 数据仍然是正确的。

**真正会中断的是：用户在当前 taskSpace 内切换到其他标签页（Details/Report/docs/terminal），然后 `ModuleRunPanel` 组件被条件渲染隐藏了。**

检查 renderTabSurface():

```tsx
if (activeTab === "details") {
  return <StageSplitView ... />;           // ← 包含 ModuleRunPanel
}
// activeTab !== "details" → StageSplitView 被卸载
// → ModuleRunPanel 被卸载
// → runWithPayload 的 setState 无效
// → 但 runModule 的 while 循环仍在后台运行
// → 最终 onRunDone dispatch 仍然生效
```

**所以如果用户只在同一 WorkspaceShell 内切换标签，异步任务不会被真正中断。** `runModule()` 在后台继续运行，最终结果通过 `dispatch` 写入 store。

### 根因 4：SSE 连接断开且无自动重连

```ts
// useTaskEvents.ts:71-96
function connectSSE(taskId: string): EventSource {
  const es = new EventSource(`/api/v1/events/task/${taskId}/stream`);
  es.onmessage = (e) => { ... };
  es.onerror = () => {
    es.close();
    eventSources.delete(taskId);     // ← 直接从全局 Map 中删除
  };
  return es;
}
```

**SSE 连接在 `onerror` 时直接关闭并删除，没有重连逻辑。** 浏览器在以下情况触发 EventSource 的 error 事件：
- 网络断开
- 服务器关闭了连接
- **页面被隐藏/进入后台**（某些浏览器行为）
- 连接超时

实际上浏览器内置的 EventSource 有自动重连机制——它会在连接断开后自动重试。但这里的代码在 `onerror` 中手动 `es.close()` 并删除引用，**阻止了这个内置重连**。

### 根因 5：`useTaskEvents` 的 SSE 回退到轮询的时机问题

```ts
// useTaskEvents.ts:156-161
const fallbackTimer = setTimeout(() => {
  const buffer = eventBuffers.get(taskId);
  if (!buffer || buffer.length === 0) {
    pollingCleanup.current = startPolling(taskId, 0);
  }
}, 3000);
```

**只有 3 秒内 SSE 没收到任何事件时，才回退到 HTTP 轮询。** 如果 SSE 已经收到了若干事件后断开，缓冲区不为空 → `startPolling` 不会被触发 → 后续事件永久丢失。

## 完整的断点总结

| 场景 | runModule() 轮询 | onRunDone dispatch | SSE 事件流 | useTaskEvents 轮询 | fetchModuleTaskStatus |
|------|:---:|:---:|:---:|:---:|:---:|
| 同 WS 切换标签 | ✅ 继续 | ✅ 仍写 store | ✅ 全局 Map 仍在 | ⚠️ SSE 断后不回退 | ❌ 只调一次 |
| 切到/tasks 页面 | ✅ 继续 | ✅ 仍写 store | ⚠️ 浏览器可能断 SSE | ⚠️ SSE 断后不回退 | ❌ WS 卸载了 |
| 切到/reports | ✅ 继续 | ✅ 仍写 store | ⚠️ 同上 | ⚠️ 同上 | ❌ WS 卸载了 |
| 刷新页面 | ❌ JS 全销毁 | ❌ | ❌ | ❌ | ❌ |
| 关闭浏览器 | ❌ | ❌ | ❌ | ❌ | ❌ |

**核心矛盾：前端是 SPA，"执行中"的状态只在内存中，没有持久化到可以跨页面追踪的机制。**

后端任务在服务器上正常运行（由 `TaskManager` 线程池管理），但前端在切换页面后：
1. `runModule()` 的 while 循环虽然仍在后台运行，但**无法通知用户**（组件已卸载）
2. `useTaskEvents` 的 SSE 可能断开且不回退
3. `fetchModuleTaskStatus` 的 useEffect 只在挂载时触发一次

---

## 修复方案

### 策略：全局任务注册表 + 持续心跳轮询

核心理念：**把"正在执行的任务"提升到全局层（Redux/app-store），让轮询不依赖任何具体组件。**

不需要改动后端。

#### 改动 1：`runModule()` 不依赖组件卸载/挂载

在 `runModule()` 执行期间绑定一个 `AbortController`，外部可以通过 abort 中断。但同时确保在 SPA 路由切换时**不 abort**——即 `runModule()` 变成一个"fire and forget"风格的全局后台任务。

#### 改动 2：全局轮询心跳（在 App 级别）

在 `App.tsx`（或一个全局 Provider）中加一个 `useEffect`：

```ts
// 全局轮询：遍历 store 中所有 isRunInProgress 的 run，逐个 check status
useEffect(() => {
  const interval = setInterval(() => {
    const runningRuns = store.runs.filter(isRunInProgress);
    for (const run of runningRuns) {
      fetchModuleTaskStatus(findModule(run.module), run.asyncTaskId)
        .then(status => {
          if (isFinal(status.state)) {
            dispatch(update_run_result(...));
          }
        })
        .catch(() => {});
    }
  }, 5000);  // 每 5 秒全局检查一次
  return () => clearInterval(interval);
}, []);
```

这意味着无论用户在哪个页面，只要 `store.moduleRuns` 里有一条 `asyncState: "running"` 的记录，全局心跳就会每 5 秒去后端问一次"做完了没"。完成了就更新 store。

**需要防范的问题：**
- 多条 running 记录并发请求 → 每轮只需要 Promise.allSettled
- 任务已完成后不再轮询 → `filter(isRunInProgress)` 保证
- 页面刷新后恢复 → 挂载时检查一次 store（配合 `fetchMyTasks` 的后端历史任务列表）

#### 改动 3：SSE 自动回退修复

```ts
// useTaskEvents.ts — 修复 onerror
es.onerror = () => {
  // 不关闭，让浏览器内置重连机制工作
  // EventSource 默认会自动重连
};

// 3 秒 fallback 计时器改为：SSE 断开时启动轮询
// 用 EventSource.readyState 判断
```

但更简单的做法是：有了全局轮询心跳（改动 2），**SSE/useTaskEvents 的轮询回退就不那么关键了。** SSE 是用于"实时展示 Timeline 细节"，全局心跳是用于"保证任务状态最终一致性"。两者互补。

#### 改动 4：页面刷新后的恢复

如果用户刷新了页面：
1. `App.tsx` 挂载
2. 全局轮询心跳检查 `store.moduleRuns` → React state 初始化为空
3. `app-store` 初始化时调用 `fetchMyTasks()` → 获取后端历史任务列表
4. 如果某个任务 `state: "running"` → 全局心跳开始轮询它
5. 如果某个任务 `state: "completed"` → 已完结，不需轮询

当前 `app-store` 初始化已经有 `fetchMyTasks()`，但只用于构建 `WorkspaceState` 恢复（把后端任务映射到前端 taskSpace）。**需要额外一步：把 `running` 状态的任务标记到 `moduleRuns` 中**，这样全局心跳才能接手。

#### 改动 5：WorkspaceShell 的 onRunDone 无需改动

当前 `onRunDone` 通过 dispatch 写入 store 后，如果全局心跳发现同一任务的 state 已变为终态，它会调用 `append_run` 更新，`app-store` 中的 merge 逻辑（已有）会合并现有字段。

## 执行优先级

| 优先级 | 改动 | 效果 |
|--------|------|------|
| **P0** | 全局轮询心跳 | 解决"切到其他页面回来状态不更新"的核心问题 |
| **P1** | 页面刷新恢复（running 任务注入 moduleRuns） | 刷新后继续追踪 |
| **P2** | SSE 错误处理修复 | Timeline 实时事件不再中断 |
| **P3** | AbortController | 用户能主动取消任务 |
