# 2026-06-05 Codex 错误记录

## 本次错误

### 1. 没有先确认任务目标，错误地把问题往产品统计链上延伸

错误表现：
- 在用户明确讨论的是“错误排查表”和“经验沉淀文档”时，先把话题延伸到 `risk统计 / evidence计数 / KPI汇总`。
- 这是把工程排错文档误当成产品运行时数据，属于目标理解错误。

根本原因：
- 没有先区分“这份内容是业务数据，还是修复过程文档”。
- 在没有确认用途前，按常见产品化思路继续外推，属于牵强附会。

后续要求：
- 先确认对象类型：
  - 是产品输入/输出
  - 还是开发排查文档/经验记录
- 未确认前，不得把排查文档自动解释为要进入统计链、指标链或业务状态机。

### 2. 没有第一时间坚持从源头定位，而是先讨论前端兼容

错误表现：
- 当用户问“为什么会出现很多 `|`、为什么没显示成表格”时，先从前端预览兼容角度展开。
- 虽然前端兼容可以缓解现象，但不是用户当前要的根治方案。

根本原因：
- 没有把“谁生成了错误格式”作为首要问题。
- 没有优先锁定唯一正确输出源，而是先讨论显示层补救。

源头问题的正确定位：
- BCR 后端在生成 `detailed_findings` 时，输出了“像表格的管道文本”，而不是标准 Markdown 表格。
- 这是根因。
- 前端是否兼容，只能算兜底，不是主修复点。

后续要求：
- 先找源头：谁生产了错误数据结构/错误格式。
- 优先修正生产者输出。
- 显示层兼容只能作为次级措施，且必须明确标注为兜底，不得冒充根治方案。

## 本次应遵守但未严格遵守的方法

1. 先澄清“目标是什么”，再给方案。
2. 先定位“错误是谁生产的”，再决定修哪一层。
3. 如果用户问的是根因，就不能先给表现层修法当主答案。
4. 不准为了让回答显得完整，就把问题强行扩展到用户没要求的方向。

## 后续执行约束

- 遇到类似问题，先回答：
  - 这是什么对象？
  - 当前目标是什么？
  - 根因在哪一层产生？
- 若根因在后端输出，优先修后端。
- 若只是临时排查文档，按工程文档处理，不得擅自产品化解释。
- 不准对用户意图做“合理但未经确认”的延伸解释。

### 3. 没有先区分“后端权威输出”与“前端 fallback 重建”，导致错误接受规则驱动分行

错误表现：
- 在后端已经可以直接输出章节正文和标准 markdown 表格的前提下，没有先把这类内容标记为权威输出。
- 继续让前端统一经过 `normalizePipeTables()`、`explodePackedLine()`、`classifyLine()`、`lineKind()` 这一整套规则驱动改写链。
- 结果是把“兜底修复逻辑”错误地施加到了“正常输出路径”上。

根本原因：
- 没有先建立内容来源分层：
  - canonical：后端直接生成、应原样信任的正文
  - fallback：前端基于残缺响应临时重建的内容
- 没有把结构修复逻辑限定在 fallback 路径内。

正确原则：
- 后端权威输出只允许做轻量规范化：
  - `\r\n -> \n`
  - markdown 基础空格修正
  - inline citation 增强
- 任何会改变结构语义的逻辑：
  - 猜表格
  - 规则拆行
  - 标题/列表重分类
  - 段落重组
  只能保留在 fallback 路径，不能默认施加到 canonical 输出。

后续要求：
- 先判断内容来源，再决定是否允许结构改写。
- 不得把 fallback 修复器当成通用渲染前置步骤。
